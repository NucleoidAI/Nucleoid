# NUC 86 -- Is and Is Not Comparisons

```
NUC: 86
Title: Is and Is Not Comparisons
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 06-Nov-2026
Requires: 44, 45, 59, 63, 65
```

## Abstract

- Add `is` and `is not` as spellings of `==` and `!=` for matching
  primitives and properties: `if value is "EXACT":`, `if value is 'EXACT':`,
  `if value is EXACT:` and `if order.status is not SHIPPED:`.
- They have the loose equality, precedence and left associativity of `==`
  and `!=`, so `count is 3`, `ready is true` and `a.x is b.x` mean
  `count == 3`, `ready == true` and `a.x == b.x`.
- Quotes are optional around a word. A quoted right operand is an ordinary
  string in either quote. When the whole right operand is one bare
  identifier, it is a *word*: it reads the variable, local, class, function
  or built-in of that name when one exists, and otherwise compares with the
  text of its spelling. So `value is EXACT` matches `"EXACT"` until something
  defines `EXACT`.
- A word records a dependency on its variable even while nothing defines it,
  so every declaration, `if` rule and class-level rule that compares with it
  re-evaluates when that variable is defined, changed or deleted.
- `is` stays an ordinary identifier, and no token, keyword or error message is
  added. It is an operator only directly after a complete operand in an
  enclosed position: conditions, parentheses, call arguments, lists, object
  values, subscripts, `?` consequents, Python-style conditions and the like.
  Where a statement can follow, it keeps its accepted reading as a name that
  begins the next juxtaposed statement, so `flag = value is "EXACT"` is still
  three statements and the comparison is written `flag = (value is "EXACT")`.
- Every program that parses at the accepted revision keeps that parse: the
  operator applies only when the whole program would otherwise fail to parse.
  Only inputs that were errors at the accepted revision change.
- The authoritative contract is
  [Is and is not comparisons](../nucleoid.spec.md#is-and-is-not-comparisons).

## Motivation

- World models are full of symbolic states: an order is `SHIPPED`, a task is
  `DONE`, a light is `RED`. Rules match them constantly, and the natural
  reading is a sentence: *if the order's status is shipped*. The user asked
  for exactly that: `is` equivalent to `==`, usable for any primitive or
  property match, with quotes optional when comparing with a string.
- At the accepted revision none of the three requested spellings parses.
  `if value is "EXACT":`, `if value is 'EXACT':` and `if value is EXACT:` each
  raise `SyntaxError("Expected ':' but found identifier 'is'")` at line 1,
  column 10, and `x = (value is 1)` raises
  `SyntaxError("Expected ')' but found identifier 'is'")`.
- `==` with a quoted constant is the accepted way to write the match. A bare
  constant needs a declaration first: `value == EXACT` raises
  `ReferenceError("EXACT is not defined")` until `EXACT = "EXACT"` exists.
- With `is`, a model can name its states as words and decide later whether a
  word is just its text or a variable that remaps it. Defining
  `SHIPPED = "SENT"` re-evaluates every rule that compares with `SHIPPED`;
  deleting it returns the word to its text.
- Language models write `is` naturally in conditions, as Python, CoffeeScript
  and SQL programmers do; conditions such as `if order.status is SHIPPED:` now
  parse.

```
value = "EXACT"
if value is "EXACT":
    double = "match"
if value is 'EXACT':
    single = "match"
if value is EXACT:
    bare = "match"
if value is not OTHER:
    other = "differs"
assert(double, "match")
assert(single, "match")
assert(bare, "match")
assert(other, "differs")
```

## Rationale

- **Category and mode.** The user requested this concrete feature, so its
  category is the confirmed Syntax enhancement with no random draw, and the
  request runs in single-proposal mode, which skips token comparison. Its
  primary purpose is a new spelling and a word rule for matching. Prior art
  such as CoffeeScript's `is`, AppleScript's `is` and SQL's `IS` does not move
  it to Language compatibility: Python's `is` means identity, and this `is`
  means `==` by request.
- **Equality, not identity.** `is` is `==` and `is not` is `!=`, as asked,
  with the same loose equality, so `count is "3"` is true where Python's
  identity test would be false. Rejected: strict `===`, which CoffeeScript
  uses, and Python identity, which would compare objects by reference only.
- **`is` stays a name.** At the accepted revision `is` is an ordinary
  identifier: `is = 5`, `def is(x) => x`, `def f(is) => is`, `{is: 1}`,
  `a.is`, `is: int` and `for is in xs:` all parse. Making it a keyword would
  break them, so the lexer is unchanged and the parser recognizes `is` only
  where it follows a complete operand.
- **Enclosed positions only.** Statements may be juxtaposed without
  separators: `a = 1 b = 2` is two statements. So at statement level
  `value is "EXACT"` is already the three statements `value`, `is` and
  `"EXACT"`; with `is = 3`, `value = 1` and `value is 4` it returns `4`. The
  same holds wherever an expression may end a statement: assignment values,
  `return`, `throw` and `delete` operands, arrow, lambda and quantifier bodies
  at statement level, conditional operands at statement level, a named arrow
  body, the second operand of `assert:` and the top level of a template
  interpolation, whose trailing tokens are ignored, so
  `` `${a is 1}` `` renders `a`. Those inputs keep their accepted reading.
  Everywhere an identifier cannot follow a complete operand at the accepted
  revision, such as before a header's `:`, a `)`, a `]`, a `,` or a `}`, the
  accepted parser raises a syntax error, and `is` becomes the operator there.
- **Accepted readings win.** Some statements parse tentatively and fall back
  to another reading when the attempt fails: `while` headers, `suppose`
  premises, Python-style conditions and destructuring declarations. With the
  operator, an attempt can succeed where it failed before, while the accepted
  fallback also parses. `while v is x: T` is `while`, `v`, `is` and the
  declaration `x: T` at the accepted revision, and is also a loop under the
  operator. So the parser reads every program with the accepted grammar
  first and keeps that result when it succeeds. Only when it fails does it
  read the program again with the operator. Every accepted input therefore
  keeps its parse by construction, and only inputs that were errors change.
- **Equivalent spellings stay equivalent.** NUC 32 defines an indented named
  arrow body, `def same(value) =>` with `value` on the next line, as exactly
  `def same(value):` with `return value`, and the executable documents are
  checked against that rewrite. `return` is a statement-level position, so the
  indented body is one too: `def same(value) =>` with `value is EXACT` on the
  next line keeps its accepted syntax error, and `(value is EXACT)` is written
  in both spellings. Other pairs stay equal because both sides are enclosed or
  both are at statement level, such as `if a is b:` and its colon-free form,
  `else a is b:` and `else if a is b:`, `assert: a is b, c` and
  `assert(a is b, c)`, and `->` and `=>`. Where one spelling of a pair was
  already a syntax error at the accepted revision, that spelling may now
  compare while the other keeps its statement reading:
  `assert(c, a is b)` beside `assert: c, a is b`, and `f = (x) => (x is 1)`
  beside `f = lambda x: x is 1`.
- **Headers that also read as statements.** In a program read the second way,
  a `while` header or `suppose` premise that needs the operator, and whose
  tokens also parse through its colon as the accepted separate statements,
  still takes the accepted reading. So `while v is x: T` means the same in a
  program on its own and beside an unrelated `if a is b:`. In
  `while state is not DONE:` with an indented body, the separate reading
  fails at the colon, so the loop takes the operator, while
  `while v is suppose:` with a body reads as `while`, `v`, `is` and a
  `suppose` block and keeps that reading. Python-style conditions and
  destructuring need no such check: their fallbacks are errors whenever the
  operator is needed.
- **The word rule.** The user chose *variable, else text* for a bare word.
  A word reads like any name when one of that spelling exists: a local such
  as a parameter, a variable, a class, a function or a built-in global such
  as `Math`. Then `is` is exactly `==`. Only when nothing of that name exists
  does it compare with its own text. Rejected: always text, which could not
  name a variable without parentheses, and checking only variables, which
  would make `kind is Order` compare a string where `kind == Order` compares
  the class.
- **What is a word.** Only a right operand that is one bare identifier token.
  Keywords keep their meaning, so `ready is true` and `value is null` compare
  with the literals and `value is this` reads the receiver. `$Class` is a
  class reference. Paths, calls, subscripts, versions, operator expressions
  and parenthesized operands read as with `==`, which makes `value is (EXACT)`
  the explicit way to require a defined name. Rejected: treating the left
  operand as a word, which would hide a misspelled subject.
- **Declarative consistency.** A word reads its variable when it is defined,
  so a rule must also follow a variable that does not exist yet. The graph
  already files a pending node for any name read before it is defined, so a
  word records the dependency through the existing tracking even while it
  reads as text. Defining the variable wakes its readers, and deleting it
  wakes them again through the existing deletion cascade, after which the
  word reads as text. No new propagation path is added, and propagation stays
  the bounded worklist it was.
- **Class-level rules.** Declaring a class-level rule rejects undefined names
  it reads. A word is not a required name, so `$Order.shipped =
  ($Order.status is SHIPPED)` is accepted while `SHIPPED` is undefined, and
  `($Order.status is (SHIPPED))` still raises
  `ReferenceError("SHIPPED is not defined")`.
- **Rendering and graph keys.** Standing `if` rules and class-level
  conditions are keyed by their rendered condition. Other aliases render
  canonically, as `and` renders `&&` and `elif` renders `else if`, so a
  quoted or otherwise ordinary `is` renders as `==` and
  `if value is "EXACT":` is the same standing rule as
  `if value == "EXACT":`. A word comparison differs from `value == EXACT`
  while `EXACT` is undefined, so it renders as `(value is EXACT)` and has its
  own key; `why` shows it in that form.
- **One binary operator.** A word comparison is the existing `Expr::Binary`
  with the new `BinaryOp::Is` or `BinaryOp::IsNot` and an identifier right
  operand. Every expression walker already visits both operands of a binary
  node, `.value` freezing keeps the operator, and the protected-assertion
  walker needs no change. Only parsing, the word read, static validation and
  rendering change. Rejected: a new `Expr` variant, which would touch every
  walker; lowering to `==` with a string, which would lose the variable and
  its dependency; and always producing `BinaryOp::Is`, which could not tell
  `value is EXACT` from `value is (EXACT)` because grouping is not kept in the
  syntax tree.
- **Diagnostics.** No message is added. A malformed `is` raises what its `==`
  or `!=` spelling raises in the same place, for example
  `SyntaxError("Unexpected ':'")` for `if value is:`. A program that fails
  both readings reports the accepted error unless the reading with the
  operator got further, so an input without `is` reports exactly what it did.
- **Precedence.** `is` and `is not` join the equality level, so they bind
  like `==` and `!=`: `a is b < c` is `a is (b < c)` and `not a is b` is
  `(not a) is b`, as `not a == b` is. Writing `value is not EXACT` or
  `not (value is EXACT)` negates the comparison. The right operand of
  `is not` starts after `not`.

## Specification

### Syntax

- `is` is not a keyword or token kind. In the equality loop, an identifier
  token spelled `is` is an equality operator when all of these hold:
  - the program, or the expression given to `parse_expression`, failed to
    parse with the accepted grammar, and is being read a second time;
  - it directly follows a complete operand;
  - the expression is in an enclosed position, listed below;
  - it is not, inside an object-literal value, directly followed by `:`,
    which keeps it the next comma-free property key (NUC 44).
- A following `not` keyword makes it `is not`. The right operand is a
  relational expression, as for `==`.
- Enclosed positions:
  - inside parentheses, call arguments including `super(...)` and
    `depth(...)`, list items, object-literal values and spreads, subscripts
    and slice bounds;
  - the condition of `if`, `elif`, `else if` and a direct alternative, with
    or without its colon, the condition of `while`, the source of `for`, the
    collection of a quantifier, the consequent after `?` and a Python-style
    condition;
  - the first operand of an `assert:` statement;
  - an arrow, lambda or quantifier body, an assignment value or a
    conditional alternate written in one of these positions.
- Every other position keeps the accepted reading, in which `is` is a name
  that begins the next statement: expression statements, assignment, compound
  assignment, destructuring and `:=` values, `return`, `throw` and `delete`
  operands, a named
  arrow body on the same line or on its own indented line, the second operand
  of `assert:`, the top level of a template interpolation and of
  `parse_expression`, and any arrow, lambda or quantifier body, operand before
  `?` or operand around a Python-style condition at statement level.
- In a program read the second time, a `while` header or `suppose` premise
  that parses only with the operator keeps the accepted reading when its
  tokens, read with the accepted grammar from the header, parse as separate
  statements through the statement that contains its colon.
- A word is a right operand of exactly one identifier token. Every other
  right operand, including a keyword, `$Class`, a path, a call, a subscript,
  a version, an operator expression or a parenthesized operand, is ordinary.

### Semantics

- `left is right` evaluates `left`, then `right`, and compares them as
  `left == right` does; `left is not right` is `left != right`.
- A word is read by its name when a local, a variable, a class, a function or
  a built-in global of that name exists, as an identifier is. Otherwise its
  value is the string of its spelling, and it records a dependency on the
  variable of that name.
- The left operand and every ordinary right operand read as they do with
  `==`, including `ReferenceError("<name> is not defined")` for an undefined
  name.
- A standing declaration, `if` rule or class-level rule that compares with a
  word re-evaluates when the variable of that name is defined, changed or
  deleted, including inside a `suppose` block, whose rollback restores it. A
  `while` condition or a function body reads the word each time it runs.
  While the variable is undefined, its name is a pending graph node: `why`
  lists it among the sources and `affects` of the pending name lists nothing
  until it is defined.
- Static class-rule validation does not require a word to be defined; it
  still requires every other name.
- A word comparison renders as `(left is word)` or `(left is not word)`. Every
  other `is` renders as `==` or `!=`.
- Errors raised while evaluating either operand propagate through the existing
  transaction, so a failed standing re-evaluation triggered by defining a word
  rolls back that definition.

```
value = "EXACT"
flag = (value is EXACT)
miss = (value is not EXACT)
assert(flag, true)
assert(miss, false)
EXACT = "OTHER"
assert(flag, false)
assert(miss, true)
value = "OTHER"
assert(flag, true)
delete EXACT
assert(flag, false)
assert(miss, true)
```

```
class Order(status, total):
    this.status = status
    this.total = total
$Order.shipped = ($Order.status is SHIPPED)
$Order.open = ($Order.status is not SHIPPED)
first = Order("SHIPPED", 0)
second = Order("PENDING", 30)
assert([first.shipped, second.shipped], [true, false])
SHIPPED = "PENDING"
assert([first.shipped, second.shipped], [false, true])
```

```
statuses = ["SHIPPED", "PENDING", "SHIPPED"]
shipped = statuses.filter(s => s is SHIPPED)
pending = statuses.filter(lambda s: s is not SHIPPED)
mode = "FAST"
speed = 10 if mode is FAST else 1
label = (mode is FAST) ? "fast" : "slow"
everyone = (all s in statuses: s is SHIPPED)
assert(shipped.length, 2)
assert(pending, ["PENDING"])
assert(speed, 10)
assert(label, "fast")
assert(everyone, false)
```

```
is = 4
value = 1
result = value is 4
assert(result, 1)
same = (value is 1)
assert(same, true)
```

### Compatibility

- Every program that parses at the accepted revision keeps its parse,
  syntax tree, rendering, result and runtime errors, because the accepted
  grammar reads it first and that result is kept. This includes every
  juxtaposed reading above, `while v is x: T`, `while v is assert: a, b`,
  `while v is suppose:` with a body, `suppose v is x: T`,
  `x = {k: 1 is: 2}` and `` `${value is 4}` ``.
- Only inputs that failed to parse at the accepted revision change: they now
  parse, or report a different syntax error.
- The public `BinaryOp` enum gains `Is` and `IsNot`. Exhaustive downstream
  matches stop compiling, so this needs human SemVer review. No project
  version is changed.
- The public `parse_expression` and `parse_expression_with_options` return a
  comparison for input such as `(a is b)`, which they rejected. They still
  return `a` for `a is b`, whose trailing tokens they ignore.
- The native REPL needs no change. Its header scans are lexical, so
  `if value is EXACT` buffers its colon-free indented body as any other
  condition does.

- No new error type or message is added. Malformed uses report the existing
  parser diagnostics of their `==` and `!=` spellings, and runtime errors come
  from the operand that raised them.
- These inputs failed to parse and now parse. Each source is the whole
  program, followed by a newline:

- A program that fails both readings reports the error of the reading that
  got further, and the accepted error when they stop at the same place. So
  `x = (1 + )`, without a final newline, still reports
  `SyntaxError("Unexpected ')'")` at line 1, column 11, and `while v is X:`
  with an indented `a = 1` followed by `x = (1 + )`, without a final newline,
  now reports that error at line 3, column 11 instead of
  `SyntaxError("Unexpected ':'")` at line 1, column 13.
- An undefined left operand or ordinary right operand raises
  `ReferenceError("<name> is not defined")` when it is evaluated, as with
  `==`: `flag = (value is (EXACT))`, `flag = (EXACT is value)` and
  `flag = (value is EXACT.size)` raise `ReferenceError("EXACT is not defined")`
  while nothing defines `EXACT`. A class-level rule raises it when declared:
  `$Order.bad = ($Order.status is (MISSING))` raises
  `ReferenceError("MISSING is not defined")`.
- At statement level the accepted runtime errors are unchanged: with `value`
  defined, `flag = value is "EXACT"` still raises
  `ReferenceError("is is not defined")` at the column of `is`, 14, unless `is`
  is defined, and `while v is x: T` still raises
  `ReferenceError("while is not defined")`.
- An accepted behavior that this NUC does not change also applies to words.
  An `if` statement in a block function body that runs while a declaration is
  evaluated stays filed as a standing rule, so a later change to a name its
  condition reads re-runs it outside the call, where its parameters are
  undefined. At the accepted revision, with `READY = "READY"`,
  `def label(v):` with `if v == READY:` and `return "go"`, then
  `return "wait"`, and `x = label("READY")`, the change `READY = "NO"` raises
  `ReferenceError("v is not defined")` and rolls back. With `if v is READY:`
  and `READY` undefined, the first `READY = "NO"` does the same. An
  expression body, `def label(v) => (v is READY) ? "go" : "wait"`, has no
  such statement and follows the word.

## Reference Implementation

- `src/lang/ast/mod.rs` adds `BinaryOp::Is` and `BinaryOp::IsNot`. No `Expr`
  variant, token or keyword is added.
- `src/lang/ast/parser.rs`:
  - `Parser::from_source` tokenizes a source and builds its parser for
    programs, `parse_expression` and template interpolations.
    `parse_program_with_options` and `parse_expression_with_options` parse
    with the accepted grammar first and keep a successful result. On a
    failure, when the source contains an `is` identifier or a template,
    `attempt` builds a fresh parser over the same tokens and options with the
    operator on and parses again, reporting the retry's error only when it is
    further than the accepted one.
  - An `enclosed` flag is set for parentheses, arguments, list items, object
    values and spreads, slice bounds, clause headers, Python-style conditions
    and the first `assert:` operand, cleared for every statement, and
    inherited by everything else.
  - The equality loop matches `==`, `!=`, `===` and `!==` as before and
    consults `word_comparison` only for any other token. It returns `Is` or
    `IsNot` only when the operator pass is on, the flag is set and the token
    is `is`, outside an object value's `is:` key. After the right operand, a
    single identifier token keeps the operator `Is` or `IsNot`; any other
    operand lowers to `Equal` or `NotEqual`.
  - The `while` and `suppose` attempts, in the operator pass, keep the
    accepted reading when the accepted attempt fails and the tokens from the
    header parse as separate statements through the colon. These checks run
    the accepted grammar on a separate probe parser. The probe borrows the
    tokens, copies the position, depth, context, `enclosed` flag and options,
    and starts with the operator off and empty memos, so the parser being
    checked keeps its own position, flags and memos. The memo keys and the
    first pass are unchanged.
  - Template interpolations are parsed in the pass of their program.
  - The unit test
    `word_headers_consult_the_accepted_grammar_without_changing_the_parser`
    checks the `while` and `suppose` readings these checks choose, and that
    the parser's position, depth, context, flags, tokens and unrelated memos
    are unchanged afterwards.
- `src/lang/ast/identifier.rs` splits the existing name lookup into
  `read_bound`, shared by `read_identifier` and the new `read_word`, which
  tracks the variable key and returns the word's text when nothing binds it.
  `read_identifier` reads its scope through a shared reference.
- `src/lang/ast/operator.rs` reads a word right operand of `Is` and `IsNot`
  through `read_word`, compares `Is` as `Equal` and `IsNot` as `NotEqual`,
  and spells them `is` and `is not`.
- `src/lang/ast/generator.rs` renders `(left is right)` and
  `(left is not right)`, and its `**` grouping rules leave them as they are.
- The caller's Rust improvement pass made the `from_source`, fresh-parser,
  probe-parser, `word_comparison`, `**` grouping pattern and shared-scope
  changes above and added the unit test, without changing behavior.
- `src/expression.rs` leaves a word out of the names that class-rule

### Measured cost

- Measured with release builds of the accepted and candidate libraries,
  timing `Runtime::check` alone; each figure is the median of 15 runs on the
  development machine.
- A program that parses at the accepted revision is read once, as before:
  1,000 to 8,000 lines take 3.0, 6.0, 12.6 and 25.8 ms on the accepted
  library and 2.9, 6.0, 12.3 and 25.7 ms on the candidate. A failing program
  without `is` is also read once and takes the same time.
- Apart from the header checks below, the second reading costs at most one
  more parse. The worst case is a program that fails only at its last lines
  because of `is`: 1,000 to 8,000
  lines take 4.2, 8.7, 18.5 and 37.1 ms, against 3.2, 6.3, 13.1 and 26.0 ms
  for the single reading at the accepted revision, so the cost stays linear
  in the program's size.
- A `while` or `suppose` header that needs the operator re-reads its own
  tokens up to the colon. 250 to 2,000 headers such as
  `while v is not DONE:` take 0.8, 1.7, 3.3 and 6.8 ms, against 0.4, 0.9, 1.5
  and 3.6 ms for the same headers written with `!=`.
- A header whose separate reading also parses past its colon re-reads the
  statement that contains it. So `while v is suppose:` headers nested D deep
  around B statements re-read up to D times B statements, and the nesting
  limit caps D at 64. D = 30 and D = 60 around 2,000 statements take 28.3 and
  50.2 ms, against 2.4 and 3.4 ms for the same programs without a line that
  needs the operator. Nested `while v is not DONE:` headers stay small:
  60 levels around 200 statements take 0.55 ms.

## Evaluation

- **Outcome: Accepted.** The user requested this one feature directly, so it
  ran as a single proposal. The user also made two choices: a bare word reads
  as a *variable, else text*, and `is not` is added. All three hard criteria
  passed in the independent evaluation and again on the integrated tree, so
  the user-requested acceptance basis applies. The independent decision is
  also Accepted.
- **Independent decision: Accepted**, with non-blocking findings and no
  blockers. The deterministic core reported `accepted` with no issues. It
  replayed all 977 accepted cases and passed all 984 candidate cases.
- **Medium finding: a later class declaration does not wake a word.** A word
  that reads as text tracks only the pending variable of its name. Declaring
  a class of that name later therefore does not re-run the rules that compare
  with the word. A later variable or `def` of that name does re-run them.
  - With `k = "Order"`, `flag = (k is Order)` and then `class Order:` with
    `pass`, `flag` stays `true`. Meanwhile `(k is Order)` now reads the class
    and is `false`. An `if k is Order:` rule behaves the same way.
  - This contradicts no promise here: the Semantics section promises
    re-evaluation only for the variable of the word's name.
  - Accepted `==` has the same blind spot for a name that changes kind. After
    `x = Math`, `flag = (x == Math)` and `Math = 5`, `flag` stays `true` on
    both revisions.
  - No executable case covers this behavior.
- **Low finding: one header choice depends on its block.** In a program read
  the second way, a `while v is suppose:` header keeps its separate-statement
  reading only when its whole `suppose:` block parses without the operator.
  - Take `v = 1`, then `while v is suppose:` with the body
    `w = (v is 1)`, then `v`. Here the header becomes a loop and the program
    returns `1`.
  - This follows the rule in Syntax. It does not match the Rationale's
    sentence that such a header keeps that reading.
  - Only inputs that were syntax errors at the accepted revision are
    affected.
- **Low finding, diagnostics only: the further-error choice can pick a stale
  error.** The choice compares positions inside a template, which are
  relative to the `${...}` text by default, with program positions.
  - For `a = 1`, `if a is 1:` and `` c = `${(a is }` ``, the program reports
    the accepted error `Expected ':' but found identifier 'is'` at line 2,
    column 6, on a line the second reading accepts.
  - With `--c-style-comments` it reports the template error at line 3,
    column 18.
  - This contradicts the sentence that the error of the reading that got
    further is reported.
- **By design, no action needed.** `return v is READY` returns `v`, because
  `is` stays a name where a statement can follow. The block-function `if`
  behavior in Errors matches `==`.
