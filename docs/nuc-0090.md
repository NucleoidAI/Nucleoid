```

Type: Standards Track

Created: 07-Nov-2026
Requires: 45, 54, 57, 65, 72, 81
```

## Abstract

- An enum declaration names a closed set of categories once:
  `enum Status: PENDING, PAID, SHIPPED` on one line, or `enum Status:`
  followed by an indented block with one member per line. A member may take
  a scalar literal value, as in `enum Level: LOW = 1, HIGH = 3`; a member
  without one holds its own name as a string.
- An enum declaration declares its name as `Status = {...}` would, with an
  object that holds the members in declaration order. Binding, standing and
  imperative contexts, locals, readers, redeclaration, `why`, `affects`,
  transactions and rollback are those of that declaration, and members read
  as ordinary properties.
- The enum's object is read-only. Assigning a member, adding a property or
  deleting one raises `TypeError("Enums are read-only")` through every write
  path and every name that holds the object, and rolls back its transaction.
  Binding the name to another value stays allowed.
- A declaration may start wherever a statement may start, except inside a
  class body, where every `enum` spelling keeps its accepted reading.
- `enum` stays an ordinary name and no token kind is added. The one-line form
  needs at least two members: `enum Status: PENDING` keeps its accepted
  reading, the name `enum` followed by the typed declaration
  `Status: PENDING`, and a single member uses the block form.
  `enum assert: ...`, `enum lambda: ...` and `enum suppose: ...` keep theirs
  too. Only inputs that were syntax errors at the accepted revision change.
- Canonical source writes `enum Status:PENDING,PAID,SHIPPED`, `why` rules
  show it, and it parses back to the same declaration.
- The public `Expr` enum gains `Expr::Enum(Vec<EnumMember>)`, and the public
  `ast` module gains the struct `EnumMember` with the fields `name` and
  `value`; they need human SemVer review, and no project version changes.
  Runtime applicability is `existing_comparable`, so the token
  non-regression gate applies. The authoritative contract is
  [Enum declarations](../nucleoid.spec.md#enum-declarations).
- **Outcome: Accepted.** The independent evaluation and the caller's
  integrated-tree checks passed all three hard criteria, and the independent
  evaluator decided Accepted with no defects and one low cost finding. The
  required token comparison ran in continuous mode: 11 cases use fewer
  tokens, 1,019 the same and none more. No policy check failed.

## Motivation

- World models classify. An order is pending, paid or shipped; a ticket's
  priority is low or high; a shirt is small, medium or large. Language
  models write these categories as enums in TypeScript, Java, C#, Kotlin,
  Swift and Rust, and as `Enum` classes in Python, and they compare
  attributes against the members in every rule.
- Accepted Nucleoid has no enum declaration.
  `enum Status: PENDING, PAID` raises `SyntaxError("Unexpected ':'")` at
  line 1, column 14, and the indented form raises it at line 1, column 12.
  TypeScript's `enum Status { PENDING, PAID }` raises
  `SyntaxError("Unexpected ','")`, Kotlin's `enum class Status { ... }`
  raises `SyntaxError("Expected ':' but found '{'")`, and Python's
  `class Status(Enum):` with member assignments declares a class, so
  `Status.PAID` reads `null`.
- The accepted spelling is an object of named constants,
  `Status = {PENDING: "PENDING" PAID: "PAID"}`. It repeats every member's
  name as its value, and nothing keeps the categories fixed:
  `Status.PAID = "SHIPPED"` redefines a category that every rule compares
  against and silently re-evaluates them all, `Status.PAYED = "PAYED"` adds a
  misspelled one, and `delete Status.PAID` removes one.
- An enum declaration states the categories once, gives each member its own
  name or a literal, and keeps the set read-only, while every rule that uses
  a member stays an ordinary property read.
- Each of the eleven new cases uses between 2 and 20 fewer lexer tokens than
  the most compact behavior-equivalent accepted program found for it.

## Rationale

- **Category and applicability.** The caller selected Runtime features by one
  tool-backed uniform draw over the five categories that NUC 1's registry
  marks eligible for automatic selection: index 1, with probability 1/5 and
  no redraw, in continuous mode. Enums are data modeling, which the
  registry places in this category. Runtime applicability is
  `existing_comparable`: objects of named constants are the accepted way to
  model categories, and every new case has a behavior-equivalent accepted
  counterpart that declares the same object with the same members, values and
  order and reads it the same way. The read-only rule, rendering and
  malformed declarations have no accepted counterpart and stay out of the
  measured cases. The token non-regression gate therefore applies.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial, reward or assessment.
- **The colon spelling.** Nucleoid introduces declarations and suites with a
  header colon, as in `class Name:` and `def name():`. An enum follows them:
  `enum NAME:`, with the members on the same line or in an indented block,
  the shape of Python's member lines.
  - Rejected for this proposal: the braced spellings of TypeScript, Java, C#
    and Kotlin, `enum Status { PENDING, PAID }`, which would add a second
    member syntax; they suit a later Language compatibility proposal.
  - Rejected: Python's `class Status(Enum):`, which already declares a class
    with a constructor parameter and must keep that meaning.
- **`enum` stays a name.** A keyword would break every accepted program that
  uses `enum` as a variable, property, object key or parameter. The
  declaration is recognized only from its tokens at the start of a
  statement.
- **Only former errors change.** Statements may follow one another without a
  separator, so the accepted parser reads `enum NAME: ...` as the name
  `enum` followed by a statement that starts at `NAME`. That statement is an
  error unless it is one of four accepted shapes: a typed declaration, one
  name after the colon before the end of the statement; an assertion
  statement, `assert: ...`; a `lambda`, `lambda: ...`; or a `suppose` block,
  `suppose: ...`. The recognizer leaves those four shapes alone, so every
  input it takes was a syntax error at the accepted revision. Tentative
  parses inherit this: wherever the accepted parser tries a loop condition,
  a premise, a destructuring value, a Python-style condition or a template
  interpolation, an enum shape inside a function body made the attempt fail
  and every fallback fail too.
- **Two or more members on one line.** The single-member line keeps its
  accepted reading, so the one-line form needs at least two members, and a
  single member uses the block form, which was always an error.
  - Rejected: a single member with a value on one line,
    `enum Level: LOW = 1`. It was a syntax error and could have become an
    enum, but a rule that one line holds two or more members, whatever their
    values, is simpler to state and to read. It raises a dedicated
    `SyntaxError` instead.
  - Rejected: trailing commas and several members on one line of the block
    form, which would give two spellings to one member list.
- **Scalar literal values.** A member's value is one of the scalar literals
  that [NUC 54](nuc-0054.md) admits as parameter defaults, so it is fixed when
  the declaration is parsed and the declaration reads nothing.
  - Rejected: expressions such as `HIGH = LOW * 2` or `RATE = base`, which
    would make an enum depend on state and change with it, the drift enums
    exist to prevent.
  - Rejected: lists and objects as values, which would put mutable values
    inside a read-only enum.
- **A member's default value is its name.** A member without a value holds
  its own name as a string, as TypeScript string enums and Python's `StrEnum`
  name theirs. It reads clearly in JSON, `why` output and comparisons with
  data from outside the model.
  - Rejected: automatic numbering, as TypeScript's numeric enums and
    Python's `auto()` do, whose values move when a member is inserted and
    read as unexplained numbers.
- **An ordinary declaration of an ordinary object.** An enum declaration is
  the declaration `NAME = {...}`, so it is filed, scoped, propagated,
  explained and rolled back by the paths every declaration uses, and its
  value is an object, so every accepted object operation applies to it.
  - Rejected: a new kind of value, which every built-in, comparison,
    serializer, loop and reasoning stage would have to learn.
  - Rejected: a constant binding. Models change, and declaring an enum again
    with new members is how its categories evolve; its readers follow.
- **Read-only members.** Categories that every rule compares against should
  not change behind those rules. Every write to an enum's object raises
  `TypeError("Enums are read-only")`, the shape of [NUC 53](nuc-0053.md)'s
  `State versions are read-only`, and the failed statement rolls back.
  - Rejected: ignoring writes, which hides the mistake.
  - Rejected: a message per write that names the target. One message for
    every write keeps the rule easy to recognize, and the error's position
    names the statement.
  - A spread `{...Status}` builds a new object, which is ordinary, so a
    model can derive a writable record from an enum. A copy that a `suppose`
    block's value carries out is the hypothetical world's enum, so it stays
    read-only. `delete Status` keeps the accepted rule for objects and raises
    `TypeError("Cannot delete object '<id>'")` while the object holds a
    property other than `id`.
- **Class bodies keep their readings.** In an indented class body,
  `enum Status: PENDING` is the constructor statement `enum` and the field
  `Status: PENDING`, which accepted programs run. A class body holds fields,
  methods and constructor statements, and an enum there would be declared
  again for every instance. Every `enum` spelling inside a class body,
  including its methods and nested suites, keeps its accepted reading;
  enums are declared beside the classes that use them.
- **Canonical rendering.** Canonical source writes `enum NAME:` followed by
  the members separated by commas, without spaces, as it writes `name:type`
  and `for key,value of source`, and leaves out a value that equals the
  member's own name. An enum with one member is written with the member on
  an indented line, because one member on the line would read as the typed
  declaration. The syntax tree keeps every member's value, so the rendering
  parses back to the same declaration.
- **A syntax tree value.** The parser builds
  `Stmt::Assign { target: Expr::Identifier(NAME), value: Expr::Enum(members) }`.
  Every statement walker, scope rule and filing path treats it as the
  assignment it is, and only the value says that the object is an enum.
  - Rejected: a `Stmt::Enum` statement, which every statement walker would
    have to learn although the declaration is an assignment.
  - Rejected: lowering the value to `Expr::ObjectLiteral`, which would lose
    the read-only rule in rendering and re-parsing.
- **Not added.** The braced spellings above; enums in class bodies; members
  with methods or properties of their own, such as `Status.PAID.name`;
  lookups from a value back to its member; helpers that list members, which
  entry loops already provide; type annotations such as `status: Status`;
  exhaustiveness checks; trailing commas; and enum expressions.

- Every new case is paired with the most compact behavior-equivalent accepted
  program found: the same document, title, canonical assertions in the same
  order and expected return, executed by the accepted runtime with every
  assertion running. The pairs are in the extra-baseline file recorded with
  the evaluation baseline.
- A counterpart keeps every line without an enum declaration byte for byte.
  It replaces each declaration with the declaration of the same object in
  the comma-free literal spelling of [NUC 44](nuc-0044.md), with the same
  members, values and order: `enum Status: PENDING, PAID` becomes
  `Status = {PENDING: "PENDING" PAID: "PAID"}`, and an indented enum becomes
  the same literal on one line. Member reads stay member reads; there is no
  constant or hand-evaluated substitution.
- A one-line declaration with `d` members without a value and `v` members
  with one uses `2 + 2d + 4v` lexer tokens, and its literal `4 + 3d + 3v`. An
  indented declaration followed by another line uses `6 + 2d + 4v`, and its
  literal with its line break `5 + 3d + 3v`. A signed number costs the same
  in both spellings, and the cases write no `+` sign, which a literal could
  drop.
- The new cases use no property selectors, noun queries, `:=`,
  destructuring, two-name loop headers, spreads, `is` comparisons,
  `this.name` parameters, `function` declarations or `depth`, `diff` and
  `path` stages, because whole-corpus suites admit each only in its own
  cases. When a one-line enum mixes members with and without values, its
  first member takes the value: the destructuring suite's scan treats a colon
  as the start of a statement, and a bare first member followed by a valued
  one, `A, B = 1`, would look like an unpacking to it. The language allows
  any order.

## Specification

### Grammar

```
enum NAME: MEMBER, MEMBER, ...
enum NAME:
    MEMBER
    MEMBER
```

- `enum`, `NAME` and every member name are identifiers. `NAME` is not
  `assert`, `lambda` or `suppose`.
- A member is a name, or a name, `=` and a scalar literal. A scalar literal
  is a finite number with an optional `-` or `+` sign, a string, `true`,
  `false` or `null`, including the lexer's `None` and `undefined` spellings
  of `null`.
- At the start of a statement, `enum NAME:` begins a declaration unless the
  rest of the statement is a single name followed by a line break, `;`, the
  end of an indented block or the end of the input. That shape keeps its
  accepted reading.
- One line: two or more members separated by commas, with no trailing comma.
  The last member is followed by a line break, `;`, a block's `}`, the end of
  an indented block or of the input, or `else` or `catch`.
- Indented: a line break after the colon, then an indented block with one
  member on each line, and at least one member. Blank lines may separate
  members. Nothing else may follow a member on its line.
- A member name may appear only once in a declaration.

### Where a declaration may start

- A statement starts at the beginning of the input, after a line break, `;`,
  an indentation change, a block's `{` or a suite's `:`, and after a complete
  statement on the same line. A declaration may therefore appear at the top
  level, in indented and same-line suites, in braced blocks, in the bodies of
  named, anonymous and arrow functions, in `try`, `catch` and `suppose`
  suites, and after another statement on the same line.
- Inside a class body, every `enum` spelling keeps its accepted reading: in
  its fields and constructor statements, in suites nested in them, and in its
  methods. The same-line class body of `class A: ...` and the statement that
  `class A(b):` adopts from the next line count as class bodies.
- Expressions never start a declaration, so `x = enum Status: A, B` and
  `f(enum Status: A, B)` keep their accepted errors.

### Semantics

- `enum NAME: ...` declares `NAME` exactly as `NAME = {...}` with the same
  members would: a standing declaration at the top level and in standing
  branches, a declaration carried out in a loop body or a function body, and
  a local when `NAME` is a parameter or loop variable of the running
  function or loop.
- The value is a new object whose properties are the members in declaration
  order. A member without a value holds its own name as a string, and a
  member with a value holds that literal.
- The declaration reads nothing. `why` lists it as stated, and no change
  re-evaluates it. Declaring the name again, as an enum or otherwise,
  replaces the binding and re-evaluates every reader. A failed transaction,
  a caught error and the end of a `suppose` block restore the earlier
  binding and its readers.
- Members are ordinary properties. `Status.PAID` and `Status["PAID"]` read a
  member; a missing member reads `undefined`, as a missing property does, so
  a declaration that reads it is `null` until a declaration of the enum adds
  the member. `typeof Status` is `"Object"`, assertions compare it as they
  compare any object, JSON serializes its members, and `==` compares
  identity.
- Entry loops `for name, value of Status:` visit the members in declaration
  order, and a spread `{...Status}` copies them into an ordinary object.

```
enum Status: PENDING, PAID, SHIPPED
assert(Status.PAID, "PAID")
assert(Status["SHIPPED"], "SHIPPED")
assert(Status, {PENDING: "PENDING", PAID: "PAID", SHIPPED: "SHIPPED"})
assert(Status.REFUNDED, null)
```

- Values are scalar literals, and the members keep their written order:

```
enum Level: LOW = 1, HIGH = 10
enum Size: LARGE = "XL", SMALL, MEDIUM, CUSTOM = null
enum Move: BACK = -1, AHEAD = 1
enum Flag: ON = true, OFF = false
assert([Size.SMALL, Size.LARGE, Size.CUSTOM], ["SMALL", "XL", null])
assert(Move.BACK + Move.AHEAD, 0)
```

- Readers follow a declaration of the enum again:

```
enum Plan: FREE, PRO
choice = Plan.TEAM
assert(choice, null)
enum Plan: FREE, PRO, TEAM
assert(choice, "TEAM")
```

### Read-only enums

- The object an enum declaration creates is read-only. Each of these raises
  `TypeError("Enums are read-only")`, placed at the start of the running
  top-level statement, and rolls back its transaction as every runtime error
  does, so the enum and its readers stay as they were:
  - a property declaration of a member or of a new property, such as
    `Status.PAID = "X"` or `Status.NEW = 1`, at the top level, in a block,
    branch, loop or function body, and in a standing branch when it runs;
  - compound assignments such as `Status.PAID += "X"` and `||=`;
  - value assignments such as `Status.PAID := "X"`;
  - assignment expressions such as `(Status.PAID = "X")` and their uses in
    arguments and lambda bodies;
  - `delete Status.PAID`, whether or not the member exists;
  - the list write-back of `push`, `append`, `pop` and `shift`, which
    evaluates a member receiver's object again when it writes, so
    `(flag ? Status : plain).items.push(flag = true)`, which reads
    `plain.items` while `flag` is false, writes to `Status` and raises;
  - each of these through any other name or property that holds the
    object, such as `s = Status` followed by `s.PAID = "X"`.
- A `catch` that handles the error keeps what it keeps for every caught
  error: an assignment expression that already ran in the failing
  statement, such as the argument `flag = true` above, keeps its write, as
  it does at the accepted revision when a later error in its statement is
  caught.
- A copy that a `suppose` block's value carries out of the block is
  read-only too.
- Binding the name to another value is not a write to the object. A later
  declaration of the name replaces it, and `delete Status` follows the
  accepted rule for objects: it raises
  `TypeError("Cannot delete object '<id>'")` while the object holds a
  property other than `id`, so only an enum whose single member is named
  `id` can be deleted, as `{id: "id"}` can.
- A spread `{...Status}` builds an ordinary object, which accepts writes.
- Reads, entry loops, spreads, JSON, comparisons, `.value` and reasoning
  never write, so they are unchanged.

### Rendering

- Canonical source writes an enum with two or more members on one line, as
  `enum Status:PENDING,PAID,SHIPPED` or `enum Level:LOW=1,HIGH=10`, and an
  enum with one member as `enum NAME:` with the member on an indented line.
  A value that equals the member's own name as a string is left out; every
  other value is written in the canonical form of a parameter default.
- `why` and `affects` rules, and the keys of blocks and branches that contain
  a declaration, use that text, and it parses back to the same declaration.
  The graph lists `NAME` as a variable node, as it lists any declaration.

### Interactive input

- The line-oriented REPL runs a one-line enum at once. A line that ends with
  `enum NAME:` ends with a colon, so the REPL buffers the indented block
  until the next blank line, as it buffers every colon header, and indents
  the continuation prompt.
- The terminal workspace offers `enum` as a completion word, as it offers
  the other statement words.

## Errors

- `TypeError("Enums are read-only")`: a write to an enum's object, through
  any spelling or name listed under Read-only enums. It is placed at the
  start of the running top-level statement, which rolls back, and a `catch`
  binds it as `TypeError: Enums are read-only`.
- `SyntaxError("Enum '<name>' already has member '<member>'")`: a member name
  repeated in one declaration, at the repeated name.
- `SyntaxError("Enum '<name>' needs at least two members on one line")`: a
  one-line enum with one member, at the token after that member.
- `SyntaxError("Expected a scalar literal enum member value")`: the token
  after `=`, or after its sign, is not a number, string, `true`, `false` or
  `null`, or a sign precedes something other than a number. It is placed at
  that token.
- `SyntaxError("Enum member value must be a finite number")`: a member value
  is a number literal too large to be finite, such as `1e999`, at the number.
- `SyntaxError("Expected a name but found <token>")`: a member name is
  missing where one must begin, such as after a comma, at the start of a
  member line or directly after the colon.
- `SyntaxError("Expected ',' but found <token>")`: on one line, a member is
  followed by something other than a comma or the end of the statement.
- `SyntaxError("Expected end of line but found <token>")`: in the indented
  form, a member is followed by something other than its line break, such as
  `;` or `,`.
- `SyntaxError("Expected an indented block but found <token>")`: the line
  after `enum NAME:` and its line break is not indented.
- `SyntaxError("Statements are nested too deeply")` still bounds nesting:
  each declaration passes the existing statement depth guard.
- Syntax errors stop the program before any statement runs. Every other
  error is that of the equivalent `NAME = {...}` declaration.

## Reference Implementation

- `src/lang/ast/mod.rs`: the public variant `Expr::Enum(Vec<EnumMember>)` and
  the public struct `EnumMember { name, value }`, whose `value` is NUC 54's
  `ParameterDefault`. A member written without a value stores its own name
  as `ParameterDefault::String`, so `A` and `A = "A"` parse to the same tree.
- `src/lang/ast/parser/enumeration.rs`, a new private child module of the
  parser. `enum_header` returns the name when the tokens are `enum`, a name
  other than `assert`, `lambda` and `suppose`, and `:`, outside a class body
  and unless `is_type_declaration_at(1)` holds. `enum_declaration` skips the
  header and reads the one-line members, which end where a destructuring
  ends, or the indented block, one member per line. `enum_member` rejects a
  repeated name through the `IndexMap` that keeps the members in order, and
  `enum_value` maps the shared scalar literal reader to the two enum
  diagnostics. The result is
  `Stmt::Assign { target: Expr::Identifier(name), value: Expr::Enum(..) }`.
  Every loop consumes a token per iteration, nothing recurses, and the
  declaration passes the statement depth guard as the statement it is.
- `src/lang/ast/parser/statement.rs`: `statement_inner` tries the header after
  the `while` header and before the statement match. `src/lang/ast/parser.rs`
  holds the private `in_class` flag and the private `ScalarLiteral` outcome;
  `parser/class.rs` sets the flag around a class body and restores it, and
  the `accepted()` probes carry it. `parser/template.rs` parses each
  interpolation with the private `Parser::interpolated_expression`, which
  carries the flag and the words mode in place of the former free function
  `parse_interpolation` and its two `bool` parameters.
  `parser/function.rs`: `parameter_default` and enum values share
  `scalar_literal`, and every parameter diagnostic and position stays as
  accepted. `parser/destructuring.rs`: `ends_destructuring` becomes the
  shared `ends_line_statement`.
- `src/lang/ast/typed.rs` and `object.rs`: an `Expr::Enum` value creates a new
  anonymous object with the members and marks it read-only; `create_anonymous`
  and the enum share `insert_anonymous`. `src/lang/ast/parameter.rs` makes
  `ParameterDefault::value` crate-visible, and its rustdoc names enum member
  values beside formal lists.
- `src/state.rs`: a private `read_only` set of object identifiers, cleared by
  `clear` and by the rollback that removes a created object.
  `src/state/mutation.rs`: `ensure_writable` raises
  `TypeError("Enums are read-only")`, `write_property` runs it before
  `assign_property` and the change's propagation, and `assign_property` and
  `remove_property` assert in debug builds that no write reaches a marked
  object. The guard runs before every property write. Property declarations
