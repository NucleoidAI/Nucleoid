## Abstract

- A loop can test its condition after its body:
  `repeat:` followed by a suite, then `until CONDITION` on its own line
  after the body, at the indentation of `repeat`. The body runs at least
  once, and the loop ends after the first iteration that leaves `CONDITION`
  truthy, so `repeat:`, an indented `x = x * 2` and `until x > 100` double
  `x` until it passes 100.
- It is the exit-controlled sibling of [NUC 63](nuc-0063.md)'s
  `while CONDITION:` and [NUC 115](nuc-0115.md)'s `repeat COUNT:`. The body
  runs as theirs do, imperatively in the enclosing scope with no scope frame
  or loop variable. The condition is tested with the truthiness of `if`
  after every iteration. Each run may run its body at most 100,000 times, as
  a `while` loop may, and errors and thrown values propagate through the
  existing transaction.
- No keyword or lexer token is added. `repeat` and `until` stay ordinary
  names everywhere else, and `repeat: NAME`, the accepted typed declaration,
  keeps its reading.
- At the accepted revision every `repeat:` statement with an indented
  block, or with a same-line suite other than one bare name, is a
  whole-program `SyntaxError`, such as `Unexpected ':'`. Only those inputs
  change.
- One public syntax-tree variant, `Stmt::RepeatUntil { body, condition }`,
  and one statement node, `Nuc::RepeatUntil`, are added beside the unchanged
  `while` and `repeat` loops. A `repeat:` suite without its `until` line
  raises the new `SyntaxError("Expected 'until' after 'repeat'")`.
- The authoritative contract is
  [Exit-controlled repeat-until loops](../nucleoid.spec.md#exit-controlled-repeat-until-loops).

## Motivation

- World models step a simulation until a goal state holds: advance time
  until a tank is full, retry a draw until it succeeds, halve a step until a
  tolerance is met. The state that the condition reads is produced by the
  body, so the body must run before the test means anything.
- Many such loops start in a state where the condition already holds and
  still have to take a step: a clock that stands at a chime advances to the
  next one, a lift that stands at a call moves on to the next call, a truck
  with no minimum load still takes a crate, and a ferry that carries no
  passengers still gets its one lifeboat. A `while` loop with the negated
  condition runs no iteration there.
- Accepted programs spell such loops by writing the body twice, once before
  a `while` loop with the negated condition; by a flag that the body sets,
  as in `going = true`, `while going:` and `going = !(x > 100)`; by a test
  that only the first iteration passes, such as `while !waited or !chimes:`
  or `while chimes == !waited:`; or by `while true:` inside a function or
  method that returns once the condition holds. These repeat the body or
  the condition, invert the condition, lean on values the program happens to
  hold, or need a function. `repeat:` and `until CONDITION` state the body
  once and the exit condition once, in the order they run.
- Pascal, Modula-2 and Lua spell this loop `repeat ... until`, and C, Java,
  JavaScript, Kotlin and Swift spell it `do { ... } while` with the negated
  condition. Python has none and writes `while True:` with `break`.
- Each of the seven new executable cases uses 2 or 3 fewer lexer tokens than
  the most compact fair accepted spelling found, as
  [Counterparts](#counterparts) records.

## Rationale

- **Category and mode.** The caller drew Runtime features with one
  tool-backed uniform draw over the five categories that NUC 1's registry
  marks eligible for automatic selection: index 1, with probability 1/5, at
  08:18:11 on 21-Nov-2026, and no redraw. This is a continuous cycle, so the
  token non-regression gate is required.
- **Runtime applicability: `existing_comparable`.** Exit-controlled loops are
  written today with accepted `while` loops: the body once before a `while`
  loop with the negated condition, a flag, a test that only the first
  iteration passes, or `while true:` with `return` inside a function or
  method. Every case of this proposal is paired with such an accepted-syntax
  program, which the accepted runtime runs with every assertion, as
  [Counterparts](#counterparts) records.
- **Selection.** Within the category the caller chose one bounded
  enhancement: an exit-controlled loop, the control-flow sibling of NUC 63's
  `while` and NUC 115's `repeat`, which no NUC proposes. It set aside
  `break` and `continue`, whose bare statements parse as names today; list
  spread and expression parameter defaults, typed or repeated `catch` and
  `except` clauses and `try`/`else`, whose errors accepted tests pin; and
  atomic blocks, since a `try` block already rolls back all of its
  statements.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero, because no rubric was frozen. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Pascal's and Lua's words, without reserved words.** `repeat` opens the
  loop and `until` names the exit condition, in the sense the condition is
  read: the loop runs until it holds. Both stay ordinary identifiers. At the
  accepted revision a statement that starts with the name `repeat` and `:`
  parses only as the typed declaration `repeat: NAME`, so every loop
  spelling was a `SyntaxError`. Rejected:
  - `do:` with a final `while CONDITION` line, C's and Kotlin's word order:
    the condition reads in the opposite sense, and `while CONDITION` after a
    suite is an accepted juxtaposition of the name `while` and an expression
    that NUC 63 keeps;
  - reserving `until`, which would break programs that use it as a
    variable, function, parameter or property;
  - `repeat until CONDITION:` with the test before the body, which is
    `while not CONDITION:`;
  - `break` and `continue`, which parse as names, and Python's `while True:`
    with `break`.
- **`until` on its own line after the body, at the indentation of
  `repeat`.** As `else`, `catch`, `except` and [NUC 119](nuc-0119.md)'s
  `finally:` follow their suites, `until` starts the logical line after the
  loop's suite, at the layout level of `repeat`. The parser finds it by the
  bounded look-ahead that NUC 119 uses for `finally`, which the two clauses
  now share: after the suite only `Newline` tokens may follow, which blank
  and comment lines never add to, and the token before `until` is the
  `Newline` that ends a same-line suite or the `Dedent` that closes an
  indented one. An `until` indented into the body is a statement of the
  body, and one that is less indented than `repeat` closes no loop. A line
  at a width between the body and `repeat` closes to the level of `repeat`,
  as the lexer closes every such width, so an `until` there closes the
  loop, as a `finally:` there belongs to its `try`. When `repeat:` itself
  stands in the same-line
  suite of another statement, as in `for truck of Truck: repeat: ...`, the
  `until` line at that line's indentation closes it, as an `else` line
  closes the innermost `if` of a same-line suite at the accepted revision.
  Rejected: `until` on the suite's line after `;`, where it is already a
  statement of the same-line suite, and a braced
  `repeat { ... } until CONDITION`, whose block is an accepted juxtaposition.
- **The typed declaration stays.** `repeat: NAME` before a newline, `;`, a
  dedent or the end of input is the typed declaration of `repeat` at the
  accepted revision, also when an indented block or an `until` line follows
  it, so it keeps that reading and a same-line body never starts with one
  bare name. Executing the declaration raises
  `ReferenceError("Missing definition")`, and a body that only reads a bare
  name does nothing, so no useful loop is lost, as NUC 63 argued for
  `while NAME: TYPE`. An audit of 2,631 spellings of `repeat:` followed by
  each kind of token, at the top level, in function and class bodies and in
  braced blocks, found that the accepted parser accepts this declaration and
  nothing else: `repeat: assert: x, 1`, `repeat: lambda: 1`,
  `repeat: suppose: x`, `repeat: suppose:` with an indented block and
  `repeat: x := 1` are all `SyntaxError`s, so they become loops whose body
  holds that statement. In `repeat: suppose: x` that statement is the typed
  declaration `suppose: x`, as it is alone at the accepted revision, so
  running the loop raises `ReferenceError("Missing definition")`.
- **A condition parsed like an `if` header, ending its line or block.**
  The condition is a clause expression, so conditional expressions
  ([NUC 59](nuc-0059.md)), quantifiers ([NUC 62](nuc-0062.md)), `??`
  ([NUC 60](nuc-0060.md)), `|>` and arrows pair their own colons, and a
  lambda must be bracketed. Statements need no separators, so a token after
  the condition would otherwise start a juxtaposed statement on the `until`
  line. The condition ends the logical line instead, or the enclosing block:
  a newline, `;`, a dedent, the `}` that closes an enclosing block or the
  end of input follows it, and any other token is a `SyntaxError`, such as
  `Unexpected ':'` for `until x > 100:`. A `}` starts no juxtaposed
  statement, so the loop leaves it to the enclosing block, as a `return`,
  a `while` or an `if` statement there does at the accepted revision.
- **A missing `until` names what is missing.** A `repeat:` suite that no
  `until` line follows raises `SyntaxError("Expected 'until' after 'repeat'")`
  at the token where `until` should stand, in the form of
  `Expected 'catch' after 'try'`. It is the only new message.
- **Test after every iteration, with the truthiness of `if`.** The body runs,
  then the condition is evaluated in the current state and tested as an `if`
  condition is; a truthy condition ends the loop. So the body always runs at
  least once, which is the loop's purpose, and an unchanged condition that
  already held runs the body once.
- **The bound and the message of `while`.** Each run may run its body at most
  100,000 times, the bound of `while`. When the condition is still falsy after
  the 100,000th iteration, the loop raises `TypeError("Loop did not terminate")`,
  as a runaway `while` loop does: it is the same failure, a loop whose
  condition never settles. Rejected: a message of its own, and checking the
  bound before the first iteration, which only a counted loop can do.
- **One-shot and imperative, like `while`.** The loop runs when its statement
  runs and leaves nothing in the graph, and its body runs through the step
  that `while` and `repeat` already share, `nuc::run_iteration`: imperatively,
  in the enclosing scope, with no scope frame. Rejected: a standing loop, and
  a frame per iteration, which would turn an accumulator of an enclosing
  function into a local of the iteration, as the frame of a `for` loop in a
  function does.
- **A syntax-tree variant of its own.** The loop builds the new public
  variant `Stmt::RepeatUntil { body, condition }`, beside the unchanged
  `Stmt::While { condition, body }` and `Stmt::Repeat { count, body }`, with
  its fields in the order they run. Its `Debug` text never contains
  `Repeat { count: `, which `tests/repeat_loops.rs` searches for. Rejected: a
  flag or an optional field on `Stmt::While` or `Stmt::Repeat`, which would
  change the tree of every accepted loop and break the exhaustive
  destructuring of those variants, among them the accepted arms of
  `tests/common/assertions.rs`; and a desugaring into a `while` loop with a
  hidden flag, whose name could collide with the program's and would show in
  renderings and `why`. As for [NUC 115](nuc-0115.md)'s `Stmt::Repeat` and
  [NUC 119](nuc-0119.md)'s `Stmt::TryFinally`, that exhaustive match gains
  only the arm that visits the new variant's body and condition, and no
  other existing test changes beyond count-only pins.
- **A statement node of its own.** `Nuc::convert` maps every `Stmt` to the
  public `Nuc` enum, so the loop also needs `Nuc::RepeatUntil`, whose node
  `nuc::repeat_until::RepeatUntil` keeps its fields private, as
  `Nuc::Repeat` does. Both enums are exhaustive, so the two variants break
  exhaustive downstream matches; this needs human SemVer review, and no
  version number changes.
- **Canonical rendering.** Graph keys render a loop as
  `repeat{BODY}until(CONDITION)`, in the order it runs, as
  `while(CONDITION){BODY}` and `repeat(COUNT){BODY}` do. Inside
  default-bearing declarations a loop renders in the suite form, `repeat:`
  with an indented body and an `until CONDITION` line.
- **REPL and terminal workspace.** The native REPL already buffers a line
  that ends in `:` until a blank line, so `repeat:` waits for its indented
  body and its `until` line, which must come before that blank line. Neither
  `src/interactive.rs`, `src/continuation.rs` nor `src/terminal/` changes, and
  the workspace's completion words stay as they are.
- **The exporter keeps `until` with its loop.** The specification exporter's
  statement splitter, `build_statements.rs`, which `build.rs` and the
  exporter suites share, starts a new exported statement at every top-level
  line except one that continues the statement before it: an `else`, `elif`
  or `catch` line, a `finally:` line or a closing bracket. It gains `until`
  among those words, so a top-level loop and its `until` line run in one
  call of the exported test, as a `try` and its `finally:` line do. Without
  it, the export of the clock case runs `repeat: minute += 5; waited += 5`
  alone, which raises the missing-`until` error. No accepted record has a
  top-level line that starts with the word `until`, so every existing
  exported test is unchanged; a later record with a top-level statement that
  starts with the name `until`, such as `until = 5`, is exported in one call
  with the statement before it, which parses to the same statements.
- **Requires.** [NUC 63](nuc-0063.md), whose body semantics, iteration bound
  and message, renderings and REPL behavior this loop shares, and which
  already requires the NUCs of those rules; and [NUC 115](nuc-0115.md), whose
  shared iteration step `nuc::run_iteration` and bound `MAX_ITERATIONS` the
  loop runs through, and whose readings of the name `repeat` it keeps.
- **Not added.** `do ... while`, `repeat ... while`, `until CONDITION:` with
  the test first, `break` and `continue`, a loop variable or index, a
  reserved word, `until` on the suite's line, braced loops, class-level
  standing loops, and any change to `while`, `repeat COUNT:`, `for`, the
  string method `repeat`, recursion limits or existing diagnostics.

### Counterparts

- Every new case is compared with the most compact fair accepted-syntax
  program found that reaches the same canonical assertions in the same order
  and the same expected return. Each differs from its case only where a
  repeat-until loop is written; every other line is the case's own, and no
  helper line or function made a program shorter. They are recorded in
  `extra-baselines.json`, which the accepted runtime executed with every
  assertion run.
- Every loop of the seven cases starts at least once in a state where a
  pre-test loop would not run its body: its condition already holds, or it
  reads a name that only the body defines. So a plain `while` loop with the
  negated condition fails every case. Each case also changes something after
  its loops run, or calls their method again, so a counterpart has to keep
  the loops' imperative effects. A hardcoded spelling keeps those effects

  not defeated by them.
- The search measured these families at every loop site, each with `!`,
  `not` and flipped comparisons for the negated condition, with the other
  sites of a case in a faithful flag spelling, and then the best passing
  combinations:
  - the body once before a `while` loop with the negated condition, indented
    and on the same line, and with value assignments `:=` in the copy before

  - a flag that the body sets, `going = true` with `while going:`, and a
    first-iteration flag `first`;

  proposal leaves them unchanged, and no case depends on them:

    spellings fail wherever a condition reads a standing declaration of a

## Specification

- The normative contract is
  [Exit-controlled repeat-until loops](../nucleoid.spec.md#exit-controlled-repeat-until-loops).

### Syntax

- `repeat_until_statement: "repeat" ":" suite newline* "until" condition`,
  where `repeat` and `until` are ordinary identifiers, `suite` is the suite
  of `if`, `for` and `while`, an indented block or statements on the same
  line separated by `;`, and `condition` is a complete expression in the
  context of an `if` header.
- A statement is a repeat-until loop when it starts with the name `repeat`
  immediately followed by `:`, except the typed declaration: `repeat: NAME`
  followed by a newline, `;`, a dedent or the end of input, where NAME is one
  name of any spelling, `assert`, `lambda`, `suppose`, `every`, `is`, `until`
  and `repeat` included, keeps its accepted reading as the declaration, also
  when more statements, an indented block or an `until` line follow it.
- The suite is followed, on its own line after the body and at the
  indentation of `repeat`, by the name `until` and one condition. Only blank
  lines and comment lines may stand between them, with LF or CRLF line ends
  alike:
  - an `until` indented into an indented body is a statement of that body;
  - a line indented less than an indented body but more than `repeat` closes
    to the level of `repeat`, as the lexer closes every such width, so an
    `until` there closes that loop, as an `else` there closes its `if`:
    `n = 0`, then `repeat:` with the body `n = n + 1` at four spaces, then
    `until n > 3` at two, then `n`, gives `4`, and so does the same loop
    with a blank and a comment line before its `until` line, or inside an
    `if` body with its `until` line between the body and `repeat`;
  - an `until` less indented than `repeat` closes no loop, also at a width
    between `repeat` and an enclosing level, which closes to that enclosing
    level;
  - an `until` after `;` on the suite's line is a statement of the same-line
    suite;
  - when `repeat:` stands in the same-line suite of another statement, as in
    `for truck of Truck: repeat: ...`, the `until` line at that line's
    indentation closes it;
  - inside parentheses and brackets, where line breaks carry no meaning, no
    `until` line can follow a suite, so a loop in a callback passed as a call
    argument raises the missing-`until` error.
- The condition ends the logical line or the enclosing block: a newline,
  `;`, a dedent, the `}` that closes an enclosing block or the end of input
  follows it. Any other token is a `SyntaxError`, such as `Unexpected ':'`
  for `until x > 100:`. The `}` stays with its block, as after `return`,
  `while` and `if` statements: `x = 0`, then `{`, `repeat: x += 1` and
  `until x > 3 }`, then `x`, gives `4`, as the same program does with the
  `}` on its own line, and so do a braced arrow body
  `f = () -> { repeat: x += 1` with `until x > 3 }`, called once, and a
  block `{ if true: repeat: x += 1` with `until x > 3 }`. A `}` that closes
  no block remains an error after the loop, as after any statement. So
  does a `}` on the `until` line of a loop in an indented suite, such as an
  indented `if` body in a braced block: after `x = 0` and `{ if true:`, a
  loop indented four spaces whose line `until x > 3 }` ends with the `}`
  raises `Unexpected '}'` at that brace, line 5, column 17, where the `}`
  on its own line gives `4`. The accepted revision rejects a `}` after any
  statement of an indented suite in the same way: `x += 1 }` in that `if`
  body raises `Unexpected '}'` there.
- A `repeat:` suite that no `until` line follows raises
  `SyntaxError("Expected 'until' after 'repeat'")` at the token where `until`
  should stand.
- Statements are loops wherever a statement starts: at the top level, in
  suites, braced blocks spread over lines, function and method bodies,
  constructor bodies and the bodies of other loops, so loops nest, each with
  its own `until` line at its own indentation.
- Everything else keeps its accepted reading: `repeat := VALUE`,
  `repeat = VALUE`, `repeat(...)` calls, `def repeat(x)`, the string method
  `"ab".repeat(3)`, NUC 115's `repeat COUNT:` with its four exceptions, a
  variable, function, parameter, loop variable, object key or property named
  `repeat` or `until`, `{repeat: 1, until: 2}`, `until X` as the juxtaposed
  statements `until` and `X` wherever it does not close a repeat-until suite,
  and the class fields `repeat: int` and `until: int`. `parse_expression`,
  which reads expressions only, still reads the names `repeat` and `until`.

```
minute = 0
chimes = minute % 15 == 0
waited = 0
repeat: minute += 5; waited += 5
until chimes
assert([minute, waited, chimes], [15, 15, true])
repeat: minute += 5; waited += 5
until chimes
assert([minute, waited], [30, 30])
minute = 32
assert([chimes, waited], [false, 30])
```

- The clock stands at a chime, minute 0, so `chimes` already holds, yet each
  loop advances it to the next one, and `chimes` follows every step; setting
  `minute` later runs neither loop again.

### Loop

- The body runs, then the condition is evaluated in the current state and
  tested with the truthiness of `if`. A truthy condition ends the loop;
  otherwise the body runs again. The body always runs at least once, also
  when the condition holds before the loop starts.
- A completed loop yields `null`.
- Each iteration's assignments, and the propagation they cause, are visible
  to the rest of the body, to the condition and to the next iteration.
  `.value` in the condition reads the current value at each test.

### Bound

- Each run of a repeat-until loop runs its body at most 100,000 times, the
  bound of `while`. When the condition is still falsy after the 100,000th
  iteration, the loop raises `TypeError("Loop did not terminate")`,
  positioned at the start of the running top-level statement, and the
  transaction rolls back.
- Each run of a nested loop has its own bound, so every run terminates, but
  nested loops multiply and the bound is not a cap on total work.

### Body

- The body runs imperatively, as a `while` body does: its statements,
  including nested conditionals, blocks and loops, are carried out once per
  iteration and never filed as standing rules.
- The body runs in the enclosing scope, with no scope frame and no loop
  variable, so an assignment in the body resolves exactly as the same
  assignment would in place of the loop statement: a parameter, a local of
  the enclosing function or loop body or an enclosing loop variable is
  updated in place, and a top-level name is a state assignment carried out
  once. `this` and `self` denote the enclosing receiver.
- `return` in the body leaves the enclosing function, method, block or loop,
  as from a `while` body, and the condition is not evaluated after it. At
  the top level it ends the program with its value.
- The loop files nothing in the graph and does not run again when its
  inputs, or anything its body read, change later. A loop inside the body of
  a standing rule, such as the branch of a top-level `if` or a function
  called from a declaration, runs again whenever that rule runs, as a `while`
  loop does there.
- A repeat-until statement is never kept on a class. Outside a class-level
  rule, `$Class` in its body or condition reads the declared class, and an
  undeclared `$Name` raises `ReferenceError("Name is not defined")`. A body
  statement that is itself a class-level declaration, such as
  `$Item.flag = true`, is declared on the class when it runs. Inside the body
  of a class-level rule, the loop runs for each instance and `$Class` reads
  that instance.
- Errors raised by the body or the condition, including thrown values,
  propagate through the existing transaction unchanged. An uncaught failure
  rolls back the whole program run; a caught one restores the state from
  before the enclosing `try` body, including every iteration that already
  ran.

```
class Drone(battery):
    this.battery = battery
    this.distance = 0
    def fly(target):
        repeat:
            this.battery -= 10
            this.distance += 3
            if this.empty: return "stranded"
        until this.distance >= target
$Drone.empty = $Drone.battery < 10
scout = Drone(40)
assert([scout.fly(6), scout.distance, scout.empty], [null, 6, false])
assert([scout.fly(0), scout.distance, scout.battery], [null, 9, 10])
assert([scout.fly(20), scout.distance, scout.empty], ["stranded", 12, true])
spare = Drone(25)
assert([spare.fly(6), spare.distance], ["stranded", 6])
scout.battery = 50
assert([scout.empty, spare.empty], [false, true])
```

- Each leg reads the class-level rule `empty`, which follows the battery of
  its own drone. `scout.fly(0)` still flies one leg, and a drone whose
  battery runs empty on a leg is stranded even when that leg reaches the
  target, since the body returns before the condition is tested.

```
class Oven(temp):
    this.temp = temp
    this.steps = 0
    def heat():
        repeat: this.temp += 10; this.steps += 1
        until this.ready
marks = [150, 180, 220]
$Oven.ready = marks.includes($Oven.temp)
if $Oven.temp > 200:
    throw "OVERHEAT"
oven = Oven(150)
oven.heat()
assert([oven.temp, oven.steps, oven.ready], [180, 3, true])
try:
    oven.heat()
catch error:
    failure = error
assert([failure, oven.temp, oven.steps], ["OVERHEAT", 180, 3])
marks.push(190)
oven.heat()
[oven.temp, oven.steps]
```

- The second call starts at a mark, so `ready` already holds, and heats on:
  its third step passes 200, the class-level rule throws, and the caught
  failure rolls back all three steps. After a mark at 190 is added, the
  third call stops there.

### Rendering

- Graph keys render a loop as `repeat{BODY}until(CONDITION)`, including the
  body, as `while(CONDITION){BODY}` does, so a loop in a block renders as
  `block(repeat{n=n+1}until(n>3))`.
- Inside default-bearing declarations a loop renders in the suite form:
  `repeat:`, the body indented below it, and `until CONDITION` at the
  indentation of `repeat`.

  line can arrive, and it raises the missing-`until` error; the indented
  form is the one to type.

### Findings

- **Medium, public API:** `Stmt` and `Nuc` are exhaustive public enums, so
  the new `Stmt::RepeatUntil` and `Nuc::RepeatUntil` break downstream code
  that matches either of them exhaustively, a SemVer-major change under the
  Rust API guidelines, as for [NUC 115](nuc-0115.md) and
  [NUC 119](nuc-0119.md). The public module `nucleoid::nuc::repeat_until`
  adds the type `RepeatUntil`. No version number changed; versions stay
  human-owned.
- **Low, counterparts:** the [Counterparts](#counterparts) section's claims
  that its spellings are the most compact found, and its stated saving of 20
  tokens, are overstated by one token for the reference case and for the
  nested case, as above. The gate result is unaffected.
- **Informational:** `{repeat: 1, until: 2}` keeps both keys as an
  expression, as [Compatibility](#compatibility) says. As a bare statement
  it is a braced block, which was already a `SyntaxError` at the accepted
  revision, and its message changes from `Unexpected ':'` at column 10 to
  `Expected 'until' after 'repeat'` at column 11.
- **Informational:** the generator's `generate` and `source` now have
  exactly 60 lines, so the next statement kind needs a helper there.
- **Informational:** the documented limitations hold as stated. The REPL
  runs a same-line `repeat:` line at once and commits a block at a blank
  line before its `until`; a loop in a callback passed as a call argument
  never meets its `until` line; and a `}` that ends the `until` line of a
  loop inside an indented suite raises `Unexpected '}'`, as after any other
  statement there. Pushing to a list in a long loop grows memory
  quadratically, at both revisions.
