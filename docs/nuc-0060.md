# NUC 60 -- Nullish Coalescing

```
NUC: 60
Title: Nullish Coalescing
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Runtime features
Created: 30-Oct-2026
Requires: 59
```

## Abstract

- Add the nullish coalescing operator `left ?? right`, as in JavaScript,
  TypeScript, C#, PHP, Swift and Dart. It yields `left` unless `left` is
  null, and otherwise evaluates and yields `right`.
- `left` is null exactly when a declaration of `left` alone would store
  `null`: its value is null or undefined, or its evaluation read a null
  binding or property. Falsy values such as `0`, `""` and `false` are kept,
  unlike with `||`.
- `right` is evaluated only when `left` is null. The null reads made by such
  a `left` are absorbed, so they no longer settle the enclosing declaration
  to `null`; the reads of an evaluated `right` count as usual.
- `??` is a third operator of the existing `Expr::Logical` node. Dependencies,
  `.value` snapshots, class-level rule validation, transactions and reasoning
  detection use the existing `&&`/`||` machinery. It renders canonically as
  `(left??right)`.
- One right-associative level sits between NUC 59's conditional expression
  and the reasoning pipeline `|>`, so `??` binds more loosely than `||`, as
  in C#, PHP and Dart.
- `??` is one lexer token. Accepted syntax keeps its parsing and behavior:
  `??` never appeared outside literals and comments in a valid program.
- The authoritative contract is
  [Nullish coalescing](../nucleoid.spec.md#nullish-coalescing).

## Motivation

- Nucleoid's goal is a superset of Python, JavaScript/TypeScript, Kotlin, Go,
  Rust, Java, C# and C/C++. JavaScript, TypeScript and C# spell a default as
  `value ?? fallback`, but at the accepted revision `x = a ?? 5` raises
  `SyntaxError("Unexpected '?'")` at line 1, column 10.
- No accepted expression can supply a default for an unknown value. Every
  expression that reads a null binding or property settles its declaration to
  `null`. With `x = null`, each of `y = x || 5`, `y = x == null`,
  `y = x === null`, `y = typeof x`, `y = !x` and `y = x ? 1 : 2` stores
  `null`.
- `||` also discards legitimate falsy values: `y = 0 || 5` stores `5`.
- Null properties poison the same way. With `p.nick = null`,
  `p.label = p.nick || p.name || "anon"` stores `null`, and the class-level
  rule `$Order.discount = $Order.coupon || 0` stores `null` for an order whose
  `coupon` is `null`.
- A null read inside a callback poisons the whole declaration:
  `y = [1, null, 3].map(x => x || 0)` stores `null`.
- The accepted workaround is a statement-level rule per target, such as
  `if x == null:` with branches assigning `5` or `x`. It has limits that the
  accepted runtime shows:
  - rules with the same condition text replace each other, so each target
    needs a differently spelled condition;
  - statements cannot appear inside callbacks, list and object literals,
    template interpolations, call arguments or subscripts;
  - a class-level `if` stands aside while its condition reads an undefined
    property, so `if $Device.profile == null:` never assigns anything for a
    device without a `profile`.
- `left ?? right` states the default once, inside the declaration that uses
  it, and stays live through the existing dependency graph.

## Rationale

- **Category and applicability.** The caller selected Runtime features by one
  uniform draw over the registry's four eligible categories (index 1,
  probability 1/4, no redraw). A nullish default adds expression-level
  control flow with its own null handling: evaluate `left` once and settle it,
  then evaluate `right` only when `left` is null.
- Runtime applicability is `existing_comparable`. The feature extends the
  existing null and undefined assignment rules and standing statement-level
  conditionals (NUC 7 and reference section 8) to expression position. On the
  accepted runtime, `x = null` with `if x == null:`, `y = 5`, `else:` and
  `y = x` gives `y == 5`, and `3` after `x = 3`. The precedents are NUC 51,
  54, 55 and 59.
- Every new measured case has a behavior-equivalent accepted-syntax
  counterpart that reaches the same assertions and expected return:
  statement-level `if`/`elif`/`else` rules for null bindings and properties,
  class-level `if` rules, NUC 59's `value == null ? fallback : value` for
  undefined properties whose values may be falsy, and `||` where every
  defaulted value is truthy.
- **Where counterparts differ.** The comparison exposed four differences. They
  are recorded, not changed:
  - each statement-level rule needs its own condition text, while each `??`
    belongs to its own declaration;
  - a class-level `if` stands aside while its condition reads an undefined
    property, so the counterpart first derives a defined property, as in
    `$Order.express = $Order.rush || false`, while `if $Order.rush ?? false:`
    decides directly;
  - a null element or parameter read inside a callback poisons every accepted
    counterpart, so that use is covered by development tests and synthesized
    records instead of a measured case;
  - a statement branch takes a `.value` snapshot when it runs, while a
    declaration freezes `.value` in both operands when it is stored, as for a
    skipped logical operand.
- **One logical operator.** `LogicalOp::Coalesce` joins `And` and `Or` in the
  existing `Expr::Logical`, as ESTree's `LogicalExpression` takes `"??"`
  beside `"&&"` and `"||"`. Every operand walker already visits both operands
  of a logical node: dependency roots, class references, class-rule
  properties, call checks, `.value` freezing, reasoning detection and the
  protected-assertion walker. Only evaluation, parsing and rendering change.
- Rejected: a separate `Expr` variant, which would duplicate each walker;
  lowering to `Expr::Conditional` with a `left == null` condition, which would
  evaluate `left` twice and whose condition is itself settled to `null` by a
  null read; lowering to `||`, which discards falsy values.
- **What counts as null.** `left` is settled by the existing assignment rule,
  `Runtime::settle`, so `??` sees exactly what `y = left` would store. A null
  read anywhere in the evaluation of `left`, including in functions and
  callbacks it calls, makes `left` null: `(n + 1) ?? 0` is `0` while `n` is
  null, because `y = n + 1` stores `null`, where JavaScript yields `1`.
  Likewise `(flag || backup) ?? 9` is `9` while `backup` is a null that
  `flag || backup` reads.
- Rejected: testing only the raw value, which would let a value computed from
  an unknown input escape the null rule; keeping the null reads, which would
  make `x ?? 5` store `null` exactly as `x || 5` does.
- **Absorbed and counted reads.** When `left` is null, `??` discards the null
  and undefined reads that `left` made and then evaluates `right`, whose reads
  count as usual. So `a ?? b` with both null still stores `null`, and the
  enclosing declaration still depends on everything both operands read.
  A non-null `left` keeps its reads; it cannot have read a null value. State
  version reads already save and restore the same flags around a slot read
  (NUC 53).
- A class-level `if` statement stands aside while its condition reads
  something undefined. An undefined read that `??` replaced with its default
  no longer counts, so `if $Order.rush ?? false:` takes its `else` branch for
  an order without `rush`. Rejected: keeping the stand-aside, which would make
  `??` useless in class-level conditions. Other conditions keep standing
  aside, including one whose non-null `left` read something undefined, and the
  statement `if` itself is unchanged.
- A missing fixed self-anchor still defers its class rule (NUC 55):
  `$Account.opening = $Account.opening@first ?? 0` waits for the first
  version rather than manufacturing it from the default.
- **Undefined names stay errors.** `missing ?? 5` raises
  `ReferenceError("missing is not defined")`, as in JavaScript, where only a
  value can be nullish. Rejected: treating an undefined name as null, which
  would hide misspellings. A variable read while its deletion propagates is
  already undefined rather than an error, so `reward = bonus ?? 0` becomes `0`
  when `bonus` is deleted and follows `bonus` when it is defined again.
- **Precedence.** JavaScript rejects `??` mixed with unparenthesized `&&` or
  `||`; C#, PHP and Dart place `??` below `||` and above the conditional. The
  superset takes their reading, so every parenthesized JavaScript program and
  every C#, PHP or Dart program keeps its meaning: `a || b ?? c` is
  `(a || b) ?? c` and `a ?? b || c` is `a ?? (b || c)`.
- Comparisons and arithmetic bind more tightly, as in JavaScript and C#:
  `a ?? b == c` is `a ?? (b == c)`, so compare a default as `(x ?? 0) > 5`.
  Swift binds `??` above comparisons; such Swift programs need parentheses.
- Placing `??` below `|>` keeps every existing operator's relative order and
  lets a reasoning pipeline be an operand without parentheses:
  `x |> why ?? fallback` defaults the pipeline. The right side of `|>` is only
  a stage name, so `|>` never absorbs a `??`.
- Placing it above NUC 59's conditional, as in JavaScript and C#, makes
  `a ?? b ? c : d` test `a ?? b`. The operand before `?`, the Python
  consequent and the Python condition become coalescing-level instead of
  pipeline-level. Without `??` the two levels parse identically, so every
  accepted parse and every memoized Python-condition outcome is unchanged.
- Right-associative, as in C#, PHP and Swift: `a ?? b ?? c` is
  `a ?? (b ?? c)`. JavaScript and Dart group to the left; both groupings
  select the first non-null operand and evaluate the same operands, so only
  the AST and the rendering of parenthesized source differ.
- The chain is parsed by a loop bounded by the existing 128-operator limit and
  folded to the right. The conditional level parses the first operand
  directly, so the parser's descent for programs without `??` gains no stack
  frame.
- **Lexing.** `??` is one token by longest match, so `???` is `??` followed by
  `?`. A lone `?` keeps NUC 59's meaning and `? ?` stays two tokens. A `/`
  after `??` starts a regular expression and `a??.5` reads `.5` as a number,
  as in JavaScript.
- **Canonical rendering.** `(left??right)`, grouped like NUC 59's
  `(condition?consequent:alternate)`. Parentheses in the source are not kept
  in the AST, and rendering is a graph key, so the grouping keeps
  `(x ?? 0) > 5`, rendered `(x??0)>5`, distinct from `x ?? 0 > 5`, rendered
  `(x??0>5)`, and `(a ?? b) ?? c` distinct from `a ?? b ?? c`. `&&` and `||`
  keep their ungrouped rendering. Rejected: rendering `left??right`, which
  would give `if (x ?? 0) > 5:` and `if x ?? 0 > 5:` one conditional key.
- **Header scanners.** NUC 43's direct-alternative scan and the native REPL's
  colon-free header scan pair a top-level `?` with its `:`. `??` is another
  token and pairs with nothing, so `else a ?? b` and `if a ?? b` followed by
  an indented suite qualify like any other header, without a scanner change.
- **Not added.** Nullish assignment `??=`, which NUC 26 also left out,
  optional chaining `?.`, Kotlin's Elvis `?:`, changes to statement-level
  `if`, and any change to the null-read rule outside `??`. `?.` and `?:`
  remain errors.
- **Token policy.** In this continuous cycle, Runtime features with
  `existing_comparable` applicability require the token non-regression gate.
  All nine new measured cases were paired with accepted-syntax counterparts,
  executed by the accepted runtime and supplied through
  `NUC_PROPOSAL_EXTRA_BASELINES` before any candidate edit. No pre-existing
  case is rewritten; the independent evaluator measures the comparison.

## Specification

### Syntax

- `??` is a single lexer token, `Token::QuestionQuestion`, described as
  `'??'`. Text in strings, template literals outside interpolations, regular
  expressions and comments is unchanged.
- Expression levels, from loosest:
  - assignment, unchanged;
  - conditional: `coalescing ? expression : conditional`, or
    `coalescing if coalescing else conditional` when qualified, or
    `coalescing`;
  - coalescing: `pipeline ?? coalescing`, right-associative, or `pipeline`;
  - pipeline and every tighter level, unchanged.
- One chain holds at most 128 `??` operators; another raises
  `SyntaxError("Expression has too many operands")`, as for the other
  operator chains.
- Variables, properties, class-level rules, `if` headers, function bodies and
  returns, arrow and lambda bodies, list and object elements, template
  interpolations, call arguments, subscripts and every conditional-expression
  operand accept `??` as an ordinary operand.

### Semantics

- Evaluate `left` once and settle it with the existing assignment rule: it is
  null when its value is null, when its value is undefined, as for a missing
  property, or when its evaluation read a null binding or property.
- If `left` is not null, its value is the result. `right` is not evaluated: it
  has no effects, raises nothing and adds no dependency.
- If `left` is null, the null and undefined reads that `left` made are
  discarded, `right` is evaluated, and its value is the result. Its reads
  count as usual, so a null that `right` reads still settles the enclosing
  declaration to `null`.
- Falsy values that are not null, such as `0`, `""`, `false`, NaN and empty
  lists and objects, are kept.
- A standing variable, property or class-level rule depends on what `left`
  read and, when it was evaluated, on what `right` read. It re-evaluates when
  either changes and switches between the left value and the default as
  `left` becomes null or not, replacing obsolete dependencies.
- An undefined name raises `ReferenceError("<name> is not defined")` when the
  operand that reads it is evaluated. A variable read while its deletion
  propagates is undefined, so its dependents take their defaults.
- `.value` snapshots are taken in both operands when a declaration is stored,
  as in a skipped logical operand, so an unevaluated `right` keeps the
  snapshot it had then.
- A class-level rule validates names and `$Class` property cycles in both
  operands when it is declared, as for `||`, and each instance evaluates its
  own operands.
- A class-level `if` statement stands aside while its condition reads
  something undefined, except for an undefined read that `??` replaced with
  its default.
- A missing fixed self-anchor still defers its class rule rather than taking
  the default (NUC 55).
- Errors raised by `left` or an evaluated `right` propagate through the
  existing transaction; a failed standing re-evaluation rolls back the change
  that triggered it.

```
stock = null
count = stock ?? 0
discount = 0
rate = discount ?? 10
nickname = null
first = "Ada"
display = nickname ?? first ?? "guest"
plain = stock || 0
assert(count, 0)
assert(rate, 0)
assert(display, "Ada")
assert(plain, null)
stock = 5
discount = null
nickname = "Lady A"
assert(count, 5)
assert(rate, 10)
assert(display, "Lady A")
```

```
class Order(total, coupon):
    this.total = total
    this.coupon = coupon
$Order.discount = $Order.coupon ?? 0
if $Order.rush ?? false:
    $Order.lane = "fast"
else:
    $Order.lane = "normal"
small = Order(40, null)
large = Order(250, 25)
savings = Order.map(order => order.coupon ?? 0)
assert(small.discount, 0)
assert(small.lane, "normal")
assert(savings, [0, 25])
large.rush = true
assert(large.lane, "fast")
```

### Compatibility

- Accepted programs keep their parsing, positions, diagnostics and behavior.
  `??` outside a literal or comment was always a syntax error, because a `?`
  can start no operand.
- NUC 59's conditional keeps its spellings, precedence and rendering;
  `c ? a : b`, `a?.5:1` and `? ?` keep their tokens.
- `"why??"`, `/colou??r/`, comments and template text containing `??` are
  unchanged.
- The public `Token` and `LogicalOp` enums gain `Token::QuestionQuestion` and
  `LogicalOp::Coalesce`. Exhaustive downstream matches stop compiling, so this
  needs human SemVer review. No project version is changed.
- The public `tokenize` returns one `Token::QuestionQuestion` where it
  returned two `Token::Question` tokens, and `parse_expression` returns a
  `??` expression for input such as `a ?? b`, which it rejected. This also
  needs human SemVer review.
- The native REPL buffers `if a ?? b` as a colon-free header awaiting its
  indented body, where it previously ran the line and reported
  `SyntaxError("Unexpected '?'")`.

  description. A new unit test covers `??` beside `?`, regular expressions,
  numbers, `=` and literal text.
- `src/lang/ast/mod.rs` adds `LogicalOp::Coalesce`. No other `Expr` variant
  or walker is added: `src/expression.rs`, `src/nuc/expression.rs`,

  visit both operands of `Expr::Logical`.
