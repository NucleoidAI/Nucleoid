Created: 27-Nov-2026
Requires: 111

## Abstract

- String receivers gain four familiar names for the padding methods of
  [NUC 111](nuc-0111.md), each an exact alias of its accepted spelling:
  - Python's and Ruby's `TEXT.rjust(length, fill)` and C#'s
    `TEXT.PadLeft(length, fill)` are `TEXT.padStart(length, fill)`, so
    `"7".rjust(3, "0")` is `"007"`;
  - Python's and Ruby's `TEXT.ljust(length, fill)` and C#'s
    `TEXT.PadRight(length, fill)` are `TEXT.padEnd(length, fill)`, so
    `"ab".ljust(4, ".")` is `"ab.."`.
- Whenever its receiver evaluates to a string, each alias gives exactly
  what its accepted spelling gives: `fill` defaults to one space, a longer
  fill repeats and is cut to the missing count as Ruby's does, `length`
  converts as the count of `repeat` does, characters are Unicode scalar
  values, an oversized result raises
  `TypeError("Padded string is too large")`, further arguments are
  evaluated and ignored, and a declaration or class-level rule that calls
  an alias stays live with the accepted spelling's dependencies.
- The equivalence holds per evaluation of the receiver. When a later write
  turns the receiver of a standing call into another kind of value, the
  call reads the alias's name on that value, as every other receiver does:
  a number raises `TypeError("number.ljust is not a function")` where the
  spelling raises `TypeError("number.padEnd is not a function")`, and an
  object whose `ljust` member is a function runs it where the spelling
  gives undefined. Every such program raised the alias's `TypeError` at
  its declaration at the accepted revision.
- At the accepted revision each of these calls raises
  `TypeError("<text>.<name> is not a function")`, unless an argument
  raises first. Only those calls change, along with the programs that
  caught that error. Property reads without a call, other receivers,
  user-defined methods, functions, variables and object members of these
  names, the `String.<name>` statics and every accepted result keep their
  meanings.
- Not added: Python's and Ruby's `center`, Python's `zfill`, Python's and
  C#'s one-character fill check, Swift's
  `padding(toLength:withPad:startingAt:)`, static calls such as
  `String.rjust`, the names `padLeft`, `padRight`, `pad` and `PadStart`,
  which `tests/string_padding.rs` keeps as no functions, completion words,
  and any keyword, token, syntax or public item. Kotlin's `padStart` and
  `padEnd` already are the accepted names.
- These are familiar names for Nucleoid's accepted operation, not a claim
  of full Python, Ruby or C# compatibility. The continuous Language
  compatibility policy skips token comparison entirely; every hard
  criterion and independent check still applies.
- The authoritative contract is
  [Padding method aliases](../nucleoid.spec.md#padding-method-aliases).

## Motivation

- Programmers and language models align text with the padding names of
  their own language: Python writes `str(n).rjust(3, "0")` and
  `name.ljust(12)`, Ruby writes `id.to_s.rjust(3, "0")` and
  `name.ljust(12)`, and C# writes `code.PadLeft(3, '0')` and
  `name.PadRight(12)`. Nucleoid accepts the same operation as `padStart`
  and `padEnd`, but at the accepted revision each of these names raises:
  - `"ab".ljust(5)` raises `TypeError("ab.ljust is not a function")`, at
    line 1, column 1 of its statement;
  - `"ab".rjust(5, "0")`, `"ab".PadLeft(5)` and `"ab".PadRight(5, ".")`
    raise the same error with their own names.
- World models render aligned text from live values: zero-padded ticket,
  room and order numbers, and the columns of a report or a receipt. These
  renderings are standing declarations and class-level rules, so they must
  follow every later write, which `padStart` and `padEnd` already do and
  the aliases inherit.
- Ruby's fill rule is the accepted one: `"ab".padStart(7, "xy")` is
  `"xyxyxab"` and `"ab".padEnd(7, "xy")` is `"abxyxyx"`, which Ruby's
  `rjust` and `ljust` give for the same arguments. Python and C# take a
  single fill character, on which every spelling agrees.
- The names are free on strings: a property read such as `s.ljust` reads
  `null`, object members and instance methods of these names keep their
  values, and numbers, lists and `null` keep their accepted results. No
  accepted document case, dataset record or test calls them on a string.
- The aliases advance the language-superset aspiration of the Language
  compatibility category. The accepted `this`/`self`, `=>`/`->`, `lower`,
  `upper`, `strip`, `find`, `contains`, `substr`, and the string aliases of
  [NUC 110](nuc-0110.md), [NUC 116](nuc-0116.md), [NUC 118](nuc-0118.md),
  [NUC 131](nuc-0131.md) and [NUC 132](nuc-0132.md) follow the same
  pattern: an equivalent familiar spelling beside the canonical one, with
  no change to any accepted program.
- One shared implementation keeps each alias equal to its accepted spelling
  by construction, without a second padding routine or a parse-time
  rewrite that would change how a call renders.
- Python's `str.rjust` and `str.ljust`, Ruby's `String#rjust` and
  `String#ljust`, and C#'s `String.PadLeft` and `String.PadRight` are the
  prior art.

## Rationale

- **Category and mode.** The allocating continuous cycle found no stale
  Draft, drew Language compatibility with one tool-backed uniform draw
  over the five categories that NUC 1's registry marks eligible for
  automatic selection, index 4 with probability 1/5 at 23:24:42 on
  27-Nov-2026 and no redraw, and recorded the requested change in the
  allocation commit `c9eb7758`, which this revision pins. Token comparison
  is therefore skipped as `language_compatibility`. The skip is
  categorical; it is neither a measured comparison nor a passing token
  gate. Runtime applicability does not apply to this category.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts and no extra baselines. They execute their
  assertions and explicit returns with full coverage, and every
  pre-existing case is unchanged.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Only former errors.** At the accepted revision every call of the four
  names on a string receiver raises
  `TypeError("<text>.<name> is not a function")` at column 1 of the
  running statement, in plain and JSON output alike, unless an argument
  raises first. No accepted test, document case, dataset record or ARC
  dataset calls them, and no test pins that error; only NUC 111's prose
  names Python's `rjust` and `ljust`.
- **One arm per side.** The aliases join the two accepted arms of the
  private `string_transform` that hold `padStart` and `padEnd`, as
  [NUC 110](nuc-0110.md) added `strip` to `trim` and
  [NUC 118](nuc-0118.md) its names to the case arms, so each alias calls
  the accepted `string_pad` with the same side and the same arguments by
  construction. `rustfmt` wraps each widened arm into three lines, which
  takes `string_transform` from 50 to 54 of Clippy's 60 counted lines.
  Rejected:
  - a parse-time rewrite, which would render `padStart` where the source
    wrote `rjust` in statements, `why`, `affects`, `--graph` and graph keys;
  - a second padding routine, which could drift from the accepted one;
  - a helper that resolves the six names to a side before the dispatch,
    which a first prototype measured at 48 counted lines: it restructures
    the accepted dispatch although the widened arms stay within the limit;
  - a table of alias names consulted before the dispatch, which would add a
    lookup to every string method call.
- **Strings only.** `padStart` and `padEnd` are string methods, and so are
  their aliases. Lists, populations, numbers and every other receiver keep
  their accepted readings, and with them their errors; a list of strings
  pads as `names.map(name -> name.ljust(8))`.
- **Calls only.** Reading `s.ljust` without a call stays undefined, as
  reading `s.padEnd` does, and assigning it keeps its accepted `TypeError`.
  A property alias would change accepted outputs, since those reads give
  `null`.
- **Arguments.** The receiver is read first and then every argument once,
  left to right, as for every call, because the string route evaluates the
  arguments before any string method runs. The accepted spellings ignore
  further arguments, and so do the aliases.
- **Per evaluation of the receiver.** The aliases are methods of strings,
  not rewrites of the call, so the receiver decides the reading each time a
  call is evaluated. A standing call whose receiver a later write turns
  into another kind of value reads the alias's name on that value, as
  [Calls](#calls) says for every other receiver, while the spelling reads
  `padStart` or `padEnd` there. The two then differ in exactly the ways
  [Per evaluation](#per-evaluation) lists: an error that names the method
  as written, a member of the alias's name that runs, and the dependency on
  that member. Each such program raised the alias's `TypeError` at the
  accepted revision, at the declaration. Rejected: converting a non-string
  receiver's text, which would give lists, numbers and objects methods they
  do not have, and raising the spelling's error instead, which would add a
  second error message for one call.
- **Live and rendered as written.** While the receiver is a string, a
  declaration or class-level rule that calls an alias depends on what its
  spelling depends on: the receiver, the length and the fill, in reading
  order. Statements, `why`, `affects`, `--graph` and graph keys render the
  call as every call is rendered, with the name the source wrote.
- **Source-language differences stay documented, not emulated.**
  - Python's `rjust` and `ljust` raise
    `TypeError("The fill character must be exactly one character long")`
    for a longer or empty fill, and C#'s `PadLeft` and `PadRight` take one
    `char`. The aliases repeat and cut any fill, as `padStart`, `padEnd`
    and Ruby's `rjust` and `ljust` do, because an alias means its accepted
    spelling and a second fill rule would make two spellings of one
    operation disagree.
  - An empty fill returns the text, as the accepted spellings return it,
    where Ruby raises `ArgumentError` for zero-width padding.
  - A negative length returns the text, where C# raises
    `ArgumentOutOfRangeException`; Python and Ruby return the text too.
  - C# counts UTF-16 code units, so an emoji takes two places there and
    `"😀".PadLeft(3)` holds one space in C#, while Python and Ruby count
    code points, as the aliases count Unicode scalar values and give
    `"  😀"`.
  - A string or boolean length and a fill that is not a string convert as
    for `padStart`: `"4"` is 4 and the fill `0` is `"0"`, where Python and
    Ruby raise `TypeError`. A fractional length truncates, `2.9` being 2,
    as Ruby truncates it, where Python raises `TypeError`.
  - Python's and Ruby's `center` has no accepted spelling, and Python's
    `zfill` puts its zeros after a sign, `"-42".zfill(5)` being `"-0042"`,
    so neither is an alias of `padStart` or `padEnd`.
  - Swift's `padding(toLength:withPad:startingAt:)` needs argument labels,
    which Nucleoid calls do not have, and pads only at the end.
  - Kotlin's `padStart` and `padEnd` are the accepted names already.
  - Static calls such as `String.rjust("7", 3)` keep
    `TypeError("String.rjust is not a function")`, as every static name of
    `String` but `fromCharCode` does.
- **Kept no-function names.** `padLeft`, `padRight`, `pad` and `PadStart`
  stay unknown, because NUC 111's accepted test
  `tests/string_padding.rs` pins them as
  `TypeError("7.<name> is not a function")` through the public
  `string_method`, and changing a pinned accepted result would break
  backward compatibility. Dart's `padLeft` and `padRight` are among them;
  they also repeat a longer padding whole rather than cutting it.
- **Completion.** The terminal workspace offers the JavaScript names of
  string members, `padStart` and `padEnd`, and none of the accepted
  aliases, as [NUC 110](nuc-0110.md), [NUC 116](nuc-0116.md),
  [NUC 117](nuc-0117.md), [NUC 118](nuc-0118.md), [NUC 131](nuc-0131.md)
  and [NUC 132](nuc-0132.md) kept it. This proposal follows that precedent
  and adds no completion entry.
- **Public API.** No public item is added or removed, and no signature
  changes. `nucleoid::builtins::string_method`, the public function behind
  every string method, accepts the four names where it returned the
  `TypeError`, as it accepted `startswith` and `endswith` in
  [NUC 110](nuc-0110.md) and the case names in [NUC 118](nuc-0118.md). The
  widened set of names is the change to report for semantic-versioning
  review; no version number changes.
- **`Requires: 111`.** The aliases are names of NUC 111's `padStart` and
  `padEnd` and share their `string_pad`, so they depend on that accepted
  proposal and inherit its conversions, bounds and liveness.
- **Not added.** Property aliases, static forms, aliases on lists,
  populations or other receivers, the names left out above, a fill check,
  completion entries and any change to `padStart` or `padEnd`.

## Specification

- The normative contract is
  [Padding method aliases](../nucleoid.spec.md#padding-method-aliases).

### Calls

- `RECEIVER.rjust(...)` and `RECEIVER.PadLeft(...)` are
  `RECEIVER.padStart(...)`, and `RECEIVER.ljust(...)` and
  `RECEIVER.PadRight(...)` are `RECEIVER.padEnd(...)`, with the same
  arguments, whenever `RECEIVER` evaluates to a string.
- Strings are reached however the language reaches them: literals, names,
  properties and instance properties, indexes, call and query results such
  as `split`, `map`, `slice`, `substring`, `join` and `repeat`, templates,
  `.value` snapshots, state versions, the results of conditional
  expressions and `String(...)`, `$Name.property` inside class-level rules,
  and the empty string.
- On every other receiver the names keep the readings of
  [Compatibility](#compatibility).

### Padding

- With `missing` the length minus the number of characters of `TEXT`, the
  result is `TEXT` unchanged when `missing` is 0 or less or the fill is
  empty. Otherwise the padding is the characters of the fill repeated and
  cut to exactly `missing` characters, before `TEXT` for `rjust` and
  `PadLeft` and after it for `ljust` and `PadRight`, as
  [NUC 111](nuc-0111.md) defines for `padStart` and `padEnd`.
- Each row gives the same result with both names of its side, and with
  `padStart` or `padEnd`:

| Call | Result |
| --- | --- |
| `"7".rjust(3, "0")`, `"7".PadLeft(3, "0")` | `"007"` |
| `"ab".ljust(4, ".")`, `"ab".PadRight(4, ".")` | `"ab.."` |
| `"ab".rjust(5)`, `"ab".ljust(5)` | `"   ab"`, `"ab   "`: one space |
| `"ab".rjust(7, "xy")`, `"ab".ljust(7, "xy")` | `"xyxyxab"`, `"abxyxyx"` |
| `"5".rjust(4, "123456")`, `"abc".ljust(6, "123456")` | `"1235"`, `"abc123"` |
| `"long".rjust(2, "0")`, `"5".PadLeft(4, "")` | `"long"`, `"5"` |
| `"".ljust(3, "ab")` | `"aba"` |
| `"x".ljust(L, "-")` for `L` of `"4"`, `2.9`, `-3`, `null` and NaN | `"x---"`, `"x-"`, `"x"`, `"x"`, `"x"` |
| `"5".rjust(3, F)` for `F` of `0`, `null`, `true`, `""`, none and `undefined` | `"005"`, `"nu5"`, `"tr5"`, `"5"`, `"  5"`, `"nu5"` |
| `"5".PadLeft(4, o.missing)` after `o = {}` | `"   5"`: an undefined fill is one space |
| `"😀".PadLeft(3)`, `"Zoë".PadRight(5, "·")` | `"  😀"`, `"Zoë··"` |
| `"日".rjust(3, "本")`, `"x".PadLeft(4, "😀é")` | `"本本日"`, `"😀é😀x"` |
| `"7".rjust(3, "0", "extra")` | `"007"` |
| `"x".ljust(1 / 0)`, `"x".rjust(1e15)` | `TypeError("Padded string is too large")` |

- This program is the specification entry
  `Nucleoid pads strings with Python's and Ruby's rjust and ljust`:

```
orders = ["7", "42", "305"]
numbers = orders.map(order -> order.rjust(4, "0"))
item = "tea"
width = 8
row = item.ljust(width, ".") + "|"
assert(numbers, ["0007", "0042", "0305"])
assert(row, "tea.....|")
orders.push("1234")
item = "honey"
width = 7
assert(numbers, ["0007", "0042", "0305", "1234"])
assert(row, "honey..|")
assert(["ab".rjust(7, "xy"), "ab".ljust(7, "xy"), "5".rjust(3), "long".ljust(2)], ["xyxyxab", "abxyxyx", "  5", "long"])
row
```

- This returns `"honey..|"`: the zero-padded order numbers follow the
  pushed order and the row follows its item and width.
- Characters are Unicode scalar values, as `length` counts them. This
  program is the specification entry
  `Nucleoid pads strings with C#'s PadLeft and PadRight`:

```
name = "Zoë"
code = "7"
cell = name.PadRight(6, "·") + code.PadLeft(3, "0")
assert(cell, "Zoë···007")
name = "Ana"
code = "12"
assert(cell, "Ana···012")
assert(["😀".PadLeft(3), "añejo".PadRight(7, "*"), "x".PadLeft(4, "😀é")], ["  😀", "añejo**", "😀é😀x"])
mark = String.fromCharCode(101, 769)
assert([mark.PadLeft(3, "-"), mark.PadLeft(3, "-").length], ["-" + mark, 3])
cell.length
```

- This returns `9`. A combining mark is a character of its own, so `e`
  followed by a combining acute accent counts two and pads with one dash.

### Mapped and class-level padding

- A padding call inside a mapping follows the list, and a class-level rule
  pads each instance's own properties. This program is the specification
  entry `Nucleoid keeps padding aliases live in class level rules`:

```
class Room(floor, number):
    this.floor = floor
    this.number = number
$Room.label = String($Room.floor).rjust(2, "0") + "-" + String($Room.number).PadLeft(3, "0")
suite = Room(3, 7)
hall = Room(12, 45)
assert([suite.label, hall.label], ["03-007", "12-045"])
suite.number = 120
hall.floor = 4
assert([suite.label, hall.label], ["03-120", "04-045"])
signs = Room.map(room -> room.label.ljust(8, "."))
Room(1, 1)
assert(signs, ["03-120..", "04-045..", "01-001.."])
signs.length
```

- This returns `3`: the population mapping follows the room created last.
- Inside a class-level rule or conditional `$Name` is the instance, so
  `$Name.rjust(3)` there calls the instance's own `rjust` member or gives
  undefined, while `$Name.property.rjust(3)` pads the property's string.

### Evaluation

- The receiver is read first, and then every supplied argument once, left
  to right, including unused extras, as for every call: after the
  definitions of `text()`, `size()` and `fill()`, each of which pushes its
  name to `log`, `text().rjust(size(), fill(), log.push("extra"))` leaves
  `log` as `["text", "size", "fill", "extra"]`.
- A missing name among the arguments raises
  `ReferenceError("<name> is not defined")` before the alias runs:
  `"5".rjust(missing)` raises it, as `"5".padStart(missing)` does, and a
  failed statement rolls back the effects of the arguments before it.
- A `null` or undefined receiver keeps the accepted route: the call is
  undefined and the arguments are not evaluated, so after `u = null`,
  `u.rjust(missing)` is undefined.
- A declaration whose receiver, length or fill reads a `null` binding holds
  `null` until the binding is defined, as for `padStart`: after
  `fill = null`, `shown = "5".rjust(3, fill)` holds `null`, and
  `fill = "0"` makes it `"005"`.

### Liveness and class-level rules

- While its receiver is a string, a declaration that calls an alias depends
  on what its spelling depends on: writes of the name, the property or the
  instance property that holds the string, of the length and the fill, and
  pushes to the list of a mapping re-evaluate it. `(why shown)[0].from` is
  `["label","width","fill"]` after `shown = label.rjust(width, fill)`, as
  after `shown = label.padStart(width, fill)`, and the nodes, sources and
  values of the `why` and `affects` steps are the spelling's; only their
  rules name the call as written.
- In a class-level rule or conditional each instance evaluates its own
  alias over its own properties, and a write of the property re-evaluates
  that instance's rule; a population mapping follows new instances.

### Per evaluation

- An alias equals its spelling only while its receiver evaluates to a
  string. When a later write replaces a held receiver with another kind of
  value, the re-evaluated call reads the alias's name on that value, as
  [Calls](#calls) says for every other receiver. After `s = "ab"` and
  `u = s.ljust(4, ".")`, against `u = s.padEnd(4, ".")`:

| Later write | `u = s.ljust(4, ".")` | `u = s.padEnd(4, ".")` |
| --- | --- | --- |
| `s = "cd"` | `u` is `"cd.."`, read from `s` | The same |
| `s = ["x"]` | `TypeError("s.ljust is not a function")` at the write, which rolls back | `TypeError("s.padEnd is not a function")`, which rolls back |
| `s = 7` | `TypeError("number.ljust is not a function")`, which rolls back | `TypeError("number.padEnd is not a function")`, which rolls back |
| `s = false` | `TypeError("boolean.ljust is not a function")`, which rolls back | `TypeError("boolean.padEnd is not a function")`, which rolls back |
| `s = Date(0)` | `TypeError("Date.ljust is not a function")`, which rolls back | `TypeError("Date.padEnd is not a function")`, which rolls back |
| `s = {ljust: (n, f) -> "own"}` | `u` is `"own"`, read from `s` and the object's `ljust` | `u` is `null`, read from `s` and the object's `padEnd` |
| `class Box:` with `def ljust(n, f) => "boxed"`, then `s = Box()` | `u` is `"boxed"`, read from `s` | `u` is `null`, read from `s` and `s.padEnd` |
| `s = {other: 1}` | `u` is `null`, read from `s` and the object's `ljust` | `u` is `null`, read from `s` and the object's `padEnd` |
| `s = null` | `u` is `null`, read from `s` | The same |

- The other three aliases behave alike with their own names, `rjust` and
  `PadLeft` against `padStart`. Every program in this table raised
  `TypeError("ab.ljust is not a function")` at the declaration at the
  accepted revision, so none of these differences changes an accepted
  result.

### Transactions

- Errors of an alias propagate through the existing transaction, so a
  failed standing re-evaluation rolls back the change that triggered it: a
  length written `1 / 0` under `ticket = "42".rjust(width, fill)`, raising
  `TypeError("Padded string is too large")`, a push whose mapping reads an
  undefined length, raising `ReferenceError("size is not defined")`, and a
  name written a number under `out = label.ljust(4, ".")`, raising
  `TypeError("number.ljust is not a function")`. A failed statement or
  transaction restores declarations that call aliases, their values and
  their dependencies. This program is the specification entry
  `Nucleoid rolls back failed updates through padding aliases`:

```
width = 4
fill = "0"
ticket = "42".rjust(width, fill)
failure = ""
try:
    width = 1 / 0
catch error:
    failure = error
assert(failure, TypeError("Padded string is too large"))
assert([width, ticket], [4, "0042"])
ids = []
tags = ids.map(id -> id.PadRight(size, "-"))
try:
    ids.push("a")
catch error:
    failure = error
assert(failure, ReferenceError("size is not defined"))
assert([ids, tags], [[], []])
size = 3
ids.push("a", "bb")
assert(tags, ["a--", "bb-"])
try:
    fill = "*"
    size = 4
    assert([ticket, tags], ["**42", ["a---", "bb--"]])
    throw "UNDO"
catch error:
    assert(error, "UNDO")
assert([ticket, fill, tags], ["0042", "0", ["a--", "bb-"]])
ticket
```

- This returns `"0042"`.

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` and graph and block keys show the
  call in the canonical rendering of every call, with its name as written:
  after `shown = label.rjust(width, fill)`, `(why shown)[0].rule` is
  `"shown = label.rjust(width,fill)"`, where the spelling's is
  `"shown = label.padStart(width,fill)"`, and
  `$Room.k = $Room.name.PadRight(4, ".")` renders as
  `$Room.k=$Room.name.PadRight(4,".")`.
- While the receiver is a string, the dependencies are those of the
  accepted spelling, and `--graph` prints `shown [variable]` with
  `reads    label, width, fill`, as for `padStart`.
  [Per evaluation](#per-evaluation) lists the dependencies after a write
  replaces the string with an object or instance.

### Cost

- Each alias is one more name in the match pattern of its spelling's arm,
  so a call runs exactly the code of `padStart` or `padEnd`: the string
  route evaluates the arguments, and `string_pad` sizes the whole result
  with checked arithmetic, reserves it once and writes it.
- **Spot check, a phase-1 result.** Measured, not projected, on
  `nucleoid-phase1.exe`, the phase-1 release build, whose production code
  the final tree keeps byte for byte, through the command line with
  `--json`, rustc 1.97.1: the median of 21 interleaved runs of each
  program, including process start, one process at a time with nothing
  else running and each capped at 1.5 GB and 120 seconds, against the
  accepted revision's release build for the accepted spellings. Times are
  in milliseconds.
  - "One pad" pads `"x"` once to 100,000 characters with the fill `"ab"`;
    starting the binary and printing a number alone takes 12.8 ms on the
    candidate's build and 12.5 ms on the accepted one.
  - "100,000 calls" maps `"x".repeat(100000).split("")` through
