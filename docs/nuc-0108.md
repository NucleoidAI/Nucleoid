# NUC 108 -- List and Population Partitions

```
NUC: 108
Title: List and Population Partitions
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Utility enhancement
Created: 16-Nov-2026
Requires: 61, 73
```

## Abstract

- Adds the read-only list query `partition` to ordinary lists and class
  populations, the receivers of `filter`:
  - `xs.partition(predicate)` returns a list of two lists. The first holds
    the items that `xs.filter(predicate)` keeps, and the second the items
    it drops, each in receiver order. So
    `[3, 8, 1, 9].partition(x -> x > 4)` is `[[8, 9], [3, 1]]`.
  - The predicate runs once for every item, in receiver order, and the items
    are returned unchanged, so an instance stays the same instance. Every
    item lands in exactly one of the two lists, and an empty receiver gives
    `[[], []]`.
- `partition` never writes its receiver.
  `groups = Order.partition(o -> o.shipped)` is a standing split that
  follows later instances and later writes of the properties its predicate
  reads, as a standing `filter` does.
- For a predicate without side effects, `xs.partition(p)` evaluates to
  exactly the list that `[xs.filter(p), xs.filter(x -> not p(x))]`
  evaluates to at the accepted revision, which runs the predicate twice for
  every item. Only a receiver that creates objects differs: the spelling
  evaluates it twice, so its second list holds equal objects of the second
  evaluation.
- Only calls of `partition` on lists and class populations change. They
  raised `TypeError("<receiver>.partition is not a function")` at the
  accepted revision. Reading `xs.partition` without a call, object
  properties named `partition`, instance methods named `partition` called
  on an instance, and every other receiver keep their accepted behavior.
- No token, keyword, syntax, error type or message format, option or public
  item is added. The authoritative contract is
  [List and population partitions](../nucleoid.spec.md#list-and-population-partitions).

## Motivation

- World models sort their objects into two kinds by one rule: shapes
  inside or outside a region, cells of the background color or of an
  object, orders shipped or pending, readings over or under a threshold.
  Accepted Nucleoid states each side with its own `filter`, so the rule is
  written twice, the second time negated:

  ```
  class Order:
      def init(total, shipped):
          this.total = total
          this.shipped = shipped
  Order(40, true)
  Order(15, false)
  Order(90, true)
  [Order.filter(o -> o.shipped).map(o -> o.total), Order.filter(o -> not o.shipped).map(o -> o.total)]
  ```

  It returns `[[40, 90], [15]]`. The two predicates must be kept in step by
  hand: a rule changed on one side only drops or duplicates items without
  any error, and every item is tested twice.
- `Order.partition(o -> o.shipped)` states the rule once, returns both
  sides in receiver order, and tests every item once.
- The accepted list queries already derive new lists without writing their
  receiver: `filter`, `map`, `flatMap`, `distinct` and
  [NUC 105](nuc-0105.md)'s `sortBy`, while [NUC 73](nuc-0073.md)'s `count`
  counts the items a predicate keeps. A partition is the two-sided
  `filter`.
- Prior art: Kotlin's `partition`, which returns a pair of lists; Scala's
  and Haskell's `partition`; Rust's `Iterator::partition`; Ruby's
  `Enumerable#partition`; Elixir's `Enum.split_with`; and Lodash's
  `_.partition`.
- `Order.partition(o -> o.shipped)` is ten lexer tokens against 24 for
  `[Order.filter(o -> o.shipped), Order.filter(o -> not o.shipped)]`, and 21
  when the kept side is the [NUC 79](nuc-0079.md) selector
  `Order.filter(.shipped)`. Both totals of the example above take 26 tokens
  as `Order.partition(o -> o.shipped).map(side -> side.map(o -> o.total))`
  against 42 for its last line.

## Rationale

- **Category and mode.** The cycle that allocated this Draft made one
  tool-backed uniform draw over the five categories that NUC 1's registry
  marks eligible for automatic selection and selected Utility enhancement,
  index 2, with probability 1/5 and no redraw. Within it, the caller chose
  the two-sided `filter`, which no NUC proposed. Token comparison is
  required; runtime applicability does not apply to this category.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero. Strategy learning is `not_configured`, so this
  revision is unattributed, with no policy, selection receipt, trial or
  reward.
- **One more shared query.** `partition` joins `Runtime::list_query` beside
  `filter` and `count`, so lists however they are reached, through
  variables, members, slices, call results, `.value` snapshots and selected
  state versions, and class populations named by the class, by a variable
  that holds the class or by `$Name`, gain it at once, with the receiver
  snapshot, argument evaluation, receiver text and null-receiver routing of
  every other query. Rejected: a list-only method, which would leave
  `Name.partition(p)` raising where `Name.filter(p)` runs.
- **Two lists in a list.** The result is the list `[first, second]`, the
  shape of Kotlin's pair, Scala's and Haskell's tuples, Rust's tuple, Ruby's
  and Lodash's two-element arrays and Elixir's two-element tuple, all of
  which hold the kept items first. The language has no tuple, so a list of
  two lists indexes as `parts[0]` and `parts[1]`, maps as
  `parts.map(side -> side.length)`, and [NUC 67](nuc-0067.md)'s positional
  destructuring names the sides: `shipped, pending = Order.partition(...)`
  declares `shipped = Order.partition(...)[0]` and
  `pending = Order.partition(...)[1]`, each a standing declaration that runs
  its own partition.
- Rejected: an object with named sides such as `{kept, dropped}`, which no
  prior art uses and which would fix two property names in the language; a
  `groupBy` with more than two groups, which is another query; and the order
  of Python's `more_itertools.partition`, which yields the dropped items
  first, unlike every other prior art above and unlike `filter`, whose kept
  items the first list repeats.
- **Truthiness, as in `filter`.** An item goes to the first list exactly
  when `filter` would keep it, so `false`, `0`, `-0`, NaN, `""`, `null` and
  undefined results send it to the second, and every other value, including
  `[]`, `{}` and `"0"`, to the first. The second list is therefore exactly
  what `filter(x -> not predicate(x))` keeps. A negated comparison is not
  always that complement: NaN, undefined, as a missing property reads,
  strings that are not numeric and objects make both `x > 4` and `x <= 4`
  false, so `[1, 0 / 0, 9].partition(x -> x > 4)` puts NaN in the second
  list, where `[1, 0 / 0, 9].filter(x -> x <= 4)` drops it.
- **Every item exactly once.** The predicate is called once for every item,
  in receiver order, with only the item, as `filter` calls it, and each item
  lands in exactly one list by that one result. The accepted spelling calls
  the predicate twice for every item, first for all items and then again,
  so a predicate with side effects or one whose result changes between calls
  can put an item in both lists or in neither, as the accepted spelling
  differences below show.
- **The predicate is required.** A missing first argument, or one that is
  not a function, including `null`, raises
  `TypeError("partition expects a function")` after the arguments are
  evaluated, even on an empty receiver, as `filter` raises
  `TypeError("filter expects a function")`.
- Rejected: an identity default, Lodash's `_.partition(xs)`, which splits
  truthy items from falsy ones but would make `xs.partition()` succeed where
  `xs.filter()` raises; property-name predicates such as
  `Order.partition("shipped")`, which Lodash accepts and
  [NUC 69](nuc-0069.md), [NUC 77](nuc-0077.md) and [NUC 105](nuc-0105.md)
  rejected for their queries; and an index argument, which `filter` does not
  pass either.
- **The items themselves.** The query splits the objects of a model, so it
  returns those objects, unchanged and in receiver order, as every prior art
  above does. The receiver is never written: `call_method` routes only
  `sort` through its writable-receiver path.
- **Instance lists.** On a class name, `Name.partition(...)` is the
  population query even when the class declares an instance method
  `partition`, as for `filter`. The method stays reachable through each
  instance.
- **No noun form.** [NUC 75](nuc-0075.md)'s `NOUN of OPERAND` takes no
  argument, and `partition` needs its predicate, so `partition of xs` keeps
  raising `SyntaxError("Unexpected keyword 'of'")`.
- **Bounded cost.** The receiver and the arguments are evaluated once per
  call and the predicate once per item, in one pass that appends each item
  to one of the two lists, so a call is linear in the receiver. The accepted
  spelling reads the receiver twice and calls the predicate twice for every
  item.
- **Rendered as written.** Statements render as written, so `why` reports
  `split = readings.partition(function())`, as it renders every function
  argument, and a `partition` call and its accepted spelling are different
  statements and graph keys. Rejected: lowering `partition` to its accepted
  spelling, which would render a second callback the source never wrote and
  call the predicate twice.
- **Where the accepted spelling differs.** The parity holds for a predicate
  without side effects over a receiver that creates no objects. These
  programs differ:
  - A predicate with side effects runs once per item: after `calls = []` and
    `xs = [1, 2, 3]`, `r = xs.partition(x -> calls.push(x) > 0 && x > 1)`
    leaves `calls` as `[1, 2, 3]`, while
    `r = [xs.filter(x -> calls.push(x) > 0 && x > 1), xs.filter(x -> !(calls.push(x) > 0 && x > 1))]`
    leaves it as `[1, 2, 3, 1, 2, 3]`. Both give `r` as `[[2, 3], [1]]`.
  - A predicate whose result changes between calls: with a `toggle` helper
    that flips a stored flag and returns it, starting from `false`,
    `[1, 2, 3].partition(x -> toggle(x))` is `[[1, 3], [2]]`, while
    `[xs.filter(x -> toggle(x)), xs.filter(x -> !toggle(x))]` over the same
    list is `[[1, 3], [1, 3]]`: `1` and `3` in both lists and `2` in
    neither.
  - A receiver that creates objects is evaluated once: after
    `[{n: 3}, {}, {n: 9}].partition(x -> x.n > 4)`, both lists hold the
    three objects of that one list literal, while the accepted spelling
    evaluates the literal twice, so its second list holds the equal objects
    of the second evaluation. JSON output is the same; plain output, which
    names each object, and the graph show the extra objects.
  - `why`, `affects`, `--graph` output and graph and block keys name the
    call as written: `split = readings.partition(function())` against
    `split = [readings.filter(function()),readings.filter(function())]`, and
    an `if` whose condition holds the call is the block
    `if(xs.partition(function()).length>0)`.
- **Pre-existing defects stay.** Every callback shares two defects of the
  accepted revision, `filter`'s included, and so does a `partition`
  predicate. This proposal neither fixes nor pins them, and its cases stay
  clear of them:
  - `def key(t):` with the body `if t.n > 1:` / `return 1` and then
    `return 0`, followed by `xs = [{n: 1}, {n: 2}]`,
    `ys = xs.filter(x -> key(x))` and `xs[1].n = 0`, raises
    `ReferenceError("t is not defined")` at line 7, as
    [NUC 105](nuc-0105.md) records;
  - a callback in a function body cannot read the function's parameters:
    after `def split(values, limit) => values.filter(v -> v > limit)`,
    `split([1, 5, 9], 4)` raises `ReferenceError("limit is not defined")`.
    The same body with `partition` raised
    `TypeError("values.partition is not a function")` at the accepted
    revision and raises that `ReferenceError` under this NUC, as the
    `filter` body does. A callback that reads a binding outside the function
    works.
- **Requires.** [NUC 61](nuc-0061.md), whose shared list queries,
  population receivers, ranges and `list()` `partition` joins, and
  [NUC 73](nuc-0073.md), whose `count(predicate)` fixed the receivers,
  predicate invocation and truthiness of `filter` that `partition` shares.
  The Draft's list stands: those two already require everything else
  `partition` relies on.
- **Not added.** A global `partition(...)`, `partition of xs`, an identity
  default, property-name predicates, an index argument, more than two
  groups, named sides, an in-place partition, aliases such as `splitWith`,
  `span` or `reject`, `partition` on strings, objects or instances, and any
  change to what `filter`, `count` or the other queries return.

### Counterparts

- Every new case is compared with the most compact accepted-syntax program
  found that reaches the same canonical assertions in the same order and the
  same expected return. Each differs from its case only where an
  `R.partition(p)` is written out; every other line is the case's own.
- Every partition reads a receiver that later changes: pushed, shifted and
  replaced items, new and deleted instances, a changed threshold and changed
  properties. Every case asserts the items of both lists and their order,
  not only their lengths, so no count of either side reaches its assertions,
  and every case changes what both lists hold, so neither list is constant.
- The counterparts write `R.partition(p)` as `[R.filter(p), R.filter(q)]`,
  where `q` is the exact complement of `p` on every value the case produces:
  - a truthiness test negates with `!`, as `order -> !order.shipped`;
  - a comparison negates to the opposite comparison, `<=` for `>`, `<` for
    `>=` and `>=` for `<`, which is the complement because every compared
    value of the case is a finite number, or a string compared with a
    string;
  - a kept side that tests one property is the [NUC 79](nuc-0079.md)
    selector `R.filter(.p)`, three tokens shorter than
    `R.filter(x -> x.p)`;
  - in the class-level rule of the examples case, the receiver
    `$Store.shelves` is the [NUC 102](nuc-0102.md) receiver read `.shelves`,
    one token shorter per use.
- The cases themselves may hold neither selectors nor receiver reads, since
  `tests/property_selectors.rs` and `tests/implicit_receivers.rs` reserve
  them for the cases of NUC 79 and NUC 102. The extra baselines are not
  document cases, so those audits do not apply to them, and a more compact
  counterpart only makes the comparison stricter.
- Measured and rejected as longer: the same counterparts without selectors
  or receiver reads; complements written `not (...)`, two tokens more than
  `!` and three more than a negated comparison; comprehensions
  `[[x for x in R if P], [x for x in R if Q]]`, one token more per list than
  a filter with an arrow; `lambda x:` predicates, one token more each; and a
  named predicate helper, as `def high(reading) => reading > limit` with
  `[readings.filter(high), readings.filter(reading -> !high(reading))]`,
  170 tokens for the first case against 162, which also adds a line outside
  the call. Count-based spellings, `count` or `length` subtraction, fail the
  item assertions, and a literal for either list fails once the receiver
  changes.

## Specification

- The normative contract is
  [List and population partitions](../nucleoid.spec.md#list-and-population-partitions).

### Calls

- `RECEIVER.partition(PREDICATE, ...)` is a list query when `RECEIVER`
  evaluates to a list, including a member, an index, a slice, a call result,
  a `.value` snapshot and a list read from a state version, or to a declared
  class, named by the class, by a variable that holds the class or by
  `$Name`, whose population in population order is the receiver.
- The receiver is read once, before the arguments. Every supplied argument
  is then evaluated once, left to right, and only the first is used.
- A `null` or undefined receiver keeps the accepted method route: the
  arguments are not evaluated and the call is undefined, so a declaration
  holding it stores `null` and re-runs once the receiver exists.
- On a class name the call is the population query even when the class
  declares an instance method `partition`; `instance.partition(...)` keeps
  calling the method.

### The two lists

- The result is a new list of exactly two new lists. The first holds the
  items whose predicate result is truthy, in receiver order, and the second
  every other item, in receiver order. The items are the items themselves:
  an object or instance stays the same object.
- An empty receiver gives `[[], []]`. The receiver is never written,
  whatever its kind.

```
readings = [12, 31, 7, 45, 18]
limit = 20
split = readings.partition(reading -> reading > limit)
assert(split, [[31, 45], [12, 7, 18]])
readings.push(26)
assert(split, [[31, 45, 26], [12, 7, 18]])
limit = 15
assert(split, [[31, 45, 18, 26], [12, 7]])
assert(readings, [12, 31, 7, 45, 18, 26])
readings = []
assert(split, [[], []])
split.length
```

- This returns `2`: even an empty receiver gives two lists.

### Truthiness

- The predicate's result decides as it decides for `filter`. These results
  send an item to the second list, and every other result to the first:

| Result | List |
| --- | --- |
| `false`, `0`, `-0`, NaN, `""`, `null`, undefined | second |
| `true`, other numbers, other strings including `"0"`, `[]`, `{}`, dates, functions, regular expressions, instances | first |

```
answers = ["yes", "", 0, 7, false, "no"]
given = answers.partition(answer -> answer)
assert(given, [["yes", 7, "no"], ["", 0, false]])
answers.push([], "", true)
answers.shift()
assert(given, [[7, "no", [], true], ["", 0, false, ""]])
given[1].length
```

- This returns `4`.
- The second list is exactly the list that `R.filter(x -> not p(x))`
  keeps. A negated comparison is not always that complement: for an item
  that is NaN, undefined, as a missing property reads, a string that is not
  numeric or an object, both `x > 4` and `x <= 4` are false, so
  `x -> x > 4` sends it to the second list, where `R.filter(x -> x <= 4)`
  drops it. The same holds for a predicate that compares a property, such as
  `y -> y.k > 4` against `y -> y.k <= 4` for an item without `k`. The keyword
  `undefined` is `null`, which compares as `0`, so it does not differ.

### The accepted spelling

- For a predicate without side effects, `R.partition(p)` evaluates to
  exactly the list that `[R.filter(p), R.filter(x -> not p(x))]` evaluates
  to at the accepted revision.
- `partition` reads the receiver once and calls the predicate once per item,
  where that spelling reads the receiver twice and calls the predicate twice
  for every item. A predicate with side effects therefore sees half the
  calls, one whose result changes between calls still places every item in
  exactly one list, and a receiver that creates objects, such as a list
  literal of records, keeps the objects of its one evaluation in both lists,
  where the spelling's second list holds equal objects of a second
  evaluation, as [Where the accepted spelling differs](#rationale) shows.

### Predicates and reads

- The predicate is required. It is called once for every item, in receiver
  order, with the item as its only argument; further parameters are `null`,
  so `[5, 6].partition((x, i) -> i)` is `[[], [5, 6]]`. The call order and
  the argument are those of `filter`.
- A missing first argument, or one that is not a function, including `null`,
  raises `TypeError("partition expects a function")`, even on an empty
  receiver.
- Every supplied argument, including unused extras, is evaluated once, left
  to right, after the receiver and before the first predicate call.
- Reads inside a predicate follow the existing rules, so a predicate that
  reads a `null` binding, parameter or property settles a declaration to
  `null`, as it settles one that uses `filter`, while an item the predicate
  does not read stays an item.

| Exact source | Result |
| --- | --- |
| `xs = [1, null]`, then `r = xs.partition(x -> true)` | `r` is `[[1, null], []]` |
| `xs = [1, null]`, then `r = xs.partition(x -> x)` | `r` is `null` |
| `xs = [{k: null}, {k: 1}]`, then `r = xs.partition(x -> x.k)` | `r` is `null` |
| `limit = null`, `xs = [1, 5]`, `r = xs.partition(x -> x > limit)`, then `limit = 2` | `r` is `[[5], [1]]` |
| `xs = [1, null]`, then `xs.partition(x -> x)` as an expression statement | `[[1], [null]]` |

### Liveness and class-level rules

- A declaration that uses `partition` depends on the list or population, on
  its argument expressions and on whatever the predicate reads for every
  item. Pushing, popping, shifting or replacing a list, creating or deleting
  an instance, and changing a property or binding that the predicate reads
  re-evaluate it, and an item moves to the other list when its result
  changes.
```
class Order(item, shipped):
    this.item = item
    this.shipped = shipped
book = Order.partition(order -> order.shipped)
assert(book, [[], []])
pen = Order("pen", true)
ink = Order("ink", false)
cap = Order("cap", true)
assert(book, [[pen, cap], [ink]])
ink.shipped = true
pen.shipped = false
assert(book, [[ink, cap], [pen]])
delete pen.item
delete pen.shipped
delete pen
assert(book, [[ink, cap], []])
book[0][0] == ink
```

- This returns `true`: both lists keep population order, and the items are
  the instances themselves.
- In a class-level rule, each instance evaluates its own partition. This
  program is the one of `docs/examples.md`, since no specification entry
  partitions inside a class-level rule:

```
class Store(name, shelves):
    this.name = name
    this.shelves = shelves
$Store.restock = $Store.shelves.partition(shelf -> shelf.have < shelf.need).map(side -> side.map(shelf -> shelf.item))
north = Store("north", [{item: "tea", have: 2, need: 5}, {item: "jam", have: 9, need: 4}, {item: "oat", have: 1, need: 3}])
south = Store("south", [{item: "rice", have: 8, need: 2}])
assert([north.restock, south.restock], [[["tea", "oat"], ["jam"]], [[], ["rice"]]])
north.shelves[0].have = 7
south.shelves.push({item: "salt", have: 0, need: 1})
[north.restock, south.restock]
```

- This returns `[[["oat"],["tea","jam"]],[["salt"],["rice"]]]`: every store
  keeps its own two lists, and the south store's empty first list fills.

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` output and graph and block keys
  show the call as written, with function arguments rendered as
  `function()`: the rule that `why split` reports is
  `split = readings.partition(function())`. A `partition` call and its
  accepted spelling are different statements and keys.

### Transactions

- Predicate errors propagate through the existing transaction, so a failed
  standing re-evaluation rolls back the change that triggered it, including
  a list write or a new instance, and a failed statement or transaction
  restores partitioned declarations, their values and their dependencies.

```
parcels = [{code: "b2", kg: 4}, {code: "A7", kg: 9}]
weights = parcels.partition(parcel -> parcel.code.toUpperCase() < "B").map(side -> side.map(parcel -> parcel.kg))
failure = ""
try:
    parcels.push({code: 7, kg: 1})
catch error:
    failure = error
assert(failure, TypeError("number.toUpperCase is not a function"))
assert([parcels.length, weights], [2, [[9], [4]]])
parcels.push({code: "a1", kg: 2})
assert(weights, [[9, 2], [4]])
try:
    parcels[0].code = "a0"
    assert(weights, [[4, 9, 2], []])
    throw "UNDO"
catch error:
    assert(error, "UNDO")
weights
```

- This returns `[[9,2],[4]]`: the codes compare without regard to case, and
  the failed push and the undone rename leave the parcels and both lists as
  they were.

### Cost

- The receiver and the arguments are evaluated once per call, and the
  predicate once per item, in one pass that appends each item to one of the
  two lists, so a call is linear in the receiver.
- **Measured** on a release build of the candidate's library, rustc 1.97.1,
  through the public API, of `Runtime::run` calls of expression statements:
  `R.filter(p).length`, `R.partition(p)[1].length` and
  `[R.filter(p), R.filter(x -> not p(x))][1].length`. Each figure is the
  median of five calls, three from 500,000 items. A list holds a
  permutation of the numbers below its length in an object property, with
  `p` as `x -> x % 3 == 0`; a population of instances `Item(k)` with `k` as
  the position modulo 7 is created first by `while` loops, with `p` as
  `i -> i.k > 3`. The machine ran nothing else.

### Findings

- **Info, parity (F1).** [The accepted spelling](#the-accepted-spelling)
  equates `R.partition(p)` with `[R.filter(p), R.filter(x -> not p(x))]`
  for a predicate without side effects. Inside a function whose predicate
  is a parameter, that spelling cannot run:
  `def split(values, test) => [values.filter(test), values.filter(v -> not test(v))]`
  followed by `split([1, 5, 9], v -> v > 4)` raises
  `ReferenceError("test is not defined")` at both revisions, through the
  pre-existing callback defect that [Rationale](#rationale) records, while
  the same function with `values.partition(test)` returns `[[5, 9], [1]]`.
  The NUC documents the defect but not this direction of it, and there is
  no compatibility impact.
- **Info, rendering (F2).** For a receiver that creates objects,
  [Rationale](#rationale) says that JSON output is the same. The values
  are, but in JSON output the `from` lists of `why` and `affects` and
  template strings show the extra objects of the spelling's second
  evaluation, as plain output and the graph do, in six grid programs.
- **Info, JSON (F3).** JSON output prints NaN as `null`, at both
  revisions; on the candidate, `[1, 0 / 0, 3].partition(x -> x > 2)` prints
  `[[3.0],[1.0,null]]` with `--json`. This NUC's tables write NaN at the
  value level, which plain output shows.
- **Pre-existing, outside this NUC.** The evaluator also observed two
  behaviors of both revisions. A nested callback cannot read its enclosing
  callback's parameter: `b.flatMap(i -> a.map(j -> i + j))` raises
  `ReferenceError("i is not defined")`, in the family of the documented
  function-parameter defect. Evaluating a list literal takes time quadratic
  in its length: 0.25, 0.97 and 3.9 seconds for 10,000, 20,000 and 40,000
  items.
