```

Status: Accepted

Requires: 59, 76, 86, 93
```

## Abstract

- Add the opt-in syntax option `conditional_words`, CLI
  `--conditional-words`. Beside [NUC 93](nuc-0093.md)'s `is_assignment`, it
  lets a branch of a conditional expression in an `is` assignment's value be
  a bare word: `status is OPEN if ready else WAITING` and
  `status is ready ? OPEN : WAITING`.
- The word positions are the value, which NUC 93 already reads as a word
  when it is one identifier token, and both branches of a conditional that
  stands in a word position, in either spelling of [NUC 59](nuc-0059.md). A
  branch there is a word when it is exactly one identifier token, and it
  reads by NUC 93's word rule through the same `UnaryOp::Word` marker: the
  name when something defines it, and otherwise its own text.
- Conditions, parenthesized operands, other operators, calls, lists,
  objects and bodies inside the value, the value of an inner assignment and
  the target of an assignment operator are not word positions.
- The option changes nothing without `is_assignment`, and with
  `is_assignment` alone every program keeps NUC 93's reading. No token,
  keyword, syntax-tree variant or error message is added. The authoritative
  contract is
  [Opt-in conditional words](../nucleoid.spec.md#opt-in-conditional-words).
- Accepted: the user requested this feature directly, and the frozen
  candidate meets every hard criterion of the automatic acceptance rule, so
  the user-requested basis applies. The independent evaluator's overall
  decision is also Accepted. Token comparison was skipped as
  `single_proposal`, the rule for a single-proposal request, not a failed
  check; see [Evaluation](#evaluation).

## Motivation

- The user asked for words inside larger values of NUC 93's opt-in `is`
  assignments, where they still need quotes. Rules such as these are
  written today with quoted branches:

```
$Tile.fill is 'B' if $Tile.symmetric else 'C'
$Tile.mark is 'A' if $Tile.parts.distinct().length is 1 else 0
```

- The user wants them written as words, as a value of one word already is:

```
$Tile.fill is B if $Tile.symmetric else C
$Tile.mark is A if $Tile.parts.distinct().length is 1 else 0
```

- At the accepted revision, with `--is-assignment`, the second spelling
  fails. NUC 93 makes a value a word only when the whole value is one
  identifier token, so each branch is an ordinary name:
  - `y is A if true else B` raises `ReferenceError("A is not defined")` at
    line 1, column 1.
  - After `class Tile(symmetric, parts):` with its constructor, declaring
    `$Tile.fill is B if $Tile.symmetric else C` raises
    `ReferenceError("B is not defined")`, and declaring the `mark` rule raises
    `ReferenceError("A is not defined")`, because class-rule validation
    requires every name in either branch.
- Asked, the user chose two proposals with two opt-in flags: this one for
  the branches of conditional expressions, and a later, separate one for
  list items, dictionary values and keyword-argument values.
- With the option, a model can choose between two facts in one rule and
  decide later whether each word is its text or a variable that remaps it:

```
ready = false
status is OPEN if ready else WAITING
OPEN = "open"
ready = true
```

- `status` is `"WAITING"` while `ready` is false, and `"open"` once `ready`
  is true. The programs of this proposal execute as written in
  `tests/conditional_words.rs::the_documented_examples_run_as_written`.

## Rationale

- **Category and mode.** The user requested this concrete feature, so there
  was no random draw. Its category is Syntax enhancement, that of NUC 93 and
  NUC 86, which it extends. It runs in single-proposal mode, which skips
  token comparison. Runtime applicability does not apply. No hint was
  supplied.
- **A new option, not a change to `is_assignment`.** With `is_assignment`
  alone, `a is A if c else B` is an accepted input that fails at run time.
  Backward compatibility protects every accepted input, including those that
  fail at run time, and NUC 93's tests pin `a is 1 if c else 2` and
  `a is c ? 1 : 2` to the `=` tree. Reading words there under
  `is_assignment` would change accepted behavior, so the user chose a second
  opt-in flag, as NUC 93 chose one over NUC 86's default reading.
- **The name.** Each source option names the form it enables, as a
  snake_case field whose kebab-case flag spells the same words:
  `c_style_comments` and `--c-style-comments`, `is_assignment` and
  `--is-assignment`. The form here is a word in a conditional, so
  `conditional_words` and `--conditional-words`, plural as
  `c_style_comments` is because one statement may hold several. Rejected:
  `word_branches`, which does not say which construct has branches, and
  `is_conditional_words`, which repeats the option it extends. A later
  option for list items, dictionary values and keyword arguments can follow
  the same pattern.
- **Nothing without `is_assignment`.** Conditional words exist only in `is`
  values, so the option alone has nothing to change. Rejected: making
  `--conditional-words` imply `--is-assignment`, which would silently change
  default readings such as `a is good`, and rejecting it alone with an error,
  which would add a message that the public `SyntaxOptions` struct cannot
  enforce anyway.
- **Result positions.** A branch of a conditional in a word position is a
  result of the value: the value is exactly one of its branches. So each
  branch is a word position, recursively, and `A`, `B` and `C` are words in
  `a is A if c1 else B if c2 else C`, `a is c1 ? A : c2 ? B : C` and
  `a is c1 ? c2 ? A : B : C`. Both spellings build one node, so both get
  words.
- **One identifier token.** A branch is a word exactly when NUC 93 would
  read it as a word if it were the whole value: one identifier token.
  `1`, `"B"`, `true`, `this`, `$Order`, `A.x`, `f(A)`, `A + 1`, `not A` and
  `(A)` are not words, so `a is (A) if c else B` makes only `B` a word.
- **Conditions are never words.** A condition is a test of what the program
  knows; a bare name there is a reference. NUC 86 already reads an `is`
  comparison's right operand in a condition as a word, and that is
  unchanged: `label is MATCH if value is EXACT else MISS` compares with the
  word `EXACT` and assigns the word `MATCH` or `MISS`.
- **Parentheses opt out.** `a is (A if c else B)` makes no words, as
  `a is (good)` makes none under NUC 93 and `value is (EXACT)` none under
  NUC 86. One rule then holds for all three: grouping parentheses always
  read an ordinary expression. It also leaves a spelling for a conditional
  whose branches must name defined things and raise otherwise. Rejected:
  reading through parentheses, which would make `(A)` and `(A if c else B)`
  disagree about what parentheses mean.
- **Not inside other constructs.** Operands of other operators, call
  arguments, list items, object values, function, arrow and lambda bodies
  and template interpolations are not results of the value. List items,
  dictionary values and keyword arguments are the scope of the separate
  later proposal; the others stay ordinary expressions.
- **Assignments inside the value.** Under NUC 93, `a is b = c` makes no
  word of `c`; likewise `a is b = A if c else B` makes no words. A
  conditional that an assignment operator follows is that assignment's
  target, as in `a is X if c else Y = 5`, which raises
  `SyntaxError("Cannot assign to (c?X:Y)")` at run time. Its branches keep
  the plain tree, so it raises exactly what it raises today.
- **Reuse.** The marker is NUC 93's `UnaryOp::Word`, evaluated through
  NUC 86's `read_word`, so dependency collection, `.value` freezing, cycle
  checks and the protected-assertion walker already handle it, and static
  class-rule validation already skips it inside any conditional. The
  evaluator needs no change: a conditional evaluates its condition, then
  its selected branch, and a word there reads as a word.
- **Marking while parsing.** The syntax tree drops grouping parentheses, so
  after parsing, `(A)` and `A` are the same `Expr::Identifier`. The parser
  therefore marks a branch where it knows the branch's tokens: the
  conditional parser takes a `Branches` mode, `Plain` everywhere except the
  value of an `is` assignment with both options, where it is `Words`. The
  mode is a parameter, not parser state, so it cannot leak into nested
  constructs or into the probe parsers of NUC 86 and NUC 92, and the
  default path runs the same code with `Plain`. A conditional that an
  assignment operator turns out to follow loses its markers before it
  becomes the target. Rejected: a parser flag, which every nested construct
  would have to reset, and a pass after parsing, which cannot see
  parentheses.
- **Rendering.** A statement whose value holds a word renders as
  `target is value`, as NUC 93 renders `target is word`; its `=` spelling
  would read references. The conditional's ordinary rendering
  `(c?A:B)` would read back as a parenthesized conditional, which holds no
  words, so within such a value a conditional that holds a word renders
  without its grouping parentheses and a name in a word position that is not
  a word renders in parentheses: `a is c?A:(B)`. The label then reads back as
  the same statement with both options. Rejected: the grouped form, which
  would describe a different statement, and the `=` spelling.
- **Diagnostics.** No message is added. The option changes only markers,
  never which tokens a value consumes, so every program parses, or fails to
  parse at the same place with the same message, exactly as it does with
  `is_assignment` alone.
- **Not added.** Words in list items, dictionary values, keyword or
  positional call arguments, operands of other operators, conditions,
  `=`, `:=` and `return` values; a REPL command or terminal toggle; and
  automatic detection.
- **Optional evidence.** Advisory usefulness is unscored (`missing_rubric`),
  not zero. Strategy learning is `not_configured`; this revision is
  unattributed, without a policy, selection receipt, trial or reward.

## Specification

- The normative contract is
  [Opt-in conditional words](../nucleoid.spec.md#opt-in-conditional-words).

### Activation and API

- `SyntaxOptions` gains the public field `conditional_words: bool`, which
  defaults to false. `Runtime::new()`, `Runtime::default()`,
  `Runtime::check` and every parsing function without options keep the
  accepted grammar.
- `Runtime::with_options(SyntaxOptions { is_assignment: true, conditional_words: true, ..SyntaxOptions::default() })`
  selects the form for every `run` and template interpolation;
  `Runtime::options()` returns it and `clear()` keeps it.
  `Runtime::check_with_options`, `parse_program_with_options`,
  `parse_with_options`, `parse_expression_with_options` and
  `statement::compile_with_options` accept it. It combines with
  `c_style_comments`.
- `nucleoid --conditional-words` enables it for file runs, the plain and
  redirected REPL and the terminal workspace, with `--json`, `--graph`,
  `--is-assignment` and `--c-style-comments` in any order. `.clear` keeps
  it. Without `--is-assignment` it has no effect.

### Word positions

- With both options, the word positions of an `is` assignment's value are:
  - the value itself, as under NUC 93;
  - the consequent and the alternate of a conditional expression that is in
    a word position, in either spelling.
- A word position whose expression is exactly one identifier token is a
  word. Every other expression there keeps its reading; when it is a
  conditional, its own branches are word positions in turn.
- Not word positions: conditions; the inside of grouping parentheses,
  including a parenthesized conditional; operands of other operators; call
  arguments; list items; object values; function, arrow and lambda bodies;
  template interpolations; the value of an assignment inside the value; and
  a conditional that an assignment operator follows.
- Statement positions are those of NUC 93: every position where an `is`
  assignment applies, including the block bodies of function literals
  inside expressions and template interpolations. The top level of
  `parse_expression_with_options` holds no `is` assignment and so no word.
- At statement level, the operand before `?` is not enclosed, so an `is`
  comparison there needs parentheses, as in
  `mark is (shape is SQUARE) ? CORNER : EDGE`. A Python-style condition is
  enclosed, as in `mark is CORNER if shape is SQUARE else EDGE`. Both
  follow from NUC 86 and NUC 93.

### Semantics

- A word branch reads by NUC 93's word rule: the local, variable, class,
  function or built-in global of that name when one exists, read as an
  identifier is, and otherwise the string of its spelling, recording a
  dependency on the variable of that name.
- The condition is evaluated once and then only the selected branch, as for
  every conditional. A word in the unselected branch is not read and adds no
  dependency.
- A standing declaration, property, constructor property or class-level
  rule re-evaluates when the variable that its selected word names is
  defined, changed or deleted, including inside a `suppose` block whose
  rollback restores it, and switches branches when its condition changes.
  Deleting the variable returns the word to its text. While undefined, the
  selected word is a pending graph node that `why` lists among the sources.
- Static class-rule validation does not require a branch word to be
  defined. It still requires every other name, so
  `$Order.bad is (MISSING) if $Order.total > 0 else OTHER` raises
  `ReferenceError("MISSING is not defined")` when declared.

```
class Order(total):
    this.total = total
    this.size is BIG if this.total > 10 else SMALL
$Order.state is OPEN if $Order.total > 0 else EMPTY
first = Order(0)
second = Order(20)
assert([first.size, second.size], ["SMALL", "BIG"])
assert([first.state, second.state], ["EMPTY", "OPEN"])
OPEN = "open"
assert(second.state, "open")
```

```
value is EXACT
label is MATCH if value is EXACT else MISS
other is MATCH if value is not EXACT else MISS
assert([label, other], ["MATCH", "MISS"])
EXACT = "B"
assert([value, label, other], ["B", "MATCH", "MISS"])
```

### Rendering

- An `is` assignment whose value holds a word renders as `target is value`
  in statement rendering, block graph keys, `--graph` output and the `rule`
  of `why` and `affects`. In such a value, a conditional that holds a word
  renders without its grouping parentheses, and a name in a word position
  that is not a word renders in parentheses.

| Statement, with both options | Rendering |
| --- | --- |
| `a is A if c else B` | `a is c?A:B` |
| `a is A if c else (B)` | `a is c?A:(B)` |
| `a is A if c1 else B if c2 else C` | `a is c1?A:c2?B:C` |
| `a is c1 ? (c2 ? A : B) : C` | `a is c1?(c2?A:B):C` |
| `a is A if v is X else B` | `a is (v is X)?A:B` |
| `{ total is A if c else (B) }` | the block key `block(total is c?A:(B))` |
| `a is (A if c else B)` | `a=(c?A:B)` |
| `a is 1 if c else 2` | `a=(c?1:2)` |

- Every rendering of a statement with words in the table reads back as the
  same statement with both options. No path re-parses rendered statements;
  graph keys, `--graph` output and `why` rules are labels.

### Compatibility

- Without `conditional_words`, every input keeps its accepted parse, syntax
  tree, rendering, result, assertions, runtime errors, JSON and graph, in the
  default mode and with `is_assignment`: the conditional parser runs with
  `Branches::Plain`, which builds what the accepted parser builds, and no
  word marker is built anywhere NUC 93 did not build one. A differential in
  Reference Implementation confirms it.
- With `conditional_words` but not `is_assignment`, every input reads and
  runs as without `conditional_words`, with or without comments.
- With both options, an input changes only when its `is` values hold a
  conditional with a one-identifier-token branch in a word position, and
  then only by word markers on those branches. These readings of NUC 93
  change, each because it contains such a value:

| Program | `is_assignment` alone | With `conditional_words` too |
| --- | --- | --- |
| `a is A if c else B` with `c = true` | `ReferenceError("A is not defined")` | `a` is `"A"` until `A` is defined |
| `a is c ? A : 1` with `c = false` | `a` is `1`; `A` is an ordinary name | `a` is `1`; `A` is a word, not read |
| `$Order.s is A if $Order.n > 0 else B` | `ReferenceError("A is not defined")` when declared | accepted; each instance reads its word |
| `{ a is A if c else B }` | renders as `{a=(c?A:B)}` | renders as `{a is c?A:B}` |

- The public `SyntaxOptions` struct is not `#[non_exhaustive]` and gains a
  field, so a downstream struct literal that names every field stops
  compiling. Its `Debug` output, and that of `Runtime`, shows the new field.
  No enum gains a variant. This needs human SemVer review. No project
  version is changed.
- Without the flag, the only visible command-line change is `--help`: it
  gains the line of `--conditional-words`, and because that is the longest
  flag, clap widens the flag column by one space, realigning the other lines
  without changing their text.

## Errors

- No error type or message is added. A malformed value reports what it
  reports with `is_assignment` alone, at the same place:

| Exact source, with both options | Error |
| --- | --- |
| `a is A if c else` | `SyntaxError("Unexpected end of input")`, line 1, column 17 |
| `a is c ? A` | `SyntaxError("Expected ':' but found end of input")`, line 1, column 11 |
| `a is c ? A : (1 + )` | `SyntaxError("Unexpected ')'")`, line 1, column 20 |

- Runtime errors are those of `is_assignment` alone wherever a name is not a
  word: `a is (A) if c else B` and `a is A.x if c else B` raise
  `ReferenceError("A is not defined")` at the statement while `c` is true
  and nothing defines `A`, and `a is A if missing else B` raises
  `ReferenceError("missing is not defined")`.
- `a is X if c else Y = 5` raises `SyntaxError("Cannot assign to (c?X:Y)")`
  at its statement, as with `is_assignment` alone, and the transaction rolls
  back.
- Word branches add no nesting level. A top-level chain of 62 conditionals
  is rejected as with `is_assignment` alone and in the accepted parser, at
  the same place: a `?` chain with `Expressions are nested too deeply`, and
  a Python-style chain with `Expected ':' but found keyword 'else'`, because
  its last condition no longer fits and its `if` is read as a statement.

## Reference Implementation

- `src/lang/ast/lexer.rs` adds `SyntaxOptions::conditional_words`. No token,
  keyword, `Expr`, `Stmt` or `UnaryOp` variant is added.
- `src/lang/ast/parser/is_assignment.rs` adds the private `Branches` mode,
  `Plain` or `Words`, chosen from the options when an `is` assignment's value
  is parsed. `Branches::mark` wraps a branch of exactly one identifier token
  in `UnaryOp::Word`, through `is_word`, the criterion that NUC 93's value
  check now shares, and `Branches::unmark` removes the markers of a
  conditional that an assignment operator follows, as a worklist.
- `src/lang/ast/parser/expression.rs` threads the mode through
  `assignment_expression`, the former body of `expression_inner`,
  `clause_expression_with` and `conditional_with`. `expression_inner`,
  `clause_expression` and `conditional` keep their signatures and call them
  with `Branches::Plain`. Only the consequent and alternate of a conditional
  receive the mode; its operands, condition and every nested construct
  parse with `Plain`, at the same nesting depth as before.
- `src/lang/ast/generator.rs` adds `WordValue`, which renders a value that
  holds words as described above, and `src/lang/ast/generator/statement.rs`
  and `src/reasoning/rules.rs` use it for `target is value`, replacing the
  special case of NUC 93's single word, whose output is unchanged.
- `src/main.rs` adds `--conditional-words`, whose help line ends without a
  period, as the others do.
- The caller's Rust improvement pass changed no source file and no
  behavior. It added the test
  `word_chains_stop_where_the_chains_of_is_assignments_stop_and_read_back_at_their_deepest`,
  which builds chains of Python-style alternates, of `?` alternates and of
  `?` consequents, finds the first length that `is_assignment` alone rejects
  without assuming it, requires both options to check alike at every length
  up to it, and reads back and runs the deepest accepted chain to its last
  word. Its review under Power of 10 rule 1 found the recursion of
  `WordValue` bounded by the parser: it descends only into the two branches
  of a conditional that holds a word, such a conditional is built only with
  both options, and every nested branch is parsed under `MAX_NESTING`, since
  a Python-style first branch is a conditional only inside parentheses,
  which read no words. `holds_words` and `without_words` are worklists. It
  kept the two closures that pass the mode, because merging them into
  `expression_inner` would add a stack frame to a hot parse path in debug
  builds, and the one-element `Vec` of `holds_words`, which is not measured
  as hot.
- Compile-only edits forced by the new public field, with no assertion,
  pinned diagnostic or case byte changed: `conditional_words: false` in the
  existing struct literals of `tests/c_style_comments.rs`,
  `tests/list_comprehensions.rs`, `tests/property_selectors.rs`,
  `tests/is_assignments.rs`, `src/continuation/tests.rs` and
  `src/terminal/tests.rs`. The literals that already end in
  `..SyntaxOptions::default()` are unchanged.
- `tests/conditional_words.rs`, `tests/conditional_words_cli.rs` and the
  terminal unit test cover the claims above.
- The root specification, its conditional-expression and `is`-assignment
  sections, the consolidated reference with its source options, subsection
  and syntax summary, the README and both NUC 0 indexes are synchronized.
  The specification change is prose, and the exports are unchanged.
- `docs/nucleoid.g4` gains the opt-in `isAssignment` statement of NUC 93,
  which it did not describe, its `path IS` head for `suppose`, the word
  contract of both options, their lowerings, the parse-pass note and the
  source map.

### Measured cost

- Measured with release builds of the accepted library and of the
  candidate, linked into one process, timing `Runtime::check_with_options`
  and `Runtime::run` on generated programs of 1,000, 2,000, 4,000 and 8,000
  lines after one `flag = true`. Accepted and candidate samples alternate,
  and each figure is the median of 31 runs, in milliseconds.
- Without the new option the conditional parser adds a few position reads
  per conditional level and no allocation. `xK = K if flag else K + 1`
  checks in 2.69, 5.30, 21.30 and 45.67 on the accepted library and in 2.67,
  5.10, 21.33 and 44.91 on the candidate, and runs in 8.63, 16.90, 105.36 and
  333.57 against 8.68, 16.69, 105.57 and 333.15. With `is_assignment` alone,
  `xK is K if flag else K + 1` checks in 5.09, 10.92, 22.20 and 45.18 against
  5.17, 11.01, 22.12 and 45.37, and runs in 18.49, 40.32, 106.37 and 330.71
  against 18.72, 40.33, 105.95 and 335.96.
- With both options, the same program, which holds no word, checks in 5.25,

### Findings

- **Medium, non-blocking: debug builds use more host stack per nesting
  level.** The unoptimized parser now has a separate
  `assignment_expression` frame, extra locals in `conditional_with` and
  branch closures. On the debug Windows CLI's 1 MiB main thread, 8
  constructs overflow exactly one level earlier than on the accepted debug
  CLI: for example calls at 51 nested levels rather than 52, objects at 41
  rather than 42, and parentheses at 46 rather than 47, as in `x =` followed
  by 46 nested parentheses. 41 of 8,970 debug pairs differ. The accepted
  debug CLI already overflows below the 64-level nesting limit, release
  builds show no overflow and no difference at any depth from 8 to 72, the
  depth limit and its diagnostics are unchanged, and the test threads are
  unaffected. NUC 59 and NUC 65 recorded the same kind of debug-only effect
  as non-blocking. "At the same nesting depth as before" in Reference
  Implementation holds for the parser's depth counter, not for host stack.
- **Low, documentation: parenthesized conditionals.** `README.md` and
  `docs/README.md` say that `a is (A if c else B)` needs `A` and `B` to be
  defined. At run time only the selected branch is read, as with
  `a = (A if c else B)`: with `c = true` and `A = 1` the statement succeeds
  while `B` is undefined. Static class-rule validation does require both.
- **Low, SemVer, for the human owner.** `SyntaxOptions` gains a public field
  and is not `#[non_exhaustive]`, so a downstream struct literal that names
  every field stops compiling, and its `Debug` output shows
  `conditional_words`. No project version was changed.
- **Info.** `--help` gains the `--conditional-words` line, the longest flag,
  so the flag column widens by one space; every other line's text is
  unchanged.
- **Info, pre-existing.** Ten native-CLI test binaries write under
  `$CARGO_MANIFEST_DIR/target` and fail with `NotFound` when
  `CARGO_TARGET_DIR` points elsewhere and that directory is absent, at the
  accepted revision as on the candidate.
