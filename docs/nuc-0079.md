# NUC 79 -- Property Selector Arguments

```
NUC: 79
Title: Property Selector Arguments
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 04-Nov-2026
Requires: 8, 45, 57, 59, 61, 63, 65, 68, 69, 71, 73, 77
```

## Abstract

- A call argument written `.name`, or a dotted path such as `.a.b`, is the
  one-parameter function that reads that property path from its argument.
  `Bid.max(.amount)` means `Bid.max(bid -> bid.amount)`, and
  `shipments.map(.to.city)` means `shipments.map(s -> s.to.city)`.
- A selector is a whole argument of a parenthesized argument list: `.` and a
  property name, repeated, directly followed by `,` or `)`. Property names
  are those member access accepts after `.`, including keywords.
- The selector is exactly the function `v -> v.a.b`: it reads only its
  argument, with the reads, dependencies, liveness, transactions, `null`
  handling and `.value` meaning of member access. Extra arguments are
  ignored, and a missing argument is `null`.
- It renders as written, so `why` explains `top = Bid.max(.amount)`, and two
  selectors with different paths stay different graph keys.
- Every input this changes was a syntax error at the accepted revision:
  `SyntaxError("Unexpected '.'")` at the selector, or, in a statement the
  parser reads tentatively, such as the destructuring declaration
  `first, second = xs.map(.a)`, the error of the ordinary statement it fell
  back to. Every other input, including `.5`, member access split across
  lines, spread-like `...` and every near miss such as `.a + 1`, keeps its
  parse, result, diagnostic and position.
- Each selector saves three lexer tokens over the shortest lambda:
  `(b -> b.amount)` is seven tokens and `(.amount)` is four.
- No token kind, keyword, syntax tree node, public Rust item, dependency or
  version is added or changed. The authoritative contract is
  [Property selector arguments](../nucleoid.spec.md#property-selector-arguments).
- **Outcome: Accepted.** The independent evaluation and the caller's
  integrated-tree checks passed all three hard criteria, and the independent
  evaluator decided Accepted. The required token comparison ran in
  continuous mode: 11 cases use fewer tokens, 904 the same and none more. No
  policy check failed.

## Motivation

- A callback that reads one property is the most common lambda in Nucleoid
  world models. The executable corpus, the 904 accepted cases of the
  specification, the executable reference and the `nuc` blocks of the README
  and the examples, passes 218 property-only lambda arguments: whole call
  arguments of the form `v -> v.path` or `v => v.path` whose body reads only
  a property path of their one parameter. There are 130 in the
  specification, 36 in the executable reference, 12 in the README and 40 in
  the examples, and the single spelling `(step => step.node)` occurs 72
  times.
- Each spells a parameter twice and an arrow around the one part that
  carries meaning. In `Order.sum(order -> order.amount)` only `.amount`
  says what is summed.
- A language model that writes a world model must invent a parameter name
  and repeat it exactly. A mismatch such as `b -> bid.amount` reads an
  unrelated binding. A selector has no parameter to mistype.
- Shorter world models cost fewer tokens to generate and to read back.
  Selectors shorten the list queries the language already offers: `map`,
  `filter`, `count`, `find`, `sum`, `max`, `min`, `mode`, `distinct`,
  `maxBy`, `minBy` and every user function that takes a function.
- Prior art: Elm's record accessor `.name` is exactly this function, jq
  writes paths as `.a.b`, Clojure calls keywords as functions, Ruby passes
  `&:name`, Kotlin and Swift offer `it.name` and key paths `\.name`.

## Rationale

- **Confirmed category and mode.** The caller made one tool-backed uniform
  draw over the five categories that NUC 1's registry marks eligible for
  automatic selection and selected Syntax enhancement, index 0, with
  probability 1/5 and no redraw. This is a continuous cycle, so token
  comparison is required. Runtime applicability does not apply to this
  category.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero. Strategy learning is `not_configured`, so this revision
  is unattributed, with no policy, selection receipt, trial or reward.
- **Only a former error position.** An argument that begins with `.` reaches
  the operand parser, which raises `SyntaxError("Unexpected '.'")` for every
  `.` token. No accepted program has such an argument, so giving the
  complete path a meaning changes no accepted program.
- Some statements are parsed tentatively, and an attempt that fails falls
  back to another reading. A destructuring declaration whose value holds a
  selector failed its attempt at the accepted revision, and the fallback
  reported its own error: `first, second = xs.map(.a)` raised
  `SyntaxError("Unexpected ','")`, `{length} = xs.map(.a)`
  `SyntaxError("Unexpected '='")` and `{length: n} = xs.map(.a)`
  `SyntaxError("Unexpected ':'")`. These now destructure. They were syntax
  errors at the accepted revision, and replacing each selector with its
  lambda makes the accepted parser accept them.
- **A whole argument.** The selector ends at the `,` or `)` that ends the
  argument. Inputs where more follows, such as `.a + 1`, `.a()`, `.a[0]`,
  `.a ?? 0` and `.a == 1`, keep their accepted error. Rejected: operators
  over selectors, which would need an implicit parameter with scope rules
  of its own, and an implicit `it` or `_` placeholder for the same reason.
- **Only in argument lists.** Call arguments are where functions are passed.
  A selector anywhere else would compete with accepted readings: `x = .a`,
  `[.a]`, `{k: .a}`, `xs[.a]` and a lambda body `x -> .a` stay errors, and
  so do `x = a?.b` and `x = a?? .b`, whose diagnostics accepted tests pin. A
  line that starts with `.`, such as `xs` followed by `.length` on the next
  line, still ends the previous statement and raises its accepted error.
- **Not the colon-led assertion statement.** `assert: actual, expected` is
  not a parenthesized argument list, so `assert: .a, 1` keeps its accepted
  error. `assert(.a)` is a call and passes the function.
- **Names as member access names them.** The parser reads each name with the
  member access rule: an identifier, or a keyword in its canonical spelling.
  `.class` reads `class`, `.self` reads `this`, `.elif` reads `else`, and
  `.None` and `.undefined` read `null`, exactly as `v.self` and
  `v.undefined` do. A digit after `.` is a number token, so `.5` stays `0.5`
  and `.a.5` keeps its error.
- **Exactly the lambda.** A selector parses to the function node that
  `v -> v.a.b` builds, an anonymous function of one parameter whose body is
  the member path read from that parameter. Evaluation, invocation,
  dependency recording, `.value` freezing, class-level rules, `why`,
  `affects` and transactions therefore treat it as they treat that lambda.
  Rejected: a separate node evaluated by its own path, which would restate
  member access and could drift from it, and a pluck helper such as
  `xs.map("amount")`, which would change the accepted
  `TypeError("map expects a function")` of every list query and leave user
  functions out.
- **An unnamed parameter.** The parameter's name is empty, which no source
  can write. The body therefore cannot read or shadow any user name, a
  variable, function or class named like the property included, and its
  reads stay those of the argument.
- The empty name is never observable. The unnamed root renders as nothing,
  so canonical rendering, `why` and `affects` rules, graph and block keys
  and errors that quote an expression show only the written path. A
  parameter is a local, so it is never a graph node, a state variable, a
  dependency in a `from` list or a completion candidate, and JSON, the REPL
  and the terminal workspace show a selector's value as `[function]`, as
  every function. Only the syntax tree's `Debug` form, which no language
  output uses, prints the parameter.
- Rejected: a new public `Expr` variant. It would break exhaustive matches
  over the public syntax tree and duplicate the function node that already
  carries every behavior of the lambda.
- **`.value` keeps its meaning.** In member access `.value` is the snapshot
  read, so `[{value: 3}].map(.value)` yields the record itself, as
  `v -> v.value` does. A property named `value` is read with
  `v -> v["value"]`. Rejected: a selector-only meaning for `value`, which
  would make `.value` mean two things.
- A `.value` read of an undefined value names the path before `.value`, so
  `[{}].map(.a.value)` raises `ReferenceError(".a is not defined")`, as
  `v -> v.a.value` raises `ReferenceError("v.a is not defined")`. When the
  path before `.value` is the unnamed parameter itself, the message would
  have no name, so it reads `ReferenceError(".value is not defined")`. Only
  that parameter can reach the change: every other expression whose path is
  read there has a nonempty path, because source names, class names and
  object ids are never empty.
- **Rendered as written.** The unnamed parameter renders as nothing, so a
  selector renders as its written path: `why` gives the rule
  `top = Bid.max(.amount)`, and an error that quotes an expression quotes
  `.amount`. An anonymous lambda keeps rendering as `function()`.
- Graph keys therefore keep different selectors apart. At the accepted
  revision `if xs.some(x -> x.q):` and `if xs.some(x -> x.p):` with the same
  body render the same key `if(xs.some(function()))`, so the second replaces
  the first. With selectors they are the two standing conditions
  `if(xs.some(.q))` and `if(xs.some(.p))`. That lambda behavior is accepted
  and unchanged.
- A selector and its lambda spelling are different graph keys, as
  `sum of xs` and `xs.sum()` are under [NUC 75](nuc-0075.md). Rejected:
  rendering selectors as `function()`, which would merge every selector of a
  condition and hide the path from explanations.
- **Whitespace and lines.** Inside parentheses, line breaks carry no layout,
  so `f(. a)`, `f(.a .b)` and a selector on its own line of a multi-line
  argument list are selectors, as member access accepts `r. b` and `r .b`.
  One trailing comma is allowed after a selector, as after any argument.
- **A bounded path.** A selector names at most 127 properties, as many as the
  member chain of the equivalent lambda body can hold. The 128th `.NAME`
  pair raises `SyntaxError("Expression has too many parts")` at its `.`.
  The recognition scan stops there, so its cost is bounded, and every
  recursive walk over the body passes the existing depth guards.
- **The nesting guard of any argument.** Building a selector passes the
  expression nesting guard that every argument expression passes, so calls
  nested inside each other reach `SyntaxError("Expressions are nested too
  deeply")` at the same depth and position whether the innermost argument is
  a selector or a name, and the accepted error at that depth is kept.
  Evaluation passes the existing expression depth limit, so a 127-property
  selector exhausts it exactly where its lambda spelling does.
- **Earlier selectors move later errors.** A complete selector is a valid
  argument, so an argument list that holds one before an error now reports
  that later error: `f(.a, .b + 1)` raises `Unexpected '.'` at `.b`, and
  `f(.a,,)` raises `Unexpected ','`. At the accepted revision both raised
  `Unexpected '.'` at the first selector.
- **Interactive input.** The line-oriented REPL treats a line as a command
  only when nothing is pending, and the terminal workspace only when the
  whole input is one line starting with `.`. A selector never starts a
  statement, so neither front end changes. The workspace offers no
  completion after a selector's `.`, as after any `.` that follows no name.

### Counterparts

- Every new case is compared with the most compact accepted-syntax program
  found that reaches the same canonical assertions in the same order and
  the same expected return. Counterparts keep every other line of their case
  byte for byte, and no case uses a selector inside an assertion.
- A path used once becomes an inline lambda, `x -> x.name`, three tokens
  more. A path used twice or more becomes a standing helper written on the
  line of its first use, such as `def q x => x.qty units = orders.sum(q)`,
  which costs seven tokens and then one per use. Helpers are standing
  functions, so methods, lambda bodies and propagation see them.
- The search measured every combination of inline lambdas and helpers per
  path, with `->`, `=>` and `lambda x:` lambdas and `def`, variable and
  own-line helpers: 1,218 programs, all of which pass on the accepted
  runtime. The recorded counterpart is the smallest of each case.
- It also measured structural alternatives: a parenthesized quantifier
  instead of `some`, `flatMap` instead of `filter` and `map`, `sum of` and
  `max of`, `filter(...).length` instead of `count`, the class rule's
  condition instead of `.low`, a shared intermediate list for two paths with
  a common prefix, a loop with an inner `if` instead of a filtered header,
  `reduce` comparators instead of `maxBy` and `minBy`, and
  `reduce((a, b) -> a.next, ...)`. None is smaller than a recorded
  counterpart; the two `flatMap` spellings tie it.
- Earlier drafts were revised where review or the search found a smaller
  accepted program: a declaration that repeated what the method `weight()`
  computes, a `reduce` over a constant list that unrolls to a fixed path,
  `count(...) > 0` in a `while` header, which a quantifier beats, and a
  largest amount read with both `max` and `maxBy`, which
  `top = leader.amount ?? Number.NEGATIVE_INFINITY` replaced. The cases now
  read values no other declaration supplies, and that last substitution
  fails the revised assertions.
- An inline assignment helper such as `orders.sum(q = x -> x.qty)` is
  accepted syntax, but `q` is a local of that evaluation: when a later
  declaration that uses `q` re-evaluates during propagation it raises
  `ReferenceError("q is not defined")`, so it is not behavior-equivalent in
  these live cases.

## Specification

### Grammar

- In a parenthesized argument list, an argument is a selector when it is one
  or more `.NAME` pairs directly followed by `,` or `)`:

```
selector = "." name { "." name }
```

- `name` is any identifier or keyword, which member access accepts after
  `.`. A keyword reads its canonical spelling.
- The argument lists are those of calls, method calls, constructor calls,
  calls written with `new` and `super(...)`. A selector may be any argument,
  first or later, of any of them, and argument lists nest, so
  `f(g(.a), .b)` holds two selectors.
- Line breaks, indentation and comments inside the parentheses are not
  layout, so a selector may span or start a physical line. One trailing
  comma may follow it, as after any argument.
- Recognition consumes nothing unless the whole argument is a selector.
  Every other argument is parsed as before.

### Semantics

- `.a1.a2...ak` evaluates to the anonymous function of one parameter whose
  body is that parameter's member path `a1.a2...ak`. It is the function
  `v -> v.a1.a2...ak` with a parameter that no source can name.
- Called with an argument, it returns what the member path returns on that
  argument. A missing property, or one read from `null`, a number, a
  boolean or another value without properties, reads undefined. A string
  and a list answer `.length`, and a class answers `.length` with its
  instance count.
- Called without an argument, its parameter is `null`, as a lambda's
  missing parameter is, so the path reads undefined. Arguments after the
  first are ignored, so `reduce`, which
  calls its function with the accumulator first, reads the accumulator's
  property, and a `sort` comparator reads the first of its two items.
- `typeof` gives `"Function"`, and the value displays as `[function]`, as
  every function does.
- Reads follow member access, including the rule that a declaration which
  reads through a `null` value settles to `null`. After `oslo.to = null`,
  `cities = shipments.map(.to.city)` settles to `null`, as
  `shipments.map(s -> s.to.city)` does.
- `.value` is the snapshot read of member access. It reads the current value
  of what precedes it without recording a dependency, so `.value` is
  `v -> v.value` and `.reading.value` is `v -> v.reading.value`.
- A call that receives a selector depends on whatever the selector reads for
  each item, as with the lambda. Declarations, class-level rules, methods,
  lambda bodies, `if`, `for` and `while` headers, conditional expressions,
  template interpolations and `suppose` blocks use selectors as they use
  the lambda, and failed updates roll back through the existing transaction.

```
pen = {item: "pen", qty: 2, paid: true}
ink = {item: "ink", qty: 5, paid: false}
orders = [pen, ink]
items = orders.map(.item)
units = orders.sum(.qty)
settled = orders.count(.paid)
largest = orders.maxBy(.qty)
assert: [items, units, settled, largest], [["pen", "ink"], 7, 1, ink]
ink.paid = true
pen.qty = 8
orders.push({item: "cap", qty: 1, paid: false})
assert: [items, units, settled, largest], [["pen", "ink", "cap"], 14, 2, pen]
```

- A selector reads only the properties on its path, so a declaration that
  selects one property does not depend on the others:

```
class Sensor(room, temp):
    this.room = room
    this.temp = temp
hottest = Sensor.maxBy(.temp)
rooms = Sensor.map(.room)
lab = Sensor("lab", 21)
hall = Sensor("hall", 25)
readers = (affects hall.temp).map(.node)
listers = (affects hall.room).map(.node)
assert: [readers, listers, hottest, rooms], [["hottest"], ["rooms"], hall, ["lab", "hall"]]
```

- Selectors are ordinary function values for user functions too:

```
def spread(list, key) => list.max(key) - list.min(key)
boxes = [{w: 2, h: 9}, {w: 5, h: 4}]
wide = spread(boxes, .w)
tall = spread(boxes, .h)
chain = {at: 1, next: {at: 2, next: {at: 3, next: null}}}
steps = ["x", "y"]
hop = steps.reduce(.next, chain)
assert: [wide, tall, hop.at], [3, 5, 3]
```

### Rendering

- A selector renders as its written path without spaces: `.amount`,
  `.to.city`. Graph and block keys, `why` and `affects` rules, `--graph`
  output and errors that quote an expression use that form, so
  `[{a: 1}].map(.a).nope()` raises
  `TypeError("[{\"a\":1}].map(.a).nope is not a function")`.
- A keyword renders in its canonical spelling, as member access renders it:
  `.self` renders as `.this`.
- Anonymous lambdas keep rendering as `function()`. A selector and its
  lambda spelling are therefore different keys, and two selectors of
  different paths are different keys where two lambdas are not.

### Bound

- A selector names at most 127 properties. The 128th `.NAME` pair raises
  `SyntaxError("Expression has too many parts")` at its `.`, whatever
  follows it.
- Nesting is bounded as before: a selector inside nested calls counts toward
  the existing expression nesting limit, and evaluation passes the existing
  expression depth limit, as the lambda's body does.

  result, assertions and graph.

## Errors

- No error type is added. Syntax errors stop compilation before any
  statement of the program runs.
- `SyntaxError("Unexpected '.'")` remains the error for every argument that
  starts with `.` and is not a complete selector, at its accepted position.
  When a complete selector comes earlier in the same argument list, the
  error is reported where it now occurs, as after any valid argument.
- `SyntaxError("Expression has too many parts")`: a selector's 128th `.NAME`
  pair. It is placed at that `.`.
- `SyntaxError("Expressions are nested too deeply")`: unchanged; a selector
  passes the nesting guard of any argument.
- `ReferenceError("<path> is not defined")`: a `.value` read of an undefined
  value inside a selector, as in member access. The path is the written
  selector path before `.value`, such as `.a` for `.a.value`; when the
  selector's own argument is undefined, the message is
  `ReferenceError(".value is not defined")`.
- `TypeError("Maximum expression depth exceeded")` still bounds evaluation.
- Errors of the receiving call are unchanged. A selector is a function, so
  a query that requires one, such as `maxBy`, accepts it, and a receiver
  that is not a list raises its accepted error.

## Reference Implementation

- `src/lang/ast/parser.rs`: for each argument, `arguments` counts the
  leading `.NAME` pairs with `selector_length`, a non-consuming scan bounded
  by `MAX_CHAIN`. When `starts_selector` finds a complete selector, the
  argument is built by `selector` inside the existing `nested_expression`
  guard; otherwise `argument` parses it as before. `selector` reads each name
  with the existing `member_property`, and `position_at` places the bound's
  error. The colon-led assertion statement keeps calling `argument`
  directly, so it accepts no selector.

  name; `Function::selector` builds the anonymous one-parameter function
  whose expression body is the member path read from that parameter, and
  `Function::selector_path` recognizes exactly that shape: it returns
  `None` unless the function has the unnamed one-parameter signature, then
  walks the member chain to the unnamed root.
- `src/lang/ast/generator.rs`: `write_function` renders a recognized
  selector as its path. Every function a source can write keeps its
  rendering.
- `src/lang/ast/identifier.rs`: `read_value` names an undefined

  accepted message.
