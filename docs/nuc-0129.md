## Abstract

- A list or a class population gains `zip(other)`. It pairs each item with
  the item at the same position of `other`, a list or a class population,
  and stops at the shorter of the two, so `[1, 2, 3].zip(["a", "b"])` gives
  `[[1, "a"], [2, "b"]]` and `Driver.zip(Truck)` pairs the instances of the
  two classes in population order.
- With a function as its second argument, `zip(other, (a, b) -> EXPR)`
  combines each pair with that function instead of building the pair, as
  Kotlin's `zip` with a transform and lodash's `zipWith` do, so
  `prices.zip(quantities, (p, q) -> p * q).sum()` totals an order.
- It joins the List and Population helpers of [NUC 61](nuc-0061.md) and its
  successors: a declaration that holds a `zip` stays live, and follows
  changes to both sequences and to the instances of either class.
- At the accepted revision `zip` called on a list or a class raises
  `TypeError("... is not a function")`, and only those inputs change. A
  function, property or variable named `zip`, and every other receiver,
  keep their readings.

## Motivation

- World models keep parallel facts in step: positions and values, sensors
  and readings, drivers and trucks, prices and quantities. Pairing them
  position by position is a basic step that Python, Kotlin, Rust, Haskell
  and lodash all call `zip`.
- Accepted programs pair parallel lists through positions. They write
  `xs.map(x -> [x, ys[xs.indexOf(x)]])`, which holds only while `xs` has no
  repeated items, because callbacks receive no index, or a `reduce` that
  grows its result with `concat` and reads `ys[acc.length]`. Both are long,
  and the first depends on the values. Elementwise arithmetic, such as a dot
  product, repeats the same positional lookups. `xs.zip(ys)` and
  `xs.zip(ys, f)` state the pairing once.
