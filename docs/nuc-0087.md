## Abstract

- A constructor parameter written `this.name`, or `self.name`, is the
  parameter `name` and also assigns it to the new instance's property
  `name`, before the constructor's own statements run. `class Point(this.x,
  this.y)` declares exactly the class that `class Point(x, y):` with the
  indented body `this.x = x` and `this.y = y` declares, as Dart's
  initializing formals and TypeScript's parameter properties do.
- Constructor parameter lists are the parenthesized list of a class header,
  whether the header is bodyless, has a colon body, names its parent after a
  colon or with `extends` ([NUC 78](nuc-0078.md)), and the parenthesized
  list of a `def init(...)` written directly in a class's indented body.
- A prefixed parameter keeps its type annotation, its literal default
  ([NUC 54](nuc-0054.md)) and, as the last parameter, its rest marker
  ([NUC 74](nuc-0074.md)): `class Account(this.owner: str, this.balance:
  int = 0)` and `class Route(this.name, ...this.stops)`.
- The parser builds accepted nodes only: the ordinary parameter, and one
  ordinary assignment statement `this.name = name` per prefixed parameter at
  the start of the constructor body, in parameter order. Binding, labels
  ([NUC 47](nuc-0047.md)), defaults, rest lists, `null` for missing
  arguments, dependencies, `why`, transactions, inheritance, `super`, the
  nearest nonempty constructor, canonical rendering and graph keys are
  therefore those of the written-out spelling.
- Every other parameter list, every bare signature and every other spelling
  after `this` keep their accepted diagnostics and positions. Only inputs
  that were errors at the accepted revision change.
- Each prefixed parameter saves four lexer tokens over a plain parameter and
  its own assignment line, and a header whose body held only those lines
  also drops the colon and the body's layout tokens: `class Point(this.x,
  this.y)` is 11 tokens, and its written-out spelling 22.
- No token kind, keyword, syntax tree node, public Rust item, dependency or
  version is added or changed. The authoritative contract is
  [Initializing constructor parameters](../nucleoid.spec.md#initializing-constructor-parameters).
- **Outcome: Accepted.** The independent evaluation and the caller's
  integrated-tree checks passed all three hard criteria, and the independent
  evaluator decided Accepted. The required token comparison ran in
  continuous mode: 13 cases use fewer tokens, 984 the same and none more. No
  policy check failed.

## Motivation

- A world model starts with its classes, and nearly every constructor first
  copies its parameters into properties. In the 984 cases of the accepted
  executable corpus, the specification, the executable reference and the
  `nuc` blocks of the README and the examples:
  - 452 statements on their own line assign a property from the parameter
    of the same name, `this.p = p` or `self.p = p`: 282 in the
    specification, 47 in the executable reference, 36 in the README and 87
    in the examples, in 225 cases. 42 more are the whole same-line body of a
    class header, `class C(p): this.p = p`.
  - 306 class headers have a parameter list. 291 of them begin their
    constructor with such assignments of their own parameters, and for 252
    the constructor holds nothing else.
- ARC world models have the same shape. All 29 ARC instruction datasets, the
  25 puzzle datasets and the shared `core`, `curve`, `extension` and `line`
  datasets, declare `class Obj(x: int, y: int, width: int, height: int,
  orientation: int, ...)` and then assign 5 to 8 of those parameters, one
  line each: 171 lines that repeat names the header already wrote.
- Each such line writes the name twice more, and a model that writes the
  class must keep all three copies consistent. A slip is silent or late:
  after `this.widht = width`, a class-level rule that reads `$Obj.width`
  settles to `null` for every instance, and `this.width = widht` raises
  `ReferenceError("widht is not defined")` only when the first instance is
  created. A prefixed parameter names the property once, where the
  parameter is declared.
- Shorter world models cost fewer tokens to generate and to read back. The
  `Obj` declaration that most ARC datasets open with, five typed
  parameters, their five assignments and a tag, takes 62 lexer tokens
  written out and 42 with prefixed parameters, and both spellings parse to
  the same syntax tree.
- [NUC 14](nuc-0014.md) left constructor-property assignment out of its
  scope and kept the rule that parameters alone create no properties. This
  NUC adds the assignment explicitly, per parameter, and keeps that rule.
- Prior art: Dart's initializing formals `Point(this.x, this.y);`,
  TypeScript's parameter properties `constructor(public x: number)`, PHP 8's
  constructor promotion, Crystal's `def initialize(@x)`, Kotlin's
  `class Point(val x: Int)`, and the primary constructors of Scala and C#.
  Dart's spelling is the one adopted, because it writes the receiver that
  the body writes.

- **Confirmed category and mode.** The caller made one tool-backed uniform
  draw over the five categories that NUC 1's registry marks eligible for
  automatic selection, at 2026-11-07T00:24:29-05:00 with PowerShell's
  `Get-Random -Minimum 0 -Maximum 5`. It drew index 0, Syntax enhancement,
  with probability 1/5 and no redraw. This is a continuous cycle, so token
  comparison is required. Runtime applicability does not apply to this
  category. The primary purpose is a shorter spelling of an accepted
  construct, so the prior art in other languages does not move it to
  Language compatibility.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero, because no rubric was frozen. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Other candidates in this category.** Before this one the caller set
  aside selector expressions such as `f(.a == 1)` and optional chaining
  `a?.b`, whose `SyntaxError("Unexpected '.'")` diagnostics
  `tests/property_selectors.rs` pins; chained comparisons `a < b < c`, which
  have an accepted left-associative reading; floor division `//`, an
  accepted empty regular expression whose reading `tests/c_style_comments.rs`
  pins; and list comprehensions, which are free syntax but cost more tokens
  than `filter` and selector projections in their common filter-only and
  projection-only shapes.
- **Only a former error.** At the accepted revision a parameter written
  `this.` or `self.` in any parenthesized list raises
  `SyntaxError("Expected a parameter but found keyword 'this'")`, placed at
  the token after the keyword; `self` lexes as the keyword `this`. No test
  pins that message. Giving the complete form a meaning in constructor lists
  therefore changes no program that the accepted parser accepts.
- **The receiver it assigns.** `this.name` is the target that the body
  writes today, so the header reads as the assignment it abbreviates, in
  either receiver spelling, and no word is added to the language. Rejected:
  - a `data class` or `record` modifier: `data class Point(x)` already parses
    as the two juxtaposed statements `data` and `class Point(x)`, so a
    modifier would change accepted programs, and it would decide for every
    parameter at once;
  - assigning every parameter automatically: parameters alone create no
    properties at the accepted revision, as `class Shell(code: int)` shows,
    and [NUC 14](nuc-0014.md) and [NUC 47](nuc-0047.md) state that rule;
  - contextual words such as Kotlin's `val`, TypeScript's `public` or PHP's
    `private`: each is an ordinary identifier elsewhere, and `class P(val x)`
    would make a juxtaposed name significant inside a parameter list, where
    `this` already says what is meant;
  - Crystal's `@name`: `@` reads a state version ([NUC 53](nuc-0053.md)), so
    `@x` would give one token two meanings;
  - a leading dot, `.name`: in an argument list `.name` is a selector
    function ([NUC 79](nuc-0079.md)), so the same spelling would mean
    something else in a parameter list.
- **Only constructor lists.** A constructor creates the instance that its
  body assigns. Functions have no receiver to assign to, and in other
  methods the prefix would hide an assignment to an existing receiver behind
  its call. So named functions, methods other than `init`, function literals,
  arrow and thin-arrow functions and Python-style lambdas keep their accepted
  error.
- **Only `init` where it can be adopted.** A class with an empty constructor
  adopts the parameters and body of its `init` method, which is a method
  only when its `def` is written directly in the class's indented body. A
  `def init` written on the header's line after the colon is a constructor
  statement, not a method, and keeps its error, as one at the top level or
  nested in another statement does. Every `init` spelling with a
  parenthesized list is included: a block body, a same-line body and the
  arrow bodies `=>`, `->` and the indented `=>` of [NUC 32](nuc-0032.md).
- **Only parenthesized lists.** Bare signatures keep their accepted grammar,
  and their suites pin `SyntaxError("Expected '(' but found keyword 'this'")`
  for `def f this:` and its relatives. So `def init this.x:` in a class body
  keeps that error.
- **Accepted nodes.** A prefixed parameter becomes the ordinary `Parameter`
  with its name, annotation, default and rest flag, and the parser adds the
  ordinary statement `this.name = name` to the start of the constructor
  body, the `Stmt::Assign` that the written-out line parses to. Nothing else
  records the prefix, so the runtime, the renderer, graph keys, `why` and
  every syntax tree walker see the written-out spelling, as
  [NUC 79](nuc-0079.md) parses a selector to its lambda. Rejected: a field
  or variant that marks the parameter, which would break exhaustive matches
  over the public syntax tree and duplicate what the statement already says;
  and assigning from the parameter list at run time, a second constructor
  path that could drift from the body's.
- **Before every written statement.** The assignments come first, in
  parameter order, so the body can read the properties the header assigns
  and a subclass's own properties exist before `super(...)` runs its
  parent. A parent that assigns the same property assigns it afterwards, so
  its value stands, as in the written-out spelling with the assignment
  first. Rejected: assigning after a leading `super(...)`, as TypeScript
  does, which would make the position of `super` change what the header
  means. A body that needs another order writes its assignment out.
- **A nonempty constructor.** Because the statements are ordinary
  constructor statements, a bodyless header with a prefixed parameter has a
  nonempty constructor, exactly as its written-out spelling has. It does not
  adopt an `init` method, and a bodyless subclass header with a prefixed
  parameter is its own nearest nonempty constructor. A header whose
  parameters are all plain keeps its accepted empty constructor.
- **Names.** Exactly one property step whose name is an identifier, which is
  also the parameter's name. Rejected: paths such as `this.a.b`, which would
  assign through another object; computed names such as `this["x"]`; and
  keywords such as `this.class`, which member access accepts but which
  cannot name a parameter.
- **Accepted diagnostics.** The parser qualifies a prefixed parameter by its
  tokens, `this`, `.`, an identifier and then `,`, `)`, `:` or `=`, before
  it consumes anything. Every other spelling reaches the accepted parameter
  parser unchanged and raises its accepted error at its accepted position. A
  qualified parameter followed by a later mistake reports the mistake that
  its plain spelling reports there.
- **Repeated names.** `class P(x, x)` is accepted, and the later binding
  wins. The prefix keeps that rule: `class P(this.x, this.x)` assigns the
  later argument twice, and `class P(this.x, x)` assigns the later argument
  once, as their written-out spellings do.
- **Tentative statements.** Some statements are parsed as attempts that fall
  back to another reading when they fail: destructuring declarations,
  `while` headers, `suppose` premises, Python-style conditions and, in a
  program read again for `is` ([NUC 86](nuc-0086.md)), the check that a
  header's tokens also parse as separate statements. A class header can sit
  inside such a statement only in the braced body of a function literal or
  arrow function. At the accepted revision the attempt and its fallback both
  reach that header and fail, or the fallback fails earlier, so the input
  was an error; the attempt may now succeed. For example
  `a, b = [function() { class P(this.x) }, 1]` raised the fallback's
  `SyntaxError("Unexpected ','")` and now destructures. The grid under
  Compatibility shows the accepted error of every such context.
- **Interactive input.** The native REPL buffers input by lexical header
  scans, so `class P(this.x)` runs at once and `class P(this.x):` waits for
  its indented body, as plain headers do. Neither the REPL nor the terminal
  workspace needs a change.
- **An accepted oddity, unchanged.** At the accepted revision
  `class Sub(b): Base` followed by an unindented statement takes that
  statement as its one constructor statement, because a colon parent leaves
  the colon open for a body. So `class Base(a):` with the indented
  `this.a = a`, then `class Sub(b): Base`, `x = 5` and `x` raises
  `ReferenceError("x is not defined")`. With a prefixed parameter the
  adopted statement follows the prepended assignment, which keeps that
  accepted behavior. The `extends` spelling and an indented body avoid the
  shape, and no case uses it.

## Specification

### Grammar

- In a constructor parameter list a parameter may carry a receiver prefix:

```
parameter = [ "..." ] [ receiver "." ] name [ ":" type ] [ "=" literal ]
receiver  = "this" | "self"
```

- `name` and `type` are identifiers, and `literal` is a literal default of
  [NUC 54](nuc-0054.md). The rest marker, its placement and its errors are
  those of [NUC 74](nuc-0074.md).
- Constructor parameter lists are:
  - the parenthesized list after `class Name`, whatever follows it: the end
    of the header, `extends Parent` ([NUC 78](nuc-0078.md)), a colon and an
    indented body, a colon and a statement on the same line, or a colon and
    a parent name;
  - the parenthesized list after `def init` when that `def` is written
    directly in a class's indented body, whatever its body: indented,
    same-line, `=>`, `->` or the indented `=>` of [NUC 32](nuc-0032.md).
- A prefix qualifies only when the tokens `this` or `self`, `.` and an
  identifier are directly followed by `,`, `)`, `:` or `=`. Line breaks
  inside the parentheses are not layout, and spaces around `.` are allowed,
  as in member access.
- Every other parameter list accepts no prefix, and every other token
  sequence after `this` or `self` reaches the accepted parameter parser
  unchanged.

### Semantics

- A prefixed parameter is the ordinary parameter `name`, with the same
  annotation, default and rest flag as its plain spelling.
- For each prefixed parameter, in parameter order, the statement
  `this.name = name` is added before every statement written in the
  constructor body, including a leading `super(...)`. In a `def init` the
  statements start the method's body, and an arrow body `=> expression` is
  the statement `return expression` after them.
- The resulting class declaration and `init` method are exactly those of
  the written-out spelling, so everything that reads them behaves as it
  does for that spelling:
  - binding: positional, labelled and mixed arguments, `null` for a missing
    argument, literal defaults, the rest list and repeated names, where the
    later binding wins;
  - the instance: its properties, dependencies, standing rules that read
    them, `why` and `affects`, which explain `p.x` by the rule
    `$Point.x = x`, and rollback of a failed construction;
  - classes: redeclaration, class-level rules, populations, `init`
    adoption, `super`, the nearest nonempty constructor, canonical
    rendering, graph keys and serialization.
- A header with a prefixed parameter has a nonempty constructor even when it
  has no body. A header whose parameters are all plain, including a rest
  header, still creates no properties and does not displace a parent's
  nearest nonempty constructor. Typed attributes in class bodies, such as
  `x: int`, are unchanged.

```
class Point(this.x, this.y)
origin = Point(0, 0)
corner = Point(3, 4)
assert(corner, {"id": "corner", "x": 3, "y": 4})
assert([typeof corner, Point.length], [Object, 2])
$Point.far = $Point.x + $Point.y > 5
assert([origin.far, corner.far], [false, true])
```

- The prepended assignments run before the body, which can read both the
  parameters and the properties:

```
class Rectangle(self.width, self.height):
    this.area = width * height
    this.square = this.width == this.height
box = Rectangle(2, 5)
assert([box.width, box.height, box.area, box.square], [2, 5, 10, false])
box.width = 5
assert([box.area, box.square], [10, true])
```

- Annotations, defaults, labels and the rest marker keep their meanings:

```
class Account(this.owner: str, this.balance: int = 0, this.currency = "EUR")
named = Account(currency="USD", owner="cy")
mixed = Account("di", currency="GBP")
assert([named.owner, named.balance, named.currency], ["cy", 0, "USD"])
assert([mixed.owner, mixed.balance, mixed.currency], ["di", 0, "GBP"])
class Route(this.name, ...this.stops)
loop = Route("loop")
assert([Route("north", "oslo", "bodo").stops, loop.stops], [["oslo", "bodo"], []])
```

- A subclass's own prefixed parameters are assigned before `super(...)`
  runs, and a bodyless subclass uses its parent's prefixed constructor:

```
class Vehicle(this.make, this.wheels = 4)
class Van extends Vehicle
class Racer(this.wheels) extends Vehicle:
    super("kart", wheels * 2)
van = Van("ford")
racer = Racer(3)
assert([van.make, van.wheels, racer.make, racer.wheels], ["ford", 4, "kart", 6])
```

## Reference Implementation

- `src/lang/ast/parser.rs` is the only source file that changes, by 105
  added and 20 removed lines against the accepted revision:
  - `parameter_list(initializing)` is the accepted loop over a
    parenthesized list. It returns a private `ParameterList` that holds the
    parameters and the statements recorded for prefixed ones.
  - `parameters`, which every list that is not a constructor list uses, is
    `parameter_list(false)` and returns its parameters, so those lists parse
    exactly as before.
  - `constructor_parameters` is `parameter_list(true)`. For each parameter
    it consults `starts_initializing_parameter`, which qualifies `this`,
    `.`, an identifier and then `,`, `)`, `:` or `=` without consuming a
    token. The loop then skips the two prefix tokens, parses the parameter,
    its annotation, its default and its rest marker with the accepted code,
    and records the statement `this.name = name` that `initializer` builds.
  - `class_statement` reads a header's list with `constructor_parameters`,
    or uses an empty `ParameterList` without one, and passes it on directly
    or through `extends_class`. `class_declaration`, the former
    `empty_class`, takes the list apart and starts the declaration's
    constructor with the recorded statements, on every path: bodyless,
    colon, same-line, colon parent and `extends`. `class_body` then appends
    the written statements as before.
  - `class_members` parses each member `def` with `method_declaration`. A
    `def init` directly followed by `(` reads its list with
    `constructor_parameters` and starts its body with the recorded

## Cost

- Recognition is a four-token lookahead at each parameter of a constructor
  list, done once; every other list and every other statement are parsed
  exactly as before, with no second reading and no new pass.
- The prepended statements are the ones the written-out spelling parses to,
  so construction runs the same statements, and the work of a program is
  that of its written-out spelling.
- No new bound is needed. A parameter list has no length limit, as
  [NUC 47](nuc-0047.md) notes, and each prefixed parameter takes at least
  three tokens and adds one flat statement of constant depth: no recursion
  and no chain is involved, so `MAX_NESTING` and `MAX_CHAIN` do not apply,
  and the work is bounded by the input.
- Measured in process with release builds of the accepted and candidate
  libraries, timing `tokenize`, `parse` and `Runtime::run` with
  `std::time::Instant`, as medians of 11, 11 and 5 runs:

| Program | Accepted, written out | Candidate, written out | Candidate, prefixed |
| --- | ---: | ---: | ---: |
| 1,000 / 4,000 / 16,000 parameters, one per line: parse ms | 2.2 / 8.9 / 35.3 | 2.3 / 8.6 / 35.4 | 1.2 / 4.8 / 19.6 |
| The same with one instance: run ms | 5.6 / 22.8 / 93.1 | 5.5 / 22.3 / 96.4 | 4.5 / 19.6 / 79.2 |
| 500 / 1,000 / 2,000 / 4,000 classes of three parameters: parse ms | 4.0 / 8.1 / 16.6 / 33.9 | 4.3 / 7.8 / 15.9 / 33.1 | 2.6 / 4.4 / 9.0 / 20.1 |
| The same with one instance each: run ms | 12.3 / 24.7 / 52.7 / 116.3 | 12.5 / 25.4 / 51.2 / 118.8 | 11.4 / 22.8 / 46.0 / 103.6 |

- Parse and construction time grow linearly with the number of prefixed
  parameters, an accepted program parses in the same time on both builds,
  and the prefixed spelling is faster because it has fewer tokens. A
  re-check on the final candidate gave the same picture: 1,000, 4,000 and
  16,000 parameters one per line parse in 1.8, 8.7 and 37.4 ms written out
  on the accepted build, 2.0, 9.0 and 36.3 ms written out and 1.2, 5.0 and
  22.0 ms prefixed on the final candidate.
- A pre-existing cost of the accepted lexer is not changed: it places each
  token by counting the characters from the start of its line, so one very
  long line takes time quadratic in its length, whatever it holds. A header
  of 16,000 parameters written on one line, with its call, takes 1,270 ms to
  lex in its written-out spelling on the accepted build and 2,859 ms in the
  prefixed spelling, whose line is twice as long. The parse after lexing
  and the construction stay linear in both, and one parameter per line, as
  above, avoids the long line.
