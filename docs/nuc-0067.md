# NUC 67 -- Destructuring Declarations

```

Status: Automatic-Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 31-Oct-2026
Requires: 17, 44, 45, 65
```

## Abstract

- Adds destructuring declarations in three spellings: object patterns
  `{x, y} = point`, renamed targets `{key: name} = source`, and Python-style
  unpacking `a, b = pair`.
- Each target becomes exactly one ordinary declaration, in pattern order:
  `{x, y} = point` is `x = point.x` followed by `y = point.y`, and
  `a, b = pair` is `a = pair[0]` followed by `b = pair[1]`. A destructured
  name is filed, kept live, explained and rolled back exactly as the
  declaration it abbreviates.
- The value is evaluated once per target. A value that calls a function or
  creates an instance does so once for every target; naming such a value
  first evaluates it once.
- The parser produces the declarations. No token, syntax tree node, statement
  kind or runtime path is added.
- A destructuring is a whole statement on one line. Every input that is not a
  complete destructuring keeps its accepted parse and diagnostic, including
  JavaScript's list form `[a, b] = pair`, which still parses and raises
  `SyntaxError("Cannot assign to [a,b]")` when it runs.
- The authoritative contract is the
  [destructuring declarations](../nucleoid.spec.md#destructuring-declarations)
  section.
- The first revision was rejected on 31-Oct-2026: the value is copied into
  every target, so nested destructurings whose values hold functions with
  parameter defaults render exponentially. With two targets, the 292-byte
  program `n0, n1 = [(p = 1) => { n0, n1 = [(p = 1) => { ... }] }]`, ten
  levels deep, gives `(why n0)[0].rule.length` of 113,656, and a 1,006-byte
  block of 48-target destructurings nested four deep exceeded 1.5 GB. The
  128-target bound limits one level only.
- This revision ports that candidate, unchanged in design, onto the current
  accepted revision for a decision under the automatic acceptance rule; see
  [Port to the current accepted revision](#port-to-the-current-accepted-revision).
- Automatic-Accepted on 01-Nov-2026 under the automatic acceptance rule: the
  ported candidate meets every hard criterion, with no compile errors, every
  test passing and full backward compatibility, but its policy check failed:
  independent evaluation rejected the port again because nested
  destructurings whose values hold functions with parameter defaults still
  render exponentially. Re-measured on the port, two-target nesting 12 levels
  deep gives `(why n0)[0].rule.length` of 538,616 from 342 bytes, and a
  1,013-byte block of 48-target destructurings nested four deep hit a 1.5 GB
  watchdog. See [Evaluation of the port](#evaluation-of-the-port).

## Motivation

- A world model reads structured state: positions, sizes, ranges, routes and
  the fields of instances. Naming the parts of a record is one of the most
  common things a program does with it.
- Accepted Nucleoid names each part with its own declaration and repeats the
  source every time: `x = rover.position.x y = rover.position.y`. The
  repetition costs tokens, hides the shape of the record, and lets one copy
  drift from the others.
- LLMs write JavaScript object destructuring and Python tuple unpacking
  constantly. Both are syntax errors in accepted Nucleoid, so a model has to
  translate them into one declaration per name.
- Destructuring in Nucleoid keeps the declarative meaning of `=`: every name
  stays live. After `{x, y} = point`, changing `point.x`, or replacing
  `point`, updates `x`. JavaScript and Python copy the values once.
- The forms are shorter than the declarations they stand for:
  `{x, y} = point` is 7 lexer tokens against 10 for
  `x = point.x y = point.y`, and `a, b = pair` is 5 against 12 for
  `a = pair[0] b = pair[1]`.

## Rationale

- **Category and token policy.** The caller selected Syntax enhancement by one
  uniform draw over the four eligible registry categories, index 0 with
  probability 1/4 and no redraw, in continuous mode, so the token
  non-regression gate is required. All eleven new measured cases are paired
  with the most compact accepted spellings found, executed by the accepted
  runtime and supplied through `NUC_PROPOSAL_EXTRA_BASELINES` before any
  candidate edit. Each counterpart writes the declarations of a pattern on one
  line, with `;` inside an inline suite, where juxtaposition would move the
  later declarations out of the suite. In
  `Nucleoid rolls back failed destructuring`, the counterpart of the failed
  `try: low, high = wide` declares only `high`, because the rolled-back
  `low` is not observable. No pre-existing case is rewritten; the independent
  evaluator measures the comparison. This bullet describes the first
  revision. The port is a user-requested revision in single mode, so token
  comparison is skipped and needs no counterparts; the first revision's
  measured comparison stays in the Evaluation section.
- **A lowering, not a new statement.** Each target is one ordinary assignment
  statement whose value is the source read by key or position. Graph keys,
  `why`, `affects`, standing and imperative contexts, locals, class bodies,
  transactions and rollback are therefore those of `=`, with no second
  implementation to keep in step.
- **Why not a hidden temporary or a batched statement.** JavaScript and
  Python evaluate the source once and assign the parts. Nucleoid could do the
  same in two ways, and both were rejected:
  - a hidden temporary, `t = point` followed by `x = t.x`, would add a graph
    node the program never wrote, make `why x` explain `x = t.x` and route
    `affects point` through `t`;
  - a statement node that evaluates the source once and assigns every target,
    or that defers propagation to the end of the statement, would be a new
    public `Stmt` and `Nuc` variant, a SemVer-visible change for exhaustive
    matches, and a second assignment path whose filing, explanations and
    rollback would differ from the declarations it abbreviates.
- **The value runs once per target.** A target's declaration reads its own
  copy of the value, so a call or an instantiation in the value runs for each
  target, each time that target's declaration runs.
  `{x, y} = Point(1, 2)` creates two points, and a function with effects is
  called once per name. To evaluate such a value once, name it first:
  `p = Point(1, 2)` and then `{x, y} = p`.
- **Patterns read like the literal that rebuilds them.** An object pattern
  uses the accepted object-literal entry grammar restricted to names:
  shorthand entries, which need a following comma or `}` as in
  [NUC 17](nuc-0017.md); keyed entries `key: name`, which may follow each
  other without a comma as in [NUC 44](nuc-0044.md); and one optional trailing
  comma. `{name: other area: larger, depth}` is the literal that would put
  `other`, `larger` and `depth` back under those keys.
- **Python-style unpacking by position.** Names separated by commas, with at
  least one comma and an optional trailing comma, unpack by index: the target
  at position `i` reads `source[i]`. Lists, strings and anything else that
  `source[i]` reads unpack this way, and `first, = word` takes position 0.
  There is no arity check: a missing position reads `null`, as `source[i]`
  does, and extra positions are ignored. Rejected: Python's arity error,
  which no declaration can express and which would make a live name fail
  whenever its list grew.
- **The list form stays as it is.** `[a, b] = pair` parses today as an
  assignment to a list and raises `SyntaxError("Cannot assign to [a,b]")` only
  when it runs, so an untaken branch holding it runs cleanly. Giving it a
  meaning would change accepted behavior. The comma form is the unpacking
  spelling.
- **A whole statement on one line.** A destructuring starts where a statement
  starts on its own: at the start of the input, after a line break, a `;`, an
  indentation change, the `{` of a block or the `:` of a suite. It ends at the
  end of its line or input, a `;`, a block's `}`, or the `else` or `catch`
  that continues an inline suite. Its pattern contains no line break. So
  `let {x, y} = point`, `const a, b = pair` and `var a, b = pair`, Python's
  tuple values `a, b = 1, 2` and swaps `x, y = y, x`, and chains
  `a, b = c = pair` remain syntax errors with their accepted diagnostics,
  instead of becoming a stray name, a destructuring and a run-time failure.
- **Recognition is an attempt.** The pattern is qualified by looking ahead
  without consuming anything; the value is then parsed and the end checked.
  If any part does not qualify, the parser reads the statement exactly as the
  accepted parser does, which reports the accepted diagnostic. Rejected:
  committing after the `=`, which would place an error inside the value where
  it occurs but change the accepted diagnostic of every malformed input shaped
  like a destructuring.
- **Recognition stays linear.** The accepted parser rejects every qualified
  pattern on reaching its `=` or earlier, so falling back never parses a value
  again. Each value is parsed once by its own attempt, also when it holds
  block-bodied functions or arrows that contain destructurings themselves and
  every one of them fails. A parser that re-read values on the way back would
  read the innermost value once per enclosing level and double its work with
  each level of nesting.
- **One plain value.** The value is one expression, parsed as the right side
  of `=` is, except that it cannot itself be an assignment. A chained value
  would be copied into every target and assign its own target again whenever
  one of them re-ran.
- **Propagation between targets.** The declarations run in pattern order and
  each one propagates before the next, exactly as when they are written out.
  A standing rule that reads two targets can therefore run between them and
  see the first one new and the second one old: redeclaring `low, high` under
  `if low > high: throw "INVERTED"` raises where a simultaneous update would
  not, and writing the declarations out behaves the same way. Propagation
  caused later by a change of the source settles upstream work first, so both
  targets update before such a rule runs.
- **Transactions.** The declarations are ordinary statements of the enclosing
  run or `try` body. A failure in any target, including one raised by
  propagation, rolls back the enclosing transaction, so no target of a failed
  destructuring stays declared.
- **Duplicate targets.** A name may appear twice. Its declarations run in
  order and the last one stands, as with the declarations written out and as
  in Python and JavaScript assignment: `a, a = pair` leaves `a = pair[1]`.
- **A bound on targets.** The value is copied into every declaration, so a
  pattern names at most 128 targets, a bound of its own with the same value as
  the parser's chain bound. Without a bound, a pattern of many names over a
  large value would multiply the syntax tree by its length.
- **The statement's value** is the value of its last target's declaration, as
  for the declarations written out, so a program or a native REPL input that
  ends with a destructuring shows that value.
- **Not added.** Nested patterns, defaults, rest and star targets, string,
  numeric and computed keys, property and index targets, `:=` and compound
  operators, `let`, `var` and `const`, destructured parameters, `for` headers
  and lambda parameters, `suppose` premises, multi-line patterns, tuple values
  and swaps, destructuring in expression positions, and any change to
  `[a, b] = pair`.

## Specification

### Syntax

- An object pattern is `{` entries `}`. An entry is a shorthand `name` or a
  keyed `key: name`, where `key` and `name` are ordinary identifiers.
  Shorthand entries are followed by `,` or `}`. A keyed entry may be followed
  by `,`, `}` or directly by the next keyed entry. One trailing comma is
  allowed. A pattern has at least one entry.
- A Python-style pattern is a list of ordinary identifiers separated by
  commas, with at least one comma and an optional trailing comma: `a, b`,
  `a, b,` and `a,`.
- A destructuring is `pattern = value`, where `value` is an expression
  accepted on the right of `=` that is not itself an assignment.
- The pattern begins a statement: it is the first token of the input, or
  follows a line break, `;`, an indentation change, the `{` of a block or the
  `:` of a suite. The pattern and its `=` contain no line break.
- The value is followed by the end of the line or input, `;`, a block's `}`,
  or `else` or `catch`.
- Spaces between tokens are free: `{x,y}=point` and `{ x, y } = point` are
  the same statement.

### Lowering

- Each entry becomes one assignment statement, in pattern order:
  - an object entry with key `key` and target `name` becomes
    `name = value.key`, with `value` read as a member access;
  - the Python-style target at position `i`, counted from 0, becomes
    `name = value[i]`.
- `value` is the parsed value, copied into each statement. The statements are
  exactly those the parser builds for the written-out declarations, so
  `{x, y} = point` and `x = point.x` then `y = point.y` parse to the same
  statements.
- Each statement is then filed or carried out as that declaration would be in
  the same place.

```
point = {x: 3, y: 4, z: 0}
{x, y, z} = point
assert: [x, y, z], [3, 4, 0]
point.x = 6
point.z = 2
assert: [x, z], [6, 2]
point = {x: 1, y: 2}
assert: [x, y, z], [1, 2, null]
size = {w: 5}
{w, h,} = size
assert: [w, h], [5, null]
size.h = 4
size.w = 3
assert: [w, h], [3, 4]
x + y + w * h
```

- This is the complete
  `Nucleoid destructures object fields into standing declarations` entry,
  without its title and expected-return metadata; it returns `15`.

### Semantics

- A target's declaration evaluates its copy of the value and reads the key or
  position, so it depends on what that read reaches, and a later change to
  any of it updates the target. A missing key or position reads `null`, as
  `value.key` and `value[i]` do.
- The value is evaluated once per target, each time that target's
  declaration runs. A call or an instantiation in the value runs once per
  target: `{x, y} = Point(1, 2)` creates two points. `p = Point(1, 2)`
  followed by `{x, y} = p` creates one.
- The declarations run in pattern order. Each one propagates before the next
  runs, as consecutive statements do.
- A name that appears more than once is declared once per appearance, and the
  last declaration stands.
- The statement's value is the value of its last target's declaration.

### Contexts

- **Top level.** Each target is a standing declaration.
- **Functions and methods.** A target that names a parameter or other local
  is assigned locally; any other name is a state variable, as with `=`.
- **`for` bodies, standing `if` branches and blocks.** The declarations are
  carried out each time the body, branch or block runs, as `=` is there. A
  destructuring inside a block makes the block depend on what the value read.
- **Inline suites.** A destructuring after a suite's `:` puts all of its
  declarations in that suite: `if ready: low, high = pair` assigns both names
  only when `ready` holds.
- **Class bodies.** The declarations are constructor statements, as `=` is.
- **`suppose` suites.** The declarations run in the hypothetical world and are
  discarded with it. `PATTERN = suppose: ...` and
  `PATTERN = suppose PREMISE: ...` are not hypothetical blocks and keep their
  accepted diagnostics; `{x} = suppose` reads the name `suppose`, as
  `x = suppose` does.

### Explanations and rendering

- `why` explains a destructured name as its declaration: `x = point.x` or
  `first = pair[0]`, with the `from` of that declaration. `affects` of the
  source lists the declarations.
- Graph keys and block keys render the declarations, so a block holding
  `{x, y} = point` is the block holding `x = point.x` and `y = point.y`.
  Nothing records that the declarations were written as a pattern.

### Bound

- A destructuring names at most 128 targets. The 129th target of an otherwise
  complete destructuring raises
  `SyntaxError("Destructuring has too many targets")` at that target.

### Compatibility

- No token is added, and no accepted program changes its tokens, parse,
  diagnostics or behavior: a statement that begins with a qualified pattern
  and `=` was always a syntax error, because no statement can begin with `=`
  after a block and no statement can begin with `,`.
- These inputs keep their exact accepted parse and behavior:
  - `[a, b] = pair` parses and raises
    `SyntaxError("Cannot assign to [a,b]")` when it runs;
  - `{ x }` is a block, and `box = {x, y}` and `record = {left: x right: y}`
    build objects;
  - `for key, value of source:` and `for key, value in source:` keep the
    entry-loop parse of [NUC 72](nuc-0072.md); they are not destructuring;
  - `{ amount, label }` raises `SyntaxError("Unexpected ','")` at line 1,
    column 11, and `{ amount: 1 next: 2 }` raises
    `SyntaxError("Unexpected ':'")` at line 1, column 11.
- Inputs shaped like a destructuring that do not qualify keep their accepted
  diagnostics, among them `{x, y} == point`, `{x, y} := point`,
  `{x} += point`, `a, b += pair`, `a, b = 1, 2`, `x, y = y, x`,
  `a, b = c = pair`, `(a, b) = pair`, `let {x, y} = point`,
  `var a, b = pair`, `const [a, b] = pair`, `{x, ...rest} = p`,
  `a, *rest = p`, `{x = 1, y} = p`, `{"x"} = p`, `{0: a} = p`,
  `{x: a.b} = p`, `{x: {y}} = p`, `{x,, y} = p`, `{} = point`,
  `{x y} = point`, `{x: a y} = point`, multi-line patterns,
  `a.b, c = pair`, `a[0], c = pair`, `{x, y} = point)`,
  `{x} = point if ready`, `a, b = pair c = 1` and `{x} = suppose y = 1: y`.
- Every program that changes contains a destructuring and was a syntax error.
  The changes are:
  - well-formed patterns whose keys or targets are names that other
    statements read specially now destructure. These four inputs were syntax
    errors:

| Exact source | Previous error | Now |
| --- | --- | --- |
| `{assert: x} = p` | `SyntaxError("Expected ',' but found '}'")`, line 1, column 11 | `x = p.assert` |
| `{lambda: x} = p` | `SyntaxError("Unexpected '='")`, line 1, column 15 | `x = p.lambda` |
| `{suppose: x} = p` | `SyntaxError("Unexpected '='")`, line 1, column 16 | `x = p.suppose` |
| `{x: int} = point` | `SyntaxError("Unexpected ':'")`, line 1, column 5 | `int = point.x` |

  - a complete destructuring followed by a stray `else` or `catch` now
    reports that keyword:

| Exact source | Previous error | Error under this NUC |
| --- | --- | --- |
| `pair = [1, 2]`, then `a, b = pair else: x = 1` | `SyntaxError("Unexpected ','")`, line 2, column 4 | `SyntaxError("Unexpected keyword 'else'")`, line 2, column 17 |
| `point = {x: 1}`, then `{x} = point catch e: 1` | `SyntaxError("Unexpected '='")`, line 2, column 7 | `SyntaxError("Unexpected keyword 'catch'")`, line 2, column 19 |

  - a destructuring with more than 128 targets raises
    `SyntaxError("Destructuring has too many targets")` at its 129th target,
    where the accepted parser raised `SyntaxError("Unexpected ','")` for the
    pattern's first comma;
  - more generally, a program whose first syntax error followed a
    destructuring now reports the first error after it.
- The public `Token`, `Stmt`, `Expr` and `Nuc` enums are unchanged. `parse`
  and `parse_program` accept the new statements and return one
  `Stmt::Assign` per target, and `Program::positions` repeats the
  destructuring's position for each. These are additive changes; no project
  version is changed.

## Errors

- `SyntaxError("Destructuring has too many targets")`, at the 129th target of
  an otherwise complete destructuring.
- Each declaration raises what `=` raises for it, unchanged: for example
  `ReferenceError("pair is not defined")` when the value reads a missing
  name, errors and thrown values from calls in the value, and errors from the
  propagation a declaration causes. They roll back the enclosing transaction
  and are placed as the written-out declarations' errors are: a top-level
  destructuring's errors at its first token.
- Inputs that are not complete destructurings keep their accepted
  diagnostics.
- No other new error type or message is added.

    `tests/object_entry_loops.rs`;
  - `tests/destructuring.rs`, where `for a, b of pairs:` is no longer a near
    miss, because NUC 72 made it a valid entry-loop header. The test checks
    instead that both two-name headers keep that parse and that a
    destructuring in an entry-loop body parses to its written-out
    declarations and runs on every entry. A new test checks `while` loops
    beside destructuring, and the documents hold 846 cases.
- Beside NUC 63, `while` stays an ordinary name in patterns, as it is
  everywhere outside a loop header: `while, extra = pair`, `{while, b} = p`,
  `{loop: while} = p` and `a, b = while` destructure, and were syntax errors
  at `5573d8f6`. A destructuring in a `while` body, indented or after the
  header's `:`, is carried out on every iteration, as in a `for` body, and a
  loop condition reads destructured names as it reads their written-out
  declarations. A statement that begins with `while` and a condition followed
  by `:` stays a loop, and inputs such as `while a, b = pair: pass` keep their
  accepted diagnostics.
- The rejection finding is a property of the unchanged design and applies to
  this port as well; it is recorded in the Evaluation section and is not
  addressed here.

## Evaluation

- Independently **Rejected** on 31-Oct-2026 in continuous mode against
  accepted language revision `229950e6761c7bee5d7b6f6288913a763c18b2b9` and
  its immutable 791-case baseline: the 780 accepted cases plus the eleven
  paired accepted-syntax counterparts.
- Evaluated proposal Git blob:
  `572b565b4def32b6d4d65258ec74a702a1b34ed3`, before this outcome metadata.
- The Syntax enhancement category came from one uniform registry draw:
  index 0 among four eligible categories, with probability 1/4 and no
  redraw, so the token non-regression gate was required.
- Rejection reason: the bound on targets does not stop the value copies from
  multiplying. Parsing stays linear and function literals are shared, but a
  function literal with parameter defaults renders its full body, block keys
  render on every run, and `why` and `affects` render on demand. When a
  destructured value holds such a function whose body destructures again,
  the rendered size multiplies by the number of targets at each level:
  - with two targets, `(why n0)[0].rule.length` is 808, 4,536, 23,288 and
    113,656 at depths 4, 6, 8 and 10, from sources under 300 bytes, while
    the same nesting written with single declarations renders linearly, at
    157, 437 and 847 characters for depths 4, 8 and 12 on both revisions;
  - blocks of k-target destructurings nested d levels deep, each value
    `[(p = 1) => { ... }]`, measured with `Runtime::run` in a release build:
    k = 32, d = 4 (686 bytes) took 2.3 seconds and 501 MB; k = 128, d = 3
    (2,042 bytes) took 3.7 seconds and 832 MB; k = 48, d = 4 (1,006 bytes)
    exceeded a 1.5 GB watchdog after 10.9 seconds;
  - without parameter defaults, the k = 128, d = 3 input runs in 0.04 seconds
    and 5 MB, so the trigger is the combination.
- The Rationale presents the 128-target bound as the guard against the value
  copies multiplying the syntax tree, but it bounds one level only, and
  nesting compounds it to up to 128 to the power of the depth. Accepted

  the same reason: nested compound targets could clone an exponentially
  growing tree.
