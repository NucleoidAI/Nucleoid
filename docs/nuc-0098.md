## Abstract

- Adds three spellings of universal claims. Each builds the syntax tree of an
  accepted form, so its evaluation, dependencies, errors and rendering are
  that form's:
  - `every NAME in COLLECTION: CONDITION` is the quantifier
    `all NAME in COLLECTION: CONDITION` of [NUC 62](nuc-0062.md). It builds
    the `all` node and renders as `(all NAME in COLLECTION:CONDITION)`.
  - `every NAME`, where an operand begins, is the class reference `$NAME`,
    so `every Human.mortal = true` is `$Human.mortal = true`. Since
    revision 2 this holds outside if statements only.
  - The statement `$Class is WORD`, whose value is exactly one name that
    ends the line statement, is `$Class.WORD = true`, the rule that every
    instance has `WORD` `true`. So `$Human is mortal` and
    `every Human is mortal` both say that every Human is mortal, and render
    as `$Human.mortal=true`.
- The class-level rule of the Socrates example then reads as it is said:

```
class Human(name: str):
    this.name = name

every Human is mortal

socrates = Human("Socrates")
assert(socrates.mortal, true)
assert(every h in Human: h.mortal, true)
```

- Class names stay exact and case-sensitive: `every Human` reads `$Human`,
  and `every human` reads `$human`.
- Everywhere else `every` keeps every accepted reading, including the list
  query `xs.every(...)`, a variable, function, parameter, property, key or
  label named `every`, and `every` followed by anything but a name. Three
  readings with a following name are kept too: `every is ...`, the `is`
  assignment or comparison of a variable named `every`; `every NAME:`
  outside a header, where `NAME:` begins the next comma-free property or a
  colon statement; and the top level of a template interpolation. A variable
  named `every` does not disable the new forms.
- No token, keyword, syntax-tree variant, error type, option or flag is
  added, and no public item is added or removed. Revision 1 adds no error
  message; revision 2 adds one. The authoritative contract is
  [Every quantifiers, class references and predicate sentences](../nucleoid.spec.md#every-quantifiers-class-references-and-predicate-sentences).
- The user accepted three compatibility breaks in advance, each limited to
  the inputs it names:
  - Inputs where the name `every`, a binder name and `in` follow each other
    where an operand begins, outside the top level of a template
    interpolation, raised a `SyntaxError`, usually
    `Unexpected keyword 'in'`. They now read as `all`. The one assertion
    that pinned such an error, `ok = every v in xs: v` in
    `tests/quantifiers.rs`, moves to the quantifier reading.
  - Where an operand begins, the name `every` directly followed by a name
    ended one statement or item, and the name began the next. So after
    `every = 3`, `every Human = 4` ran as `every` and `Human = 4`. Those
    inputs now read `$NAME`, and `every Human = 4` raises
    `SyntaxError("Cannot assign to $Human")` when it runs.
  - Statement-level `$Class is WORD` that ends its line statement ran as the
    three statements `$Class`, `is` and `WORD`, so `$Human is mortal` raised
    `ReferenceError("is is not defined")` at its `is`. It now states the
    predicate. The same words followed by more of the line, as in
    `$Human is mortal x = 1`, keep their accepted reading.
- Any other change to an accepted parse, behavior, output or pinned test
  still fails backward compatibility.
- **Accepted** under the user-requested basis of the automatic acceptance
  rule: the frozen candidate meets every hard criterion, with the three
  breaks above and no other. The independent evaluator's overall decision is
  also Accepted. Token comparison was skipped as `single_proposal`, the rule
  for a single-proposal request, not a failed check; see
  [Evaluation](#evaluation).
- Revision 2 keeps `every` class references out of if statements, as the
  user requested. Lexically anywhere inside an if statement, in its
  condition and in the bodies of its `if`, `elif` and `else` clauses with
  everything nested in them, `every NAME` where revision 1 reads `$NAME`
  raises `SyntaxError("Use all instead of every inside if")` at the line and
  column of the `every`, so the program does not run. A predicate sentence
  whose subject is spelled `every Class` raises it there too.
- A condition then reads with `any` and the rule it guards with `all`, the
  spellings of `$NAME` that [NUC 104](nuc-0104.md) adds, and `every` stays
  the spelling of claims made outside if statements:

```
class Object(number):
    this.number = number
every Object.label is square
if any Object.number > 4:
    all Object.color is red
a = Object(3)
b = Object(7)
assert([a.label, b.label], ["square", "square"])
assert([a.color, b.color], [null, "red"])
```

- Only that reading changes. Inside if statements the quantifier
  `every v in xs: v > 0`, `every is ...`, `every NAME:` outside a clause,
  the top level of a template interpolation, `xs.every(...)` and `every` as
  a name keep their readings. Outside if statements, in Python-style
  conditionals, `?` conditionals and comprehension filters too, `every NAME`
  still reads `$NAME`. The rule decides no parse: a reading that the parser
  tries and drops raises nothing.
- The user accepted the compatibility break of revision 2 in advance, limited
  to the inputs it names: programs whose parse at the accepted revision
  reads `every NAME` as a class reference inside an if statement now raise
  the error. The two document cases of revision 1 that held the form are
  respelled with `any` and `all`, and the existing tests that pinned the
  form move to the new reading, as
  [Compatibility of revision 2](#compatibility-of-revision-2) lists. Any
  other change to an accepted parse, behavior, output or pinned test still
  fails backward compatibility.
- **Revision 2 outcome: Accepted** on 10-Nov-2026 under the user-requested
  basis of the automatic acceptance rule: the frozen candidate meets every
  hard criterion, with the break above and no other. The independent
  evaluator's overall decision is also Accepted. The core gate's report
  decided `rejected` only because of that break, whose two issues are the
  replays of the accepted sources of the two respelled cases. Token
  comparison was skipped as `single_proposal`, not a failed check; see
  [Revision 2](#revision-2) of the Evaluation.

## Motivation

### Universal claims (revision 1)

- World models state facts about whole classes. The specification writes
  its Socrates rule as `$Human.mortal = true` under the comment
  `# Every human is mortal`: the comment says the rule, and the code spells
  it with a sigil.
- `every` is how people and language models state a universal claim, and it
  already names the list query that quantifiers equal: NUC 62 specifies
  `all v in xs: v > 0` to equal `xs.every(v => v > 0)` in results, reads and
  dependencies. Yet `every v in xs: v > 0` is a syntax error, and NUC 62
  pins it as one.
- `$` is Nucleoid's own mark for each instance of a class, and no other
  language reads it that way. A model that writes `every Human.mortal = true`
  today gets `ReferenceError("every is not defined")`.
- A predicate over a class can only be written as an assignment of `true`:
  `$Human.mortal = true` or `$Human.mortal is true`. The `is` assignments of
  [NUC 93](nuc-0093.md) need a property after a `$Class` root, so
  `$Human is mortal` runs as three statements and raises
  `ReferenceError("is is not defined")`.
- The user requested `every` as a spelling of `all` and of `$`, and
  `every Human is mortal` as the same statement as `$Human is mortal`.

### Every in if statements (revision 2)

- The user asked: "NUC 98 Use all instead of every inside if statement, not
  allow every as well".
- [NUC 104](nuc-0104.md) gave a class condition its own words: `any` in the
  condition and `all` in the rule it guards, as in
  `if any Object.number > 4:` with `all Object.color is red`. Revision 1
  still read `if every Order.total > 100:` as the same per-instance
  conditional, so one condition had two spellings, and the one with `every`
  says a universal claim where each instance is tested on its own:
  `if every Order.total > 100:` holds for each large order, not only when
  every order is large.
- A model that writes `every` in an if statement now learns at parse time,
  before the program runs, which word to write instead, while `every` stays
  the word of claims stated outside if statements, such as
  `every Human is mortal`.

## Rationale

### Universal claims (revision 1)

- **Category and mode.** The user requested this concrete feature and the
  category Syntax enhancement, so there was no random draw. It runs in
  single-proposal mode, which skips token comparison. Runtime applicability
  does not apply. No hint was supplied.
- **The user's decisions.** Asked to choose, the user selected all three
  forms, accepted each one's compatibility break in advance, and chose
  exact, case-sensitive class names over capitalizing the name after
  `every`.
- **Every quantifiers lower to `all`.** `Quantifier::starting` now maps the
  word `every` to `Quantifier::All`, so `every v in xs: v > 0` is the node
  that `all v in xs: v > 0` builds, renders as `(all v in xs:v>0)` and is
  the same standing rule and graph key. This follows the accepted aliases
  that render canonically: `self` as `this`, `->` as `=>`, `elif` as
  `else`, `None` as `null` and NUC 86's `is` as `==`. Rejected:
  - a `Quantifier::Every` variant, because the public enum is not
    `#[non_exhaustive]`, so a variant breaks exhaustive downstream matches,
    and because `every` and `all` would then be different rules and graph
    keys for one claim;
  - a spelling flag on `Expr::Quantified`, which changes a public variant's
    fields and every pattern on it.
- **One recognition rule.** The parser, the direct-alternative lookahead
  and the REPL's colon-free header scan all ask `Quantifier::starting`, so
  they agree about where an every quantifier starts and which colon is its
  own. The prefix needs `in` after a binder name, which the accepted parser
  rejected wherever it reads an operand, as NUC 62 argued for `all`.
- **Interpolations and `parse_expression`, as NUC 62.** A template
  interpolation ignores its trailing tokens, so its top level keeps reading
  `every` as a name, as it keeps `all`, `lambda` and the nouns of NUC 75.
  `parse_expression` reads every quantifiers and every class references,
  as NUC 62 made it read quantifiers. Both choices follow NUC 62, and the
  first narrows the second break.
- **Every class references build `$NAME`.** The parser reads `every NAME`
  in `primary`, where every operand begins, and returns exactly
  `Expr::ClassRef(NAME)`. Member, call, subscript and version chains then
  follow as they follow `$NAME`, and evaluation, class-level rule
  validation, cycle checks, dependencies, `why`, `affects`, rendering and
  the protected-assertion walker need no change.
- **Recognition without state.** The reading depends only on tokens: a
  variable named `every`, a defined class or the case of `NAME` never
  changes it. Rejected:
  - requiring a capitalized name or a declared class, which the user
    declined and which would make a line's meaning depend on the state;
  - an accepted-first retry as NUC 86 uses, because juxtaposition makes
    every `every NAME` program parse at the accepted revision, so a retry
    would never reach `every Human.mortal = true`;
  - a keyword, which would break every variable, parameter, property and
    key named `every`.
- **Three kept readings.** Each keeps accepted programs working:
  - `every NAME in` is the quantifier.
  - `every is ...` is not a juxtaposition: NUC 93 reads `every is 3` as an
    assignment to a variable named `every`, and NUC 86 reads
    `(every is 3)` as a comparison. Reading `$is` there would change
    accepted programs outside the second break.
  - `every NAME:` outside a clause, where `NAME:` begins the next comma-free
    property of [NUC 44](nuc-0044.md) or a colon statement: a typed
    declaration, an `assert:` statement of [NUC 45](nuc-0045.md), `suppose:`
    or `lambda:`. `$NAME:` is never valid there, so the guard loses no new
    reading, and it keeps those programs as the accepted grammar keeps
    `lambda NAME:` (NUC 57), `stated NAME:` and `derived NAME:` (NUC 48)
    and `enum NAME: T` (NUC 90). In a header, `suppose` premise, subscript
    start, `?` consequent, Python-style condition or quantifier collection
    the colon belongs to the clause, so `while every Ready:` reads
    `while $Ready:`.
- **Other juxtapositions follow the break.** `every x => x`,
  `every x := 1` and `every all v in xs: v` juxtaposed a bare `every`
  statement with the next statement on the same line. The user accepted
  that these read `$NAME`, and they now raise the syntax errors of their
  `$NAME` spelling. Guarding them would add rules that no valid program
  needs.
- **Predicate sentences end their line statement.** The parser reads a
  sentence after an expression statement's head: a bare class reference,
  then `is`, one name and a token that ends a line statement, the tokens
  that end a destructuring declaration: a line break, `;`, a dedent, `}`,
  the end of input, `else` or `catch`. Before such a token the accepted
  grammar always read `$Class`, `is` and `WORD` as three one-token
  statements, so the sentence changes only inputs of the third break. Every
  other input keeps its accepted reading: `$Human is mortal := 1`,
  `$Human is mortal: int`, `$Human is mortal is wise`, `$Human is is wise`,
  `$Human is enum E: A, B`, and same-line juxtapositions such as
  `$Human is mortal x = 1` and `$Human is mortal $Human is wise`, whose
  first sentence does not end its line. The check is a comparison of three
  tokens, done only after a bare class reference.
- Rejected: reading a sentence wherever the accepted grammar read three
  one-token statements, also when another statement follows on the same
  line. Deciding that needs the statement at the word parsed in advance,
  and the parse after a refusal repeats it. A first draft did so, and
  review measured its parse time doubling with each level of nesting, as in
  `$H is w = function() { $H is w = function() { ... } }`. The line-end rule
  narrows the third break instead, needs no lookahead past the word, and
  keeps every way a sentence ends its own line or block. Inside parentheses,
  where line breaks are not statement ends, a sentence in a function body
  passed to a call needs a `;` or the end of the body after it.
- **The value is `true`.** The user asked that `$Human is mortal` mean what
  the comment `# Every human is mortal` means over `$Human.mortal = true`.
  The word is the property's name, not a word value: a variable named
  `mortal` does not change the property, and the value is not a
  `UnaryOp::Word`.
- **Rendering as the `=` spelling.** A sentence builds the tree of
  `$Class.WORD = true`, so it renders as that statement in graph keys,
  `--graph` output and the `rule` that `why` and `affects` report. The two
  spellings are one rule: either replaces the other. This follows
  [NUC 96](nuc-0096.md), whose `b is @a` renders as `b=a`, and NUC 93,
  whose non-word values render as `=`. Rejected: rendering
  `$Human is mortal`, which needs a marker in the tree, a new variant or
  flag, and would make the two spellings different rules.
- **Statements only.** `is` inside an expression stays NUC 86's comparison,
  so `if $Human is mortal:` compares. A sentence applies in every statement
  position of NUC 93, including inline suites, one-statement class bodies
  and the block bodies of function literals inside calls and template
  interpolations.
- **Not added: `is not` sentences.** `$Human is not mortal` keeps its
  accepted reading as `$Human`, `is` and `not mortal`. A later proposal
  could read it as `$Human.mortal = false`; it is a separate compatibility
  break that the user has not accepted.
- **Host stack.** The new parser steps live in callees, so no existing
  parser function's debug frame grows, and every nesting shape stops at the
  depth where it stopped before; see Reference Implementation.
- **Optional evidence.** Advisory usefulness is unscored (`missing_rubric`),
  not zero. Strategy learning is `not_configured`; this revision is
  unattributed, without a policy, selection receipt, trial or reward.

### Every in if statements (revision 2)

- **Category, mode and inputs.** The user requested this revision directly,
  so there was no random draw, and it keeps the category of this proposal,
  Syntax enhancement. It runs in single-proposal mode, which skips token
  comparison. Runtime applicability does not apply. No hint was supplied.
  Advisory usefulness is unscored (`missing_rubric`), not zero, and
  strategy learning is `not_configured`, so the revision is unattributed.
- **`Requires`.** NUC 104 is added: its `any` and `all` spellings of `$NAME`
  are what the error tells a program to write instead.
- **The user's decisions.** Asked to choose, the user chose:
  - the whole if statement as the scope: the condition and the bodies of
    `if`, `elif` and `else` in every spelling, with everything lexically
    inside them, while `while`, `for`, `suppose`, `try`, function and class
    bodies outside if statements, Python-style conditionals, `?`
    conditionals and comprehension filters keep `every`;
  - the `$` spellings only: the class reference `every NAME` and the
    predicate sentences whose subject it spells, while the quantifier and
    every other reading of the word stay;
  - a parse-time `SyntaxError("Use all instead of every inside if")` at the
    `every`, over a runtime error;
  - the compatibility break in advance, exactly as
    [Compatibility of revision 2](#compatibility-of-revision-2) lists it.
- **One rule on top of revision 1's.** Recognition stays NUC 98's and
  NUC 104's: `starts_spelled_class` decides, by the same three tokens,
  whether `every NAME` is a class reference, so the quantifier priority,
  the `is` and colon guards and the interpolation guard are unchanged. The
  parser counts the if statements it is inside, and where `spelled_class`
  reads the word `every` with that count above zero, it notes the position
  of the first such `every` and still builds `Expr::ClassRef`.
- **Checked on the reading the parser keeps.** The note decides no parse.
  When the parse that the accepted grammar keeps holds a note, the parse
  fails with the error at that position; otherwise nothing changes. A
  tentative reading keeps its own note and hands it on only when it is
  kept: a Python-style condition, a `while` header, a `suppose` premise and
  a destructuring value, whose cached outcomes carry their note, and the
  parse passes of NUC 86, NUC 92 and NUC 102, each of which starts with no
  note. So every decision the accepted grammar makes stays, and a program
  that fails to parse keeps its accepted error.
- **Rejected: raising the error where the form is read.** That was the
  first draft, and the differential of
  [Preparation checks of revision 2](#preparation-checks-of-revision-2)
  found it changing programs outside the break:
  - `r = 1 if every Human is mortal else 2`: the first parse pass, without
    `is` comparisons, reads `if every Human ...` as an if statement and
    fails, and the next pass reads the Python-style conditional, which is
    outside any if statement. Raising in the first pass rejected an
    accepted program. The ARC rule `$Obj.fill_color is 5 if $Obj.parts.distinct().length is 1 else 0`,
    spelled with `every`, is such a program;
  - `while every lambda: 1` inside an if body: the tentative `while` header
    reads `every lambda` as a class reference in its clause and is
    dropped, and the accepted reading is `while`, `every` and `lambda: 1`.
- **Rejected: letting tentative readings swallow the error.** The fallback
  reading then reports another error: inside an if body
  `x = (1 if every Order.ok else 2)` would fail with
  `SyntaxError("Expected ')' but found keyword 'if'")`.
- **Rejected: reporting the form in programs that fail anyway.** A failing
  pass's note could replace its error, so that
  `if every Order.total > 1:` with a later syntax error reports the
  `every` first. The differential found that it also reports the form in
  malformed Python-style conditionals, such as
  `r = 1 if every x = 1 else 2`, whose failed reading has an if statement
  the program does not hold, and that it changes 1,508 errors. Failing
  programs keep their accepted errors instead.
- **Sub-parsers.** A template interpolation's parser inherits the count, so
  `` `${(every Order)}` `` inside an if statement is the form, and hands its
  note to the enclosing reading with the position mapped into the source as
  its diagnostics are. The `accepted` probe parsers of `while` and
  `suppose` headers (NUC 93) inherit the count too, as NUC 102 requires of
  every probe; their notes are dropped with them, so their decisions are
  unchanged.
- **`parse_expression`.** It parses no if statement around its input, so
  `parse_expression("every Human")` still returns `$Human`. An expression
  whose function literal holds an if statement with the form returns the
  error.
- **No REPL or terminal change.** The REPL's colon-free header scan and the
  terminal's indentation are lexical and unchanged:
  `if every Order.total > 100` waits for its indented body as before, and
  the submitted statement reports the error.
- **No tree marker.** The rule needs no new token, variant or flag: the
  class reference is the same node, and only its position inside an if
  statement matters.
- **Host stack.** The count, the note and the hand-offs add a few words to
  the parser and to three cached outcomes. Every nesting shape stops at the
  depth where it stopped before; see
  [Measured cost of revision 2](#measured-cost-of-revision-2).

## Specification

- The normative contract is
  [Every quantifiers, class references and predicate sentences](../nucleoid.spec.md#every-quantifiers-class-references-and-predicate-sentences).

### Every quantifiers

- `every NAME in COLLECTION: CONDITION` starts where the name `every`, a
  binder name and the keyword `in` follow each other, wherever
  `all NAME in` starts a quantifier. It builds the quantifier node with
  `Quantifier::All`, so it is `all NAME in COLLECTION: CONDITION` in every
  respect: members, order, truthiness, short-circuiting, dependencies, null
  settling, class-level validation, cycles, reasoning observers, rollback,
  diagnostics and the rendering `(all NAME in COLLECTION:CONDITION)`.
- Statement headers take it: `if`, `else if`, `elif if`, the colon-free `if`
  of NUC 49, the direct alternatives `else CONDITION` and `elif CONDITION`
  of NUC 43 and `while`. The direct-alternative lookahead and the REPL's
  colon-free header scan pair its colon with its `every`.
- At the top level of a template interpolation it is not recognized, so
  `` `${every v in xs: v}` `` reads the variable `every`; inside
  parentheses, brackets, braces or arguments it is.

### Every class references

- Where an operand begins, outside the top level of a template
  interpolation, the name `every` followed by a name token `NAME` builds
  `Expr::ClassRef(NAME)`, the tree of `$NAME`. A block comment may stand
  between them; outside parentheses and brackets a line break separates
  them, and they keep their accepted reading. Since revision 2, a parse
  that holds such a class reference inside an if statement fails, as the
  revision 2 part of this [Specification](#specification) states.
- It does not apply, and `every` keeps its accepted reading, when:
  - `in` follows `NAME`, which is an every quantifier;
  - `NAME` is `is`;
  - `:` follows `NAME` outside a clause. The clauses are statement headers,
    `suppose` premises, subscript starts, the consequent after `?`,
    Python-style conditions and quantifier collections.
- Everything else about `every` is unchanged: `every` followed by anything
  but a name, `every` after `.` as a property or method, and `every` as a
  declared name, parameter, key, label, loop name, binder or class name.

```
class Order(total):
    this.total = total
every Order.big = every Order.total > 10
if any Order.total > 100:
    all Order.vip = true
small = Order(5)
large = Order(200)
assert([small.big, large.big], [false, true])
assert([small.vip, large.vip], [null, true])
```

### Predicate sentences

- In every statement position of NUC 93, a statement is a predicate
  sentence when all of these hold:
  - its leading expression is exactly a class reference, written `$Class`
    or, outside if statements since revision 2, `every Class`, and
    possibly grouped in parentheses;
  - the next two tokens are the identifier `is` and a name token `WORD`;
  - the token after `WORD` ends a line statement: a line break, `;`, a
    dedent, `}`, the end of input, `else` or `catch`. The accepted grammar
    then always read `$Class`, `is` and `WORD` as three one-token
    statements.
- Inside parentheses and brackets the lexer emits no line breaks, so a
  sentence in a function literal's body inside a call ends with `;` or the
  body's `}`.
- It builds `Stmt::Assign` with the target `Expr::Member` of the class
  reference and `WORD`, and the value `Expr::Bool(true)`: the tree of
  `$Class.WORD = true`.
- Every other statement keeps its accepted reading, among them
  `$Order is 5`, `$Human is true`, `$Human is "mortal"`,
  `$Human is (mortal)`, `$Human is not mortal`, `$Human is mortal and wise`,
  `$Human is mortal.x`, `$Human is mortal = 1`, `$Human is mortal := 1`,
  `$Human is mortal: int`, `$Human is mortal is wise`, `$Human is is wise`,
  `$Human is suppose:` with a body, `$Human is mortal x = 1`,
  `$Human.kind is mortal`, `$Human@first is mortal`, `this is mortal` and
  `socrates is mortal`. In `$Human is mortal $Human is wise` only the second
  sentence ends its line, so only it states a predicate.

```
class Human(name: str):
    this.name = name
plato = Human("Plato")
every Human is mortal
socrates = Human("Socrates")
assert([plato.mortal, socrates.mortal], [true, true])
$Human is wise
assert(socrates.wise, true)
assert((why socrates.mortal)[0].rule, "$Human.mortal = true")
```

### Rendering

| Statement | Rendering |
| --- | --- |
| `ok = every v in xs: v > 0` | `ok=(all v in xs:v>0)` |
| `every Human.mortal = true` | `$Human.mortal=true` |
| `if any Order.total > 10:` with `all Order.big = true` | the rendering of `if $Order.total > 10:` with `$Order.big = true` |
| `$Human is mortal` | `$Human.mortal=true` |
| `every Human is mortal` | `$Human.mortal=true` |
| `{ $Human is mortal }` | the block key of `{ $Human.mortal = true }` |

### Compatibility of revision 1

- These inputs change, each under a break the user accepted in advance:
  - **Every quantifiers.** At the accepted revision `every NAME in` where
    an operand begins is always a syntax error outside the top level of a
    template interpolation. Such inputs now parse as `all`, or report the
    diagnostics of `all`, as Errors lists. `parse_expression` returns the
    quantifier for `every x in xs: x`, where it returned the name `every`.
    The REPL buffers a colon-free `if every v in xs: v > 0` until its
    indented body, where it submitted the line and reported
    `SyntaxError("Expected ':' but found identifier 'v'")`.
  - **Every class references.** `every NAME` where an operand begins, apart
    from the kept readings, read `every` as a complete operand followed by
    a statement or item that begins with `NAME`. It now reads `$NAME`. So
    `every Human = 4` after `every = 3` assigned `Human` and now raises
    `SyntaxError("Cannot assign to $Human")` at its statement, `r = every x`
