## Abstract

- Add only static `Math.smoothstep(lower, upper, value)` through the existing
  Math call path.
- Normalize the numeric value between the supplied bounds, apply the accepted
  maximum-then-minimum unit clamp, then evaluate the ordered cubic.
- Preserve accepted syntax, intrinsic conversion, once-only argument
  evaluation, deferred reads and reactive transactions.
- Accepted after independent per-case lexer evaluation and compatibility checks.

## Motivation

- Live transitions often need a cubic easing relationship rather than linear
  interpolation or a hard unit clamp alone.
- Name that relationship while retaining all three live inputs and the
  accepted arithmetic composition's edge behavior.
- Keep independent normalization controls and assertions when demonstrating
  the new intrinsic, rather than removing evidence to shorten examples.

## Rationale

- Use conventional lower/upper/value argument order, deliberately unlike
  `Math.clamp(value, lower, upper)`.
- Reuse the existing private numeric clamp and its unchanged extremum folds.
- Use separate ordered operations so rounding, overflow, nonfinite values,
  subnormals and signed zeros match accepted composition.
- Reject host `f64::clamp`, `powf`, fused operations, reordered polynomials,
  endpoint shortcuts and post-polynomial clamping.
- Do not import a GLSL undefined-range convention or introduce range validation
  for equal or reversed bounds.
- Specify expected NaNs by classification and other numeric bits by parity
  with host accepted controls, not an invented portable zero-sign guarantee.
- Convert intrinsically; shadowable `Number` or `Math.saturate` calls would
  introduce lookup, effects or dependencies not belonging to this operation.
- Treat omissions as numeric NaN under the accepted fixed-arity convention.
- Keep extras in evaluation and the supplied-undefined gate, not conversion.
- Depend only on accepted behavior; do not combine unrelated pending proposals.
- Leave first-class Math methods, closure capture, public representations,
  versions, MSRV, dependencies and resource limits unchanged.

## Specification

### Static numeric contract

- The authoritative [Reactive cubic smoothstep section](../nucleoid.spec.md#reactive-cubic-smoothstep)
  specifies this accepted behavior and takes precedence over this proposal.
- An unshadowed static call has signature `Math.smoothstep(lower, upper, value)`.
- Evaluate all supplied argument expressions through the unchanged call path
  before the existing Math gate.
- If any supplied value is `Undefined`, including an extra, return `Undefined`
  before numeric conversion.
- Convert the first three supplied values with `Value::to_number`, in lower,
  upper, value order; the dispatcher already intrinsically converts lower.
- Supply numeric NaN for each omitted input; omission is not supplied Undefined.
- Numbers retain their values, literal null converts to zero, booleans to
  zero/one, trimmed strings and empty/singleton lists retain their numeric
  conversion, and dates contribute milliseconds.
- Other nonnumeric values yield numeric NaN, not a new TypeError.
- Compute `numerator = value - lower`.
- Compute `denominator = upper - lower`.
- Compute `normalize = numerator / denominator`.
- Compute `t = numeric_clamp(normalize, 0.0, 1.0)`, using the existing maximum
  fold first and minimum fold second.
- Compute `square = t * t`.
- Compute `scaled = 2.0 * t`.
- Compute `falloff = 3.0 - scaled`.
- Return numeric `square * falloff`.
- Each operation is separate ordinary `f64` arithmetic in exactly that order.
- Do not skip coercion, validate/reorder bounds, shortcut endpoints, use
  `powf`/`mul_add`/`f64::clamp`, reorder the polynomial or clamp its result.
- Equal/reversed bounds, NaNs, infinities, overflow, subnormals and signed
  zeros follow this exact composition.
- Equal finite bounds with the same value yield numeric NaN; a lower/higher
  value first normalizes to negative/positive infinity.
- Overflow or infinite subtraction can produce NaN even at an endpoint.
- Expected NaNs compare by classification; every non-NaN numeric result,
  including zero, matches the accepted host composition's bits.
- Numerically ignore extra supplied values without converting them.

### Evaluation and compatibility

- Every supplied expression runs exactly once, left to right, including extras.
- Preserve all reads, effects and dependency edges through the existing path.
- A dependent assignment retains live-null/deferred behavior and recovers when
  a missing property becomes defined.
- Literal-null numeric conversion does not replace live assignment or parameter
  handling.
- Strict unknown identifiers throw even in extras or after an undefined property.
- Preserve error positions, caught values, rollback and later recovery.
- Keep state/local Math shadowing and ordinary receiver `.Math` members unchanged.
- A `Math.smoothstep` method read is unsupported/Undefined like other static
  Math method reads; it is not a first-class alias.
- Neither resolve nor track shadowable `Number` or `Math.saturate`.
- Do not recursively invoke public Math dispatch.
- Wrappers, methods, initializers, class rules, property deletion and reactivity
  use the existing call, scope, graph and transaction machinery.
- All other Math functions, constants and errors retain their exact behavior.
- Preserve every accepted syntax form and its parsing/runtime semantics.
- Add no types, public Global/Value/AST/API variants, grammar, lexer, parser,
  generator, CLI, scope, graph, evaluation or resource-limit changes.
- Do not repair inherited noncapture or parameter-dependent-local failures or
  claim broader Windows debug stack safety.
- The new call intentionally reads lower/upper/value directly, while an
  emulated result reads its unit-control node; immediate graph shapes need not
  match, but asserted controls, values and transitive behavior must.
