```

Category: Runtime features
Created: 01-Nov-2026
Requires: 8, 31, 45, 51, 57, 60, 61, 65, 68
```

## Abstract

- Adds loops over an object's entries: `for KEY, VALUE of SOURCE:` and its
  `in` spelling `for KEY, VALUE in SOURCE:`, with every suite the
  single-name loop accepts.
- The body runs once for each entry the object holds, in insertion order,
  with `KEY` bound to the entry's key and `VALUE` to its value. An instance
  lists its `id` first, then its fields in the order they were stored.
- `SOURCE` is evaluated once, before the names are bound, and the entries,
  keys and values, are snapshotted before the first body runs. The loop is
  one-shot and imperative, exactly like the single-name loop: the same
  scopes, receivers, returns, rollback and propagation. Taking the snapshot
  records no dependency of its own.
- Every source that is not an object raises
  `TypeError("<source> is not an object")`. Single-name loops are unchanged,
  including `TypeError("<name> is not iterable")` for objects.
- Rolling back restores the order of every object's entries. Undoing a
  deletion puts the property back at the position it held, and undoing an
  addition removes it, so a caught failure in `try`, a failed top-level
  statement, the end of a `suppose` block and every other rollback leave
  each object's entries exactly as they were, in the same order.
- This revises [NUC 70](nuc-0070.md), whose loop design it keeps and whose
  rejection it answers: NUC 70's rollback put a restored property at the end
  of its object, which its entry loops exposed.
- No keyword, token or error type is added. The public `Stmt` enum gains the
  variant `Stmt::ForEntries { key, value, iterable, body }` and the public
  `nuc::r#for::For` struct the field `value: Option<String>`; both need human
  SemVer review. The rollback change adds no public API. No project version
  is changed.

## Motivation

- A world model keeps records: a price table, the stock of each item, the
  sales of each region, the fields of an instance. Acting on every entry of
  one, by seeding instances from a table, totalling it, copying an instance
  into facts or checking every field, needs each key together with its
  value.
- Accepted Nucleoid cannot iterate an object's entries. A single-name loop
  raises `TypeError("rec is not iterable")` for an object, `Object.keys`,
  `Object.entries` and `JSON` are not defined, `"a" in rec` raises
  `SyntaxError("Unexpected keyword 'in'")`, and `rec.keys()` is undefined.
  `rec[k]` reads a computed key, but `rec[k] = 5` raises
  `SyntaxError("Cannot assign to rec[k]")`, so every key of every object
  comes from the program's text.
- The accepted spellings therefore name every key by hand, for example
  `"rice oil salt".split(" ").map(name -> Item(shelf, name, table[name]))`,
  and they break down exactly where a world model needs to be general:
  - a lambda sees neither the enclosing function's parameters nor `this`:
    `def f(r) => ["a"].map(k -> r[k])` raises
    `ReferenceError("r is not defined")`, so functions and methods first copy
    them with `cur := r` and `me := this`;
  - a function that receives different tables needs a key list for each
    call, a dispatch on the table's contents, or a key list it switches after
    each call when the calls sit in one assertion;
  - an `if` statement inside a block-arrow callback is filed as a standing
    conditional, so when a later call reassigns the capture its condition
    read, it runs again with its parameter unbound and raises
    `ReferenceError("item is not defined")`, unless the condition reads
    through `.value`;
  - inside a standing `if`, a key-list loop reads every entry, so changing
    any of them runs the branch's actions again unless each read is wrapped
    in `.value`;
  - deleting a property and assigning it again moves it to the end of the
    object, and a hand-written key list does not follow.
- The graph reflection channel `model |> why` lists the property
  declarations the graph holds, not the entries an object holds. It misses
  the entries of object literals, every instance's `id` and properties
  written inside loops, branches and blocks, and it follows graph order.
- Python's `for key, value in record.items():`, JavaScript's
  `for (const [key, value] of Object.entries(record))`, Go's
  `for key, value := range record` and Kotlin's
  `for ((key, value) in record)` all name both parts of each entry, and LLMs
  write them constantly. In accepted Nucleoid each raises a syntax error;
  `for key, value of record:` raises
  `SyntaxError("Expected 'of' in for statement")` at the comma.
- A transaction promises to leave the state exactly as it was, and NUC 65
  promises that `suppose` discards everything it did. Once entry loops can
  see the order of an object's entries, that order is part of the state, so
  rollback has to restore it. NUC 70 was rejected because it did not: after
  `o = {a: 1, b: 2, c: 3}`, a `try` that deleted `o.a` and failed left a loop
  visiting `b`, `c`, `a`.
- Each of the eleven new cases uses 21 to 33 fewer lexer tokens than the
  most compact behavior-equivalent accepted program found for it.

## Rationale

- **Category and applicability.** The caller selected Runtime features by one
  uniform draw over the four eligible registry categories, index 1 with
  probability 1/4 and no redraw, in continuous mode. Runtime applicability
  is `existing_comparable`: `for` loops and rollback exist, and because every
  key comes from the program's text, every case can be written in accepted
  syntax with hand-written key lists. NUC 70's evaluation verified that
  computed writes such as `rec[k] = 5`, `rec["b"] = 2` and `this[k] = 1`
  fail with "Cannot assign to ...", that `{[k]: 1}` and `{...a}` do not
  parse, and that `Object` and `JSON` are undefined. The token
  non-regression gate therefore applies, and each new case is paired with
  the most compact accepted counterpart found, recorded in the evaluation
  baseline.
- **Relationship to NUC 70.** [NUC 70](nuc-0070.md), Object Entry Loops, is
  this revision's rejected predecessor and stays Rejected; this NUC does not
  replace or reopen it. Its decisive finding was that a rolled-back deletion
  re-inserted the property at the end of its object. This revision answers
  it:
  - rollback restores entry order, as Rollback order specifies, for every
    path its evaluation reproduced: a caught failure in `try`, a `suppose`
    block, a restored instance field and a failed top-level statement;
  - the specification entries
    `Nucleoid restores object entries in place when it rolls back`,
    `Nucleoid restores object entries at nested savepoints` and
    `Nucleoid loops over the entries an instance holds` assert the order after
    rollback, and each fails on NUC 70's runtime;
  - a randomized model test compares the order after every rollback with an
    ordered model.
- NUC 70's evaluation also recorded four documentation inaccuracies, which
  this text corrects:
  - the Compatibility tables state the result of each exact source both
    without and with a final newline where they differ, including the two
    `x = )` rows and the comment-only body;
  - margins are reported against the most compact counterpart found by a
    search that includes the spellings its evaluation used, with every other
    measured spelling listed;
  - the snapshot case now holds four bills, so even its data-copied spelling,
    which its evaluation measured at 140 tokens against 142, is longer than
    the candidate: 156 against 148;
  - Contexts states that a class-level block whose loop source reads
    `$Class` fails when declared, as single-name loops already do.
- **NUC 70's loop, unchanged.** The header, sources, entries, snapshot,
  iteration, dependencies, rendering and syntax-tree shape below are NUC 70's
  design, which its evaluation found sound apart from rollback order. Its
  rationale carries over and is summarized here.
- **Two names after `for`.** A header is a two-name header exactly when `for`
  is followed by a name, a comma, a name and `of` or `in`. Nothing else
  commits to the new form, so every other input keeps its accepted parse and
  diagnostic, including `for values, other:` and `for t := "ab": pass`.
  Rejected: parenthesized or bracketed patterns such as `for (key, value) of`
  and `for [key, value] of`, which read as destructuring, rejected in
  [NUC 67](nuc-0067.md), and collide with parenthesized sources.
- **Objects only.** Only objects have entries. Every other source raises
  `TypeError("<source> is not an object")`, rendering the source as the
  single-name loop renders it in `is not iterable`. Rejected: index and item
  pairs for lists, a separate feature that would also have to settle the
  single-name loop's rule of visiting only registered instances in a list.
- **Entries as the object holds them.** The loop lists exactly the entries
  that `--json` and deep equality see, in the object's insertion order, with
  an instance's `id` first. Rejected: sorted keys, which would lose the order
  the world model built.
- **A full snapshot.** All entries, keys and values, are captured before the
  first body runs, as the string loop captures every character and the class
  loop every instance. Rejected: reading each value when its iteration
  starts, and Python's error for a record that changes size, which no
  accepted loop raises.
- **No dependency of its own.** Taking the snapshot reads the entries
  directly, as the class, list and string snapshots read theirs. A loop is an
  action; tracking each entry would make a standing branch take its actions
  again whenever any value of its record changed, the trap
  [NUC 66](nuc-0066.md) describes for actions written as laws.
- **A syntax-tree variant and a node field.** A two-name loop parses to the
  new variant `Stmt::ForEntries`, and a single-name loop keeps `Stmt::For`
  exactly as it was, so every accepted program keeps a byte-identical syntax
  tree and `Debug` text, which the historical regression seals in
  `tests/flat_map.rs`, `tests/math_remap.rs` and `tests/replace_all.rs` hash.
  Both kinds run through the existing `For` node, which gains
  `value: Option<String>`, so the loop machinery is shared. Rejected: an
  optional field on `Stmt::For`, which changes the `Debug` text of every
  historical loop and fails those seals.
- **Ordered rollback.** The undo log keeps exactly what reverses each
  structural change of a property map: a removed key with the position it
  held and the value it had, and a key that did not exist before. Both are
  recorded whenever they happen, while an overwrite in place keeps the
  accepted rule of recording only the first write to a slot. Rollback undoes
  the log in reverse, so every key sequence is rebuilt step by step: a
  removed key is inserted back at its recorded position and an added key is
  removed.
- Rejected: recording a position only with the first write to a slot and
  re-inserting there. The first-write rule drops later writes, and a later
  deletion of the same key then goes unrecorded, so the positions recorded
  for other keys no longer match the object they are restored into. After
  `o = {x: 1, k: 2, y: 3}`, a rolled-back `try` running `o.x = 5`,
  `delete o.k` and `delete o.x` restores `x`, `y`, `k`. A prototype of that
  variant fixed every reproducer of NUC 70's evaluation yet failed this
  case, the case
  `Nucleoid restores object entries in place when it rolls back`, which runs
  the interleaving, and 9 of the model test's 300 programs, starting with
  the first.
- Rejected: copying an object's whole property map at its first write in each
  transaction or savepoint. It restores order, but a loop over a large
  object's entries whose body opens a `try` and changes the object copies
  the whole map on every iteration, quadratic in the size of the object.
- Rejected: restoring the order of graph nodes and dependency edges too. Their
  rollback order is observable through `model |> why` today, so changing it
  would change accepted behavior; this NUC leaves it as accepted.
- **Not added.** Index and item pairs over lists, strings or classes,
  `Object.keys`, `Object.values`, `Object.entries`, computed property
  writes, destructuring patterns, three or more names, colon-free, implicit
  or parenthesized two-name forms, sorted iteration and standing loops.

### Counterparts

- Every new case is paired with the most compact behavior-equivalent
  accepted program found: the same canonical assertions in the same order

  assertion running.

  measured include:

    `ks := ks == "milk eggs" ? "wine cider" : "milk eggs"`, and dispatch on

## Specification

### Syntax

- `for_statement` gains the two-name header:
  `"for" NAME "," NAME ("of" | "in") expression ":" suite`.
- A header is a two-name header exactly when the tokens after `for` are an
  ordinary identifier, a comma, an ordinary identifier and the keyword `of`
  or `in`. Otherwise the accepted single-name, implicit and explicit paths
  run unchanged.
- `expression` is parsed as the single-name loop's source, and `suite` is
  any suite that loop accepts: an indented block, statements on the same
  line separated by `;`, or a braced block after the colon. There is no
  colon-free, implicit, parenthesized or three-name form.
- The statement is `Stmt::ForEntries { key: KEY, value: VALUE, iterable,
  body }`; single-name loops remain `Stmt::For { variable, iterable, body }`.

### Sources and errors

- `SOURCE` is evaluated once, before `KEY` and `VALUE` are bound, so
  `for key, value of {key: key}:` reads the outer `key`.
- An object value has entries: an object literal, `Object()`, an instance,
  the step objects `why` and the reasoning stages return, a `suppose` block's
  escaped copy, and every other object.
- Every other value raises `TypeError("<source> is not an object")`, where
  `<source>` is the source expression in canonical form: a list, a class, a
  string, a number, a boolean, `null`, an undefined property, a function, a
  date and a regular expression. After `xs = [1, 2]`,
  `for key, value of xs: pass` raises `TypeError("xs is not an object")`,
  and `for key, value of [1, 2]: pass` raises
  `TypeError("[1,2] is not an object")`.
- An undefined name raises `ReferenceError("<name> is not defined")`, as
  before. Both errors are positioned at the running top-level statement and
  roll back its transaction.

### Entries

- The loop visits the object's own entries in insertion order. An object
  literal holds its keys as written; a property assigned later is appended
  when it is first assigned; a deleted property is removed; a property
  deleted and assigned again is appended again.
- An instance holds `id` first, then the properties its constructor
  assigns, the properties its class-level rules derive and the properties
  assigned later, in the order each was first stored.
- An entry whose value is `null` is visited. A slot whose value is undefined
  is not an entry; only object literals hold such slots, such as `a` in
  `{a: none.x}` when `none.x` was never set. An empty object runs no body.
- The visited keys are exactly the keys of the object's JSON serialization,
  and of the deep equality `assert` uses.

```
class Room(name, width, depth):
    this.name = name
    this.width = width
    this.depth = depth
$Room.area = $Room.width * $Room.depth
lab = Room("lab", 3, 4)
lab.width = 5
delete lab.name
lab.name = "studio"
fields = []
for field, value of lab: fields.push(field + "=" + value)
assert: fields, ["id=lab", "width=5", "depth=4", "area=20", "name=studio"]
```

### Snapshot

- Every entry, key and value, is captured before the first body runs.
- Entries the body adds are not visited. Entries it deletes are still
  visited with their snapshotted values. An entry whose value it changes is
  still bound to the snapshotted value; `SOURCE[KEY]` reads the current one.
  A value that is an object is the same object, so changes made through it
  are visible.
- A later loop, or a later run of the same loop, takes a fresh snapshot.

```
bills = {rent: 900, food: 300, travel: 200, gym: 50}
seen = []
for bill, amount of bills:
    seen.push(bill + ":" + amount + ":" + (bills[bill] ?? "gone"))
    bills.food = 0
    delete bills.travel
    bills.fee = (bills.fee ?? 0) + 5
assert: seen, ["rent:900:900", "food:300:0", "travel:200:gone", "gym:50:50"]
```

### Iteration

- Each iteration pushes a scope, declares `KEY` as the entry's key, a
  string, and `VALUE` as its value, enters imperative mode, runs the body,
  and restores the mode and scope on completion, return or error.
- The names shadow outer names and are restored afterwards; assigning them
  in the body changes only the current iteration. When `KEY` and `VALUE` are
  the same name, the value is bound.
- An explicit or bare `return` leaves the loop and the enclosing function,
  method or block, or ends a top-level program, as from a single-name loop.
  A normally completed or empty loop yields `null`.
- Errors and thrown values in the source or the body roll back through the
  existing transaction; a caught failure restores the state from before the
  enclosing `try` body, including the order of every object's entries.

### Dependencies

- Taking the snapshot records no dependency of its own, as the class, list
  and string snapshots do. Evaluating `SOURCE` records its reads as usual,
  and so do the body's statements.
- A loop in a standing `if` branch, a block or a function called by a
  declaration runs whenever that branch, block or function runs. Replacing
  the binding `SOURCE` reads, such as `lights = {shed: 30}`, runs it again;
  changing or adding an entry, such as `lights.desk = 100`, does not.
- A body that reads `SOURCE[KEY]` depends on each entry it reads, as any
  property read does.

### Contexts

- **Functions and methods.** The loop sees parameters, locals and `this`, as
  a single-name loop does.
- **Constructors.** A constructor can loop over a record argument, for
  example to create parts and count them.
- **Class-level rules.** Inside a class-level `if` or block, the loop runs
  for each instance, and `$Class` in its body is that instance. A source
  such as `$Box.parts` that reads `$Class` fails when the block is declared,
  with `TypeError("$Box.parts is not an object")`, as the single-name loop
  fails with `TypeError("$Box.parts is not iterable")`.
- **`suppose` suites.** The loop runs in the hypothetical world, and its
  effects are discarded with the block.
- **`try` bodies and nesting.** Loops nest, and an inner source may be an
  outer value.

### Rollback order

- An object's entries, and their order, are part of the state rollback
  restores. When a transaction or a savepoint rolls back, through a caught
  failure in `try`, a failed top-level statement, the end of a `suppose`
  block or an error inside one, every object holds exactly the entries it
  held when the rolled-back work began, with the same values in the same
  order.
- A property the rolled-back work deleted returns at the position it held. A
  property it added is removed. A property it overwrote keeps its position
  and regains its value. A property it deleted and assigned again, any
  number of times, returns to its original position with its original value.
- This holds for object literals, instances, whose `id` comes back first,
  properties that class-level rules added, objects a rolled-back statement
  replaced or deleted, and at every nested savepoint: an inner `try` or
  `suppose` restores the order its own work changed, and an enclosing
  rollback restores the rest.
- Work that is not rolled back keeps the order rules of Entries.
- Rollback keeps its accepted behavior for everything else it restores:
  variable, object, class, function and state-version values, and the order
  of graph nodes and dependency edges, which `model |> why` reflects.

```
basket = {tea: 4, jam: 3, oats: 2}
try:
    basket.tea = 9
    delete basket.jam
    delete basket.tea
    basket.tea = 6
    throw "DECLINED"
catch error:
    pass
held = []
for item, qty of basket: held.push(item + qty)
assert: held, ["tea4", "jam3", "oats2"]
plan = suppose:
    delete basket.jam
    basket.rye = 5
    seen = []
    for item, qty of basket: seen.push(item)
    seen
assert: plan, ["tea", "oats", "rye"]
assert: basket.jam, 3
```

- The specification entry
  `Nucleoid restores object entries in place when it rolls back` runs the
  same edits inside a failing loop and checks the order its later loops
  see.

### Rendering, REPL and terminal

- Graph and block keys render the header as `for KEY,VALUE of SOURCE`,
  without the body, as they render `for NAME of SOURCE`; `in` renders as
  `of`. A block holding the loop is keyed `block(for KEY,VALUE of SOURCE)`.
- Default-bearing declarations render the suite form
  `for KEY,VALUE of SOURCE:` with its indented body, which parses back to the
  same statement.
- The native REPL buffers a header ending in `:` until a blank line and runs
  an inline loop at once, as before. Completion already offers `for`, `of`
  and `in`. Neither changes.

  its parse, positions, diagnostics and behavior: a two-name header was
  always `SyntaxError("Expected 'of' in for statement")`.
- Property order had no observable channel before this NUC: deep equality
  ignores order, JSON output sorts keys, and the graph reflection channel
  follows graph order. Restoring it on rollback changes no accepted program.

## Reference Implementation

- Implemented in the isolated candidate against accepted revision
  `a0fcd88363d385ba2dfd136d6bd69bd626116247`. The loop is NUC 70's prototype,
  rebased unchanged: none of its files had changed since NUC 70's base. The
  rollback change and the eleven cases were prototyped outside the candidate
  before any candidate edit, and the counterparts were recorded in the
  evaluation baseline before it.
- `src/lang/ast/mod.rs`, `src/lang/ast/parser.rs`,
  `src/lang/ast/generator.rs`, `src/nuc/for.rs` and `src/nuc/mod.rs`: the
  `Stmt::ForEntries` variant, the lookahead `entry_names` qualifier, the
  renderings, the `For::value` field with its typed entry snapshot, and the
  conversion, as in NUC 70.
- `src/transaction.rs`: the private undo entry `PropertyRemoved { object,
  property, index, before }`, and crate-private `record_property_added` and
  `record_property_removed`, which log every new key and every removal
  regardless of the first-write rule and mark the slot as recorded.
  `record_property` keeps logging the first overwrite of a slot.
- `src/state.rs`: `assign_property` logs a new key through
  `record_property_added`; `remove_property` removes with
  `shift_remove_full` and logs the position and value it removed; the new
  `restore_removed_property` inserts the property with
  `IndexMap::insert_full` and moves it with `IndexMap::move_index` to the
  recorded position, clamped to the map's bounds. It does not use
  `IndexMap::shift_insert`, which exists only from indexmap 2.2.3, while the
  manifest accepts any indexmap 2.x release. Only the first of two
  whole-object replacements of the same object in one transaction is logged,
  so positions recorded between them are undone against the second map
  before the logged image restores the first; the clamp keeps those
  intermediate moves inside the map.
- Whole-object writes keep their accepted records: `insert_object` and
  `remove_object` log the whole object, which already restores its entries
  in order.
- Every structural change of a property map is logged and undone in reverse
  order, so the key sequence is rebuilt exactly; overwrites in place do not
  move keys, so their first-write records suffice.
- Cost: one undo entry for each key removal or new key, where the log already
  keeps a state-version entry for every changed write. Restoring a removal
  shifts the keys after it, as the forward `shift_remove` did. Deleting every
  key of an 8,000-key object front to back inside a rolled-back `try` takes
  about 0.31 seconds against the accepted 0.23 seconds in a release build,
  both quadratic through the forward deletions; back to front, both take
  about 0.06 seconds.
- `tests/object_entry_loops.rs` holds 20 tests: the appended document cases
  and their 38 assertions, that no earlier document case uses the form, the
  syntax tree of every suite form, insertion order with additions, deletions,
  re-additions, `null` values, undefined slots, `Object()` and `why` steps,
  instances and their JSON keys, constructors, the snapshot and once-only
  source evaluation, every other source's exact error and position,
  class-level sources, unchanged single-name errors, every near miss and
  every changed diagnostic with exact positions, rendering and round trips,
  block keys, functions, methods, class-level rules, returns, `suppose`,
  `try` and rollback, shadowing and duplicate names, dependencies in standing
  branches and blocks, protected assertions inside two-name bodies, a
  20,000-entry loop that evaluates its source once, and the native REPL.
- `tests/ordered_rollback.rs` holds 12 tests:
  - a randomized model test over 300 seeded programs, each three to eight
    runs of random writes, deletions and re-additions on an object literal and
    an instance, nested in `try` and `suppose` up to three deep, with a third
    of the runs failing at the top level, built by an inline SplitMix64
    generator without a new dependency. After every run it compares each
    object's entries with an ordered model, and at the end the entries an
    entry loop reports;
  - deterministic cases for every audited path: rolled-back additions and
    overwrites, deletions and re-additions, the overwrite-then-deletions
    interleaving, nested `try` and `suppose` savepoints and their escaped
