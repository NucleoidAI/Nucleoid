# NUC 92 -- List Comprehensions

```

Title: List Comprehensions
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Language compatibility
Created: 08-Nov-2026
Requires: 8, 59
```

## Abstract

- A list may be built as Python builds one: `[price * 2 for price in prices]`
  maps each item, and one `if` clause filters them first, as in
  `[price * 2 for price in prices if price > limit]`. `for price of prices`
  is an equal spelling, as in Nucleoid's `for` statement.
- A comprehension is exactly its arrow spelling. `[EXPR for NAME in SOURCE]`
  builds the syntax tree of `SOURCE.map(NAME => EXPR)`, and
  `[EXPR for NAME in SOURCE if COND]` the tree of
  `SOURCE.filter(NAME => COND).map(NAME => EXPR)`. Evaluation, errors, graph
  keys, liveness, `why`, `affects`, transactions and canonical rendering are
  therefore those of the arrow spelling, which canonical source keeps
  writing.
- SOURCE is a list or a class's population, evaluated once as the receiver.
  The result stays live on SOURCE and on everything EXPR and COND read. NAME
  is local to the comprehension. The limits of lambdas are inherited: their
  bodies read variables and their own name, but not the parameters of an
  enclosing function or lambda.
- A comprehension stands wherever a list literal may. Multiple `for` or `if`
  clauses, tuple targets, dict and set comprehensions, parenthesized
  generators and bare generator arguments are not added; each raises a
  documented `SyntaxError`.
- Every input the accepted parser accepts keeps its parse. A source is parsed
  with comprehensions only after the accepted parse fails, the way
  [NUC 86](nuc-0086.md) retries `is`, so only former syntax errors change,
  including template interpolations and `parse_expression` inputs whose
  ignored trailing tokens contain `for`.
- Two diagnostics are new in this position:
  `SyntaxError("Expected a name but found <token>")` and
  `SyntaxError("Expected 'in' or 'of' but found <token>")`. No token kind,
  keyword, syntax tree node, runtime path, dependency, public Rust API or
  project version is added or changed. The authoritative contract is
  [List comprehensions](../nucleoid.spec.md#list-comprehensions).
- Accepted: the frozen candidate meets every hard criterion of the automatic
  acceptance rule and passes every policy check, and the independent
  evaluator's overall decision is Accepted. Token comparison was skipped as
  `language_compatibility`, the category's rule, not a failed check; see
  [Evaluation](#evaluation).

## Motivation

- Nucleoid aspires to be a superset of familiar languages. Python's list
  comprehension is how Python maps and filters a list, and language models
  trained on Python write it constantly, including in world models that
  derive one list of facts from another.
- At the accepted revision every comprehension is a syntax error:
  `ys = [x * 2 for x in xs]` raises
  `SyntaxError("Expected ']' but found keyword 'for'")` at the `for` and stops
  the whole program before any statement runs.
- The accepted spelling,
  `prices.filter(price => price > limit).map(price => price * 2)`, means the
  same, but translating each comprehension reorders its parts and names its
  loop variable twice.
- Reading a comprehension as that spelling gives it everything the spelling
  already has: the result is a standing relationship that follows its source
  list, the population of its class, the properties it reads and the
  variables it reads, and `why` explains it.

## Rationale

- **Confirmed category and mode.** The caller made one tool-backed uniform
  draw over the five categories that NUC 1's registry marks eligible for
  automatic selection. It selected Language compatibility, index 4, with
  probability 1/5 and no redraw, and chose this bounded enhancement within
  it. This is a continuous cycle, so token comparison is skipped as
  `language_compatibility`. That skip is categorical; it is neither a
  measured comparison nor a passing token gate.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts. They execute their assertions and explicit
  returns with full coverage. Every pre-existing case is unchanged. Runtime
  applicability does not apply to this category.
- **Accepted first, not in place.** At the accepted revision a list literal's
  first item followed by `for` is always an error, because no expression
  consumes `for`. But tentative parses catch errors and some inputs ignore
  their trailing tokens: `parse_expression("x if [y for y in ys] else z")`
  tries the Python-style condition, fails inside it, falls back and returns
  `x`, and an interpolation such as `` `${x if [y for y in ys] else z}` ``
  reads `x`. Extending the list grammar in place would give those accepted
  inputs new readings, the class of break that rejected
  [NUC 91](nuc-0091.md). So a source is parsed exactly as the accepted parser
  parses it first, including its `is` retry, and is parsed again with
  comprehensions only when that fails and it contains `for` or a template.
  Every accepted input keeps its parse by construction.
- **The arrow spelling's trees.** A comprehension builds the existing
  `Expr::Call`, `Expr::Member` and `Expr::Function` nodes that the arrow
  spelling builds, with the parameter that `x => ...` builds. Rejected: a
  dedicated comprehension node, which would need its own evaluation,
  dependency tracking, rendering and graph keys, and would duplicate what
  `map` and `filter` already do reactively.
- **`filter`, then `map`, uniformly.** With an `if` clause the condition sees
  every item and the expression only the kept ones, as in Python. Python
  interleaves the two per item, while `filter` runs before `map`; the order
  differs only when COND or EXPR has side effects. Rejected: one combined
  callback such as `flatMap(x => c ? [e] : [])`, which renders and explains
  differently from the spelling a reader would write by hand.
- **`of` as well as `in`.** Nucleoid's `for` statement accepts both, and
  JavaScript iterates with `of`, so `[x for x of xs]` is the same
  comprehension.
- **SOURCE ends before `if`.** Python's grammar gives the iterable no
  conditional expression, so `[x for x in a if c else b]` is a Python syntax
  error and `if` there always starts the filter. A Python-style conditional
  at SOURCE's top level is therefore not read; parentheses select one.
  `?:` has no `if`, so it needs none.
- **COND to `]`.** COND is a full expression, so `if a if b else c` filters
  by the conditional `a if b else c`. A second `if` without `else` is not a
  conditional and raises `SyntaxError("Expected ']' but found keyword 'if'")`.
- **One `for`, at most one `if`.** Python's `[x for row in grid for x in row]`
  would need a `flatMap` lowering whose inner callback reads the outer name,
  which lambdas cannot do. Rejected, with the other Python forms that need
  more than an exact lowering: tuple targets need destructuring parameters,
  which lambdas lack; dict comprehensions need object construction and set
  comprehensions a set type; generator expressions `(x for x in xs)` and
  `f(x for x in xs)` are lazy in Python, and reading them as lists would give
  them another meaning. All keep or raise a syntax error.
- **Inherited lambda limits.** NAME is the lambdas' parameter, so it is local
  to the comprehension, as in Python 3. Lambdas do not capture an enclosing
  function's or lambda's parameters, so
  `def scale(xs, k): return [x * k for x in xs]` raises
  `ReferenceError("k is not defined")` when it runs, as `xs.map(x => x * k)`
  does. Changing lambda scoping is outside this proposal; the limit is
  documented.
- **Interactive input.** The line-oriented REPL keeps its buffering rules. A
  comprehension on one line runs, and one inside a header that the REPL
  buffers runs with it; a comprehension split over lines fails at its first
  line, as a list literal split over lines does. The terminal workspace
  submits explicitly.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial, reward or assessment.

## Specification

### Grammar

- A list literal whose whole content has one of these forms is a
  comprehension:

```
[EXPR for NAME in SOURCE]
[EXPR for NAME of SOURCE]
[EXPR for NAME in SOURCE if COND]
[EXPR for NAME of SOURCE if COND]
```

- NAME is one identifier. A keyword such as `this` or `self`, a class
  reference, a number, a parenthesized target and a tuple of names are not.
- EXPR is a full expression, as a list item is: a Python-style conditional,
  `?:`, `??`, a lambda, a quantifier, a noun query, an `is` comparison or
  another comprehension.
- SOURCE is a full expression except that a Python-style conditional is not
  read at its top level, so an `if` there ends SOURCE. Inside brackets,
  braces, parentheses and call arguments the conditional reads as usual.
- COND is a full expression up to `]`.
- There is exactly one `for` clause and at most one `if` clause, with no
  other items and no trailing comma. Line breaks, indentation and opt-in
  comments inside the brackets carry no layout, as in every list literal.

### Semantics

- `[EXPR for NAME in SOURCE]` is `SOURCE.map(NAME => EXPR)`, and
  `[EXPR for NAME in SOURCE if COND]` is
  `SOURCE.filter(NAME => COND).map(NAME => EXPR)`. `of` is the same as `in`.
  The trees are those the arrow spellings build, so every behavior is
  theirs.

```
prices = [12, 30, 8]
doubled = [price * 2 for price in prices]
labels = ["#" + price for price in prices]
assert(doubled, [24, 60, 16])
assert(labels, ["#12", "#30", "#8"])
prices.push(5)
assert(doubled, [24, 60, 16, 10])
prices = [1, 2]
assert(doubled, [2, 4])
```

- SOURCE is evaluated once, as the receiver. A list and a class's population
  are receivers, and the comprehension stays live on SOURCE, on the
  instances and properties that EXPR and COND read and on the variables they
  read:

```
class Order(item, qty):
    this.item = item
    this.qty = qty
minimum = 2
bulk = [order.item for order in Order if order.qty >= minimum]
Order("pen", 1)
ink = Order("ink", 3)
assert(bulk, ["ink"])
Order("cap", 5)
assert(bulk, ["ink", "cap"])
minimum = 4
assert(bulk, ["cap"])
ink.qty = 9
assert(bulk, ["ink", "cap"])
```

- NAME is local: a variable with the same name keeps its value. Nested
  comprehensions work when each reads only its own name, and a comprehension
  may span lines:

```
grid = [[1, 2], [3, 4]]
scaled = [[cell * 10 for cell in row] for row in grid]
assert(scaled, [[10, 20], [30, 40]])
readings = [18, 25, 31, 22]
warm = [
    reading - 20
    for reading in readings
    if reading > 20
]
assert(warm, [5, 11, 2])
```

- The lambdas are those of the arrow spelling, so their limits hold: a
  comprehension in a function reads the function's parameters only in
  SOURCE, a nested comprehension reads only its own names, `this` in a
  method's comprehension raises `ReferenceError("this is not defined")`, and
  `[c for c in "abc"]` raises `TypeError("abc.map is not a function")`.
- A comprehension as an assignment target raises
  `SyntaxError("Cannot assign to xs.map(function())")` when the statement
  runs, as `xs.map(x => x) = 1` does, with the run rolled back.

### Rendering

- Canonical source, graph keys, `why` and `affects` rules and errors that
  quote an expression write the arrow spelling with anonymous functions
  rendered as `function()`:
  `listed = [qty * 2 for qty in stock if qty > limit]` is explained by the
  rule `listed = stock.filter(function()).map(function())`.

```
stock = [3, 0, 7]
limit = 1
listed = [qty * 2 for qty in stock if qty > limit]
spelled = stock.filter(qty => qty > limit).map(qty => qty * 2)
assert(listed, spelled)
assert((why listed).map(step -> step.rule), ["listed = stock.filter(function()).map(function())", "stock = [3,0,7]", "limit = 1"])
assert((affects limit).map(step -> step.node), ["listed", "spelled"])
```

### Positions

- A comprehension may stand wherever a list literal may: as an assignment
  value, a call or constructor argument, a return value, an arrow or lambda
  body, an object value, a list item, inside a template interpolation, in an
  `if`, `while` or `for` header, a quantifier's collection, a conditional's
  branch or condition, a destructuring value, an assertion, a `throw` or
  `suppose` statement and at the start of a statement.
- Brackets that are not list literals keep their accepted errors: index and
  slice brackets such as `xs[x for x in ys]` and `Item[x for x in ys]`, and
  `x = 1 [y for y in ys]`, which indexes `1`. So do parenthesized generators
  `(x for x in xs)`, bare call arguments `f(x for x in xs)`, dict and set
  comprehensions and a `for` after a list's second item, as in
  `[x, y for y in ys]`.

### Interactive input

- The line-oriented REPL keeps its buffering rules, in `--plain` and with
  `--json`. A comprehension on one line, or in a header the REPL buffers,
  runs with its line or header. A comprehension split over lines fails at its
  first line, as a list literal split over lines does at the accepted
  revision.
- The terminal workspace submits explicitly, so a multi-line comprehension
  runs there.

## Errors

- No error type, runtime error or catch value is added. Syntax errors stop
  compilation before any statement of the program runs.
- `SyntaxError("Expected a name but found <token>")`: the token after `for`
  is not an identifier. It is placed at that token and uses the existing
  token descriptions, such as `'('`, `keyword 'this'` (also for `self`),
  `'$Item'`, `number 1` and `']'`.
- `SyntaxError("Expected 'in' or 'of' but found <token>")`: the token after
  NAME is neither `in` nor `of`, as for a tuple target's comma. It is placed
  at that token.
- `SyntaxError("Expected ']' but found <token>")`, the existing diagnostic:
  any token other than `]` after SOURCE or COND, such as a second `for` or
  `if` clause, a comma, an `else` or the end of the input. It is placed at
  that token.
- `SyntaxError("Unexpected <token>")`, the existing diagnostic, when SOURCE
  or COND is missing, placed as for every such error at the token after the
  offending one: `[x for x in]` reports `']'` at line 1, column 13.
- `SyntaxError("Expressions are nested too deeply")` still bounds nesting.
  Each comprehension item, SOURCE and COND pass the existing depth guard, so
  nested comprehensions reach the limit where nested list literals do: 62
  levels parse at the start of a statement and 63 raise the error, while the
  arrow spelling, which spends two levels on each `map`, parses 31.
- `SyntaxError("Cannot assign to <rendering>")`, the existing diagnostic, for
  a comprehension as an assignment target, raised when the statement runs,
  as for the arrow spelling.
- Runtime errors are those of the arrow spelling, such as
  `ReferenceError("<name> is not defined")` for an enclosing parameter or an
  undefined SOURCE, `ReferenceError("this is not defined")` for `this` in a
  method's comprehension and `TypeError("<receiver>.map is not a function")`
  for a string or number SOURCE. A `null` SOURCE, or an object without a
  `map` property, gives what `SOURCE.map(...)` gives.
- The Compatibility table lists exact former and new results.

## Reference Implementation

- `src/lang/ast/parser.rs` adds the private `Lists` enum, `Literals` or
  `Comprehensions`, as the parser's `lists` field, and the
  `ExpressionContext::ComprehensionSource` variant. `attempt` runs the
  accepted `attempt_words`, which is the former `attempt` with its `is`
  retry, unchanged. When that fails and `mentions_comprehensions` finds a
  `for` keyword or a template token, it resets the parser with
  `Lists::Comprehensions` and runs `attempt_words` again, returning its
  result.
- `src/lang/ast/parser/comprehension.rs` is new. `starts_comprehension`
  holds at `for` when the parser reads comprehensions. `comprehension` reads
  NAME through `comprehension_name`, which reuses the arrows'
  `untyped_parameter`, then `in` or `of`, SOURCE in `ComprehensionSource`,
  the optional `if` and COND, and `]`, and builds the trees with the private
  `method_call` and `lambda` functions.
- `src/lang/ast/parser/primary.rs`: `list_literal` hands its first item to
  `comprehension` when `starts_comprehension` holds.
  `src/lang/ast/parser/expression.rs`: `python_condition` declines in
  `ComprehensionSource`, as it does in `Interpolation`.
  `src/lang/ast/parser/statement.rs` and `src/lang/ast/parser/template.rs`:
  the accepted-grammar probe of the `is` retry and the interpolation
  sub-parser inherit `lists`.
- A comprehension adds one path back into the expression grammar, from a

  existing depth guard, so no unguarded recursion is added. No function
