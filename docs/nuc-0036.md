## Abstract

- Add only unshadowed static `Math.fract(value)`, the intrinsic numeric
  composition of `value - Math.floor(value)`.
- Convert the first input intrinsically, compute its floor, then subtract
  that floor using separate ordinary floating-point operations.
- Preserve accepted syntax, argument effects, reactive reads, class rules,
  scope, frames, error positions and transactional recovery.
- Independent evaluation accepted the frozen implementation before integration.

## Motivation

- Name a live fractional-part relationship without repeating its input in
  a subtraction and a floor call.
- Treat negative finite values consistently with floor-based partitions,
  such as `-1.25` contributing the fraction `0.75`.
- Retain independent whole-part controls, assertions and expected returns
  rather than weakening demonstrations to abbreviate them.

## Rationale

- Floor subtraction, not host `f64::fract`, supplies the negative-input
  behavior. Truncation, remainder, absolute value and sign correction are
  different operations and are not substitutes.
- Specify the operation order so every non-NaN result matches independent
  accepted arithmetic/floor controls by bits, including zero.
- Tiny negative values can round to exactly one after subtraction; clamping
  or promising a strict `[0, 1)` result would contradict the composition.
- Compare expected NaNs by classification rather than imposing NaN payload
  bits; do not introduce a portable zero-sign convention.
- Reuse the existing Math supplied-Undefined gate and first-input conversion
  instead of adding a namespace, callable representation or helper abstraction.
- Intrinsic conversion and host floor must not resolve, invoke or track a
  shadowable `Number` or `Math.floor` binding.
- Retain every supplied expression's once-only left-to-right evaluation,
  even when its resulting extra value is ignored numerically.
- Depend only on accepted arithmetic, conversion, calls and reactive behavior,
  not a pending proposal or a change to public representations.

## Specification

### Static numeric contract

- The authoritative [Reactive fractional part section](../nucleoid.spec.md#reactive-fractional-part)
  defines the accepted behavior and takes precedence over this proposal.
- The only added unshadowed static signature is `Math.fract(value)`.
- Evaluate every supplied expression once, left to right, through unchanged
  call machinery before Math's existing numeric gate.
- If any supplied value is `Undefined`, including an ignored extra, return
  `Undefined` before conversion.
- Reuse the dispatcher's intrinsic first-input `Value::to_number` conversion.
  A missing first input supplies numeric NaN, not a supplied Undefined.
- Numbers retain their values, literal null converts to zero, booleans to
  zero/one, trimmed strings and empty/singleton lists retain existing numeric
  conversion, and dates contribute milliseconds.
- Other nonnumeric conversions produce numeric NaN, not a new type error.
- Compute `floor = first.floor()`.
- Return numeric `first - floor`.
- These are separate ordinary `f64` operations in exactly that order.
- Do not use `f64::fract`, truncation, remainder, absolute value, sign
  correction, conversion skips, normalization or result clamping.
- Negative finite fractions subtract floor; `-1.25` yields `0.75`.
- Both infinities produce numeric NaN by subtraction; numeric NaNs remain NaN.
- Integers, subnormals and signed zeros retain the accepted composition's
  exact result. Expected NaNs use classification; every non-NaN result,
  including zero, matches independent arithmetic/floor controls by bits.
- A tiny negative input such as `-0.00000000000000000001` can round to
  exactly one. Do not promise that all results lie strictly in `[0, 1)`.
- Extra supplied values are neither numerically converted nor used in the
  floor/subtraction computation.

### Evaluation and compatibility

- Keep all supplied expressions' reads, effects, dependencies and strict
  errors, including extras and expressions after an undefined property.
- Supplied Undefined preserves deferred assignments and recovery when
  missing properties become defined.
- Intrinsic literal-null conversion does not override live assignment or
  parameter-null deferral.
- Preserve statement positions, caught values, graph transactions, rollback,
  property deletion and subsequent propagation.
- State/local Math bindings still shadow the static namespace; ordinary
  `.Math` members retain their existing lookup.
- Reading `Math.fract` as a value remains unsupported/Undefined, like other
  static Math method reads, not a callable reference or alias.
- Intrinsic conversion and host floor neither invoke nor track shadowable
  `Number` or `Math.floor`; do not recursively call public Math dispatch.
- Typed wrappers, call frames, receivers, per-instance class rules and
  scopes use unchanged machinery.
- The arithmetic/floor emulation and intrinsic have intentionally different
  RHS ASTs; controls, values and transitive behavior agree without requiring
  identical whole-new-program ASTs or immediate dependency graphs.
- Every existing Math match arm, numeric helper, constant and control remains
  unchanged, including its arithmetic order and errors.
- The existing `value - Math.floor(value)` spelling and every previously
  accepted syntax form remain available with the same semantics.
- Add no parser, lexer, AST, generator, CLI implementation, public API/
  representation, dependency, version, MSRV or resource-limit change.
- Do not repair inherited noncapture, parameter-dependent-local or old
  whole-suite Gitless discovery limitations, or make broader safety claims.

## Errors

- Introduce no new numeric, coercion, range-validation or arity errors.
- Numeric NaNs, omitted first inputs and nonfinite results are not errors.
- Argument/application failures retain inherited kinds, exact messages,
  statement positions, caught values and transactional recovery.
- Never skip an expression because an earlier supplied value is undefined.

| Condition | Exact inherited error |
| --- | --- |
| Strict unknown argument `missing`, including extras or after an undefined property | `ReferenceError("missing is not defined")` |
| Unsupported static `Math.random()` argument | `TypeError("Math.random is not supported")` |
| Unchanged unknown static method `unknown` | `TypeError("Math.unknown is not a function")` |
| Calling through numeric state `Math = 7` | `TypeError("number.fract is not a function")` |

- Unknown/random Math calls still pass through the existing supplied-Undefined
  gate; ordinary shadowed receivers retain their existing method errors.
- User throws propagate and roll back unchanged, including `"ROLLBACK"` in
  the paired deferred-read entry.
