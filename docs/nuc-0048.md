# NUC 48 -- State-Filtered Reasoning Selections

```

Title: State-Filtered Reasoning Selections

Status: Accepted
Type: Standards Track
Category: Reasoning enhancement
Created: 25-Oct-2026
```

## Abstract

- Add optional `stated` and `derived` reasoning stages that filter an existing
  graph selection by its existing typed `StepState`.
- Retain selected steps' order, fields, live observations, materialization and
  transaction behavior without introducing a second provenance representation.

## Motivation

- An explanation often needs its supporting stated facts separately from its
  derived conclusions.
- Accepted list filters can already distinguish these states, but repeating
  their callbacks obscures a graph-selection pipeline.
- Keep the distinction available before materialization so further reasoning
  stages can operate on the selected graph nodes.

## Rationale

- This is a Reasoning enhancement: its purpose is graph selection over the
  accepted explanation model, not a general list-filter utility.
- The caller's single unbiased draw selected index 3, Reasoning enhancement,
  from the four eligible registry categories; no second draw is required.
- Reuse the typed states already exposed by `why`, rather than recording new
  provenance or guessing state from `from.length`.
- Class-governed steps may be derived with no input edges; filtering must not
  relabel them as stated facts.
- Reuse the parser's contextual stage vocabulary, not reserved lexer keywords,
  a new call form, or reinterpretation of ordinary names and methods.
- Retain the source selection's complete observations, rather than subscribing
  only to the steps that currently pass the filter.
- The semantic basis is the already implemented reasoning entries in
  `nucleoid.spec.md`, including `Nucleoid explains how a value was derived`,
  `Nucleoid states a fact that follows from nothing else`,
  `Nucleoid names the class-level rule a property was derived from`, and
  `Nucleoid chains reasoning operations`.
- No unaccepted operation or dependency from the broader Draft NUC 11 is
  required; this revision does not change that proposal.

## Specification

### Selection and composition

- `selection |> stated` retains exactly its `StepState::Stated` steps;
  `selection |> derived` retains exactly its `StepState::Derived` steps.
- Preserve the relative order of retained steps and all their existing
  `node`, `holds`, `rule`, `state`, and `from` fields.
- Existing state classification is authoritative; this proposal changes
  neither graph state inference nor the meaning of those fields.
- `result |> why |> stated` selects the stated supporting steps of that
  explanation; `result |> why |> derived` selects its derived steps.
- `model |> stated` and `model |> derived` filter the current model directly,
  with the accepted exclusion of pending nodes and reasoning observers.
- Prefix `stated seed` and `derived result` filter a single reference's
  existing selection; neither prefix implicitly applies `why`.
- A nonmatching or absent-property selection yields `[]`; a never-defined
  name retains its existing reference error.
- Pipelines, including parenthesized nested pipelines, compose as graph
  selections. Materialize only through the existing final selection path.
- The root specification's
  [state-filtered reasoning contract](../nucleoid.spec.md#state-filtered-reasoning-selections)
  and `Nucleoid filters reasoning selections by stated and derived state`
  define this example:

```nuc
seed = 2
middle = seed + 3
result = middle * 2
facts = result |> why |> stated
conclusions = result |> why |> derived
assert(facts.map(step => step.node), ["seed"])
assert(facts[0].holds, 2)
assert(facts[0].from, [])
assert(conclusions.map(step => step.node), ["result", "middle"])
assert(conclusions[0].holds, 10)
assert(conclusions[0].from, ["middle"])
assert(conclusions[0].state, "derived")
```

- `Nucleoid filters individual references without traversing their ancestors`
  protects the distinction between filtering a reference and explaining it:

```nuc
seed = 1
value = seed + 1
fact = stated seed
notFact = stated value
conclusion = derived value
assert(fact.map(step => step.node), ["seed"])
assert(notFact, [])
assert(conclusion.map(step => step.node), ["value"])
```

- `Nucleoid retains derived class rules without input edges in state filters`
  protects existing class-governed classification:

```nuc
class Subject
$Subject.active = true
item = Subject()
facts = item.active |> why |> stated
conclusions = item.active |> why |> derived
assert(facts, [])
assert(conclusions.length, 1)
assert(conclusions[0].node, "item.active")
assert(conclusions[0].from, [])
assert(conclusions[0].rule, "$Subject.active = true")
assert(conclusions[0].holds, true)
```

### Observation and compatibility

- Resolve the complete source selection before filtering, preserving every
  value and shape observation, including excluded steps and model membership.
- Empty results remain live; changing a declaration or state without changing
  its value must still refresh both filters.
- Ancestry changes, reference replacement, deletion and redefinition,
  functions, class rules, propagation order and observer exclusion retain
  their accepted behavior.
- `.value` still snapshots the materialized reading; a failed transaction
  restores selections, observations and pending work through existing rollback.
- `Nucleoid keeps reasoning state filters live through equal valued rewrites`,
  `Nucleoid observes empty state filtered model selections`, and
  `Nucleoid restores state filtered explanations and preserves snapshots`
  are the additional normative live-state traces.
- `stated` and `derived` remain ordinary identifier tokens. Recognize them
  only at the parser's existing pipeline-stage and prefix-stage positions.
- Preserve variables, parameters, object keys, property access, user functions
  and methods named `stated` or `derived`.
- A local/parameter, state variable, function or class binding of a new stage
  name shadows that operation. Reject it before selecting the source, retaining
  the accepted `<name> is not an operation` pipeline diagnostic.
- Preserve a complete ordinary identifier value before the next comma-free
  explicit object field, including values named `stated` or `derived`.
- Do not change accepted `why` or `affects` shadowing behavior.
- `stated(seed)` and `derived(result)` remain ordinary calls; do not silently
  rewrite them into reasoning stages.
- Keep `why`, `affects`, list `.filter`, other accepted grammar and existing
  parser limits unchanged.
- Accepted computation counterparts remain
  `(why result).filter(step => step.state == "stated")` and
  `(why result).filter(step => step.state == "derived")`.
- Prefix counterparts use the single-reference portion,
  `(why value).slice(0, 1).filter(step => step.state == "derived")`,
  not an unbounded ancestor filter.
- The nine caller-supplied, pre-executed counterparts pair seven appended
  spec entries, `Reasoning state filters distinguish facts from conclusions`
  in `tests/reference.md`, and
  `Reasoning state filters separate supporting facts from derived totals`
  in `docs/examples.md`. Preserve identities, assertion order, canonical
  assertions, expected returns and executed coverage.

## Errors

- Introduce no new error type or diagnostic wording; reference selection
  validates the source before filtering.
- `Nucleoid preserves reference errors while filtering reasoning states`
  protects the first two exact inherited diagnostics below and their
  caught-error behavior; the specification prose and focused shadowing
  regressions protect the last two:

| Source | Error |
| --- | --- |
| `1 |> stated` | `TypeError("Cannot explain 1")` |
| `stated missing` | `ReferenceError("missing is not defined")` |
| `seed |> stated`, with `stated` bound | `TypeError("stated is not an operation")` |
| `seed |> derived`, with `derived` bound | `TypeError("derived is not an operation")` |

- `derived` uses the same source-validation path and inherited diagnostics.
- Errors evaluating a reference or nested source propagate unchanged; failed
  transactions must not leave partial state, observations or queued refreshes.
- Ordinary call and unknown-stage diagnostics remain those of the accepted
  parser and runtime, rather than being converted into filter-specific errors.

## Reference Implementation

- Candidate implementation: add concrete `Stage::Stated` and `Stage::Derived`
  variants and typed `StepState` filtering in `src/reasoning.rs`.
- Reuse the contextual stage parser, source selection, observation tracking and
  materialization without lexer, graph-storage or provenance changes.
- `src/lang/ast/reason.rs` checks bindings only for the two new stage names;
  `src/lang/ast/parser.rs` protects accepted comma-free object-field boundaries
  from their prefix spellings. Existing `why`/`affects` routing is unchanged.
- `tests/state_filtered_reasoning.rs` covers nested composition, complete
  observations of excluded steps, empty/property/model selections, equal-valued
  changes, replacement/deletion, functions, class rules, snapshots, rollback,
  exact inherited diagnostics and ordinary-name/call compatibility.
- Its opt-in compatibility replay uses the existing `tests/common` harness,
  the four exact accepted Git documents and nine immutable extra sources.
  It checks both accepted and candidate programs against protected canonical
  assertions, expected returns and actual assertion coverage, without a token
  acceptance gate or outcome report.
- Synchronize `docs/README.md`, the executable reference/example, and new
  canonical `synth-21-0119` and `synth-21-0120` training records.
- Regenerate `dataset/nucleoid.spec.jsonl` with
  `UPDATE_DATASET=1 cargo test --test dataset` and `tests/nucleoid.spec.rs` with
  `UPDATE_SPEC_TESTS=1 cargo build`; do not edit generated exports manually.
- Public Rust API note: adding variants to the currently exhaustive public
  `Stage` enum can break downstream exhaustive matches. A human must determine
  the appropriate semantic-versioning treatment; no version or release
  metadata is changed by this candidate.
- Independent evaluation accepted the frozen revision recorded below;
  development checks alone were not the acceptance decision.
