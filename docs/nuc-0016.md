# NUC 16 -- Bare Zero-Argument Super Calls


## Abstract

- Specifies bare `super` as behavior-equivalent shorthand for the expression `super()`.
- Preserves explicit `super(arguments...)`, including its argument evaluation, syntax diagnostics, and canonical rendering.
- Reuses the existing keyword, `Expr::Super(Vec<Expr>)`, call dispatch, and parent-constructor runtime.

## Motivation

- Calling a parent constructor without arguments needs no empty argument-list syntax to convey its behavior.
- The shorter expression is useful in block constructors, expression-bodied initializers, and methods.
- Removing the empty parentheses does not require another public token, AST variant, or execution path.

## Rationale

- The existing `super` keyword already identifies the parent-constructor operation.
- An absent argument list denotes an empty argument vector, not implicit arguments or forwarding of the current constructor's parameters.
- An immediately following left-parenthesis token must retain the existing explicit argument parser.
- Checking the next token, without skipping separators, preserves the existing logical-line grammar.
- The change is a primary-expression shorthand, not a statement-only feature or an automatic call rule for ordinary identifiers.
- Existing postfix and operator grammar remains applicable to the expression.
- Canonical generation stays `super()` so equivalent source spellings have the same AST and graph source.
- Parenthesis-free function definitions, changes to receiver resolution, and unrelated CLI stack infrastructure are out of scope.

## Specification

### Primary expression and boundaries

- After consuming `Keyword::Super`, an immediate `LeftParen` enters the existing argument-list parser.
- Otherwise, the primary expression is exactly `Expr::Super(Vec::new())`.
- Ordinary whitespace before `(` does not change an explicit call because it introduces no intervening token.
- The parser does not skip newlines, semicolons, indents, or dedents to search for an argument list.
- `super` followed by `(7)` on the next logical line is a zero-argument call followed by a separate parenthesized expression.
- Inside already-open parentheses or brackets, the lexer suppresses line breaks as before; `(super` followed by `(7))` there is the explicit call `super(7)`.
- Bare `super` may appear in an assignment, a return, a collection, or a function or method expression body.
- Member access, indexing, slicing, subsequent calls, and operators use the existing postfix and expression grammar.
- For example, `super.amount` has the same AST as `super().amount`, `(super)()` as `(super())()`, and `super - 1` as `super() - 1`.
- These expressions operate on the existing result of the zero-argument call; they do not supply parent-constructor arguments.
- The pre-existing general adjacent-statement grammar is not tightened: `super amount` and `super 7` parse as a zero-argument call followed by another expression statement.
- Explicit arguments still require `super(amount)`; existing multiline lists and trailing commas remain valid.
- Ordinary identifiers remain references, and function definitions retain their existing parameter-list grammar.
- The paired expression/receiver specification entry below covers expression-bodied initializers and methods; [tests/bare_super.rs](../tests/bare_super.rs) checks full ASTs, logical lines, postfix forms, operators, adjacent statements, and explicit-call boundaries.

### Inherited execution

- Both spellings use the existing call dispatch and `Runtime::call_super`.
- Explicit arguments are evaluated in order before checking the receiver; bare `super` evaluates no arguments.
- Without an instance receiver, the call raises `ReferenceError("super is not defined")`.
- With a receiver, resolution starts from the constructor currently executing.
- When no constructor context is set, including in methods, resolution falls back to the actual receiver's class.
- The parent constructor runs against that same object, using the existing nearest-ancestor constructor lookup.
- On success, the call returns `null`, irrespective of a return value from the parent's constructor.
- A receiver whose class has no parent makes the call a no-op returning `null`, not an error.
- Missing parent parameters bind to `null`; bare `super` never forwards child parameters or consumes following expressions as arguments.
- A passive subclass continues to use the nearest ancestor constructor, whose own `super` advances from that executing constructor rather than restarting from the receiver's class.
- Class-instance populations remain distinct; running a parent constructor does not create a separate parent instance.
- Inherited reactive properties, graph-source canonicalization, transactions, and rollback use their existing representations and behavior.
- A failure in the parent constructor rolls back the enclosing transaction, including property writes, instance registration, and the failed instance's name.

### Normative behavior coverage

- [nucleoid.spec.md](../nucleoid.spec.md) is normative for the candidate's implemented behavior.
- Each new executable entry has an immutable, already-executed accepted-syntax counterpart with exactly the same identity, ordered canonical assertions, and expected return.
- Only empty `super()` calls in those paired programs are rewritten; explicit argument-bearing calls remain unchanged.

| Specification entry | Implemented behavior |
| --- | --- |
| `Nucleoid invokes a parent constructor with bare super on the same instance` | Parent initialization on the existing child, named receiver identity, and distinct parent/child populations |
| `Nucleoid resolves bare super through the executing constructor chain` | Multi-level constructor context, passive-subclass lookup, and distinct populations |
| `Nucleoid preserves omitted parent arguments with bare super` | Zero arguments bind missing parent parameters to `null`; explicit arguments remain compatible |
| `Nucleoid preserves bare super expression and receiver behavior` | Expression-bodied initializers, method calls, `null` results without a parent, and the missing-receiver error |
| `Nucleoid rolls back a failing parent constructor called with bare super` | Propagated parent failure, property rollback, population rollback, and removal of the failed name |

```nuc
class Parent:
    def init():
        this.amount = 4

class Child: Parent
    def init():
        super
        this.amount = this.amount + 1

child = Child()

assert(child.amount, 5)
assert(child.id, "child")
assert(Parent.length, 0)
assert(Child.length, 1)
```

- Existing entries `Nucleoid creates a class and a subclass` and `Nucleoid resolves super from the constructor currently executing` retain their explicit argument-bearing calls.
- Existing inherited-rule entries, including `Nucleoid preserves subtype property rules when a parent rule changes`, retain their behavior.
- The paired example `Bare super preserves inherited reactive properties` in [docs/examples.md](examples.md) checks inherited propagation alongside parent initialization.
- Handwritten regressions additionally compare method receiver-class fallback through a parent chain, argument evaluation, canonical graph keys and reasoning source, and failed-parent dependency restoration.

## Errors

- The shorthand adds no error kind, runtime restriction, or catch-value format.
- The missing-receiver error is exactly `ReferenceError("super is not defined")`, as asserted by the paired expression/receiver specification entry.
- No parent is not an error: the paired `Root` constructor stores `null`.
- Existing argument-expression and parent-constructor failures propagate unchanged.
- The paired rollback entry catches the exact thrown value `"BLOCKED"` and later observes `ReferenceError("failed is not defined")`.
- Malformed explicit calls retain the existing argument parser's exact syntax diagnostics and positions.
- The following diagnostics were captured with the unchanged accepted runtime and are checked by [tests/bare_super.rs](../tests/bare_super.rs).

| Explicit source | Error | Line | Column |
| --- | --- | --- | --- |
| `super(` | `SyntaxError("Unexpected end of input")` | 1 | 7 |
| `super(1` | `SyntaxError("Expected ')' but found end of input")` | 1 | 8 |
| `super(,)` | `SyntaxError("Unexpected ','")` | 1 | 8 |
| `super(1 2)` | `SyntaxError("Expected ')' but found number 2")` | 1 | 9 |
| `super(1 +)` | `SyntaxError("Unexpected ')'")` | 1 | 11 |
| `super(;)` | `SyntaxError("Unexpected ';'")` | 1 | 8 |
| `super(1,,2)` | `SyntaxError("Unexpected ','")` | 1 | 10 |
| `super(`, then `1 +`, then `)` on three lines | `SyntaxError("Unexpected ')'")` | 3 | 2 |
| `super(1;` | `SyntaxError("Expected ')' but found ';'")` | 1 | 8 |

- `super(1,)` is valid syntax, not a malformed call.
- Error positions retain one-based lines and character columns.
- Runtime failures remain placed at the top-level statement that initiated them; `saved = 7` followed by bare `super` reports `ReferenceError: super is not defined (line 2, column 1)`.
- Invalid explicit calls are rejected before any earlier statements in that submitted source execute.
- Existing nesting, operator-chain, and execution safeguards are unchanged.
