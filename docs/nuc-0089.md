# NUC 89 -- Named Function Declarations

```
NUC: 89
Title: Named Function Declarations
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Language compatibility
Created: 07-Nov-2026
Requires: 8, 87
```

## Abstract

- A named function may be declared as JavaScript, TypeScript and PHP declare
  one: the keyword `function`, a name, a parenthesized parameter list and a
  braced body, as in `function double(amount) { return amount * 2 }`.
- The declaration builds exactly the function that `def double(amount):`
  builds with the same statements: the same name, parameters and block body.
  State, redefinition, callers, `.value`, graph keys, `why`, `affects`,
  transactions and canonical rendering are those of `def`, which canonical
  source keeps writing.
- The parameter list is the parenthesized list of `def`, with annotations,
  literal defaults, a final rest parameter and, for `init` in a class body,
  the `this.name` parameters of [NUC 87](nuc-0087.md). The body is the braced
  block of the accepted anonymous `function (params) { ... }` literal.
- The declaration is a statement wherever a statement may start, including
  after another statement on the same line. In an indented class body it
  declares a method, and `function init(...)` becomes the constructor, as
  `def` does there. Declarations are not hoisted.
- `function` stays a keyword with its accepted meaning in expressions:
  `g = function f(a) { return a }` still raises
  `SyntaxError("Expected '(' but found identifier 'f'")`, and anonymous
  literals are unchanged. Only inputs that were syntax errors at the accepted
  revision change.
- Malformed declarations raise the existing
  `SyntaxError("Expected '{' but found <token>")` and
  `SyntaxError("Expected '(' but found <token>")` diagnostics, at the
  offending token, with the anonymous literal's and `def`'s parameter
  diagnostics.
- No token kind, keyword, syntax tree node, runtime path, dependency, public
  Rust API or project version is added or changed. The line-oriented REPL
  buffers an unfinished declaration until its braces close. The
  authoritative contract is
  [Named function declarations](../nucleoid.spec.md#named-function-declarations).
- **Outcome: Accepted.** The independent evaluation and the caller's
  integrated-tree checks passed all three hard criteria, and the independent
  evaluator decided Accepted with no defects and two low REPL findings.
  Token comparison was skipped as `language_compatibility`, the category's
  continuous-mode policy; no policy check failed.

## Motivation

- Nucleoid aspires to be a superset of familiar languages. Python, Scala and
  Ruby name functions with `def`, which Nucleoid accepts. JavaScript,
  TypeScript and PHP write `function total(price, qty) { ... }`, which fails
  at the accepted revision.
- `function` is already a Nucleoid keyword, but only for anonymous literals,
  so every named declaration raises
  `SyntaxError("Expected '(' but found identifier '<name>'")` at its name and
  stops the whole program before any statement runs. World models written by
  language models trained on JavaScript and TypeScript routinely contain such
  declarations.
- The nearest accepted spelling, `total = function (price, qty) { ... }`,
  stores a function value in a variable rather than declaring a function:
  its graph node is a variable, `why` explains it as an assignment, and
  canonical source writes the assignment. Translating each declaration to
  `def` means rewriting its body as an indented suite.
- `function total(price, qty) { ... }` gives JavaScript's declaration its
  familiar meaning: the function that `def total(price, qty):` declares.

## Rationale

- **Confirmed category and mode.** The caller made one tool-backed uniform
  draw over the five categories that NUC 1's registry marks eligible for
  automatic selection. It selected Language compatibility, index 4, with
  probability 1/5 and no redraw. This is a continuous cycle, so token
  comparison is skipped as `language_compatibility`. That skip is
  categorical; it is neither a measured comparison nor a passing token gate.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts. They execute their assertions and explicit
  returns with full coverage. Every pre-existing case, its spelling and its
  `def` declarations are unchanged. Runtime applicability does not apply to
  this category.
- **Only a former error position.** The accepted parser consumes the keyword
  `function` in two places only: as an anonymous literal, which requires `(`
  next, and as a property name directly after `.`, as in `record.function`.
  So every input in which `function` is followed by a name, other than after
  `.`, was a syntax error, and giving that sequence a meaning at the start of
  a statement changes no accepted program.
- **Statements only.** JavaScript also has named function expressions,
  `g = function f(a) { ... }`, whose name is bound inside the body only.
  Nucleoid functions do not capture or bind names in their bodies, so such a
  name would need a new scope rule. Rejected: the expression keeps its
  accepted error, and assigning an anonymous literal remains the expression
  spelling.
- **Braced bodies only.** The body is the anonymous literal's braced block,
  so the two `function` spellings share one body grammar. Rejected:
  `function f(a) => a` and `function f(a):` with a suite, which would mix the
  two spellings into forms that neither language writes, and TypeScript
  return annotations, which have no place in `Stmt::Function` and would be
  dropped silently. All of them stay syntax errors.
- **The brace on the header's line.** A newline after the parameter list ends
  the header, as it does after the anonymous literal's parameters, and a `{`
  that starts a line is a block statement. Rejected: Allman-style braces on
  the next line, which would give a newline two meanings after a header.
- **The parameter list of `def`.** The parenthesized list of `def` already
  covers annotations, literal defaults, final rest parameters and, in a class
  body, `init`'s initializing parameters, so `function` and `def` stay
  interchangeable. The bare, comma-free and typed bare lists of NUCs 18 to 40
  stay `def` spellings: `function amount:` with an indented body is pinned as
  a syntax error by accepted tests, and stays one.
- **Not hoisted.** JavaScript hoists function declarations to the top of
  their scope. Nucleoid runs statements in order, each in its own
  transaction, and a declaration files its function when it runs. Hoisting
  would reorder state, graph and rollback. A call that runs before the
  declaration raises `ReferenceError("<name> is not defined")`, as for `def`.
- **Same declaration.** The existing `Stmt::Function` with a name and a
  `FunctionBody::Block` already describes the declaration, so no syntax tree
  node, token kind or runtime path is needed. The generator writes `def`, so
  graph labels and canonical source do not distinguish the two spellings.
- **Classes.** In an indented class body, a member that starts with `def`
  declares a method. Treating `function` the same way keeps class bodies
  interchangeable, and `init` is adopted as the constructor because the
  runtime adopts any method named `init`. As for `def`, a declaration after a
  class header's colon on the same line, `class A: function f() { ... }`, is
  the class's constructor statement.
- **Juxtaposition stays.** Statements may follow one another without a
  separator, so `function f(a) { return a } f(2)` declares and calls `f`.
  For the same reason `export function f(a) { ... }` and
  `async function f(a) { ... }` now parse as the name `export` or `async`
  followed by a declaration, and running them raises
  `ReferenceError("export is not defined")`, as `let x = 1` raises
  `ReferenceError("let is not defined")` at the accepted revision.
- **PHP parameters.** PHP writes `function f($a) { ... }`. A `$` name is a
  class reference in Nucleoid, so it is not a parameter, and
  `SyntaxError("Expected a parameter but found '$a'")` remains its error.
- **Interactive input.** The line-oriented REPL ran `function f(a) {` at
  once, so a declaration typed over several lines failed at its first line
  and ran its body lines as separate statements. It now buffers an input that
  contains a declaration until its braces close, through blank lines, as it
  buffers an open block comment. Other braced input, such as
  `f = function (a) {` or `{`, keeps running at once; changing it is outside
  this proposal. The terminal workspace submits explicitly and needs no
  change, and `function` is already one of its completion words.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial, reward or assessment.

## Specification

### Grammar

- At the start of a statement, the keyword `function` followed by an
  identifier begins a declaration:

```
function name(parameters) { statements }
function name(parameters) {
    statements
}
```

- The name is an ordinary identifier. The parameter list is the
  parenthesized parameter list of `def`: names with optional annotations and
  scalar literal defaults, an optional final rest parameter, an optional
  trailing comma, and newlines inside the parentheses. In an indented class
  body, `function init(...)` also accepts the `this.name` and `self.name`
  parameters of [NUC 87](nuc-0087.md).
- The body is the braced block of the anonymous `function (params) { ... }`
  literal: statements separated by newlines, semicolons or nothing,
  including colon suites and nested blocks. Its `{` is the next token after
  the closing parenthesis, on the same line. `{}` is an empty body.
- A statement starts at the beginning of the input, after a newline, `;`, an
  indentation change, a block's `{` or a suite's `:`, and after a complete
  statement on the same line.

### Semantics

- A declaration builds the `Stmt::Function` that `def name(parameters):`
  builds with the same statements: the same name, parameters and block body.
  An empty body returns `null`, as a block without a `return` does.
- A function is stored in the state when its declaration runs. Calls in
  later statements, standing declarations that call it, redefinition with
  either spelling, function and variable bindings that replace one another,
  live and frozen `.value` definitions, graph keys, `why`, `affects`,
  transactions and rollback are therefore those of `def`.

```
function double(amount) {
    return amount * 2
}
function area(width, height) { return width * height }
function describe(size) {
    if size > 10:
        return "large"
    return "small"
}
room = area(3, 4)
assert(double(room), 24)
assert(describe(room), "large")
assert(describe(double(2)), "small")
room = area(2, 2)
assert([room, describe(room)], [4, "small"])
```

- The two spellings declare one function, so a redefinition with either
  spelling updates every caller:

```
def fee(amount) => amount / 10
base = 200
charge = fee(base)
assert(charge, 20)
function fee(amount) { return amount / 4 }
assert(charge, 50)
function label(name, count: int = 1, ...tags) { return [name, count, tags] }
assert(label("a"), ["a", 1, []])
assert(label("b", 2, "x", "y"), ["b", 2, ["x", "y"]])
```

- In an indented class body, a declaration is a method, and `init` becomes
  the constructor:

```
class Account:
    owner: str
    function init(owner, balance = 0) {
        this.owner = owner
        this.balance = balance
    }
    function deposit(amount) { return this.balance + amount }
    def withdraw(amount) => this.balance - amount
ana = Account("ana", 80)
assert([ana.owner, ana.deposit(30), ana.withdraw(30)], ["ana", 110, 50])
```

- Declarations are not hoisted, and a failed transaction rolls back a
  declaration with everything it updated:

```
try:
    early = rate(2)
catch error:
    assert(error, ReferenceError("rate is not defined"))
function rate(x) { return x * 2 }
base = 3
charge = rate(base)
try:
    function rate(x) { return x * 100 }
    assert(charge, 300)
    throw "UNDO"
catch error:
    assert(error, "UNDO")
assert(charge, 6)
```

### Rendering

- Canonical source writes `def`. A declaration renders as `def name` unless
  its parameters have literal defaults or a rest parameter; such a
  declaration renders in full as `def name(signature):` with an indented
  body, and an empty body renders as `pass`.
- `why`, `affects`, graph keys and `--graph` output name the function, never
  the spelling the source used.

### Expressions and ordinary names

- Only the start of a statement takes a declaration. In every expression
  position `function` keeps its accepted grammar, so a name after it keeps
  raising `SyntaxError("Expected '(' but found identifier '<name>'")` at the
  name. This includes assignment values, `return`, `throw` and `delete`
  values, list items, object values, call arguments, operands, `new`,
  `typeof`, `!`, `if` conditions, `for` iterables, conditional expressions,
  quantifiers, lambdas and template interpolations.
- The headers of `while` and `suppose` are contextual: when the condition or
  premise after the word does not parse, the word is read as a name. A
  declaration after it then starts a statement, so
  `while function f() {}:` and `suppose function f() {}: n` now report the
  stray colon, `SyntaxError("Unexpected ':'")`, instead of the name.
- Anonymous literals keep their meaning wherever they appear, including as
  statements. `function` after `.` stays a property name, so
  `record.function f` reads a property and then the name `f`.

### Interactive input

- The line-oriented REPL buffers a pending input that contains `function`
  followed by a name, other than after `.`, while it has more `{` than `}`
  tokens. It keeps blank lines inside, and runs the input once the braces
  close, or at the next blank line when the input also opened a colon
  header. If the pending input does not lex, the REPL runs it at once and
  reports the error, as before.
- A declaration on one line, such as `function f(a) { return a }`, runs at
  once. The continuation prompt keeps the indentation of the line above.
- The terminal workspace submits with F5 or Ctrl-Enter, so a multi-line
  declaration needs no buffering, and Ctrl-J keeps the indentation of a
  braced header line, as for other braced input.
- Every other REPL and terminal behavior is unchanged.

## Errors

- No error type, runtime error or catch value is added. Syntax errors stop
  compilation before any statement of the program runs.
- `SyntaxError("Expected '{' but found <token>")`: the token after the
  parameter list is not `{`. It is placed at that token and uses the existing
  token descriptions, such as `'=>'`, `'->'`, `':'`, `';'`, `end of line` and
  `end of input`.
- `SyntaxError("Expected '(' but found <token>")`: the token after the name
  is not `(`, as in `function f a { ... }`, `function f { ... }`,
  `function f<T>(...)` and `function amount:`. It is placed at that token.
- The parameter list raises the diagnostics of `def`'s parenthesized list,
  such as `Expected a parameter but found <token>`,
  `Expected a type but found <token>`,
  `Expected a scalar literal parameter default`,
  `Rest parameter must be last` and the other rest diagnostics, placed as for
  `def`, which reports a parameter or type error at the token after the
  offending one.
- `SyntaxError("Unterminated block")`: the input ends inside the body, at
  the end of the input.
- `SyntaxError("Statements are nested too deeply")` and
  `SyntaxError("Expressions are nested too deeply")` still bound nesting:
  each declaration and each statement in its body pass the existing depth
  guards, so nested declarations reach the limits at the depths that nested
  `def` declarations do.
- Runtime errors are those of `def`, such as
  `ReferenceError("<name> is not defined")` for a call before the
  declaration and the existing `TypeError` for a call through a binding that
  is not a function.
- The Compatibility table lists exact former and new results.

## Reference Implementation

- `src/lang/ast/parser.rs` adds the private `FunctionSpelling` enum, `Def`
  or `Function`, beside the other shared parser types.
- `src/lang/ast/parser/function.rs`: `starts_function_declaration` holds at
  `def`, or at `function` followed by an identifier. `function_keyword` eats
  `function` or requires `def` and returns the spelling, and
  `function_name` reads the name. `function_declaration` then matches the
  spelling exhaustively: `def` keeps its unchanged `named_parameters()` and
  `named_body()`, and `function` takes the parenthesized `parameters()` and
  the braced body, through `declaration_body(spelling)`.
- `src/lang/ast/parser/statement.rs`: `statement_inner` dispatches on
  `starts_function_declaration` where it matched `def`.
  `src/lang/ast/parser/class.rs`: `class_members` uses the same guard for
  methods, and `method_declaration` reads an adopted `init`'s spelling
  through `function_keyword` and gives it the braced body for `function`.
  Every declaration and nested statement passes the existing depth guard; no
  function exceeds 60 lines, no file exceeds 500, and no `unwrap`, indexing,
  macro or dynamic dispatch is added.
- `src/continuation.rs`: `opens_function_body` lexes the pending input, and
  `Pending::accept` keeps buffering, through blank lines, while it holds.
