## Abstract

- Accepted under the automatic-acceptance rule after independent behavior,
  compatibility and development checks passed. The continuous Language
  compatibility policy categorically skips token comparison.
- Add Rust's `starts_with(prefix)` and `ends_with(suffix)` names to string
  receivers as exact aliases of accepted `startsWith(prefix)` and
  `endsWith(suffix)`. Preserve those spellings and the accepted Python
  `startswith` and `endswith` aliases.
- Reuse the existing query arms, argument evaluation, conversion to text,
  boolean results, live dependencies and written call rendering. Only these
  formerly unsupported string calls change. Other receivers, user-defined
  methods, property reads and existing errors retain their meanings.
- No Rust pattern traits, start/end positions, static string calls, new
  keywords, syntax, token kinds, public types or configuration are added.
  These are familiar names for Nucleoid's accepted operations, not a claim
  of full Rust compatibility.
- This continuous cycle selected Language compatibility with one unbiased
  live-registry draw, index 4 of five eligible categories. Token comparison
  is entirely skipped for that category, not a passing gate; immutable
  accepted-source replay, independent behavior, compatibility, development
  checks and every automatic-acceptance hard criterion remain required.

## Motivation

- Rust programmers and language models commonly write
  `name.starts_with("pre")` and `name.ends_with(".csv")`. The accepted
  string-method dispatch rejects these names despite implementing the same
  literal-prefix and literal-suffix operations under other spellings.
- Adding the two snake-case names advances the language-superset aspiration
  without reserving identifiers or changing accepted operations. Sharing the
  existing implementation avoids a second matcher or different coercions.
- Keep this bounded family separate from accepted NUC 110's Python names,
  NUC 118's case-conversion aliases and accepted NUC 131's reversal aliases.
  Preserve NUC 131 unchanged; no pending proposal is a dependency.

## Specification

- The authoritative contract is
  [Rust string boundary method aliases](../nucleoid.spec.md#rust-string-boundary-method-aliases).
- On string receivers, `TEXT.starts_with(prefix)` dispatches to the same
  query arm as `TEXT.startsWith(prefix)` and `TEXT.startswith(prefix)`;
  `TEXT.ends_with(suffix)` dispatches to the same arm as
  `TEXT.endsWith(suffix)` and `TEXT.endswith(suffix)`.
- The first argument converts with the accepted Nucleoid text conversion.
  Matching is literal and case-sensitive, without Unicode normalization;
  empty affixes match empty strings. Numbers and booleans test their text,
  `null` tests `"null"` and a missing argument tests `"undefined"`.
  A list tests its comma-joined text, not alternatives.
- The runtime evaluates the receiver first and every argument once, left
  to right. Further arguments are evaluated and ignored, not positions.
  An argument's error propagates before matching. A null or undefined
  receiver stays undefined without evaluating arguments.
- Standing declarations and class-level rules retain all accepted
  dependencies, including ignored arguments, in written evaluation order.
  Rules follow receiver and affix changes, and errors roll back the
  triggering update or transaction using the existing machinery.
- Statements, `why`, `affects`, graph keys and CLI graph output retain the
  call as written. Names are not normalized in the syntax tree.
- Only the two formerly unsupported string-call names change, including
  programs that caught those errors. Every old alias and every other
  receiver, property, user function and method keeps its routing.
  Reading `text.starts_with` or `text.ends_with` without a call stays
  undefined; static `String` methods and assignment behavior do not change.
- Rust's familiar names do not introduce its `Pattern` traits, character
  type, static type checking or arity rules. Nucleoid's conversions,
  missing arguments and ignored extra arguments remain deliberate
  differences, not full Rust compatibility.
- The root entries `Nucleoid tests string boundaries with Rust spellings`
  and `Nucleoid keeps Rust boundary rules live and rolls back failed
  receiver updates` specify the direct results, liveness and rollback.
  The first includes this Unicode and conversion example:

```
text = "café.csv"
assert([text.starts_with("café"), text.ends_with(".csv")], [true, true])
assert([text.starts_with("Café"), text.ends_with("CSV")], [false, false])
assert(["".starts_with(""), "".ends_with("")], [true, true])
assert(["é".starts_with("é"), "é".ends_with("é")], [false, false])
assert(["12 notes".starts_with(12), "flagtrue".ends_with(true), "null notes".starts_with(null)], [true, true, true])
assert(["undefined notes".starts_with(), "notesundefined".ends_with()], [true, true])
assert(["notes.csv".ends_with([".csv", ".txt"]), "notes.csv,.txt".ends_with([".csv", ".txt"])], [false, true])
assert(["abc".starts_with("b", 1), "abc".ends_with("b", 0, 2)], [false, false])
[text.starts_with("café"), text.ends_with(".csv")]
```

## Errors

- No new error kind or message format is introduced. On strings, the
  former `TypeError("<text>.starts_with is not a function")` and
  `TypeError("<text>.ends_with is not a function")` become boolean results
  after the same argument evaluation; argument errors still propagate.
- Non-string routing retains its existing diagnostics, for example
  `(5).starts_with("5")` raises
  `TypeError("number.starts_with is not a function")`, and
  `xs.ends_with("x")` on a list raises
  `TypeError("xs.ends_with is not a function")`.
- `String.starts_with("x")` and `String.ends_with("x")` retain
  `TypeError("String.starts_with is not a function")` and
  `TypeError("String.ends_with is not a function")`.
- Assignments to string members retain
  `TypeError("Cannot assign 'starts_with' on string")` and
  `TypeError("Cannot assign 'ends_with' on string")`.
- A missing argument is not an error. Null or undefined receivers keep
  their undefined result. A missing argument expression, such as the
  unbound identifier `missing`, retains
  `ReferenceError("missing is not defined")`.
- Existing statement-start positions and plain/JSON error formatting are
  unchanged.
