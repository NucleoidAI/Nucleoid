# NUC 83 -- Hypothetical Difference Selections

```

Title: Hypothetical Difference Selections
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Reasoning enhancement
Created: 05-Nov-2026
Requires: 8, 12, 14, 45, 48, 57, 59, 62, 65, 82
```

## Abstract

- Add the pipeline stage `SELECTION |> diff`. Inside a `suppose` block it
  keeps the steps of `SELECTION` whose node did not exist when the innermost
  running block began, its premise included, or whose value differs from the
  value the node held then. It keeps them in their order with every field
  unchanged, so `suppose reading = 95: model |> diff` lists the reading and
  the alarm it trips, and `alarm |> why |> diff` the changed facts behind the
  alarm.
- Values compare as a write compares the value it stores with the one it
  replaces, the rule that decides whether the write propagates: numbers by
  value and sign with `NaN` equal to `NaN`; strings, booleans, `null`, dates,
  regular expressions and class values by value; lists item by item; and
  objects, instances and function values by identity. Classes, named
  functions, conditions and blocks hold `null` in a step, so only their
  appearance counts.
- The values a block began with are read from the undo records the
  transaction already keeps since the block's savepoint, which hold the first
  value of every slot the block wrote. No snapshot, copy or per-write work is
  added: a block only pushes its savepoint mark when it starts and pops it
  when it ends.
- Evaluating the stage when no block is running raises
  `TypeError("Cannot use 'diff' outside suppose")` at the running statement.
  Running is dynamic: a function, method or lambda called inside a block may
  use the stage, and a nested block compares with its own start. A binding
  named `diff` shadows the stage, as bindings shadow NUC 48's `stated` and
  `derived` and NUC 82's `depth`.
- No keyword, token or error type is added. Every accepted program keeps its
  parse and behavior; only inputs that were errors at the accepted revision
  change. The public `Stage` enum gains `Stage::Diff`, which needs human
  SemVer review. No project version is changed. The authoritative contract is
  [Hypothetical differences](../nucleoid.spec.md#hypothetical-differences).
- **Outcome: Accepted.** The independent evaluation and the caller's
  integrated-tree checks passed all three hard criteria, and the independent
  evaluator decided Accepted. The required token comparison ran in
  continuous mode: 11 cases use fewer tokens, 948 the same and none more. No
  policy check failed. The evaluation adds one cost that the Cost section
  does not state: a standing selection that holds `model |> diff` re-derives
  on every write in its block and rereads the block's growing undo records
  each time, so such a block grows about 6 to 15 times per doubling of its
  writes, while a single question stays linear.

## Motivation

- Draft [NUC 11](nuc-0011.md) motivates its hypotheticals with "An LLM
  proposing a change needs to know what the change would do before committing
  it". [NUC 65](nuc-0065.md) accepted `suppose`, which answers that only for
  the nodes a question names: `suppose price = 20: total` reports the total
  and nothing else.
- What a change would do is the set of nodes it moves. A model that an LLM
  maintains holds many more nodes than any question names, and a changed
  premise reaches some of them through rules nobody remembers writing: a
  class-level rule, a population count, a derived label. Naming them in
  advance means knowing the answer before asking.
- Accepted Nucleoid can only spell the answer with a snapshot taken before
  every block and a comparison inside it,
  `snap = (model |> why).value` followed by
  `(model |> why).filter(s -> all b in snap: b.node != s.node or b.holds != s.holds)`,
  38 lexer tokens more than `model |> diff` for one question, and one more
  snapshot for each block. The spelling is also wrong in ways a model cannot
  see:
  - loose `!=` coerces, so `1` and `"1"`, `0` and `false`, or `[5]` and `5`
    count as unchanged, and it never equates `NaN` or a function value with
    itself, so an unchanged lambda is always listed;
  - `!==` counts `0` turning into `-0` as unchanged, although the runtime
    propagates that write as a change;
  - in a standing declaration, any step that holds `null`, as every class and
    named function does, makes the whole selection `null` by the accepted
    null-read rule, unless every read of `holds` is wrapped in `.value`;
  - `model |> diff |> affects`, what rests on anything the change moved, has
    no general accepted spelling, because `affects` takes references and a
    filtered list is not one.
- NUC 11's roadmap plans "Hypotheticals -- `suppose`, `diff` and freezing" as
  its sixth stage. NUC 65 accepted `suppose` and freezing and left `diff`
  out; this NUC specifies that one stage on its own.
- Each of the eleven new cases uses 38 to 101 fewer lexer tokens than the
  most compact behavior-equivalent accepted program found for it.

## Rationale

- **Category and selection.** The caller selected Reasoning enhancement by one
  tool-backed uniform draw over the five categories NUC 1's registry marks
  eligible for automatic selection: index 3 with probability 1/5 and no
  redraw, in continuous mode. Within it the caller chose NUC 11's planned
  `diff`: the remaining part of NUC 11's sixth stage, bounded, a filter like
  NUC 48's state filters and NUC 82's `depth`, and a parse error today that no
  test pins. The category's token gate therefore applies; runtime
  applicability does not.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **A filter stage.** `diff` narrows a selection, as `stated`, `derived` and
  `depth` do, so it is a pipeline stage that composes with every other stage
  and keeps its source's order and fields. `model |> diff` is NUC 11's bare
  `diff`.
  - Rejected: NUC 11's bare `diff`. A bare name is an ordinary identifier,
    and `suppose a = 2: diff` is accepted input that raises
    `ReferenceError("diff is not defined")`; NUC 65's compatibility table
    lists it. Keeping that input costs the two tokens of `model |>`.
  - Rejected: a prefix form `diff x`, which is two juxtaposed statements
    today and keeps that meaning.
  - Rejected: NUC 11's `before` and `after` fields. Every stage returns steps
    of one shape, which is what lets `diff` stand anywhere in a pipeline:
    `model |> diff |> affects` walks on from the changed nodes, and the walk's
    steps would lose a `before` again. `after` is `holds`, and the value a
    node had before a block is what it holds once the block has rolled back.
- **The innermost running block.** A comparison needs one reference world,
  and the innermost running block is the world a question asked inside it is
  about: an outer block's changes are part of the inner world already.
  Running is dynamic, so a function, method or lambda defined anywhere and
  called inside a block compares with that block.
  - Rejected: the block that lexically encloses the stage, which would make a
    function that asks for a diff useless, and would need every reasoning
    observer to remember the block it was declared in.
  - Consequence: a standing selection is evaluated again when its source
    changes, as every standing selection is. Entering a nested block is not
    such a change, so a selection declared in an outer block keeps its value
    until something it observes changes inside the nested block; from then
    until the nested block rolls back, it compares with the nested block's
    start.
- **The runtime's change rule.** NUC 11 compares values. The runtime already
  decides, on every write, whether the stored value differs from the value it
  replaces, and only a difference propagates (`Value::same_value`). Using
  that rule lists a node exactly when writing its current value over its
  block-start value would count as a change.
  - Rejected: language `==`, which coerces between types and never equates
    `NaN` or a function value with itself.
  - Rejected: `===`, which treats `-0` as `0` although a write of `-0` over
    `0` propagates, and never equates `NaN`.
  - Rejected: listing every node written inside the block. An equal-valued
    write, a value restored before the stage runs, or a rule rewritten to the
    same value is a write the undo log records, but not a difference the
    question asks about.
- **Values for lists, identity for objects.** A list is a value: `push`
  stores a new list, so a list mutated in place differs and one restored by
  `pop` does not. An object, an instance or a function value is a reference.
  A step for an instance holds the instance, whose properties are nodes of
  their own, so each changed property is listed on its own and the instance
  is not listed again because of them. A new object with equal entries is a
  different object, as it is for propagation.
- **What existed.** A node that the model did not hold when the block began
  is new. Selections list the model's nodes, so the comparison uses the same
  membership as `model`:
  - a placeholder for a name read before its definition did not exist: under
    `$Item.total = $Item.price * 2`, an item's `price` that only the rule has
    read is new when the block first defines it;
  - a reasoning observer did not exist either, so `t = why a` redeclared in
    the block as an ordinary `t = t.value` is new, although it holds the same
    list;
  - a node the block deletes cannot appear, because a filter only keeps steps
    that exist.
  - Rejected: existence in the graph alone, which would leave out the
    redeclared observer above although it joined the model in the block.
- **The block start from the undo log.** A `suppose` block runs on a
  transaction savepoint, and opening a savepoint makes the transaction record
  the first write of every slot again. The first undo record of each slot
  after the block's mark therefore holds what the slot held when the block
  began. Records that a later `try` savepoint makes come after it, and a
  caught failure removes the records its body wrote, so undone writes leave
  nothing behind. One pass over those records builds a map, and each step is
  looked up once:
  - variables, including instances held by variables, and lists held by
    variables: the first `Variable` record;
  - properties, including lists held by properties: the first `Property` or
    `PropertyRemoved` record of the property, or the first `Object` record of
    its object, whichever comes first, because creating or re-creating an
    object writes its whole property map at once;
  - whether a node existed and of which kind: the first `Node` record, which
    covers new, deleted, re-created and redeclared nodes and placeholders,
    and whose statement tells whether the node was a reasoning declaration;
  - whether a node observed the graph's shape, which also makes it a
    reasoning observer: for each of its subscriptions to a node or to the
    model, the first `ShapeDependentAdded` or `ShapeDependentRemoved` record,
    because a subscription that the block removed was there when it began
    and one it added was not;
  - classes, named functions, conditions and blocks: no value record is
    needed, because their steps hold `null`.
  - Rejected: a snapshot at block entry, which every block would pay for
    whether or not it asks.
  - Rejected: recording writes per block, which would add work to every
    write in every program.
- **Outside a block is an error.** Without a running block there is nothing
  to compare with, and an empty selection would claim that nothing changed.
  The error is a `TypeError`, not NUC 11's `SyntaxError`: whether a block is
  running is known only at run time, and the same function may be called
  inside a block and outside one, so the source is well formed either way.
  The accepted runtime raises `TypeError` when an operation cannot apply where
  it is used, as `TypeError("diff is not an operation")` and
  `TypeError("suppose has no value")` do. The message is NUC 11's.
- **Bindings shadow the stage.** A local or parameter, state variable,
  function or class named `diff` makes the stage raise
  `TypeError("diff is not an operation")`, as NUC 48 does for `stated` and
  `derived` and NUC 82 for `depth`, rather than ignoring the binding as `why`
  and `affects` do. `diff` is a common name for the difference of two
  numbers, and a model that defines its own `diff` never has it silently
  replaced by the stage. The cost is that such a program cannot use the
  stage until the binding is renamed.
- **Observations as for filters.** The stage keeps every value and structural
  observation its source made, including those of the steps it drops. Its
  other input, the world the block began with, does not change while the
  block runs, so the source's observations are all a standing selection
  needs.
- **Distances kept.** The stage keeps the NUC 82 distances of the steps it
  keeps, as `stated`, `derived` and `depth` do, so it composes with `depth` in
  either order.
- **Programs without the stage are untouched.** Parsing changes only after
  `|>` followed by the name `diff`, and every program with those tokens was a
  parse error. At run time, a block pushes its savepoint mark on a stack when
  it starts and pops it when it ends; nothing else runs unless the stage is
  evaluated.
- **Not added.** NUC 11's bare `diff`, its `before` and `after` fields and its
  re-evaluation order, a prefix or call form, comparison with an outer block,
  a step field that tells new nodes from changed ones, the list of nodes a
  block removed, and live hypotheticals.

### Departures from Draft NUC 11

- NUC 11's `diff` is a bare selection. Here it is the stage
  `SELECTION |> diff`, and `model |> diff` selects what NUC 11's bare `diff`
  does, so NUC 11's `fallout = suppose reading = 95: diff |> affects` is
  `fallout = suppose reading = 95: model |> diff |> affects`.
- NUC 11 lists nodes "in the order they were re-evaluated". Here the stage
  keeps its source's order, which for `model` is the model's order.
- NUC 11 adds `before` and `after` to each step. They are not added.
- NUC 11 selects the nodes whose values differ from the enclosing world. Here
  it also selects the nodes the block added, the enclosing world is the
  innermost running block's start with its premise included, and values
  compare by the runtime's change rule.
- NUC 11 raises `SyntaxError("Cannot use 'diff' outside suppose")`. Here the
  same message is a `TypeError` raised at run time, because a function that
  uses the stage may run inside a block or outside one.
- NUC 11 makes stage names lose to variables of the same name. Here every
  binding shadows the stage, as for NUC 48's filters and NUC 82's `depth`.
- NUC 11 itself is not edited and remains Draft.

## Specification

### Syntax

- `SELECTION |> diff` is a pipeline stage: `|>` followed by the identifier
  `diff`, with no argument. It takes part in the pipeline as `stated` and
  `derived` do: it binds at the precedence of `|>`, may be followed by
  further stages, and may follow a prefix stage, so `why c |> diff` is
  `(why c) |> diff`.
- `c |> diff(1)` is the stage followed by the juxtaposed statement `(1)`, as
  `c |> why(1)` is, and `c |> diff()` reports the `SyntaxError` of `()`.
- Everywhere else `diff` is an ordinary identifier. There is no prefix form,
  so `diff c` is two juxtaposed statements; `diff(c)` is an ordinary call;
  `c.diff` and `{diff: 1}` are a property and a key; and a bare `diff`,
  including `suppose a = 2: diff`, raises
  `ReferenceError("diff is not defined")` when nothing of that name exists.
- The stage parses to `Expr::Reason { stage: Stage::Diff, source }`, with the
  new public variant `Stage::Diff`. `Stage::from_name`, which names the
  stages that have a prefix form, does not know `diff`, so prefix stages are
  unchanged.

### Selection

- Inside a running `suppose` block, the stage evaluates its source selection
  and keeps the steps whose node did not exist when the innermost running
  block began, or whose value differs from the value the node held then. It
  keeps them in their order with their `node`, `holds`, `rule`, `state` and
  `from` fields unchanged.
- The block began before its premise ran, so a premise's changes are
  differences.
- A node existed when the block began if the model held it then. The
  placeholder of a name read before its definition and a reasoning observer,
  which no selection lists, did not exist, so a property first defined in the
  block under a rule that already read it is new, and so is a former
  reasoning declaration redeclared there as an ordinary one. A property that a
  statement declares inside the block is new, even when an object literal
  already held that value.
- A node removed inside the block cannot appear, because the stage only keeps
  steps that exist.
- `model |> diff` lists every node the block added or changed, in the model's
  order. `alarm |> why |> diff` lists the changed steps of an explanation,
  `price |> affects |> diff` the changed steps of an impact, and
  `model |> diff |> affects` everything that rests on a change.

```
threshold = 90
reading = 40
alarm = reading > threshold
level = reading > 10
suppose reading = 95:
    moved = model |> diff
    assert(moved.map(s -> s.node), ["reading", "alarm"])
    threshold = 99
    assert(moved.map(s -> s.node), ["threshold", "reading"])
```

### Values

- The value a node held is what its step holds: the value of a variable,
  including an instance or a list it holds, the value of a property, and
  `null` for classes, named functions, conditions and blocks, which
  therefore count only when they are new.
- Values compare as a write compares the value it stores with the one it
  replaces, which is what decides whether the write propagates:
  - numbers are the same when they are equal and have the same sign, and
    `NaN` is the same as `NaN`, so `-0` differs from `0`;
  - strings, booleans, `null`, dates and class values compare by value, and
    regular expressions by their pattern;
  - lists are the same when they have the same length and the same items in
    order under this rule, so a list mutated in place, as by `push`, differs
    and a list restored, as by `pop`, does not;
  - objects, instances and function values are the same only when they are
    the same object or function. An instance whose properties change is not
    listed, while each changed property is, and a new object with equal
    entries differs.
- An equal-valued write, a value restored before the stage runs, a rule
  rewritten to give the same value, a node deleted and declared again with
  the value it had, and a write undone by a caught failure are not
  differences.

```
a = 1
b = a + 1
c = b * 2
suppose a = 1:
    moved = model |> diff
    b = 1 + a
    delete c
    c = b * 2
    assert(moved, [])
    a = 3
    assert(moved.map(s -> s.node), ["a", "b", "c"])
```

### The running block

- The innermost running block is the one whose premise or suite is running
  when the stage is evaluated: directly, in a function, method or lambda
  called there, or in a rule that propagation evaluates there.
- `try` savepoints inside the block do not change it. A nested block
  compares with its own start, and when it rolls back, the enclosing block is
  the running one again.
- Each evaluation compares with the block running when it happens. A
  standing selection declared in an outer block that re-derives inside a
  nested block therefore compares with the nested block's start, until the
  nested block rolls back and restores its outer value.
- Evaluating the stage when no `suppose` block is running raises
  `TypeError("Cannot use 'diff' outside suppose")`, positioned at the running
  top-level statement, and rolls back that statement's transaction. The error
  is raised when the stage applies, after its source has been selected and
  the stages before it have applied.
- A declaration, class-level rule, condition or function that holds the
  stage can therefore only be evaluated inside a block. Outside one, its
  evaluation raises and rolls back the statement that triggered it, such as
  the creation of an instance whose class-level rule holds the stage.

```
class Tank(level):
    this.level = level
    def changed() => (model |> diff).map(s -> s.node)
low = 10
tank = Tank(5)
empty = tank.level < low
suppose tank.level = 20:
    assert(tank.changed(), ["tank.level", "empty"])
```

### Bindings and sources

- Before its source is selected, the stage checks for a local or parameter,
  state variable, function or class named `diff` and, when one exists,
  raises `TypeError("diff is not an operation")` at the running statement.
  Function and method parameters, lambda and arrow parameters, loop
  variables, quantifier binders and block locals are all bindings.
- A binding declared after a standing selection makes that selection's next
  evaluation raise, so the statement that triggered the refresh fails and
  rolls back, as for the accepted state filters.
- The checks of a pipeline's stages run from the outermost stage inward,
  then the source is selected, then the stages apply from the innermost
  outward. Accepted pipelines keep this order.
- An invalid source keeps its accepted diagnostic and is reported first,
  inside a block or not: `1 |> diff` raises `TypeError("Cannot explain 1")`
  and `missing |> diff` raises `ReferenceError("missing is not defined")`.
- The accepted shadowing of `why` and `affects`, which ignore bindings, and
  of `stated`, `derived` and `depth`, which a binding shadows, is unchanged.

### Observation, liveness and transactions

- The stage keeps every value and structural observation its source
  selection made, including those of the steps it drops, so a standing
  selection inside a block re-derives when its source does, and a dropped
  step joins it once that node changes.
- An expression that contains the stage is a reasoning expression: a
  declaration, property, class-level rule, condition or quantifier holding it
  is a reasoning observer that walks neither select nor traverse and that
  `model` excludes. Functions, methods and lambdas evaluate it in place, and
  class-level rules give each instance its own selection.
- `.value` snapshots a selection as for the accepted stages, and a selection
  that leaves the block is plain data, as NUC 65 specifies.
- The stage keeps the distances of the steps it keeps, so
  `c |> why |> diff |> depth(1)` and `c |> why |> depth(1) |> diff` select
  the same steps.
- Propagation order, caught failures, nested blocks and failed statements
  behave as for the accepted stages: rollback restores selections,
  observations and queued refreshes.

### Cost

- Programs that never evaluate the stage do no work for it beyond pushing a
  block's savepoint mark on a stack when the block starts and popping it when
  the block ends.
- Each evaluation of the stage reads the transaction's undo records since
  the innermost running block's mark once, keeping the first record of each
  slot in a map, and then looks up each step of its source once, so it takes
  time linear in those records and those steps.

### Rendering

- The stage renders as `SOURCE|>diff` in graph keys, block keys, conditions
  and `rule` text, with its source rendered once, so rendered size stays
  linear: each chained `|> diff` adds exactly the six characters of `|>diff`.
- The rendering parses back to the same expression, as `model|>diff`,
  `c|>why|>diff|>depth(1)|>diff` and `(any s in model|>diff:s.node=="a")` do,
  except where the accepted renderer already abbreviates part of it: a member
  or index access on a pipeline renders without its parentheses, as

## Reference Implementation

- `src/reasoning.rs`: the public variant `Stage::Diff`, which `as_str` names
  `diff` and `Stage::from_name` does not know, so no prefix form exists.
  The crate-private `apply_stage` and `apply_ranked` return a `Result`. For
  `Stage::Diff` they take the innermost running block's origin from the
  private `Runtime::origin`, which returns
  `TypeError("Cannot use 'diff' outside suppose")` when no block is running,
  and keep the steps that `changed` marks: the plain path filters the steps,
  and the ranked path uses the existing `Ranked::retained`, so distances are
  kept. `start_kind` gives the kind a node had when the block began, from
  the origin's first `Node` record, or from the graph when the node has no
  record, and gives nothing for a missing node, a placeholder, a reasoning
  declaration or a node that observed the graph's shape, which are new.
  `changed` then compares the block-start value that `held` gives for that
  kind with `Value::same_value`.
- `src/transaction.rs`: `Transaction` gains the private stack `hypotheses`,
  with the module-private `begin_hypothesis` and `end_hypothesis`, which
  debug-asserts that it closes the innermost block, and the crate-private
  `hypotheses`. The crate-private `Runtime::hypothesis_savepoint` takes a
  savepoint and begins a hypothesis at its mark, and
  `Runtime::rollback_hypothesis` ends that hypothesis and rolls back to the
  savepoint, so no other code reads a savepoint's mark. `Transaction::origin`
  reads the undo records since the innermost mark once into the
  crate-private `Origin`: the first record of each variable, property,
  object and node key, the first record of each structural subscription to
  the graph's shape, and from those the nodes that observed the graph when
  the block began. Its lookups return the crate-private `Start`, which tells
  an untouched slot from one that was absent or held a value, and pick a
  property's own record or its object's, whichever came first.
- `src/graph.rs`: `ShapeKey::observes_graph` becomes crate-visible.
- `src/nuc/suppose.rs`: `Runtime::suppose` takes its savepoint with
  `hypothesis_savepoint` and rolls back with `rollback_hypothesis`. Nothing

  hypothesis: a normal end, a `return`, an error or a thrown value in the
