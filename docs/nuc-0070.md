# NUC 70 -- Object Entry Loops

```

Author: Claude <noreply@anthropic.com>

Type: Standards Track
Category: Runtime features
Created: 31-Oct-2026
Requires: 8, 31, 45, 51, 57, 60, 61, 68
```

## Abstract

- Adds loops over an object's entries: `for KEY, VALUE of SOURCE:` and its
  `in` spelling `for KEY, VALUE in SOURCE:`, with every suite the
  single-name loop accepts.
- The body runs once for each entry the object holds, in insertion order,
  with `KEY` bound to the entry's key and `VALUE` to its value. An instance
  lists its `id` first, then its fields in the order they were stored.
- `SOURCE` is evaluated once, before the names are bound, and the entries,
  keys and values, are snapshotted before the first body runs. The loop is
  one-shot and imperative, exactly like the single-name loop: the same
  scopes, receivers, returns, rollback and propagation.
- Every source that is not an object raises
  `TypeError("<source> is not an object")`. Single-name loops are unchanged,
  including `TypeError("<name> is not iterable")` for objects.
- Taking the snapshot records no dependency of its own, as the class, list
  and string snapshots already do.
- No keyword, token or error type is added. The public `Stmt` enum gains the
  variant `Stmt::ForEntries { key, value, iterable, body }` and the public
  `nuc::r#for::For` struct the field `value: Option<String>`. Both need human
  SemVer review; no project version is changed.
- The accepted contract is the
  [object entry loops with ordered rollback](../nucleoid.spec.md#object-entry-loops-with-ordered-rollback)
  section that [NUC 72](nuc-0072.md) added; this NUC's own isolated
  `Object entry loops` section was not integrated.
- Automatic-Accepted on 01-Nov-2026 under the automatic acceptance rule. Its
  frozen candidate met every hard criterion, but its policy check failed:
  independent evaluation rejected it because undoing a deletion re-inserts the
  key at the end of the object, so a rolled-back `delete` changes the order an
  entry loop sees. After `o = {a: 1, b: 2, c: 3}`, a `try` whose loop runs
  `delete o.a` and then throws leaves `for k, v of o:` visiting `b`, `c`, `a`,
  and a `suppose` block that deletes `o.a` does the same. Its loops are part
  of the accepted language through NUC 72, which integrated this NUC's loop
  code unchanged together with order-preserving rollback that removes the
  defect, so no separate code was integrated for this NUC.

## Motivation

- A world model keeps records: a price table, the stock of each item, the
  sales of each region, the fields of an instance. Acting on every entry of
  one, by seeding instances from a table, totalling it, copying an instance
  into facts or checking every field, needs each key together with its
  value.
- Accepted Nucleoid cannot iterate an object's entries. A single-name loop
  raises `TypeError("rec is not iterable")` for an object, `Object.keys`,
  `Object.entries` and `JSON` are not defined, `"a" in rec` raises
  `SyntaxError("Unexpected keyword 'in'")`, and `rec.keys()` is undefined.
  `rec[k]` reads a computed key, but `rec[k] = 5` raises
  `SyntaxError("Cannot assign to rec[k]")`, so every key of every object
  comes from the program's text.
- The accepted spellings therefore name every key by hand, for example
  `"rice oil salt".split(" ").map(name -> Item(shelf, name, table[name]))`,
  and they break down exactly where a world model needs to be general:
  - a lambda sees neither the enclosing function's parameters nor `this`:
    `def f(r) => ["a"].map(k -> r[k])` raises
    `ReferenceError("r is not defined")`, so functions and methods first copy
    them with `cur := r` and `me := this`;
  - a function that receives different tables needs a key list for each
    call, or a dispatch on the table's contents when the calls are written
    inside assertions;
  - deleting a property and assigning it again moves it to the end of the
    object, and a hand-written key list does not follow;
  - a statement inside a `map` callback is filed as a standing declaration
    and runs again when the record changes, failing with
    `ReferenceError("k is not defined")`, unless it is written with `:=` or
    as an expression;
  - inside a standing `if`, a key-list loop reads every entry, so changing
    any of them runs the branch's actions again unless each read is wrapped
    in `.value`.
- The graph reflection channel `model |> why` lists the property
  declarations the graph holds, not the entries an object holds. It misses
  the entries of object literals, every instance's `id` and properties
  written inside loops, branches and blocks, and it follows graph order.
- Python's `for key, value in record.items():`, JavaScript's
  `for (const [key, value] of Object.entries(record))`, Go's
  `for key, value := range record` and Kotlin's
  `for ((key, value) in record)` all name both parts of each entry, and LLMs
  write them constantly. In accepted Nucleoid each raises a syntax error;
  `for key, value of record:` raises
  `SyntaxError("Expected 'of' in for statement")` at the comma.
- Each of the eleven new cases uses 15 to 34 fewer lexer tokens than the
  most compact behavior-equivalent accepted program found for it.

## Rationale

- **Category and applicability.** The caller selected Runtime features by one
  uniform draw over the four eligible registry categories, index 1 with
  probability 1/4 and no redraw, in continuous mode. Runtime applicability
  is `existing_comparable`: `for` loops exist, and because every key comes
  from the program's text, every case can be written in accepted syntax with
  hand-written key lists or direct property reads. The graph reflection
  channel also lists filed property declarations. The token non-regression
  gate therefore applies, and each new case is paired with the most compact
  accepted counterpart found, recorded in the evaluation baseline.
- **Two names after `for`.** A header is a two-name header exactly when `for`
  is followed by a name, a comma, a name and `of` or `in`. Nothing else
  commits to the new form, so every other input keeps its accepted parse
  and diagnostic, including `for values, other:` and `for t := "ab": pass`.
  The source and the suite are parsed exactly as for the explicit
  single-name loop. Rejected: parenthesized or bracketed patterns such as
  `for (key, value) of` and `for [key, value] of`, which read as
  destructuring, rejected in [NUC 67](nuc-0067.md), and collide with
  parenthesized sources; `for (values):` keeps its accepted diagnostic.
- **Objects only.** The two-name form iterates entries, and only objects have
  entries: object literals, instances and any other object value, such as
  the step objects `why` returns. Every other source raises
  `TypeError("<source> is not an object")`, rendering the source as the
  single-name loop renders it in `is not iterable`. The single-name message
  does not fit: lists, strings and classes are iterable by the single-name
  loop. Rejected: index and item pairs for lists, as in JavaScript's
  `entries()` and Python's `enumerate`, a separate feature that would also
  have to settle the single-name loop's rule of visiting only registered
  instances in a list.
- **Entries as the object holds them.** The loop lists exactly the entries
  that `--json` and deep equality see, in the object's insertion order:
  - an object literal's keys as written, later properties appended when they
    are first assigned, deleted properties gone, and a property deleted and
    assigned again moved to the end;
  - an instance's `id` first, because every instance stores it and
    `assert(p, {id: "p", x: 1})` compares it, then the properties its
    constructor assigns, those its class-level rules derive and those
    assigned later, in the order they were first stored;
  - `null` values, which are entries;
  - but not a literal slot whose value is undefined, such as `a` in
    `{a: none.x}` when `none.x` was never set, which deep equality and JSON
    serialization already skip.
- Rejected: sorting keys, as Go's maps encourage and as the JSON output
  shows, which would lose the order the world model built.
- **A full snapshot.** All entries, keys and values, are captured before the
  first body runs, as the string loop captures every character and the class
  loop every instance. Entries the body adds are not visited, entries it
  deletes are still visited with their snapshotted values, and the value
  binding keeps its snapshotted value, while `SOURCE[KEY]` reads the current
  one. Rejected: reading each value when its iteration starts, which makes a
  deleted entry undefined halfway through, and Python's error for a record
  that changes size, which no accepted loop raises.
- **The same loop.** The `For` node gains one optional field. Each iteration
  pushes a scope, declares the key, a string, and the value, enters
  imperative mode and runs the body, exactly as a single-name iteration
  does, so receivers, returns, rollback and propagation are shared rather
  than restated. When both names are the same, the value is bound, as
  `def f(a, a)` binds its last argument.
- **No dependency of its own.** Taking the snapshot reads the object's
  entries directly, as the class, list and string snapshots read theirs, and
  records nothing; evaluating `SOURCE` records its reads as usual. A loop is
  an action. Inside a standing `if` branch or a block it runs whenever the
  branch or block runs, and replacing the binding `SOURCE` reads runs it
  again, but changing or adding an entry does not. Rejected: tracking each
  entry the snapshot reads, which would make a standing branch take its
  actions again whenever any value of its record changed, the trap
  [NUC 66](nuc-0066.md) describes for actions written as laws, while still
  missing added entries.
- **Rendering stays linear.** Graph and block keys render the header once as
  `for KEY,VALUE of SOURCE`, with the body omitted, as they render the
  single-name loop, and default-bearing declarations render its suite form.
  Nothing is copied: the source is evaluated once per run and the snapshot
  is linear in the number of entries.
- **A syntax-tree variant and a node field.** A two-name loop parses to the
  new variant `Stmt::ForEntries { key, value, iterable, body }`, and a
  single-name loop keeps `Stmt::For` exactly as it was. Every accepted
  program therefore keeps a byte-identical syntax tree, including the derived
  `Debug` text that the historical regression seals in `tests/flat_map.rs`,
  `tests/math_remap.rs` and `tests/replace_all.rs` hash. Both kinds run
  through the existing `For` node, which gains `value: Option<String>`, so
  the loop machinery is shared and `Nuc` gains no variant. Exhaustive matches
  on `Stmt` must add the variant; in this repository that is the shared
  helper `tests/common/assertions.rs`, which walks two-name bodies as it walks
  single-name ones. Rejected: an optional field on `Stmt::For`, which changed
  the `Debug` text of every historical loop, failed those three seals, and
  broke the one full `Stmt::For` pattern in
  `tests/implicit_iterator_loops.rs`.
- **Not added.** Index and item pairs over lists, strings or classes,
  `Object.keys`, `Object.values`, `Object.entries`, computed property
  writes, destructuring patterns, three or more names, colon-free, implicit
  or parenthesized two-name forms, sorted iteration and standing loops.

### Counterparts

- Every new case is paired with the most compact behavior-equivalent
  accepted program found: the same canonical assertions in the same order
  and the same expected return, executed by the accepted runtime with every
  assertion running.
- A counterpart keeps every other statement of its case and replaces each
  entry loop by accepted code that enumerates the same keys and reads each
  value from the record at run time:
  - hand-written key lists, written as one string and split, such as
    `"rice oil salt".split(" ")`, which costs six tokens however many keys
    it names;
  - dispatch on the record's contents where calls sit inside assertions and
    cannot take a key list, such as
    `(cur.milk ? "milk eggs" : "rice oil salt").split(" ")`;
  - captures `cur := table` and `me := this` for the lambda bodies;
  - `map`, `find`, `every`, `filter` and `sum`, block arrows with `:=`,
    parenthesized compound assignments, `.value` reads in standing branches,
    throw helpers, shared key lists, juxtaposed statements, inline suites,
    direct property reads, generic nested maps, index loops over digit
    strings, the graph reflection channel and inlined calls.
- A program that copies record values into its code, or replaces a loop's
  work with results computed by hand, is not a counterpart. It no longer
  reads the data the loop reads, and under that reading every one-shot loop
  over literal data reduces to its asserted results. The accepted proposals
  compare traversal with traversal: [NUC 51](nuc-0051.md) against
  `split` and `map`, [NUC 63](nuc-0063.md) against a fixed-count loop with
  the same body, [NUC 69](nuc-0069.md) against comparing `reduce` calls.
  Writing `seen = ["c", "a", "b"]` into NUC 51's first case would have cost
  35 tokens against its 45.

## Specification

### Syntax

- `for_statement` gains the two-name header:
  `"for" NAME "," NAME ("of" | "in") expression ":" suite`.
- A header is a two-name header exactly when the tokens after `for` are an
  ordinary identifier, a comma, an ordinary identifier and the keyword `of`
  or `in`. Otherwise the accepted single-name, implicit and explicit paths
  run unchanged.
- `expression` is parsed as the single-name loop's source, and `suite` is
  any suite that loop accepts: an indented block, statements on the same
  line separated by `;`, or a braced block after the colon. There is no
  colon-free, implicit, parenthesized or three-name form.
- The statement is `Stmt::ForEntries { key: KEY, value: VALUE, iterable,
  body }`; single-name loops remain `Stmt::For { variable, iterable, body }`.

```
prices = {apple: 3, pear: 2}
prices.fig = 6
log = []
for fruit, price of prices:
    log.push(fruit + "=" + price)
for fruit, price in {kiwi: 1}: log.push(fruit + price)
```

### Sources and errors

- `SOURCE` is evaluated once, before `KEY` and `VALUE` are bound, so
  `for key, value of {key: key}:` reads the outer `key`.
- An object value has entries: an object literal, `Object()`, an instance,
  the step objects `why` and the reasoning stages return, and every other
  object.
- Every other value raises `TypeError("<source> is not an object")`, where
  `<source>` is the source expression in canonical form: a list, a class, a
  string, a number, a boolean, `null`, an undefined property, a function, a
  date and a regular expression. For example, after `xs = [1, 2]`,
  `for key, value of xs: pass` raises `TypeError("xs is not an object")`,
  and `for key, value of [1, 2]: pass` raises
  `TypeError("[1,2] is not an object")`.
- An undefined name raises `ReferenceError("<name> is not defined")`, as
  before. Both errors are positioned at the running top-level statement and
  roll back its transaction.

### Entries

- The loop visits the object's own entries in insertion order. An object
  literal holds its keys as written; a property assigned later is appended
  when it is first assigned; a deleted property is removed; a property
  deleted and assigned again is appended again.
- An instance holds `id` first, then the properties its constructor
  assigns, the properties its class-level rules derive and the properties
  assigned later, in the order each was first stored.
- An entry whose value is `null` is visited. A slot whose value is undefined
  is not an entry; only object literals hold such slots, such as `a` in
  `{a: none.x}` when `none.x` was never set. An empty object runs no body.
- The visited keys are exactly the keys of the object's JSON serialization,
  and of the deep equality `assert` uses.

```
class Room(name, width, depth):
    this.name = name
    this.width = width
    this.depth = depth
$Room.area = $Room.width * $Room.depth
lab = Room("lab", 3, 4)
lab.width = 5
delete lab.name
lab.name = "studio"
fields = []
for field, value of lab: fields.push(field + "=" + value)
assert: fields, ["id=lab", "width=5", "depth=4", "area=20", "name=studio"]
```

### Snapshot

- Every entry, key and value, is captured before the first body runs.
- Entries the body adds are not visited. Entries it deletes are still
  visited with their snapshotted values. An entry whose value it changes is
  still bound to the snapshotted value; `SOURCE[KEY]` reads the current one.
  A value that is an object is the same object, so changes made through it
  are visible.
- A later loop, or a later run of the same loop, takes a fresh snapshot.

```
bills = {rent: 900, food: 300, travel: 200}
seen = []
for bill, amount of bills:
    seen.push(bill + ":" + amount + ":" + (bills[bill] ?? "gone"))
    bills.food = 0
    delete bills.travel
    bills.fee = (bills.fee ?? 0) + 5
assert: seen, ["rent:900:900", "food:300:0", "travel:200:gone"]
```

### Iteration

- Each iteration pushes a scope, declares `KEY` as the entry's key, a
  string, and `VALUE` as its value, enters imperative mode, runs the body,
  and restores the mode and scope on completion, return or error.
- The names shadow outer names and are restored afterwards; assigning them
  in the body changes only the current iteration. When `KEY` and `VALUE` are
  the same name, the value is bound.
- An explicit or bare `return` leaves the loop and the enclosing function,
  method or block, or ends a top-level program, as from a single-name loop.
  A normally completed or empty loop yields `null`.
- Errors and thrown values in the source or the body roll back through the
  existing transaction; a caught failure restores the state from before the
  enclosing `try` body.

### Dependencies

- Taking the snapshot records no dependency of its own, as the class, list
  and string snapshots do. Evaluating `SOURCE` records its reads as usual,
  and so do the body's statements.
- A loop in a standing `if` branch, a block or a function called by a
  declaration runs whenever that branch, block or function runs. Replacing
  the binding `SOURCE` reads, such as `lights = {shed: 5}`, runs it again;
  changing or adding an entry, such as `lights.desk = 100`, does not.
- A body that reads `SOURCE[KEY]` depends on each entry it reads, as any
  property read does.

### Contexts

- **Functions and methods.** The loop sees parameters, locals and `this`, as
  a single-name loop does.
- **Constructors and class bodies.** A constructor can loop over a record
  argument, for example to create parts and count them.
- **Class-level rules.** Inside a class-level `if` or block, the loop runs
  for each instance, and `$Class` in its body is that instance.
- **`suppose` suites.** The loop runs in the hypothetical world, and its
  effects are discarded with the block.
- **`try` bodies and nesting.** Loops nest, and an inner source may be an
  outer value.

### Rendering, REPL and terminal

- Graph and block keys render the header as `for KEY,VALUE of SOURCE`,
  without the body, as they render `for NAME of SOURCE`; `in` renders as
  `of`. A block holding the loop is keyed `block(for KEY,VALUE of SOURCE)`.
- Default-bearing declarations render the suite form
  `for KEY,VALUE of SOURCE:` with its indented body, which parses back to the
  same statement.
- The native REPL buffers a header ending in `:` until a blank line and runs
  an inline loop at once, as before. Completion already offers `for`, `of`
  and `in`. Neither changes.

## Evaluation

- Independently **Rejected** on 31-Oct-2026 in continuous mode against
  accepted language revision `d1b7237301ae11baa512671de3e5aa01aeef9030` and
  its immutable 813-case baseline: the 802 accepted cases plus the eleven
  paired accepted-syntax counterparts. Re-recording the baseline in a clean
  clone with the same extra baselines gave a byte-identical artifact.
- Evaluated proposal Git blob:
  `b46208cae860a20c23d78fbe4062c32091a70487`, before this outcome metadata.
- The Runtime features category came from one uniform registry draw:
  index 1 among four eligible categories, with probability 1/4 and no
  redraw. The evaluator verified `existing_comparable`: computed writes such
  as `rec[k] = 5`, `rec["b"] = 2` and `this[k] = 1` fail with "Cannot assign
  to ...", `{[k]: 1}` and `{...a}` do not parse, and `Object` and `JSON` are
  undefined, so every key comes from program text and hand-written key lists
  are fair counterparts. The token non-regression gate was required.
- Rejection reason: undoing a deletion re-inserts the property at the end of
  the object, so a rolled-back `delete` reorders the entries an entry loop
  visits. The undo log keeps only a deleted property's old value and
  restores it with an appending insert. The evaluator reproduced it with
  the candidate binary, and the caller reproduced it again:

```
o = {a: 1, b: 2, c: 3}
before = []
for k, v of o: before.push(k)
try:
    for k, v of o:
        delete o.a
        throw "x"
catch e:
    pass
after = []
for k, v of o: after.push(k)
[before, after, o.a]
```

- That program returns `[["a","b","c"],["b","c","a"],1]`. A `suppose:`
  block that deletes `o.a` also leaves the order `b`, `c`, `a`; an instance
  whose deleted field is restored iterates `id`, `y`, `x`; and a failed
  top-level statement reorders in the same way. This contradicts the NUC's
  statements that a caught failure restores the state from before the
  enclosing `try` body, that `suppose` effects are discarded with the block
  and that instance fields come in the order each was first stored, and the
  NUC 65 guarantee that `suppose` discards everything it did. Before this
  NUC no accepted program could observe property order, so the defect stayed
  latent; entry loops are the first feature that exposes it.
