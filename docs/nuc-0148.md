Created: 25-Nov-2026
Requires: 10, 61, 63, 86, 92, 93, 97, 102, 107, 109, 115, 125, 149

## Abstract

- Two range operators build a list of consecutive integers.
  `START..<END` holds the integers from `START` up to, but not including,
  `END`, and `START..=END` holds the integers from `START` through `END`.
  After these declarations `hours` is `[9, 10, 11, 12]` and `levels` is
  `[1, 2, 3, 4, 5]`:

  ```
  first = 9
  last = 13
  hours = first..<last
  levels = 1..=5
  ```

- A range is an ordinary list value, so list methods, membership tests,
  equality, indexing and JSON output treat it as they treat a list
  literal. It is computed from its bounds each time it is evaluated: a
  declaration such as `hours = first..<last` is a standing declaration
  that follows changes of `first` and `last`, and
  `$Shift.hours = $Shift.start..<$Shift.end` is a class-level rule for
  every shift.
- Both bounds must be integers from `-9007199254740991` to
  `9007199254740991`, or the range raises
  `TypeError("Range bounds must be integers")`; an undefined bound makes
  the range undefined, which a declaration stores as `null`. A range is
  empty when `START` is not below `END` (`..<`) or is above `END` (`..=`),
  and a range of more than 100,000 items raises
  `TypeError("Range is too large")`.
- Each operator is three adjacent lexer tokens, two dots and `<` or `=`,
  which the parser reads; the lexer does not change. Both operators share
  one non-associative level between the comparisons and `+` and `-`, so
  `0..<n + 1` is `0..<(n + 1)` and `x in 1..=5` is `x in (1..=5)`.
- At the accepted revision `..<` and `..=` after an operand raise
  `SyntaxError("Expected a property but found '.'")` for the second dot,
  reported at the token after it, in statements, conditions, arguments,
  list items, object values and template interpolations alike, and a few
  forms fail elsewhere first. A
  template interpolation ignores the tokens after the expression it reads,
  so it accepts them where that expression ends before them, as after a
  pipeline stage (`` `${x |> why ..<3}` ``). Ranges are therefore read only
  in a final parse pass that runs after the whole accepted parse sequence
  fails, the newline-separated list run of [NUC 149](nuc-0149.md)
  included, so every program that the accepted parser reads keeps its parse
  and result, those included. Only programs that failed to parse change.
- A range is not read at the top level of a subscript's index, slice
  bound or step, of a `for` statement's source or of a `repeat`
  statement's count: `xs[0..<2]`, `for i in 0..<3:` and `repeat 0..<3:`
  keep their syntax errors, which leaves those readings open. A bare
  `a..b`, a three-dot `a...b`, a range without an operand, steps and
  descending ranges stay errors.
- The public `BinaryOp` enum gains `Range` and `RangeInclusive`, the kind
  of change that [NUC 86](nuc-0086.md) and [NUC 97](nuc-0097.md) made to it.
  No keyword, token or error type is added; the two messages above are
  new.
- The authoritative contract is
  [Integer range literals](../nucleoid.spec.md#integer-range-literals).

## Motivation

- A world model often needs consecutive integers: the hours of a shift,
  the floors of a building, the rows and columns of a grid, the seats of a
  row, the stops of an elevator. Accepted programs have no integer
  sequence. A list literal hard-codes its length, and a list that follows
  its bounds needs a detour through a repeated string:

  ```
  hours = "x".repeat(last - first).split("").reduce(q -> q.concat(q.length + first), [])
  ```

  That declaration takes 34 lexer tokens, against 7 for
  `hours = first..<last`, and it hides what it means. The coordinates of a
  `w` by `h` grid take 49 tokens through the same detour and 31 as
  `cells = (0..<w * h).map(i -> [i % w, Math.floor(i / w)])`. A recursive
  helper, `def span(a, b) => a < b ? span(a, b - 1).concat(b - 1) : []`,
  follows its bounds too, but its definition takes 30 tokens, and every
  use takes at least one token more than a range: `hours = span(first, last)`
  takes 8.
- Literal bounds save tokens as well: `digits = 0..<10` takes 7 tokens
  against 14 for the shortest accepted spelling found, the written-out list
  with one element per line that [NUC 149](nuc-0149.md) allows, 16 for
  `digits = "0123456789".split("").map(d -> +d)` and 23 for the list with
  commas. The smallest literal ranges do not: `x = 0..<1` takes 7 tokens
  where `x = [0]` takes 5, and `x = 0..<2` ties with `x = [0, 1]` and takes
  one token more than `x = [0` with `1]` on the next line.
- Callbacks receive no index, so pairing items with their positions takes
  a `reduce` that counts them through its accumulator,
  `pairs = names.reduce(lambda q, name: q.concat([[q.length, name]]), [])`,
  29 tokens, where a range of positions states it as
  `pairs = (0..<names.length).map(i -> [i, names[i]])`, 25 tokens.
  `pairs = names.map(name -> [names.indexOf(name), name])`, 19 tokens,
  gives the same pairs only while no item repeats.
- A membership test against a range reads as the rule is said:
  `valid = stars in 1..=5` holds for the whole numbers from 1 to 5 and not
  for `4.5`, which `valid = stars >= 1 && stars <= 5` admits. It saves no
  tokens over that comparison, 9 each, or over the string test
  `valid = stars in "1,2,3,4,5"`, 5 tokens, which gives the same result for
  every number because the text of a number holds no comma; the written-out
  list `valid = stars in [1, 2, 3, 4, 5]` takes 15, and 11 with one element
  per line.
- The two spellings come from Kotlin and Swift (`..<`, half-open) and Rust
  (`..=`, closed), and no language reads either of them differently. The
  bare `..` is half-open in Rust and C# but closed in Kotlin, Ruby and
  Haskell, so it stays an error rather than guess.

## Rationale

- **Category and mode.** The caller drew Syntax enhancement with one
  tool-backed uniform draw over the five categories that NUC 1's registry
  marks eligible for automatic selection: index 0, with probability 1/5,
  at about 10:46 on 25-Nov-2026, and no redraw. It allocated this NUC in
  the pushed commit `3bf9d8e5`. This revision pins the pushed claim
  `7efa636c4153bfe7fa80ee4a3bf4381bfb399cb3`,
  `Resume NUC 148 Integer Range Literals`, which holds
  [NUC 147](nuc-0147.md), [NUC 149](nuc-0149.md) and [NUC 151](nuc-0151.md),
  accepted after the allocation; the candidate first prepared against
  `3bf9d8e5` was ported onto it, and every measurement below was taken
  against it. This is a
  continuous cycle, so the token non-regression gate is required. Runtime
  applicability does not apply to this category, and the ARC-requested
  and user-requested bases do not apply.
- **Selection.** Within the category the caller chose integer range
  literals. Accepted Nucleoid has no integer sequence, no NUC proposes
  ranges, [NUC 135](nuc-0135.md) lists `x !in 1..5` among what it does not
  add because Nucleoid has no literal for it, and
  [NUC 61](nuc-0061.md)'s instance list ranges are population slices. The
  caller ruled out a `range(...)` global, because any new global changes
  the accepted reading of a bare word in an `is` sentence, and digit
  separators and hexadecimal literals, because `1_000` and `0xFF` lex as
  two juxtaposed statements.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Two operators, one for each end.** A half-open range counts positions
  and lengths, `0..<xs.length`, and a closed range lists what both ends
  name, `1..=5`. Kotlin and Swift write the half-open range `..<`, and
  Rust writes the closed range `..=`; no language gives either spelling
  another meaning. Rejected:
  - a bare `..`, which is half-open in Rust and C# but closed in Kotlin,
    Ruby and Haskell, so half of the programs written from habit would be
    off by one;
  - Swift's closed `...`, which Ruby reads as half-open;
  - a `range(a, b)` global or a method on numbers, which would change the
    accepted reading of bare words and of number receivers;
  - Haskell's `[a..b]`, which would put a range where an index or a list
    item stands.
- **Three adjacent tokens, read by the parser.** The lexer is unchanged:
  `.` stays `Dot`, `<` stays `Less` and `=` stays `Assign`, so every
  accepted input keeps its exact tokens and every pinned lexer and dot
  diagnostic stays byte-identical, among them `class P(this..x)` at line 1,
  column 13 and `f(..a)`'s `Unexpected '.'`. The parser reads the operator
  from three tokens, `Dot`, `Dot` and then `Less` or `Assign`, each starting
  on the line of the one before it, in the column right after it, as
  [NUC 135](nuc-0135.md)'s `touches_next` reads `!in`. A column counts the
  characters since the start of its line, so the check means exactly that
  nothing lies between the three tokens. Rejected: a lexer token for each
  operator, which would change the tokens of every input that writes one,
  so the inputs that still fail, the reserved positions among them, would
  no longer report their accepted errors at the second dot.
- **One level between the comparisons and `+`, without chaining.** Kotlin
  and Swift both place their range operators above the comparisons and
  below `+` and `-`, so a computed end needs no parentheses, `0..<n + 1`,
  a membership test needs none either, `x in 1..=5`, and a prefix operator
  applies to a bound, `-1..<2`. The level does not chain, as Swift's range
  operators do not: `a..<b..<c` has no meaning, since a range of lists is
  not a range. Rejected: Rust's level below `||`, which would read
  `x in 1..=5` as `(x in 1)..=5`, and a level above `+`, which would read
  `0..<n + 1` as `(0..<n) + 1`.
- **Read only in a final parse pass.** Accepted inputs already hold the
  operators where a parse gives up before them. A template interpolation
  ignores the tokens after the expression it reads, so
  `` `${x |> why ..<3}` `` renders the selection `x |> why`, and so do
  `depth(1)`, `nodes`, `holds`, `stated`, `union(...)` and `model |> why`
  before `..<` or `..=`, spaced or not. It also ignores a trailing
  Python-style `if`, `is` comparison or `in` test, so
  `` `${x if true else 2 ..<3}` ``, `` `${x is 1 ..<3}` `` and
  `` `${x in [1] ..<3}` `` render `1`, as `` `${x if false else 2}` ``
  does. `parse_expression` ignores its tail the same way. The range run
  keeps every one of those readings, as measured, but the design does not
  rest on that list being complete: a program is parsed exactly as at the
  accepted revision first, through its whole parse sequence: the plain
  parse, the `is` retry of [NUC 86](nuc-0086.md), the comprehension retry
  of [NUC 92](nuc-0092.md), the final parse of [NUC 102](nuc-0102.md), the
  receiver run of [NUC 107](nuc-0107.md), the section run of
  [NUC 109](nuc-0109.md) and the line-break run of
  [NUC 149](nuc-0149.md). Only when all of it fails does the same sequence
  run once more, reading ranges, as NUC 109's section run and NUC 149's
  line-break run follow the sequence before them. Every accepted input
  keeps its parse by construction, and no list of tentative parts has to
  be complete, the class of break that rejected [NUC 91](nuc-0091.md).
- **The same readings everywhere in the range run.** Every parser the
  range run creates reads ranges: each retry, the section run, the
  line-break run, the `accepted` and `separates` probes with which a
  `while` header or a `suppose` premise decides [NUC 93](nuc-0093.md)'s
  separate statements, the tentative statements and every template
  interpolation. So a range stands in every expression position of that
  run, apart from the reserved positions, and a probe decides a header
  that holds a range as it decides the same header with the range written
  as its list.
- **After the line-break run.** [NUC 149](nuc-0149.md) separates list
  elements by line breaks only in its own run, after the rest of the
  accepted sequence fails. The range run restarts from the initial modes
  with only the range mode on, so it separates list elements by commas
  again, and it keeps the source's inter-token line breaks, which the
  parser saves before the accepted sequence starts. It then runs the whole
  accepted sequence once more, its own line-break run included under
  NUC 149's condition. So a program that needs both newline-separated
  elements and ranges parses in the range run's line-break run, as
  `a = 2`, `xs = [`, `0..<a`, `a..=4` and `]` on lines of their own do.
  The saved copy matters because a `while` header or `suppose` premise
  probed in a words-mode retry discards the line breaks of the run it
  belongs to, so that run's line-break retry finds none. Without the copy,
  `xs = [1` and `2]` on two lines, then `class O`, `o = O()`, `o.is = 1`,
  `x = 1`, `while x < 3: x = x + 1` and `r = 0..<3` would fail, because
  the accepted line-break run probes that header after the list; with it,
  the program parses, as the same program with `r = [0, 1, 2]` parses at
  the accepted revision. Inside the range run that probe still discards
  its own run's line breaks, so `x = 1`, `y = x is 1`,
  `while x < 3: x = x + 1`, then `xs = [0..<2` and `2]` on two lines still
  fails, as the same program with `[0, 1` fails at the accepted revision.
- **New statements read ranges too.** The suite of a contextual `defer:`
  ([NUC 147](nuc-0147.md)) is a list of statements, each a new top level,
  and the value of `TARGET &&:= EXPR` ([NUC 151](nuc-0151.md)) is a value
  like that of `:=`, so both read ranges and neither is a reserved
  position. A skipped `&&:=` never evaluates its value, range included, and
  a deferred range is evaluated when the block exits.
- **A cheap trigger.** The range run starts only when the tokens hold the
  adjacent operator or a template whose text holds `..<` or `..=`, because
  an interpolation is lexed only when it is parsed. Every other failing
  program is reported after the accepted sequence, with no extra parse.
  Measured, accepted programs parse as fast as before, within 5%, and a
  failing program that holds a range parses 1.6 to 3 times as long, as the
  [Preparation checks](#preparation-checks) list.
- **Errors at the furthest point.** When the range run fails too, the
  input reports whichever of the accepted error and the range run's error
  lies further into the source, the accepted one on a tie, as NUC 102 and
  NUC 109 do. So a valid range followed by an unrelated mistake reports
  the mistake, and a form that the range run rejects at the second dot, a
  reserved position among them, keeps the accepted error.
- **Reserved positions.** A list used where a number is expected converts
  through the numeric conversion: `xs[[1, 2]]` is `xs[0]`, `xs[[2]]` is
  `xs[2]`, `xs[[1]:]` starts at `1`, `xs[::[2]]` steps by `2`,
  `repeat [1, 2, 3]:` runs no iteration and `repeat [3]:` runs three. A
  `for` statement over a list of numbers runs no iteration, because a list
  supplies only registered object references. A range read there would
  silently do one of those. So a range is not read at the top level of a
  subscript's index, slice start, slice end or slice step, of a `for`
  statement's source or of a `repeat` statement's count, outside any
  parentheses, brackets, braces or call arguments there, and those forms
  keep their accepted errors. That leaves a later proposal free to give
  `xs[a..<b]`, `for i in 0..<n:` and `repeat 0..<n:` the meanings they
  suggest. The binding decisions of this cycle name the subscript index
  and slice bounds and the `for` source as the places where a whole range
  is not read; this revision adds the slice step of [NUC 125](nuc-0125.md)
  and the count of [NUC 115](nuc-0115.md)'s `repeat` for the same reason,
  and reserves the whole top level of each place, so that
  `xs[x in 0..<3]` and `xs[0..<2 == ys]`, which would index by a boolean,
  stay errors too. In a subscript and a `for` source the postfix chain
  then reads the first dot as a member, exactly as the accepted parser
  does, so those inputs fail with the accepted error at the same token. A
  `repeat` header is tentative: when it fails, the accepted parser reads
  `repeat` as a name and its count as the next statement, which the range
  run would read as a range and fail later, at the colon. So the range run
  reads the header, ranges included, and then raises the accepted error
  itself, at the third token of the first range at the top level of the
  count. A parenthesized range is an ordinary list in those positions. A
  comprehension's source and a quantifier's collection do read ranges,
  because a comprehension maps its source and a quantifier reads a list's
  items, so `[f(i) for i in 0..<n]` is `(0..<n).map(i -> f(i))`.
- **Conditions read ranges.** A range in a condition is a list, which is
  truthy even when it is empty, as every list is. So `if 0..<0:` runs its
  body, and `while 0..<3:`, `while 0..<0:` and `while x..<3:` raise
  `TypeError("Loop did not terminate")` at the `while` statement after
  100,000 iterations, exactly as `while [0]:` and `while []:` do at the accepted
  revision; both were measured on their release builds. A condition is no
  reserved position, because a list there converts to nothing: it is
  truthy, as written.
- **Integers only, checked strictly.** A range lists consecutive integers,
  as Python's `range`, Rust's and Kotlin's integer ranges and Swift's
  countable ranges do. A fraction, a numeric string, a boolean or `null`
  raises rather than converting, as the rank of `quantile` does, because a
  converted bound would list items nobody wrote, and a `null` bound would
  silently count from `0`. An undefined bound makes the range undefined,
  as it makes arithmetic undefined, so a class-level rule waits for a
  property that is not set yet, as `$X.s = $X.a + $X.b` does. Beyond
  `9007199254740991`, the largest safe integer, consecutive integers are no
  longer distinct numbers, so such a bound raises. `-0` counts as `0`, so a
  range never holds `-0`.
- **Empty when the bounds cross.** `5..<2` and `5..=4` are empty, as
  `range(5, 2)` is in Python and `5..2` in Rust and `5..<2` in Kotlin, so a
  standing range never turns around when its bounds cross; it empties.
  Swift stops the program on such a range, which a standing declaration
  whose bounds cross while they change could not afford. Descending ranges
  and steps are left to later proposals, and a stepped slice already takes
  every other item of a range: `(0..<10)[::2]`.
- **At most 100,000 items.** That is the limit of the iterations of a
  `while` loop and of a `repeat` count. The size is checked before any item
  is built, so `0..<1e15` raises at once instead of exhausting memory.
- **A list like any other.** A range is evaluated to an ordinary list,
  so every list method and query, membership test, equality, index,
  slice, `push`, printed form and JSON output treats it as a list literal,
  and `typeof` gives `"List"`. Rejected: a lazy range value, which would
  need a new runtime value and would change equality, printing, JSON and
  `typeof` for it.
- **A binary expression like any other.** The operators add two variants
  to the public `BinaryOp` enum on `Expr::Binary`, as NUC 86 added `Is` and
  `IsNot` and NUC 97 added `In` and `NotIn`. Evaluation order, dependency
  tracking, `.value` freezing, class-level validation, rollback, graph keys
  and rendering therefore carry the new operators, and every `match` over
  `BinaryOp` names them. Rejected: a new `Expr` variant, which would add an
  arm to every exhaustive match over `Expr` for nothing a binary node lacks.
  `BinaryOp` is not `#[non_exhaustive]`, so the variants break downstream
  exhaustive matches, a semantic-versioning change for the human review.
- **Rendered as written.** A range renders as `START..<END` or
  `START..=END` in statements, `why`, `affects`, graph keys and error
  messages. The renderer drops the grouping parentheses of every binary
  operand at the accepted revision, as [NUC 124](nuc-0124.md) found for
  `(xs.length - 1) * q`. A range is most often the base of a postfix chain,
  `(0..<n).length` and `(1..=k).map(f)`, so it is grouped there, as a noun
  query already is, and reads back as the same chain; inside another
  operator's operand it shares the accepted behavior. A whole template
  interpolation, where a noun query is grouped too, renders a range as
  written, `` `${0..<3}` ``, because an interpolation reads the whole
  range.
- **Interactive input.** A range opens no block, so the REPL and the
  terminal workspace run a line that holds one as they run any other line.
- **Where the cases stand.** [NUC 139](nuc-0139.md)'s placement test keeps
  its cases directly before [NUC 135](nuc-0135.md)'s, and NUC 135's keeps
  its cases at the end of `README.md` and `docs/examples.md` and followed
  by exactly ten cases in the specification and the reference, those of
  NUC 138, 141 to 146, 147, 149 and 151. So the
  new cases stand after the last case of [NUC 136](nuc-0136.md) and before
  the first case of NUC 139 in all four documents. They stand after
  [NUC 97](nuc-0097.md)'s cases, whose audit forbids membership tests only
  before its own. The placement test of this proposal names no other
  proposal's case: it requires that the new cases are contiguous and stand
  before NUC 139's and NUC 135's.
- **Requires.** The Draft named NUC 10, whose lists a range builds and
  whose subscripts hold reserved positions. This revision adds NUC 61,
  whose population subscripts `Name[a:b]` are reserved too; NUC 63 and
  NUC 115, whose 100,000-iteration limit the size limit matches and whose
  `repeat` count is reserved; NUC 86, NUC 92, NUC 102, NUC 107 and NUC 109,
  whose parse sequence and section run the range run repeats; NUC 93,
  whose probes read ranges in that run; NUC 97, whose level of `<` and
  membership tests the range level stands above; NUC 125, whose slice
  step is a reserved position; and NUC 149, whose line-break run the range
  run follows and repeats.
- **Not added.** Bare `..` and `...`; open ranges such as `..<n` and
  `a..<`; steps and descending ranges; ranges over strings, characters or
  dates; lazy ranges; ranges as subscripts, `for` sources or `repeat`
  counts; a `range(...)` global; and any change to lists, subscripts,
  `for`, `repeat`, comprehensions or membership tests.

### Counterparts

- Every new case is compared with the most compact accepted-syntax program
  found at the accepted revision that reaches the same canonical
  assertions in the same order and the same expected return. Each
  counterpart keeps every other line of its case byte for byte and writes
  out only the ranges, plus a helper or table at the top where that makes
  the program shorter or, in the rollback case, where the counterpart needs
  one to raise the range's two errors. No case puts a range inside an
  assertion, so both sides keep the same canonical assertions. The seven
  counterparts are recorded in `extra-baselines-7efa636c.json`, which the
  accepted runtime executed with all 28 of their assertions and all seven
  returns.
- Every range follows a bound that changes after it is declared: new
  floors and a basement removed, an instance's changed end and start and a
  new shift, a grid's changed size, a seat count and a row, a fractional
  and an oversized bound and an undone transaction, crossing and negative
  bounds, a later closing hour, and an elevator's lowered top floor. So a
  written-out literal, a `repeat` or `while` loop with `push`, which runs
  once, and a one-shot `&&:=` of [NUC 151](nuc-0151.md), which assigns
  once, fail at every site; on a class-level rule `&&:=` raises
  `TypeError("Cannot use ':=' on a class-level property")`.
- **Tables written one element per line.** [NUC 149](nuc-0149.md) lets a
  list element end at a line break instead of a comma, and `tokenize` gives
  no token for a line break or an indentation inside brackets, so a table
  written one element per line costs one token per element instead of two.
  An element that starts with `-` still needs its comma, because it would
  continue the element before it: `[-2` with `-1` on the next line reads
  `[-3]`. Every recorded counterpart therefore writes its tables one
  element per line, and such a table gives the smallest passing program of
  every case. Each counterpart needs NUC 149's run: at `3bf9d8e5`, before
  it, every one raises `SyntaxError("Expected ']' but found number …")` at
  its first comma-free line break.
- A counterpart may pass only because of the case's values. That makes the
  comparison stricter, so the search admitted such spellings whenever they
  pass every asserted value and expected return of the case, as
  [NUC 125](nuc-0125.md)'s did. The recorded counterparts rely on these
  properties, each true of its case and none equivalent in general:
  - **A table slice.** The tables `-2, -1` and then `0` to `5`, sliced by
    `[lowest + 2:highest + 3]`; `6` to `22`, by
    `[$Shift.start - 6:$Shift.end - 6]`; `-1` to `4`, by
    `[first + 1:last + 1]`; `9` to `14`, by `[:close - 9]`; `-1` to `12`,
    by `[$Elevator.lowest + 1:$Elevator.highest + 2]`; and `1` to `7`, by
    `[:count(last - first + 1)]`, each written one element per line, hold
    only while the bounds stay within their table, the `9` and `1` tables
    only while `open` and `first` keep their values.
  - **A shared table.** `xs`, the table `0` to `12` at the top of the grid
    case, gives `xs[:columns * rows].map(...)` and
    `xs[1:seats + 1].map(n -> row + n)` only while the grid has at most 13
    cells and a row at most 12 seats; its two uses pay for its line, as a
    helper's do.
  - **A slice of another range.** `floors[:-lowest]` equals `lowest..<0`,
    and `floors[1 - lowest:]` equals `1..=highest`, only while `lowest` is
    not above `0`.
  - **A checking helper on the count.** The rollback counterpart's
    `count(n)` raises `TypeError("Range bounds must be integers")` for a
    fractional count and `TypeError("Range is too large")` for a count above

## Specification

- The normative contract is
  [Integer range literals](../nucleoid.spec.md#integer-range-literals).

### Syntax

- A range stands on a new level between `relational` and `additive`:

```
relational    ::= range (relationalOperator range)*
range         ::= additive (rangeOperator additive)?
rangeOperator ::= DOT DOT LESS | DOT DOT ASSIGN
```

- The three tokens of `rangeOperator` are adjacent: each starts on the
  line of the token before it, in the column right after it. Space around
  the operator is free.
- `..<` builds `Expr::Binary` with `BinaryOp::Range`, and `..=` with
  `BinaryOp::RangeInclusive`.
- Both operands are additive expressions, and a range is one operand of a
  comparison, a membership test or any looser operator:

| Source | Reads as |
| --- | --- |
| `0..<n + 1` | `0..<(n + 1)` |
| `a - 1..=b * 2` | `(a - 1)..=(b * 2)` |
| `-1..<2` | `(-1)..<2` |
| `a ** 2..=b` | `(a ** 2)..=b` |
| `x in 1..=5` | `x in (1..=5)` |
| `x !in 0..<n` | `x !in (0..<n)` |
| `a < 0..<3` | `a < (0..<3)` |
| `0..<3 == xs` | `(0..<3) == xs` |
| `c ? 0..<a : 1..=b` | `c ? (0..<a) : (1..=b)` |
| `x ?? 0..<3` | `x ?? (0..<3)` |
| `a..<b..<c` | a `SyntaxError` at the second operator |

### Where ranges are read

- An input first runs the whole accepted parse sequence, the section run
  and the line-break run of [NUC 149](nuc-0149.md) included. Only when all
  of it fails, and the tokens hold an adjacent `..<` or `..=` or a
  template whose text holds `..<` or `..=`, does the same sequence run
  once more with ranges read in every pass, probe, tentative statement and
  template interpolation. That run starts from the initial modes, so it
  separates list elements by commas until its own line-break run, which
  follows NUC 149's condition, and it keeps the inter-token line breaks of
  the source, saved before the accepted sequence starts. Its first success
  is the result. When it fails too, the input reports whichever of the
  accepted error and its own lies further into the source, by line and
  column, the accepted one on a tie.
- `parse_expression` runs the same sequence on its input, so an input that
  an accepted pass reads keeps that result even when the tokens it ignores
  hold a range.
- Inside the range run, a range stands wherever an expression stands:
  declarations and assignment values, `:=`, `+=`, `&&:=`, `??:=`, `is`
  assignments, `if`, `elif` and `while` headers, `suppose` premises,
  class-level rules and conditionals, function, method and lambda bodies,
  `defer:` suites, call and constructor arguments, list items, comma- or
  newline-separated, object values, conditional branches, `return`,
  `throw`, `assert` in both spellings, comprehension sources and filters,
  quantifier collections and conditions, and template interpolations,
  apart from the reserved positions.

### Reserved positions

- A range is not read at the top level of the index, slice start, slice
  end or slice step of a subscript, on lists, strings, objects and classes
  alike: `xs[0..<2]`, `Seat[1..=3]`, `xs[a..<b:]`, `xs[:a..=b]`,
  `xs[::0..<2]`, and also `xs[x in 0..<3]`.
- A range is not read at the top level of the source of a `for`
  statement, `for i in 0..<3:`, `for i of 0..<3:` and `for k, v in 0..<3:`
  with an indented or a same-line body, or of the count of a `repeat`
  statement, `repeat 0..<3:` with an indented or a same-line body. The
  colon-free implicit loop `for NAME` takes a single name as its source,
  and `repeat COUNT` without a colon is the statements `repeat` and
  `COUNT`, so neither holds a reserved range.
- The top level of such a position is everything outside the parentheses,
  brackets and braces in it: grouping, list and object literals, call and
  constructor arguments, stage arguments such as `depth(...)`, and the
  statements of a function or arrow body in braces each open a new top
  level, where ranges are read again. A template interpolation is a new
  top level too.
- In a subscript and a `for` source the postfix chain reads the first dot
  of a reserved range as a member, as the accepted parser does, so the
  input fails with the accepted error at the same token. A `repeat` header
  is read with ranges and, when its count holds a range at the top level,
  raises the accepted `SyntaxError("Expected a property but found '.'")`
  itself, at the third token of the first such range, which is where the
  accepted parser reports the statement after `repeat`.
- So those inputs keep their accepted errors. A range nested inside those
  positions is read: `xs[(0..<2)]` indexes `xs` by a list, which converts
  as any list index does and gives `xs[0]`; `xs[h(0..<2)]` passes a list;
  `for i in (0..<3):` iterates a list of numbers, which runs no iteration;
  `repeat (0..<3):` converts a list to a count, running no iteration, and
  `repeat (3..<4):` runs three.

### Bounds and items

- `START` is evaluated first, then `END`, each once, left to right.
- When either bound is undefined, the range is undefined, which an
  assignment stores as `null`. This is checked after both bounds are
  evaluated.
- Otherwise each bound must be a `Number` whose value is an integer from
  `-9007199254740991` to `9007199254740991`; `-0` counts as `0`. Every other
  bound raises `TypeError("Range bounds must be integers")`: `null`, strings,
  numeric strings included, booleans, lists, objects, instances, classes,
  functions, dates, regular expressions, NaN, `Infinity`, `-Infinity`,
  fractions and integers beyond that interval.
- The range is a new list of the numbers `START + k` for `k = 0, 1, ...`,
  in ascending order, up to `END - 1` for `..<` and through `END` for
  `..=`. It is empty when `START >= END` for `..<` or `START > END` for
  `..=`. A `-0` start gives `0`.
- A range of more than 100,000 items raises
  `TypeError("Range is too large")`, checked before any item is built.

| `1..=5` | `[1, 2, 3, 4, 5]` |

### Liveness, class-level rules and transactions

- A declaration that holds a range is a standing declaration: it depends on
  what both bounds read and re-evaluates when they change. `.value`
  freezes a bound.
- A class-level rule with `$Class` bounds, such as
  `$Shift.hours = $Shift.start..<$Shift.end`, holds for every instance,
  created before or after it, follows each instance's bounds, and checks
  the references in its bounds when it is declared.
- A bound error raised while a declaration is re-evaluated fails the
  statement that triggered it and rolls it back, so the previous list
  stays. `suppose` and transactions treat ranges as they treat every
  operator.

### Rendering

- A range renders as `START..<END` or `START..=END`, its bounds as any
  binary operand renders: `hours = first..<last` explains as
  `hours = first..<last`, and `0..<n + 1` renders as `0..<n+1`.
- A range that is the base of a postfix chain is grouped,
  `(0..<n).length` and `(1..=k).map(f)`, so the rendering reads back as
  the same chain. A range inside an operand of another binary operator is
  not grouped, as no binary operand is at the accepted revision, so
  `(0..<n) + 1` renders as `0..<n+1`, which reads back as `0..<(n + 1)`.
