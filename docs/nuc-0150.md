## Abstract

- **Rejected:** an existing `Math.copySign` document locator test fails after
  appended cases shift its locator. The mandatory full-test hard criterion
  fails; the proposed runtime, executable documents and datasets are not
  integrated.
- Add only unshadowed static `Math.Truncate(value)` as an optional C#-style
  spelling of accepted `Math.trunc(value)`, reusing its complete numeric
  conversion, argument evaluation, supplied-Undefined gate and reactive
  behavior.
- Preserve `Math.trunc`, every existing method and accepted source form,
  numeric edge behavior, shadowed/user-defined receivers and unsupported
  first-class Math method values. Do not add a new numeric operation,
  decimal type, overload system, parser rule or family of Pascal-case aliases.
- This caller-selected continuous cycle retains its one uniform
  Language compatibility draw. Token comparison is categorically skipped;
  immutable accepted-source replay, behavior/integrity, compatibility,
  development checks and independent evaluation remain mandatory.

## Motivation

- C# exposes `System.Math.Truncate` for discarding a number's fractional
  portion. Nucleoid already provides that operation as `Math.trunc`; a
  familiar spelling can reuse the same implementation rather than introduce
  another numeric feature or claim full C#/.NET compatibility.
- The accepted runtime rejects `Math.Truncate(-3.75)` as an unknown Math
  method. All-status proposal and source searches found no existing
  proposal for this spelling. NUC 137 concerns `Math.fabs`, not truncation.
- Microsoft documents the established spelling in
  [Math.Truncate](https://learn.microsoft.com/en-us/dotnet/api/system.math.truncate).
  Existing Nucleoid semantics, not .NET overloads or coercion rules, govern
  the alias.

## Rationale

- Reuse the accepted `trunc` arm of `math_unary`, not a wrapper function,
  second conversion, rewritten call or new numeric implementation. The
  optional spelling must behave identically wherever existing call lookup
  reaches native Math.
- Keep Nucleoid's numeric model and coercions. Microsoft's
  [official reference](https://learn.microsoft.com/en-us/dotnet/api/system.math.truncate)
  supplies the familiar spelling, not .NET's decimal/double overload
  selection, static typing or foreign argument rules.
- Add exactly `Truncate`, case sensitively. Do not normalize method names
  or add `Trunc`, `truncate`, `TRUNCATE`, `Abs`, `Floor`, `Ceiling`, `Round`
  or a family of Pascal-case helpers.
- Preserve the existing early supplied-Undefined gate for every Math name,
  including unsupported ones. A previously successful call supplied a
  missing-property Undefined must not become an error or numeric NaN.
- Keep native method value reads unsupported rather than broadening this
  revision into first-class built-ins.
- The caller's one uniform eligible-registry draw selected Language
  compatibility before choosing this bounded alias. This continuous cycle
  retains that category and skips token comparison as
  `language_compatibility`, not as a passing gate or zero-case comparison.

## Specification

- The rejected prototype adds native static `Math.Truncate(value)` as an
  exact alias of `Math.trunc(value)` from NUC 10. Existing native namespace
  routing also applies when an ordinary binding or parameter holds native
  Math; no additional receiver protocol is introduced.
- Evaluate all supplied argument expressions exactly once, left to right,
  using the existing call machinery. Strict reads and errors still happen
  after an earlier argument produces Undefined.
- After successful argument evaluation, any supplied top-level Undefined
  returns Undefined before numeric conversion or name dispatch. This
  includes numerically ignored extras. An Undefined nested in a list
  alone does not trigger that gate.
- Otherwise intrinsically convert only the first value with the accepted
  numeric conversion. Omission supplies numeric NaN. Literal null converts
  to zero; booleans, trimmed numeric strings, lists and dates retain their
  existing conversions. Invalid conversions produce NaN without a new
  error. Do not consult a shadowable `Number` or `Math.trunc`.
- Discard the fractional portion toward zero using the same operation as
  `Math.trunc`. Keep both zero signs, subnormal behavior, finite integral
  results, NaN behavior and both infinities. No alternate rounding,
  saturation, decimal arithmetic or range restriction is added.
- Extra values do not undergo numeric conversion. Their expressions still
  retain eager effects, errors, reads and standing dependencies.
- Keep literal-null coercion distinct from accepted live-null and
  parameter-null deferral. Named functions, independent class rules,
  captures, `.value` snapshots, propagation, deletion/recovery and
  transactions continue through the existing machinery.
- Ordinary identifiers, `.Math` members and state/local Math shadowing
  keep ordinary lookup. User-defined `Truncate` members are not replaced
  by the intrinsic. Native `Math.Truncate` and `Math.trunc` value reads
  stay Undefined/non-callable.
- The candidate's cases are `Nucleoid truncates with a C sharp alias` in
  `nucleoid.spec.md` and `Nucleoid propagates C sharp truncation aliases`
  in `tests/reference.md`. Their accepted counterparts use `Math.trunc`;
  only those relevant calls change. Each retains six ordered canonical
  assertions and explicit expected return `1`. These candidate additions
  are not part of the accepted documents.

```
input = -3.75
truncated = Math.Truncate(input)
assert(truncated, -3)
input = 3.75
assert(truncated, 3)
input = 0.25
assert(truncated, 0)
assert(1 / truncated, Number.POSITIVE_INFINITY)
input = -0.25
assert(truncated, 0)
assert(1 / truncated, Number.NEGATIVE_INFINITY)
1
```

## Errors

- The proposed alias adds no new arity, conversion, range or numeric errors.
  Omitted input and invalid numeric conversion produce numeric NaN, as for
  `Math.trunc`.
- Strict missing inputs and extras retain
  `ReferenceError("<name> is not defined")`, including after supplied
  Undefined. Earlier argument failures still win in evaluation order.
- Unsupported native names retain
  `TypeError("Math.<name> is not a function")`, and `Math.random()`
  retains `TypeError("Math.random is not supported")`, after the
  unchanged supplied-Undefined gate.
- A numeric shadow such as `Math = 7` keeps
  `TypeError("number.Truncate is not a function")`. Other non-native
  receivers keep their receiver-specific diagnostics. Error positions,
  catches, rollback and recovery remain ordinary.
