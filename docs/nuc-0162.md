# NUC 162 -- Population Instance Removal

```

Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Runtime features
Created: 28-Nov-2026
```

## Abstract

- Class populations gain `Name.remove(instance)`, which removes one
  instance in `Name`'s own population from the world model in one
  statement: every property the instance holds, its own and those that
  class-level rules derived, the most recently added first, and then the
  instance itself, as deleting each property with
  `delete instance.property` and then the instance with `delete instance`
  does at the accepted revision.
- Dependents follow, as they follow those deletions: population counts,
  mappings, filters and reads of the removed instance's properties
  re-evaluate, the variable named by the instance's id is unbound, and a
  failed statement or transaction restores the instance, its properties,
  the variable and their dependencies.
- Any other first argument, an instance of a subclass or of a parent class
  among them, raises `TypeError("remove expects an instance of <Name>")`
  before anything is deleted; further arguments are evaluated and ignored,
  and the call is undefined. A subclass instance leaves through its own
  class.
- At the accepted revision every such call raises
  `TypeError("<Name>.remove is not a function")`, and only calls whose
  arguments evaluate without error change. `delete` keeps its accepted
  rule, so deleting an instance that still has properties keeps raising
  `TypeError("Cannot delete object '<id>'")`; lists, instances, user
  methods, variables and object members named `remove` keep their
  readings.
- This continuous Runtime features proposal extends an existing comparable
  feature, deletion, so the token comparison runs: each new case is paired
  with its most compact accepted spelling through `delete`.
- The authoritative contract is
  [Population instance removal](../nucleoid.spec.md#population-instance-removal).

## Motivation

- World models gain and lose objects: an order is fulfilled, a vehicle
  leaves the lot, a task is cancelled. Nucleoid creates an instance with
  one call, but removing one that holds properties takes a `delete` for
  every property it holds, including each property a class-level rule
  derived, before `delete instance` succeeds; a forgotten property leaves
  `TypeError("Cannot delete object '<id>'")`.
- At the accepted revision, with `class Robot(name)` and
  `a = Robot("a")`, `delete a` raises
  `TypeError("Cannot delete object 'a'")`, while `delete a.name` followed
  by `delete a` removes the instance from `Robot`'s population, and
  `Robot.remove(a)` raises `TypeError("Robot.remove is not a function")`.
- Inside a function, a method, a lambda or a loop, `delete r` only unbinds
  the parameter or loop variable `r`, so code that removes the instance it
  receives must name each property and then reach the instance through its
  population, as `delete Robot[r.id]` does.
- The removal reuses the accepted deletion of properties and instances,
  with their propagation and rollback, so dependents and transactions
  behave as they already do for those deletions.
- Python's `list.remove(item)`, Kotlin's `remove(element)` and C#'s
  `Remove(item)` name the operation on collections; Nucleoid's class
  populations already answer `map`, `filter` and the other list queries.

- **Only former errors.** At the accepted revision every call of
  `Name.remove` on a declared class raises
  `TypeError("<Name>.remove is not a function")` at column 1 of the running
  statement, whatever its arguments, unless an argument raises first.
  Outside this proposal, `git grep` at the accepted revision finds
  `.remove(` only in Rust sources, as methods of Rust collections; no
  accepted test, document case, dataset record or ARC dataset calls it.
- **A population method, not syntax or a new `delete`.** `Name.remove(x)`
  reads as the population queries `Name.map`, `Name.filter` and
  `Name.list()` do, adds no token or keyword, and leaves every `delete`
  reading as it is. Rejected:
  - deleting an instance's properties in `delete instance`, because
    accepted specification cases pin `TypeError("Cannot delete object '<id>'")`
    for exactly that program;
  - a `remove x` statement or keyword, because `remove` is an ordinary name
    and `remove a` already parses as the two statements `remove` and `a`,
    raising `ReferenceError("remove is not defined")` without a definition;
  - `instance.remove()`, because it reads an absent method and is undefined
    at the accepted revision, and instance methods named `remove` run;
  - `xs.remove(x)` on lists, `Name.list().remove(x)` on copies, a predicate
    form `Name.remove(r -> ...)` and several instances in one call, which
    are other proposals.
- **Membership follows the population.** At the accepted revision
  `Name.length`, `Name.map(...)`, `Name[i]` and `x in Name` see only
  `Name`'s own instances: with `class Dog extends Animal`, `rex = Dog("rex")`
  and `cat = Animal("cat")`, `Animal.length` and `Dog.length` are both `1`,
  `rex in Animal` is `false`, and the specification pins
  `assert(Animal.length, 0)` in `Nucleoid declares subclasses with extends clauses`.
  `Name.remove(x)` therefore accepts exactly an instance in `Name`'s own
  population, so for every instance and every value that is not an object
  it accepts `x` exactly when `x in Name` holds. A subclass instance leaves
  through its own class, and an instance of a subclass or of a parent class
  through another class raises the membership `TypeError`. Class-level rules
  still follow the lineage, so `Truck.remove(rig)` deletes the `toll` that
  `$Vehicle` derived for it. The one value that `x in Name` admits and the
  removal refuses is a plain object whose properties equal an instance's,
  such as `{id: "a", name: "a"}` with `a = Robot("a")`, because `in`
  compares objects by their properties: the object is not that instance,
  so no removal reaches an instance its argument does not hold.
- **The most recently added property first.** An instance gains its `id`,
  then its constructor's properties, then the properties that class-level
  rules derive, then any assigned later. Deleting in the reverse order
  removes a derived property before the properties it reads, so no rule
  derives it again for an instance that is about to disappear, and each
  deletion re-evaluates only what still reads the instance. Deleting in
  the order of creation leaves the same population and values with more
  transient re-evaluation: after `delete a.name`, the rule
  `$Tag.label = $Tag.name + "!"` runs again and sets `a.label` to `null`
  before `delete a.label` removes it, while `delete a.label` first leaves
  nothing for the rule to set.
- **The instance leaves as an index deletion removes it.**
  `delete Name[i]` is the accepted deletion that reaches an instance
  wherever it is held: it takes the instance out of its class's
  population, removes its node, unbinds the variable named by its id and
  propagates the class, for named and anonymous instances, at the top
  level and inside functions. For a named instance, the graph that this
  leaves equals the one `delete name` leaves, because the instance and its
  variable share one node key.
- **One message, in the form of the population errors.** Population calls
  that need an argument of one kind raise
  `TypeError("<query> expects a function")` or
  `TypeError("zip expects a list")`, also for an undefined or `null`
  argument, and none gives undefined for an undefined argument.
  `TypeError("remove expects an instance of <Name>")` follows that form,
  names the class whose population the call reads, and needs no rendering
  of the argument. No accepted test, document or dataset contains the text
  `expects an instance`.
- **Undefined result.** The call is made for its effect, as a statement;
  the removed instance no longer exists to be returned, and a boolean such
  as `delete` returns would read as a membership test.
- **No loop over re-added properties.** When a class-level rule or a
  standing statement gives the instance a property again while the others
  are deleted, the removal raises `TypeError("Cannot delete object '<id>'")`,
  as the accepted deletion sequence does at its `delete instance`, and the
  statement rolls back. A loop that deleted the new property again would
  need a bound of its own and could still meet a rule that adds it each
  time.
- **Declared removals stand, as declared mutations do.** A declaration, a
  declared mapping or a class-level rule that calls `Name.remove` reads the
  population, as every population call does, and its arguments, so it
  runs again when they change, as a declared `xs.push(v)` and a declared
  `x = delete Order[0]` do at the accepted revision. After
  `gone = Robot.remove(a)`, the next change of `Robot`'s population runs
  the declaration again with `a` gone, and its
  `TypeError("remove expects an instance of Robot")` fails and rolls back
  that change. This is a limitation of declared removals, which the
  specification records with the advice that removals belong in
  statements; a statement, a function, a method, a lambda or a loop body
  removes once each time it runs.
- **No `Requires` header.** The removal uses only the population dispatch,
  the deletion of properties and instances and class-level rules, which the
  core specification defines and no accepted NUC introduced; NUC 3 and
  NUC 4, which describe them, are reference Drafts.
- **Public API.** No public item is added or removed, and no signature
  changes. `Runtime::run` and the other public entry points run these
  programs, which raised the `TypeError` at the accepted revision; that
  widened behavior is the change to report for semantic-versioning review.
  No version number changes.

## Specification

- The normative contract is
  [Population instance removal](../nucleoid.spec.md#population-instance-removal).

### Calls

- `Name.remove(instance)` is a call on a class population, wherever a
  population call is reached: statements, functions and methods, lambdas
  and callbacks, loop bodies, `try` and `catch`, `suppose`, templates,
  declarations and class-level rules.
- `Name` is any receiver that reads a declared class, as for every
  population query: the class's name, unless a local, a parameter or a
  variable of that name shadows it, or a variable that holds the class,
  such as `R` after `R = Robot`. Every other receiver keeps its accepted
  reading: a list keeps `TypeError("<receiver>.remove is not a function")`,
  and an undeclared name keeps `ReferenceError("<Name> is not defined")`.

### Argument evaluation

- The population and then every argument are evaluated once, left to
  right, as for every population call, and an argument's error propagates
  before anything is deleted: `Robot.remove(missing)` raises
  `ReferenceError("missing is not defined")`, and
  `Robot.remove(a, log.push(1))` raises `ReferenceError("log is not defined")`
  without removing `a`.
- Arguments after the first are evaluated and ignored.
- Membership is tested when the call runs, after its arguments, so
  `Robot.remove(Robot("z"))` creates `z` and removes it.

### Membership

- The first argument must be an instance in `Name`'s own population, the
  population that `Name.length`, `Name.map(...)` and `x in Name` read.
- Anything else raises `TypeError("remove expects an instance of <Name>")`
  at the running statement, before anything is deleted:

| First argument | Example |
| --- | --- |
| None | `Robot.remove()` |
| `null` or an undefined value | `Robot.remove(null)`, `Robot.remove(o.missing)` |
| A number, a string, a boolean, a date or a regular expression | `Robot.remove(5)`, `Robot.remove("a")` |
| A list, a plain object, a class or a function | `Robot.remove([a])`, `Robot.remove({})`, `Robot.remove(Robot)` |
| A plain object whose properties equal an instance's | `Robot.remove({id: "a", name: "a"})`, although `{id: "a", name: "a"} in Robot` is `true` |
| An instance of another class | `Robot.remove(crate)` |
| An instance of a subclass | `Animal.remove(rex)` with `class Dog extends Animal` and `rex = Dog("rex")` |
| An instance of a parent class | `Dog.remove(cat)` with `cat = Animal("cat")` |
| An instance already removed | a second `Robot.remove(xs[0])` after `xs.push(a)` |

### Effect

- **Properties first.** The instance's properties other than its `id` are
  deleted one at a time, in the reverse of the order it holds them. Each is
  deleted as `delete instance.property` deletes it: the property leaves the
  instance, its node is left as a placeholder that keeps its readers, and
  what reads it re-evaluates. A property that a re-evaluation has already
  deleted is skipped, as `delete instance.property` returns `false` for it.
- With `class Order(item, qty, price)` and
  `$Order.total = $Order.qty * $Order.price`, an order holds `item`, `qty`,
  `price` and `total`, so `Order.remove(tea)` deletes `tea.total`,
  `tea.price`, `tea.qty` and `tea.item`, in that order.
- An instance held in a property stays in its own population; only the
  property is deleted.
- **Then the instance.** It leaves its class's population as
  `delete Name[index]` removes it: its node is removed, the variable named
  by its id is unbound when one exists, and what reads its class
  re-evaluates. Anonymous instances, such as those a `Robot("c")` statement
  creates, have no variable to unbind.
- A declaration that reads the instance's variable re-evaluates as after
  `delete`, so `r = a` becomes `null`. A reference held without such a
  dependency, such as the item that `xs.push(a)` added, stays, and the
  instance's properties read as undefined through it.
- When a class-level rule or a standing statement gives the instance a
  property again while the others are deleted, the removal raises
  `TypeError("Cannot delete object '<id>'")`, as `delete` does, and the
  statement rolls back.

### Result

- The call is undefined: `null` in JSON and `undefined` in plain output,
  and `typeof Robot.remove(a)` is `"undefined"`.

### Transactions

- The removal runs in the running statement's transaction. A failure while
  its changes propagate, later in the statement or in an enclosing
  transaction restores the instance, its properties in their order, the
  variable and every dependent, as a failed `try` body or a thrown block
  does for the accepted deletions.

### Equivalence with delete

- Wherever `delete` names the instance, through its variable or an index,
  the final state equals the one that deleting each property, in the same
  order, and then the instance gives.
- Inside a function, a method, a lambda or a loop, `delete r` only unbinds
  the parameter or loop variable `r`: with `def retire(r)` deleting
  `r.name` and then `r`, `retire(b)` leaves `b` in `Robot`'s population
  without a name, and `Robot.map(r -> r.name)` is `["a", null]`, as it is
  for the same deletions in a lambda or a method. There `Robot.remove(r)`
  still removes the instance, as `delete Robot[r.id]` does, so the mapping
  is `["a"]`.

### Liveness and class-level rules

- As for `delete`: population counts, mappings and filters, reads of the
  removed instance's properties and class-level rules re-evaluate. After
  `count = Robot.length`, `names = Robot.map(r -> r.name)` and
  `label = a.name`, `Robot.remove(a)` makes `count` and `names` follow and
  `label` `null`.
- The rules of the instance's class and of its ancestors stop governing it,
  and instances created later join the population as before.

### Positions

- A call in a statement, a function, a method, a lambda or a loop body
  removes once each time it runs. A loop over the population, such as
  `for order in Order:` with `Order.remove(order)` under a condition,
  removes every instance the condition selects.
- A standing `if` at the top level runs again when what it reads changes,
  so `if Robot.length > 2:` with `Robot.remove(Robot[0])` removes the
  oldest robot whenever a third one arrives, as the same `if` with the
  deletions does.
- A declaration, a declared mapping or a class-level rule that calls it is
  standing, as one that calls `push` is: it reads the population and its
  arguments, and calls again when they change. After
  `gone = Robot.remove(a)`, a later `Robot("c")` or `Robot.remove(b)` runs
  the declaration again with `a` gone, which raises
  `TypeError("remove expects an instance of Robot")` at that later
  statement and rolls it back. Removals belong in statements.
- Inside `suppose` the removal is hypothetical, as every deletion there
  is: the block ends with the instance, its properties and its variable
  restored.

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` and graph keys show the call as
  written, as for every population call. After a removal, `--graph` shows
  the instance and its properties as `[pending]` placeholders, as after
  the deletions.

### Cost

- The membership test looks the instance up in its class's instances; each
  property deletion and the instance's removal cost what the accepted
  deletions cost. Before the call dispatches, the population read checks
  that the class is declared and records the read, as for every population
  call, but collects none of the class's instances, which the removal does
  not need.
- **Spot check, a final-tree result.** Measured, not projected, on the
  final release build `nucleoid-final.exe` and the accepted revision's
  release build, through the command line with `--json`: the median of 21
  interleaved runs of each program, including process start, one process
  at a time and each capped at 1.5 GB and 120 seconds. Each program builds
  1,000 instances of three properties and removes them all. Times are in
  milliseconds.

| Program | Candidate | Accepted revision |
| --- | ---: | ---: |
| Build 1,000 anonymous instances in a `repeat` loop | 25.1 | 25.1 |
| Then `for item in Item:` with `Item.remove(item)` | 50.6 | Not supported |
| Then the same loop with three `delete item.p` and `delete Item[item.id]` | 67.8 | 66.8 |
| Build 1,000 named instances `i0` to `i999` | 34.0 | 33.5 |
| Then 1,000 statements `Item.remove(iN)` | 74.9 | Not supported |
| Then 1,000 times `delete iN.c`, `delete iN.b`, `delete iN.a` and `delete iN` | 79.8 | 78.1 |

- Beyond its build, the loop's 1,000 removals take 25.5 ms, where its four
  deletions of each instance take 42.7 ms on the candidate and 41.7 ms at
  the accepted revision. The 1,000 named removals take 40.9 ms, where the
  identifier deletions take 45.8 ms and 44.6 ms. One call replaces four
  statements, and its population read collects no instances. Every removal
  and every deletion walks the class's instances, so removing all of a
  population one instance at a time is quadratic in either spelling. The
  peak memory of each run stays under 33 MB.

### Findings

- **Low, documented limitation:** a declared removal such as
  `gone = Robot.remove(a)` stands, so a later change of the population
  raises the membership `TypeError` and rolls that change back, as
  [Positions](#positions) records. A declared `x = delete Box[0]` stands the
  same way at the accepted revision.
- **Low, test depth:** five of the evaluator's twelve mutants are each
  caught by a single test: deleting the properties in the reverse order,
  skipping the check for an already deleted property, deleting `id`,
  returning `null`, and evaluating the arguments before the class check.
- **Informational, semantic versioning:** the public entry points that run
  programs now remove instances for calls that raised `TypeError`.
- **Informational, pre-existing on both builds:** pushes inside a `for` loop
  with a single loop name over a list are lost, even into a list local to a
  function, which is wider than the top-level case the preparation noted
  and outside this proposal.
