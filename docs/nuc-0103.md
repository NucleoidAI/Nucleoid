# NUC 103 -- Reactive List Flattening

```
NUC: 103
Title: Reactive List Flattening
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Utility enhancement
Created: 10-Nov-2026
Requires: 41, 61
```

## Abstract

- Adds the read-only query `flat` to ordinary lists and class populations,
  the receivers of `flatMap`:
  - `xs.flat()` flattens one level, exactly as `xs.flatMap(v => v)` does,
    so `[[1, 2], 3, [[4]]].flat()` is `[1, 2, 3, [4]]`.
  - `xs.flat(depth)` flattens `depth` levels, exactly as that many
    `flatMap(v => v)` steps do; `xs.flat(0)` is a copy, as
    `xs.map(v => v)` is, and `xs.flat(Number.POSITIVE_INFINITY)` flattens
    every level.
- The depth converts as the index of `at` does, and a missing depth is 1.
- A declaration holding the call is a live derived value with the reads,
  dependencies, `null` handling and rollback of its `flatMap` spelling:
  `cells = grid.flat()` follows every later write of `grid` that
  `cells = grid.flatMap(v => v)` follows, such as `grid.push(row)` or a new
  `grid`, while `grid[0].push(9)`, which writes nothing through an index,
  changes neither. Rendering shows the call as written.
- Only calls of `flat` on lists and class populations change. They raised
  `TypeError("<receiver>.flat is not a function")` at the accepted revision.
  Reading `xs.flat` without a call, object properties named `flat`, and
  every other receiver keep their accepted behavior.
- No token, keyword, syntax, error type or message, option or public item is
  added. The authoritative contract is
  [Reactive list flattening](../nucleoid.spec.md#reactive-list-flattening).
- **Accepted** on 10-Nov-2026: the frozen candidate meets every hard
  criterion of the automatic acceptance rule and passes every policy check.
  The required token comparison ran with every new case using fewer lexer
  tokens, and the independent evaluator's overall decision is Accepted; see
  [Evaluation](#evaluation).

## Motivation

- World models hold nested lists: grids of cells, groups of members,
  adjacency lists and batches of results. JavaScript's standard library
  flattens them with `Array.prototype.flat`, which programmers and language
  models write, yet `[[1, 2], [3]].flat()` raises
  `TypeError("[[1,2],[3]].flat is not a function")`.
- [NUC 41](nuc-0041.md) added `flatMap` and left recursive flattening and a
  depth option outside its revision. The identity spelling is how the
  specification, the examples and a synthesized record flatten a list today:
  `mixed.flatMap(item => item)` in `Nucleoid flat maps lists by one level`
  and its export, `batches.flatMap(batch => batch)` in
  `Flattened batches retain live object identities`, and a record of
  `dataset/nucleoid.synth.22.jsonl`.
- `xs.flat()` is five lexer tokens against eight for `xs.flatMap(v => v)`,
  and `xs.flat(2)` six against fifteen for two such steps. It also names the
  operation instead of spelling an identity callback, and a depth replaces a
  chain of callbacks.
- The code fields of the ARC instruction datasets flatten nothing today, so
  the motivation is JavaScript familiarity and the corpus, not a puzzle.

## Rationale

- **Category and mode.** The caller made one tool-backed uniform draw over
  the five categories that NUC 1's registry marks eligible for automatic
  selection and selected Utility enhancement, index 2, with probability 1/5
  and no redraw. This is a continuous cycle, so token comparison is
  required. Runtime applicability does not apply to this category.
- **Selection.** Within the category the caller chose JavaScript's standard
  `Array.prototype.flat`, the helper NUC 41 left out, over the others it
  considered: a floored `Math.mod`, which saves one token against its
  compact accepted spelling `(a % n + n) % n` for plain operands,
  `Math.hypot`, `sortBy`, `padStart`, `zip` and `groupBy`, which have no fair
  accepted spelling because callbacks receive no index, and `Object.keys`, a
  runtime feature with no accepted spelling.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero. Strategy learning is `not_configured`, so this
  revision is unattributed, with no policy, selection receipt, trial or
  reward.
- **Defined by its accepted spelling.** `flat` is exactly the identity
  spelling it replaces, so every claim about results, reads, dependencies,
  liveness, rendering and rollback is a claim about `flatMap(v => v)` and
  `map(v => v)`, which the accepted runtime already runs. A program can move
  between the spellings without changing what it computes.
- **The shared list-query route.** `flat` joins `Runtime::list_query` beside
  `flatMap`, so lists, slices, members, call results, lists read from a
  state version and class populations gain it at once, with the receiver
  snapshot, argument evaluation, receiver text and null-receiver routing of
  every other query. Rejected: a list-only method, which would leave
  `Name.flat()` raising where `Name.flatMap(f)` runs.
- **Reads as the identity callback reads.** The identity callback reads its
  parameter, and a declaration that reads `null` settles to `null`, so
  `cells = [[1], null].flatMap(v => v)` stores `null` at the accepted
  revision. `flat` reads each item of every level it flattens in the same
  way, so the two spellings stay interchangeable in declarations. Rejected:
  JavaScript's `[1, null]` for that declaration, which would make the short
  spelling store a different value from the long one; a program that wants
  the `null` item keeps it one level down, as `[[1, null]].flat()` does.
- **The depth converts as `at`'s index.** `at` converts its index with the
  arithmetic number conversion, reads NaN as 0 and truncates toward zero, as
  JavaScript's `ToIntegerOrInfinity` does. `flat` reuses that conversion, so
  one rule converts the whole-number arguments of list queries, and then
  saturates it to a count of levels: 0 or less flattens nothing and positive
  infinity flattens every level. JavaScript's `Array.prototype.flat` agrees on
  every supplied value except an undefined one, which it reads as the missing
  depth 1. Nucleoid's `undefined` keyword is `null`, which both read as 0, so
  only a supplied undefined value, such as that of a missing property,
  differs: it converts as `at`'s index does, to 0, and flattens nothing. Only
  an omitted depth is 1, as in JavaScript, because `xs.flat()` is the
  one-level spelling it replaces.
- **Infinity.** Nucleoid defines no name `Infinity`; positive infinity is
  `Number.POSITIVE_INFINITY`, `1 / 0` or the text `"Infinity"`. So
  `xs.flat(Infinity)` keeps raising
  `ReferenceError("Infinity is not defined")` when its argument is evaluated,
  at both revisions. Defining the name is another proposal.
- **Every level.** Steps past the receiver's nesting depth leave the list
  unchanged, so positive infinity and every depth larger than the nesting
  depth give the same list and read every item, and a finite depth beyond the
  largest count saturates to it.
- **An explicit worklist.** Flattening keeps a stack of item iterators on the
  heap instead of recursing over nested lists, and descends into a list item
  only while its level is within the depth. Each item is visited at most
  once, so the cost is linear in the items visited, rather than the depth
  times the width that `n` separate passes over the whole list would cost,
  and depth takes no stack: in a debug build the walk flattens a list nested
  25,000 deep on a thread with a 128 KiB stack. The
  [Power of 10](../.claude/rules/power-of-ten.instructions.md) gap for
  values built at run time is the existing known gap and unchanged: reading a
  receiver clones it, and cloning, comparing, rendering and dropping a list
  nested about 25,000 deep recurse as they do at the accepted revision. In a
  debug build the clone and drop around such a call overflow a 16 MiB stack
  and fit in 64 MiB, so the end-to-end test of that depth runs on a thread
  with a 256 MiB stack. No Nucleoid program builds such a list in practice:
  the parser nests expressions at most 64 deep, and a loop that wraps a list
  in a list copies it on every iteration.
- **Rendered as written.** Statements render as written, so `why` reports
  `cells = rows.flat()` and a `flat` call and its `flatMap` spelling are
  different statements and graph keys, as `sum of xs` and `xs.sum()` are
  under [NUC 75](nuc-0075.md). Rejected: lowering `flat` to its `flatMap`
  spelling, which would render an identity callback the source never wrote.
- **No callback is invoked.** `flat` calls no function. The identity
  callback's body is evaluated one level below the call, the level at which
  the call's receiver and arguments are evaluated, so both spellings reach
  the expression depth limit at the same place: at the accepted revision,
  `flatMap(v => v)`, `map(v => v)`, `concat()` and `slice()` called at the
  end of a recursion raise `TypeError("Maximum expression depth exceeded")`
  at the same recursion depth.
- **Errors.** `flat` raises nothing of its own: every depth converts,
  arguments after the depth are ignored after they are evaluated, and other
  receivers keep their routes.
- **Requires.** The draft named [NUC 41](nuc-0041.md), whose `flatMap` and
  shared route `flat` extends. This revision adds [NUC 61](nuc-0061.md),
  which added `at` and its index conversion that the depth reuses.
- **Not added.** A `flatten` alias, `flat` on strings, objects or instances,
  a depth for `flatMap`, a defined `Infinity`, a flattening-specific size or
  depth limit, and any change to `flatMap`, `map`, `concat` or `at`.
  JavaScript's skipping of array holes does not arise, since Nucleoid lists
  have none.

## Specification

- The normative contract is
  [Reactive list flattening](../nucleoid.spec.md#reactive-list-flattening).

### Calls

- `RECEIVER.flat()` and `RECEIVER.flat(DEPTH, ...)` are list queries when
  `RECEIVER` evaluates to a list, including a member, an index, a slice, a
  call result and a list read from a state version, or to a declared class,
  whose population is the receiver.
- The receiver is read once, before the arguments. Every supplied argument
  is then evaluated once, left to right, and only the first is used.
- A `null` or undefined receiver keeps the accepted method route: the
  arguments are not evaluated and the call is undefined, so a declaration
  holding it stores `null` and re-runs once the receiver exists.

### Depth

- A missing depth is 1. A supplied depth converts to a number as arithmetic
  converts it, NaN reads as 0 and a fraction truncates toward zero, as the
  index of `at` does. The result counts levels: 0 or less flattens nothing,
  and positive infinity or a finite depth beyond the largest count flattens
  every level.

| Depth | Levels |
| --- | --- |
| missing | 1 |
| `1`, `1.9`, `true`, `"1"`, `[1]` | 1 |
| `2`, `2.9`, `"2"`, `" 2 "`, `[2]` | 2 |
| `0`, `-0`, `0.5`, `null`, `undefined`, `false`, `""`, `" "`, `[]` | 0 |
| `-1`, `-0.5`, `Number.NEGATIVE_INFINITY` | 0 |
| `Number.NaN`, `"a"`, `"0x10"`, `"NaN"`, `[1, 2]`, `{}`, an instance, a function, a class, a regular expression, the undefined value of a missing property | 0 |
| `Number.POSITIVE_INFINITY`, `1 / 0`, `"Infinity"`, `"inf"`, `1e300`, `Number.MAX_VALUE` | every level |

- A date converts to its milliseconds, as in arithmetic.

### Flattening

- The receiver's items are at level 1, and the items of a list at level `k`
  are at level `k + 1`.
- `flat(n)` with `n` at least 1 replaces every list item at the first `n`
  levels by its items, in order: the result is the items at levels up to `n`
  that are not lists, with the items at level `n + 1`, in the order a
  depth-first walk meets them. That is the result of `n` successive
  `flatMap(v => v)` steps. `flat(0)` is a copy of the receiver's items, the
  result of `map(v => v)`.
- Order, duplicates and object and function identities are kept, an empty
  list contributes nothing, a string is one item, and deeper lists stay
  lists. The receiver is never written.

```
deep = [1, [2, [3, [4, [5]]]], [[6]]]
two = deep.flat(2)
three = deep.flat(3)
same = deep.flat(0)
assert(two, [1, 2, 3, [4, [5]], 6])
assert(three, [1, 2, 3, 4, [5], 6])
assert(same, [1, [2, [3, [4, [5]]]], [[6]]])
deep.push([[7, [8]]])
assert(two, [1, 2, 3, [4, [5]], 6, 7, [8]])
assert(three, [1, 2, 3, 4, [5], 6, 7, 8])
assert(same, deep)
```

### Reads and dependencies

- The call reads its receiver and arguments as every list query does: a
  variable or property receiver, a class population and whatever the
  arguments read are its dependencies.
- `flat(n)` reads each item at the first `n` levels, `flat(0)` the items of
  the receiver and an infinite depth every item, as the identity callback
  reads its parameter: a read `null` item makes the assignment holding the
  call settle to `null`, as it does for the `flatMap` and `map` spellings.
  Items record no dependency and no undefined read.

| Exact source | Result |
| --- | --- |
| `cells = [[1], null].flat()` | `cells` is `null` |
| `cells = [[1, null]].flat()` | `cells` is `[1, null]` |
| `cells = [[null]].flat()` | `cells` is `[null]` |
| `cells = [[null]].flat(2)` | `cells` is `null` |
| `cells = [1, null].flat(0)` | `cells` is `null` |
| `[[1], null].flat()` as an expression statement | `[1, null]` |

### Liveness

- A declaration holding the call follows later writes of its receiver and
  arguments: `push`, `pop`, `shift`, a replaced list or property, a new or
  removed instance of a population and a changed depth argument. A statement
  that writes nothing, such as `grid[0].push(9)`, which writes nothing
  through an index, changes nothing.

```
shifts = [["ana", "bo"], ["cy"]]
staff = shifts.flat()
size = staff.length
assert([staff, size], [["ana", "bo", "cy"], 3])
shifts.push(["di"])
assert([staff, size], [["ana", "bo", "cy", "di"], 4])
shifts = [["eve"], [], ["fay", "gus"]]
assert([staff, size], [["eve", "fay", "gus"], 3])
shifts.shift()
assert([staff, size], [["fay", "gus"], 2])
```

### Populations

- A population's items are instances, which are not lists, so `Name.flat(n)`
  is the instance list in population order for every depth, read as a
  dependency on the population, exactly as `Name.flatMap(v => v)` and
  `Name.map(v => v)` are.

### Class-level rules

- A class-level rule flattens each instance's own lists:

```
class Team(squads):
    this.squads = squads
$Team.members = $Team.squads.flat()
red = Team([["ana", "bo"], ["cy"]])
blue = Team([["di"]])
assert([red.members, blue.members], [["ana", "bo", "cy"], ["di"]])
red.squads.push(["ed"])
blue.squads = [["fay"], ["gus", "hal"]]
assert([red.members, blue.members], [["ana", "bo", "cy", "ed"], ["fay", "gus", "hal"]])
```

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` output and graph and block keys
  show the call as written: `why cells` reports `cells = rows.flat()`, and
  `cells = rows.flat()` and `cells = rows.flatMap(v => v)` are different
  statements and keys.

### Transactions

- A failed statement or transaction restores flattened declarations, their
  values and their dependencies as for any declaration, and later updates
  keep working:

```
rows = [[1, [2]], [3]]
cells = rows.flat()
try:
    cells = rows.flat(2)
    assert(cells, [1, 2, 3])
    throw "UNDO"
catch error:
    assert(error, "UNDO")
rows.push([[5]])
cells
```

- This returns `[1,[2],3,[5]]`: the transaction restored the one-level
  definition.

### Bounds

- Flattening walks an explicit worklist of item iterators. It visits each
  item at most once and takes no stack for a level, so its cost is linear in
  the items it visits, and the result holds no more items than the receiver
  does at all its levels. The accepted expression, statement and propagation
  limits apply, and no flattening-specific limit is added.

  declared class and whose arguments evaluate. They now return the

  define a method `flat`, since a class's methods belong to its instances:
  `instance.flat()` keeps calling the method.

## Errors

- No error type or message is added, and `flat` raises no error of its own.
- Arguments are evaluated before the query, so their errors propagate
  unchanged: `xs.flat(missing)` raises
  `ReferenceError("missing is not defined")` and `xs.flat(Infinity)` raises
  `ReferenceError("Infinity is not defined")`, as at the accepted revision.
- Receivers other than lists and classes keep their accepted errors, which
  the [Compatibility](#compatibility) table lists, such as
  `TypeError("ab.flat is not a function")` for `"ab".flat()`.
- Expression, statement and propagation limits keep their accepted errors,
  such as `TypeError("Maximum expression depth exceeded")`, which a `flat`
  call reaches where its `flatMap` spelling does.

## Reference Implementation

- **State:** Implemented and Accepted; the frozen candidate, after the
  caller's Rust improvement pass, is integrated unchanged, as
  [Evaluation](#evaluation) records. No token, keyword, syntax-tree node,
  error type or message, dependency, manifest entry or public item is added.
- `src/lang/ast/array/query.rs`: one arm,
  `"flat" => Ok(Value::List(self.flatten_items(items, arguments.first())))`,
  in `Runtime::list_query` beside `flatMap`. Lists reach it through
  `call_list_method`, members, indexes, slices, call results and lists read
  from a state version among them, and populations through
  `call_class_method`, after the receiver snapshot and the evaluation of
  every argument.
- `src/lang/ast/array/flat.rs`, a new private child module of 60 lines:
  - `Depth`, the number of levels a call flattens: 1 for an omitted
    argument, otherwise the argument converted with `integer_or_infinity`
    and saturated to a count with `number::to_usize`. Its `reads` and
    `descends` tell the walk which levels it reads and which it flattens.
  - `Runtime::flatten_items`, the walk: a worklist of item iterators on the
    heap, one for each list being walked, so an item's level is the
    worklist's length when it is taken. It moves each item out of the
    receiver's snapshot, reads it with the runtime's existing
    `note_nullish` at the levels the call reads, descends into a list item
    while its level is within the depth and pushes every other item to the
    result.
- `src/lang/ast/array/index.rs`: `integer_or_infinity`, the step that reads
  NaN as zero and truncates, which `relative_index` applied to `at`'s index,
  factored out once, made `pub(super)` for its sibling and called by both.
  `at` is unchanged.
- `src/lang/ast/array.rs` declares the module, and
  `src/terminal/completion.rs` lists `flat` after `flatMap` in
  `LIST_MEMBERS`.
- `src/lang/ast/array/flat/tests.rs` holds four unit tests of the walk,
  `tests/list_flattening.rs` the 16 focused regressions listed in
  [Executable traces](#executable-traces), and
  `src/terminal/completion/tests.rs` gains one completion test. A new
  `dataset/nucleoid.synth.68.jsonl` adds eight self-contained synthesized
  records, each run with its return.
- The root specification, the executable reference, the README, the
  examples and the consolidated reference with its built-in table and syntax

- The cost of `flat` grows with the items it visits, ten times for ten times
  as many numbers, and stays near the cost of reading the receiver at every
  depth, while each `flatMap` step invokes its callback on every item again.
  A list nested beside a long one costs `flat` one visit per item, where `n`
  identity steps pass over the whole list `n` times. The accepted spelling
  cannot even write some depths: 101 chained steps raise
  `SyntaxError("Expression has too many parts")` at the accepted chain
  limit.
- The deep lists ran on a thread with a 1 GiB stack, for the clone and drop
  of the known gap. The 10,000-deep and deeper rows are dominated by them.
- In the debug test suite, the end-to-end test of a list 25,000 deep and of
  25,000 lists of three takes 0.03 to 0.04 s, and the unit test of the walk
  on its 128 KiB stack 0.01 s.
