# NUC 91 -- Increment and Decrement Statements

```

Title: Increment and Decrement Statements
Author: Can Mingir <canmingir@gmail.com>
Status: Rejected
Type: Standards Track
Category: Syntax enhancement
Created: 08-Nov-2026
Requires: 13
```

## Abstract

- Adds the statements `TARGET++` and `TARGET--`. `count++` is exactly
  `count += 1` and `count--` is exactly `count -= 1`, each one lexer token
  shorter.
- Both lower to the assignment that [NUC 13](nuc-0013.md) builds for
  `TARGET += 1` and `TARGET -= 1`, `TARGET = TARGET + 1` or
  `TARGET = TARGET - 1`. No syntax tree node or runtime path is added, so
  relationships, self-reference, dependents, return values, graph keys,
  `why`, canonical rendering, rollback and errors are those of the compound
  assignment.
- The targets are those of compound assignment: a name or a plain dotted
  path rooted in a name, `$Class`, `this` or `self`, optionally grouped in
  parentheses.
- An increment is a statement, never an expression, as in Go. It stands
  wherever a statement may, and its value is the target's new value, as the
  value of `TARGET += 1` is; it is not C's postfix expression.
- `++` and `--` become single tokens only where two adjacent signs end a
  statement outside parentheses and brackets. Every other pair of signs keeps
  its two tokens, so `++x`, `x++ y`, `x+++1` and a sign pair at the end of a
  line inside brackets keep their accepted meanings.
- A misplaced operator raises
  `SyntaxError("Invalid compound assignment target")` after a statement
  that is not a path, as `+=` does, and `SyntaxError("Unexpected '++'")` or
  `SyntaxError("Unexpected '--'")` after any other expression, as in
  `y = x++`.
- Only inputs that were syntax errors at the accepted revision change. The
  public `Token` enum gains two variants, which needs a human SemVer
  decision; no version is changed. The authoritative contract is
  [Increment and decrement statements](../nucleoid.spec.md#increment-and-decrement-statements).
- Independent evaluation rejected this revision because it is not backward
  compatible, so the prototype is not part of the accepted language and the
  specification section, cases and records it proposed were not integrated.
  A template interpolation whose expression ends in a `|>` stage followed by
  `++` or `--`, such as `` t = `${x |> why ++}` ``, runs at the accepted
  revision, which ignores the signs after the stage, and the candidate
  raises `SyntaxError("Unexpected '++'")` instead. The claim above that only
  former syntax errors change is therefore false; see
  [Evaluation](#evaluation).

## Motivation

- Counting is the most common update in a model of events: arrivals and
  departures, items sold and returned, retries, the steps of a simulation
  and the counters of `while` loops. Nucleoid spells it `count += 1`, three
  lexer tokens, or `count = count + 1`, five. `count++` is two.
- The accepted executable corpus, the specification, the executable
  reference and the `nuc` blocks of the README and the examples, writes
  `+= 1` or `-= 1` 14 times and `x = x + 1` or `x = x - 1` 18 more, in 26
  cases. The synthesized training records write them 17 times in 15
  records.
- `i++` is the spelling of C, C++, Java, JavaScript, TypeScript, C#, Kotlin,
  PHP and Go, so language models write it in loops and counters. At the
  accepted revision every such line is a syntax error, such as
  `SyntaxError("Unexpected end of input")` for `count++` at the end of a
  program, and it stops the whole program before any statement runs.
- [NUC 13](nuc-0013.md) left increment and decrement operators out of its
  scope; it did not reject them.

## Rationale

- **Confirmed category and mode.** The caller made one tool-backed uniform
  draw over the five categories that NUC 1's registry marks eligible for
  automatic selection, at 2026-11-08T04:29:21-05:00 with PowerShell's
  `Get-Random -Minimum 0 -Maximum 5`. It drew index 0, Syntax enhancement,
  with probability 1/5 and no redraw. This is a continuous cycle, so token
  comparison is required. Runtime applicability does not apply to this
  category. The primary purpose is a shorter spelling of an accepted
  statement, so the prior art in other languages does not move it to
  Language compatibility.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero, because no rubric was frozen. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Other candidates in this category.** The caller set aside `??=`, whose
  `SyntaxError("Unexpected '='")` diagnostics `tests/nullish_coalescing.rs`
  pins; slices, `elif`, `not`, `and`, `or` and same-line `if` suites, which
  are already accepted; numeric separators, hexadecimal numbers, string
  prefixes and `it` lambdas, which already parse as juxtaposed statements;
  and multi-line continuations, which cannot save tokens over one line.
- **Exactly `+= 1`.** The parser builds the `Stmt::Assign` with the
  `Expr::Binary` that `TARGET += 1` builds, so every property of the
  compound assignment carries over without a second code path. Rejected: a
  new increment node, which would change the public syntax tree, break
  exhaustive matches over it and duplicate the assignment path; and an
  imperative read-modify-write that bypasses relationships.
- **Canonical source writes the expansion.** `score++` renders as
  `score = score+1`, as `score += 1` does, so graph keys, `rule` texts and
  canonical source do not depend on the spelling. Rejected: rendering
  `score++`, which would need the tree to remember the spelling.
- **Statements only.** C's postfix expression yields the old value and its
  prefix form the new one, and either writes in the middle of an
  expression. A Nucleoid declaration is a relationship, so `y = x++` would
  have to be a relationship for `y` and a write to `x` at once. Go makes
  increments statements and Swift removed them for that confusion; this NUC
  follows Go. `y = x++`, `return x++` and the other expression positions
  raise `SyntaxError("Unexpected '++'")`.
- **The new value.** Every Nucleoid statement has a value, which a program
  returns and the REPL prints. An increment's value is the target's new
  value, the value of `TARGET += 1`. No expression can read it, so the old
  and new values of C cannot be confused.
- **Postfix only.** `++x` and `--x` are accepted programs, `+(+x)` and
  `-(-x)`, so they cannot become prefix increments.
- **Merging only where a statement ends.** In an accepted program the second
  of two adjacent signs is a prefix operator followed by its operand. A pair
  followed by the end of a line or input, `;`, `}`, `else` or `catch` is
  therefore a syntax error wherever the accepted parser reads it, and only
  such pairs become one token.
  `else` and `catch` are included because a same-line suite may be followed
  by its alternative, as in `if ready: x += 1 else: y += 1` and
  `try: x += 1 catch error: y += 1`, which are accepted programs.
- **Not inside parentheses and brackets.** A line break inside `(` or `[`
  ends nothing, so `[1 ++` followed by `2]` on the next line is `[3]`, an
  accepted program. Merging only outside parentheses and brackets keeps one
  rule: an increment works wherever a line break ends a statement. A braced
  body passed as an argument, such as `xs.forEach(x => { total++ })`, keeps
  its accepted syntax error, and `total += 1` remains its spelling.
- **No lexer pattern for `++` or `--`.** A longest-match token would turn the
  accepted `x+++1`, `x ++ y` and `++x` into other token streams, and
  `tests/thin_arrows_and_lambdas.rs` pins
  `("x-->y", "Unexpected '->'", 1, 5)`, which a `--` token would change. The
  signs are merged after scanning instead, and only in the positions above.
- **Adjacent signs, any space before them.** `count ++` is an increment, as
  in C and Java, but `count + +` keeps the two operators of `x + +y`.
  Comments in either comment mode are skipped when the next token is
  looked for, so `count++ # note` is an increment; a comment between the two
  signs separates them.
- **Errors.** An operator after a statement that is not a path reports what
  `+=` reports there, `SyntaxError("Invalid compound assignment target")` at
  the operator. After any other expression the operator is reported as
  unexpected at the operator itself, in the existing `Unexpected <token>`
  form. Template interpolations ignore their trailing tokens, so an
  increment there would otherwise be dropped silently; it raises the same
  error instead.
- **Public API.** The public `Token` enum is exhaustive and gains
  `Token::PlusPlus` and `Token::MinusMinus`, described `'++'` and `'--'`, as
  [NUC 13](nuc-0013.md), [NUC 26](nuc-0026.md) and [NUC 64](nuc-0064.md)
  added theirs. Downstream exhaustive matches stop compiling, so a human
  decides the SemVer change; no version is changed. `parse_expression` and
  `tokenize` change their results only for inputs that the accepted parser
  rejects.

## Specification

### Lexing

- After scanning, two sign tokens become one `++` or `--` token when all of
  these hold:
  - both are `+`, or both are `-`, and nothing separates them in the source,
    neither whitespace nor a comment;
  - they stand outside parentheses and brackets, where layout is not
    suppressed; braces do not count;
  - the next token is the end of a line, `;`, `}`, the keyword `else`
    (including its `elif` spelling) or `catch`, or there is none. Comments
    are skipped when the next token is looked for, in the default mode and
    with `--c-style-comments`.
- The merged token takes the position of its first sign. Every other token,
  including every other pair of signs, is unchanged.
- `+=`, `-=` and `->` are single tokens before merging, so `x++=1`,
  `x--=1` and `x-->y` contain no pair of signs and keep their tokens.
- Template interpolations are lexed with the same rule.

```
count++
count --
count++; total--
count++ # note
[x ++
    y]
```

- The first four lines each hold one increment or decrement. In the last
  two, the line break inside the brackets ends nothing, so they read
  `[x + +y]`.

### Statements

- An expression statement whose expression is a compound assignment target
  and is followed by `++` or `--` is an increment or decrement statement.
  The target is a name, or a dotted path rooted in a name, `$Class`, `this`
  or `self`, where a class or receiver root needs a property, optionally
  grouped in parentheses, with at most 128 dotted links: exactly the targets
  of NUC 13.
- An increment may stand wherever a statement may:
  - at the top level, after a newline, `;` or an indentation change, or
    after another statement on the same line;
  - in the indented and same-line suites of `if`, `else`, `while`, `for`,
    `try`, `catch`, class bodies, functions and methods;
  - in braced blocks, and in the braced bodies of anonymous functions, arrow
    functions and named function declarations that stand outside
    parentheses and brackets.
- Lambda and arrow expression bodies, `def name(...) => ...` bodies and every
  other expression position take no increment.

```
class Gate(limit):
    this.limit = limit
    this.inside = 0
    def enter(): this.inside++
    def leave(): self.inside--
$Gate.full = $Gate.inside >= $Gate.limit
north = Gate(2)
north.enter()
assert([north.inside, north.full], [1, false])
north.enter()
assert([north.inside, north.full], [2, true])
north.leave()
assert([north.inside, north.full], [1, false])
```

### Semantics

- `TARGET++` builds `TARGET = TARGET + 1` and `TARGET--` builds
  `TARGET = TARGET - 1`, the assignments that `TARGET += 1` and
  `TARGET -= 1` build. Statements keep the existing distinction between
  local bindings and standing state assignments.
- A standing increment replaces the target's earlier relationship and reads
  the target's current value, as NUC 13's self-reference does. Declarations
  and class-level rules that read the target re-evaluate, and `.value`
  snapshots stay fixed.
- The statement's value is the target's new value.
- `+` and `-` keep their conversions: a string target gains the text `1`,
  so `"a"` becomes `"a1"`, and a null target stays null.
- A failed transaction rolls an increment back with everything else it
  changed. A class-level target such as `$Order.count++` raises
  `TypeError("Circular Dependency")`, and an undefined target raises
  `ReferenceError("<name> is not defined")`, as for `+=`.
- `why`, `affects`, graph keys and canonical source show the expanded
  assignment, such as `score = score+1`.
- An increment inside a braced block runs whenever its block runs. A block
  re-runs when a value it reads changes, as at the accepted revision, so
  after `{ hits++ }` a later `hits = 7` leaves `hits` at `8`, exactly as
  after `{ hits += 1 }`. A top-level `hits++` is replaced by the later
  declaration instead, and `hits` is `7`. A top-level `if` statement whose
  branch increments reruns in the same way when a value it reads changes.
- An increment keeps the scope that `+= 1` has where it stands. A `for`
  body keeps, at the accepted revision, only the changes made through its
  loop variable, so `for i of [1, 2]: total++` leaves `total` unchanged,
  exactly as `for i of [1, 2]: total += 1` does, while
  `for plant of Plant: plant.leaves++` keeps each new value. `while` bodies
  update outer names.

```
base = 4
score = base * 2
assert(score, 8)
score++
assert(score, 9)
base = 10
assert(score, 9)
assert((why score).map(step -> step.rule), ["score = score+1"])
score--
assert((why score).map(step -> step.rule), ["score = score-1"])
assert(score, 8)
```

### Interactive input

- The line-oriented REPL decides buffering from colons, keywords and
  braces, so `count++` runs at once and every header buffers as before.
  `src/continuation.rs` lexes with the shared lexer, and a merged token is
  an ordinary token to its scans. Same-line `if ready: a++ else: b--` and
  `try: a++ catch e: b--` run at once, and `y = count++` reports
  `SyntaxError: Unexpected '++' (line 1, column 10)` and keeps the session
  running, with `--plain` and with piped `--json` input alike.
- The terminal workspace submits explicitly, with F5 or Ctrl-Enter, and
  needs no change.

## Errors

- No error type, runtime error or catch value is added. Syntax errors stop
  compilation before any statement of the program runs.
- `SyntaxError("Invalid compound assignment target")`: `++` or `--` follows
  a statement's expression that is not a compound target, such as `xs[0]`,
  `f()`, `1`, `(a + b)`, `$Order`, `this` or an assignment such as
  `(y = x)`. It is placed at the operator, as for `+=`.
- `SyntaxError("Expression has too many parts")`: the target has more than
  128 dotted links, as for `+=`.
- `SyntaxError("Unexpected '++'")` and `SyntaxError("Unexpected '--'")`:
  the operator follows any other complete expression, such as an assignment
  value, the operand of `return`, `throw` or `delete`, an `if`, `elif` or
  `for` header, an object value, a lambda or arrow expression body, or a
  template interpolation. It is placed at the operator. The contextual
  `while` and `suppose` headers instead fall back to reading their word as
  a name, as the Compatibility section describes.
- The same messages where a statement or an operand must start, such as a
  line holding only `++`, placed at the token after the operator, like every
  unexpected operand.
- `SyntaxError("Expected <what> but found '++'")` and its `'--'` form: the
  grammar requires a name, key, property or particular token there, as in
  `class ++` or `o = {++}`, with the existing message and position.
- In other former syntax errors a joined operator ends a statement where the
  accepted reading took an operand, so a different existing diagnostic can
  follow. For example `try: x++` with its `catch` on a further-indented
  next line now raises `SyntaxError("Expected 'catch' after 'try'")`, and
  `if c: x++` with an indented `else:` on the next line raises
  `SyntaxError("Unexpected keyword 'else'")`; both raised
  `SyntaxError("Unexpected end of line")` at the accepted revision.
- Runtime errors are those of the expanded assignment, such as
  `TypeError("Circular Dependency")` for `$Order.count++`,
  `ReferenceError("<name> is not defined")` for an undefined target,
  `ReferenceError("this is not defined")` outside an instance and the
  errors of a standing rule that rejects the new value. They roll back the
  transaction and can be caught.
- Existing nesting and runtime limits apply unchanged, including
  `SyntaxError("Statements are nested too deeply")` and
  `SyntaxError("Expressions are nested too deeply")`. An increment takes
  the one expression level of its target, as the expression statement
  `TARGET` does, so it reaches the expression limit at the nesting depth
  where `TARGET` does: one block deeper than `TARGET += 1`, whose right
  operand takes a second level.

## Reference Implementation

- `src/lang/ast/lexer/token.rs` adds the public variants `Token::PlusPlus`
  and `Token::MinusMinus`, described `'++'` and `'--'`. `raw.rs` keeps its
  logos patterns, so no source text lexes as `++` or `--` directly.
- `src/lang/ast/lexer/indentation.rs` holds `layout_depth`, the
  parenthesis and bracket depth rule, raised by `(` and `[` and lowered by
  `)` and `]` without going below 0. `layout`, the scanner's `record` in
  `src/lang/ast/lexer/scanner.rs` and the new pass below share it, so all
  three apply one rule for where layout is suppressed.
- `src/lang/ast/lexer/increment.rs`, a new private module, holds
  `join_increments`, which `tokenize_with_options` in
  `src/lang/ast/lexer.rs` runs between scanning and layout. One pass,
  `increment_starts`, walks the scanned tokens and tracks the depth with
  `layout_depth`. At depth 0 it records each pair of equal signs on one line
  in consecutive columns whose next scanned token is a newline, including a
  newline inside a C-style block comment, `;`, `}`, `else` or `catch`, or
  none. A second pass rebuilds the tokens, and each joined token keeps its
  first sign's position and layout data. Without a pair the tokens are
  returned unchanged. Both passes are bounded `for` loops without recursion,
  indexing or panics, and a debug assertion checks the rebuilt length.
  `interpolation_end`, which only counts braces, is unchanged.
- `src/lang/ast/parser/expression.rs`: `expression_inner` reads its operand
  with `conditional` and continues in `assignment`, which keeps the
  accepted assignment and compound grammar, targets and diagnostics and
  raises `SyntaxError("Unexpected '++'")` or `SyntaxError("Unexpected '--'")`
  at an operator that follows its complete expression. The new
  `statement_expression` enters at the nesting level that `expression`
  takes. When `++` or `--` follows its operand, it checks the target with
  the accepted `check_compound_target`; otherwise it continues in
  `assignment`. Both paths build their trees with the private
  `compound_assignment(target, operator, operand)`, so an increment is the
  tree of `TARGET += 1` or `TARGET -= 1` with the operand
  `Expr::Number(1.0)`. `src/lang/ast/parser.rs` derives `Clone` and `Copy`
  for the private `CompoundOp` that it takes.
- `src/lang/ast/parser/statement.rs`: the expression-statement branch of
  `statement_inner` calls `statement_expression` instead of `expression`.
- The changed production files are `src/lang/ast/lexer.rs` (94 lines),
  `src/lang/ast/lexer/token.rs` (250), `src/lang/ast/lexer/increment.rs`

### Hard criteria

- **No compile errors: passed.** `cargo build --all-targets`,
  `cargo clippy --all-targets -- -D warnings`, CI's
  `cargo clippy --all-targets --all-features --locked -- -D warnings` on
  stable 1.97.1 and on 1.99.1, `cargo fmt --check` and rustdoc with
  `RUSTDOCFLAGS=-D warnings` exit 0 without warnings.
- **Every test passes: passed.** The full `cargo test --no-fail-fast` passes

  passed and 25 ignored in 101 suites at the accepted revision. All 2,766
  accepted test identities keep their status and multiplicity, and 26 are
  added. Existing tests change only count pins, and both exports only gain
  lines and match their sources without regeneration.
- **Backward compatible: failed.** A template interpolation whose expression
  ends in a `|>` stage (`why`, `stated`, `derived`, `diff`, `depth(n)` or
  `path(t)`, also after `??`, a conditional's last branch or an assignment
  value) directly followed by `++` or `--` and then the end of the
  interpolation, `;`, `}`, a line break, `else` or `catch` is accepted at the
  accepted revision, which ignores those trailing signs. The candidate joins
  the signs and raises at the operator instead:

| Exact source | Accepted revision | Candidate |
| --- | --- | --- |
| `x = 1`, then `` t = `${x \|> why ++}` ``, then `t` | `[object obj:0]`, exit 0 | `SyntaxError("Unexpected '++'")`, 1:10, exit 1 |
| `x = 1`, then `` t = `v ${x \|> why --} w` ``, then `t` | `v [object obj:0] w`, exit 0 | `SyntaxError("Unexpected '--'")`, 1:10, exit 1 |
| `x = 1`, `y = 2`, then `` t = `${y ?? x \|> why ++}` ``, then `t` | `2`, exit 0 | `SyntaxError("Unexpected '++'")`, 1:15, exit 1 |

- The caller reproduced all three rows on the accepted and candidate
  release binaries. Positions are relative to the interpolation, as for
  every interpolation error at the accepted revision.
- The public `parse_expression` and `parse_expression_with_options` also
  reject inputs such as `x |> why ++` that they accepted before.
- Cause: `Parser::assignment` raises on `++` or `--` directly after any
  complete expression, including an interpolation's, while at the accepted
  revision an interpolation ignores the tokens after its expression and a
  `|>` stage does not take a following `+` or `-`. The proposer's
  differential never placed a stage before a sign pair. Keeping
  interpolations out of the merge, so that they keep their accepted tokens,
  is one direction for a future revision.
