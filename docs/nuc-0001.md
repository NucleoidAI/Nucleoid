## What is a NUC?

- NUC is the language proposal series, including proposals about language-development processes.
- Every NUC is evaluated as a proposal when added or updated.
- Accepted, implemented claims are the canonical documentation for the Nucleoid Language Reference.
- The format follows Python Enhancement Proposals, adapted for Nucleoid.

## Relationship to the Specification

- `nucleoid.spec.md` is normative: statements paired with the assertions that must hold after them.
- A NUC may propose syntax or behavior not yet implemented; proposal text does not change the accepted runtime.
- Where a NUC claims implemented behavior that disagrees with the specification, **the specification wins** and that claim is in error.
- Every implemented NUC claim about runtime behavior must trace to one or more spec entries.
- Candidate runtime, specification, and test rewrites remain isolated until the proposal passes evaluation.
- `dataset/nucleoid.synth.*.jsonl` and `dataset/arc.jsonl` are canonical, self-contained synthesized and ARC training records, not Markdown-derived copies; they have no independent authority over the root specification.
- The root spec, relevant training JSONL, the language reference in `docs/`, and runtime semantics must stay in sync; propagate affected behavior changes in the same change.
- Preserve training-record IDs, assertions, expected results, and coverage when updating relevant JSONL.
- `dataset/` must contain only regular `.jsonl` files, with no Markdown files or subdirectories.
- Do not recreate or relocate duplicate Markdown datasets or dataset cards; `docs/dataset/` must not exist.
- The root `nucleoid.spec.md` remains authoritative; `dataset/nucleoid.spec.jsonl` is generated from it and regenerated when it changes, never hand-edited.

## NUC Types

- **Standards Track** -- a language feature: syntax, semantics, errors. Most Language Reference NUCs.
- **Informational** -- a design issue, index, or guidelines. Revisions still undergo proposal evaluation. NUC 0.
- **Process** -- a process around Nucleoid, or a change to one. This document.

## Proposal Categories

- This table is the authoritative category registry; `Category` labels one primary purpose, independently of `Type` and `Status`.

| Category | Purpose | Eligible for automatic selection |
| --- | --- | --- |
| Syntax enhancement | Grammar, spellings, and source forms. | Yes |
| Runtime features | Core execution, data modeling, scope, control flow, and transactions. | Yes |
| Utility enhancement | Standard built-in helpers, including math, collections, and strings. | Yes |
| Reasoning enhancement | Logic rules, inference, graph queries, and explanations. | Yes |
| Documentation | Indexes, guidelines, reference documentation, and development processes. | No |

- Every existing and future NUC must have exactly one registered `Category` header, including Draft, Accepted, Rejected, Active, and Superseded proposals.
- Classify the NUC's overall primary purpose, not merely its latest edit; a metadata-only revision does not make a language proposal Documentation.
- NUC 0 and NUC 1 use Documentation.
- Only the user may add categories and specify their automatic-selection eligibility; keep this registry, affected proposal headers, and both category and numerical indexes synchronized.
- Every category addition requires the coordinating caller to review all existing NUCs across every status and update proposals that fit the new category more accurately.
- Each NUC changed by that review requires its own revision under the ordinary independent proposal/evaluation process; preserve unaffected categories and every proposal's `Type`, `Status`, and historical evaluation outcomes.
- Use the user's confirmed classifications; preserve clear assignments unless the category-addition review warrants a more accurate fit.
- Whenever a category is added, selected, or updated, the coordinating caller must ask the user for confirmation before proceeding if anything is uncertain, including its meaning, automatic-selection eligibility, or proposal placement; workers return the question to the caller rather than guessing.
- This category-confirmation requirement is the explicit exception during otherwise non-confirming continuous proposal cycles; only the caller asks the user.

### Selecting an Unspecified Enhancement

- Explicit feature or category requests take precedence; documentation and process work are not randomly selected as language enhancements.
- When no feature or category is specified for a language enhancement, the caller reads the current registry and makes one tool-backed, unbiased random draw with equal probability across all currently eligible categories.
- Derive the eligible set and its size from the registry, without a hard-coded category count; future user-added eligible categories join the same uniform draw.
- With the current four eligible categories, each has a 25% chance; do not retain the former 50/50 syntax/runtime split.
- For example, populate `$categories` from the registry's Yes entries and select one index with `Get-Random -Minimum 0 -Maximum $categories.Count`.
- Draw before recording baselines or delegating preparation, then choose one bounded enhancement within the selected category; do not redraw to favor a category or substitute deterministic alternation for randomness.
- The caller supplies the selected category, requested change, and selection rationale to the proposal worker; the worker uses that selection without redrawing.
- Every category retains immutable accepted-corpus baselines, behavior/integrity checks, syntax compatibility, development checks, and independent evaluation; token comparison follows the execution-mode policy below.

## NUC Status

- **Draft** -- under development, subject to change.
- **Accepted** -- passed proposal evaluation, settled, and matching the specification.
- **Rejected** -- evaluated and refused, including any per-case token increase when the token gate is required.
- **Active** -- informational or process NUCs that remain current; their revisions still undergo evaluation.
- **Superseded** -- replaced by a later NUC, named in `Superseded-By`.

## Proposal Evaluation

- The **token non-regression gate** requires each compared case to use the same or fewer lexer tokens than its accepted baseline.
- `/nuc-proposal` defaults to continuous mode for open-ended requests; omitted evaluator mode also means `continuous` for existing invocations.
- A request for one specific NUC, concrete feature, or particular revision uses single-proposal mode; pass `NUC_PROPOSAL_MODE=single` explicitly through evaluation, record its outcome, then stop.
- Single-proposal requests always skip token comparison, regardless of category or runtime applicability; they still require independent behavior, integrity, syntax-compatibility, development evaluation, and outcome recording.
- Only continuous cycles apply this token-gate matrix:

| Category | Continuous-cycle token gate |
| --- | --- |
| Syntax enhancement | Required. |
| Runtime features | Required for an existing feature with a behavior-equivalent accepted-syntax comparison. |
| Runtime features | Skipped entirely for a brand-new feature. |
| Runtime features | Skipped for a genuinely uncomparable existing feature, with an explicit reason and evidence. |
| Utility enhancement | Required. |
| Reasoning enhancement | Required. |
| Documentation | Skipped. |

- Read the proposal's actual `Category` header and validate it against the registry; an unknown or missing category blocks evaluation, never selects a skip.
- Runtime proposals require explicit applicability (`new_feature`, `existing_comparable`, or `existing_uncomparable`), including in single mode; uncomparable existing features require nonblank reason and evidence, independently verified by the evaluator.
- A missing comparison artifact is not evidence that an existing feature is uncomparable; missing required comparisons still block acceptance.
- Every added or updated `docs/nuc-XXXX.md`, including process and documentation-only changes, requires a fresh `nuc-proposal` agent followed by a separate, independent fresh `nuc-evaluate` agent for that revision.
- Preparation follows the [nuc-proposal profile](../.github/agents/nuc-proposal.agent.md) and [proposal skill](../.github/skills/nuc-proposal/SKILL.md).
- Independent evaluation follows the [nuc-evaluate profile](../.github/agents/nuc-evaluate.agent.md) and [evaluation skill](../.github/skills/nuc-evaluate/SKILL.md).
- Persistent session instructions are [copilot-instructions.md](../.github/copilot-instructions.md).
- The caller launches both stages; neither role spawns agents or is reused for another role, proposal, or revision. If named agents are unavailable, the caller supplies each profile and skill to separate fresh general-purpose agents.
- Pin an accepted Git revision and record its immutable baseline before changing runtime behavior or executable cases. Do not assume a revision containing the candidate is an accepted baseline.
- Prepare and evaluate each revision in an isolated candidate worktree. Dependencies must already be accepted; do not combine pending proposals. Concurrent revisions that rewrite shared files need separate worktrees.
- The proposal agent drafts and prototypes one revision, implementing candidate runtime support and rewriting equivalent executable source cases where necessary. Process-only changes need no runtime or corpus rewrite or artificial new cases.
- Preserve previously accepted syntax and its parsing and runtime semantics; new forms are additive and optional, never replacements that break legacy programs.
- Verify unchanged accepted-syntax counterparts from the pinned revision and any supplied extra baselines alongside candidate forms, including protected assertions, expected returns, and executed assertion coverage.
- Preserve each case's document and title, assertion order and canonical assertions, expected return, and executed assertion coverage. Removing, renaming, weakening, replacing assertions with tautologies, or bypassing cases or assertions invalidates the rewrite.
- The proposal agent synchronizes affected reference, canonical training JSONL, runtime semantics, and generated normative exports.
- Edit normative source documents and regenerate affected exports, never hand-edit generated Rust or `dataset/nucleoid.spec.jsonl`; maintain synthesized and ARC training records directly as canonical JSONL.
- The proposal agent runs relevant development tests, formatting, and warning-denied Clippy. It must not run `evaluate_proposal`, produce an acceptance report, or declare Accepted or Rejected.
- The caller completes the required Rust improvement pass, when applicable, before the final frozen proposal handoff.
- The proposal agent returns a frozen handoff: proposal path and Git blob revision, execution mode, confirmed category and selection rationale when applicable, runtime applicability and supporting rationale, accepted baseline revision and artifact, candidate worktree, changed files, development and syntax-compatibility checks, and explicit blockers. It then stops editing the candidate.
- After the completed handoff, the caller launches the fresh evaluation agent with that handoff and a fresh report path. The evaluator verifies the proposal blob and baseline revision independently.
- The evaluator treats candidate sources, canonical training JSONL, generated normative exports, and the baseline as read-only; no repairs, case rewrites, regeneration, or status/index edits. It may write new external session reports and learner checkpoints, and normal ignored build outputs, never overwrite prior artifacts.
- The evaluator independently validates behavior, development checks, and export consistency, then runs `evaluate_proposal` with the preserved mode and validated applicability. This always checks behavior and integrity and runs token comparison only when required; only this role returns the acceptance decision.
- A substantive revision, repair, rebase, or source change after handoff requires a new fresh proposal/evaluation pair, not an in-place evaluator repair.
- The checked corpus is `nucleoid.spec.md`, `tests/reference.md`, and the `nuc` blocks in `README.md` and `docs/examples.md`. Generated Rust scaffolding, JSONL, and synthesized training cases are not token-scored.
- When token comparison is required, count `tokenize(case.source.trim())` from the accepted lexer before rewriting, and from the candidate lexer afterward. Count every token, including `Newline`, `Indent`, and `Dedent`, except `Eof`.
- When the gate is required, new cases need behavior-equivalent accepted-syntax baselines with the same identities, canonical assertions, and expected returns, executed by the accepted runtime before candidate changes. Supply them through `NUC_PROPOSAL_EXTRA_BASELINES` when recording the baseline; a missing comparison blocks acceptance.
- When token comparison is legitimately skipped, genuinely new behavior cases may have no accepted-syntax counterpart; execute their assertions or explicit expected returns and verify assertion coverage. Never fabricate a counterpart or before-count.
- Skipping token comparison never permits removing or changing pre-existing case identities, protected assertions, expected returns, coverage, or legacy syntax. The immutable accepted-corpus artifact remains required and must be valid; replay unchanged pinned sources and original extra-baseline sources in every mode.
- `tests/proposals.rs` reports the actual mode, registered category, runtime applicability, behavior checks, and whether token checking ran or was skipped with its reason; commands and input formats are in [CONTRIBUTING.md](../CONTRIBUTING.md#evaluating-a-language-proposal).
- A token check that ran records paired `before`, `after`, and `less`, `same`, or `more`; a skipped check has no measured-case list or placeholder zero counts and is not a passing token gate.
- When the gate is required, acceptance requires every paired case to use the same or fewer tokens. Any increase rejects the revision, even if another saves more or the total falls.
- All modes require passing behavior, integrity, syntax compatibility, and development checks; skipped token comparison cannot conceal an invalid/corrupt baseline, bad input, or any such failure.
- Rewrites that fail behavior checks or change protected assertions, returns, or coverage are rejected. Missing prerequisites block acceptance; unevaluated drafts remain Draft, not accepted by default.
- Keep immutable baseline and create-once report artifacts in the session workspace. Never edit or overwrite them or replace missing measurements with estimates.
- The caller integrates unchanged accepted candidates with synchronized runtime, specification, reference, canonical training JSONL, and generated normative exports; serialize integration. Do not apply rejected candidates or erase another user's changes or proposal.
- The caller owns evaluation status and index metadata; these outcomes do not recursively trigger another pair.
- Only the caller continues continuous cycles after recording and committing each outcome; single-proposal mode stops after its outcome, without selecting another NUC.
- Informational and Process documents may retain `Active` after an accepted revision; a rejected revision does not replace their accepted text.
- This is a Copilot-session process, not a filesystem watcher, GitHub Actions workflow, or automatic pull-request trigger.

### Advisory Usefulness and Evaluation Cost

- `tests/proposals.rs` adds callable advisory scoring to `evaluate_proposal`; scores never change its deterministic verdict, token applicability, category selection, or the independent acceptance requirements above.
- Scoring alone reports experience; the separate opt-in bandit below learns proposal strategies from those verified rewards. Neither mechanism trains LLM weights, makes paid calls, or changes the language/runtime.
- Before drafting, the caller may freeze one independently testable usefulness criterion in a create-once session JSON rubric: `criterion_id`, `proposal_path`, `baseline_revision`, and `criterion`.
- Keep scoring inputs outside the repository; pin the rubric's full Git blob using `git hash-object --no-filters` before drafting and preserve that pin through both handoffs. A criterion invented or changed after seeing the candidate cannot demonstrate usefulness for that revision.
- The proposer preserves the caller-owned rubric and pin; it neither assesses its own usefulness nor supplies independent-check claims.
- After checking the frozen candidate, the independent evaluator may create a new session assessment; candidate sources and the baseline remain read-only.
- Bind that assessment to the exact rubric blob and criterion ID, accepted baseline revision, proposal path, and handed-off proposal blob; identify its independent evaluator/session.
- Assess the criterion using real nonblank observations, not `Accepted`, changed lines, additional cases/assertions, token skips, or the proposer's claims.
- Use `demonstrated`, `no_demonstrated_benefit`, or `unknown`; both scored judgments require evidence, while unknown usefulness requires an explicit reason and remains unscored, not zero.
- Independently record behavior/integrity, syntax compatibility, development suites, formatting, Clippy, and export consistency as `passed`/`failed` with evidence, or `unresolved` with a reason. Missing evidence is never a successful check; the core gate does not run external suites or Clippy.
- Positive and neutral rewards require every independent check to pass; a known failure cannot be hidden behind useful or unknown usefulness. A check claiming success while contradicting a corresponding core integrity/legacy failure is invalid assessment input.
- Legacy invocations without scoring inputs still evaluate normally and explicitly report unscored usefulness. A rubric without an assessment is also unscored; an assessment without its pinned rubric is an error.
- Supplied malformed, stale, contradictory, blank-evidence, or provenance-mismatched inputs produce explicit errors, never a successful unscored fallback. Verify scoring blobs remain stable through evaluation.
- The advisory metric is `nuc-advisory-usefulness-evaluator-time-v1`; its reward precedence is:

| Evidence/state | Base reward | Applied cost adjustment | Final reward |
| --- | --- | --- | --- |
| Blocked core evaluation | Unscored | Not applied | Unscored |
| Genuine core rejection | -1 | 0 | -1, regardless of claimed or missing usefulness |
| Core passed, independently failed check | -1 | 0 | -1; independent overall outcome remains Rejected |
| Core passed, unresolved independent check or missing/unknown usefulness | Unscored | Not applied | Unscored |
| Core passed, every independent check passed, demonstrated usefulness | +1 | `-0.1 * t / (t + 1)` | `1 - 0.1 * t / (t + 1)`, in `[0.9, 1]` |
| Core passed, every independent check passed, assessed no demonstrated benefit | 0 | 0 | 0 |

- `t` is seconds measured with `std::time::Instant` in the actual evaluator execution path, covering input validation, source loading, legacy/candidate checking, and blob stability verification.
- Record raw `evaluation_time.elapsed_seconds` and its scope even for neutral, rejected, blocked, or unknown results that reach reporting; an early infrastructure/input error produces no fabricated duration or successful report.
- Timing excludes compilation, external suites/Clippy, proposal/model time, score calculation, and report writing. It is nondeterministic evaluator work, not language runtime performance, total proposal cost, API/model cost, or token-skip savings.
- Reports add usefulness status/basis and input provenance, independent-check eligibility, timing scope, formula/metric identity, and either base reward, applied adjustment and final reward or an explicit unscored reason.
- The existing top-level `decision` remains the deterministic core gate's result; advisory eligibility does not replace the evaluator's overall decision from all independent checks. Failed or unresolved external checks still require Rejected or Blocked under the ordinary rules.
- Return scores and their limitations with the independent evaluation evidence; never infer usefulness merely from acceptance or use rewards to bypass a failure. JSON schemas and optional input paths are in [CONTRIBUTING.md](../CONTRIBUTING.md#advisory-usefulnesscost-scoring).

### Reward-Driven Proposal Strategies

- `tests/proposals.rs` and its focused `tests/proposals/strategy.rs` helper implement opt-in, category-conditioned UCB1 strategy learning: `nuc-category-strategy-ucb1-v1`.
- Category selection remains the unchanged uniform random draw above when unspecified; explicit categories, requested features, and single-proposal stop rules always take precedence. The learner chooses an approach **within** the confirmed category, never a category or replacement feature.
- The fixed typed strategy registry has this stable order; proposers must execute the selected approach, not merely record its label:

| Order | Strategy | Required preparation approach |
| --- | --- | --- |
| 1 | `reuse_first` | Prioritize accepted primitives/helpers; make a minimal additive implementation for the requested feature. |
| 2 | `evidence_first` | Begin with a concrete unsupported/failing use case or counterexample for the requested feature, then make the minimal preserving fix/extension. |

- Both strategies retain every mandatory baseline, behavior/integrity, compatibility, development, independent-evaluation, and applicable token check; neither may change acceptance criteria, reward definitions, category, or user scope.
- The only supported learning scope is `all_attributed_trials`: both single and continuous attributed trials may learn, including Documentation. Learning from a single trial never starts another proposal.
- The caller freezes an explicit external genesis policy with empty `history`, or uses the latest verified checkpoint in its single-owner chain; the harness never silently initializes, resets, or imports older unassigned reports.
- **Before drafting**, the caller runs `select_proposal_strategy`, pins the create-once receipt and policy with `git hash-object --no-filters`, and supplies both artifacts/pins, trial identity, and actionable strategy to the fresh proposer.
- The receipt binds algorithm, parent policy blob, trial ID, proposal path, accepted baseline, confirmed category, mode, and selected strategy; the standard empty-policy selection is `reuse_first`, without a bootstrap exception.
- The proposer verifies and consumes this receipt, describes how it followed the selected approach, and preserves attribution through its handoff. It cannot retroactively select a strategy or update its own trial's policy.
- `evaluate_proposal` validates the pinned inputs and embeds their attribution in the actual saved report alongside the final evaluated proposal blob and existing advisory score. Absent learning configuration explicitly reports `not_configured`; partial, invalid, stale, or mismatched supplied configuration is an error.
- After checking that saved report and the overall independent evidence, `/nuc-evaluate` pins the report and invokes the separate ignored `learn_proposal_strategy` command. The report already exists before the new checkpoint; it contains no self-referential output hash.
- Learn only from the existing verifier's **scored** raw reward: usefulness with its existing time discount, assessed neutral `0`, or known core/external rejection `-1`. Blocked, unresolved, unknown/missing evidence, and unattributed outcomes do not increment trials or create checkpoints.
- Reproduce score/evidence bindings and the existing formula on reload; reject fabricated self-reported reward fields. Only positive floating calculations admit a two-`f64::EPSILON` absolute JSON round-trip tolerance; neutral/rejection rewards and metadata remain exact.
- Normalize each observed raw reward `r` in `[-1, 1]` to `(r + 1) / 2`; neutral `0` is an observed `0.5`, not missing evidence.
- Within each category, try unobserved arms in registry order. Once both are observed, maximize `mean + sqrt(2 * ln(category_trials) / arm_trials)`, with registry-order ties.
- Derive counts and means from typed chronological observations; validate finite/range/counter bounds, using only exactly representable counters up to `2^53 - 1`. Never divide by zero or persist Infinity/NaN sentinels.
- Store observations, parent checkpoint, selection receipt, saved report provenance, actual evaluated proposal blob, and verified raw reward in create-once external JSON checkpoints. Retain all referenced artifacts for validation and subsequent selection; never overwrite old state.
- Validate the exact parent-history prefix, receipt/policy choice, trial/proposal/baseline/mode/category identities, scoring artifacts, and report pins. Reject duplicate trial IDs or actual evaluated proposal blobs, even if a rerun's report bytes/timing differ.
- This is an immutable **single-owner** checkpoint chain: the caller advances its retained head and uses the resulting checkpoint for future pre-draft selections. Old receipts cannot update a newer parent; this is not concurrent/global-head or fork protection.
- Blob pins detect changed inputs, not cryptographic evaluator authentication or proof of wall-clock pre-draft timing. Genuine independent evaluation and pre-draft ordering remain workflow obligations; never fabricate attribution for historical reports.
- This is a reward-driven two-arm contextual bandit, not LLM-weight training, a full multi-step RL system, or a claim that proposal quality improved. Cold-start exploration, small category samples, rubric/reward proxies, and noisy partial evaluator timing limit interpretation.
- Callable commands, schemas, environment contracts, and reload/update examples are in [CONTRIBUTING.md](../CONTRIBUTING.md#reward-driven-proposal-strategies); the proposer and evaluator skills require actual receipt consumption and checkpoint use.

## NUC Format

- One Markdown file per NUC, named `nuc-XXXX.md` with a zero-padded number.
- Opens with `# NUC N -- Title`, then a fenced header block in RFC 822 style.

Required headers:

```
NUC: <number>
Title: <title>
Author: <name> <<email>>
Status: Draft | Accepted | Rejected | Active | Superseded
Type: Standards Track | Informational | Process
Category: <registered proposal category>
Created: <DD-Mmm-YYYY>
```

Optional headers:

```
Requires: <NUC numbers>
Replaces: <NUC number>
Superseded-By: <NUC number>
```

## Required Sections

A Standards Track NUC contains these sections, in order:

- **Abstract** -- what the document specifies.
- **Motivation** -- why the feature exists and what it makes possible.
- **Rationale** -- why the design is as it is, and what was rejected.
- **Specification** -- the technical description, in enough detail to implement from.
- **Errors** -- every error the feature raises, with exact type and message.
- **Reference Implementation** -- implementation state, if any.
- **Copyright** -- the license notice; Nucleoid is licensed under Apache-2.0, and every NUC carries the same notice.

Notes:

- A section that does not apply is kept with the text "N/A" rather than dropped, so structure stays uniform.
- Informational and Process NUCs use whatever subset fits.

## Conventions

- Descriptions are short and written as bullet points; prose paragraphs are avoided.
- One point per bullet, each standing on its own.
- Code examples are Nucleoid, in fenced blocks, taken from `nucleoid.spec.md` wherever an entry covers the behaviour.
- Examples carry no explanatory comments; the bullets above them do that work.
- An abbreviated example must not change the behaviour it shows.
- Error types and messages are quoted exactly as the specification gives them, including capitalisation and punctuation — they are observable behaviour.
