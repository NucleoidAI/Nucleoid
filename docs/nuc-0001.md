## What is a NUC?

- NUC is the language proposal series, including proposals about language-development processes.
- Every NUC is evaluated as a proposal when added or updated.
- Accepted, implemented claims are the canonical documentation for the Nucleoid Language Reference.
- The format follows Python Enhancement Proposals, adapted for Nucleoid.

## Relationship to the Specification

- `nucleoid.spec.md` is normative: statements paired with the assertions that must hold after them.
- A NUC may propose syntax or behavior not yet implemented; proposal text does not change the accepted runtime.
- Where a NUC claims implemented behavior that disagrees with the specification, **the specification wins** and that claim is in error.
- Every implemented NUC claim about runtime behavior must trace to one or more spec entries.
- Candidate runtime, specification, and test rewrites remain isolated until the proposal passes evaluation.
- `dataset/nucleoid.spec.synth.*.md` holds synthesized use cases, also derived from the spec, with no independent authority.
- The spec, the synthesized sources in `dataset/` and `docs/` must stay in sync; a change to one is propagated to the others in the same change.

## NUC Types

- **Standards Track** -- a language feature: syntax, semantics, errors. Most Language Reference NUCs.
- **Informational** -- a design issue, index, or guidelines. Revisions still undergo proposal evaluation. NUC 0.
- **Process** -- a process around Nucleoid, or a change to one. This document.

## NUC Status

- **Draft** -- under development, subject to change.
- **Accepted** -- passed proposal evaluation, settled, and matching the specification.
- **Rejected** -- evaluated and refused, including any per-case token increase.
- **Active** -- informational or process NUCs that remain current; their revisions still undergo evaluation.
- **Superseded** -- replaced by a later NUC, named in `Superseded-By`.

## Proposal Evaluation

- Every added or updated `docs/nuc-XXXX.md` gets a fresh `nuc-proposal` agent in the Copilot session; one agent evaluates one proposal revision.
- Do not reuse an agent for another proposal or later revision. Evaluation status and index updates are outcomes of that revision, not recursive triggers.
- The agent profile is [nuc-proposal.agent.md](../.github/agents/nuc-proposal.agent.md); persistent session instructions are [copilot-instructions.md](../.github/copilot-instructions.md).
- Pin an accepted Git revision and record its immutable baseline before changing runtime behavior or executable cases. Do not assume a revision containing the candidate is an accepted baseline.
- Evaluate each proposal separately in a candidate worktree. Dependencies must already be accepted; do not compare combined pending proposals.
- Rewrite applicable executable source cases using the proposed syntax and implement the candidate runtime support they require. Process-only changes may leave cases unchanged.
- The measured corpus is `nucleoid.spec.md`, `tests/reference.md`, and the `nuc` blocks in `README.md` and `docs/examples.md`. Generated Rust scaffolding, JSONL, and synthesized training cases are not scored.
- Count `tokenize(case.source.trim())` from the accepted lexer before rewriting, and from the candidate lexer afterward. Count every token, including `Newline`, `Indent`, and `Dedent`, except `Eof`.
- Preserve each case's document and title, canonical assertions, expected return, and executed assertion coverage. Removing, renaming, weakening, or bypassing cases or assertions invalidates the rewrite.
- New cases require behavior-equivalent accepted-syntax baselines with the same identities and assertions, executed before candidate changes. Supply them through `NUC_PROPOSAL_EXTRA_BASELINES`; a missing baseline blocks acceptance.
- `tests/proposals.rs` records the baseline and writes a per-case report with `before`, `after`, and `less`, `same`, or `more`; commands and baseline input format are in [CONTRIBUTING.md](../CONTRIBUTING.md#evaluating-a-language-proposal).
- Accept when every paired case uses the same or fewer tokens and behavior checks pass. Reject if any case uses more tokens, even if another saves more or the total falls.
- Rewrites that fail behavior checks or change assertion or return expectations are rejected. Missing prerequisites remain blocked and Draft, not accepted by default.
- Keep baseline and report artifacts in the session workspace. Never edit a recorded baseline or replace missing measurements with estimates.
- Integrate accepted candidate changes with synchronized runtime, specification, reference, synthesized sources, and rendered exports. Do not apply rejected candidate changes or erase a user's proposal.
- Informational and Process documents may retain `Active` after an accepted revision; a rejected revision does not replace their accepted text.
- This is a Copilot-session process, not a filesystem watcher or an automatic GitHub pull-request trigger.

## NUC Format

- One Markdown file per NUC, named `nuc-XXXX.md` with a zero-padded number.
- Opens with `# NUC N -- Title`, then a fenced header block in RFC 822 style.

Required headers:

```
NUC: <number>
Title: <title>
Author: <name> <<email>>
Status: Draft | Accepted | Rejected | Active | Superseded
Type: Standards Track | Informational | Process
Created: <DD-Mmm-YYYY>
```

Optional headers:

```
Requires: <NUC numbers>
Replaces: <NUC number>
Superseded-By: <NUC number>
```

## Required Sections

A Standards Track NUC contains these sections, in order:

- **Abstract** -- what the document specifies.
- **Motivation** -- why the feature exists and what it makes possible.
- **Rationale** -- why the design is as it is, and what was rejected.
- **Specification** -- the technical description, in enough detail to implement from.
- **Errors** -- every error the feature raises, with exact type and message.
- **Reference Implementation** -- implementation state, if any.
- **Copyright** -- the license notice; Nucleoid is licensed under Apache-2.0, and every NUC carries the same notice.

Notes:

- A section that does not apply is kept with the text "N/A" rather than dropped, so structure stays uniform.
- Informational and Process NUCs use whatever subset fits.

## Conventions

- Descriptions are short and written as bullet points; prose paragraphs are avoided.
- One point per bullet, each standing on its own.
- Code examples are Nucleoid, in fenced blocks, taken from `nucleoid.spec.md` wherever an entry covers the behaviour.
- Examples carry no explanatory comments; the bullets above them do that work.
- An abbreviated example must not change the behaviour it shows.
- Error types and messages are quoted exactly as the specification gives them, including capitalisation and punctuation — they are observable behaviour.
