## What is a NUC?

- NUC is the language proposal series, including proposals about language-development processes.
- Every NUC is evaluated as a proposal when added or updated.
- Accepted, implemented claims are the canonical documentation for the Nucleoid Language Reference.
- The format follows Python Enhancement Proposals, adapted for Nucleoid.

## Relationship to the Specification

- `nucleoid.spec.md` is normative: statements paired with the assertions that must hold after them.
- A NUC may propose syntax or behavior not yet implemented; proposal text does not change the accepted runtime.
- Where a NUC claims implemented behavior that disagrees with the specification, **the specification wins** and that claim is in error.
- Every implemented NUC claim about runtime behavior must trace to one or more spec entries.
- Candidate runtime, specification, and test rewrites remain isolated until the proposal passes evaluation.
- `dataset/nucleoid.synth.*.jsonl` and `dataset/arc.jsonl` are canonical, self-contained synthesized and ARC training records, not Markdown-derived copies; they have no independent authority over the root specification.
- The root spec, relevant training JSONL, the language reference in `docs/`, and runtime semantics must stay in sync; propagate affected behavior changes in the same change.
- Preserve training-record IDs, assertions, expected results, and coverage when updating relevant JSONL.
- `dataset/` must contain only regular `.jsonl` files, with no Markdown files or subdirectories.
- Do not recreate or relocate duplicate Markdown datasets or dataset cards; `docs/dataset/` must not exist.
- The root `nucleoid.spec.md` remains authoritative; `dataset/nucleoid.spec.jsonl` is generated from it and regenerated when it changes, never hand-edited.

## NUC Types

- **Standards Track** -- a language feature: syntax, semantics, errors. Most Language Reference NUCs.
- **Informational** -- a design issue, index, or guidelines. Revisions still undergo proposal evaluation. NUC 0.
- **Process** -- a process around Nucleoid, or a change to one. This document.

## NUC Status

- **Draft** -- under development, subject to change.
- **Accepted** -- passed proposal evaluation, settled, and matching the specification.
- **Rejected** -- evaluated and refused, including any per-case token increase.
- **Active** -- informational or process NUCs that remain current; their revisions still undergo evaluation.
- **Superseded** -- replaced by a later NUC, named in `Superseded-By`.

## Proposal Evaluation

- Every added or updated `docs/nuc-XXXX.md`, including process and documentation-only changes, requires a fresh `nuc-proposal` agent followed by a separate, independent fresh `nuc-evaluate` agent for that revision.
- Preparation follows the [nuc-proposal profile](../.github/agents/nuc-proposal.agent.md) and [proposal skill](../.github/skills/nuc-proposal/SKILL.md).
- Independent evaluation follows the [nuc-evaluate profile](../.github/agents/nuc-evaluate.agent.md) and [evaluation skill](../.github/skills/nuc-evaluate/SKILL.md).
- Persistent session instructions are [copilot-instructions.md](../.github/copilot-instructions.md).
- The caller launches both stages; neither role spawns agents or is reused for another role, proposal, or revision. If named agents are unavailable, the caller supplies each profile and skill to separate fresh general-purpose agents.
- Pin an accepted Git revision and record its immutable baseline before changing runtime behavior or executable cases. Do not assume a revision containing the candidate is an accepted baseline.
- Prepare and evaluate each revision in an isolated candidate worktree. Dependencies must already be accepted; do not combine pending proposals. Concurrent revisions that rewrite shared files need separate worktrees.
- The proposal agent drafts and prototypes one revision, implementing candidate runtime support and rewriting equivalent executable source cases where necessary. Process-only changes need no runtime or corpus rewrite or artificial new cases.
- Preserve each case's document and title, assertion order and canonical assertions, expected return, and executed assertion coverage. Removing, renaming, weakening, replacing assertions with tautologies, or bypassing cases or assertions invalidates the rewrite.
- The proposal agent synchronizes affected reference, canonical training JSONL, runtime semantics, and generated normative exports.
- Edit normative source documents and regenerate affected exports, never hand-edit generated Rust or `dataset/nucleoid.spec.jsonl`; maintain synthesized and ARC training records directly as canonical JSONL.
- The proposal agent runs relevant development tests, formatting, and warning-denied Clippy. It must not run `evaluate_proposal`, produce an acceptance report, or declare Accepted or Rejected.
- The proposal agent returns a frozen handoff: proposal path and Git blob revision, accepted baseline revision and artifact, candidate worktree, changed files, development checks, and explicit blockers. It then stops editing the candidate.
- After the completed handoff, the caller launches the fresh evaluation agent with that handoff and a fresh report path. The evaluator verifies the proposal blob and baseline revision independently.
- The evaluator treats candidate sources, canonical training JSONL, generated normative exports, and the baseline as read-only; no repairs, case rewrites, regeneration, or status/index edits. It may write only new session reports and normal ignored build outputs.
- The evaluator independently validates behavior, development checks, and export consistency, then runs the actual per-case `evaluate_proposal` gate. Only this role returns the acceptance decision.
- A substantive revision, repair, rebase, or source change after handoff requires a new fresh proposal/evaluation pair, not an in-place evaluator repair.
- The measured corpus is `nucleoid.spec.md`, `tests/reference.md`, and the `nuc` blocks in `README.md` and `docs/examples.md`. Generated Rust scaffolding, JSONL, and synthesized training cases are not scored.
- Count `tokenize(case.source.trim())` from the accepted lexer before rewriting, and from the candidate lexer afterward. Count every token, including `Newline`, `Indent`, and `Dedent`, except `Eof`.
- New cases require behavior-equivalent accepted-syntax baselines with the same identities, canonical assertions, and expected returns, executed by the accepted runtime before candidate changes. Supply them through `NUC_PROPOSAL_EXTRA_BASELINES` when recording the baseline; a missing baseline blocks acceptance.
- `tests/proposals.rs` records the baseline and writes a per-case report with `before`, `after`, and `less`, `same`, or `more`; commands and baseline input format are in [CONTRIBUTING.md](../CONTRIBUTING.md#evaluating-a-language-proposal).
- The evaluator accepts only when every paired case uses the same or fewer tokens and all behavior and development checks pass. Any case using more tokens rejects the revision, even if another saves more or the total falls.
- Rewrites that fail behavior checks or change protected assertions, returns, or coverage are rejected. Missing prerequisites block acceptance; unevaluated drafts remain Draft, not accepted by default.
- Keep immutable baseline and create-once report artifacts in the session workspace. Never edit or overwrite them or replace missing measurements with estimates.
- The caller integrates unchanged accepted candidates with synchronized runtime, specification, reference, canonical training JSONL, and generated normative exports; serialize integration. Do not apply rejected candidates or erase another user's changes or proposal.
- The caller owns evaluation status and index metadata; these outcomes do not recursively trigger another pair.
- Informational and Process documents may retain `Active` after an accepted revision; a rejected revision does not replace their accepted text.
- This is a Copilot-session process, not a filesystem watcher, GitHub Actions workflow, or automatic pull-request trigger.

## NUC Format

- One Markdown file per NUC, named `nuc-XXXX.md` with a zero-padded number.
- Opens with `# NUC N -- Title`, then a fenced header block in RFC 822 style.

Required headers:

```
NUC: <number>
Title: <title>
Author: <name> <<email>>
Status: Draft | Accepted | Rejected | Active | Superseded
Type: Standards Track | Informational | Process
Created: <DD-Mmm-YYYY>
```

Optional headers:

```
Requires: <NUC numbers>
Replaces: <NUC number>
Superseded-By: <NUC number>
```

## Required Sections

A Standards Track NUC contains these sections, in order:

- **Abstract** -- what the document specifies.
- **Motivation** -- why the feature exists and what it makes possible.
- **Rationale** -- why the design is as it is, and what was rejected.
- **Specification** -- the technical description, in enough detail to implement from.
- **Errors** -- every error the feature raises, with exact type and message.
- **Reference Implementation** -- implementation state, if any.
- **Copyright** -- the license notice; Nucleoid is licensed under Apache-2.0, and every NUC carries the same notice.

Notes:

- A section that does not apply is kept with the text "N/A" rather than dropped, so structure stays uniform.
- Informational and Process NUCs use whatever subset fits.

## Conventions

- Descriptions are short and written as bullet points; prose paragraphs are avoided.
- One point per bullet, each standing on its own.
- Code examples are Nucleoid, in fenced blocks, taken from `nucleoid.spec.md` wherever an entry covers the behaviour.
- Examples carry no explanatory comments; the bullets above them do that work.
- An abbreviated example must not change the behaviour it shows.
- Error types and messages are quoted exactly as the specification gives them, including capitalisation and punctuation — they are observable behaviour.
