# NUC 17 -- Object-Property Shorthand

```
NUC: 17
Title: Object-Property Shorthand
Author: Copilot <223556219+Copilot@users.noreply.github.com>
Status: Accepted
Type: Standards Track
Created: 13-Oct-2026
Requires: 12
```

## Abstract

- Specifies an ordinary identifier field in an object-literal expression as behavior-equivalent shorthand for an explicit same-name field.
- `{ amount, label }` has exactly the AST and behavior of `{ amount: amount, label: label }`.
- Preserves explicit fields, object evaluation, canonical expanded source, expression/block disambiguation, and existing diagnostics.

## Motivation

- Repeating a field name as its identifier value contributes syntax without expressing another relationship.
- Object expressions that package named inputs become shorter without losing their reactive relationships.
- Reusing existing field tuples avoids a new token, AST variant, runtime operation, or library API.

## Rationale

- Only a key token that is an ordinary `Token::Identifier` identifies both the string key and the identifier expression.
- Quoted and numeric keys retain their existing explicit-value grammar; keyword, class-reference, dotted, and computed keys do not gain shorthand.
- A comma or closing brace after the identifier, allowing only existing newline/semicolon separators, makes the field boundary unambiguous.
- Read-only lookahead preserves the old missing-colon error and position when the following token cannot end a field.
- Explicit `key: expression` remains on the existing expression parser and retains its errors.
- Canonical source remains quoted and expanded so assertions, graph keys, and reasoning sources cannot distinguish equivalent spellings.
- Existing statement blocks and anonymous arrow bodies remain blocks; object shorthand does not introduce implicit returns.
- Indentation changes, colon continuation, closure capture, destructuring, new key grammar, and parenthesis-free function definitions are out of scope.
- Existing object-literal behavior is defined by authoritative [nucleoid.spec.md](../nucleoid.spec.md); named expression returns depend on accepted [NUC 12](nuc-0012.md).

## Specification

### Field lowering

- In an existing object-literal expression context, consuming an ordinary identifier key `name` may omit its colon and value only at a proper field boundary.
- The shorthand field is exactly `(name, Expr::Identifier(name))` in the existing `Expr::ObjectLiteral(Vec<(String, Expr)>)`.
- The key's spelling is its string key; its value is an ordinary identifier read in the current scope, not a string or property lookup.
- Ordinary identifiers retain the existing lexer grammar, including underscores and digits after the first character.
- Keyword aliases such as `self`, `None`, and `undefined` are not ordinary identifier tokens.
- An explicit string key whose text is an ordinary identifier, such as `"amount": amount`, has the same field tuple; a bare quoted string is still not shorthand.
- Keys with different names, expression values, numeric keys, and snapshot values still need their explicit fields.
- For example, `amount: other`, `"quoted-key": label`, `1: amount`, and `amount: amount.value` do not shorten to bare keys.

### Boundaries and existing contexts

- After the identifier key, look ahead through only `Newline` and `Semicolon` tokens.
- The next token must be `Comma` or `RightBrace`; lookahead does not consume any token.
- Otherwise, require `Colon` immediately after the key and use the existing expression parser, including its syntax diagnostics and positions.
- A colon already following the key always selects that unchanged explicit-value path.
- The object parser then skips its existing newline/semicolon separators and consumes the comma or closing brace as before.
- Commas remain necessary between fields; semicolons and physical line breaks do not replace them.
- Existing leading separators, trailing commas, empty objects, explicit values, nested objects, lists, and parenthesized continuations remain supported.
- `Indent` and `Dedent` are not field-boundary separators.
- Indented multiline braces still require an existing layout-suppressing expression context, such as the outer parentheses in the mixed-field specification entry.
- This proposal does not extend colon continuation across a logical line.
- Assignment values, returns, call arguments, lists, grouping, and named arrow expression bodies keep their existing object-expression contexts.
- Statement-leading `{ amount }` remains a statement block.
- Named `def wrap(amount) => { amount }` returns an object through the existing single-return block lowering.
- Anonymous `amount => { amount }` remains a statement block and returns `null` without an explicit return.
- An anonymous arrow returning an object still uses `amount => ({ amount })`, or an explicit return from its block.
- Ordinary function definitions still require their parameter parentheses and retain their existing block-return rules.

### Inherited evaluation and canonical source

- Both spellings use the same ordered field vector and existing object evaluator.
- Values evaluate in field order, including fields later replaced by a duplicate key.
- Duplicate keys replace their earlier values while preserving the key's original insertion position.
- Mixed explicit fields and nested shorthand objects retain those same rules.
- An identifier value follows existing global, local, parameter, and receiver scope resolution.
- Object values and aliases retain their existing identities; shorthand does not copy a referenced object or change the literal's allocation path.
- Returning a local value in an object does not introduce capture of the callee's parameters by a returned anonymous function.
- Identifier reads inside objects remain reactive dependencies; changing their inputs updates existing dependent relationships.
- `.value` snapshots stay explicit and preserve their existing fixed values and absence of dependency edges.
- An undefined identifier read inside an object raises the existing reference error, rather than silently creating a `null` property.
- A failed transaction restores the previous object value and its dependencies, including after replacing a shorthand object with another one.
- The canonical generator remains unchanged: `{ amount }` displays as `{"amount":amount}`, and duplicate fields remain in their original AST order.
- Graph keys and reasoning rule source use that same expanded canonical representation.
- Existing resource limits, public lexer tokens, AST variants, object runtime, generator, and API remain unchanged.

- Only direct same-name identifier fields in those paired sources are shortened.

## Errors

- The shorthand introduces no new error kind, message format, runtime restriction, or caught-value format.
- The strict missing-name error is exactly `ReferenceError("missing is not defined")`, as asserted by the paired snapshot/undefined-read entry.
- The paired rollback entry catches the exact thrown value `"ABORT"`; shorthand does not intercept or transform failures.
- Other explicit value-expression failures propagate through the unchanged evaluator and transaction machinery.
- Invalid boundaries still use the existing `SyntaxError` missing-colon diagnostic; invalid key tokens still use the existing expected-key diagnostic.
