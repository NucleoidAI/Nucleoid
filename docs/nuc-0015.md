# NUC 15 -- Parenthesis-Free Nullary Function Definitions

```
NUC: 15
Title: Parenthesis-Free Nullary Function Definitions
Author: Copilot <223556219+Copilot@users.noreply.github.com>
Status: Rejected
Type: Standards Track
Category: Syntax enhancement
Created: 13-Oct-2026
Requires: 8, 12
```

## Abstract

- A named zero-parameter function or method may omit its empty `()` immediately before `:` or `=>` on its logical header line.
- The compact spelling has exactly the existing parenthesized definition's syntax tree and runtime behavior.
- Calls remain explicit: `total()` calls the function; `total` reads its value or reference.
- Independent evaluation rejected this revision; the prototype is not part of the accepted language.

## Motivation

- Empty parameter lists repeat punctuation without declaring a parameter.
- Remove that repetition from named definitions while preserving callable references and ordinary call syntax.
- Reuse existing tokens, parameter types and body representations rather than introducing a function kind.

## Rationale

- Require a body marker immediately after the name so omission cannot consume parameters or a following statement.
- Keep parentheses around every nonempty parameter list and around a zero-argument anonymous arrow's parameter list.
- Keep named arrow bodies on the accepted [NUC 12](nuc-0012.md) block-with-return execution path.
- Keep parenthesized definitions valid; there is no automatic invocation, getter, bodyless definition or return annotation.
- Depend only on the already accepted behavior of [NUC 8](nuc-0008.md) and NUC 12, not another pending proposal.

## Specification

### Definition headers

- After `def` and the existing required name, inspect the next token without skipping separators.
- If that token is `:` or `=>`, use the existing empty `Vec<Parameter>` instead of parsing `()`.
- Otherwise, use the existing parameter parser, including its expected-parenthesis diagnostics.
- `def total => expression` is exactly `def total() => expression`.
- `def total:` followed by a suite is exactly `def total():` followed by that same suite.
- The colon introduces the existing suite grammar, including its indented and single-line forms; it is not a return annotation.
- Methods and `init` use the same named-definition rule through the existing class parser.
- Class declaration parameter lists and every nonempty function parameter list remain unchanged.

### Lines and bodies

- The body marker must be the next token on the same logical header line as the name.
- Do not skip `Newline`, `Semicolon`, `Indent` or `Dedent` to find that marker.
- Existing whitespace and comments retain their lexer behavior; a comment ending the header line does not join it to the next line.
- The expression after `=>` must begin on that logical line; parenthesized continuation inside the body still permits physical line breaks.
- Named arrow bodies lower to `FunctionBody::Block` containing `Stmt::Return(Some(expression))`, just as in NUC 12.
- A colon body retains its existing statements and return flow; no implicit return is added to a suite.
- Braces in a named arrow body still denote an object literal rather than a statement block.
- Anonymous zero-argument arrow functions retain `() => expression`; anonymous `function()` bodies are unchanged.

### Reactive functions

- Names, scope lookup, state reads, dependencies and callable redefinition retain the behavior of the [main specification](../nucleoid.spec.md).
- Calls still require parentheses; the compact definition does not turn a bare name into a call.
- `Nucleoid keeps parenthesis free nullary functions reactive` specifies state-read propagation and redefinition.

```nuc
source = 2
def reading => source + 1
answer = reading()
assert(answer, 3)
source = 4
assert(answer, 5)
def reading => source * 3
assert(answer, 12)
```

### Suites, methods and initialization

- No-return suites still return `null`; explicit returns keep their existing values and effects.
- Methods retain receiver binding; `this` and `self` remain interchangeable.
- A nullary `init` uses the existing initializer-adoption path; construction returns the instance.
- `Nucleoid keeps parenthesis free nullary blocks and methods equivalent` specifies a pass-only function, block initializer, arrow method and multi-statement method.

```nuc
seed = 3
def empty:
    pass
assert(empty(), null)
class Gauge:
    def init:
        this.amount = seed
    def reading => self.amount
    def adjust:
        this.amount = this.amount + 1
        return this.amount
gauge = Gauge()
assert(gauge.amount, 3)
assert(gauge.reading(), 3)
assert(gauge.adjust(), 4)
assert(gauge.reading(), 4)
```

### Callable values

- A live named reference follows redefinitions; `.value` retains its captured definition.
- State read by a captured definition and anonymous functions returned by it keep their existing behavior.
- `Nucleoid preserves parenthesis free nullary callable references` specifies live references, snapshots and a returned parameterized anonymous function.

```nuc
def literal => 4
live = literal
snapshot = literal.value
assert(live(), 4)
assert(snapshot(), 4)
def literal => 7
assert(live(), 7)
assert(snapshot(), 4)
def factory => number => number * 2
double = factory()
assert(double(3), 6)
```

### Compatibility and isolation

- Canonical AST rendering and generated graph source remain identical to the fully parenthesized spelling.
- Transactions, rollback and parser/runtime resource limits remain unchanged.
- Existing normative nullary definitions are rewritten only by removing their header's empty `()`; call sites and unrelated body syntax are preserved.
- Preserve document/title identities, canonical assertions in order, expected returns and executed assertion coverage.
- The six new measured cases have already executed accepted-syntax counterparts in the caller's immutable baseline.
- No additional measured case is introduced without its own accepted-syntax baseline.
- The prototype remains isolated after rejection under [NUC 1](nuc-0001.md#proposal-evaluation); its language changes were not integrated.

## Reference Implementation

- The rejected, isolated prototype changes [`Parser::function_statement`](../src/lang/ast/parser.rs) to select an empty parameter vector only when its immediate lookahead is `Colon` or `Arrow`.
- Existing suite parsing, named-arrow block lowering, class-method parsing and [`ClassData::adopt_initializer`](../src/nuc/class.rs) are reused without runtime changes.
- No token, public enum variant, API, dependency or project release metadata is added or changed.
- The isolated candidate's three new normative entries named above cover its reactive, method, return and reference claims; they were not added to the accepted specification.
- The prototype's equivalent header rewrites preserve existing spec coverage, including:
  - `Nucleoid restores enclosing null tracking after failed local assignments`.
  - `Nucleoid restores enclosing null tracking after failed property assignments`.
  - `Nucleoid ends temporary undefined reads when a deletion cascade finishes`.
  - `Nucleoid tracks named functions forwarded as values`.
  - `Nucleoid treats this and self as interchangeable instance keywords`.
  - `Nucleoid keeps expression bodied methods and initializers equivalent`.
  - `Nucleoid preserves expression body returns and callable references`.
- Prototype parser tests compare syntax trees and canonical rendering for both body forms, methods, initializers, returned lambdas and physical-line continuations.
- Prototype integration tests verify exact errors and positions, graph-source equivalence, references and snapshots, failed redefinitions, method rollback and resource-limit recovery in normal Rust test threads.
- The isolated candidate adds the three other pre-baselined measured cases to its executable reference, README and examples; its synchronized synthesized sources and generated exports were not integrated.
- Only rejection metadata is recorded in the accepted repository; the runtime, executable documents, reference, training data, generated exports and project versions remain unchanged.

### Evaluation outcome

- Frozen proposal Git blob: `80fcc9229e4cb61fe9ccdb4d20540955ec56d33d`.
- Accepted baseline Git revision: `c769225eed62e53005972d564ca86f16f1947822`.
- The per-case lexer gate passed all 377 paired cases: 19 used fewer tokens, 358 used the same, and none used more; no identity, assertion, return or executed-coverage issues were found.
- Counts measure trimmed source with the runtime lexer, including layout markers and excluding only `Eof`; they are not LLM token counts.
- Overall decision: **Rejected**, because independent Windows debug CLI checks failed the required resource-limit errors and recovery.
- A definition containing 4096 nested parentheses and a directly recursive nullary call both terminated the CLI with `0xC00000FD` (`STATUS_STACK_OVERFLOW`) rather than returning the required structured error.
- Both compact and parenthesized definitions failed in the candidate. The caller reproduced both failures with parenthesized syntax in the unchanged accepted CLI at the pinned baseline, confirming a pre-existing blocker rather than a demonstrated header-specific regression.
- The required Rust improvement pass found no justified source changes; the original handoff remained frozen throughout evaluation.
- Baseline, gate, independent-check and accepted-CLI reproduction reports remain in the session workspace. Fixing the inherited CLI stack-safety issue is outside this grammar proposal.
