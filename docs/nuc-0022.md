# NUC 22 -- Reactive Numeric Interpolation

```
NUC: 22
Title: Reactive Numeric Interpolation
Author: Copilot <223556219+Copilot@users.noreply.github.com>
Status: Accepted
Type: Standards Track
Created: 14-Oct-2026
```

## Abstract

- Add static `Math.lerp(start, end, weight)` as one bounded runtime capability.
- Convert inputs numerically, then subtract, multiply and add in the exact
  accepted ordinary arithmetic order `start + (end - start) * weight`.
- Keep all three inputs reactive through the existing static Math call path,
  without changing syntax, coercion, dependencies, deferred reads or transactions.

## Motivation

- Animated positions, numeric blends and live progress values otherwise restate
  an arithmetic relationship and repeat the start expression.
- Provide one intrinsic numeric operation that does not accidentally concatenate
  string inputs through the language's ordinary `+`.
- Let weights outside zero through one extrapolate without introducing a separate
  validation or clamping policy.

## Rationale

- Choose the accepted ordinary arithmetic order deliberately rather than promise
  optimized, weighted, clamped or higher-precision interpolation.
- Preserve rounding at each subtraction, multiplication and addition, including
  overflow, cancellation, signed zeros, infinities and numeric `NaN`.
- Reject fused arithmetic, alternate formulas, midpoint/endpoint shortcuts and
  endpoint validation/reordering: each can change an observable result.
- In particular, a zero weight does not suppress `Infinity * 0`, and equal
  infinite endpoints do not suppress `Infinity - Infinity`.
- Use the existing fixed-arity omission convention, numeric `NaN`, not a new
  arity error or an undefined property read.
- Ignore extra values numerically without suppressing their once-only evaluation,
  read dependencies or participation in the existing any-`Undefined` gate.
- Make numeric conversion intrinsic; resolving a shadowable `Number()` function
  would introduce a dependency and potentially change the result.
- Require no pending proposal: established Math behavior comes from
  `nucleoid.spec.md`, not from treating Draft NUC10 as an accepted dependency.
- Leave aliases, callable method values, closure capture, namespace redesign,
  public representations, dependencies and inherited scope/resource limits alone.

## Specification

### Static numeric contract

- The authoritative [`Reactive numeric interpolation` section](../nucleoid.spec.md#reactive-numeric-interpolation)
  and its five executable entries define this capability's behavior.
- An unshadowed static `Math.lerp(...)` call uses the existing Math dispatcher.
- After the unchanged any-`Undefined` gate, convert each of the first three
  supplied values with `Value::to_number`; each omitted position supplies `NaN`.
- Numbers keep their value, literal `null` becomes zero, booleans become
  zero/one, trimmed strings and empty/singleton lists retain their numeric
  conversion, and dates contribute their millisecond value.
- Other nonnumeric conversions yield numeric `NaN`; there is no new type constraint.
- Let `start`, `end` and `weight` below denote the three converted `f64` numbers.
- First compute `delta = end - start` using ordinary accepted subtraction.
- Next compute `scaled = delta * weight` using ordinary accepted multiplication.
- Finally compute `result = start + scaled` using ordinary accepted addition.
- Do not fuse, rearrange, raise precision or replace any of these operations.
- Weights below zero or above one extrapolate; weights are never clamped.
- Equal/reversed endpoints, infinities, overflow, cancellation, numeric `NaN`
  in any position and signed zeros follow those same ordered operations.
- `0 + Infinity * 0` and `Infinity - Infinity` therefore yield numeric `NaN`,
  not an endpoint or equal-endpoint shortcut.
- A finite endpoint difference may overflow before scaling; a weight of one
  is not a promise to reproduce the end value after that overflow or cancellation.
- Extra supplied values do not enter the numeric formula.

### Evaluation, reactivity and compatibility

- Evaluate every supplied argument expression exactly once from left to right
  before dispatch, including expressions whose extra values are ignored numerically.
- Keep the existing Math gate over all supplied values: any `Undefined`,
  including an extra, returns `Undefined` before numerical dispatch.
- An omitted numeric position is not a supplied undefined read.
- Dependent assignments retain existing live-null/deferred-read handling,
  storing `null` and recovering when their missing properties are defined.
- Literal-null numeric conversion does not override that live assignment context.
- Preserve all argument reads, named-wrapper dependencies, class rules,
  object-property deletion/recovery, transaction rollback and subsequent propagation.
- Strict unknown identifiers still throw during argument evaluation, even in an
  extra or after an undefined property; numeric conversion does not catch the error.
- State variables and local bindings named `Math` keep their namespace shadowing.
- Ordinary `.Math` properties and methods keep their existing lookup behavior.
- `Math.lerp` read as a value stays unsupported/`Undefined`, like other Math
  method references; no first-class callable or callable alias is added.
- Numeric conversion does not call or subscribe to a `Number` name.
- Keep `Math.clamp`, `min`, `max`, `round`, other Math members, accepted syntax,
  operators, coercion, error representations and public Rust types/APIs unchanged.
- Add no new local capture or remedy for inherited parameter-dependent/nested
  noncapturing failures or extreme Windows debug stack limitations.

## Errors

- Introduce no new error kind, numeric-coercion error, arity error, endpoint
  validation error or weight-range error.
- Numeric `NaN`, omitted inputs and all special-value results are defined above,
  not swallowed errors.
- Argument-expression failures keep their inherited exact types/messages,
  top-level statement positions and caught values.
- Failed updates/redefinitions roll back before subsequent reactive recovery.
- Static namespace shadowing preserves ordinary receiver-specific errors.

| Condition | Exact inherited error |
| --- | --- |
| Strict unknown argument identifier `missing`, including an extra | `ReferenceError("missing is not defined")` |
| An unchanged unknown static Math method `unknown` | `TypeError("Math.unknown is not a function")` |
| The unchanged unsupported static random operation | `TypeError("Math.random is not supported")` |
| Calling `Math.lerp(...)` when state `Math` is the number `7` | `TypeError("number.lerp is not a function")` |

- Unknown/random static dispatch remains subject to the existing any-undefined gate.
- No argument is silently skipped to avoid an error or undefined read.

## Reference Implementation

- The isolated prototype adds only one narrow `lerp` arm to
  [`src/builtins/mod.rs`](../src/builtins/mod.rs), reusing fixed-arity coercion idioms.
- The common first-value conversion supplies the start number; the arm converts
  the second/third inputs and performs subtraction, multiplication, then addition.
- No lexer/parser/generator, public Global/Value/AST/API, call/member resolution,
  operator/coercion, class, scope, dependency, MSRV or version change is needed.
- Builtin tests compare every concrete Value kind and special-number/zero bits
  against the existing ordered binary arithmetic, with omission/extra/undefined checks.
- [`tests/math_lerp.rs`](../tests/math_lerp.rs) covers live inputs, coercion,
  nonfinite/overflow/cancellation results, once-only ordered effects, strict errors,
  rollback/recovery, live-null and class/property contexts, named dependencies,
  Number/Math shadowing, unsupported method reads and other-Math regressions.
- Native tests use ordinary exact-byte files and REPL stdin, without named-pipe
  fixtures or automatically appended EOF newlines; only owned probes are removed.
- [`tests/nuc22_compatibility.rs`](../tests/nuc22_compatibility.rs) uses closed,
  typed document metadata; its ignored paired audit uses actual pinned Git
  sources and sealed extras, while ordinary metadata uses shipped source data.
- Reuse `common::assertions` and `common::check_with_count` for ordered canonical
  assertions, normative expected-return matching and same-execution coverage.
- The fresh NUC22 audit checks the 30 registered RHS changes, explicit Number
  conversions and raw exceptions without introducing another assertion walker.
- The directly coupled NUC21/22 ordinary metadata helpers purely validate exact
  historical source prefixes, rejecting short/duplicate sources and misordered
  or renamed registered tails without needing Git in shallow checkouts or archives.
- Forward-addition regressions protect both snapshots, and subprocess checks
  execute the ordinary metadata tests with no Git executable or accessible
  repository/object directories; no source fixture or baseline artifact is copied.
- Historical NUC documentation and ignored historical audits remain unchanged.
- Edit source documents only; render JSONL with `UPDATE_DATASET=1 cargo test --test dataset`
