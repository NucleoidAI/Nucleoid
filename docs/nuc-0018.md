# NUC 18 -- Bare Single-Parameter Named Arrows

```
NUC: 18
Title: Bare Single-Parameter Named Arrows
Author: Copilot <223556219+Copilot@users.noreply.github.com>
Status: Accepted
Type: Standards Track
Created: 14-Oct-2026
Requires: 12
```

## Abstract

- A named arrow definition or method may omit parameter parentheses for exactly one untyped ordinary identifier.
- `def double amount => amount * 2` is exactly `def double(amount) => amount * 2`.
- The candidate reuses the named return-block representation of accepted [NUC 12](nuc-0012.md), without changing public tokens, AST types, runtime behavior or canonical output.

## Motivation

- Parentheses around one untyped named-arrow parameter add delimiters without resolving an ambiguity.
- Keep the declaration name, parameter and arrow explicit while reducing syntax for single-input relationships.
- Keep all parenthesized definitions and calls available rather than introducing a new invocation or binding mode.

## Rationale

- Recognize only immediate `Identifier` followed by `Arrow` after `def` and the required function name.
- Do not skip separators or infer annotations, defaults or destructuring from another prefix.
- Reuse `Parameter { name, type_name: None }` and NUC 12's `FunctionBody::Block` containing one `Stmt::Return(Some(expression))`.
- Keep parentheses for block bodies, typed parameters, empty parameter lists and multiple parameters.
- Keep ordinary identifiers as references, calls parenthesized, and anonymous single-identifier arrows unchanged.
- Require only NUC 12, whose status is Accepted; do not combine a pending proposal or adopt rejected NUC 15's broader omissions.
- Keep canonical name-based function rendering and explicit-return body rendering, not a new generator spelling.

## Specification

### Grammar and scope

- The [authoritative specification](../nucleoid.spec.md), including its `Bare single-parameter named arrows` section, governs the prototype.
- Parse `def` and the required name exactly as before.
- If the next token is `Token::Identifier` and `peek_at(1)` is `Token::Arrow`, consume exactly that identifier as one untyped parameter.
- Otherwise call the existing parenthesized parameter parser unchanged, preserving its errors and source positions.
- After the parameter, reuse the existing named-arrow expression or block-suite path without modifying expression precedence.
- The same guard applies to methods and `init`, because they already use the named function-statement parser.
- Whitespace must keep the definition name and bare parameter as separate tokens; no logical newline or semicolon is skipped between the name, parameter, arrow or first body expression.
- A body expression beginning with `(` on the logical header line may continue across physical lines under the existing lexer rules.
- Braces after the named arrow remain object literals, not statement blocks; object indentation restrictions remain unchanged.
- A returned anonymous function retains its own expression/block grammar and existing noncapturing parameter behavior.
- Bare typed, nullary, multi-parameter, defaulted, destructured and block definitions are not added.
- Return annotations, call-site parenthesis omission, automatic ordinary-identifier calls and new colon precedence are not added.

### Runtime equivalence

- Global and local lookups, parameter shadowing and assignment-expression effects are unchanged.
- A missing argument still binds `null`; extra arguments keep the existing handling.
- Annotations on parenthesized parameters remain intact and use their existing runtime behavior.
- Calls remain reactive to their arguments, body dependencies and named redefinitions.
- Live callable references follow redefinitions; `.value` captures the definition, not the state subsequently read by its body.
- Methods preserve their receiver; `this` and `self` still share the same binding.
- Expression-bodied `init` still uses initializer adoption and construction returns the instance, not the expression result.
- Existing parent constructors and explicit `super(arguments)` still run on the accepted path.
- Failed definitions or redefinitions preserve transaction rollback, caught error values, graph edges and subsequent recovery.
- Existing parser and runtime resource bounds are not bypassed or changed.
- Public `Token`, `Parameter`, `Function`, `FunctionBody` and runtime/generator types remain unchanged.

- This complete example is the new reactive entry without its title comment.

```nuc
base = 2

def scaled amount => amount + base

result = scaled(3)

assert(result, 5)

base = 4

assert(result, 7)

def scaled amount => amount * base

assert(result, 12)
```

- This complete example is the new method/initializer entry without its title comment.

```nuc
class Gauge:
    def init amount => this.amount = amount
    def reading offset => self.amount + offset

gauge = Gauge(4)

assert(gauge.amount, 4)
assert(gauge.reading(3), 7)

gauge.amount = 6

assert(gauge.reading(3), 9)
```

## Errors

- No new error kind or runtime message is introduced.
- Unsupported headers retain the mandatory parameter-parenthesis diagnostics before consuming the unsupported prefix.
- The exact exercised errors below follow the normative boundary section and existing expression/runtime rules.

| Condition or input | Exact error |
| --- | --- |
| `def f amount:`, `def f amount: int => amount`, `def f amount, other => amount`, or `amount` separated from `=>` by a logical newline/semicolon | `SyntaxError("Expected '(' but found identifier 'amount'")` |
| Bare default, unrelated identifier or return-annotation prefix after `amount` | `SyntaxError("Expected '(' but found identifier 'amount'")` |
| `def f => 1` | `SyntaxError("Expected '(' but found '=>'")` |
| Logical newline immediately after `def f` | `SyntaxError("Expected '(' but found end of line")` |
| Semicolon immediately after `def f` | `SyntaxError("Expected '(' but found ';'")` |
| End of input immediately after `def f` | `SyntaxError("Expected '(' but found end of input")` |
| `def f 1 => 1` | `SyntaxError("Expected '(' but found number 1")` |
| `def f this => this` | `SyntaxError("Expected '(' but found keyword 'this'")` |
| `def f [amount] => amount` | `SyntaxError("Expected '(' but found '['")` |
| `def f {amount} => amount` | `SyntaxError("Expected '(' but found '{'")` |
| `def f $Amount => 1` | `SyntaxError("Expected '(' but found '$Amount'")` |
| A string instead of a parameter | `SyntaxError("Expected '(' but found a string")` |
| `def f ...amount => amount` | `SyntaxError("Expected '(' but found '.'")` |
| `def f(amount:) => amount` | `SyntaxError("Expected a type but found ')'")` |
| `def f(amount = 1) => amount` | `SyntaxError("Expected ')' but found '='")` |
| `def f(amount => amount` | `SyntaxError("Expected ')' but found '=>'")` |
| `def f(1) => 1` | `SyntaxError("Expected a parameter but found number 1")` |
| `def f() -> int => 1` | `SyntaxError("Expected ':' but found '-'")` |
| End of input after a bare parameter and `=>` | `SyntaxError("Unexpected end of input")` |
| Logical newline before the first expression after `=>` | `SyntaxError("Unexpected end of line")` |
| Named arrow object body containing `return` as a key | `SyntaxError("Expected a key but found keyword 'return'")` |
| Named arrow object key followed by `=` | `SyntaxError("Expected ':' but found '='")` |
| An unparenthesized multiline object body introduces indentation | `SyntaxError("Expected a key but found an indented block")` |
| `amount +` before a closing body parenthesis | `SyntaxError("Unexpected ')'")` |
| Undefined body dependency or object shorthand field `missing` | `ReferenceError("missing is not defined")` |
| A returned anonymous function reads uncaptured outer parameter `amount` | `ReferenceError("amount is not defined")` |
| `this`/`self` without an instance receiver | `ReferenceError("this is not defined")` |
| A non-callable parameter shadows `operation` | `TypeError("operation is not a function")` |
| Expression nesting exceeds the existing limit | `SyntaxError("Expressions are nested too deeply")` |
| An operator chain exceeds the existing limit | `SyntaxError("Expression has too many operands")` |
| A postfix chain exceeds the existing limit | `SyntaxError("Expression has too many parts")` |

- `def f amount:` and the other `amount` header boundaries above still point to line 1, column 7; `def f => 1` still points to line 1, column 7.
- Other syntax errors retain the existing parser position rules; runtime errors point to the top-level statement, and caught values omit positions.
- Deep-parentheses and direct-nullary-recursion Windows debug CLI stack-overflow limitations documented in [rejected NUC 15](nuc-0015.md) are outside this revision; no broad CLI stack-safety claim is made.

## Reference Implementation

- The integrated implementation changes only the parameter guard in [`Parser::function_statement`](../src/lang/ast/parser.rs).
- The existing named-arrow body parser, class method parser and [`ClassData::adopt_initializer`](../src/nuc/class.rs) execute the result unchanged.
- No dependency, MSRV, public enum/API, runtime or generator implementation change is required.
- [`tests/bare_named_arrows.rs`](../tests/bare_named_arrows.rs) compares ASTs, parameter metadata, block lowering, canonical body/source rendering and complete program returns against parenthesized equivalents.
- Focused regressions cover exact accepted guard diagnostics/positions, methods/init, explicit super, local/arity binding, reactivity, live references/snapshots, strict objects, returned lambdas and redefinition rollback.
- Resource tests cover existing unary/assignment, operand-chain and postfix limits plus runtime recovery; CLI fixtures and REPL checks cover normal execution, diagnostics, canonical graph output and bounded operand-limit recovery.
- The executable reference, README/examples, related synthesized Markdown, JSONL and exported spec tests are synchronized from source documents.
