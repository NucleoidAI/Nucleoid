## Abstract

- A `try` statement may spell its catch clause with Python's catch-all
  `except` headers. Where a `catch` clause belongs, directly after the
  body:
  - `except:` and `except Exception:` are exactly `catch:`, so the error is
    bound to the name `error`;
  - `except Exception as NAME:`, where `NAME` is a name, is exactly
    `catch NAME:`.
- Each header builds the statement of its `catch` spelling, `Stmt::Try`, or
  `Stmt::TryFinally` with a `finally:` clause of [NUC 119](nuc-0119.md)
  after it, with the same parameter and suites. So the clause behaves as
  `catch` does: the failed body is rolled back first, the bound name is
  scoped to the clause, and returns, loops, nested `try` statements and the
  declarations of either suite run as they do with `catch`.
- The header ends with its colon, as Python requires. Every other header
  where `catch` belongs keeps the accepted
  `SyntaxError("Expected 'catch' after 'try'")` at the `except`, byte for
  byte, among them `except e:`, `except ValueError:`, a parenthesized or
  comma-separated list, a binder that is not a name and a header without its
  colon. A `try` statement still takes one clause.
- `except`, `Exception` and `as` stay ordinary names everywhere else,
  including the `except` stage of [NUC 106](nuc-0106.md). No keyword, lexer
  token, syntax-tree node, error type or message is added.
- Only inputs that were errors at the accepted revision change: programs
  in which a `try` statement's body is directly followed by a matching
  header, each of which raised `SyntaxError("Expected 'catch' after 'try'")`
  at the `except` of such a header. The authoritative contract is
  [Python-style except clauses](../nucleoid.spec.md#python-style-except-clauses).

## Motivation

- Nucleoid already reads many of Python's spellings: `def`, `elif`, `None`,
  `self`, `lambda`, `not in`, `pass` and, through [NUC 119](nuc-0119.md),
  `finally:`. Its error handling still knows only `catch`, so a model or a
  programmer who writes Python's `try:` and `except Exception as error:`
  gets a parse error for the whole program, and nothing in it runs:

  ```
  def ratio(part, whole):
      try:
          if whole == 0:
              throw "EMPTY"
          return part / whole
      except Exception as reason:
          return reason
  ratio(1, 0)
  ```

  The accepted parser rejects it with
  `SyntaxError("Expected 'catch' after 'try'")` at line 6, column 5.
  Writing `catch reason:` makes it run and return `"EMPTY"`.
- The catch-all forms `except:`, `except Exception:` and
  `except Exception as error:` are Python's spellings of a clause that
  catches every error, which is what Nucleoid's `catch` does. Reading them
  lets familiar error handling run unchanged, as the language-superset
  aspiration of [NUC 1](nuc-0001.md) asks.
- World models handle readings and updates that can fail: a sensor that has
  not reported, a transfer that a wallet cannot cover. The `except` clause
  keeps the Python habit for that handling, and the transaction rollback of
  Nucleoid's `catch` keeps the model consistent.

## Rationale

- **Category and mode.** The allocating continuous cycle drew Language
  compatibility with one tool-backed uniform draw over the five categories
  that NUC 1's registry marks eligible for automatic selection, index 4 with
  probability 1/5 and no redraw, and recorded the requested change in the
  allocation commit `259343d1`, which this revision pins. Token comparison
  is therefore skipped as `language_compatibility`. That skip is
  categorical; it is neither a measured comparison nor a passing token
  gate. Runtime applicability does not apply to this category.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts and there is no Baseline B or extra baseline.
  They execute their assertions and explicit returns with full coverage,
  and every pre-existing case is unchanged. Each new case has a
  behavior-equivalent accepted spelling, the same program with `catch`,
  which [Executable traces](#executable-traces) checks.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Only a former error.** At the accepted revision `try_statement` requires
  the keyword `catch` after the body, its line breaks skipped, and raises
  `SyntaxError("Expected 'catch' after 'try'")` at whatever token stands
  there. A program with a matching `except` header therefore never parsed,
  and giving that header clause meaning changes no accepted program.
- **Contextual words, not keywords.** `except`, `Exception` and `as` stay
  identifiers, as `finally` does. Reserving any of them would break programs
  that use them as variables, properties, keys, functions, parameters or
  [NUC 106](nuc-0106.md)'s `except` stage.
- **The whole header first.** The parser matches the complete header,
  through its colon, before it consumes any of it, and takes the `except`
  branch only then. A header that does not match is left untouched, so the
  accepted error and its position come out of the unchanged `catch` path.
  This also keeps `except e:` an error, which
  `tests/selection_intersections.rs` pins.
- **Only the catch-all forms.** Python reads `except NAME:` as a filter by
  exception class, and Nucleoid's errors carry no class to filter by.
  Reading `except ValueError:` as a catch-all would catch errors that the
  program means to let through, so every header that names a class other
  than `Exception` keeps its error. `Exception` is a fixed word of the
  header: a program that defines a variable or class named `Exception` still
  catches every error with it, as Python's `Exception` does for every error
  Nucleoid can raise.
- **The colon is required.** Python requires it, and so does every familiar
  form. [NUC 46](nuc-0046.md) lets `catch NAME` drop its colon before an
  indented block because `catch` is a keyword with no other reading;
  `except` is a name, and a line `except Exception as e` followed by an
  indented block is no Python program. The colon also keeps the header a
  pattern of one line that ends in a colon, which the REPL already buffers
  and indents after, and a colon-free `except` keeps the accepted error
  byte for byte.
- **Where `catch` may stand.** The header is read exactly where the parser
  looks for `catch`, so line breaks, blank lines and comment lines may stand
  between the body and the header, and the header may follow an inline
  body on its line, as `catch` does in `try: x = 1 catch: x = 2`. On
  the line of an inline body, `except` after a `;` begins another statement
  of the body, and a destructuring, a one-line enum or a predicate sentence
  there ends only at the end of the line, `else` or `catch`, as their
  accepted rules state. Those rules stay, so these programs keep their
  accepted errors; extending them to `except` would change programs outside
  any `try` statement.
- **One clause.** Nucleoid's `try` statement has one catch clause, which
  catches every error. Python's several typed clauses would need typed
  errors, and its `else:` clause has no Nucleoid counterpart, so neither is
  added. After an `except` clause, a second `except` header, a `catch` or an
  `else` reads as it reads after a complete `try`/`catch` statement.
- **The same tree.** Each header produces the parameter that its `catch`
  spelling produces, and the clause suite is parsed by the same code, so no
  syntax-tree node, renderer, runtime path or public item changes. Graph
  keys, `--graph`, `--json`, `why` and the suite rendering of
  default-bearing declarations therefore show an `except` clause as its
  `catch` spelling, `catch NAME:`.
- **REPL and terminal workspace.** The native REPL already buffers a `try:`
  statement until a blank line, and every matching header ends in a colon,
  so the clause is buffered with its statement and parsed with it, as
  [NUC 119](nuc-0119.md) found for `finally:`. The REPL needs no change. The
  terminal workspace indents after the header, since it ends in a colon, and
  completes `except` from its alphabetical place among the completion
  words, between `enum` and `extends`, as NUC 119 added `finally`.
- **Differences from Python, documented, not emulated:**
  - typed clauses, tuples of classes and several clauses, which need typed
    errors;
  - the `else:` clause and `except*` groups;
  - the exception object: Nucleoid binds its error's text, such as
    `"ReferenceError: missing is not defined"`, or the thrown value, as
    `catch` binds them;
  - `raise` and re-raising, since Nucleoid raises with `throw`, including
    from a clause;
  - Python's `Exception` leaves out `SystemExit`, `KeyboardInterrupt` and
    `GeneratorExit`, exits that Nucleoid does not have, so it catches what a
    bare `except:` catches, as Python's bare `except:` catches every error;
  - Python unbinds the name of `except Exception as NAME:` after the clause,
    even when it was bound before; Nucleoid scopes the binding to the clause,
    so an outer `NAME` keeps its value.
- **Requires.** [NUC 9](nuc-0009.md), whose `try` statement, `throw`,
  rollback and bindings the clause spells; [NUC 46](nuc-0046.md), whose
  colon-free `try` header may precede the clause and whose colon-free
  `catch` header the clause does not take; and [NUC 119](nuc-0119.md),
  whose `finally:` clause may follow it.
- **Public API.** `Stmt`, `Expr` and every public item keep their
  signatures, and no variant or field is added. The parser accepts more
  inputs, which is the change to report for the human semantic-versioning
  review. No project version is changed.

## Specification

- The normative contract is
  [Python-style except clauses](../nucleoid.spec.md#python-style-except-clauses).

### Syntax

- `try_statement: "try" body (catch_clause | except_clause) finally_clause?`,
  with `except_clause: "except" ("Exception" ("as" NAME)?)? suite`, where
  `except`, `Exception` and `as` are ordinary identifiers, `NAME` is an
  identifier and `suite` is the explicit-colon suite of `catch`: an
  indented block, statements on the same line separated by `;`, or a braced
  block.
- The header is read where the parser looks for `catch`: after the body and
  the line breaks that follow it. Blank lines and comment lines produce no
  tokens, so they may stand between, and the spacing inside the header is
  free, as in `except  Exception  as  e :`.
- `except:` and `except Exception:` bind `error`, as `catch:` does, and
  `except Exception as NAME:` binds `NAME`, as `catch NAME:` does. `NAME`
  may be any identifier, contextual words such as `as`, `except`,
  `Exception`, `error` and `finally` included, as after `catch`; a keyword
  such as `this`, `self` or `None` is no identifier.

```
def ratio(part, whole):
    try:
        if whole == 0:
            throw "EMPTY"
        return part / whole
    except Exception as reason:
        return reason
assert([ratio(3, 4), ratio(1, 0)], [0.75, "EMPTY"])
try:
    share = stock / 2
except Exception:
    share = 0
try:
    level = stock.reorder()
except:
    level = error
assert([share, level], [0, ReferenceError("stock is not defined")])
stock = 8
share
```

- `ratio` returns its quotient or the reason it refused, and the two
  top-level statements fall back when `stock` is not yet defined. The
  fallback `share = 0` is a declaration of the clause, so defining `stock`
  later does not run the `try` statement again; the program returns `0`.

### Semantics

- An `except` clause runs exactly as its `catch` spelling does, because it
  is that statement:
  - when the body fails, its changes are rolled back, with their pending
    propagation and deletion tracking, and then the clause runs;
  - the bound value is the error's text, such as
    `"ReferenceError: missing is not defined"`, whose `typeof` is
    `"string"`, or the thrown value, as `catch` binds them;
  - the binding is scoped to the clause and shadows an outer name of its
    spelling only there; after the statement the outer value is read again,
    or the name is undefined;
  - an error raised in the clause propagates, to an enclosing `try`
    statement or out of the run;
  - a `finally:` clause after it runs as after a `catch` clause;
  - the statements of either suite run as those of a `catch` statement do:
    a top-level assignment is a declaration, and in a function, method,
    constructor, loop or block body they run in that body.

```
class Account(owner, balance):
    this.owner = owner
    this.balance = balance
ada = Account("Ada", 100)
limit = ada.balance * 2
def withdraw(account, amount):
    if amount > account.balance.value:
        throw "INSUFFICIENT FUNDS"
    account.balance = account.balance - amount
    return account.balance
try:
    ada.balance = 500
    withdraw(ada, 900)
except Exception as reason:
    assert([ada.balance, limit], [100, 200])
    refusal = reason
assert(refusal, "INSUFFICIENT FUNDS")
```

- The write of `500` and its propagation to `limit` are undone before the
  clause runs, and the clause records the refusal.

### Kept readings

- Where a `catch` clause belongs, every other header keeps
  `SyntaxError("Expected 'catch' after 'try'")` at the `except`:
  - another name, as in `except e:`, `except ValueError:`,
    `except BaseException:`, `except exception:` and `except Exceptions:`;
  - a parenthesized or comma-separated list, as in
    `except (TypeError, ReferenceError):`, `except (Exception):` and
    `except Exception, e:`;
  - a binder that is not an identifier, as in `except Exception as (e):`,
    `except Exception as 5:`, `except Exception as this:` and
    `except Exception as e.f:`;
  - a second `as` or name, as in `except Exception as e as f:` and
    `except Exception as e, f:`, and a missing binder, as in
    `except Exception as:` and `except as e:`;
  - a header without its colon, also before an indented block, as in
    `except Exception as e` and `except`;
  - `except` followed by anything else, as in `except = 1`, `except(1)`,
    `except*:`, `except:= 1` and `except.x = 1`.
- A `try` statement takes one clause. After an `except` clause, a second
  `except` header, a `catch`, an `else` or a bare `finally` reads as it
  reads after a complete `try`/`catch` statement, and the program raises
  that statement's error.
- On the line of an inline body, these programs keep their accepted
  errors, while their `catch` spellings run:
  - `try: x = 1; except: y = 2` raises
    `SyntaxError("Expected 'catch' after 'try'")` at line 1, column 19, its
    colon, because `except` after a `;` begins another statement of the
    body;
  - `xs = [1, 2]`, then `try: a, b = xs except: a = 0`, raises it at line 2,
    column 7, the comma, because a destructuring ends only before a newline,
    `;`, a dedent, `}`, the end of input, `else` or `catch`;
  - `try: enum Color: RED, GREEN except: x = 1` raises
    `SyntaxError("Expected ',' but found identifier 'except'")` at line 1,
    column 29, because a one-line enum ends only before those tokens;
  - `class P`, `p = P()`, then `try: $P is open except: x = 1`, raises
    `SyntaxError("Expected 'catch' after 'try'")` at line 3, column 9, the
    `is`, because a predicate sentence ends only before those tokens.
- This limitation stays: ending these statements before `except` as well
  would change programs outside any `try` statement, where `except` is an
  ordinary name, and only programs in which a `try` body is followed by a
  matching header may change.
- Variables, properties, object keys, functions, methods, parameters, loop
  variables, enums and the [NUC 106](nuc-0106.md) stage named `except`,
  `Exception` or `as` keep working, and so do `except:` anywhere a `catch`
  clause does not belong, a declaration `except: int` and a lambda
  parameter `lambda except: ...`.

### REPL and terminal workspace

- The native REPL buffers a `try:` statement through its `except` clause
  until a blank line, as through a `catch` clause, with LF or CRLF input,
  plain or `--json`. A blank line before the header commits the statement
  first, so the header is then a statement of its own and raises
  `SyntaxError("Unexpected ':'")`, as a `catch:` typed after one raises
  `SyntaxError("Unexpected keyword 'catch'")`. A `try` line with an inline
  or braced body does not end in a colon, so the REPL submits it on its
  own, and a header on the next line is likewise a statement of its own,
  with either spelling.
- The terminal workspace indents the line after the header and completes
  `except`.

### Cost

- Recognizing the header costs one look at up to five tokens where the
  parser already reads `catch`. A `try` statement spelled with `catch`
  parses through exactly the accepted code after that look, and the
  runtime is unchanged, since the statement is the same.
- **Spot check**, not a benchmark, measured on the final tree: programs of
  10,000 top-level `try` statements, each followed by its header and the
  suite `v = 2`, whose body either fails with `v = missing` or completes
  with `v = 1`, on `nucleoid-final.exe`, the final release build, and on
  the caller's release build of the accepted revision, rustc 1.97.1,
  through the command line with `--json`: the median of 21 runs of each
  program, including process start, one process at a time, after one
  warm-up round, with the 24 runs of each round in a shuffled order. Times
  are in milliseconds; the accepted build parses none of the `except`
  programs and stops at the first header, after lexing the whole file.

| 10,000 statements | `except` spelling, this NUC | `catch` spelling, this NUC | `catch` spelling, accepted | `except` spelling, accepted |
| --- | ---: | ---: | ---: | --- |
| `except:`, body fails | 76.0 | 74.9 | 76.2 | `SyntaxError`, 33.4 |
| `except Exception:`, body fails | 76.9 | 75.9 | 76.1 | `SyntaxError`, 34.1 |
| `except Exception as e:`, body fails | 79.6 | 75.9 | 76.5 | `SyntaxError`, 37.3 |

- Each `catch` spelling takes 0.98 to 1.00 times its time on the accepted
  build, so it parses and runs as fast as it did at the accepted revision.
  Each `except` program takes 0.98 to 1.05 times its `catch` spelling on
  the same build. The longest header adds 140,000 bytes of source over
  `catch e:`, which the lexer reads: the accepted build's own error runs,
  which lex the whole file and parse only up to the first header, take 3.9
  and 4.1 ms longer for the `except Exception as e:` files than for the
  `except:` files, which hold 150,000 bytes fewer.
- A second shuffled measurement, with another seed, agrees with every
  median of the table within 2.4 ms; in it the `catch` spellings take
  0.97 to 1.02 times their accepted times, and the `except` programs 1.02
  to 1.07 times their `catch` spellings.
- Phase 1 measured the same rows with the median of 11 runs in a fixed
  order, between 0.99 and 1.04 times the `catch` spellings. On the final
  build, three measurements in that fixed order each added 20 to 32 ms to
  every row, or to three rows, of one or two columns, different columns
  each time, while the other columns stayed within 6 ms of the table. A fixed
  order runs each program in the same position of every round, so the
  runs of each round are shuffled for the table.

### Compatibility

- The lexer, its token stream, the syntax tree, the runtime and every
  diagnostic message are unchanged; no keyword is reserved.
- Only inputs that were errors at the accepted revision change: programs in
  which a `try` statement's body is directly followed by a matching header.
  Each raised `SyntaxError("Expected 'catch' after 'try'")` at the `except`
  of such a header, since the accepted parser cannot read past one. Every
  accepted program keeps its parse, positions, diagnostics and behavior.
- A program whose matching header is followed by a further clause changes
  from that error to the error of its `catch` spelling, as
  [Kept readings](#kept-readings) states.
- Two error-to-error differences from the `catch` spelling stand: an error
  reported on the header's own line has its column moved by the header's
  extra length, as [Errors](#errors) lists, and in the REPL a header typed
  after the statement was committed raises `SyntaxError("Unexpected ':'")`
  where `catch` raises `SyntaxError("Unexpected keyword 'catch'")`, as
  [REPL and terminal workspace](#repl-and-terminal-workspace) states.
