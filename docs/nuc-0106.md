## Abstract

- Adds two pipeline stages that compare one reasoning selection with
  another:
  - `SELECTION |> intersect(OTHER)` keeps the steps of `SELECTION` whose
    node `OTHER` also selects;
  - `SELECTION |> except(OTHER)` keeps the steps of `SELECTION` whose node
    `OTHER` does not select.
- Both keep the steps they keep in `SELECTION`'s order, with their `node`,
  `holds`, `rule`, `state` and `from` fields unchanged. With
  `subtotal = price * quantity`, `tax = subtotal * rate` and
  `shipping = quantity * 2`:
  - `why tax |> intersect(why shipping)` selects `quantity`, the one node
    both values rest on;
  - `why tax |> except(why shipping)` selects `tax`, `subtotal`, `rate` and
    `price`, what the tax rests on and the shipping does not;
  - with `total = subtotal + tax + shipping`,
    `affects price |> intersect(affects rate)` selects `tax` and `total`,
    what both inputs move.
- Steps are compared by their graph node, not by value. `OTHER` is one
  expression in parentheses that denotes a selection, as the source of a
  pipeline does: a reference, `model`, a prefix stage such as `why b`, or a
  pipeline such as `b |> why |> stated`. It is evaluated in place each time
  the stage applies, after the source selection and the stages before it.
- The kept steps keep the direction of `SELECTION`'s most recent walk and
  their [NUC 82](nuc-0082.md) distances. Between two walks, the stages
  therefore select the same steps in any order with `stated`, `derived`,
  `depth`, `diff`, `path` and each other, and a later `why` or `affects`
  walks from the kept steps. An `OTHER` that a `depth(null)` makes undefined
  makes the whole selection undefined.
- A standing selection that holds either stage stays live through every
  value and structural observation of both `SELECTION` and `OTHER`,
  including the steps each one drops. It renders as
  `SOURCE|>intersect(OTHER)` or `SOURCE|>except(OTHER)`.
- Only `|>` followed by the name `intersect` or `except` and then a `(`
  token is a stage. Both names stay ordinary identifiers everywhere else,
  and a binding of either name shadows its stage, as bindings shadow
  [NUC 48](nuc-0048.md)'s `stated` and `derived`, `depth`, `diff` and
  `path`. An invalid `OTHER` keeps the diagnostics of a pipeline source,
  such as `TypeError("Cannot explain 1")`.
- No keyword, lexer token or error type is added, and no union stage is
  added. Every accepted program keeps its parse and behavior. Only inputs
  that were parse errors at the accepted revision change: most raised the
  parse-time `TypeError("intersect is not an operation")` or
  `TypeError("except is not an operation")`, and where the parser
  backtracks some raised another parse error first, such as
  `SyntaxError("Unexpected ','")` for an unpacking declaration.
- The public `Expr` enum gains one variant, `Expr::Combine`, with a new
  public `SetOperation` enum, which needs human SemVer review. No project
  version is changed. The authoritative contract is
  [Intersect and except reasoning selections](../nucleoid.spec.md#intersect-and-except-reasoning-selections).

## Motivation

- Diagnosis asks what two observations have in common. When two symptoms
  appear, the facts behind both are the candidate root causes, and the facts
  behind one but not the other tell them apart. Impact analysis asks the
  dual question: what do two inputs both move? Each answer is the
  intersection or the difference of two explanations or impact selections.
- The accepted stages each narrow a single selection: `stated` and
  `derived` by a step's state, `depth` by distance, `path` by reachability
  of one target and `diff` by change since a `suppose` block began. None
  compares a selection with another one.
- Accepted Nucleoid spells the comparison as a membership test that walks
  the second selection inside a lambda or comprehension. The most compact
  spelling found is `[s for s in why tax if s in why shipping]`, 13 lexer
  tokens, against 8 for `why tax |> intersect(why shipping)` and 10 for
  `tax |> why |> intersect(shipping |> why)`. The spelling by node name,
  `(tax |> why).filter(s -> s.node in (shipping |> why).map(t -> t.node))`,
  is 29. Each accepted spelling:
  - walks the second selection again for every step of the first, so one
    question costs time quadratic in the size of the explanations;
  - compares steps by value or by name rather than as graph nodes. A value
    test drops a step whose value is NaN, which equals nothing: with
    `x = 0 / 0` and `y = x + 1`,
    `[s for s in why y if s in why x]` is empty, though both explanations
    hold the node `x`;
  - returns a plain list instead of a selection, so it cannot be chained:
    appending `|> affects` raises
    `TypeError("Cannot explain tax|>why.filter(function()).map(function())")`
    for the comprehension and
    `TypeError("Cannot explain tax|>why.filter(function())")` for the
    filter.
- Prior art: Bazel query's `intersect` and `except` operators over target
  sets, as in `deps(//a) intersect deps(//b)`; SQL's `INTERSECT` and
  `EXCEPT`; C# LINQ's `Intersect` and `Except`; Kotlin's `intersect` and
  `subtract`; Python's set `&` and `-`; and JavaScript's
  `Set.prototype.intersection` and `Set.prototype.difference`.
- Draft [NUC 11](nuc-0011.md) plans the stages `why`, `why not`, `affects`,
  `rules`, `conflicts`, `describe`, `export` and `depth(n)` and filters over
  a single selection; none combines two selections.
  [NUC 83](nuc-0083.md)'s `diff` compares a selection with the world before
  a `suppose` block, not with another selection.

## Rationale

- **Category and selection.** The cycle that allocated this Draft, in the
  pushed commit `cc21315a` on 11-Nov-2026, made one tool-backed uniform draw
  over the five categories that NUC 1's registry marks eligible for
  automatic selection and selected Reasoning enhancement, index 3, with
  probability 1/5 and no redraw. A later continuous cycle found the Draft
  stale and claimed it with the pushed empty commit
  `Resume NUC 106 Intersect and Except Reasoning Selections`, `4cba3006`,
  keeping its number, title, category and requested change without a new
  draw. Token comparison is required; runtime applicability does not apply
  to this category.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero, because no rubric was frozen. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Only former errors.** At the accepted revision the pipeline parser reads
  the name after `|>` as a stage and raises the parse-time
  `TypeError("<name> is not an operation")` for `intersect` and `except`,
  and only that parser consumes `|>`. Giving `|> intersect(` and
  `|> except(` a meaning therefore changes only inputs that were parse
  errors. Where the statement parser backtracks, some of those inputs
  reported another parse error first: `a, b = tax |> why |> intersect(why shipping)`
  raised `SyntaxError("Unexpected ','")` and
  `{node} = why tax |> except(why shipping)` raised
  `SyntaxError("Unexpected '='")`, as for [NUC 88](nuc-0088.md)'s `path`.
  Inside a template interpolation the accepted parser ignores trailing
  tokens, so `` `v ${quantity why tax |> intersect(why shipping)}` `` keeps
  its accepted result.
- **A stage, not a function, prefix or operator.** Both stages narrow a
  selection, as `stated`, `derived`, `depth`, `diff` and `path` do, so they
  are pipeline stages, and their argument is written as NUC 82 writes
  `depth(LIMIT)` and NUC 88 writes `path(TARGET)`. Rejected:
  - an infix operator such as Bazel's `a intersect b` or Python's `a & b`,
    which would be a new keyword or a new meaning of an accepted operator;
  - a call form `intersect(a, b)`, which is an ordinary call today and
    stays one;
  - a prefix form `intersect a b`, which is juxtaposed statements today;
  - a bare `|> intersect` with the other selection elsewhere, which keeps
    its accepted error.
- **Selections, not values.** `OTHER` denotes a selection exactly as a
  pipeline's source does, so a reference selects its own node, `model`
  selects the model and a prefix stage or a pipeline selects what it walks.
  The source rule settles every kind of `OTHER` at once, including its
  diagnostics. Rejected: evaluating `OTHER` to a value and matching step
  records, which is the accepted spelling's defect.
  - A name that holds a selection is a reasoning observer, which no
    selection holds, so after `causes = why shipping`, `intersect(causes)`
    keeps nothing. That is the accepted reading of `causes` as a source:
    `causes |> stated` and `why causes` select nothing at the accepted
    revision. The selection is written out, as in `intersect(why shipping)`.
  - `model` is read as the model when it is all of `OTHER`, as it is when it
    is all of a pipeline's source, so `intersect(model)` keeps every step
    and `except(model)` none. The prefix `why model` keeps its accepted
    `ReferenceError("model is not defined")`.
- **Membership by node.** A step is kept by whether `OTHER` has a step for
  the same graph node. Every field of a step is a property of its node at
  that moment, so two selections never disagree about a node they share.
  The comparison goes through a set of `OTHER`'s nodes, linear in the sizes
  of both selections.
- **`SELECTION`'s order, fields, direction and distances.** The stages only
  remove steps, so `SELECTION`'s order and every field stay, including a
  kept step's `from`, which may name a dropped step. The walk direction and
  NUC 82's distances stay too, so a later `depth(n)` or `path(t)` treats
  the kept steps as `SELECTION`'s own, and a later `why` or `affects` walks
  from them. `OTHER`'s order, direction and distances are not used.
  - Rejected: taking the order or distances from `OTHER`, which would make
    `intersect` the only stage whose result is not a part of its source.
- **The algebra.** Membership in a fixed `OTHER`, a step's state, its
  distance, its change since a `suppose` began and its reachability of a
  target are all properties of one step, so between two walks the filters
  select the same steps in any order. The identities that follow are under
  [Algebra](#algebra), with the cases where the order still shows: which
  error is reported first, and whether `OTHER` is evaluated before a later
  `depth(null)` makes the selection undefined.
- **Evaluated in place, once per application.** `OTHER` is evaluated when
  its stage applies, after the source selection and the stages before it,
  as NUC 82 evaluates a limit and NUC 88 resolves a target. It is evaluated
  once per application, however many steps `SELECTION` has, and it is
  evaluated even when `SELECTION` is empty, so an empty result still
  follows `OTHER`.
- **An undefined `OTHER` makes the selection undefined.** NUC 82 makes a
  selection undefined when a `depth` limit is `null` or undefined: the stage
  keeps nothing that could be known. An `OTHER` that holds such a stage is
  undefined in the same way, and the stage then makes the whole selection
  undefined, applies no later stage and evaluates no later argument.
  Rejected: reading an undefined `OTHER` as empty, which would make
  `except` return all of `SELECTION` and `intersect` nothing from a value
  that is not known.
- **Bindings shadow the stages.** A local or parameter, state variable,
  function or class named `intersect` or `except` makes its stage raise
  `TypeError("<name> is not an operation")`, as NUC 48, NUC 82,
  [NUC 83](nuc-0083.md) and NUC 88 do for their stages. A model that
  defines its own `intersect` or `except` never has it silently replaced by
  a stage. The check runs with the pipeline's other checks, before the
  source is selected and so before `OTHER` is evaluated, as the accepted
  checks run before a limit or a target is.
- **Observations.** A standing selection must change when either side
  does, so the stage keeps every observation `SELECTION` made, including
  those of the steps it drops, as the filters do, and adds every observation
  that evaluating `OTHER` makes, including those of the steps `OTHER`'s own
  stages drop and model membership when `OTHER` is `model`.
- **Naming.** `intersect` and `except` are Bazel query's names for these
  operators on build graphs and SQL's for the set operators on queries, and
  both read as verbs in a pipeline. Rejected:
  - `intersection` and `difference`, JavaScript's and Python's method
    names, which are nouns and longer;
  - `minus`, `subtract` and `without`, which read as arithmetic or as
    removing values rather than nodes;
  - `and` and `not`, which are keywords;
  - `both` and `only`, which read as quantities and are common variable
    names.
- **Requires.** NUC 48, NUC 82, NUC 83 and NUC 88, whose stages these
  compose with and whose argument, distance, direction and shadowing rules
  they share. The Draft's list stands: those already require everything
  else the stages rely on, such as pipelines, `why`, `affects` and `model`.
- **Not added.** A union stage, which the request excludes and whose order
  would need a rule of its own; a symmetric difference; several selections
  in one stage; an infix, call or prefix form; matching by value or by node
  name; taking the order or distances of `OTHER`; and any change to the
  accepted stages.

## Specification

- The normative contract is
  [Intersect and except reasoning selections](../nucleoid.spec.md#intersect-and-except-reasoning-selections).

### Syntax

- `SELECTION |> intersect(OTHER)` and `SELECTION |> except(OTHER)` are
  pipeline stages: `|>`, the identifier `intersect` or `except`, then a `(`
  token, one expression and `)`. Whitespace may separate the name from `(`;
  a line break may only where the lexer suppresses it, inside parentheses
  and brackets.
- `OTHER` is parsed as a parenthesized expression is, and an `OTHER` that is
  exactly the name `model` is the model, as a pipeline's source `model` is.
  `|> intersect()` and `|> intersect(a, b)` report the errors that `()` and
  `(a, b)` report.
- The stages take part in a pipeline as the other stages do: they bind at
  the precedence of `|>`, may be followed by further stages, and may follow
  a prefix stage, so `why tax |> intersect(why shipping)` is
  `(why tax) |> intersect(why shipping)`.
- Everywhere else `intersect` and `except` are ordinary identifiers, and
  `|> intersect` or `|> except` not followed by `(` keeps the accepted
  parse-time `TypeError("<name> is not an operation")`. There is no prefix
  form, and `intersect(a, b)` is an ordinary call.
- Both stages parse to the public variant
  `Expr::Combine { operation: SetOperation, source: Box<Expr>, other: Box<Expr> }`,
  with the new public enum `SetOperation { Intersect, Except }`. It is
  `#[non_exhaustive]`, derives `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`
  and `Hash`, and names each operation with `as_str`. The accepted
  `Expr::Reason`, `Expr::Depth`, `Expr::Path` and the public `Stage` enum
  are unchanged.

### Selection

- A stage evaluates its source selection and the stages before it, then
  evaluates `OTHER` as a selection, and keeps the steps of the source whose
  node `OTHER` selects, for `intersect`, or does not select, for `except`,
  in their order, with their `node`, `holds`, `rule`, `state` and `from`
  fields and their distances unchanged.
- Steps are compared by graph node, whatever they hold, so a step whose
  value is NaN is kept by `intersect` when `OTHER` selects its node. The
  order, the walk direction and the distances of `OTHER`'s steps are not
  used.
- The kept steps keep the direction of `SELECTION`'s most recent walk, so a
  later `path(t)` follows it, and their distances, so a later `depth(n)`
  measures them as before. A later `why` or `affects` walks from the kept
  steps.

```
price = 10
quantity = 3
rate = 0.2
subtotal = price * quantity
tax = subtotal * rate
shipping = quantity * 2
common = why tax |> intersect(why shipping)
only = why tax |> except(why shipping)
assert(common.map(s -> s.node), ["quantity"])
assert(only.map(s -> s.node), ["tax", "subtotal", "rate", "price"])
shipping = price + quantity
assert(common.map(s -> s.node), ["price", "quantity"])
```

### Other selections

- `OTHER` denotes a selection, as the source of a pipeline does:
  - a reference selects its own node: a name, a property path such as
    `order.price`, `this.price` in a method, or `$Class.property` inside a
    class-level rule for the instance's property;
  - `model` selects every node of the model, in model order;
  - a prefix stage such as `why shipping`, or a pipeline such as
    `shipping |> why |> stated`, selects what it selects, and may itself
    hold `intersect` and `except`.
- A reference to a node that is not in the model, such as an absent
  property, selects nothing, and the result fills in once the property is
  defined.
- A name that holds a selection is a reasoning observer, which no selection
  holds, so as `OTHER` it selects nothing: after `causes = why shipping`,
  `why tax |> intersect(causes)` is empty and `why tax |> except(causes)` is
  all of `why tax`. That is how the accepted revision reads such a name as a
  source: `causes |> stated` and `why causes` select nothing there. The
  pipeline is written in place instead, as in `why tax |> intersect(why shipping)`.
- `OTHER` is evaluated when its stage applies, after the source selection
  and the stages before it, and before the stages after it, once per
  application, even when `SELECTION` is empty.
- An invalid `OTHER` keeps the diagnostics of a pipeline source:
  - a literal, a property path whose base holds no object, and any other
    expression that is neither a reference nor a selection raise
    `TypeError("Cannot explain <other>")`, where `<other>` is the canonical
    source of `OTHER`: `intersect(1)`, `intersect("price")`,
    `intersect(price + 1)`, `intersect(this)`, and `$Class.property`
    outside a class-level rule;
  - a name that nothing defines raises `ReferenceError("<name> is not defined")`,
    including the first name of a property path;
  - a pipeline in `OTHER` raises what it raises as a pipeline, including the
    shadowing error of a stage in it.
- These errors are positioned at the running top-level statement and roll
  back its transaction.

### Algebra

- Between two walks, `stated`, `derived`, `depth`, `diff`, `path`,
  `intersect` and `except` select the same steps in any order: each keeps a
  step by a property of that step alone, given the selection's walk and a
  fixed `OTHER`.
- `S |> intersect(S)` selects what `S` selects, and `S |> except(S)` selects
  nothing, for the same pipeline `S` written twice.
- `S |> intersect(model)` selects what `S` selects and `S |> except(model)`
  selects nothing, because every step of a selection is a node of the model.
- Repeating a stage with the same `OTHER` changes nothing, two `intersect`
  stages keep what both other selections hold in either order, and
  `S |> except(B) |> except(C)` keeps what neither holds.
- `A |> intersect(B)` and `B |> intersect(A)` select the same nodes, each in
  its own source's order, with its own distances.
- The order still shows in two ways:
  - when two stages would fail, the one applied first reports its error,
    so outside a `suppose` block `S |> diff |> intersect(missing)` raises
    `TypeError("Cannot use 'diff' outside suppose")` and
    `S |> intersect(missing) |> diff` raises
    `ReferenceError("missing is not defined")`;
  - a `depth` stage whose limit is `null` makes the selection undefined, and
    `OTHER` is evaluated only when its stage comes before that `depth`
    stage.

### Undefined selections

- A `depth` stage whose limit is `null` or undefined makes a selection
  undefined, as [NUC 82](nuc-0082.md) specifies.
- When `OTHER` is undefined for that reason, the stage makes the reasoning
  expression undefined: the stages after it are not applied and their
  arguments are not evaluated, and a declaration stores the undefined value
  as `null`, as it does for an undefined `SELECTION`.
- When `SELECTION` is undefined before the stage, `OTHER` is not evaluated.

### Bindings and sources

- Before its source is selected, each stage checks for a local or
  parameter, state variable, function or class named after it and, when one
  exists, raises `TypeError("intersect is not an operation")` or
  `TypeError("except is not an operation")` at the running statement.
  Function and method parameters, lambda and arrow parameters, loop
  variables, quantifier binders and block locals are bindings; methods,
  properties and object keys are not.
- The checks of a pipeline's stages run from the outermost stage inward,
  then the source is selected, then the stages apply from the innermost
  outward, each `intersect` or `except` evaluating its `OTHER`, whose own
  checks run when it is evaluated. Accepted pipelines keep this order.
- A binding declared after a standing selection makes that selection's next
  evaluation raise, so the statement that triggered the refresh fails and
  rolls back, as for the accepted stages.
- An invalid source keeps its accepted diagnostic and is reported before
  `OTHER` is evaluated: `1 |> intersect(missing)` raises
  `TypeError("Cannot explain 1")` and `missing |> except(1)` raises
  `ReferenceError("missing is not defined")`.
- The accepted shadowing of `why` and `affects`, which ignore bindings, and
  of `stated`, `derived`, `depth`, `diff` and `path`, which a binding
  shadows, is unchanged.

### Observation, liveness and transactions

- The stage keeps every value and structural observation its source made,
  including those of the steps it drops.
- It adds every observation that evaluating `OTHER` makes, including those
  of the steps `OTHER`'s own stages drop and of model membership when
  `OTHER` is `model`, so a standing selection refreshes when either side
  changes through a value, a rule, a new or deleted node or a class-level
  rule. So does a declaration that calls a function evaluating a stage,
  because subscriptions are replaced on every evaluation. An empty result
  still follows both sides.
- `model` selects every node of the model, so a standing selection that
  holds `intersect(model)` or `except(model)` reads every node and the model
  membership, and re-derives when any of them changes, as `model |> stated`
  does.
- An expression that contains a stage is a reasoning expression: a
  declaration, property, class-level rule, condition or quantifier holding
  it is a reasoning observer that walks neither select nor traverse and
  that `model` excludes. Functions, methods and lambdas evaluate it in
  place, and class-level rules give each instance its own selection.
- `.value` snapshots a selection as for the accepted stages. When a
  declaration is stored, a `.value` read in the limit of a `depth` stage
  inside `OTHER` is frozen, as it is in a limit elsewhere, while the sources
  in `OTHER` stay unfrozen, as a pipeline's source does.
- Propagation order, `suppose` blocks, caught failures and failed
  statements behave as for the accepted stages: rollback restores
  selections, observations and queued refreshes.

```
price = 10
quantity = 3
fee = 2
subtotal = price * quantity
total = subtotal + 5
credit = fee * 2
refund = credit + 1
shared = why total |> stated |> intersect(why refund |> stated)
assert(shared, [])
subtotal = price * quantity + fee
assert(shared.map(s -> s.node), ["fee"])
credit = price - fee
assert(shared.map(s -> s.node), ["price", "fee"])
```

### Rendering

- The stages render as `SOURCE|>intersect(OTHER)` and
  `SOURCE|>except(OTHER)` in graph keys, block keys, conditions and `rule`
  text, with the source and `OTHER` rendered once each, so rendered size
  stays linear. `why tax |> intersect(why shipping)` renders as
  `tax|>why|>intersect(shipping|>why)`.
- The rendering parses back to the same expression, except where the
  accepted renderer already abbreviates part of it, as NUC 88 records.
- A stage and its accepted spelling render differently, so they are
  different graph keys, conditions and `rule` texts.

### Cost

- Pipelines without the stages take their accepted paths and do no work
  for them.
- One application evaluates `OTHER` once, builds a set of its nodes and
  keeps the source's steps that the set holds or does not hold, in time and
  memory linear in the sizes of both selections, besides the walks of
  `OTHER` itself. The accepted spellings evaluate the second selection once
  for every step of the first, so their time grows with the product of the
  two sizes.
- The figures below were measured on release builds of the candidate and of
  the accepted revision, on one Windows 11 machine with 16 logical
  processors. Each is the best of three runs of one statement after its
  setup program. They compare spellings on one machine and are not
  guarantees. The questions are:
  - chain: `v0 = 1` and `v1 = v0 + 1` onward, n nodes, asking
    `why v{n-1} |> intersect(why v{n/2})`, which keeps n/2 + 1 steps;

    `y{i} = a + b + i`, asking `affects a |> intersect(affects b)`;

    groups at a time into `h0` onward, and every `h` into `top`, asking
    `why top |> intersect(why h0)`;
  - each against the counterparts' comprehension `[s for s in A if s in B]`
    and the filter `(A).filter(s -> s.node in (B).map(t -> t.node))`.

## Errors

| Condition | Error |
| --- | --- |
| An `OTHER` that is a literal, a property path whose base holds no object, or any other expression that is neither a reference nor a selection | `TypeError("Cannot explain <other>")`, at the running top-level statement |
| An `OTHER` that names nothing, or a property path whose first name names nothing | `ReferenceError("<name> is not defined")`, at the running top-level statement |
| A local or parameter, state variable, function or class named `intersect` or `except` | `TypeError("intersect is not an operation")` or `TypeError("except is not an operation")`, at the running top-level statement, before the source is selected |
| `\|> intersect` or `\|> except` not followed by `(` | `TypeError("intersect is not an operation")` or `TypeError("except is not an operation")`, while parsing, as before |
| `\|> intersect()` or `\|> except()` | `SyntaxError("Unexpected ')'")` |
| `\|> intersect(` or `\|> except(` with more than one expression | `SyntaxError("Expected ')' but found ','")` |
| A source that is not a reference, a selection or `model` | `TypeError("Cannot explain <source>")`, as before, before `OTHER` is evaluated |
| A source that reads an undefined name | `ReferenceError("<name> is not defined")`, as before, before `OTHER` is evaluated |
| `OTHER` selections nested more deeply than the parser allows | `SyntaxError("Expressions are nested too deeply")`, as for any nested expression |

- No error type or message is added. `<name> is not an operation` is the
  accepted pipeline diagnostic, and the errors of `OTHER` are those of a
  pipeline source.
- Source text cannot nest `OTHER` past the parser's limit. A tree built
  through the public API past the runtime's `MAX_DEPTH` raises the existing
  `TypeError("Maximum expression depth exceeded")` instead of overflowing
  the stack.
