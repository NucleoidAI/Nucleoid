# NUC 78 -- Extends Clauses for Subclasses

```

Title: Extends Clauses for Subclasses
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Language compatibility
Created: 04-Nov-2026
Requires: 14
```

## Abstract

- A class header may name its parent with `extends`, as JavaScript,
  TypeScript, Java, PHP, Dart, Scala and Groovy do. The clause follows the
  class name and its optional parameter list:
  `class Dog(name, breed) extends Animal:`.
- With a colon, the clause takes the body that the colon spelling takes:
  `class Dog extends Animal:` with an indented body declares the class that
  `class Dog: Animal` with that body declares.
- Without a colon, `class Dog extends Animal` is a bodyless subclass, exactly
  `class Dog: Animal` with an indented `pass`. Like [NUC 14](nuc-0014.md)'s
  `class Entity`, it ends at a statement boundary and does not adopt the
  next statement as a constructor.
- Every spelling builds the same class declaration. Populations,
  constructors, `super`, class-level rules, cycle checks, graph keys, `why`,
  rendering and transactions are those of the colon spelling, which canonical
  source keeps writing.
- `extends` is not a keyword. It starts the clause only directly after a
  class name or its parameter list, where the accepted parser raised
  `SyntaxError("Expected ':' but found identifier 'extends'")`. Every other
  use of the name keeps its meaning, and only such former syntax errors
  change.
- Malformed clauses raise
  `SyntaxError("Expected a parent class name but found <token>")`,
  `SyntaxError("Class '<Name>' already extends '<Parent>'")` or the existing
  `SyntaxError("Expected ':' but found <token>")`.
- No token kind, keyword, syntax tree node, runtime path, dependency, public
  Rust API or project version is added or changed. The authoritative contract
  is [Extends clauses for subclasses](../nucleoid.spec.md#extends-clauses-for-subclasses).
- **Outcome: Accepted.** The independent evaluation and the caller's
  integrated-tree checks passed all three hard criteria, and the independent
  evaluator decided Accepted with non-blocking documentation findings. Token
  comparison was skipped as `language_compatibility`, the category's
  continuous-mode policy; no policy check failed.

## Motivation

- Nucleoid aspires to be a superset of familiar languages. Kotlin, C#, C++
  and Swift name a parent after a colon, which Nucleoid already accepts.
  JavaScript, TypeScript, Java, PHP, Dart, Scala and Groovy write
  `class Car extends Vehicle`, which fails at the accepted revision.
- World models written by language models routinely use that spelling. Each
  such header raises `SyntaxError("Expected ':' but found identifier 'extends'")`
  and stops the whole program before any statement runs.
- The accepted language has no bodyless subclass. A parent after the colon
  leaves the colon open for a body, so `class Dog: Animal` followed by
  `d = Dog("rex")` takes that statement as its constructor, and reading `d`
  then raises `ReferenceError("d is not defined")`. A subclass without
  members needs an indented `pass` before any statement that follows it.
- `class Dog extends Animal` gives that common declaration a one-line form
  that ends where it appears, as the bodyless root headers of
  [NUC 14](nuc-0014.md) do.

## Rationale

- **Confirmed category and mode.** The caller made one tool-backed uniform
  draw over the five categories that NUC 1's registry marks eligible for
  automatic selection. It selected Language compatibility, index 4, with
  probability 1/5 and no redraw. This is a continuous cycle, so token
  comparison is skipped as `language_compatibility`. That skip is
  categorical; it is neither a measured comparison nor a passing token gate.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts. They execute their assertions and explicit
  returns with full coverage. Every pre-existing case, its spelling and its
  colon headers are unchanged. Runtime applicability does not apply to this
  category.
- **Only a former error position.** After a class name and its optional
  parameter list, the accepted parser requires a statement terminator or a
  colon; any identifier there raises `Expected ':' but found identifier ...`.
  So every input with `extends` in that position failed to parse, and giving
  it a meaning changes no accepted program.
- **Contextual, not reserved.** Reserving `extends` would break variables,
  properties, keys, parameters, functions, methods, loop variables, catch
  bindings and classes with that name. Only the identifier `extends` directly
  after the name or parameter list on the same logical line qualifies. A
  newline ends a header, so `class Dog` followed by `extends = 1` on the next
  line keeps its meaning.
- **Parameters first.** Nucleoid's parameters belong to the class name, as in
  `class Dog(name) extends Animal`, matching Scala's
  `class Dog(name: String) extends Animal` and Kotlin's primary constructors.
  Rejected: `class Dog extends Animal(name)`, which reads as Scala's or
  Kotlin's superclass constructor call, or as a JavaScript mixin expression.
  Nucleoid passes parent arguments with `super(...)` in `init`, so it stays a
  syntax error.
- **One parent name.** The parent is one identifier, exactly as after
  `class Name:`, and may be declared later. Rejected: expressions, dotted
  names, `$Animal`, several parents and `implements`. Nucleoid has no mixins
  or interfaces, so these stay syntax errors.
- **The colon keeps one class body grammar.** After `extends Parent:`, the
  accepted body grammar of `class Name(params):` applies unchanged: an
  indented body, one statement on the same line, or, when the colon ends its
  line without indentation, the next statement as the one constructor
  statement. `class Dog:` and `class Dog: Animal` already behave this way.
  Rejected: an error or an empty body after a colon that ends its line. Either
  would give the colon a second meaning, so the `extends` and colon spellings
  of the same class would differ. Changing the accepted colon behavior would
  break accepted programs.
- **The bodyless form follows NUC 14.** Without a colon there is nothing to
  open a body, so the header ends at the statement boundary as
  `class Name(params)` does. Rejected: adopting the next statement as the
  colon spelling does, which would make `class Car extends Vehicle` followed
  by `car = Car()` fail as the motivating example does. Also rejected:
  requiring a colon, which would leave the most common foreign spelling an
  error.
- **A second parent stays an error.** After the colon, a name followed by
  the end of its line or input is where `class Dog: Cat` names its parent.
  Reading `Cat` there as a constructor statement would silently give
  `class Dog extends Animal: Cat` a meaning unrelated to `class Dog: Cat`, so
  it raises `Class 'Dog' already extends 'Animal'`.
- **Diagnostics.** `Expected a parent class name but found <token>` follows
  the existing `Expected <what> but found <token>` messages with the existing
  token descriptions. Like `expect`, it is placed at the offending token.
  Tokens after a well-formed parent keep the existing
  `Expected ':' but found <token>` diagnostic.
- **Same declaration.** The existing `ClassDecl` already records an optional
  parent, so the clause needs no token kind, syntax tree node or runtime
  path. The generator writes the colon spelling, so graph labels and canonical
  source do not distinguish the two spellings.
- **Shared parser helpers.** The bodyless terminator check, the colon's
  parent test and the class body are factored into helpers that both
  spellings call. The colon path keeps its accepted behavior, and the two
  spellings cannot disagree on boundaries, body grammar or what names a
  parent.
- **Interactive input.** The line-oriented REPL already buffers a header
  that ends in a colon, and the terminal workspace already indents after one,
  so a colon clause continues and a bodyless clause runs at once with no
  change. Like `while` ([NUC 63](nuc-0063.md)) and `suppose`
  ([NUC 65](nuc-0065.md)), `extends` joins the workspace's completion words.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial, reward or assessment.

## Specification

### Grammar

- After `class`, a name and an optional parameter list, the clause is the
  identifier `extends` followed by one identifier, the parent. A colon may
  follow:

```
class Name extends Parent
class Name(parameters) extends Parent
class Name extends Parent:
    body
class Name(parameters) extends Parent: statement
```

- The parameter list keeps its accepted grammar, including annotations,
  literal defaults, a final rest parameter and newlines inside the
  parentheses. The parent is an ordinary identifier, so a class or a parent
  may itself be named `extends`.
- With a colon, the body is that of `class Name(parameters):`: an indented
  body of typed fields, constructor statements, `init` and methods, or one
  statement on the same line. A colon that ends its line without an indented
  body takes the next statement, if any, as the one constructor statement,
  as after `class Name:` and `class Name: Parent`.
- Directly after that colon, a name followed by the end of its line or input
  is a second parent and raises
  `SyntaxError("Class '<Name>' already extends '<Parent>'")`.
- Without a colon, the header is bodyless. It ends at a logical newline,
  semicolon, end of input, or the enclosing block's closing brace or dedent.
  The terminator and the following statement are not part of a constructor.
- An indented body still requires the colon, including across blank lines,
  comments and semicolons.

### Semantics

- A colon clause builds the declaration of the colon spelling with the same
  body: the same name, parent, parameters, fields, constructor statements
  and methods. A bodyless clause builds that of the colon spelling with an
  indented `pass`.
- Registration in `Class`, separate parent and child instance lists, `$Parent`
  rules on child instances, the nearest ancestor constructor, `init`, `super`
  and bare `super`, named constructor arguments, inheritance cycle checks,
  redeclaration, graph keys, `why`, `affects`, rendering and transactions are
  therefore those of the colon spelling.

```
class Animal(name):
    this.name = name
$Animal.legs = 4
class Dog(name, breed) extends Animal:
    this.name = name
    this.breed = breed
    def speak():
        return this.name + " barks"
class Cat extends Animal:
    def speak() => this.name + " meows"
rex = Dog("Rex", "lab")
tom = Cat("Tom")
assert(rex.speak(), "Rex barks")
assert(tom.name, "Tom")
assert(tom.speak(), "Tom meows")
assert(tom.legs, 4)
assert(Animal.length, 0)
assert(Cat.length, 1)
```

- A bodyless clause stops at its boundary, so the following statement stays
  outside the class:

```
class Shape(sides):
    this.sides = sides
$Shape.polygon = $Shape.sides > 2
class Square extends Shape
square = Square(4)
class Triangle(sides) extends Shape; triangle = Triangle(3)
{ class Segment extends Shape }
segment = Segment(1)
assert(square.polygon, true)
assert(triangle.sides, 3)
assert(segment.polygon, false)
assert(Shape.length, 0)
```

- Spellings may be mixed within one inheritance chain:

```
class Base:
    def init():
        this.trace = "A"
class Middle extends Base:
    def init():
        super
        this.trace = this.trace + "B"
class Leaf: Middle
    def init():
        super
        this.trace = this.trace + "C"
class Passive extends Leaf
passive = Passive()
assert(passive.trace, "ABC")
```

### Rendering

- Canonical source writes the colon spelling. A class renders as
  `class Name` unless its parameters or its methods' parameters have literal
  defaults or a rest parameter. Such a class renders in full, with the parent
  after the colon of its header, as in `class Dog(name,...tags): Animal`,
  followed by its body.
- `why`, `affects`, graph keys and `--graph` output name `$Dog` and the
  colon-form rules, never the spelling the source used.

### Ordinary names

- Variables, properties and object keys, shorthand, parameters, functions,
  methods, loop variables, catch bindings, classes and parents named
  `extends` keep their accepted readings:

```
extends = 2
limits = {extends: 3}
def scale(extends) => extends * 10
class Gate:
    def extends(step) => step + 1
gate = Gate()
class extends
class Probe extends extends
$extends.ready = true
probe = Probe()
assert(extends + limits.extends, 5)
assert(scale(extends), 20)
assert(gate.extends(4), 5)
assert(probe.ready, true)
```

- The same error message elsewhere is unchanged: `if ready extends:` still
  raises `SyntaxError("Expected ':' but found identifier 'extends'")`, as do
  the corresponding `for`, `def`, `try`, `catch`, conditional, quantifier and
  method headers.

### Interactive input

- The line-oriented REPL buffers `class Dog extends Animal:` and
  `class Dog(name) extends Animal: # body` until a blank line, as it buffers
  other headers ending in a colon. It runs `class Dog extends Animal` at
  once, like `class Entity`.
- The terminal workspace indents the next line after a colon clause, not
  after a bodyless one, and offers `extends` as a completion word.
- No accepted REPL or terminal behavior changes otherwise.

## Errors

- No error type, runtime error or catch value is added. Syntax errors stop
  compilation before any statement of the program runs.
- `SyntaxError("Expected a parent class name but found <token>")`: the token
  after `extends` is not an identifier. It is placed at that token and uses
  the existing token descriptions, such as `end of input`, `end of line`,
  `';'`, `':'`, `'('`, `number 5`, `a string`, `'$Animal'` and
  `keyword 'this'`.
- `SyntaxError("Class '<Name>' already extends '<Parent>'")`: after
  `extends Parent:`, a name followed by the end of its line or input names a
  second parent. It is placed at that name.
- `SyntaxError("Expected ':' but found <token>")` remains the error for any
  other token after the parent, and for a bodyless clause followed by
  indentation (`end of line`, or `';'` after a semicolon).
- `SyntaxError("Statements are nested too deeply")` still bounds nesting:
  bodies and same-line statements after a clause pass the existing
  statement-depth guard, so 64 nested blocks or same-line clauses raise it.
- Runtime errors are those of the colon spelling, such as
  `TypeError("Circular Inheritance")` for `class Loop extends Loop` and for a
  redeclaration that closes a cycle.
- The Compatibility table lists exact former and new results.
