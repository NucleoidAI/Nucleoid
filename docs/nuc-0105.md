## Abstract

- Adds the read-only list query `sortBy` to ordinary lists and class
  populations, the receivers of `maxBy` and `minBy`:
  - `xs.sortBy(selector)` returns a new list of the receiver's items in
    ascending order of `selector(item)`. Items with equal keys keep their
    receiver order, so
    `[{n: "b", k: 2}, {n: "a", k: 1}, {n: "c", k: 2}].sortBy(x -> x.k)`
    lists `a`, `b`, `c`.
  - Keys compare as `<` compares them, the rule of `maxBy` and `minBy`: two
    strings as text, and every other pair as numbers.
  - The selector runs once for every item, in receiver order, and the items
    are returned unchanged, so an instance stays the same instance. An empty
    receiver gives `[]`.
- Unlike `sort`, which [NUC 58](nuc-0058.md) makes reorder a writable
  receiver in place, `sortBy` never writes its receiver.
  `ranked = scores.sortBy(s -> s)` is a standing ordering that follows later
  writes of `scores`, while `scores` keeps its own order.
- When every key can be compared with itself, the list `xs.sortBy(f)`
  evaluates to is exactly the list that
  `xs.map(x -> [f(x), x]).sort((a, b) -> a[0] < b[0] ? -1 : 0).map(p -> p[1])`
  evaluates to at the accepted revision, including where strings and other
  keys mix. A key that cannot be compared with itself makes the result
  undefined, as it makes `maxBy` and `minBy` undefined.
- Only calls of `sortBy` on lists and class populations change. They raised
  `TypeError("<receiver>.sortBy is not a function")` at the accepted
  revision. Reading `xs.sortBy` without a call, object properties named
  `sortBy`, instance methods named `sortBy` called on an instance, and every
  other receiver keep their accepted behavior.
- No token, keyword, syntax, error type or message format, option or public
  item is added. The authoritative contract is
  [List and population sorting by key](../nucleoid.spec.md#list-and-population-sorting-by-key).

## Motivation

- World models rank and order their objects: shapes by size, events by
  time, cells from left to right, bids by amount. [NUC 77](nuc-0077.md)'s
  `maxBy` and `minBy` pick the extreme item by a key, but a complete ordering
  by a key still needs a comparator, such as
  `Shape.sort((a, b) -> a.size - b.size)` for numeric keys, or
  `(a, b) -> a.name < b.name ? -1 : 0` for text, which reads both keys again
  on every comparison.
- [NUC 58](nuc-0058.md) makes `sort` reorder a writable receiver in place.
  `ranked = scores.sort(comparator)` therefore sorts `scores` itself. Two
  standing sorts of one list with different orders re-run each other, so a
  later change of that list raises `TypeError("Propagation did not settle")`.
  A derived ordering that leaves its list alone has to copy first, as
  `ranked = scores.slice().sort(comparator)` does. A read-only query that
  derives the order without writing state is the declarative form.
- Programmers and language models know key-based sorting from lodash's
  `_.sortBy`, Ruby's `sort_by`, Scala's `sortBy`, Kotlin's `sortedBy` and
  Python's `sorted(xs, key=f)`, yet `[3, 1, 2].sortBy(x -> x)` raises
  `TypeError("[3,1,2].sortBy is not a function")`.
- `Shape.sortBy(s -> s.size)` is ten lexer tokens against eighteen for
  `Shape.sort((a, b) -> a.size - b.size)` and seventeen for
  `Shape.sort(lambda a, b: a.size - b.size)`, and it names the key once
  instead of spelling a comparator. A list adds a copy to the comparator
  spelling: `ranked = scores.sortBy(s -> s.points)` is twelve tokens against
  twenty-two for `ranked = scores[:].sort(lambda a, b: a.points - b.points)`.

- **Category and mode.** The cycle that allocated this Draft made one
  tool-backed uniform draw over the five categories that NUC 1's registry
  marks eligible for automatic selection and selected Utility enhancement,
  index 2, with probability 1/5 and no redraw. A later continuous cycle
  found the Draft stale and claimed it with the pushed empty commit
  `Resume NUC 105 List and Population Sorting by Key`, `120db05d`, keeping
  its number, title, category and requested change without a new draw.
  Token comparison is required; runtime applicability does not apply to this
  category.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero. Strategy learning is `not_configured`, so this
  revision is unattributed, with no policy, selection receipt, trial or
  reward.
- **One more shared query.** `sortBy` joins `Runtime::list_query` beside
  `maxBy` and `minBy`, so lists however they are reached, through variables,
  members, slices, call results, `.value` snapshots and selected state
  versions, and class populations named by the class, by a variable that
  holds the class or by `$Name`, gain it at once, with the receiver snapshot,
  argument evaluation, receiver text and null-receiver routing of every other
  query. Rejected: a list-only method, which would leave `Name.sortBy(f)`
  raising where `Name.maxBy(f)` runs.
- **Read-only, unlike `sort`.** [NUC 58](nuc-0058.md)'s `sort` writes a
  writable receiver, so a declaration holding it is a standing sort of that
  list, and two standing sorts of one list conflict. `sortBy` never writes:
  `call_method` routes only `sort` through its writable-receiver path, so a
  declaration holding `sortBy` is a derived ordering, and several orderings
  of one list coexist. Rejected: an in-place `sortBy`; lodash's `_.sortBy`,
  Ruby's `sort_by`, Kotlin's `sortedBy`, Scala's `sortBy` and Python's
  `sorted` all return a new list.
- **The items themselves.** The query orders the objects of a model, so it
  returns those objects, unchanged and in order, as every prior art above
  does. The keys stay one query away: `xs.sortBy(f).map(f)`.
- **Compared as `<` compares.** The keys go to `compare`, the function behind
  `<` that `maxBy` and `minBy` already share: two strings compare as text, by
  code point, and every other pair as numbers with the numeric conversion of
  the comparisons, so dates compare by time. This is the comparison of the
  accepted comparator spellings, by construction rather than by a second set
  of rules.
- Rejected: [NUC 69](nuc-0069.md)'s numeric conversion, under which names,
  labels and codes written as strings would all be NaN; the order of the
  default `sort`, by string forms, under which `10` comes before `9`; and a
  new order across kinds of values, which the language does not have.
- **Ascending and stable.** Keys ascend, and items with equal keys keep their
  receiver order, as lodash's `_.sortBy`, Kotlin's `sortedBy`, Scala's
  `sortBy` and Python's `sorted` keep them, and as the accepted comparator
  sort keeps equal items. `0` and `-0` keys tie. A descending order of
  numbers negates the key, as `score -> -score.points` does.
- Rejected: a descending flag, a comparator argument, which is what `sort`
  takes, and several keys or a tie-breaking argument.
- **Defined by its accepted spelling.** When every key can be compared with
  itself, the list a call evaluates to is exactly the list of the decorate
  spelling `R.map(x -> [f(x), x]).sort((a, b) -> a[0] < b[0] ? -1 : 0).map(p -> p[1])`
  at the accepted revision: each item, in receiver order, is placed before
  the first already placed item whose key it compares below, which is the
  rule of the accepted comparator sort. That holds where strings and other
  keys mix too, where `<` is not a total order: a string that is not numeric
  is neither smaller nor greater than a number, and `"10" < "9"` as text
  while `9 < "10"` as numbers.
- **An unordered key makes the result undefined.** A key that cannot be
  compared with itself, undefined, NaN, an object, an instance, a class, a
  function, a regular expression or a list that converts to NaN, has no place
  in an order, so the result is undefined, which a declaration stores as
  `null`, as for `maxBy` and `minBy`. Every item is still visited, so every
  selector read is a dependency, and a declaration such as
  `queue = Job.sortBy(job -> job.due)` waits for every due date to be set and
  valid.
- Rejected: placing such items at either end, as some libraries do, and the
  decorate spelling's placement, under which such an item is never below
  another and so lands after every earlier item. Either would silently give
  an order in which an unknown key decides a position.
- **An empty receiver gives `[]`.** Ordering nothing gives an empty list, as
  `map`, `filter` and `sort` of an empty list do and as the decorate spelling
  does, so `board = Runner.sortBy(r -> r.time)` holds `[]` before the first
  runner. `maxBy` gives undefined there because nothing is the largest item
  of nothing; an empty order exists.
- **The selector is required.** `By` names the key, and without a selector
  `sortBy` would be a second `sort` with another comparison. A missing first
  argument, or one that is not a function, including `null`, raises
  `TypeError("sortBy expects a function")` after the arguments are evaluated,
  even on an empty receiver, as `maxBy` raises.
- Rejected: property-name selectors such as `Bid.sortBy("amount")`, which
  lodash accepts and [NUC 69](nuc-0069.md) and [NUC 77](nuc-0077.md)
  rejected for `max` and `maxBy`, and lodash's arrays of selectors.
- **The selector is called like `map`'s callback.** It runs once per item, in
  receiver order, with only the item; further parameters stay `null`. A
  `null` key compares as `0`, while a selector that reads a `null` binding or
  property settles a declaration to `null`, as the same callback does in
  `map`, `max` and `maxBy`. Extra arguments are evaluated once, left to
  right, and ignored, as every list query does.
- **Instance lists.** On a class name, `Name.sortBy(...)` is the population
  query even when the class declares an instance method `sortBy`, as for
  `maxBy`. The method stays reachable through each instance.
- **No noun form.** [NUC 75](nuc-0075.md)'s `NOUN of OPERAND` takes no
  argument, and `sortBy` needs its selector, so `sortBy of xs` keeps raising
  `SyntaxError("Unexpected keyword 'of'")`.
- **Bounded cost.** The receiver and the arguments are evaluated once per
  call and the selector once per item. Keys that are all strings, or among
  which none is a string, form a total preorder, and a stable sort orders
  them in O(n log n) comparisons; that is the order of the placement rule.
  Only a mix of strings and other keys follows the placement rule itself,
  over the computed keys, in up to O(n²) comparisons. The standard
  library's sort is never handed a comparison that is not a total order,
  since it may panic on one from Rust 1.81 on, and production code has no
  panic paths. The
  accepted comparator sort places every item by that linear scan and calls
  its comparator for each comparison, so its spellings take up to O(n²)
  calls, about n²/2 for a receiver already in order, where `sortBy` compares
  computed keys; [Cost](#cost) records the measurements.
- **Rendered as written.** Statements render as written, so `why` reports
  `ranked = scores.sortBy(function())`, as it renders every function
  argument, and a `sortBy` call and its accepted spelling are different
  statements and graph keys, as `sum of xs` and `xs.sum()` are under
  [NUC 75](nuc-0075.md). Rejected: lowering `sortBy` to its decorate
  spelling, which would render callbacks the source never wrote.
- **Where the accepted spellings differ.** The parity holds for the list a
  call evaluates to. A declaration settles by what each spelling reads, and
  depends on what each spelling evaluates, so these programs differ:
  - A decorate mapper reads its item: after `xs = [1, null]`,
    `r = xs.map(x -> [1, x]).sort((a, b) -> a[0] < b[0] ? -1 : 0).map(p -> p[1])`
    stores `null`, as `m = xs.map(x -> x)` does, while
    `r = xs.sortBy(x -> 1)` stores `[1, null]`, as `r = xs.maxBy(x -> 1)`
    stores `1`. As expression statements both give `[1, null]`.
  - A comparator is never called for one item: after `xs = [{k: null}]`,
    `r = xs[:].sort((a, b) -> a.k < b.k ? -1 : 0)` stores `[{k: null}]`,
    while `r = xs.sortBy(x -> x.k)` and the decorate spelling call their
    selector once per item, read the `null` key and store `null`.
  - An argument is evaluated even on an empty receiver: after
    `def key(x) => x.k`, `r = [].sortBy(key)` depends on `key`, so
    `affects key` lists `r`, as for `r = [].maxBy(key)`, while the decorate
    spelling's mapper never runs, so its declaration does not depend on
    `key`.
- **A pre-existing defect stays.** At the accepted revision, `def key(t):`
  with the body `if t.n > 1:` / `return 1` and then `return 0`, followed by
  `xs = [{n: 1}, {n: 2}]`, `ys = xs.map(x -> key(x))` and `xs[1].n = 0`,
  raises `ReferenceError("t is not defined")` at line 7, while writing
  `xs[0]`, or a body without the `if`, works. Every callback shares it,
  including `map`, `maxBy`, `sum` and `sort` comparators, and so does a
  `sortBy` selector. This proposal neither fixes nor pins it, and its cases
  stay clear of it.
- **Requires.** [NUC 58](nuc-0058.md), whose `sort` and comparator placement
  rule define the accepted spelling and whose in-place writes `sortBy`
  avoids, and [NUC 77](nuc-0077.md), whose comparison, unordered-key rule,
  selector rules and receivers `sortBy` shares. The Draft's list stands:
  those two already require everything else `sortBy` relies on, such as the
  shared query rules of [NUC 61](nuc-0061.md).
- **Not added.** A global `sortBy(...)`, `sortBy of xs`, a descending order
  or flag, several keys, tie-breaking or comparator arguments, property-name
  selectors, an in-place `sortBy`, aliases such as `sortedBy` or `orderBy`,
  `sortBy` on strings, objects or instances, results that pair the items
  with their keys, ranks or positions, and any change to `sort`, `maxBy` or
  `minBy`.

## Specification

- The normative contract is
  [List and population sorting by key](../nucleoid.spec.md#list-and-population-sorting-by-key).

### Calls

- `RECEIVER.sortBy(SELECTOR, ...)` is a list query when `RECEIVER` evaluates
  to a list, including a member, an index, a slice, a call result, a `.value`
  snapshot and a list read from a state version, or to a declared class,
  named by the class, by a variable that holds the class or by `$Name`, whose
  population in population order is the receiver.
- The receiver is read once, before the arguments. Every supplied argument
  is then evaluated once, left to right, and only the first is used.
- A `null` or undefined receiver keeps the accepted method route: the
  arguments are not evaluated and the call is undefined, so a declaration
  holding it stores `null` and re-runs once the receiver exists.
- On a class name the call is the population query even when the class
  declares an instance method `sortBy`; `instance.sortBy(...)` keeps calling
  the method.

### Order

- The result is a new list of the receiver's items in ascending order of
  their keys, `selector(item)`. The items are the items themselves: an object
  or instance stays the same object, and the keys are not returned.
- Items with equal keys keep their receiver order. An empty receiver gives
  `[]`. The receiver is never written, whatever its kind.

```
parcels = [{code: "B12", kg: 4}, {code: "A7", kg: 9}, {code: "B3", kg: 4}, {code: "C1", kg: 2}]
light = parcels.sortBy(parcel -> parcel.kg)
coded = parcels.sortBy(parcel -> parcel.code)
assert(light.map(parcel -> parcel.code), ["C1", "B12", "B3", "A7"])
assert(coded.map(parcel -> parcel.code), ["A7", "B12", "B3", "C1"])
assert(light[1] == parcels[0], true)
parcels.push({code: "A10", kg: 4})
assert(light.map(parcel -> parcel.code), ["C1", "B12", "B3", "A10", "A7"])
assert(coded.map(parcel -> parcel.code), ["A10", "A7", "B12", "B3", "C1"])
parcels.map(parcel -> parcel.code)
```

- This returns `["B12","A7","B3","C1","A10"]`: the receiver keeps its order.

### Keys

- Keys compare as `<` compares them: two strings as text, by code point, and
  every other pair as numbers with the numeric conversion of the
  comparisons. Dates compare by time, and `true`, `false`, `null`, empty
  lists and one-item lists count as numbers; `0` and `-0` tie.

| Keys | Order |
| --- | --- |
| `["10", "9", "2"]` | `["10", "2", "9"]` |
| `[10, 9, 2]` | `[2, 9, 10]` |
| `[true, null, false, [2], [], "1"]` | `[null, false, [], true, "1", [2]]` |
| `["b", 5, "a", 3]` | `["a", "b", 3, 5]` |
| `["10", 9, "9"]` | `[9, "10", "9"]` |

- Each row is `KEYS.sortBy(key -> key)`. The last three mix strings and
  other keys, so the placement rule below decides them; with one numeric
  string, as in the third, that is the numeric order.

### Unordered keys

- A key that cannot be compared with itself, one for which `key >= key` is
  `false`, makes the result undefined, which a declaration stores as `null`:
  undefined, NaN, objects, instances, classes, functions, regular expressions
  and lists that convert to NaN. Every item is still visited.

```
class Job(name):
    this.name = name
queue = Job.sortBy(job -> job.due)
press = Job("press")
press.due = new Date("2026-12-01")
coat = Job("coat")
assert(queue, null)
coat.due = new Date("2026-11-20")
assert(queue, [coat, press])
weld = Job("weld")
weld.due = new Date("2026-11-28")
assert(queue, [coat, weld, press])
weld.due = 0 / 0
assert(queue, null)
weld.due = coat.due
queue.map(job -> job.name)
```

- This returns `["coat","weld","press"]`: `weld` ties `coat` and keeps its
  population place after it.

### The accepted spelling

- When every key can be compared with itself, `R.sortBy(f)` evaluates to
  exactly the list that
  `R.map(x -> [f(x), x]).sort((a, b) -> a[0] < b[0] ? -1 : 0).map(p -> p[1])`
  evaluates to at the accepted revision, including where strings and other
  keys mix. Both read the receiver once and call `f` once per item, in
  receiver order, with only the item.
- The reference order is the accepted comparator sort's: each item, in
  receiver order, is placed before the first already placed item whose key
  it compares below, and after every placed item otherwise.
- When the keys are all strings, or none is a string, they form a total
  preorder, and that placement is the stable ascending sort.
- Declarations differ where the spellings read or evaluate different things,
  as [Where the accepted spellings differ](#rationale) lists: a decorate
  mapper that reads a `null` item, a comparator that one item never calls,
  and a named-function argument on an empty receiver.

### Selectors and reads

- The selector is required. It is called once for every item, in receiver
  order, with the item as its only argument; further parameters are `null`.
  The call order and the argument are those of `map`.
- A missing first argument, or one that is not a function, including `null`,
  raises `TypeError("sortBy expects a function")`, even on an empty receiver.
- Every supplied argument, including unused extras, is evaluated once, left
  to right, after the receiver and before the first selector call.
- A `null` key compares as `0`. Reads inside a selector follow the existing
  rules, so a selector that reads a `null` binding or property settles a
  declaration to `null`, while an item the selector does not read stays an
  item.

| Exact source | Result |
| --- | --- |
| `xs = [1, null]`, then `r = xs.sortBy(x -> 1)` | `r` is `[1, null]` |
| `xs = [1, null]`, then `r = xs.sortBy(x -> x)` | `r` is `null` |
| `xs = [{k: null}, {k: -1}]`, then `r = xs.sortBy(x -> x.k)` | `r` is `null` |
| `[{k: null}, {k: -1}].sortBy(x -> x.k).map(x -> x.k)` as an expression statement | `[-1, null]` |

### Liveness and class-level rules

- A declaration that uses `sortBy` depends on the list or population, on its
  argument expressions and on whatever the selector reads for every item.
  Pushing, popping, shifting or replacing a list, creating or deleting an
  instance, and changing a property that a selector reads re-evaluate it.
- In a class-level rule, each instance evaluates its own ordering, and
  `$Class` inside a selector is the instance the rule is evaluated for.

```
class Runner(name, time):
    this.name = name
    this.time = time
$Runner.place = Runner.sortBy(runner -> runner.time).indexOf($Runner) + 1
ana = Runner("ana", 31)
bo = Runner("bo", 28)
cy = Runner("cy", 31)
assert([ana.place, bo.place, cy.place], [2, 1, 3])
bo.time = 33
assert([ana.place, bo.place, cy.place], [1, 3, 2])
Runner("di", 25)
[ana.place, bo.place, cy.place]
```

- This returns `[2,4,3]`: `ana` and `cy` tie and keep their population order.

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` output and graph and block keys
  show the call as written, with function arguments rendered as
  `function()`: the rule that `why ranked` reports is
  `ranked = scores.sortBy(function())`. A `sortBy` call and its accepted
  spelling are different statements and keys.

### Transactions

- Selector errors propagate through the existing transaction, so a failed
  standing re-evaluation rolls back the change that triggered it, including
  a list write or a new instance, and a failed statement or transaction
  restores sorted declarations, their values and their dependencies.

```
parcels = [{id: 1, code: "B2"}, {id: 2, code: "a9"}]
labels = parcels.sortBy(parcel -> parcel.code.toUpperCase()).map(parcel -> parcel.id)
failure = ""
try:
    parcels.push({id: 3, code: 7})
catch error:
    failure = error
assert(failure, TypeError("number.toUpperCase is not a function"))
assert([parcels.length, labels], [2, [2, 1]])
parcels.push({id: 4, code: "a1"})
assert(labels, [4, 2, 1])
try:
    parcels[0].code = "a0"
    assert(labels, [1, 4, 2])
    throw "UNDO"
catch error:
    assert(error, "UNDO")
labels
```

- This returns `[4,2,1]`: the codes order without regard to case, the failed

### Cost

- The receiver and the arguments are evaluated once per call, and the
  selector once per item. Each key is checked once for an order with itself.
- Keys that are all strings, or among which none is a string, are ordered by
  a stable sort in O(n log n) comparisons. A mix of strings and other keys is
  ordered by the placement rule over the computed keys, in up to O(n²)
  comparisons, the worst case of the accepted comparator sort, which calls
  a comparator for each one.
- **Measured** on a release build of the candidate's library, rustc 1.97.1,
  through the public API, of `Runtime::run` calls of an expression statement
  that ends in `.length`. Each `sortBy` figure is the median of five calls,
  three from 500,000 items; each figure of the accepted spellings the median
  of three calls up to 4,000 items and one call above; and each mixed-key
  figure the median of three calls up to 32,000 items and one call above. A
  list is held in an object property, and a population is created first by
  `while` loops. Every call includes reading the receiver. Number keys
  repeat about four times each, text keys are the same values written as
  seven-digit codes, and instances hold such a number in `k`. Larger sizes
  are labeled as projections wherever no run was made.
