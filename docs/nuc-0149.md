## Abstract

- Optionally omit a list-element comma when a complete ordinary element
  leaves the next element on a later physical source line:

  ```
  seed = 2
  readings = [
      seed
      seed + 1
      seed * 2
  ]
  ```

- This is a separator change, not a new list type. Reuse the accepted list
  AST, standing declarations, dependency tracking and runtime behavior.
  Keep commas, trailing commas, nested lists and existing item-word rules.
- Preserve every previously accepted parse and behavior. Parse the whole
  original element before considering a separator: calls, subscripts,
  operators and comprehensions retain their priority across newlines.
  Same-line omissions such as `[1 2]` remain syntax errors. Distinguish a
  newline after a token from a newline inside a multiline literal.

- **Accepted:** all three hard criteria and every independent policy check
  passed. Continuous-mode token comparison found two shorter cases, 1,322
  unchanged cases and no increases.

## Motivation

- Lists written vertically already give each element a visible boundary.
  Requiring a comma at every such boundary repeats that structure and adds
  lexer tokens without changing the model.
- NUC 44 relaxed explicit object-property separators but deliberately left
  lists unchanged. This separate, bounded syntax proposal addresses physical
  newline boundaries without removing arbitrary list or call commas.
- The caller's existing uniform category draw selected Syntax enhancement.
  This proposal stays in that category and continuous mode; actual per-case
  token comparison against executed accepted-syntax counterparts is required.

## Rationale

- Recognize a boundary only after the unchanged ordinary item parser
  succeeds. A newline cannot terminate an unfinished expression or rescue
  a failed call, subscript, conditional or other expression.
- Keep the entire accepted parse-pass sequence first, including its word,
  comprehension, receiver, receiver-parameter and operator-section readings.
  Even a runtime-failing accepted parse wins. Only an input that fails that
  whole sequence is considered with optional newline separators.
- Preserve the public token stream instead of exposing layout tokens inside
  brackets. Private scanner end-line metadata distinguishes the gap after a
  token from a line break inside a string, template or continued regex.
- Commas remain necessary at ambiguous boundaries. In particular,
  `[[1, 2]` followed by `[0]]` on another line is a subscript expression,
  not two rows. Keep the outer comma and omit suitable commas inside rows.
- Reject same-line whitespace separators, early expression splitting,
  speculative item-error recovery and changes to call or parameter grammar.
  Integer ranges, destructuring and other pending proposals are out of scope.

## Specification

- This is optional syntax for the existing list literal, not a new value,
  syntax-tree variant, scope, dependency or runtime operation.
- Try every existing parse reading of the whole input with the original
  comma-only list grammar first. Preserve its first successful result and
  the existing error-selection rules within that sequence.
- Only after that sequence fails, repeat it once with physical-newline
  boundaries enabled. Each item still uses the original full `list_head`
  or `item` parser and its normal expression context and limits. Propagate
  an item error; never retry a prefix as a shorter item.
- After a successful complete item, keep an explicit comma first. Otherwise
  another iteration is permitted only when the next token starts on a
  physical line after the preceding token ends. The guard consumes no
  token. A closing bracket still closes the list; an invalid next item
  still fails normally. Each iteration consumes a complete item.
- Do not take a boundary before contextual `is`: let the existing word
  comparison retry finish that item, including `is not`. This priority also
  holds when another list in the same input needs the new separator.
- An LF outside the preceding token qualifies, including the LF of CRLF,
  a blank line or a comment. A bare CR, spaces, tabs or a same-line comment
  do not qualify. No LF inside a string, template or regex qualifies as a
  boundary after that token. An escaped regex LF remains part of its token.
- Calls, indexes, slices, members, version reads, operators, assignments,
  conditionals, arrows, lambdas and comprehensions retain full-expression
  priority across newlines. A following `(` or `[` may therefore continue
  the preceding expression; use a comma when two items are intended.
- Empty lists, ordinary commas, mixed comma/newline separators and trailing
  commas remain valid. Item-word marking under `is` assignments and variable
  readings under `=` are unchanged. The rule also applies in separately
  parsed template interpolations, using their own source boundaries.
- Public `tokenize`, `Spanned`, `Token`, token start positions, list AST shape,
  canonical comma rendering and runtime list behavior remain unchanged.
  The existing 64-level nesting and 128-link expression-chain guards remain.
- The normative contract is
  [Newline-separated list elements](../nucleoid.spec.md#newline-separated-list-elements).
  Its `Nucleoid separates list elements on new lines` case and the reference
  `Nucleoid nests newline separated lists` case retain their two executed
  accepted counterparts' identities, six ordered canonical assertions each
  and explicit expected return `1`. No historical executable case is rewritten.

## Errors

- No new error kind or message is introduced. Existing expression errors
  and closing-bracket diagnostics retain their token descriptions and
  physical positions when no new separator applies.
- Exact `items = [1 2]` retains
  `SyntaxError("Expected ']' but found number 2")` at line 1, column 12.
  Its existing NUC 44 regression remains unchanged.
- In exact `items = ["é` followed by `猫" 2]` on the next line, the newline
  is inside the string: retain the same closing-bracket error at line 2,
  column 4. Multiline single-quoted strings, templates and continued regex
  tokens likewise do not supply a separator on their closing line.
- Exact `items = [f` followed by `(1 2)]` retains
  `SyntaxError("Expected ')' but found number 2")` at line 2, column 4.
  Exact `items = [[1]` followed by `[2, 3]]` retains
  `SyntaxError("Expected ']' but found ','")` at line 2, column 3.
  Neither is recovered as a list boundary.
- The accepted parse of exact `result = [1` followed by `(2)]` still raises
  `TypeError("1 is not a function")` at line 1, column 1. Runtime failures
  do not permit another syntax reading.

## Reference Implementation

- `lexer/scanner.rs` records each scanned token's actual ending line after
  any regex continuation. `lexer/source.rs` derives sorted private positions
  at which an inter-token physical line break occurred, then calls the
  unchanged layout transformation. The public lexer still returns exactly
  its original token/position representation.
- `parser/source.rs` preserves that metadata through the existing parse
  retries and runs the comma-only reading before the newline-enabled one.
  `parser/list.rs` retains the ordinary item/comprehension/word-marking loop
  and adds a non-consuming source-boundary guard after the comma check.
  That guard defers contextual `is` to the existing comparison reading.
  `parser/template.rs` carries the selected reading into interpolation
  parsers without sharing their relative source positions.
- `docs/nucleoid.ebnf` records the zero-token contextual list boundary,
  whole-expression priority, physical-token-end contract and outer parse-pass
  priority. No new public token is added.
- `tests/newline_list_elements.rs` covers paired cases and native grammar,
  runtime, diagnostic, multiline-token, retry, limit and state regressions.
  Canonical synthesized records are in `dataset/nucleoid.synth.149.jsonl`.
  The specification JSONL and exported Rust tests are regenerated from
  their sources, never hand-edited.
- Preparation uses allocation revision
  `8844869ce2fc9eaaf7dbce1958755c0adb9ad01d` and the caller's immutable
  1,324-case baseline. The original preparation handoff records no outcome;
  the completed Rust improvement pass, independent evaluation and caller's
  integrated decision are recorded below.

## Backward Compatibility

- An accepted parse returns before newline separation is enabled, regardless
  of whether execution would succeed. Original parser readings, item errors,
  native NUC 44 diagnostics and all historical programs remain protected.
- Newline-enabled parsing uses the same item grammar without newline-aware
  early stopping or error recovery. Only a successful item's remaining
  inter-token gap can omit its comma.
- Public Rust signatures and variants, tokenization and positions, generated
  comma source, standing list relationships, class rules, propagation,
  snapshots and transactions keep their existing meaning. No dependency,
  feature flag, CLI option, ARC change, version or MSRV change is included.
