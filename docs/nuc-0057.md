# NUC 57 -- Thin Arrows and Python-Style Lambdas

```
NUC: 57
Title: Thin Arrows and Python-Style Lambdas
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 28-Oct-2026
Requires: 8, 12, 18, 20, 27, 29, 32, 37, 44, 45, 54
```

## Abstract

- Add `->` as an optional spelling of the `=>` arrow, accepted everywhere
  `=>` is accepted, with identical parsing, AST and runtime behavior.
- Add contextual Python-style lambdas: `lambda: expression`,
  `lambda name: expression` and `lambda first, second: expression` lower to
  exactly `() => (expression)`, `(name) => (expression)` and
  `(first, second) => (expression)`.
- `=>` stays canonical. Every accepted form keeps its parsing, AST, canonical
  rendering and behavior, and `lambda` is not a reserved word.
- This second revision re-prepares the first on the current accepted
  baseline. Independent evaluation rejected the first revision because its
  lambda scan took over [NUC 45](nuc-0045.md)'s `assert:` statement after an
  expression, as in `x = lambda assert: x, 1`. This revision leaves that
  statement, and every other colon-led reading, with its accepted meaning.
- The authoritative contract is
  [Thin arrows and Python-style lambdas](../nucleoid.spec.md#thin-arrows-and-python-style-lambdas).

## Motivation

- Nucleoid's goal is a superset of Python, JavaScript/TypeScript, Kotlin, Go,
  Rust, Java, C# and C/C++. Java writes lambdas as `item -> item * 2` and
  `(left, right) -> left + right`; Python writes `lambda item: item * 2`.
  Both currently fail to parse.
- Lambdas are how lists and class lists are queried ([NUC 8](nuc-0008.md)).
  Callbacks written in a familiar style should join the same dependency graph
  instead of raising a syntax error, especially in LLM-written programs.
- Both spellings reuse the existing anonymous function, so they need no new
  runtime semantics, AST node, evaluation path or canonical spelling.

## Rationale

- **`->` is its own token.** Lex adjacent `->` as `Token::ThinArrow` and let
  the parser accept `Arrow` or `ThinArrow` wherever it accepted `Arrow`,
  through one `Token::is_arrow` predicate. A separate token lets diagnostics
  name the arrow that was written: `def f -> 1` reports
  `Expected '(' but found '->'`, not `'=>'`.
- Rejected: lexing `->` as `Token::Arrow`, which would misreport every `->`
  diagnostic as `'=>'`. Rejected: a parser check for adjacent `Minus` and
  `Greater` tokens, which would depend on source positions and would also
  have to keep `- >` with whitespace distinct.
- **Adjacent `->` had no accepted meaning.** Both binary and unary `-` require
  an operand, and `>` cannot start one, so every accepted program spelling
  `->` outside a string, a template's literal text, a regular expression or a
  comment was a syntax error. Longest-match lexing still reads `-=>` as `-=`
  then `>` and `x>-1` as `>` then `-`; `x-->y` reads as `-` then `->`.
- **Return annotations.** Python (`def f(x) -> int:`), Rust
  (`fn f(x) -> i32`) and C++ trailing return types spell a return type with
  `->`. Making `->` an arrow means these lookalikes behave exactly like their
  `=>` spellings: `def f(x) -> int` returns the value of `int`,
  `def f() -> int => 1` returns a one-parameter function, and
  `def f(x) -> int:` followed by a body still fails, now at the colon.
- That trade-off is deliberate. Return annotations are not part of the
  accepted language, and earlier NUCs list them as not added. A future
  proposal could still claim only `def NAME PARAMS -> TYPE:` followed by a
  real indented suite, which remains invalid under this NUC, through a
  complete non-consuming guard. Expression-bodied annotation spellings and
  Rust-style `-> Type { ... }` would collide with this alias exactly as they
  already collide with `=>`.
- **`lambda` is contextual.** Reserving it would break programs that use
  `lambda` as a variable, key, member, label, parameter or annotation.
  Instead, a complete non-consuming scan at an operand position qualifies
  `lambda`, then nothing or comma-separated ordinary names, then `:`.
- **Where accepted syntax owns the colon.** The accepted parser reads
  `lambda` at an operand position as a complete operand. No name, comma or
  colon continues an expression, so whatever follows `lambda` belongs to the
  construct around the expression it ends.
- Statement loops accept a statement directly after another, with no
  separator. Exactly two statements begin with a name and a colon: a typed
  declaration, whose colon is followed by one name and a newline, semicolon,
  dedent or end of input, and [NUC 45](nuc-0045.md)'s `assert:` statement.
  Class bodies read the same declaration as a field.
- So the scan leaves `lambda` an ordinary identifier in exactly these places:
  - the top level of `if`, `else`, `elif` and `for` headers, subscript starts
    (the index or slice start inside `[...]`) and template interpolations,
    whose colon belongs to the header or slice and whose interpolation ignores
    trailing tokens;
  - a single parameter in an object-literal value, where
    `{first: lambda next: 2}` is [NUC 44](nuc-0044.md)'s pair of comma-free
    properties;
  - a single parameter whose colon starts one of those two statements:
    `this.copy = lambda x: int` keeps assigning `lambda` and declaring the
    field `x`, and `x = lambda assert: x, 1` keeps assigning `lambda` and then
    running the assertion statement.
- The scan asks the statement parser's own guards, `is_type_declaration_at`
  and `is_assertion_statement_at`, whether such a statement starts there, so
  the two cannot disagree.
- Every other lambda shape was a syntax error, so recognizing it is
  additive. A colon directly after the operand has no owner outside the
  excluded places. A name and a colon after it start only the excluded
  property or statements. A name and a comma after it start nothing:
  statement loops, suites, call arguments, lists and object literals all
  reject the comma, so lambdas with two or more names never collide.
- Parentheses or call arguments select the lambda in the excluded places, for
  example `(lambda x: x)` or `items.map(lambda x: x)`. Only a single
  parameter named `assert` never qualifies, even there; a lambda with more
  names may still name one `assert`.
- Rejected: keyword semantics, which break the readings above. Rejected:
  trying a lambda and falling back on failure, which the parser avoids; one
  complete lookahead decides without consuming tokens. Rejected: excluding
  `assert:` only where a statement may follow, which would need another
  expression context just to admit a lambda that no accepted program
  contains; Python also rejects `assert` as a parameter name.
- **Bounded to Python's lambda.** Parameters are plain comma-separated names
  and the body is one expression. Python forbids annotations in lambdas, and
  the colon would be ambiguous. Defaults, trailing commas, starred,
  parenthesized or keyword parameters, statement bodies and indented bodies
  are not added; the parenthesized arrow already provides annotations,
  defaults ([NUC 54](nuc-0054.md)) and braced statement bodies.
- A leading brace in a lambda body is an object literal, matching Python's
  dict displays and named-arrow bodies ([NUC 32](nuc-0032.md)), so
  `lambda left, right: {left, right}` returns an object.
- **Alias lowering.** A lambda builds the same
  `Expr::Function(Function { name: None, parameters, body: FunctionBody::Expression(...) })`
  as the parenthesized arrow, with untyped, defaultless parameters. Canonical
  rendering, graph keys, invocation, parameter shadowing, noncapturing scopes,
  dependencies and duplicate-name handling are therefore inherited.
- The body extends exactly as an anonymous arrow's expression body does: an
  assignment-level expression that stops at `,`, `)`, `]`, `}` or the next
  comma-free property in an object value. Like an arrow, a lambda may appear
  wherever an operand may.
- This single-proposal request skips token comparison. Neither spelling is
  shorter than the canonical arrow it aliases, so no accepted case is
  rewritten; new cases are appended.

## Specification

### Thin arrows

- The lexer reads adjacent `->` as one `Token::ThinArrow`, described as
  `'->'`. `-` and `>` separated by whitespace remain `Minus` and `Greater`.
  Strings, template text outside interpolations, regular expressions and
  comments keep their text; an interpolation is an expression and accepts
  either arrow.
- `Token::is_arrow` is true for `Arrow` and `ThinArrow`. A `/` after either
  arrow starts a regular expression.
- Every arrow position accepts either spelling with identical parsing:
  - anonymous `name -> body` and parenthesized `(params) -> body`, including
    annotations, literal defaults, trailing commas and braced statement
    bodies;
  - named `def name(params) -> expression` ([NUC 12](nuc-0012.md)), bare
    single ([NUC 18](nuc-0018.md)), bare typed single
    ([NUC 20](nuc-0020.md)), bare multiple ([NUC 27](nuc-0027.md)), bare
    typed/mixed multiple ([NUC 29](nuc-0029.md)) and comma-free
    ([NUC 37](nuc-0037.md)) headers;
  - [NUC 32](nuc-0032.md)'s single expression in a real indented body,
    methods, `init`, nesting and redefinition.
- Both spellings produce the same complete AST and canonical source, so
  graph keys, evaluation and runtime behavior are identical. Spellings may be
  mixed, one per arrow.
- The native REPL buffers a lexical named header ending in its only arrow of
  either spelling, including a trailing comment; arrow text in literals or
  comments does not count. The parser still validates the committed input.

### Lambdas

- Grammar, at an operand position:
  `lambda` `:` expression, or
  `lambda` Identifier (`,` Identifier)* `:` expression.
- `lambda` must be an ordinary `Identifier` spelled exactly `lambda`. Names
  are ordinary identifiers; keywords such as `this`, `self`, `null`, `else`
  and `catch`, `$Type` references and literals do not qualify. Ordinary
  lexer whitespace is allowed; no newline, semicolon or comment-induced break
  is skipped.
- `name => body` and `name -> body` are checked first, so `lambda -> lambda * 2`
  is an arrow whose parameter is named `lambda`.
- The scan never qualifies:
  - at the top level of a clause header, subscript start or template
    interpolation;
  - for exactly one name in an object value;
  - for exactly one name whose colon starts a statement: a name whose colon
    is followed by an identifier and then a newline, semicolon, dedent or end
    of input (the existing typed-declaration boundary, without a right-brace
    boundary), or the name `assert`, whatever follows its colon
    ([NUC 45](nuc-0045.md)'s statement).
- A statement-leading `lambda: Type` is still parsed as a typed declaration
  first and keeps raising `ReferenceError("Missing definition")`.
- Lowering: consume the qualified names as untyped parameters without
  defaults, consume the colon, and parse the body as the anonymous arrow's
  expression body in the enclosing expression context.
- Grouping parentheses, call arguments, list items and slice ends start a
  fresh context, so a lambda is recognized there even when the enclosing
  expression is a header, subscript start or interpolation.
- Lambdas nest within the existing expression depth bound. Parameter lists
  are uncapped, like parenthesized lists.

```
scale = 3
items = [1, 2, 3]
tripled = items.map(lambda item: item * scale)
total = items.reduce(lambda sum, item: sum + item, 0)
zero = lambda: 0
add = lambda left, right: left + right
pair = lambda left, right: {left: left, right: right}
assert(tripled, [3, 6, 9])
assert(total, 6)
assert(zero(), 0)
assert(add(2, 3), 5)
assert(pair(1, 2).right, 2)
assert((lambda value: value * 2)(4), 8)
scale = 2
assert(tripled, [2, 4, 6])
items.push(4)
assert(tripled, [2, 4, 6, 8])
assert(total, 10)
```

### Compatibility

- Variables, assignments, compound targets, members, calls, indexing and
  version reads named `lambda` are unchanged, as are object keys, shorthand,
  constructor labels, function and class names, parameter names and
  annotations, typed declarations, class fields, catch parameters and loop
  variables.
- `if lambda:`, `else lambda:`, `elif lambda:`, `for item of lambda:`,
  `for lambda:`, `items[lambda:]`, `{first: lambda next: 2}`,
  `` `${lambda: 1}` ``, `return lambda x: int`,
  `this.copy = lambda x: int` and `x = lambda assert: x, 1` keep their
  accepted readings.
- The juxtaposed `assert:` statement keeps its reading in every statement
  context: after assignments, compound assignments, `return`, `throw` and
  `delete`, inside operators and reasoning stages, in anonymous and named
  arrow bodies, inline and indented suites, braced blocks and class bodies.
- Existing `=>` arrows, `function(...) { ... }` expressions, named arrow
  headers, colon suites and assertion statements keep their grammar and
  diagnostics.
- No public AST node, runtime path, generator change, keyword, dependency,
  MSRV or project version is added. `Token::ThinArrow` and `Token::is_arrow`
  are public additions to the lexer API; adding a variant to the exhaustive
  public `Token` enum needs human SemVer review before publication.
- The public `parse_expression` library function still parses one leading
  expression and ignores what follows it, and that expression may now be a
  lambda: `parse_expression("lambda x: 1")` returns the function, not
  `Identifier("lambda")`. The runtime never calls it: programs use the
  statement parser, and template interpolations parse in the clause context.
  This library-level change also needs human SemVer review.

```
lambda = 1
values = [10, 20, 30]
assert(values[lambda:], [20, 30])
record = { first: lambda next: 2 }
assert(record.first, 1)
assert(record.next, 2)
keyed = { lambda: 5 }
assert(keyed.lambda, 5)
short = { lambda }
assert(short.lambda, 1)
if lambda:
    state = "on"
assert(state, "on")
alias = lambda assert: alias, 1
double = lambda -> lambda * 2
assert(double(4), 8)
lambda = 2
assert(values[lambda:], [30])
assert(record.first, 2)
assert(alias, 2)
```

## Errors

- No new error type, message format or runtime error is added. Existing
  diagnostics name `'->'` where the source wrote it.
- Programs that previously failed may now parse, or fail with a different
  existing message. The changed diagnostics include:

| Exact source | Previous error | Error under this NUC |
| --- | --- | --- |
| `def f -> 1` | `SyntaxError("Expected '(' but found '-'")`, line 1, column 7 | `SyntaxError("Expected '(' but found '->'")`, line 1, column 7 |
| `x = ->` | `SyntaxError("Unexpected '>'")`, line 1, column 7 | `SyntaxError("Unexpected '->'")`, line 1, column 7 |
| `x = 1->2` | `SyntaxError("Unexpected '>'")`, line 1, column 8 | `SyntaxError("Unexpected '->'")`, line 1, column 8 |
| `def f(x ->` | `SyntaxError("Expected ')' but found '-'")`, line 1, column 9 | `SyntaxError("Expected ')' but found '->'")`, line 1, column 9 |
| `def f x ->` | `SyntaxError("Expected '(' but found identifier 'x'")`, line 1, column 7 | `SyntaxError("Unexpected end of input")`, line 1, column 11 |
| `def f x ->` then a newline | the same `Expected '(' but found identifier 'x'` | `SyntaxError("Unexpected end of line")`, line 2, column 1 |
| `def f x ->;` then an indented `x` | the same `Expected '(' but found identifier 'x'` | `SyntaxError("Unexpected ';'")`, line 1, column 11 |
| `def f() -> int:` then an indented `return 1` | `SyntaxError("Expected ':' but found '-'")`, line 1, column 9 | `SyntaxError("Unexpected ':'")`, line 1, column 15 |
| `def f amount -> int:` then an indented `return amount` | `SyntaxError("Expected '(' but found identifier 'amount'")`, line 1, column 7 | `SyntaxError("Unexpected ':'")`, line 1, column 20 |
| `f = lambda x:` | `SyntaxError("Unexpected ':'")`, line 1, column 14 | `SyntaxError("Unexpected end of input")`, line 1, column 14 |
| `f = lambda:` then an indented `1` | `SyntaxError("Unexpected ':'")`, line 1, column 11 | `SyntaxError("Unexpected end of line")`, line 2, column 5 |
| `f = lambda x: { return x }` | `SyntaxError("Unexpected ':'")`, line 1, column 15 | `SyntaxError("Expected a key but found keyword 'return'")`, line 1, column 24 |

- `def f(x) -> int { return x }` and `def f() -> int => 1` now parse exactly
  like their `=>` spellings; the first then evaluates `return x` in a
  following top-level block and raises `ReferenceError("x is not defined")`.
- Unqualified and excluded lambda shapes keep their accepted identifier
  reading and exactly its errors:

| Exact source | Unchanged error |
| --- | --- |
| `f = lambda x=1: x` | `SyntaxError("Unexpected ':'")`, line 1, column 17 |
| `f = lambda (x): x` | `SyntaxError("Unexpected ':'")`, line 1, column 17 |
| `f = lambda x,: x` | `SyntaxError("Unexpected ','")`, line 1, column 14 |
| `f = lambda assert:` | `SyntaxError("Unexpected end of input")`, line 1, column 19 |
| `f = lambda assert: 1, 2, 3` | `SyntaxError("Assertion statements expect exactly two arguments")`, line 1, column 24 |
| `items.map(lambda assert: assert)` | `SyntaxError("Expected ')' but found identifier 'assert'")`, line 1, column 18 |
| `x = lambda assert: x, 1` while `lambda` is unbound | `ReferenceError("lambda is not defined")`, line 1, column 1 |
| `f = lambda x: int` while `lambda` is unbound | `ReferenceError("lambda is not defined")`, line 1, column 1 |
| `lambda = 1` then `f = lambda x: int` | `ReferenceError("Missing definition")`, line 2, column 12 |

- Resource bounds are unchanged: deeply nested lambdas or arrows raise
  `SyntaxError("Expressions are nested too deeply")`.
- Runtime errors are inherited from anonymous arrows, including noncapture:
  calling the inner function of `lambda a: lambda b: a + b` raises
  `ReferenceError("a is not defined")`, as the `=>` spelling does.

## Reference Implementation

- `src/lang/ast/lexer.rs` adds `Token::ThinArrow`, its `'->'` description
  and the public `Token::is_arrow` predicate.
- `src/lang/ast/parser.rs` accepts either arrow through `eat_arrow`,
  `expect_arrow` and `is_arrow` in every arrow guard, replaces the private
  object-value flag with a closed `ExpressionContext` (`Ordinary`,
  `ObjectValue`, `Clause`), and adds the non-consuming
  `lambda_parameter_count` scan and `lambda` lowering. Clause headers,
  subscript starts and template interpolations parse in the `Clause` context.
- The scan's statement exclusion is `starts_colon_statement_at`: the
  typed-declaration guard `is_type_declaration_at` or the new
  `is_assertion_statement_at`, which the parser's declaration, class-field
  and `assert:` branches use.
- `src/main.rs` buffers named REPL headers ending in either arrow spelling.
- `tests/thin_arrows_and_lambdas.rs` covers AST and canonical equivalence for
  every arrow position, the lambda lowering, every preserved `lambda` name
  reading including the juxtaposed `assert:` statement in every statement
  context, return-annotation lookalikes, exact diagnostics, runtime behavior,
  nesting bounds and native stdin input. Lexer, parser and REPL unit tests
  cover the token, the lookahead, the shared colon-statement guard and
  header buffering.
- The return-annotation probes in ten earlier bare-header regression files
  now spell the unsupported annotation as a separated `- >`, keeping their
  exact accepted errors; the new file asserts the original adjacent `->`
  sources behave exactly like their `=>` spellings.
- The root specification, executable reference, README, examples, the
  consolidated reference, a new canonical `dataset/nucleoid.synth.37.jsonl`
  and the regenerated normative exports are synchronized in the isolated
  candidate.

## Evaluation

- Accepted in single-proposal mode on the independent evaluator's overall
  `Accepted` decision, against accepted language revision
  `0f1b35e1fa1726611a6f7bc3430e499e7f618030` and its immutable 689-case
  accepted-corpus baseline. The candidate was integrated unchanged.
- Evaluated proposal Git blob:
  `ceeda3f80f72b224b6c9e64304e12616c9f5c74c`, before this outcome metadata.
- Single-proposal mode skipped token comparison (`single_proposal`); no
  per-case counts were measured, and a skip is not a passing token gate.
- The deterministic core gate reported `accepted` with no issues: all 689
  pinned accepted programs replayed with their assertions, expected returns
  and coverage, and all 697 candidate cases passed, including the eight new
  cases with full assertion coverage.
- As a user-requested proposal, the frozen candidate also met the
  user-requested proposal rule in `.claude/rules/proposals.instructions.md`:
  the full `cargo test` suite compiled without errors or warnings and passed
  1,674 tests with 0 failures and 25 ignored. All 1,673 baseline tests remain
  and pass, the 26 new tests pass, and no existing test was removed or
  weakened.
- The 16 return-annotation probes in ten earlier test files are respelled
  from `->` to `- >`. The evaluator judged them modified, not weakened: both
  spellings lex to `-` then `>` at the accepted revision, so each probe still
  checks its identical error. The baseline versions of those files fail 12
  test functions against this revision, where the adjacent `->` sources now
  behave like their `=>` spellings, as the new suite asserts.
- `cargo fmt --check`, warning-denied Clippy, export consistency and every
  Errors table row passed independently, without regeneration.
- Differential parsing against the accepted build found no accepted-syntax
  break across about 649,000 programs: every pinned source, the first
  revision's generators, generated `lambda` contexts, real programs mutated
  to use `lambda`, and seeded random token fuzz.
- Revision 1, prepared as NUC 58 against
  `62f695c4e5477cd3664973b571031af24198a1a8` (proposal blob
  `39988d51d3e84275d06d1dc02bde8ff194573dbf`), was rejected because its
  lambda scan took over [NUC 45](nuc-0045.md)'s juxtaposed `assert:`
  statement: `lambda = 1`, `x = lambda assert: x, 1`, `x` returns `1` at the
  accepted revision but raised `SyntaxError("Unexpected ','")`, and 258 of
  49,040 generated accepted programs failed. This revision returns `1` and

- The required Rust improvement pass made `is_type_declaration_at` check a

- Human SemVer review is still needed: `Token::ThinArrow` is a new variant of
