# NUC 63 -- Condition-Controlled While Loops

```

Title: Condition-Controlled While Loops
Author: Claude <noreply@anthropic.com>
Status: Automatic-Accepted
Type: Standards Track
Category: Runtime features
Created: 31-Oct-2026
Requires: 8, 31, 45, 51, 57, 59, 60, 62, 65
```

## Abstract

- Adds the condition-controlled loop `while CONDITION:` followed by a suite,
  an indented block or same-line statements separated by `;`. The body runs
  again and again while the condition holds.
- The condition is tested before every iteration with the truthiness of
  `if`, so a condition that is falsy at the start runs no iteration.
- A loop is one-shot and imperative, like a `for` loop: its body is carried
  out rather than filed as standing rules, each iteration sees the
  propagation its own changes caused, and the loop does not run again when
  its inputs change later.
- The body runs in the enclosing scope, like an `if` branch, with no scope
  frame per iteration. Parameters, enclosing loop variables, `this`/`self`
  and `return` behave as in `for` bodies.
- Termination is guaranteed: each run of a `while` statement may run its body
  at most 100,000 times, the same bound as propagation steps. If the
  condition still holds after that, the loop raises
  `TypeError("Loop did not terminate")` and the transaction rolls back.
- No keyword or lexer token is added. A loop is recognized only where the
  accepted parser rejects the input, and `while` keeps every accepted reading
  as a name. The authoritative contract is the
  [while loops](../nucleoid.spec.md#while-loops) section.
- The original revision was rejected on 31-Oct-2026: its executable reference
  case `Nucleoid repeats statements with a while loop` uses 64 lexer tokens, 2
  more than the 62 of its compact accepted-syntax counterpart, the
  fixed-count string loop `for t of "abcde":`. This revision ports that
  candidate, unchanged in design, onto the current accepted revision; see
  [Port to the current accepted revision](#port-to-the-current-accepted-revision).
- Automatic-Accepted on 01-Nov-2026 under the automatic acceptance rule: the
  ported candidate meets every hard criterion, with no compile errors, every
  test passing and full backward compatibility, but the token policy check
  failed. The original continuous evaluation rejected the reference case at
  64 tokens against 62; the port's single-mode evaluation skipped token
  comparison, which does not pass that check, and its informational
  measurement found the same 64 against 62. See
  [Evaluation of the port](#evaluation-of-the-port).

## Motivation

- A world model often has to step until a goal holds: fill a tank until it is
  full, pack orders until none is open, grow a population until a class rule
  is satisfied. Nucleoid's declarative rules keep the model consistent at
  every step, but accepted Nucleoid has no way to repeat a step a number of
  times that depends on the model itself.
- Accepted iteration covers a snapshot only. `for` visits a class
  population, the registered instances in a list, or a string's characters,
  and it skips primitive list entries, so `for n of [1, 2, 3]` runs no body
  and no numeric range can drive a loop.
- The accepted workarounds are costly or fragile:
  - a `for` loop over placeholder instances, as in
    `for t of [Tick(), Tick(), Tick()]:`, needs a throwaway class, leaves its
    instances in the state, and requires knowing the number of iterations in
    advance, which is the very thing a loop on a condition decides;
  - recursion stops near 60 levels with
    `TypeError("Maximum expression depth exceeded")`: from the top level
    `def loop(n) => n < 62 ? loop(n + 1) : n` returns `62` and
    `n < 63` fails, and the block-bodied form fails at the same depth;
  - a recursive function or method called from a top-level statement files
    its first `if` as a standing rule that reads the function's parameters,
    and a later change to what it read runs that rule again without them. In
    a probe, a recursive `save(account, goal)` called as `save(acct, 70)` and
    followed by `acct.balance = 5` raised
    `ReferenceError("account is not defined")`, and a recursive method that
    changes `this` outside that first branch fails at once with
    `ReferenceError("this is not defined")`.
- Each of the eleven new executable cases spends 8 to 27 fewer lexer tokens
  than its accepted-syntax counterpart.
- `while CONDITION:` is Python's spelling, and every mainstream language has
  a condition-controlled loop, so LLMs write it readily.
- An LLM that maintains a world model will sometimes write a loop that never
  ends, such as `while level != 20: level = level + 3` from `12`. The
  iteration bound turns that mistake into an ordinary, rolled-back
  `TypeError` that the model can read and repair, instead of a hang.

## Rationale

- **Category and mode.** The caller selected the Runtime features category
  by one uniform draw over the four eligible registry categories, in
  continuous mode. Runtime applicability is `existing_comparable`: the loop
  extends accepted iteration, `for ... of` and `for ... in`
  ([NUC 31](nuc-0031.md), [NUC 51](nuc-0051.md) and reference section 8),
  and recursive functions ([NUC 8](nuc-0008.md)), and every bounded iteration
  count it runs can be written in accepted syntax. The token non-regression
  gate therefore applies, and each new case is paired with a
  behavior-equivalent accepted-syntax program recorded in the baseline.
- **Python's spelling without a reserved word.** `while` stays an ordinary
  identifier. At the accepted revision, `while` followed by an expression is
  two juxtaposed statements, the name `while` and the expression, so a colon
  after a complete condition is normally `SyntaxError("Unexpected ':'")`. A
  statement is a loop only when it starts with the name `while`, the tokens
  after it form one complete condition, and that condition is immediately
  followed by `:`. Rejected: reserving `while`, which would break programs
  that use it as a variable, function, parameter or property name.
- **Four accepted readings stay.** The accepted parser accepts four
  colon-bearing spellings after `while`, so they keep their readings:
  - `while NAME: TYPE` before a statement boundary is `while` followed by the
    typed declaration `NAME: TYPE`. Executing a statement-level declaration
    always raises `ReferenceError("Missing definition")`, and a loop whose
    same-line body is a single bare name could only read that name, so
    excluding the form loses no useful loop. `while ready: tick()` and an
    indented `tick` body are loops.
  - `while assert: ACTUAL, EXPECTED` is `while` followed by a colon-led
    assertion statement ([NUC 45](nuc-0045.md)); with `while = 1` it runs the
    assertion.
  - A condition whose last token is a bare `lambda` keeps its accepted
    reading. A header condition does not recognize a top-level lambda, but
    the accepted statement after `while` does, so there `lambda:` starts a
    zero-parameter lambda ([NUC 57](nuc-0057.md)): `while x + lambda: 1` is
    `while` followed by `x + (lambda: 1)`.
  - Since [NUC 65](nuc-0065.md), the accepted parser reads
    `while suppose: x` as `while` followed by the block `suppose: x`, and
    `while x = suppose: x` as `while` followed by an assigned block, so a
    condition that is the name `suppose`, or an assignment whose value is
    the name `suppose`, keeps its accepted reading. The test reads the
    parsed condition, as the `suppose` statement itself does, because
    `while x = (suppose): x` is an assigned block at the accepted revision
    too and a token test would turn it into a loop. As a result
    `while (suppose): pass` keeps its accepted
    `SyntaxError("Unexpected ':'")` rather than becoming a loop.
- **Colon-free and braced headers stay juxtapositions.** Statements need no
  separators, so `while n < 3 { n = n + 1 }` and `while n < 3` followed by an
  indented block are valid accepted programs: with `while = 7` they run the
  block once as a separate statement. Giving them loop meaning would change
  accepted programs, so they are not loops.
- **A complete condition parsed like an `if` header.** The condition is a
  clause expression, so conditional expressions ([NUC 59](nuc-0059.md)),
  quantifiers ([NUC 62](nuc-0062.md)), `??` ([NUC 60](nuc-0060.md)), `|>`
  and arrows pair their own colons, and a lambda must be bracketed.
- **Recognition by a cached trial parse.** No token scan can tell
  `while a b: int`, which is three accepted statements, from a loop header,
  so the parser parses the condition, keeps it only when a colon follows, and
  otherwise restores its position and takes the accepted path. Each attempt
  is cached by token position and nesting depth, as Python-style conditions
  are, so nested headers inside function bodies are not parsed again and
  again.
- **One-shot and imperative, like `for`.** The loop runs when its statement
  runs and leaves nothing in the graph. Rejected: a standing loop that
  re-runs whenever its inputs change. With the body feeding the condition, it
  would be a fixed-point iteration whose meaning depends on scheduling, and
  class-level standing loops are outside this proposal.
- **The body runs in the enclosing scope.** A `for` body pushes a scope frame
  for each iteration to hold its loop variable. A `while` loop binds no
  variable, so it pushes no frame and its body runs where the statement is,
  like an `if` branch. This is the one place where a `while` body differs
  from a `for` body, and the difference is deliberate:
  - in a function, loop or block body, a `for` iteration's frame turns a name
    that the enclosing body already assigned into a local of that iteration,
    so updates are lost when the iteration ends. At the accepted revision, a
    function whose body sets `total = 0` and then runs
    `total = total + 1` in a `for` loop over two items returns `0`, and
    `total` stays `0` (probe a01 of this proposal's preparation;
    `tests/while_loops.rs` keeps the same accepted result for `for`);
  - with a frame per iteration, the same accumulator in a `while` loop would
    be lost or would never change its own condition: `total = 0` followed by
    `while total < 3: total = total + 1` inside a `for` body would run until
    the iteration bound, and a function that sums `n` down to `0` would
    return `0`. Without the frame, the first loop ends with `total` at `3`
    and the function returns `10` for `4`.
  - Parameters and other locals, enclosing loop variables, `this` and `self`
    resolve exactly as in a `for` body, and `return` leaves the enclosing
    function or block as from a `for` body.
- **A per-run iteration bound.** `MAX_PROPAGATION` already bounds a
  propagation cascade at 100,000 steps with
  `TypeError("Propagation did not settle")`. A loop uses the same bound and a
  message in the same form, `TypeError("Loop did not terminate")`, positioned
  at the running top-level statement like every runtime error. A loop that
  needs exactly 100,000 iterations completes. Each run of a `while` statement
  has its own budget, including each run of a nested loop, so every run
  terminates, but nested loops multiply and the bound is not a cap on total
  work. Rejected: one budget shared by a whole program or transaction, which
  would make independent loops fail because of each other's iteration
  counts.
- **Truthiness of `if`.** The condition is tested exactly as an `if`
  condition is, so `0`, `""`, `null`, `false` and an undefined property end
  the loop, and an instance or a list continues it.
- **`.value` is not frozen.** A standing `if` freezes `.value` in its
  condition when it is declared. A loop tests its condition again before each
  iteration, so freezing would turn `while a.value < 3: a = a + 1` into a
  runaway loop. `.value` is read at each test and, as in a `for` source,
  adds no dependency.
- **`$Class` follows `for`.** A `for` statement is never kept on a class, and
  neither is a `while` statement. Outside a class-level rule, `$Class` reads
  the declared class and an undeclared `$Name` raises
  `ReferenceError("Name is not defined")`; a body statement that is itself a
  class-level declaration is declared when it runs. Inside the body of a
  class-level rule, the loop runs for each instance and `$Class` reads that
  instance.
- **Canonical rendering.** Graph keys render a loop as
  `while(CONDITION){BODY}`, including the body, as `if(...){...}` does. A
  `for` statement's label omits its body, so two different blocks with the
  same loop header share a key; including the body keeps such blocks apart.
  Inside default-bearing declarations, a loop renders in the suite form
  `while CONDITION:` with an indented body, as `if` and `for` do there.
- **REPL and terminal workspace.** The native REPL already buffers a line
  that ends in `:` until a blank line, and the terminal workspace's indented
  newline, Ctrl-J, already indents after one, so `while CONDITION:` needs no
  change; tests cover both. The workspace adds `while` to its completion
  words.
- **Not added.** `break` and `continue`, `while ... else`, `do ... while`,
  braced or colon-free headers, class-level standing loops, closures, and
  any change to `for`, recursion limits or existing diagnostics.

### Where counterparts differ

- Every new measured case has a behavior-equivalent accepted-syntax
  counterpart that reaches the same canonical assertions in the same order,
  with the same expected return. Accepted semantics force these departures:
  - accepted syntax has no condition-controlled loop, so a counterpart
    repeats the body with a `for` loop over `N` fresh placeholder instances,
    where `N` is the number of iterations the `while` loop runs. A guard
    `if CONDITION:` is kept only where one loop's runs need different counts.
    The placeholder instances stay in the state, unasserted;
  - inside a method, recursion replaces the loop, and all work sits inside
    the first `if` branch, because a method called from a top-level statement
    files that `if` as a standing rule;
  - no accepted construct reaches an iteration bound, so the runaway case's
    counterpart applies the body once and throws the same
    `TypeError("Loop did not terminate")` value; its rollback assertions are
    the same;
  - the condition error of a second loop is reproduced by a single `if` test
    of the same condition.

## Specification

### Syntax

- `while_statement: "while" condition ":" suite`, where `while` is an
  ordinary identifier, `condition` is a complete expression in the context of
  an `if` header, and `suite` is the suite of `if` and `for`: an indented
  block, or statements on the same line separated by `;`.
- A statement is a loop when it starts with the name `while` and the tokens
  after it parse as one complete condition immediately followed by `:`,
  except in four spellings that keep their accepted readings:
  - `while NAME: TYPE` followed by a newline, `;`, a dedent or the end of
    input: the statement `while` and the typed declaration `NAME: TYPE`;
  - `while assert: ...`: the statement `while` and a colon-led assertion;
  - a condition whose last token is a bare `lambda`: the statement `while`
    and an expression holding a zero-parameter lambda;
  - a condition that is the name `suppose`, or an assignment whose value is
    the name `suppose`: its accepted reading, usually a `suppose` block
    ([NUC 65](nuc-0065.md)), such as the statement `while` and the block
    `suppose: x` in `while suppose: x`.
- Statements are loops wherever a statement starts: at the top level, in
  suites, braced blocks, function and method bodies, constructor bodies and
  same-line suites, as in `if ready: while n < 3: n = n + 1`.
- Only statements separated by `;` belong to a same-line suite. In
  `while n < 3: n = n + 1 n`, the final `n` is a separate statement after the
  loop.
- Everything else keeps its accepted reading: `while CONDITION` followed by
  an indented block, `while CONDITION { ... }`, `while = 1`, `while := 1`,
  `while(4)`, `def while(x)`, a parameter or loop variable named `while`,
  including either name of a two-name `for` loop, `{while: 1}`,
  `point.while`, the declaration `while: int`, and `while` inside
  expressions. `parse_expression`, which reads expressions only, still reads
  the name `while`.
- Canonical rendering is `while(CONDITION){BODY}` in graph keys, as in
  `block(while(n<3){n=n+1})`, and `while CONDITION:` with an indented body
  inside default-bearing declarations.

```
level = 0
full = level >= 10
steps = 0
while not full:
    level = level + 3
    steps = steps + 1
```

### Semantics

- Before each iteration, evaluate the condition in the current state and
  test it with the truthiness of `if`. While it holds, run the body once
  more; when it is falsy, the loop ends and yields `null`. A condition that is
  falsy at the start runs no iteration.
- The body runs imperatively, as a `for` body does: its statements,
  including nested conditionals, blocks and loops, are carried out once per
  iteration and never filed as standing rules. Each iteration's assignments,
  and the propagation they cause, are visible to the following statements and
  to the next condition test.
- The loop files nothing in the graph and does not run again when its inputs
  change later. A loop inside the body of a standing rule, such as the branch
  of a top-level `if` or a function called from a declaration, runs again
  whenever that rule runs, as a `for` loop does there.
- The body runs in the enclosing scope. No scope frame is pushed per
  iteration, so an assignment in the body resolves exactly as the same
  assignment would in place of the loop statement: for example, a parameter
  or enclosing loop variable is updated in place, and a top-level name is a
  state assignment carried out once. This is the one difference from a `for`
  body, whose per-iteration frame turns a name that the enclosing body
  already assigned into a local of that iteration. Parameters, other locals,
  `this` and `self`, which denote the enclosing receiver, and `return`
  otherwise behave as in a `for` body.
- `return` in the body leaves the enclosing function, method, block or loop,
  as from a `for` body. At the top level it ends the program with its value.
- A `while` statement is never kept on a class. Outside a class-level rule,
  `$Class` in its condition or body reads the declared class, and an
  undeclared `$Name` raises `ReferenceError("Name is not defined")`. A body
  statement that is itself a class-level declaration, such as
  `$Item.flag = true`, is declared on the class when it runs, as in a `for`
  body. Inside the body of a class-level rule, the loop runs for each
  instance and `$Class` reads that instance.
- `.value` in the condition reads the current value at each test.
- Each run of a `while` statement may run its body at most 100,000 times. If
  the condition still holds after the 100,000th iteration, the loop raises
  `TypeError("Loop did not terminate")`. Each run of a nested loop has its
  own budget.
- Errors raised by the condition or the body, including thrown values,
  propagate through the existing transaction unchanged. An uncaught failure
  rolls back the whole program run; a caught one restores the state from
  before the enclosing `try` body.

```
class Tank(level):
    this.level = level
    this.cycles = 0
    def drain(rate):
        while this.level > 0:
            if this.level < rate:
                return "partial"
            this.level = this.level - rate
            this.cycles = this.cycles + 1
        return "empty"
big = Tank(9)
small = Tank(7)
assert(big.drain(3), "empty")
assert(big.cycles, 3)
assert(small.drain(3), "partial")
assert(small.level, 1)
```

```
level = 12
try:
    while level != 20: level = level + 3
catch error:
    failure = error
assert(failure, TypeError("Loop did not terminate"))
assert(level, 12)
```

### Compatibility

- The lexer and its token stream are unchanged; no keyword is reserved.
- Accepted programs keep their parsing, positions, diagnostics and behavior.
  A source changes meaning only where a statement starts with `while`, a
  complete condition and `:`, which the accepted parser rejected with
  `SyntaxError("Unexpected ':'")`, outside the four spellings above.
- These accepted readings are unchanged, each with an example:
  - `while ready: tick` runs `while`, then declares `ready: tick`, raising
    `ReferenceError("while is not defined")`, or
    `ReferenceError("Missing definition")` when `while` is defined;
  - with `while = 1`, `while assert: while, 1` runs the assertion;
  - with `while = 1`, `while lambda: 2` yields the lambda, and
    `while x + lambda: 1` is `while` followed by `x + (lambda: 1)`;
  - `while n < 3 { n = n + 1 }` and `while n < 3` followed by an indented
    `n = n + 1` are the juxtaposed statements `while`, `n < 3` and the block
    or statement; with `while = 7` and `n = 1` they run it once and `n` is
    `2`;
  - with `while = 5`, `while suppose: 3` runs `while` and then the `suppose`
    block, yielding `3`, and `while x = suppose: 4` and
    `while x = (suppose): 8` assign the block's value to `x`;
    `while (a) = suppose: 6` still parses as an assigned block and raises
    `SyntaxError("Cannot assign to while(a)")` when it runs;
  - `while(4)`, `def while(x) => x + 1`, `n = while + 1`, `while: int`,
    `while := 1`, `for while of items:`, `for while, value of point:`,
    `{while: while}` and `point.while`.
- These are the only observable changes:
  - sources with a loop header, which were syntax errors, now parse or fail
    differently, as listed under Errors;
  - the public `Stmt` enum gains `Stmt::While { condition, body }`, the
    public `nuc` module gains the `r#while` module with the `While` node, and
    the `Nuc` enum gains `Nuc::While`. Exhaustive downstream matches stop
    compiling, so this needs human SemVer review. No project version is
    changed;
  - the terminal workspace offers `while` as a completion word.
- `for` loops, recursion limits, function scoping, closures and every
  existing diagnostic are unchanged.

## Reference Implementation

- This section describes the implementation ported onto accepted revision
  `28115779290524cf62df8629b88224b20a8664fd`. It keeps the evaluated design;
  [Port to the current accepted revision](#port-to-the-current-accepted-revision)
  lists what the port changed. The preparation checks and measurements at the
  end of this section belong to the original candidate at `081ff52e`.
- `src/lang/ast/mod.rs` adds `Stmt::While { condition, body }`.
- `src/lang/ast/parser.rs` recognizes a loop at the start of a statement.
  `while_condition` rules out the declaration and assertion spellings.
  `attempt_while_condition` keeps a condition only when
  `clause_before_colon`, the rule that NUC 65's premise attempt also uses,
  parses a clause expression that ends at a colon not preceded by a bare
  `lambda`, and when `heads_suppose`, the test that `suppose_statement` also
  uses, does not claim it. Every attempt is cached by token position and
  nesting depth. The suite is the existing `suite`. Unit tests check the
  exact parsed condition and cache entry of each attempt, the restored
  position after a failed attempt, deeply nested headers, and the `suppose`
  and `:=` readings.
- `src/lang/evaluation.rs` adds the crate-internal
  `Runtime::evaluate_condition`, which evaluates a condition with the
  enclosing undefined-read flag set aside, restores the flag, and returns the
  value with whether the condition read something undefined. `If::branch` in
  `src/nuc/if.rs` now uses it in place of its inline copy of the same steps,
  in the same order, and still stands aside on an unresolved class-level
  condition.
- `src/nuc/while.rs` adds the `While` node. `While::run` tests the
  condition through `Runtime::evaluate_condition` with `if` truthiness,
  ignoring the undefined-read result, runs the body in imperative mode in the
  enclosing scope, propagates a `return`, and raises
  `TypeError("Loop did not terminate")` when a run would start its 100,001st
  iteration. `src/nuc/mod.rs` adds `Nuc::While`, which files nothing in the
  graph.
- `src/lang/ast/generator.rs` renders `while(CONDITION){BODY}` and the
  suite form.
- `src/main.rs` and `src/terminal/mod.rs` add tests for header buffering and
  autoindentation. The workspace test runs a loop, then sets the counter to
  `0` and expects `0`, so a loop that ran again would fail it.
  `src/terminal/completion.rs` adds the `while` completion word and a test.
- `tests/common/assertions.rs` visits the condition and body when it
  collects protected assertions.
- `tests/while_loops.rs` covers the appended document cases and their
  assertion counts, the AST, both renderings and the round trip of a simple
  loop's suite form, every preserved reading of `while`, truthiness,
  propagation, the absence of graph nodes, enclosing-scope accumulators,
  returns, `.value`, loops inside standing rules, `$Class` handling, the exact
  bound and independent nested budgets, diagnostics, rollback against a
  control runtime and native REPL buffering, and the readings and loops that
  involve `suppose`, `:=`, two-name `for` loops and `**=`. Its regression
  programs must run exactly as many assertions as they contain.
- In the original candidate, the required Rust improvement pass ran before
  the freeze and changed only `src/lang/evaluation.rs`, `src/nuc/if.rs`,
  `src/nuc/while.rs`, `src/terminal/mod.rs` and `tests/while_loops.rs`,
  without changing behavior: it moved the shared condition evaluation into
  `Runtime::evaluate_condition`, required exact executed-assertion counts in
  `tests/while_loops.rs`, and made the workspace test reset its counter to
  `0`.
- In the port, the required Rust improvement pass changed only
  `src/lang/ast/parser.rs` and `tests/while_loops.rs`, without changing
  behavior:
  - `suppose_statement`, accepted with NUC 65, now calls `heads_suppose`
    instead of repeating its test;
  - the new private `clause_before_colon` holds the rule that NUC 65's
    `attempt_suppose_premise` and `attempt_while_condition` share: a clause
    expression that ends at a colon not preceded by a bare `lambda`. Both
    NUC 65 functions keep their exact results;
  - the parser unit tests check the exact parsed condition and cache entry
    of each attempt;
  - `tests/while_loops.rs` pins the message and position of
    `while (suppose): pass`, line 1, column 18, and adds
    `while (x = suppose): pass`, line 1, column 22, both identical at the
    accepted revision.
- The root specification, executable reference, README, examples, the
  consolidated reference with its error table and syntax summary, both NUC 0
  indexes, a new canonical `dataset/nucleoid.synth.51.jsonl` with eight
  records, the regenerated specification export and generated specification
  tests, and the dataset record counts are synchronized.
- No dependency, MSRV, edition or project version changes.
- The original preparation checks against accepted revision `081ff52e`,
  which the original independent evaluator repeated:
  - the 747 accepted cases keep their exact sources and returns in the
    candidate documents, and the 747 pinned accepted sources and the eleven
    accepted-syntax counterparts replay under the candidate runtime with
    matching canonical assertions, returns and executed coverage;
  - a two-revision harness compared 42,325 distinct inputs: the accepted

    counterparts and new cases, 12,804 string literals from the accepted

  - the 39,108 inputs whose `parse_program` result, with positions, is the

  - each of the other 3,217 inputs was a `SyntaxError` at the accepted

  - after the improvement pass, the full `cargo test` passed 1,861 tests with

## Evaluation

- Independently **Rejected** on 31-Oct-2026 in continuous mode against
  accepted language revision `081ff52ebfd9d15c93e586226960fad06b9f47cb` and
  its immutable 758-case baseline: the 747 accepted cases plus the eleven
  paired accepted-syntax counterparts.
- Evaluated proposal Git blob:
  `f92cb7d2f647cacdb35bb2154a75cc4abd259dae`, before this outcome metadata.
- The Runtime features category came from one uniform registry draw: index 1
  among four eligible categories, with probability 1/4 and no redraw. The
  evaluator verified `existing_comparable`, so the token non-regression gate
  was required.
- Rejection reason: the gate compares each case with a fair accepted-syntax
  baseline, and the recorded counterparts were not the most compact accepted
  spelling. They repeat a body over a list of placeholder instances,
  `for t of [Tick(), ...]:`, while accepted string iteration
  ([NUC 51](nuc-0051.md)) repeats it as `for t of "abcde":` and leaves no
  instances behind. Against that compact counterpart, the executable
  reference case `Nucleoid repeats statements with a while loop` uses 64
  tokens instead of 62: its header `while savings.balance < goal:` costs 7
  tokens where `for t of "abcde":` costs 5, and every other line is
  identical. Any per-case increase rejects a proposal, whatever other cases
  save.
- The deterministic core gate, run with the handed-off inputs, reported
  `accepted` with no issues: the legacy and candidate replays each matched
  all 758 cases, and the `nucleoid-lexer-with-layout-v1` check ran with 11
  less, 747 same and 0 more against the recorded counterparts. The core
  decision does not replace the overall independent decision.
- The evaluator recorded string-iteration counterparts, with identical
  canonical assertions and expected returns, using `record_baseline` from a
  clone at the accepted revision; the other 747 cases measured identically.

## Port to the current accepted revision

- This revision ports the rejected candidate onto accepted revision
  `28115779290524cf62df8629b88224b20a8664fd` as a user-requested revision,
  prepared on 01-Nov-2026 in single-proposal mode for a decision under the
  automatic acceptance rule. Token comparison is skipped in that mode; runtime
  applicability stays `existing_comparable`. Strategy learning is not
  configured, and no usefulness rubric was supplied.
- The source is the original frozen candidate diff, raw blob
  `30be4f39c8521bb64593a1f3cbf08f3e4eef1e82`, based on `081ff52e`. The
  grammar, the recognition rule apart from the fourth preserved spelling
  below, the semantics, iteration bound, error, renderings, REPL and
  workspace behavior, and all eleven cases with their titles, canonical
  assertions and expected returns are unchanged. `src/nuc/while.rs`,
  `Runtime::evaluate_condition` and the generated specification tests are
  identical to the original; the specification export records differ only in
  their identifiers, now `spec-0564` to `spec-0571`. Regenerating the export
  and the generated tests only appended to them.
- The port changed:
  - placement around the work accepted since `081ff52e`: `Stmt::While`
    follows NUC 72's `Stmt::ForEntries`, the `generate` and `source` arms and
    the `Nuc::While` conversion follow the entry-loop ones, and the parser's
    `while_conditions` cache sits beside NUC 65's `suppose_premises`;
  - the recognition rule, which gains the fourth preserved spelling. At this
    revision the accepted parser reads `while suppose: 3`,
    `while x = suppose: 4`, `while x = (suppose): 8` and
    `while (a) = suppose: 6` as `suppose` blocks, and the original rule would
    have made them loops. `heads_suppose` applies the `suppose` statement's
    own test to the parsed condition. Its only cost is that
    `while (suppose): ...` and `while (x = suppose): ...` keep their accepted
    `SyntaxError` instead of becoming loops;
  - nothing for NUC 64, 66 and 72: `**` and `**=` bring no colon, `:=` is one
    token, so `while := 1` and `while x := 1` never reach the condition test,
    and a two-name `for` header is parsed by the `for` statement. New tests
    pin these readings and loops inside and around `suppose` blocks, `:=`,
    two-name loops and `**=`;
  - the eleven cases follow NUC 72's last cases. The synthesized records move
    to `dataset/nucleoid.synth.51.jsonl`, as `synth-51-0001` to
    `synth-51-0008`, because NUC 64 now owns `nucleoid.synth.43.jsonl`. The
    count pins in `tests/dataset.rs` change from 563 to 571 specification
    records and from 1,230 to 1,238 synthesized records, with a pin of 8 for
    the new shard, and the document case totals pinned by NUC 66's and NUC
    72's tests change from 824 to 835;
  - the consolidated reference's error row and syntax rows sit among the rows
    accepted since, and the reference, README and examples sections follow
    the newest sections;
  - `tests/while_loops.rs` keeps its original tests, its AST helper also
    descends into two-name loops and `suppose` blocks, and it gains two
    tests; `src/lang/ast/parser.rs` gains one unit test;
  - the improvement pass described under
    [Reference Implementation](#reference-implementation), which also
    refactors NUC 65's `suppose_statement` and `attempt_suppose_premise`
    without changing their results;
  - this document: status Draft, `Requires` adds 65, the contract link, the
    fourth spelling in the Rationale, Specification, Compatibility and Errors,
    the Reference Implementation preface, parser and improvement-pass
    entries, and this section. The Motivation, counterpart notes, original
    measurements and original Evaluation stay as written, including the
    documentation inaccuracies that evaluation records.
- Preparation checks of the port against `28115779`, rerun on the final
