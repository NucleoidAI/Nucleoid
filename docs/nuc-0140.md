# NUC 140 -- Match Statements

```

Status: Rejected
Type: Standards Track

Created: 24-Nov-2026
Requires: 7, 8, 9
```

## Abstract

- A `match` statement compares one subject with the values of its `case`
  clauses, in order, and runs the suite of the first case that holds a
  value equal to the subject. An optional final `else:` clause runs when no
  case does:

  ```
  match light.state:
      case "red":
          light.next = "green"
      case "yellow", "flashing":
          light.next = "red"
      else:
          light.next = "yellow"
  ```

- The statement is the `if`/`elif` chain that tests `(SUBJECT) == (VALUE)`
  for each value, with `||` between the values of one case and `else:` as
  its last branch, except that the subject is written and evaluated once.
  Like an `if` statement it is a standing rule, so it runs again when what
  it read changes, and with a `$Class` subject it is a class-level
  conditional for every instance. It yields what that chain yields: the
  value of the last statement of the suite that ran, and `null` when no
  suite runs.
- At the accepted revision a program that writes `match SUBJECT:` before an
  indented block fails to parse, with `SyntaxError("Unexpected ':'")` at
  the header's colon for subjects such as `v`, `light.state` and
  `$Order.status`, and only such programs change. `match` and `case` stay
  ordinary names: variables, functions, parameters, properties and keys
  named `match` or `case`, and typed declarations such as `match: int`,
  keep their readings.
- One public syntax-tree variant, `Stmt::Match`, with the public case struct
  `MatchCase`, one statement node, `Nuc::Match` with its module
  `nuc::r#match`, and one graph node kind, `NodeKind::Match`, are added; no
  keyword, lexer token or error type is.
- Each of the seven new executable cases uses 7 to 12 fewer lexer tokens
  than its recorded counterpart, the most compact fair accepted spelling
  found, and fewer than every other fair spelling measured. Hand-evaluated
  substitutions, which read the cases' inputs and are excluded, come within
  2 to 6 tokens of the cases, and one of them, which stacks a hard-coded
  stop value with two coincidence tests, uses one token fewer than the
  method case, as [Counterparts](#counterparts) records.
- The authoritative contract is
  [Match statements](../nucleoid.spec.md#match-statements).
- Independent evaluation rejected this revision because it is not backward
  compatible, so the prototype is not part of the accepted language and the
  specification section, cases, grammar, records and exports it proposed
  were not integrated. A statement that starts with the name `match`,
  followed by `every`, `any` or `all` and then the word `repeat` or
  `suppose` before a colon and an indented block, such as
  `match every repeat:` over an indented body and `until n >= 3`, parses at
  the accepted revision as the name `match` beside the quantifier and a
  repeat-until loop or `suppose` block, and can run cleanly there; the
  candidate reads it as a match statement and raises a `SyntaxError`. The
  claim above that only programs that failed to parse change is therefore
  false; the outcome's Evaluation section at the end of this document
  records the evidence.

## Motivation

- A world model often dispatches on a state: the phase of a traffic light,
  the status of an order, the color of a cell. Accepted programs spell each
  dispatch as an `if`/`elif` chain that repeats the subject in every
  condition, and a case that shares a suite between several values repeats
  it once more per value with `||`:

  ```
  if $Order.status == "paid" || $Order.status == "packed":
      $Order.stage = "warehouse"
  elif $Order.status == "shipped":
      $Order.stage = "transit"
  elif $Order.status == "delivered" || $Order.status == "returned":
      $Order.stage = "closed"
  ```

- That chain takes 59 lexer tokens, against 47 for the same rule as a
  `match` statement over `$Order.status` with the cases
  `"paid", "packed"`, `"shipped"` and `"delivered", "returned"`. Written as
  compactly as each allows, with every suite on its line and NUC 97's
  membership test `$Order.status in ["paid", "packed"]` for the shared
  values, three separate `if` statements take 46 tokens and the match
  statement 38.
- An object lookup,
  `$Order.stage = {paid: "warehouse", packed: "warehouse", ...}[$Order.status]`,
  takes 30, because every suite of this rule picks one value of one
  property. It is not the same rule: it assigns `null` to an order whose
  status it does not list, where the chain and the match statement leave
  the stage as it was, and it cannot run a statement. The match statement
  pays off when suites do more than pick one value, as the cases of this
  proposal do.
- The statement pays off as the subject grows and as cases share suites. A
  light whose two cases and `else` set two properties each takes 66 tokens
  as an indented chain and 62 as a match statement, or 56 and 53 with
  same-line suites and `in`. With a bare variable as the subject and two
  cases before `else:`, the chain is shorter: 32 tokens against 34
  indented, and 24 against 25 on single lines.
- Writing the subject once also states the intent, one decision over one
  value, and keeps the cases from drifting apart when the subject changes.
- The form follows Python's `match` and `case`, Swift's `switch` with
  `case A, B:`, and Kotlin's `when` with comma-separated values and `else`.
  As in Swift and Kotlin, and unlike C and JavaScript, no case falls
  through into the next.

## Rationale

- **Category and mode.** The caller drew Runtime features with one
  tool-backed uniform draw over the five categories that NUC 1's registry
  marks eligible for automatic selection: index 1, with probability 1/5, at
  15:21:59 on 24-Nov-2026, and no redraw. This is a continuous cycle, so the
  token non-regression gate is required.
- **Runtime applicability: `existing_comparable`.** Every match statement
  has an accepted spelling: the `if`/`elif` chain that tests
  `SUBJECT == VALUE`, with `||` or a membership test between the values of
  one case. Every case of this proposal is paired with such an
  accepted-syntax program, which the accepted runtime runs with every
  assertion, as [Counterparts](#counterparts) records.
- **Selection.** Within the category the caller chose one bounded
  enhancement, a multi-way `match` statement, which no NUC proposes under
  `match`, `switch`, `when` or `case`. It set aside four candidates whose
  current behavior accepted tests pin: lambdas that read an enclosing
  function's or lambda's parameters, index-value loops over lists,
  a `try`/`catch`/`else` clause and deleting an instance that still has
  properties; and `super.method()`, which gives `undefined`, an accepted
  result.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero, because no rubric was frozen. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Python's words, without reserved words.** `match` opens the statement
  and `case` opens each clause, as in Python, and both stay ordinary
  identifiers. `else` is the existing keyword, so the final clause reads as
  the last branch of the chain it replaces. Rejected:
  - `switch` and `when`, which read less naturally with `else:` and with the
    comma-separated values of one case;
  - reserving `match` or `case`, which would break the programs that use
    them as variables, functions, parameters, properties, object keys and
    classes;
  - `default:` or `case _:` as the final clause: `_` is an ordinary name,
    so `case _:` compares the subject with the value of `_`, and `else`
    already means "otherwise".
- **A header that the accepted parser cannot read.** At the accepted
  revision `match SUBJECT:` before an indented block parses as the name
  `match` followed by a statement that starts with the subject, and every
  such statement fails at the colon, apart from the few that a name and a
  colon begin. So the header is `match`, one expression read as an `if`
  header reads its condition, and a colon that ends the line before an
  indented block, and it is not recognized where the accepted parser reads
  those tokens:
  - `match NAME: TYPE` is the name `match` beside the typed declaration of
    `NAME`, and `match: TYPE` the typed declaration of `match`: the colon
    must follow a subject and end its line;
  - `match assert: ...`, `match repeat:` with its `until` line and
    `match suppose:`, also as `match x = suppose:`, are the name `match`
    beside the statement that the colon belongs to, so the subject is never
    a colon statement, the word `repeat` before its colon or a `suppose`
    head, as the header of a `while` loop is never a `suppose` head;
  - a header with more on its line after the colon, such as
    `match v: case 1: r = 1`, stays a `SyntaxError`: a match statement
    always opens an indented block, which is also what lets the REPL and
    the workspace treat it as a colon header.
- **A block of clauses.** The block holds one or more `case` clauses and at
  most one `else:` clause, which stands last; blank lines and comment lines,
  which add no tokens, may stand between clauses. A block without a case is
  an error rather than a statement that does nothing, as a suite without a
  statement is. Rejected: other statements between clauses, which would
  read as part of no case, and `else` before or between cases.
- **Values are expressions, compared with `==`.** A case value is any
  expression that an `if` condition can be, so `case limit + 1:` and
  `case Color.RED:` work. The values of one case are separated by commas,
  with no trailing comma, so the colon after the last value is the case's.
  The comparison is `==`, the loose equality of conditions, because the
  statement is a spelling of the chain over `SUBJECT == VALUE`: `1` equals
  `"1"`, lists compare by their items, `null` equals `undefined`, and NaN
  equals nothing. The subject and every value are compared as whole
  expressions, so the chain parenthesizes them: `case 0 || 1:` compares the
  subject with the value of `0 || 1`, and `case 1 === 1:` with `true`,
  where an unparenthesized `s == 1 === 1` would read as `(s == 1) === 1`.
  Rejected: `===`, which would make the statement a different decision from
  its chain, and patterns, guards, destructuring and class tests, which are
  new semantics with a syntax of their own.
- **The subject once, the values in order, the first match.** Each run
  evaluates the subject once, before any value, and then the values in
  source order, left to right within a case, until one equals the subject.
  The suite of that case runs, and no later value is evaluated, as the
  short-circuit of `||` and the order of `elif` give in the chain. No suite
  falls through into the next, so `break` is not needed. Evaluating the
  subject once is the first of three differences from the chain, which
  evaluates the subject again for every test it reaches; the two differ
  when that evaluation has an effect. The second is `.value`, which the
  statement freezes in its subject and every value, as `If::before` freezes
  an `if` condition, where the chain freezes only its first condition. The
  third is the key, below.
- **Suites as `if` writes them.** Each clause's suite is the explicit-colon
  suite of `if`: an indented block, or statements on the same line
  separated by `;`, a braced block among them. Colon-free clause headers are
  not added, so a case or an `else` without its colon is an error, as a
  same-line suite without its colon is.
- **A standing rule, as `if` is.** The statement runs through the machinery
  of `nuc::If`, shared rather than copied: freezing `.value`, the
  class-level declaration, tracking, filing and the stand-aside rule. At the
  top level it is a standing rule that runs again when its subject, a value
  it evaluated or a read of the suite that ran changes; its suites run in
  the surrounding scope, so their assignments are state assignments, and a
  run in which no suite runs leaves earlier assignments as they are. With
  `$Class` reads it is a class-level rule for every instance, which stands
  aside for an instance while it reads something undefined. When it names
  several classes, the first in source order decides which class holds the
  rule, as for its chain: the subject, then each case's values followed by
  its suite, then the `else` suite. Inside functions, methods, loops, `try`,
  blocks and `suppose` it runs as `if` runs there. Rejected: a one-shot
  statement, which would make the statement a different decision from its
  chain as soon as anything it read changed.
- **A key of its own.** A match statement is filed under
  `match(SUBJECT)`, as an `if` statement is under `if(CONDITION)`, so a
  second match statement over the same subject replaces the first, as a
  second `if` with the same condition does at the accepted revision, and a
  match statement and an `if` statement never replace each other, even
  where the subject and the condition render alike. The key names the
  subject alone, as an `if` statement's key names its condition and not its
  suites, so two match statements over one subject replace each other even
  when their cases differ, where two chains over that subject whose first
  conditions differ have different keys and both stand. This is the third
  difference from the chain. Rejected: a key that also renders the cases,
  which would keep an edited match statement standing beside the one it
  replaces, both assigning the same targets. No other node is keyed
  `match(...)`: variables and functions are keyed by their names,
  properties by `<object>.<property>`, classes by `$<name>`, and
  conditionals and blocks by `if(...)` and `block(...)`.
- **A syntax-tree variant of its own.** The statement builds the new public
  variant `Stmt::Match`, which holds the subject, the cases, as a public
  struct with the values and the suite of each, and the optional `else`
  suite. Rejected: a desugaring into `Stmt::If`, which would evaluate the
  subject once per test, give the statement the key of an `if` and render
  it as an `if`; and a flag on `Stmt::If`, which would change the tree of
  every accepted conditional and break the exhaustive destructuring of that
  variant, among them the accepted arms of `tests/common/assertions.rs`. As
  for [NUC 115](nuc-0115.md)'s `Stmt::Repeat`, [NUC 119](nuc-0119.md)'s
  `Stmt::TryFinally` and [NUC 126](nuc-0126.md)'s `Stmt::RepeatUntil`, that
  exhaustive match gains only the arm that visits the new variant's subject,
  each case's values and suite, and the `else` suite, and no other existing
  test changes beyond count-only pins.
- **A statement node and a node kind of their own.** `Nuc::convert` maps
  every `Stmt` to the public `Nuc` enum, so the statement also needs
  `Nuc::Match`, whose node keeps its fields private. It is filed as the new
  `NodeKind::Match`, shown as `match` by `--graph`, rather than as an `if`.
  The three enums are exhaustive, so the variants break exhaustive
  downstream matches; this needs human SemVer review, and no version number
  changes.
- **Canonical rendering.** Graph and block keys render the statement as
  `match(SUBJECT){case(VALUES){SUITE}...else{SUITE}}`, in the style of
  `if(CONDITION){...}else{...}`. Inside default-bearing declarations it
  renders in its suite form, `match SUBJECT:` with its clauses indented
  below it.
- **REPL and terminal workspace.** The native REPL already buffers a line
  that ends in `:` until a blank line, so `match SUBJECT:` waits for its
  block, and so do the case headers. The workspace already indents after a
  line that ends in `:`, and its completion words gain `match` and `case`,
  as they gained `finally`.
- **The exporter needs no change.** The specification exporter's statement
  splitter starts a new exported statement at every unindented line, and
  the clauses of a match statement are indented under its header, so a
  top-level match statement is exported in one piece.
- **Requires.** [NUC 7](nuc-0007.md), whose standing conditionals, branch
  scopes and class-level conditionals the statement follows;
  [NUC 8](nuc-0008.md), whose functions a `return` in a suite leaves; and
  [NUC 9](nuc-0009.md), whose transactions roll back a failed update with
  everything it caused.
- **Not added.** Colon-free headers, same-line match statements, a wildcard,
  guards, patterns, destructuring, class tests, fallthrough, `break`,
  `switch`, `when`, `default`, a reserved word, and any change to `if`,
  `elif`, `else`, `==`, the loops, functions or existing diagnostics.

### Counterparts

- Every new case is compared with the most compact fair accepted-syntax
  program found that reaches the same canonical assertions in the same order
  and the same expected return. Each differs from its case only where the
  match statement is written; every other line is the case's own. They are
  recorded in `extra-baselines.json`, which the accepted runtime executed
  with every assertion run.
- The search measured these families wherever they apply, each run on the
  accepted runtime with the same harness rule as the suites, every
  assertion executed and passing:
  - the `if`/`elif` chain with indented suites, and the same chain with
    same-line suites, which must spell `else if`: at the accepted revision a
    direct alternative such as `elif COND:` qualifies only before an
    indented suite, so `elif COND: statement` is a `SyntaxError`;
  - separate `if` statements, which need no `else` keyword where the case
    has no `else` clause and its values never meet two cases;
  - `||` between the values of one case against NUC 97's membership test
    `SUBJECT in [A, B]`, which is shorter for two or more values;
  - a local or top-level alias of the subject, such as `s = printer.state`;
  - object lookups, `{red: "green", ...}[SUBJECT]`, with `?? DEFAULT`, with
    `?? TARGET` to keep a value, with `?? (() => { throw ... })()` or a
    helper function for a throwing `else`, and inside an `if` whose
    membership test lists every value, so that an unlisted value runs
    nothing;
  - conditional expressions, with the same keep, default and throw forms;
  - early returns in the method, with and without a membership guard;
  - second properties derived from the first, such as
    `$Cell.cost = {background: 1, wall: 9, goal: 0}[$Cell.kind]` or
    `$Valve.noisy = $Valve.mode == "throttle"`;
  - truthiness and parity tests in place of `== 0` and value lists.
- The first phase's search ran 82 programs on the accepted runtime, 77 of
  them passing, and each case uses fewer tokens than every passing fair
  spelling it found. The excluded spellings below were measured on their
  own.
- `in` is fair here because it compares as `==` does for the values of
  these cases: every subject and every value of one case are strings, or
  numbers in the cell case. At the accepted revision `in` is strict for
  other kinds: `1 in ["1"]` and `0 in [false]` are false where `1 == "1"`
  and `0 == false` are true, and an object is in a list of an equal object,
  where `==` compares objects by identity.
- **Lookups and conditional expressions cannot keep a value in a
  class-level rule.** A class-level lookup or conditional expression that
  reads its own target, such as
  `$Order.stage = {paid: "warehouse"}[$Order.status] ?? $Order.stage`,
  raises `TypeError("Circular Dependency")` at the accepted revision, while
  the same spelling at the top level keeps the value. So in the four
  class-level cases without `else`, an instance whose subject moves to a
  value that no case names, the cell's color 7, the order's `lost`, the
  light's `dark` and the ticket's `spam`, keeps what an earlier case
  assigned only in statement spellings. Every plain lookup fails there; a
  lookup inside an `if` whose membership test lists every value passes and
  is longer than the statement.
- **Two properties per case.** Every case sets two properties in most of
  its suites, or runs a `return` or a `throw`, so a lookup or a conditional
  expression per property, or a second property derived from the first, is
  longer than the statement.
- **A pre-existing limit of the accepted revision shapes the method case.**
  After a method or function whose body reads `this` or a parameter's
  property in a top-level `if` condition or suite has run, a later write to
  what it read raises `ReferenceError("this is not defined")` or
  `ReferenceError("<parameter> is not defined")` at the writing statement:
  `class P(zone):` with `this.zone = zone` and
  `def cost():` whose body is `if this.zone == "a": return 1` and
  `return 2`, then `x = P("a")`, `first = x.cost()` and `x.zone = "b"`,
  raises `ReferenceError("this is not defined")` at line 8, also when the
  method reads `this.zone` through a local or the call is kept with `:=`,
  and the same happens for a function's parameter. A conditional expression
  in place of the `if` does not raise it. The method case therefore writes
  its parcel's weight before the first call and uses a fresh parcel for each
  later call. A match statement runs as `if` runs there, so it shares the
  limit, which this proposal leaves unchanged and no case depends on.
- **Excluded** spellings are hand-evaluated substitutions: each holds only
  because of the values that one run happens to reach, so it is a different
  rule from the case's. They are reported with their token counts, each run
  on the accepted runtime with every assertion passing, and never recorded:
  - **Hard-coded stop values**, a guard on the one unlisted value a case
    uses, such as `if $Order.status != "lost":` before one lookup, or
    `if this.zone == "moon": throw "NO ROUTE"` before one conditional
    expression.
  - **Coincidence tests**, a test that agrees with a case's value list on
    the values the statement lists and the run reaches, but not in general:
    a string's length, one of its letters, a piece it holds, its order
    against a letter, or a number's remainder or threshold. For
    `["local", "pickup"]`, `zone[2] == "c"` holds for both, and for
    `[1, 5]`, `$Cell.color % 4 == 1` does. The search tried, for every test
    of each recorded spelling, and of the chain for the rollback case, whose
    recorded lookup has no test: `==` and `!=` against a listed value; `<`,
    `>`, `<=` and `>=` against every letter and listed value; `.length`
    against 0 to 12 under each comparison; `[0]` to `[4]` against every
    letter; `includes`, `startsWith` and `endsWith` of each one- and
    two-letter piece; and for numbers every comparison with -1 to 10,
    `% 2` to `% 9` against each remainder, truthiness and `!`. It kept a
    test when it agreed with the original on every listed value that reaches
    it: all of them for separate `if` statements, and in a chain the values
    of its own and later cases and the value that must reach `else` or the
    `throw`. It then ran the combinations on the accepted runtime in order
    of tokens, and the cheapest passing one is reported.
  - **A stacked spelling**, a hard-coded stop value whose expression also
    uses coincidence tests. The method case's
    `if this.zone == "moon": throw "NO ROUTE"` spelling, with
    `this.zone[2] == "c"` for `["local", "pickup"]` and
    `this.zone.length == 7` for `["express", "courier"]` in its conditional
    expression, takes 189 tokens, one fewer than the case; with only the
    length test it ties the case at 190, and with only the letter test it
    takes 191. No other case has one: their hard-coded spellings are
    lookups, whose keys no test can shorten, behind guards that no

  - Spellings that drop listed values the run never reaches, such as the

## Specification

- The normative contract is
  [Match statements](../nucleoid.spec.md#match-statements).

### Syntax

- `match_statement: "match" condition ":" NEWLINE INDENT case_clause+
  else_clause? DEDENT`, where `case_clause: "case" condition ("," condition)*
  ":" suite` and `else_clause: "else" ":" suite`. `match` and `case` are
  ordinary identifiers, `condition` is a complete expression in the context
  of an `if` header, and `suite` is the explicit-colon suite of `if`: an
  indented block, or statements on the same line separated by `;`, a braced
  block among them.
- A statement is a match statement when it starts with the name `match`,
  followed by one condition and the colon after it, which ends its line, and
  the next line opens an indented block, unless one of these accepted
  readings holds, which keep their parse:
  - the token after `match` starts a colon statement: `match NAME: TYPE`,
    the name `match` beside the typed declaration of `NAME`, or
    `match assert: ...`;
  - the token after `match` is a colon: `match: TYPE`, the typed declaration
    of `match`, or a `SyntaxError`;
  - the subject is the word `repeat` before its colon, which is the name
    `match` beside a repeat-until loop, or a `suppose` head, `suppose` or an
    assignment whose value is `suppose`, which is the name `match` beside a
    `suppose` block.
- Clauses start lines at the block's indentation, and blank lines and
  comment lines may stand between them, with LF or CRLF line ends alike. A
  clause may also follow the same-line suite of the clause before it, as
  `else` follows a same-line `if` suite at the accepted revision:
  `case 1: r = 1 case 2: r = 2` holds two cases, where
  `case 1: r = 1; case 2: r = 2` reads `case` as the first suite's second
  statement and fails. Every clause before the last is a `case` clause; the
  `else` clause, when there is one, is the last. `elif` is the same keyword
  as `else`, so `elif:` opens the `else` clause too.
- Match statements stand wherever a statement starts: at the top level, in
  suites, in braced blocks spread over lines, in function, method and
  constructor bodies and in loop bodies, and they nest, each with its own
  block.

```
printer = {state: "idle", pages: 4}
match printer.state:
    case "idle": printer.light = "green"; printer.eta = 0
    case "printing": printer.light = "blue"; printer.eta = printer.pages * 5
    case "jammed", "empty": printer.light = "red"; printer.eta = 60
    else: printer.fault = true
assert([printer.light, printer.eta], ["green", 0])
printer.state = "printing"
assert([printer.light, printer.eta], ["blue", 20])
printer.pages = 6
assert(printer.eta, 30)
printer.state = "empty"
assert([printer.light, printer.eta], ["red", 60])
printer.state = "offline"
assert([printer.light, printer.eta, printer.fault], ["red", 60, true])
```

- Each change of the state runs the statement again, and so does a change
  of the pages that the printing case read. The `offline` state runs the
  `else` suite, which sets only the fault, so the light and the estimate
  keep what the `empty` case set.

### Evaluation

- Each run evaluates the subject once, before any value.
- The case values are evaluated in source order, left to right within a
  case, and only until one equals the subject under `==`. The suite of that
  case runs, and no later value is evaluated.
- When no value equals the subject, the `else` suite runs, or nothing does.
- No suite falls through into the next.
- A match statement yields what its `if`/`elif` chain yields, wherever it
  stands: the value of the last statement of the suite that ran, the `else`
  suite included, and `null` when no suite runs. As the last statement of a
  program, a REPL entry, a braced block or a suite it gives that value, so
  `v = 2`, then a match over `v` with `case 1: "one"` and `case 2: "two"`,
  gives `"two"`. Where the accepted revision discards the value of an `if`
  statement, both spellings give the same: a class-level rule yields
  `null`, a loop yields `null`, a function or method without a `return`
  returns `null`, and a `suppose` block that ends with either statement has
  no value. A `return` in a suite leaves the enclosing function, method or
  block, as from an `if` suite.
- `==` is the loose equality of conditions: `1` equals `"1"`, `[1]` equals
  `[1]`, `null` equals `undefined`, and `0` equals `false`; NaN equals
  nothing, so a NaN subject runs the `else` suite. The subject and each
  value are compared whole, as if parenthesized: `case 0 || 1:` compares
  with `1`, and `case 1 === 1:` with `true`.
- So the statement behaves as its `if`/`elif` chain over
  `(SUBJECT) == (VALUE)`, except in three ways:
  - the match statement evaluates its subject once per run, and the chain
    once for every test it reaches, so they differ where the subject has an
    effect, such as a call that counts its calls;
  - the match statement freezes `.value` in every test, the chain only in
    its first, as [Standing rules](#standing-rules) states;
  - the match statement's key names its subject alone, so two match
    statements over one subject replace each other even when their cases
    differ, where two chains over that subject whose first conditions
    differ have different keys and both stand.

### Standing rules

- At the top level a match statement is a standing rule. It runs again
  whenever its subject, a case value it evaluated or a read of the suite that
  ran changes, and its suites run in the surrounding scope, so their
  assignments are state assignments. A run in which no suite runs leaves
  earlier assignments as they are.
- A match statement whose subject, values or suites read `$Class` is a
  class-level rule for every instance, created before or after it. While it
  reads something undefined for an instance, it stands aside for that
  instance, as a class-level `if` does.
- When it names several classes, the first `$Class` in source order
  decides which class holds the rule, as for its chain: the subject, then
  each case's values followed by its suite, then the `else` suite. With
  `class A(v)`, `class B(w)`, `a = A(1)`, `b = B(2)` and `x = 1`, a match
  over `x` whose `case 1:` sets `$B.r = "one"` and whose `case $A.v:` sets
  `r = 2` is a rule on `B`, so `[b.r, a.r]` gives `["one", null]`, as its
  chain `if x == 1: $B.r = "one"` with `else if x == $A.v: r = 2` gives at
  the accepted revision.
- Inside functions, methods, loops, `try`, blocks and `suppose` it runs as
  an `if` statement runs there.
- `.value` in the subject or in a case value is the value when the
  statement is declared, as in an `if` condition; a class-level rule reads
  the current value for every instance.
- An `if`/`elif` chain freezes only its first condition: each `elif` is a
  nested `if` that reads `.value` when it runs. At the accepted revision
  `limit = 1`, `x = 0`, then `if x == limit.value:` with `r = "first"` and
  `elif x == limit.value + 1:` with `s = x`, then `limit = 5`, `x = 6` and
  `s`, gives `6`, where a frozen `limit.value + 1` would leave `s`
  undefined. So a match statement and its chain differ where `.value`
  stands in the subject or in the value of a later case: the match
  statement compares with the declared value in every test.
- A second match statement over the same subject replaces the first, as a
  second `if` statement with the same condition does, even when their cases
  differ: `x = 1`, a match over `x` whose `case 1:` sets `a = "first"`, a
  second one whose `case 2:` sets `b = "second"`, then `a = "reset-a"`,
  `x = 2` and `x = 1`, gives `["reset-a", "second"]` for `[a, b]`, where
  the separate `if x == 1:` and `if x == 2:` statements give
  `["first", "second"]`. A match statement and an `if` statement never
  replace each other.
- Errors raised by the subject, a case value or a suite, and thrown values,
  propagate through the existing transaction unchanged: an uncaught failure
  rolls back the whole program run, and a caught one restores the state from
  before the enclosing `try` body.

```
class Valve(mode, size):
    this.mode = mode
    this.size = size
match $Valve.mode:
    case "open", "purge": $Valve.flow = $Valve.size * 10
    case "throttle": $Valve.flow = $Valve.size + 2; $Valve.noisy = true
    case "shut", "locked": $Valve.flow = 0
    else: throw "UNKNOWN MODE"
main = Valve("open", 3)
assert(main.flow, 30)
try:
    main.mode = "half"
catch error:
    assert(error, "UNKNOWN MODE")
assert([main.mode, main.flow], ["open", 30])
try:
    Valve("half", 1)
catch error:
    assert([error, Valve.length], ["UNKNOWN MODE", 1])
main.mode = "throttle"
assert([main.flow, main.noisy], [5, true])
```

- An unknown mode throws from the class-level rule, so the update that set
  it rolls back, and so does the construction of a valve with that mode.

### Rendering

- The graph files a match statement under `match(SUBJECT)`, followed by
  `@` and the instance for an instance's copy of a class-level rule, as a
  node of kind `match`, and `why` names it the same way.
- Graph and block keys render the statement as
  `match(SUBJECT){case(VALUES){SUITE}...else{SUITE}}`, with the values of a
  case separated by commas, as `if(CONDITION){...}else{...}` renders an
  `if` statement.
- Inside default-bearing declarations the statement renders in its suite
  form: `match SUBJECT:`, each clause indented below it and each suite
  below its clause, the values of a case separated by commas without
  spaces. As the accepted suite forms of `while` and `repeat COUNT:` do, it
  writes the subject without parentheses, so the rendering of
  `match (assert):` or `match (repeat):` reads back as the name `match`
  beside another statement, as that of `while (assert):` does at the
  accepted revision. These renderings name and display nodes; nothing
  parses them again.

### Interactive use

- The native REPL already buffers a line that ends in `:` until a blank
  line, so `match SUBJECT:` waits for its block, which must come before
  that blank line: a blank line between two clauses submits the statement
  that far, as it submits any indented block, and a case header after it
  starts a new entry.
- Each entry prints what the statement yields. A session that enters
  `v = 2`, a match over `v` whose cases set `r` to `"one"` and `"two"`,
  `r`, `v = 1`, `r`, a match over `v` with `case 1:` and `else:` suites
  setting `s`, `s`, a match over `v` with only `case 5: "five"`, `v = 5` and
  `s` prints `2`, `two`, `two`, `1`, `one`, `a`, `a`, `null`, `5` and `a`
  with `--plain`, the same values in JSON with `--plain --json` and with
  `--json`, with LF and CRLF line ends alike and nothing on standard error.
  The third match statement replaces the second, so `v = 5` leaves `s` as
  it was.
- The terminal workspace indents after the header and after each case
  header, keeps `match v: int` unindented after it, and completes `match`
  and `case`.
