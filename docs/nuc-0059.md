# NUC 59 -- Conditional Expressions

```
NUC: 59
Title: Conditional Expressions
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Runtime features
Created: 29-Oct-2026
Requires: 8, 43, 44, 45, 49, 57
```

## Abstract

- Add conditional expressions in two optional spellings that build one new
  expression node: `condition ? consequent : alternate`, as in JavaScript,
  TypeScript, Java, C# and C/C++, and `consequent if condition else alternate`,
  as in Python.
- The condition is evaluated once with the existing truthiness of `if`, `not`,
  `&&` and `||`; then exactly one branch is evaluated and yields the result.
  The unselected branch is not evaluated.
- Dependencies, null and undefined handling, `.value` snapshots, class-level
  rule validation and transactions use the existing `&&`/`||` and assignment
  machinery; no new evaluation rule is added.
- Both spellings share one right-associative precedence level above
  assignment and below the reasoning pipeline `|>`, and render canonically as
  `(condition?consequent:alternate)`.
- Accepted syntax keeps its parsing and behavior. `?` was an unexpected
  character, and the Python spelling applies only when `else` immediately
  follows its condition, so an `if` statement written after an expression on
  the same line keeps its accepted reading.
- The authoritative contract is
  [Conditional expressions](../nucleoid.spec.md#conditional-expressions).

## Motivation

- Nucleoid's goal is a superset of Python, JavaScript/TypeScript, Kotlin, Go,
  Rust, Java, C# and C/C++. At the accepted revision, `x = c ? 1 : 2` raises
  `SyntaxError("Unexpected character '?'")` and `x = 1 if ready else 2` raises
  `SyntaxError("Expected ':' but found keyword 'else'")`, although both are
  the most common way those languages choose a value.
- Choosing a value from a condition currently needs a statement-level
  `if`/`else` rule per target, or an `&&`/`||` idiom. Both have pitfalls that
  the accepted runtime shows:
  - `c && a || b` yields `b` whenever `a` is falsy:
    `shipping = total > 100 && 0 || 5` is always `5`.
  - Statement-level conditionals are keyed by their condition text, so two
    `if total > 100:` rules, one assigning `shipping` and one assigning `size`,
    replace each other: after `total = 120`, `size` is `"large"` but
    `shipping` stays `5`.
  - An `if` statement in a function body is filed as a standing conditional.
    With `limit = 2`, a `def size(value):` body of
    `if value > limit: return "big"` and `return "small"`, then `size(1)`
    and `limit = 0`, the conditional re-runs outside the call and raises
    `ReferenceError("value is not defined")` at line 7.
    `def size(value) => value > limit ? "big" : "small"` has no statement node.
  - Statements cannot appear inside callbacks, list and object literals,
    template interpolations, call arguments or subscripts.
- A conditional expression is one value-level choice that belongs to the
  declaration containing it and stays live through the existing dependency
  graph, which is what LLM-written programs in either family expect.

## Rationale

- **Category and applicability.** The caller selected Runtime features by one
  uniform draw over the registry's four eligible categories (index 1,
  probability 1/4, no redraw). A conditional expression adds a new
  expression-level control-flow evaluation: evaluate a condition once, then
  evaluate and yield exactly one branch. No existing expression represents it
  exactly, as `(c && a) || b` differs whenever `a` is falsy.
- Runtime applicability is `existing_comparable`. The feature extends the
  existing conditionals feature, standing statement-level `if`/`else` rules
  (NUC 7 and reference section 8), to expression position. Every new measured
  case has a behavior-equivalent accepted-syntax counterpart that reaches the
  same assertions with statement-level `if`/`elif`/`else` rules or, where a
  statement cannot express the value, `&&`/`||` selections with truthy
  consequents. The precedents are NUC 51, 54 and 55.
- **Where counterparts differ.** The comparison exposed four places where
  the statement form differs from the expression form. They are recorded,
  not changed:
  - statement conditionals with the same condition text replace each other,
    while a conditional expression belongs to its own declaration;
  - an `if` statement in a function body is filed as a standing rule;
  - a statement branch takes a `.value` snapshot when the branch runs, while
    an expression takes it in every operand when its declaration is stored,
    as for a skipped logical operand;
  - a class-level `if` statement stands aside while its condition reads
    something undefined, while a conditional expression treats that condition
    as false and selects the alternate, as `||` does.
- **One node, two spellings.** The public
  `Expr::Conditional { condition, consequent, alternate }` is evaluated like
  `Expr::Logical`: evaluate the condition, test it with `Value::truthy`, then
  evaluate only the selected operand. Rejected: lowering to existing nodes. `&&`/`||` mishandles falsy
  consequents, and a list-index encoding would allocate and change rendering.
- **Existing machinery.** Reads are recorded as they happen, so a standing
  declaration depends on the condition and the selected branch, and replaces
  obsolete dependencies when the branch changes. Static queries see every
  operand: class-rule reference validation, class-cycle detection, `.value`
  freezing and reasoning detection treat the unselected branch exactly like a
  skipped logical operand. Rejected: freezing only the selected branch,
  standing aside on undefined conditions, or validating only one branch, as
  each would invent a rule that `&&` and `||` do not have.
- **Precedence.** C, Java, JavaScript, C# and Python all place the
  conditional immediately above assignment. Placing it below `|>` keeps every
  existing operator's relative order and lets a reasoning pipeline be a
  condition or a branch without parentheses; the right side of `|>` is only a
  stage name, so `|>` can never absorb a `?`. Like F#'s `if ... else`, a
  pipeline after the alternate stays in the alternate.
- Both spellings share one right-associative level, so
  `a ? b : c ? d : e`, `a if b else c if d else e` and mixed chains group to
  the right. The consequent after `?` is a complete expression, as in
  JavaScript, C# and C++. The operand before `?` and both operands before
  `else` are pipeline-level, the counterpart of Python's disjunction, so an
  unparenthesized conditional or lambda is never a Python condition. Either
  alternate is conditional-level.
- **Who owns the colon.** The `?` consequent and the Python condition are
  parsed in the clause context that `if` headers use, so `lambda` stays an
  ordinary name where the conditional owns the following `:` or `else`,
  following [NUC 57](nuc-0057.md): `c ? lambda : d` reads the variable
  `lambda`. Parentheses select a lambda there.
- **Qualifying the Python spelling.** Statement loops accept a statement
  directly after another, so `x = 1 if ready:` followed by an indented suite
  is an assignment and then an `if` statement. An accepted `if` header must
  be followed by `:` or a real indented body, never by `else`, so a program in
  which the parsed condition is immediately followed by `else` was always a
  syntax error. Recognizing exactly that case is additive.
- The parser therefore parses one condition after `if` and commits only if
  `else` follows. Otherwise it restores its position, and the statement
  parser reads `if` with its original positions and diagnostics, including
  [NUC 49](nuc-0049.md) colon-free suites, [NUC 43](nuc-0043.md) direct
  alternatives, [NUC 34](nuc-0034.md) final `else`, `elif` aliasing and
  inline suites.
- An attempt depends only on its `if` token position and nesting depth, so
  its complete outcome, the condition and the position after `else` or
  failure, is memoized and reused when the same tokens are parsed again.
  Without this, nested attempts inside block bodies re-parse exponentially.
  During preparation, a failure-only memo still took about 2.9 seconds for 20
  nested levels near the nesting limit, while with the complete memo the
  robustness test's 160-level inputs check in about a quarter of a second.
  Rejected: a non-consuming token scan that commits at a
  top-level `else`, which would change diagnostics of already-invalid
  programs such as `x = 1 if a b else 2`. Also rejected: keys without the
  depth, which could misjudge attempts near the nesting limit.
- **Template interpolations.** The accepted parser ignores trailing tokens in
  an interpolation, so `` `${a if b else c}` `` renders `a`. The Python
  spelling stays unrecognized at an interpolation's top level, exactly as
  NUC 57 kept `lambda` a name there. The `?` spelling was a lexer error
  inside interpolations and is additive.
- **Lexing `?`.** One `Token::Question`. `??`, `?.` and Kotlin's `?:` are not
  added and remain errors. A `/` after `?` starts a regular expression, and
  `a?.5:1` reads `.5` as a number, as JavaScript does.
- **Canonical rendering.** `(condition?consequent:alternate)` uses the symbol
  form, as `and`, `or` and `not` render as `&&`, `||` and `!`. Rendering is a
  graph key that adds no precedence parentheses elsewhere, so the grouping
  keeps `(c?a:b)+1` and `(c?a:b+1)` distinct; `UnaryOp::Positional` already
  renders `(operand)`.
- **Header scanners.** [NUC 43](nuc-0043.md)'s non-consuming direct-alternative
  scan and the native REPL's colon-free header scan pair a top-level `?` with
  its `:`, so `else c ? a : b` followed by an indented suite qualifies and
  `if c ? a : b` buffers like any other colon-free header.
- **Not added.** `??`, `?.`, Elvis `?:`, Kotlin and Rust `if` expressions,
  statement-level changes and reserved words. As in Python, a conditional
  spanning lines needs parentheses.
- **Token policy.** In this continuous cycle, Runtime features with
  `existing_comparable` applicability require the token non-regression gate.
  All nine new measured cases were paired with accepted-syntax counterparts,
  executed by the accepted runtime and recorded through
  `NUC_PROPOSAL_EXTRA_BASELINES` before any candidate edit. No pre-existing
  case is rewritten; the independent evaluator measures the comparison.

## Specification

### Syntax

- `?` is a single lexer token, `Token::Question`, described as `'?'`. Text in
  strings, template literals outside interpolations, regular expressions and
  comments is unchanged.
- Expression levels, from loosest:
  - assignment, unchanged: `conditional`, optionally followed by `=` or a
    compound operator and a right-associative expression;
  - conditional: `pipeline ? expression : conditional`, or
    `pipeline if pipeline else conditional` when qualified, or `pipeline`;
  - pipeline and every tighter level, unchanged.
- The consequent after `?` and the Python condition parse in the clause
  context; the alternate continues in the enclosing context, so an object
  value's alternate still ends at NUC 44's next `name:` property.
- The Python spelling qualifies only when `if` directly follows a complete
  operand, outside a template interpolation's top level, and the condition is
  immediately followed by `else` or its existing lexical alias `elif`.
  Otherwise no token is consumed. Attempts are memoized by `if` position and
  nesting depth.
- Arrow and lambda bodies extend over a conditional, as in
  `x => x > 2 ? "big" : "small"` and
  `lambda x: "odd" if x % 2 else "even"`.

### Semantics

- Evaluate the condition once and test it with `Value::truthy`: null, an
  undefined property, `false`, `0`, NaN and the empty string are false;
  everything else, including empty lists and objects, is true.
- Evaluate only the selected branch; its value is the result. The unselected
  branch has no effects, raises nothing and adds no dependency.
- A standing variable, property or class-level rule depends on what its
  condition and selected branch read, re-evaluates when they change and
  switches branches when the condition changes.
- A stored declaration whose evaluation read a null binding or property,
  including in its condition, settles to `null`, as `x = flag || 2` does. A
  missing property read by the condition is false and stays subscribed; an
  undefined selected branch stores `null` until it is defined; a deleted
  variable read during its deletion's propagation defers to `null`.
- `.value` snapshots are taken in all three operands when a declaration is
  stored, so an unselected branch keeps its snapshot from that moment.
- A class-level rule validates names and `$Class` property cycles in all
  three operands when it is declared, and each instance evaluates only its
  selected branch.
- Errors raised by the condition or the selected branch propagate through the
  existing transaction; a failed standing re-evaluation rolls back the change
  that triggered it, keeping the earlier branch selection.

```
total = 80
member = false
shipping = 0 if total > 100 else 5
discount = member ? 10 : 0
grade = total >= 90 ? "A" : total >= 70 ? "B" : "C"
size = total > 100 ? "large" : "medium" if total > 50 else "small"
label = member || total > 100 ? "priority" : "standard"
charge = total + (member ? 0 : shipping)
assert(shipping, 5)
assert(grade, "B")
assert(size, "medium")
assert(charge, 85)
total = 120
assert(shipping, 0)
assert(grade, "A")
assert(size, "large")
assert(label, "priority")
assert(charge, 120)
```

```
log = []
def note(tag):
    log.push(tag)
    return tag
flag = true
other = 1
pick = flag ? note("yes") : note(other)
assert(log, ["yes"])
other = 2
assert(log, ["yes"])
flag = false
assert(pick, 2)
assert(log, ["yes", 2])
```

### Compatibility

- `x = 1 if ready:` with an indented suite, `z = 3 if lit: w = 4`,
  `if true: y = 1 else: y = 2`, `x = 1 y = 2`, colon-free NUC 49 headers,
  NUC 43 direct alternatives and NUC 34 final `else` keep their readings,
  statement positions and diagnostics.
- `` `${a if b else c}` `` keeps rendering `a`; `` `${(a if b else c)}` `` and
  `` `${b ? a : c}` `` select a value.
- Every accepted colon role is unchanged: `assert:` statements, typed
  declarations, lambda headers and their exclusions, object properties,
  slices and every statement header.
- The public `Token` and `Expr` enums gain the `Token::Question` and
  `Expr::Conditional` variants. Exhaustive downstream matches stop compiling,
  so this needs human SemVer review. No project version is changed.
- The public `parse_expression` still parses one leading expression and
  ignores what follows, but that expression may now be conditional:
  `parse_expression("a if b else c")` returns the conditional rather than
  `Identifier("a")`. This also needs human SemVer review.

```
ready = true
armed = true
lit = true
limit = 10
mode = "on" if ready else "off"
x = 1 if armed:
    y = 2
z = 3 if lit: w = 4
if limit > 5: a = 1 else: a = 2
b = 5 c = 6
note = "ready? yes"
pattern = /colou?r/
assert(mode, "on")
assert([x, y, z, w, a, b, c], [1, 2, 3, 4, 1, 5, 6])
assert(note, "ready? yes")
assert(pattern.test("color"), true)
ready = false
armed = false
assert(mode, "off")
assert([x, y, z, w, a], [1, 2, 3, 4, 1])
```

## Reference Implementation

- `src/lang/ast/lexer.rs` adds `Token::Question` and its `'?'` description.
- `src/lang/ast/mod.rs` adds `Expr::Conditional`, dispatches it to the
  operator evaluator and includes it in reasoning detection.
  `src/lang/ast/operator.rs` adds `evaluate_conditional`, the counterpart of
  `evaluate_logical`, and walks all three operands.
- `src/lang/ast/parser.rs` adds the conditional level between assignment and
  the pipeline, and the memoized, non-consuming Python-form qualification.
  It also adds the private `Interpolation` expression context, used for
  template interpolations, and pairs a top-level `?` with its `:` in the
  direct-alternative scan. A private `nested_expression_in` helper restores
  the enclosing context after every nested parse, including a failed
  Python-condition attempt, and `expression_in` uses it too.
- The extra precedence level costs host stack per nesting level.
  - On the debug Windows CLI, the stack needed for 64 nested parentheses rises
    from 1027 KiB at the accepted revision to 1154 KiB. The stack needed for
    the 160-level nested Python-condition input rises from 835 KiB to 899 KiB.
  - The debug CLI's 1 MiB main-thread stack already overflows on such nesting
    at the accepted revision, for example `tests/robustness.rs`'s 4096 nested
    parentheses after `amount += `.
  - Release builds report `SyntaxError("Expressions are nested too deeply")`,
    and the test suites' 2 MiB threads are unaffected. The nesting limit
    itself is unchanged.
- `src/lang/ast/generator.rs` renders `(condition?consequent:alternate)`.
  `src/expression.rs` visits all three operands for roots, class references,
  class-rule properties and call checks. `src/nuc/expression.rs` freezes
  `.value` in all three operands. `src/main.rs` pairs `?` with its `:` in the
  colon-free REPL header scan.
- `tests/conditional_expressions.rs` covers lowering, canonical rendering,
  precedence, every operand position, `lambda` naming, accepted adjacent
  statements, unchanged and changed diagnostics, interpolations, literal
  question marks, truthiness parity, laziness, the documented
  statement-versus-expression differences, class-rule validation,
  `parse_expression` and native REPL buffering.
- Lexer, parser and REPL unit tests cover the token, the qualification and
  its memo, the scanners and the contexts. `tests/robustness.rs` covers
  160-level nested Python conditions that do not qualify.
- `tests/common/assertions.rs` walks all three operands for protected
  assertions.
- Four existing development assertions used `?` as an invalid character:
  - `tests/diagnostics.rs` now places `^`, which still begins no token, at
    the same positions with the same message format, as at the accepted
    revision.
  - The two bare typed-header suites keep their `int?` sources with the new
    exact diagnostic and add `int^` rows that keep the original
    unexpected-character check.
- The root specification, executable reference, README, examples, the
  consolidated reference with its syntax summary, both NUC 0 indexes, a new
  canonical `dataset/nucleoid.synth.39.jsonl` and the regenerated normative
  exports are synchronized in the isolated candidate.
