## Abstract

- Add only the statement `TARGET ??:= EXPR`: when the current target value
  is Null or Undefined, perform one ordinary imperative value assignment;
  otherwise do nothing and never evaluate the right-hand expression.
- Keep the whole operation one-shot and isolated from dependency tracking,
  including its guard, target reads and called code. A skipped operation
  must not change the target's declaration, history or dependencies.
- Reuse the existing `??` and `:=` tokens without relaxing the accepted
  `??=` rejection or any other existing syntax, diagnostic or behavior.
- The caller's one uniform live-registry draw selected Runtime features.
  **Accepted:** the fresh independent evaluation and unchanged integrated
  candidate passed every hard criterion and policy check. The single
  caller-owned Rust-improvement pass is complete.

## Motivation

- A fallback action currently needs an explicit conditional, snapshot reads
  for its guard and a separate `:=`. Omitting those snapshot boundaries
  can accidentally turn the guard into a standing dependency.
- A distinct conditional value-assignment operation should preserve
  Nucleoid's law/action distinction: write a missing value once, rather
  than installing a coalescing law or replacing an already supplied value.
- Preserve false, zero, empty Strings and every other non-nullish value.
  A skipped right-hand side must not run effects, raise errors or record
  dependencies; a taken one keeps the ordinary `:=` semantics.
- The accepted runtime rejects `slot ??:= 7`. Existing proposals expressly
  leave out `??=` and protect its diagnostics, so this proposal does not
  repurpose that spelling.

## Rationale

- This is a core short-circuit assignment execution mode, not a
  cross-language alias. Keep the confirmed Runtime features category.
- A coalescing declaration, `target = target ?? fallback`, is a live law.
  An unconditional `target := target ?? fallback` still writes on a supplied
  value, replacing its standing declaration and dependencies. Neither models
  a no-op skip. A normal standing `if` can also subscribe to its guard.
- The new statement makes the check an isolated action and delegates a taken
  write to `:=`. It neither creates a standing guard nor changes what a taken
  value assignment stores.
- Existing accepted guarded `if` statements using `target.value == null`
  and `:=` are comparable for the two selected concrete programs. Their
  immutable accepted sources were executed and minimized before drafting;
  that does not make equality a general implementation of nullishness.

## Specification

- The only new form is the statement `TARGET ??:= EXPR`. The lexer emits its
  existing `??` and `:=` tokens, with ordinary inter-token whitespace or
  comments permitted. No token, reserved word or assignment expression is
  added. A logical newline still separates statements.
- At an expression-statement head only, the parser stops before the exact
  `??`/`:=` pair at that head's expression level. It validates the same path
  as `:=` and parses the ordinary assignment value. Parentheses may group a
  target; they do not enable assignments inside expressions. Public
  `parse_expression`, templates, arguments, defaults, headers and nested
  expression parsing retain their old readings.
- Resolve and read the target using ordinary lookup in the current scope.
  An unbound root name remains an error, not an implicit declaration.
  An ordinary missing object property may yield Undefined. Only the actual
  Null and Undefined value kinds take the write. False, both zero signs,
  empty text, NaN and all containers, references and callable values skip.
- On a skip, do not evaluate `EXPR`, file any declaration, change identity,
  append history or replace dependencies. In particular, a standing target
  relationship continues reacting to its existing inputs.
- On a take, evaluate `EXPR` exactly once through the existing `:=` action.
  Preserve its scope, effects, called-code and extra-argument behavior,
  target-resolution timing, named-constructor binding, instance context,
  null/undefined settlement, propagation and transactions. At the top level
  the target becomes a stated literal/fact; imperative bodies keep the same
  carry-out-without-filing behavior as `:=`.
- Isolate target resolution and guard reads as well as a taken RHS, including
  functions, methods, callbacks and structural subscriptions, from both the
  target and every enclosing tracking frame. An enclosing standing `if paid`
  depends on `paid`, not on this action's guard or fallback.
- Restore the enclosing null/undefined-read flags after the guard, even on
  errors. A null guard must not defer a constant fill. Do not disable null-read
  settlement inside the RHS: reading `nullable + 1` there stores what `:=`
  would store.
- Keep the existing path, parser and runtime depth limits, class-level
  boundaries, property-name restrictions and transaction implementation.
  This revision does not repair inherited multi-dependent rollback ordering
  or add a runtime-value nesting policy.
- A taken statement returns the existing action's value; a skipped statement
  is a no-op with the ordinary `pass` result. Canonical source rendering is
  `target??:=value`, distinct from both declarations and unconditional actions.
- The normative [root contract](../nucleoid.spec.md#nullish-value-assignment)
  and exactly two appended executable cases specify the measured behavior:
  `Nucleoid fills nullish values with one-shot assignments` in the spec and
  `Nucleoid keeps nullish assignment guards isolated` in the reference. Each
  retains its six supplied assertions, their order, and explicit return `1`.

## Errors

- Preserve all accepted syntax, pinned diagnostics and existing tests.
  In particular, keep the old `??=` spellings and scalar-default errors.
- Unsupported targets report `SyntaxError("Invalid value assignment target")`
  at the `??`, as `:=` validates its target at that operator. Existing path
  resource errors remain unchanged.
- Ordinary lookup, invalid-owner, read-only-version and forbidden `value`
  property errors remain in force, including on an otherwise skipped target.
  Class-level targets outside instance rules retain
  `TypeError("Cannot use ':=' on a class-level property")`.
- RHS and propagation errors use the existing transaction and error paths.
  The new form does not suppress errors from resolving its target. A skipped
  RHS cannot raise an error because it is not evaluated.
- Backward compatibility covers erroneous runtime inputs accepted by the old
  parser too. No old test, canonical assertion, expected return or pinned
  diagnostic is intentionally changed.

## Reference Implementation

- `Stmt::NullishValueAssign` represents the statement. The contextual
  expression-head boundary is tracked by expression nesting depth; ordinary
  coalescing is otherwise unchanged. The generator and assignment, root-read,
  class-reference, class-rule and assertion walkers handle the variant.
- The private `nuc::nullish_value_assign` converter uses the existing isolated
  tracking frame and `Nuc::value_assignment`. It prepares member targets using
  the ordinary path machinery, then checks the current value by enum kind.
  Identifier preparation is delayed until a take so a skip cannot record a
  scope assignment. A skipped conversion returns `Nuc::Pass`; a taken one
  returns the existing `ValueAssign`, with no new public runtime node.
- Share the existing property-name check without changing its old execution
  order. Restore guard flags before the existing action runs; its own isolated
  RHS evaluator and literal-storage machinery are unchanged.
- `docs/nucleoid.ebnf` adds the statement and its contextual/token-source
  contract, sharing the existing path and receiver rules. The reference,
  synthesized JSONL and generated normative exports stay synchronized.
- Adding a variant to the existing public, closed `Stmt` enum affects
  downstream exhaustive matches and requires human SemVer/API review.
  No project version, Cargo manifest, dependency or existing public path is
  changed.
