```

Type: Standards Track

Created: 15-Oct-2026
```

## Abstract

- Optionally place exactly one expression in a genuine indented body after an
  existing named definition's `=>`.
- Lower to the existing named `FunctionBody::Block` containing exactly
  `Stmt::Return(Some(expression))`, just like the accepted inline named arrow.
- Preserve every accepted header, inline arrow, colon suite, anonymous function,
  call, runtime behavior, canonical rendering and resource bound.

## Motivation

- A single return expression can keep its existing readable indentation without
  repeating the `return` keyword.
- Reuse existing named arrows and layout tokens rather than a new implicit
  last-statement-return rule or keyword.
- Implement only the caller-selected syntax improvement, retaining its single
  category draw `0`; do not redraw or combine a pending proposal.

## Rationale

- Separate body layout from the already accepted parameter/header grammar.
- Qualify the complete real-indent prefix without consuming layout; missing
  indentation must preserve the inline path's diagnostics and positions.
- Parse exactly one expression through unchanged `expression()` and then demand
  the closing body `Dedent`; do not speculate, catch/retry, rewind or clone ASTs.
- Keep explicit returns for multi-statement colon suites. A final expression in
  an ordinary suite still does not implicitly return.
- Leading braces in a named expression are objects, not the anonymous arrow's
  statement block. Returned anonymous functions keep their noncapturing scope.
- This distinct revision extends the earlier named-arrow first-expression
  layout restrictions; it does not revise the text of earlier NUCs or depend
  on a Draft NUC. The root specification is authoritative.

## Specification

### Grammar and lowering

- Normative detail is in
  [indented named arrow expressions](../nucleoid.spec.md#indented-named-arrow-expressions).
- Accept all existing named parameter spellings without reimplementing them:
  parenthesized empty/single/multiple/annotated/trailing-comma/multiline lists,
  bare untyped or typed single parameters, and bare untyped/mixed/fully typed
  multiple parameters. Preserve each name, annotation and position in the list.
- Preserve the existing required definition name, complete immediate bare-header
  guards and parenthesized fallback diagnostics. `def f =>` and `def f:` remain
  invalid; rejected bare-nullary syntax is not restored.
- After the existing named `Arrow`, require immediate `Newline` or `Indent`.
  Look ahead across only `Newline`/`Semicolon` tokens; the first other token
  must be a real `Indent`. Consume no layout unless both conditions qualify.
- On failed qualification, run the old inline expression path unchanged.
  In particular, do not reinterpret valid inline bodies or their following
  statements, and do not skip layout to recover a missing body.
- On success, consume the permitted layout and `Indent`, skip normal leading
  newline/semicolon body layout, parse unchanged `expression()` exactly once,
  skip normal trailing newline/semicolon layout, and require/consume `Dedent`.
- Lower exactly to the same named
  `FunctionBody::Block(vec![Stmt::Return(Some(expression))])` as a colon suite
  containing only `return expression`. Keep the complete expression AST, not
  just its value, and the existing generator spelling `def NAME`.
- An immediate semicolon after `=>` never qualifies, even before a later indent.
  Semicolon-only lines after the initial newline may precede the real indent or
  expression; trailing semicolons are permitted. `expression; other` inside
  the body is rejected, as is a second expression on another body line.
- Blank/comment-only lines create no indentation. Preserve existing CRLF,
  tab indentation, parentheses/brackets and multiline-expression layout.
- No new anonymous indented-arrow path, arbitrary statement suite, implicit
  last-statement return, token, keyword, public AST/runtime/generator/API,
  capture, type checking, dependency, MSRV or project-version change is added.

### Behavior and compatibility

- Argument order, missing/null/extra/unchecked arguments, local shadowing,
  assignment-expression returns, callable null deferral and non-callable errors
  retain their accepted behavior.
- Named methods, nested definitions and `init` use the same lowering; preserve
  receivers, `this`/`self`, explicit/bare `super`, adoption and object identity.
- Preserve live callable aliases, `.value` definition snapshots, redefinition,
  external state reads, reactive arguments, graph keys/dependencies, reasoning,
  transaction rollback and actual assertion execution.
- Preserve inherited noncapturing and parameter-dependent local/nested
  propagation failures; the new layout does not repair or swallow them.
- Keep all existing statement/expression nesting and operator/postfix limits.
  Flat parameter lists remain uncapped, including the tested 1,024 parameters.
- The native CLI buffers a lexical named header when its only arrow is the last
  significant token, including comments after it. It leaves parameter validation
  and the real-indent check to the parser on blank-line commit or stdin EOF.
- Inline named arrows, direct expressions, anonymous arrows and arrow text in
  strings, regexes, templates or comments retain their existing interaction.
  Source files use the same parser. Invalid input reports structured diagnostics,
  clears the input buffer and allows later recovery with prior state intact.
- Existing multiline parameter-list parsing remains available through complete
  source/file input; this revision does not add general interactive delimiter
  continuation for headers that were previously executed line by line.

## Errors

- All errors are the existing typed errors, with physical parser/lexer positions
  or the existing top-level runtime statement positions. No body error is caught,
  retried, relocated to a fabricated source or treated as a successful parse.
- A leftover body token raises
  `SyntaxError("Expected the end of a block but found TOKEN")`, where `TOKEN`
  is the unchanged lexer description. For exact `def f x =>\n    x\n    x + 1`,
  the message is `"Expected the end of a block but found identifier 'x'"`
  at line 3, column 5. `def f x =>\n    x; x + 1` gives that same message at
  line 2, column 8; `def f x =>\n    x 1` gives
  `"Expected the end of a block but found number 1"` at line 2, column 7.
- Exact `def f x =>\n    x\n        1` gives
  `SyntaxError("Expected the end of a block but found an indented block")`
  at line 3, column 9.
- Exact `def f x =>` keeps `SyntaxError("Unexpected end of input")` at line 1,
  column 11. A final newline, or exact `def f x =>\nx`, keeps
  `SyntaxError("Unexpected end of line")` at line 2, column 1.
- Exact `def f x =>;\n    x` keeps `SyntaxError("Unexpected ';'")` at line 1,
  column 11; a later indent cannot rescue a same-line semicolon.
- After exact `def f x =>` and a newline, four-space-indented `return x` gives
  `SyntaxError("Unexpected keyword 'return'")` at line 2, column 12; `(x +)`
  gives `SyntaxError("Unexpected ')'")` at line 2, column 10; `{ return x }`
  gives `SyntaxError("Expected a key but found keyword 'return'")` at line 2,
  column 14; `@` gives `SyntaxError("Unexpected character '@'")` at line 2,
  column 5. Other expression diagnostics use the unchanged expression parser.
- Exact `def f =>\n    1` keeps `SyntaxError("Expected '(' but found '=>'")`
  at line 1, column 7; `def f:\n    1` keeps
  `SyntaxError("Expected '(' but found ':'")` at line 1, column 6.
  Exact `def f left: int, right, =>\n    left` keeps
  `SyntaxError("Expected '(' but found identifier 'left'")` at line 1, column 7.
  Existing malformed parenthesized and unsupported bare prefixes are unchanged.
- Existing resource errors remain `SyntaxError("Statements are nested too deeply")`,
  `SyntaxError("Expressions are nested too deeply")`,
  `SyntaxError("Expression has too many operands")` and
  `SyntaxError("Expression has too many parts")`.
- Runtime errors are unchanged, including `ReferenceError("missing is not defined")`,
  uncaptured-name `ReferenceError("value is not defined")`, unbound-receiver
  `ReferenceError("this is not defined")`, and
  `TypeError("operation is not a function")` for a non-callable parameter.
  Existing caught values omit positions; rollback and later recovery are unchanged.
