# NUC 21 -- Reactive Numeric Clamping

```

Title: Reactive Numeric Clamping
Author: Copilot <223556219+Copilot@users.noreply.github.com>
Status: Accepted
Type: Standards Track
Category: Utility enhancement
Created: 14-Oct-2026
```

## Abstract

- Add static `Math.clamp(value, lower, upper)` as one bounded runtime capability.
- Define its numerical result as exactly the ordered composition
  `Math.min(Math.max(value, lower), upper)` after existing numeric coercion.
- Preserve the existing call path, dependencies, deferred reads, errors and
  transactions; add no grammar, public representation or callable-reference feature.

## Motivation

- Numeric readings, capacities and thresholds often need a value bounded by
  two live inputs without restating a nested pair of Math calls.
- Keep the value, lower bound and upper bound reactive through one static call.
- Provide one explicit numerical contract rather than introduce a separate
  bounds-validation model.

## Rationale

- Deliberately use ordered-composition semantics: reversed bounds yield the
  upper bound, and numeric `NaN` in any of the first three positions propagates.
- Reuse the accepted min/max folds, including their infinity seeds and
  signed-zero behavior, rather than silently substitute different extrema rules.
- Do not use Rust `f64::clamp`: its NaN/reversed-bound preconditions and panic
  behavior would violate this contract.
- Use the existing fixed-arity omission convention, numeric `NaN`, not an
  undefined property read or a new arity error.
- Ignore extra values numerically without suppressing argument evaluation,
  dependency reads or the existing any-`Undefined` gate.
- Preserve static namespace shadowing and unsupported Math method references.
- Require no pending proposal; existing Math behavior is established by
  `nucleoid.spec.md`, not by treating Draft NUC10 as Accepted.
- Leave aliases, closures, namespace redesign, parser changes, new types/errors,
  dependencies and inherited scope/resource limitations outside this revision.

## Specification

### Static numeric contract

- The authoritative [`Reactive numeric clamping` section](../nucleoid.spec.md#reactive-numeric-clamping)
  and its five executable entries define the candidate behavior.
- An unshadowed static `Math.clamp(...)` call uses the existing Math dispatcher.
- Convert the first three supplied values with the existing `Value::to_number`
  semantics; each omitted first/second/third position instead supplies numeric `NaN`.
- Numbers retain their values, literal `null` converts to zero, booleans to
  zero/one, trimmed strings and empty/singleton lists retain their numeric
  conversion, and dates contribute their millisecond value.
- Other nonnumeric values convert to numeric `NaN`; there is no new type constraint.
- Fold maximum over the converted value and lower bound using the existing
  negative-infinity seed and explicit NaN propagation.
- Fold minimum over that result and the converted upper bound using the existing
  positive-infinity seed and explicit NaN propagation.
- Reversed bounds therefore yield the upper bound unless NaN propagation applies;
  equal bounds, infinities and signed zeros match those same ordered folds.
- Do not validate, swap or reject bounds; NaN and reversed-bound results are
  defined handling, not swallowed errors.
- Extra supplied values do not enter the numerical folds.

### Evaluation, reactivity and compatibility

- Evaluate every supplied argument expression left to right before dispatch,
  including expressions whose extra values are numerically ignored.
- Keep the existing Math gate over all supplied values: any `Undefined`,
  including an extra, returns `Undefined` before numerical dispatch.
- A dependent assignment follows existing null/deferred-read handling, storing
  `null` and recovering when a missing property is defined.
- An omitted numerical position is not a supplied `Undefined` read.
- Preserve existing live-null assignment handling; literal-null numeric
  conversion does not override that assignment context.
- Strict unknown identifiers still throw during argument evaluation; no undefined
  property or extra argument bypasses such an error.
- Keep all read dependencies, class rules, object-property delete/recovery,
  transactional rollback and subsequent propagation on the existing runtime paths.
- State variables and local bindings named `Math` still shadow the static namespace;
  ordinary `.Math` methods and properties retain their existing lookup behavior.
- `Math.clamp` read as a value remains unsupported/undefined like other Math
  method references; it does not become a first-class function or callable alias.
- Keep all other Math functions/constants, accepted syntax, AST/value/API types,
  lexer/parser/generator behavior, annotations and error representations unchanged.
- No new local capture or remedy for inherited parameter-dependent/nested
  noncapturing propagation or extreme Windows debug stack limitations is implied.

## Errors

- Introduce no new error kind, arity error, range error or numeric-coercion error.
- Numeric NaN, omitted inputs and reversed bounds are the defined results above.
- Argument-expression failures retain their inherited exact types/messages;
  numeric conversion does not catch or replace them.
- The clamping section and deferred/rollback entry preserve these observable errors.

| Condition | Exact inherited error |
| --- | --- |
| Strict unknown argument identifier `missing`, including an extra | `ReferenceError("missing is not defined")` |
| An unchanged unknown static Math method `unknown` | `TypeError("Math.unknown is not a function")` |
| The unchanged unsupported static random operation | `TypeError("Math.random is not supported")` |

- The latter two remain subject to the existing pre-dispatch any-undefined gate.
- Runtime errors retain top-level statement positions; caught error values omit
  positions, and failed updates/redefinitions roll back before recovery.
