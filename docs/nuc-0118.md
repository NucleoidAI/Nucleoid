# NUC 118 -- Case Conversion Method Aliases

```
NUC: 118
Title: Case Conversion Method Aliases
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Language compatibility
Created: 18-Nov-2026
```

## Abstract

- Strings gain the case conversion methods that Kotlin, Rust and Swift
  spell, as aliases of the accepted `toUpperCase()` and `toLowerCase()`:
  - `TEXT.uppercase()` and `TEXT.lowercase()`, Kotlin's;
  - `TEXT.to_uppercase()` and `TEXT.to_lowercase()`, Rust's;
  - `TEXT.uppercased()` and `TEXT.lowercased()`, Swift's.
- Whenever its receiver evaluates to a string, each alias gives exactly
  what its accepted spelling gives: it converts the whole string with the
  same full Unicode case mapping, so `"straße".uppercase()` gives
  `"STRASSE"`; further arguments are evaluated and ignored; and a
  declaration that holds the call stays live as the string changes, with
  the accepted spelling's dependencies.
- The equivalence holds per evaluation of the receiver. When a later write
  turns the receiver of a standing call into another kind of value, the
  call reads the alias's name on that value, as every other receiver does:
  a number raises `TypeError("number.uppercase is not a function")` where
  the spelling raises `TypeError("number.toUpperCase is not a function")`,
  and an object whose `uppercase` member is a function runs it where the
  spelling gives undefined. Every such program raised the alias's
  `TypeError` at its declaration at the accepted revision.
- At the accepted revision each of these calls raises
  `TypeError("<text>.<name> is not a function")`, unless an argument
  raises first. Only those calls change, along with the programs that
  caught that error. Every other reading of the names is kept: lists,
  numbers and other values keep their accepted errors, object members,
  instance methods and functions named like the aliases keep running,
  `null` and undefined receivers stay null-safe, `String.uppercase()` keeps
  its error, and reads without a call, such as `s.uppercase`, stay
  undefined.
- `toUpperCase`, `toLowerCase`, `upper` and `lower` stay the canonical
  spellings. No token, keyword, syntax-tree node, error type or message
  format, dependency or public item is added.
- The authoritative contract is
  [Case conversion method aliases](../nucleoid.spec.md#case-conversion-method-aliases).

## Motivation

- Programs and models written by people and LLMs that know Kotlin, Rust
  or Swift convert case by those languages' names: `name.uppercase()` in
  Kotlin, `name.to_uppercase()` in Rust and `name.uppercased()` in Swift.
  In Nucleoid every one of them raises
  `TypeError("<text>.<name> is not a function")`, so a world model that
  normalizes a sensor's label with `label.lowercase()` or a code with
  `code.to_uppercase()` fails before it runs, although the accepted
  spellings `label.toLowerCase()` and `code.toUpperCase()` say the same
  thing.
- World models normalize the text they compare: identifiers, labels,
  codes and names read from different sources, such as a badge reader
  that prints names in capitals and a roster that does not. These
  conversions are standing, so they must follow every later write of the
  string, which the accepted `toUpperCase` and `toLowerCase` already do and
  the aliases inherit.
- The aliases advance the language-superset aspiration of the Language
  compatibility category. The accepted `this`/`self`, `=>`/`->`, `lower`,
  `upper`, `strip`, `find`, `contains`, `substr`, NUC 110's `startswith`,
  `endswith` and `join`, NUC 116's `size`, `len`, `isEmpty`, `is_empty` and
  `isNotEmpty`, and NUC 117's `first` and `last` follow the same pattern:
  an equivalent familiar spelling beside the canonical one, with no change
  to any accepted program.
- Kotlin's `uppercase()` and `lowercase()`, Rust's `to_uppercase()` and
  `to_lowercase()`, and Swift's `uppercased()` and `lowercased()` are the
  prior art.

## Rationale

- **Category and mode.** The allocating continuous cycle drew Language
  compatibility with one tool-backed uniform draw over the five categories
  that NUC 1's registry marks eligible for automatic selection, index 4
  with probability 1/5 and no redraw, and recorded the requested change in
  the allocation commit `266b9114`, which this revision pins. Token
  comparison is therefore skipped as `language_compatibility`. The skip is
  categorical; it is neither a measured comparison nor a passing token
  gate. Runtime applicability does not apply to this category.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts. They execute their assertions and explicit
  returns with full coverage, and every pre-existing case is unchanged.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Only former errors.** At the accepted revision every call of the six
  names on a string receiver raises
  `TypeError("<text>.<name> is not a function")` at the start of the
  running statement, in plain and JSON output alike, unless an argument
  raises first. No accepted test, document case, dataset record or ARC
  dataset calls them, and no test pins that error; in programs the names
  occur only inside comments, such as `# key is department lowercased`.
- **One arm per direction.** The aliases join the two accepted arms of the
  string transforms that `toUpperCase` and `toLowerCase` already share with
  `upper` and `lower`, so each alias returns its spelling's result by
  construction: Rust's `str::to_uppercase` or `str::to_lowercase` of the
  whole receiver. Rejected: rewriting the calls at parse time, which would
  render `toUpperCase` where the source wrote `uppercase()` in statements,
  `why`, `affects`, `--graph` and graph keys; a second implementation,
  which could drift from the accepted one; and a table of alias names
  consulted before the dispatch, which would add a lookup to every string
  method call.
- **Strings only.** `toUpperCase` and `toLowerCase` are string methods, and
  so are their aliases. Lists, populations, numbers and every other
  receiver keep their accepted readings, and with them their errors; a list
  of strings converts as `names.map(name -> name.uppercase())`.
- **Calls only.** Reading `s.uppercase` without a call stays undefined, as
  reading `s.toUpperCase` does, and assigning it keeps its accepted
  `TypeError`. A property alias would change accepted outputs, since those
  reads give undefined rather than a string.
- **Arguments.** The receiver is read first and then every argument once,
  left to right, as for every call, because the string route evaluates the
  arguments before any string method runs. The accepted spellings ignore
  their arguments, and so do the aliases; a locale passed as Kotlin, Java
  or Swift would pass it is therefore evaluated and ignored.
- **Per evaluation of the receiver.** The aliases are methods of strings,
  not rewrites of the call, so the receiver decides the reading each time a
  call is evaluated. A standing call whose receiver a later write turns
  into another kind of value reads the alias's name on that value, as
  [Calls](#calls) says for every other receiver, while the spelling reads
  `toUpperCase` or `toLowerCase` there, and a receiver that becomes a
  string only later is read as the value it held until then. The two then
  differ in exactly the ways [Per evaluation](#per-evaluation) lists: an
  error that names the method as written, a member of the alias's name
  that runs, and the dependency on that member. Each such program raised
  the alias's `TypeError` at the accepted revision, at the declaration or
  when the string arrived. Rejected: converting a non-string receiver's
  text, which would give lists, numbers and objects methods they do not
  have, and raising the spelling's error instead, which would add a second
  error message for one call.
- **Live and rendered as written.** While the receiver is a string, a
  declaration or class-level rule that calls an alias depends on what its
  spelling depends on: its receiver's reads. Statements, `why`, `affects`,
  `--graph` and graph keys render the call as every call is rendered, with
  the name the source wrote; nothing renders `toUpperCase` in its place.
- **Source-language differences stay documented, not emulated.**
  - Kotlin's `uppercase()` and `lowercase()` use the invariant locale, as
    Nucleoid's mapping does, and Rust's `str::to_uppercase()` and
    `str::to_lowercase()` are that mapping: `ß` becomes `SS`, the ligature
    `ﬁ` becomes `FI`, the title-case digraph `ǅ` becomes `Ǆ` or `ǆ`, and a
    word-final capital sigma lowers to `ς`.
  - Kotlin's and Java's `Locale` overloads and Swift's `uppercased(with:)`
    would arrive as arguments, which are ignored, so no locale-specific
    mapping applies: `"I".lowercase("tr")` is `"i"`, not Turkish dotless
    `"ı"`.
  - Kotlin's `Char.uppercase()` has no counterpart, as Nucleoid has no
    character type; a one-character string converts as any string does.
  - C#'s `ToUpper()` and `ToLower()` are not added: they follow the
    current culture, which Nucleoid has none of, and their invariant forms
    `ToUpperInvariant()` and `ToLowerInvariant()` would be two more names
    whose capitalization no accepted string method uses.
  - Rust's `to_ascii_uppercase()` and `to_ascii_lowercase()` are not added:
    their mapping changes ASCII letters only, so `"straße"` would keep its
    `ß`, which differs from the accepted spellings.
  - Ruby's `upcase` and `downcase` are not added: Ruby writes them without
    a call, as `name.upcase`, which reads as a property here and stays
    undefined, and their options such as `:turkic` select mappings that
    Nucleoid does not have.
  - Python's `casefold()`, `swapcase()`, `title()` and `capitalize()`,
    Kotlin's `capitalize()` and `replaceFirstChar`, and Swift's
    `capitalized` are not added: they are other operations, which fold
    case for comparison, invert it or change only the first letters, not
    spellings of `toUpperCase` or `toLowerCase`.
  - Go's `strings.ToUpper(s)` and `strings.ToLower(s)` are not added: they
    are functions of a package rather than methods of the string.
- **Completion.** The terminal workspace offers the JavaScript names of
  string members, `toUpperCase` and `toLowerCase`, and none of the
  accepted aliases, as [NUC 110](nuc-0110.md), [NUC 116](nuc-0116.md) and
  [NUC 117](nuc-0117.md) kept it. This proposal follows that precedent and
  adds no completion entry.
- **Public API.** No public item is added or removed.
  `nucleoid::builtins::string_method`, the public function behind every
  string method, keeps its signature and accepts the six names where it
  returned the `TypeError`, as it accepted `startswith` and `endswith` in
  [NUC 110](nuc-0110.md) and the size names in [NUC 116](nuc-0116.md). The
  widened set of names is the change to report for semantic-versioning
  review.
- **No `Requires`.** `toUpperCase`, `toLowerCase`, `upper` and `lower` are
  base built-ins that no NUC introduced. NUC 110, NUC 116 and NUC 117 are
  followed as precedents, not depended on.
- **Not added.** Property aliases, static forms such as `String.uppercase`,
  aliases on lists, populations or other receivers, the names left out
  above, locale-specific mappings, completion entries and any change to
  `toUpperCase`, `toLowerCase`, `upper` or `lower`.

## Specification

- The normative contract is
  [Case conversion method aliases](../nucleoid.spec.md#case-conversion-method-aliases).

### Calls

- `RECEIVER.uppercase(...)`, `RECEIVER.to_uppercase(...)` and
  `RECEIVER.uppercased(...)` are `RECEIVER.toUpperCase(...)`, and
  `RECEIVER.lowercase(...)`, `RECEIVER.to_lowercase(...)` and
  `RECEIVER.lowercased(...)` are `RECEIVER.toLowerCase(...)`, whenever
  `RECEIVER` evaluates to a string.
- Strings are reached however the language reaches them: literals, names,
  properties and instance properties, call and query results such as
  `split`, `map`, `slice`, `substring`, `join` and `repeat`, templates,
  concatenations, indexes, `.value` snapshots, state versions, the results
  of conditional expressions, `String(...)` and `typeof`, and
  `$Name.property` inside class-level rules.
- On every other receiver the names keep the readings of
  [Compatibility](#compatibility).

### Conversion

- The upper aliases give the whole string in Unicode's full uppercase
  mapping and the lower aliases in its full lowercase mapping, the
  mappings of `toUpperCase()` and `toLowerCase()`. A mapping can change the
  number of characters, and `length` counts the result's characters.

| `TEXT` | `TEXT.uppercase()` | `TEXT.lowercase()` |
| --- | --- | --- |
| `"Front Door"` | `"FRONT DOOR"` | `"front door"` |
| `"Straße"` | `"STRASSE"`, seven characters | `"straße"` |
| `"ﬁx"` | `"FIX"`, three characters | `"ﬁx"` |
| `"ǅ"` | `"Ǆ"` | `"ǆ"` |
| `"ΟΔΟΣ"` | `"ΟΔΟΣ"` | `"οδος"`, with a final `ς` |
| `"İ"` | `"İ"` | `"i̇"`, two characters |
| `"ı"` | `"I"` | `"ı"` |
| `""` | `""` | `""` |
| `"😀 1,2"` | `"😀 1,2"` | `"😀 1,2"` |

- The other aliases of each direction give the same results. This program
  is the specification entry
  `Nucleoid converts case with Kotlin, Rust and Swift spellings`:

```
label = "Front Door"
key = label.lowercase()
code = label.to_uppercase()
banner = label.uppercased()
assert([key, code, banner], ["front door", "FRONT DOOR", "FRONT DOOR"])
label = "Back Gate"
assert([key, code, banner], ["back gate", "BACK GATE", "BACK GATE"])
assert(["NORTH".to_lowercase(), "Mixed Case".lowercased(), "ok".uppercase()], ["north", "mixed case", "OK"])
street = "Straße"
upper = street.uppercase()
assert([upper, upper.length, street.length], ["STRASSE", 7, 6])
assert([street.to_uppercase(), street.uppercased(), street.toUpperCase()], [upper, upper, upper])
assert(["ΟΔΟΣ".lowercase(), "ǅ".uppercased(), "ﬁx".to_uppercase(), "".lowercased()], ["οδος", "Ǆ", "FIX", ""])
street = "Gasse"
[upper, key]
```

- This returns `["GASSE","back gate"]`: every declaration follows the
  writes of its string.

### Mapped and class-level conversions

- A conversion inside a mapping follows the list, and a class-level rule
  converts each instance's own property. This program is the
  specification entry
  `Nucleoid keeps class-level and mapped case conversions live`:

```
class Badge(name, team):
    this.name = name
    this.team = team
$Badge.login = $Badge.name.to_lowercase()
$Badge.crest = $Badge.team.uppercased()
ana = Badge("Ana Lima", "blue")
bo = Badge("BO CHEN", "Red")
assert([ana.login, ana.crest, bo.login, bo.crest], ["ana lima", "BLUE", "bo chen", "RED"])
bo.name = "Bo Chen-Wu"
ana.team = "green"
assert([bo.login, ana.crest], ["bo chen-wu", "GREEN"])
tags = ["Urgent", "low"]
shout = tags.map(tag -> tag.uppercase())
quiet = tags.map(tag -> tag.lowercased())
assert([shout, quiet], [["URGENT", "LOW"], ["urgent", "low"]])
tags.push("Straße")
assert(shout, ["URGENT", "LOW", "STRASSE"])
quiet
```

- This returns `["urgent","low","straße"]`.
- Inside a class-level rule or conditional `$Name` is the instance, so
  `$Name.uppercase()` there calls the instance's own `uppercase` member or
  gives undefined, while `$Name.property.uppercase()` converts the
  property's string.

### Evaluation

- The receiver is read first, and then every supplied argument once, left
  to right, including unused extras, as for every call. A missing name
  among them raises `ReferenceError("<name> is not defined")` before the
  alias runs: `"ab".uppercase(missing)` raises it, as
  `"ab".toUpperCase(missing)` does, and a failed statement rolls back the
  effects of the arguments before it.
- A `null` or undefined receiver keeps the accepted route: the call is
  undefined and the arguments are not evaluated, so after `u = null`,
  `u.uppercase(missing)` is undefined.

### Liveness and class-level rules

- While its receiver is a string, a declaration that calls an alias depends
  on what its spelling depends on: writes of the name, the property or the
  instance property that holds the string, of the operands of a
  concatenation or template, and pushes to the list of a mapping
  re-evaluate it. `(why key)[0].from` is `["label"]` after
  `key = label.lowercase()`, as after `key = label.toLowerCase()`, and the
  nodes, sources and values of the `why` and `affects` steps are the
  spelling's; only their rules name the call as written.
- In a class-level rule or conditional each instance evaluates its own
  alias over its own properties, and a write of the property re-evaluates
  that instance's rule.

### Per evaluation

- An alias equals its spelling only while its receiver evaluates to a
  string. When a later write replaces a held receiver with another kind of
  value, the re-evaluated call reads the alias's name on that value, as
  [Calls](#calls) says for every other receiver. After `s = "aB"` and
  `u = s.uppercase()`, against `u = s.toUpperCase()`:

| Later write | `u = s.uppercase()` | `u = s.toUpperCase()` |
| --- | --- | --- |
| `s = "Cd"` | `u` is `"CD"`, read from `s` | The same |
| `s = ["x"]` | `TypeError("s.uppercase is not a function")` at the write, which rolls back | `TypeError("s.toUpperCase is not a function")`, which rolls back |
| `s = 7` | `TypeError("number.uppercase is not a function")`, which rolls back | `TypeError("number.toUpperCase is not a function")`, which rolls back |
| `s = false` | `TypeError("boolean.uppercase is not a function")`, which rolls back | `TypeError("boolean.toUpperCase is not a function")`, which rolls back |
| `s = Date(0)` | `TypeError("Date.uppercase is not a function")`, which rolls back | `TypeError("Date.toUpperCase is not a function")`, which rolls back |
| `s = {uppercase: () => "own"}` | `u` is `"own"`, read from `s` and the object's `uppercase` | `u` is `null`, read from `s` and the object's `toUpperCase` |
| Then `s.uppercase = () => "changed"` | `u` is `"changed"` | `u` stays `null` |
| `class Box:` with `def uppercase() => "boxed"`, then `s = Box()` | `u` is `"boxed"`, read from `s` | `u` is `null`, read from `s` and `s.toUpperCase` |
| `s = {other: 1}` | `u` is `null`, read from `s` and the object's `uppercase` | `u` is `null`, read from `s` and the object's `toUpperCase` |
| `s = null` | `u` is `null`, read from `s` | The same |

- The other five aliases behave alike with their own names, and the lower
  aliases against `toLowerCase`. Every program in this table raised
  `TypeError("aB.uppercase is not a function")` at the declaration at the
  accepted revision, so none of these differences changes an accepted
  result.
- The same holds the other way round: a class-level rule
  `$C.r = $C.v.uppercase()` over an instance whose `v` is first an object
  or instance and is later written a string reads the member `uppercase`
  of that object first, as every member call does, and converts the string
  afterwards. Its values equal the spelling's once the string arrives,
  except that a member `uppercase` that is a function ran with its
  arguments, which the spelling's undefined `toUpperCase` does not
  evaluate. `--graph` then lists the member read under the name the call
  used, `obj:0.uppercase [pending]` where the spelling lists
  `obj:0.toUpperCase [pending]`, and lists none after a method `uppercase`
  ran, where the spelling lists `q.toUpperCase [pending]`. Each such
  program raised `TypeError("<text>.uppercase is not a function")` at the
  accepted revision when the string arrived.

### Transactions

- Errors of an alias propagate through the existing transaction, so a
  failed standing re-evaluation rolls back the change that triggered it: a
  name written a number under `code = label.uppercase()`, raising
  `TypeError("number.uppercase is not a function")`, and a property written
  `true` under a class-level rule, raising
  `TypeError("boolean.to_lowercase is not a function")`. A failed statement
  or transaction restores declarations that call aliases, their values and
  their dependencies. This program is the specification entry
  `Nucleoid rolls back failed updates through case conversion aliases`:

```
label = "door"
code = label.uppercase()
failure = ""
try:
    label = 7
catch error:
    failure = error
assert(failure, TypeError("number.uppercase is not a function"))
assert([label, code], ["door", "DOOR"])
try:
    label = "gate"
    assert(code, "GATE")
    throw "UNDO"
catch error:
    assert(error, "UNDO")
assert([label, code], ["door", "DOOR"])
class Tag(name):
    this.name = name
$Tag.key = $Tag.name.to_lowercase()
red = Tag("RED")
try:
    red.name = true
catch error:
    failure = error
assert(failure, TypeError("boolean.to_lowercase is not a function"))
assert([red.name, red.key], ["RED", "red"])
red.name = "Crimson"
red.key
```

- This returns `"crimson"`.

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` and graph and block keys show the
  call in the canonical rendering of every call, with its name as written:
  after `key = label.lowercase()`, `(why key)[0].rule` is
  `"key = label.lowercase()"`, where the spelling's is
  `"key = label.toLowerCase()"`, and `$Tag.k = $Tag.name.lowercased()`
  renders as `$Tag.k=$Tag.name.lowercased()`. A class-level `if` whose
  condition calls an alias names it in the block key that `--graph`
  prints.
- While the receiver is a string, the dependencies are those of the
  accepted spelling: `(why key)[0].from` is `["label"]` after
  `key = label.lowercase()`, as after `key = label.toLowerCase()`, and
  `(why u)[0].from` is `["s"]` after `u = s.uppercase()`.
  [Per evaluation](#per-evaluation) lists the dependencies after a write
  replaces the string with an object or instance.

### Cost

- Each alias is one more name in the match of its spelling's arm, so a
  call runs exactly the code of `toUpperCase` or `toLowerCase`: the string
  route evaluates the arguments and then converts the receiver in one pass
  of Rust's case mapping.
- **Measured**, not projected, on the final tree: on `nucleoid-final.exe`,
  its release build, through the command line, rustc 1.97.1, the median of
  21 interleaved runs of each program with `--json`, including process
  start, one process at a time with nothing else running, against the
  accepted revision's release build for the accepted spellings. Times are
  in milliseconds.
  - "100,000 calls" maps `items`, `"x".repeat(100000).split("")`, through
    `x -> x.NAME()`; building `items` alone takes 29.8 ms on the final
    build and 29.3 ms on the accepted one.
  - "One call" converts `"aßc".repeat(400000)`, 1,200,000 characters, once;
    building it alone takes 12.8 ms on the final build and 12.2 ms on the
    accepted one.
  - "10,000 writes" declares `u = s.NAME()` and then writes `s` 10,000
    times from a `while` loop, alternating `"Ab"` and `"cD"`, so that every
    write re-evaluates `u`; the loop without the declaration takes about
    30 ms.

| Program | `uppercase` | `to_uppercase` | `uppercased` | `toUpperCase` | `toUpperCase`, accepted revision |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100,000 calls | 69.2 | 71.3 | 72.0 | 72.1 | 71.4 |
| One call | 19.7 | 19.4 | 19.4 | 19.2 | 19.7 |
| 10,000 writes | 57.6 | 59.5 | 59.9 | 58.7 | 59.2 |

| Program | `lowercase` | `to_lowercase` | `lowercased` | `toLowerCase` | `toLowerCase`, accepted revision |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100,000 calls | 70.1 | 69.8 | 69.3 | 69.6 | 69.9 |
| One call | 17.9 | 17.8 | 17.8 | 18.2 | 18.1 |
| 10,000 writes | 59.3 | 59.5 | 58.1 | 58.0 | 58.7 |

- Each alias takes 0.96 to 1.03 times its spelling's time on the same
  build, and the final build's spellings, `upper` and `lower` included,
  take 0.97 to 1.03 times the accepted revision's, so the aliases cost
  what their spellings cost and the added names cost nothing measurable.
  The same programs on the phase-1 build gave 0.97 to 1.02 and 0.97 to
  1.01.
- The standing declaration re-evaluates once per write: in five runs each,
  with it 10,000 writes take about 61 ms and 20,000 about 104 ms on the
  final build, with either spelling, against about 30 ms and 46 ms for the
  loop alone, and 61 ms and 105 ms with `toUpperCase` on the accepted
  build.

### Compatibility

- Parsing, the syntax tree, canonical rendering and graph keys are
  unchanged; the six names stay ordinary method names.
- Only inputs that were errors at the accepted revision change: calls of
  the six names on string receivers, each of which raised
  `TypeError("<text>.<name> is not a function")` at the start of the
  running statement, and the programs that caught that error. Calls whose
  arguments raise first keep that error. "The tags" are `class Tag(name):`
  with the body `this.name = name`.

| Program | Accepted result | Result under this NUC |
| --- | --- | --- |
| `"abc".uppercase()` | `TypeError("abc.uppercase is not a function")` | `"ABC"` |
| `"ABC".lowercase()` | `TypeError("ABC.lowercase is not a function")` | `"abc"` |
| `"abc".to_uppercase()` | `TypeError("abc.to_uppercase is not a function")` | `"ABC"` |
| `"ABC".to_lowercase()` | `TypeError("ABC.to_lowercase is not a function")` | `"abc"` |
| `"abc".uppercased()` | `TypeError("abc.uppercased is not a function")` | `"ABC"` |
| `"ABC".lowercased()` | `TypeError("ABC.lowercased is not a function")` | `"abc"` |
| `["straße".uppercase(), "ǅ".lowercase(), "İ".lowercased().length]` | `TypeError("straße.uppercase is not a function")` | `["STRASSE","ǆ",2]` |
| `["".uppercase(), "".to_lowercase()]` | `TypeError(".uppercase is not a function")` | `["",""]` |
| `"abc".uppercase("tr", 2)` | `TypeError("abc.uppercase is not a function")` | `"ABC"` |
