## Abstract

- Lets a call argument that begins with a binary operator stand for the
  function of one parameter that applies the operator to it, an *operator
  section*:
  - `xs.filter(> 4)` passes the function `x -> x > 4`, so
    `[3, 8, 1, 9].filter(> 4)` is `[8, 9]`.
  - The section's operator is one of the symbol binary operators that
    cannot begin an operand: `==`, `!=`, `===`, `!==`, `<`, `<=`, `>`,
    `>=`, `*`, `%`, `**`, `&&`, `||` and `??`.
  - The rest of the argument, up to the `,` or `)` that ends it, is read as
    if the parameter stood before the operator, with the usual precedence.
    So `xs.count(% 2 == 0)` counts the even items, `xs.map(* 2 + 1)` maps
    `x -> x * 2 + 1` and `xs.map(?? 0)` maps `x -> x ?? 0`.
- The parameter has no name, so a section reads it only as the operator's
  left operand, and no name in the argument can shadow it. Every name in
  the operand reads as it does in the body of the equivalent lambda, once
  per call of the function. So the standing declaration
  `big = xs.filter(> limit)` follows later writes of `xs` and of `limit`,
  as `xs.filter(x -> x > limit)` does.
- A section is a whole positional argument of a call, as
  [NUC 79](nuc-0079.md)'s property selectors are: of a method, a function,
  a constructor, `new` or `super(...)`. Grouping parentheses, list items,
  object values, named arguments, subscripts, pipeline stage arguments and
  every other position keep their accepted readings and errors.
- `+` and `-` keep their accepted unary readings, so `xs.map(- 1)` still
  passes the number `-1`. `!`, `/`, which may begin a regular expression
  after `(`, and the word operators `is`, `is not`, `in`, `not in`, `and`
  and `or` are not section operators.
- The parser builds the tree of the lambda itself, so evaluation, liveness,
  dependencies, `why` and `affects`, graph keys and rollback are the
  lambda's, and a section renders as `function()`, as every anonymous
  lambda does.
- Only inputs that were errors at the accepted revision change. A program
  is parsed exactly as at the accepted revision first, and only when that
  whole parse fails are sections read, in one more run of the same parse
  passes. So an accepted program that holds a section where the accepted
  parser never reads it keeps its result: the ignored tail of the template
  interpolation `` `v ${xs.length, xs.filter(> 4)}` `` still gives
  `"v 4"`, and `parse_expression("1 if xs.some(> 4) else 2")` still
  returns `1`.
- Each section saves three lexer tokens over its inline lambda:
  `(x -> x > 4)` is seven tokens and `(> 4)` is four.
- No token, keyword, syntax-tree node, error type or message format, option
  or public item is added. The authoritative contract is
  [Operator section arguments](../nucleoid.spec.md#operator-section-arguments).

## Motivation

- World models compare values with thresholds, categories and defaults
  everywhere: the cells that are not background, the readings over a
  limit, the even positions, the missing values and their defaults.
  Accepted Nucleoid writes each such test as a lambda that names a
  parameter only to use it once, at once, as the operator's left operand:

  ```
  cells = [0, 3, 0, 7, 7]
  [cells.filter(c -> c != 0), cells.count(c -> c == 7), cells.map(c -> c * 2)]
  ```

  It returns `[[3, 7, 7], 2, [0, 6, 0, 14, 14]]`.
- With sections the same line reads
  `[cells.filter(!= 0), cells.count(== 7), cells.map(* 2)]`. Every section
  saves three lexer tokens: the parameter, the arrow and the parameter's
  one use.
- The accepted executable corpus, its 1,122 cases, already passes 44 such
  lambdas as whole call arguments, in 32 cases: a one-parameter `->` or
  `=>` lambda whose body starts with its parameter and a section operator
  and reads the parameter nowhere else. `>` alone accounts for 22 of them.
- A language model that writes a world model must invent a parameter name
  for each and repeat it exactly. A mismatch such as `c -> cell != 0` reads
  an unrelated binding. A section has no parameter to mistype.
- [NUC 79](nuc-0079.md)'s property selectors already pass `.name` for
  `x -> x.name`. It rejected operators over selectors and an implicit `it`
  or `_` placeholder, because a named implicit parameter needs scope rules
  of its own. A section needs none: its parameter has no name and stands
  only where the operator's left operand would.
- Prior art: Haskell's operator sections `(> 4)`, Scala's placeholder
  `_ > 4`, Swift's `$0 > 4`, Kotlin's `it > 4` and Raku's Whatever-star
  `* > 4`.

## Rationale

- **Confirmed category and mode.** The allocating cycle drew Syntax
  enhancement with one tool-backed uniform draw over the five categories
  that NUC 1's registry marks eligible for automatic selection, index 0
  with probability 1/5 and no redraw, and recorded the requested change in
  the allocation commit `8ee7817e`. This is a continuous cycle, so token
  comparison is required. Runtime applicability does not apply to this
  category, and the ARC-requested and user-requested bases do not apply.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Only former errors.** At the accepted revision an argument that begins
  with a section operator reaches the operand parser, which raises
  `SyntaxError("Unexpected '<operator>'")`, placed at the token after the
  operator, because no operand begins with one. A statement that the parser
  reads tentatively reported its fallback's error instead: the
  destructuring declaration `first, second = xs.filter(> 4)` raised
  `SyntaxError("Unexpected ','")`. No accepted test or executable case
  holds a section operator directly after the `(` or `,` of a call
  argument list; the only such windows in the test sources are parameter
  lists such as `class Pair(*, a)` and the destructuring `a, *rest = p`,
  which keep their pinned errors.
- **Accepted first, then sections.** Accepted inputs can already hold a
  section where a tentative parse gives up on it. `parse_expression`
  ignores the tokens after the expression it reads, so
  `parse_expression("1 if xs.some(> 4) else 2")` returns the number `1`:
  the Python-style condition fails at `>` and is dropped. Reading sections
  in place would make it return the whole conditional, the class of break
  that rejected [NUC 91](nuc-0091.md). Template interpolations, which also
  ignore their tails, read no Python-style condition at their top level, so
  `` `${1 if xs.some(> 4) else 2}` `` gives `"1"` with or without
  sections. So a program is parsed exactly as at the accepted revision
  first, through its whole parse sequence: the plain parse, the `is` retry
  of [NUC 86](nuc-0086.md), the comprehension retry of
  [NUC 92](nuc-0092.md), the final parse of [NUC 102](nuc-0102.md) and the
  receiver run of [NUC 107](nuc-0107.md). Only when that whole sequence
  fails does the same sequence run once more, reading sections. Every
  accepted input keeps its parse by construction, and no list of tentative
  parts has to be complete.
- **The same readings everywhere in the section run.** Every parser the
  section run creates reads sections: each retry, NUC 102's final parse,
  NUC 107's receiver run, the `accepted` and `separates` probes with which
  a `while` header or a `suppose` premise decides [NUC 93](nuc-0093.md)'s
  separate statements, the tentative statements and every template
  interpolation. So a section parses as its lambda in every position. A
  method `def m(self, xs) => xs.filter(> 4)` in a class body needs both
  NUC 107's receivers and sections, and returns `[8]` for `[3, 8]`, as its
  lambda spelling does.
- **A cheap trigger.** The section run starts only when the tokens hold `(`
  or `,` directly followed by a section operator, or a template, because
  interpolations are lexed only when they are parsed. Any other failing
  program is reported after its first sequence, with no extra parse.
- **Fourteen operators.** A section operator is a binary operator that no
  operand begins with, so its place at the start of an argument has no
  accepted reading. `+` and `-` begin operands as signs, and `xs.map(- 1)`
  passes `-1` before `map` raises `TypeError("map expects a function")`, so
  they keep that reading. `!` begins a negation, `/` after `(` begins a
  regular expression, so `xs.map(/ 2).map(/ 3)` lexes `/ 2).map(/` as one
  pattern, and `is`, `in`, `not`, `and` and `or` are words whose positions
  NUC 86, NUC 93 and NUC 97 already give readings. `?`, `=`, `:=`, the
  compound assignments, `|>` and the arrows are not binary operators of a
  value.
- **One operator, then the usual precedence.** The parameter stands before
  the first operator only. The rest of the argument is the operator's right
  operand and every operator after it, so `* 2 + 1` is `(v * 2) + 1` and
  `> 4 ? 1 : 0` is `(v > 4) ? 1 : 0`, exactly as in the lambda's body. In
  `> 4 && < 9` the second operator has no left operand, so it raises
  `SyntaxError("Unexpected '<'")` there. Rejected: repeating the implicit
  parameter before every operator, which is the scope rule NUC 79 refused
  to add; the lambda `x -> x > 4 && x < 9` states it.
- **Right sections only.** A left section such as `(1 +)` needs a parameter
  after its operator, and its accepted error is pinned: `x **= (1 +)` and
  `x = (a ??)` raise `SyntaxError("Unexpected ')'")`, and `xs.map(1 +)`
  keeps that error.
- **A whole argument, only in argument lists.** Call arguments are where
  functions are passed, and that is where NUC 79 placed selectors. A
  section in grouping parentheses, `f = (> 4)`, a list item, an object
  value, a subscript, the value of a named argument `f(test= > 4)` or a
  lambda body `x -> > 4` would give the operator a reading in an operand
  position, so all of them keep their accepted errors. The argument of a
  pipeline stage such as `|> depth(> 1)` is not a call argument list, and
  the colon-led `assert: > 4, true` is a statement, not a call; both keep
  their errors.
- **Exactly the lambda.** A section parses to the function node that
  `v -> v OP REST` builds: an anonymous function of one parameter whose
  expression body is the operator expression with that parameter as its
  left operand. Evaluation, invocation, dependency recording, `.value`
  freezing, class-level rules, `why`, `affects`, rendering and transactions
  therefore treat it as they treat that lambda, including its accepted
  limits: a lambda reads variables and its own parameter but not the
  parameters of an enclosing function or constructor, so
  `super(> n)` in a constructor with the parameter `n` raises
  `ReferenceError("n is not defined")` when it runs, as `super(x -> x > n)`
  does. Rejected: a new `Expr` variant, which would break exhaustive
  matches over the public syntax tree and restate what the function node
  already carries.
- **An unnamed parameter.** The parameter is NUC 79's unnamed parameter,
  the empty name that no source can write. REST therefore cannot read or
  shadow it, a section nested inside another reads only its own, and every
  name REST writes reads what it reads in the lambda's body. A parameter is
  a local, so it is never a graph node, a state variable, a dependency or a
  completion candidate. A section's body is always an operator expression,
  never a bare member path, so NUC 79's selector recognition never takes it
  for a selector. Rejected: a nameable placeholder such as `it` or `_`,
  which NUC 79 rejected for its scope rules.
- **Rendered as `function()`.** An anonymous lambda renders as
  `function()`, so a section and its lambda spelling are the same graph
  key, `why` explains `big = xs.filter(function())` for both, and every
  output equals the lambda spelling's. The one difference is an error that
  quotes an expression holding the parameter, which quotes it without the
  empty name: `[1].map(> 4 = 1)` raises `SyntaxError("Cannot assign to >4")`
  where `[1].map(x -> x > 4 = 1)` raises
  `SyntaxError("Cannot assign to x>4")`. Rejected: rendering sections as
  written, as selectors render their path. It would keep two sections in
  standing conditions apart where two lambdas merge, but every `why`,
  `affects`, graph, block-key and error output would then differ from the
  lambda spelling. Anonymous lambdas in standing conditions share the key
  `if(xs.some(function()))` at the accepted revision, and sections inherit
  that accepted behavior unchanged.
- **Errors at the furthest point.** When the section run fails too, the
  input reports whichever of the accepted error and the section run's
  error lies further into the source, the accepted one on a tie, as NUC 102
  does. So `xs.filter(> 4 && < 9)` reports its second operator, and a valid
  section followed by an unrelated mistake reports the mistake, while
  `xs.filter(>)`, whose section run fails at the accepted error's position,
  keeps the accepted error. Interpolation errors are already program
  positions when they are compared, so a template-relative position never
  meets a program position, the mismatch that [NUC 86](nuc-0086.md)'s
  retry had to avoid. Rejected: NUC 107's rule of always reporting the
  accepted error, which would point every such program at its first, valid
  section.
- **Interactive input.** The line-oriented REPL treats a line as a command
  only when it starts with `.`, and the terminal workspace only when the
  whole input is one such line. A section never starts a statement, so
  neither front end changes.
- **Requires.** The Draft named NUC 60 for `??`, NUC 64 for `**` and NUC 79
  for the argument positions and the unnamed parameter. This revision adds
  NUC 57, whose `->` lambda a section abbreviates, NUC 86, NUC 92, NUC 102
  and NUC 107, whose parse sequence the section run repeats, and NUC 93,
  whose probes read sections in that run.

  case puts a section inside an assertion.
- Each section was measured written as an inline lambda `x -> x OP REST`,

## Specification

- The normative contract is
  [Operator section arguments](../nucleoid.spec.md#operator-section-arguments).

### Grammar

- In a parenthesized argument list, an argument is a section when it begins
  with a section operator:

```
argument        = section | selector | expression
section         = sectionOperator rest
sectionOperator = "==" | "!=" | "===" | "!==" | "<" | "<=" | ">" | ">="
                | "*" | "%" | "**" | "&&" | "||" | "??"
```

- `rest` is what follows the first operand of an expression: the
  operator's right operand and every operator, conditional and assignment
  after it, with the usual precedence and associativity, up to the `,` or
  `)` that ends the argument.
- The argument lists are those of calls, method calls, constructor calls,
  calls written with `new`, `super(...)` and a call juxtaposed with its
  callee, such as `xs (> 4)`. A section may be any argument, first or
  later, and argument lists nest, so `f(> g(> 1), < 2)` holds three
  sections.
- Line breaks, indentation and comments inside the parentheses are not
  layout, so a section may span or start a physical line. One trailing
  comma may follow it, as after any argument.
- Sections are read only in the section run of the parse passes.

### Semantics

- `OP REST` evaluates to the anonymous function of one parameter whose
  body is `v OP REST`, read as `REST` would be read after an operand `v`.
  It is the function `v -> v OP REST` with a parameter that no source can
  name.
- Called with an argument, it returns what that expression returns with
  the argument as `v`. A missing argument is `null`, as a lambda's missing
  parameter is, and arguments after the first are ignored. `typeof` gives
  `"Function"`, and the value displays as `[function]`.
- Names in REST are read when the function runs, once per call, as in the
  lambda's body. A list query over an empty list never calls it, so
  `[].filter(> missing)` is `[]`, while `xs.filter(> missing)` raises
  `ReferenceError("missing is not defined")` at its statement.
- A call that receives a section depends on whatever the section reads for
  each item, as with the lambda. A stored declaration whose section reads a
  `null` item settles to `null`, as with the lambda, while `??` reads a
  `null` item without settling.

```
readings = [12, 31, 7, 45, 18]
high = readings.filter(> 20)
low = readings.count(<= 12)
peak = readings.find(>= 40)
spot = readings.findIndex(< 10)
alarm = readings.some(> 50)
sane = readings.every(!= 0)
assert([high, low, peak, spot, alarm, sane], [[31, 45], 2, 45, 2, false, true])
readings.push(60, 0)
assert([high, low, peak, spot, alarm, sane], [[31, 45, 60], 3, 45, 2, true, false])
readings.shift()
assert([low, spot], [2, 1])
high.length
```

- The rest of the argument keeps the usual precedence:

```
values = [3, 8, 1, 9]
low = 2
doubled = values.map(* 2 + 1)
squares = values.map(** 2 - 1)
evens = values.count(% 2 == 0)
rests = values.map(% 3)
sizes = values.map(> 4 ? "big" : "small")
above = values.filter(> low + 1)
assert([doubled, squares], [[7, 17, 3, 19], [8, 63, 0, 80]])
assert([evens, rests], [1, [0, 2, 1, 0]])
assert([sizes, above], [["small", "big", "small", "big"], [8, 9]])
low = 0
values.push(4)
assert([above, evens, rests], [[3, 8, 9, 4], 2, [0, 2, 1, 0, 1]])
sizes
```

- Sections are ordinary function values for user functions and
  constructors, beside other arguments and lambdas:

```
def keep(values, test, change) => values.filter(test).map(change)
class Gate(name, test):
    this.name = name
    this.test = test
loud = Gate("loud", > 80)
quiet = new Gate("quiet", < 30)
levels = [20, 90, 50, 85]
heard = levels.filter(loud.test)
scaled = keep(levels, >= 50, x -> x / 10)
first = levels.find(> 100) ?? levels.find(quiet.test)
assert([heard, scaled, first], [[90, 85], [9, 5, 8.5], 20])
levels.push(120)
assert([heard, scaled, first], [[90, 85, 120], [9, 5, 8.5, 12], 120])
quiet.name
```

- Declarations, class-level rules, methods, function and lambda bodies,
  `if`, `for` and `while` headers, `suppose` premises and blocks,
  conditional expressions and template interpolations use sections as they
  use the lambda, and failed updates roll back through the existing
  transaction.

### Rendering

- A section renders as `function()`, as every anonymous lambda does. Graph
  and block keys, `why` and `affects` rules, `--graph` output, the REPL and
  errors that quote an expression holding a section are those of the
  lambda spelling, so `xs.filter(> 4).nope()` raises
  `TypeError("xs.filter(function()).nope is not a function")`.
- An expression inside a section's body that holds the parameter renders
  without it, which only an error message can show:
  `[1].map(> 4 = 1)` raises `SyntaxError("Cannot assign to >4")` when it
  runs.

### Parse passes

- Every input first runs the parse sequence of the accepted revision: the
  plain parse, the parse with `is` comparisons when its tokens hold `is` or
  a template, the parses with comprehensions when they hold `for` or a
  template, NUC 102's final parse when they hold a receiver dot or a
  template, and NUC 107's receiver run when that whole sequence fails and
  they hold a receiver window. The first success is the result.
- Only when all of that fails, and the tokens hold `(` or `,` directly
  followed by a section operator, or a template, the same sequence runs
  once more reading sections in every pass, probe, tentative statement and
  interpolation. Its first success is the result.
- When that run fails too, the input reports whichever of the accepted
  error and that run's error lies further into the source, by line and
  column, the accepted one on a tie. An error raised inside a template
  interpolation is placed at its line and column in the program before it
  leaves the interpolation, as at the accepted revision, so both errors are
  compared as program positions.
- `parse_expression` runs the same sequence on its input, so an input that
  an accepted pass reads keeps that result even when the tokens it ignores
  hold a section.

### Bounds

- Building a section passes the nesting guard of an argument and that of a
  lambda body, so calls nested inside sections reach
  `SyntaxError("Expressions are nested too deeply")` at the nesting depth
  of their lambda spellings, and the accepted error at that depth is kept:
  `y = f(> f(> ... 1))` parses to 30 levels and fails at 31, as its lambda
  spelling does, and in a template, a `while` header and a `suppose`
  premise each fails at the level where its lambda spelling fails.
- A Python-style condition in REST always belongs to the section's body.
  Near the limit, a lambda spelling whose condition no longer fits in its
  body is read by the accepted parser with the condition around the lambda,
  `(x -> x > 1) if c else 0`, a different program; a section has no such
  reading. So `y = f(> 1 if f(> 1 if ... c else 0) else 0)` reads 20 levels
  exactly as its lambda spelling does, and at 21 levels it raises
  `SyntaxError("Expected ')' but found keyword 'if'")` at its first `if`,
  line 2, column 11, where the lambda spelling still parses, to 30 levels,
  by reading its deepest conditions around their lambdas. A section never
  changes its reading with its depth.
- REST keeps every limit of an expression, including
  `SyntaxError("Expression has too many operands")` and
  `SyntaxError("Expression has too many parts")`. Evaluation passes the
  existing expression depth limit, as the lambda's body does.

### Compatibility

  because the section run starts only after every accepted pass has failed.
  Only inputs that were errors at the accepted revision change. Each source
  below is the whole program, with `\n` for a line break; `xs` is
  `xs = [3, 8, 1, 9]` on a first line of its own.

  any statement of the program runs.

  token after the operator.

  input is reported where it occurs, as after any valid argument, and an
  earlier mistake keeps its accepted error.

  positions. The interpolation parser places its error at the error's line

## Reference Implementation

- **State:** Implemented and Accepted; the frozen candidate, after the
  caller's Rust improvement pass, is integrated unchanged, as
  [Evaluation](#evaluation) records. It adds no token, keyword, `Expr`,
  `Stmt` or `Parameter` variant, error type or message, dependency or
  public item.
- `src/lang/ast/parser/section.rs`, a new private child module of 80 lines:
  - `Sections`, the mode of a parse: `Accepted` in every parser that
    `Parser::new` builds, and `Read` in the section run.
  - `section_operator`, one exhaustive `matches!` over the fourteen tokens.
  - `attempt_sections`, the section run. When the accepted sequence has
    failed and the trigger holds, it replaces the parser with
    `Parser::new` over the same tokens in the `Read` mode, so no state of
    the failed sequence carries over, runs the whole sequence again with
    `attempt_selves` and maps a failure to `furthest(accepted, sectioned)`,
    the accepted revision's rule that NUC 86's retry and NUC 102's final
    parse already use.
  - `mentions_sections`, the trigger: a template, as for NUC 102's final
    parse, or a `(` or `,` token directly followed by a section operator,
    in one scan of token pairs.
  - `starts_section`, true only in the `Read` mode at a section operator.
  - `section`, called by `arguments` inside `within(true, ..)`, as the
    ordinary argument is: it builds the argument inside
    `nested_expression_in(Ordinary, ..)`, leaves NUC 95's item words with
    `leave_items`, as every lambda body does, puts NUC 79's unnamed
    parameter in the pending-operand slot, parses the body with
    `expression_in` in that context, takes the slot back whether or not the
    body parsed, restores the item words and wraps the body in
    `Function::section`. A `debug_assert!` checks that the slot is empty
    when a section starts and another that the body read it.
  - Its unit tests, in `section/tests.rs`, check the operator set against
    the other operator, word and layout tokens, the trigger on positive and
    negative sources, and that `starts_section` holds only in the `Read`
    mode.
- `src/lang/ast/parser.rs` declares the module and gives `Parser` the
  fields `sections` and `operand`, the pending left operand. `attempt` is
  one expression,
  `self.attempt_selves(&parse).or_else(|accepted| self.attempt_sections(&parse, accepted))`.
  `attempt_selves` holds the accepted sequence with NUC 107's receiver run,
  which formed the body of `attempt` before: its receiver run now starts
  from `rewound`, and it ends in
  `self.attempt_readings(parse).map_err(|_| accepted)`, NUC 107's rule of
  reporting the accepted error when that run fails too, in the place of the
  `match` that said the same. `rewound`, which every retry, NUC 102's final
  parse and the statement probe `accepted` use, keeps the section mode, so
  every pass and probe of the section run reads sections. The file has 491
  lines.
- `parser/postfix.rs`: `postfix` takes the pending operand, when there is
  one, in place of its primary, so the body continues exactly as after an
  operand: postfix operators, then every binary, conditional and
  assignment level above it, with the usual precedence. `arguments` asks
  `starts_section` after NUC 79's selector window and before the ordinary
  argument; the two windows are disjoint, a `.` against a section operator.
  `parser/template.rs`: interpolation parsers take the mode with the other
  parse modes.
- `src/lang/ast/function.rs`: `unnamed_parameter`, the read of NUC 79's
  unnamed parameter, and `over_unnamed_parameter`, the anonymous function
  of that one parameter, are shared by `selector` and the new `section`,
  whose `debug_assert!` checks that `selector_path` never takes a section
  for a selector.
- The lexer, the generator, identifier reads, evaluation, the graph, the
  REPL, its continuation rules, the terminal and the CLI are unchanged, and
  nothing under `arc/` changes.
- The handwritten production source adds 128 and removes 17 lines in five
  files, 80 of them the new module, besides its 103 lines of unit tests:

- The new code follows the Power of 10 adaptation: its one recursive path,
