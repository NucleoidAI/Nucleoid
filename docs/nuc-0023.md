# NUC 23 -- Reactive Unit-Interval Saturation

```
NUC: 23
Title: Reactive Unit-Interval Saturation
Author: Copilot <223556219+Copilot@users.noreply.github.com>
Status: Accepted
Type: Standards Track
Created: 14-Oct-2026
```

## Abstract

- Add static `Math.saturate(value)` as one bounded numeric runtime capability.
- Define it as exactly the accepted ordered `Math.clamp(value, 0, 1)`, using
  the existing maximum fold followed by the existing minimum fold.
- Preserve intrinsic numeric conversion, once-only argument evaluation and
  reactive behavior without changing grammar, lookup or public representations.

## Motivation

- Live progress, fractions and animation opacity repeatedly clamp a numeric
  input to the same zero-through-one interval.
- Name that relationship without restating its fixed bounds at every call.
- Keep the accepted composition's special values and deferred behavior rather
  than introducing a separate range-validation or coercion policy.

## Rationale

- Reuse the exact ordered extrema semantics, not host `f64::clamp`.
- Retain numeric `NaN`, infinities, subnormal inputs and signed-zero results
  through the accepted folds, including their existing zero-tie behavior.
- Specify signed zeros by parity with independent accepted min/max controls,
  not a platform-specific sign promise.
- Reject input validation, endpoint shortcuts, conversion skips and changed
  extrema folds because they can change an observable result or error.
- Convert the first input intrinsically; a shadowable `Number()` call would
  change lookup and introduce a dependency.
- Do not delegate to a shadowable `Math.clamp` member or recursively invoke
  the public Math dispatcher.
- Omission follows the existing fixed-arity numeric-`NaN` convention, not a
  new arity error or a supplied undefined-property read.
- Ignore extra values numerically, never their evaluation, effects, reads or
  participation in the existing any-supplied-`Undefined` gate.
- Keep `Math.clamp(value, lower, upper)` available with identical behavior.
- Depend only on accepted specification behavior, not any pending NUC.
- Leave callable method values, namespace redesign, closure capture, public
  APIs, versions, MSRV, dependencies and inherited resource limits alone.

## Specification

### Static numeric contract

- The authoritative [Reactive unit-interval saturation section](../nucleoid.spec.md#reactive-unit-interval-saturation)
  and its five executable entries define the isolated candidate behavior.
- An unshadowed static `Math.saturate(...)` call uses the existing Math call path.
- Apply the unchanged any-supplied-`Undefined` gate before numeric dispatch.
- Convert the first supplied value with existing `Value::to_number`; an
  omitted first value supplies numeric `NaN`.
- Numbers retain their values, literal `null` becomes zero, booleans become
  zero/one, trimmed strings and empty/singleton lists keep existing conversion,
  and dates contribute their millisecond value.
- Other nonnumeric conversions yield numeric `NaN`, not a new type constraint.
- Apply the accepted maximum fold to `[first, 0]`, then the accepted minimum
  fold to `[bounded, 1]`, using numeric fixed bounds in exactly that order.
- This is exactly `Math.min(Math.max(first, 0), 1)` and the existing
  `Math.clamp(first, 0, 1)`, including numeric `NaN`, infinities and zero bits.
- Do not use host range validation, rearrange extrema, special-case endpoints,
  skip conversion or modify either accepted extremum fold.
- Extra supplied values do not enter the numeric composition.

### Evaluation, reactivity and compatibility

- Evaluate every supplied expression exactly once from left to right before
  dispatch, including expressions whose extra values are ignored numerically.
- Preserve all argument reads, effects and their dependency edges.
- Any supplied `Undefined`, including an extra, returns `Undefined`; omission
  is not a supplied undefined read.
- Dependent assignments retain existing live-null/deferred handling, storing
  `null` and recovering when missing properties are defined.
- Literal-null numeric conversion does not override live assignment context.
- Class rules, named wrappers, property deletion/recovery and transactions
  retain their accepted behavior.
- Strict unknown identifiers still throw during argument evaluation, including
  extras or arguments evaluated after an undefined property.
- Preserve top-level statement positions, caught values, rollback and recovery.
- State and local names `Math` retain static-namespace shadowing.
- Ordinary `.Math` properties and methods retain their member lookup.
- `Math.saturate` read as a value remains unsupported/`Undefined`, like other
  Math method references; no first-class callable or alias is added.
- Intrinsic conversion neither calls nor subscribes to `Number` or `Math.clamp`.
- Keep `Math.clamp`, `lerp`, `min`, `max`, `round`, all other Math functions and
  constants, their exact errors and all previously accepted syntax unchanged.
- Add no grammar, coercion, operator, call/member, class, scope, public
  Global/Value/AST/API, dependency or resource-limit change.
- Do not repair inherited parameter-dependent local/nested noncapturing
  failures or claim broader Windows debug stack safety.

## Errors

- Introduce no new numeric-coercion, input-validation, bound or arity error.
- Numeric `NaN`, omitted inputs and special results are defined behavior, not
  swallowed errors.
- Argument failures retain their inherited kind, exact message, position and
  caught value; failed updates roll back before subsequent recovery.
- Namespace shadowing retains ordinary receiver-specific errors.

| Condition | Exact inherited error |
| --- | --- |
| Strict unknown argument `missing`, including an extra | `ReferenceError("missing is not defined")` |
| Unchanged unknown static Math method `unknown` | `TypeError("Math.unknown is not a function")` |
| Unchanged unsupported random operation | `TypeError("Math.random is not supported")` |
| Calling `Math.saturate(...)` with numeric state `Math = 7` | `TypeError("number.saturate is not a function")` |

- Unknown/random dispatch remains subject to the existing any-undefined gate.
- No supplied expression is silently skipped to avoid an error or missing read.
