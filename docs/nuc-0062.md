## Abstract

- Adds the quantified expressions `all NAME in COLLECTION: CONDITION` and
  `any NAME in COLLECTION: CONDITION`, the universal and existential
  quantifiers planned as stage 5 of Draft [NUC 11](nuc-0011.md), as a
  standalone proposal.
- `all` is true when the condition holds for every member of the collection,
  including an empty one; `any` is true when it holds for at least one. The
  collection is a declared class's instances, in population order, or a list,
  including a reasoning selection such as `why c`.
- A quantifier is a live expression. Over lists and instance lists, its
  results, reads, dependencies, short-circuiting and null settling are those
  of `COLLECTION.every(NAME => CONDITION)` and
  `COLLECTION.some(NAME => CONDITION)`.
- The condition is evaluated in place with the binder in a new innermost
  frame, not as a function call, so it reads enclosing binders, parameters,
  locals, `this` and the instance of a class-level rule. Quantifiers therefore
  nest: `all t in Task: any w in Worker: w.skill == t.skill`. The nested
  callbacks `Task.every(t => Worker.some(w => w.skill == t.skill))` raise
  `ReferenceError("t is not defined")` at the accepted revision.
- No keyword or lexer token is added. A quantifier starts only at the token
  sequence `all` or `any`, a name and the existing `in` keyword, which the
  accepted parser rejects everywhere outside a template interpolation; `all`
  and `any` keep every accepted reading as names.
- A collection that is neither null nor a list or instance list raises the new
  message `TypeError("<collection> is not a collection")`. The authoritative
  contract is the [quantifiers](../nucleoid.spec.md#quantifiers) section.

## Motivation

- A world model states facts about whole populations: every task is staffed,
  some sensor in a zone fails, no order is overdue. Universal and existential
  quantification are the core of first-order logic, and Nucleoid's goal is a
  language in which an LLM builds and maintains such models.
- The accepted spelling is a method call with a callback:
  `ready = Check.every(c => c.passed)`. Around the collection and the
  condition it spends six tokens, `.`, `every`, `(`, the binder, `=>` and `)`,
  where `all c in Check: c.passed` spends four: `all`, the binder, `in` and
  `:`.
- The method spelling cannot nest. Functions do not close over enclosing
  names: `Runtime::invoke_with_this` starts every call from a fresh scope, so
  an inner callback cannot read the outer callback's parameter. At the
  accepted revision these programs fail on their first evaluation:
  - `covered = Task.every(t => Worker.some(w => w.skill == t.skill))` raises
    `ReferenceError("t is not defined")` once a task and a worker exist;
  - `[1, 2].map(x => [10].map(y => x + y))` raises
    `ReferenceError("x is not defined")`.
- The workaround is a class-level helper rule that stores the inner result on
  every instance, `$Task.staffed = Worker.some(w => w.skill == $Task.skill)`,
  then `covered = Task.every(t => t.staffed)`. It adds a property to the model
  only to carry a binder across a function boundary.
- `all` and `any` read as the claims they state, in the order a logician or a
  Python programmer writes them: `all(c.passed for c in checks)` in Python,
  `∀c ∈ Check: passed(c)` in mathematics. LLMs produce both forms readily.
- Draft NUC 11 already proposes this spelling and its error message as stage
  5, and stage 5 depends on no other unimplemented part of NUC 11, so it can be
  accepted alone.

## Rationale

- **Category and mode.** The caller selected the Reasoning enhancement
  category by one uniform draw over the four eligible registry categories, in
  continuous mode, so the token non-regression gate applies. Quantifiers are
  logic: they state rules over populations and selections. Each new case is
  paired with a behavior-equivalent accepted-syntax program recorded in the
  baseline.
- **A prefix with an explicit binder and the existing `in`.** `all c in Check:`
  matches NUC 11's draft, mathematical notation and Python's
  `for c in checks`, and reuses the `in` keyword of `for` headers.
  Rejected: implicit binders such as `all Check: passed`, which NUC 11 also
  rejects because bare names would silently mean instance properties.
- **Recognition by an exact three-token prefix, without a reserved word.** At
  the accepted revision `in` is not an operator, and a name followed by
  another name ends an expression, so `all NAME in` is a syntax error wherever
  the parser reads it, except at the top level of a template interpolation,
  whose trailing tokens are ignored. Recognizing that sequence everywhere else
  therefore changes no accepted program, and `all` and `any` stay ordinary
  names in every other position.
- Rejected: NUC 11's rule that a reasoning keyword loses to a variable of the
  same name. It would make `all = [1, 2]` disable quantifiers for the rest of
  the program and would make the meaning of a line depend on the state. With
  the prefix rule, `all n in all: n > any` reads the variables `all` and `any`
  and still quantifies.
- **Evaluation in place, not a lowered callback.** NUC 11 planned to reuse the
  nodes `every` and `some` build. A lowered callback could not read an
  enclosing binder, so nesting, the reason for this proposal, would still fail.
  Rejected: adding closures to every function, which would change accepted
  function semantics, stored callbacks and dependency tracking far beyond this
  proposal.
- The condition is evaluated in the enclosing scope with a new innermost frame
  for each member. The binder shadows an outer name only inside the condition,
  never leaks, and is invisible to functions the condition calls, so accepted
  function semantics are unchanged.
- **Parity with `every` and `some`.** The members, their order, truthiness,
  short-circuiting, the population dependency, the null-read settling rule and
  error propagation are those of the callback spelling, so a program can move
  between spellings without changing results. Members after the deciding one
  are not visited and add no dependency, which is sound for the same reason as
  for `find`: an unvisited member cannot change the result unless a visited
  one changes first.
- **A complete condition that extends to the right.** The condition is a full
  expression, like an arrow or lambda body, so `x and all v in xs: v > 0` and
  `not all v in xs: v > 0` read as written. Parentheses combine a quantifier
  with what follows, as with lambdas and Python's generator expressions.
  Rejected: a closing delimiter, which costs a token in every quantifier, and
  binding the condition tighter than `and` and `or`, which would cut
  `all v in xs: v > 0 and v < 9` in two.
- The collection ends at the quantifier's own colon and is parsed like the
  source of a `for` header, so `all s in c |> why |> stated: s.holds > 0` needs
  no parentheses. Statement and REPL header scans pair that colon with its
  prefix, as NUC 59 pairs a conditional's colon with its `?`.
- **One logical line.** An indented condition after the colon would look like
  a block suite, as in `if all v in xs:` followed by an indented line.
  Parentheses and brackets, where layout is suppressed, continue a quantifier
  across lines.
- **Template interpolations keep their reading.** An interpolation ignores
  trailing tokens, so `` `${all v in xs}` `` renders the variable `all` at the
  accepted revision. A top-level quantifier there is not recognized, as NUC 57
  keeps a top-level `lambda` and NUC 59 a trailing Python `if`; parentheses
  select the quantifier.
- **A collection error of its own.** Over a number, string or boolean,
  `x.every(...)` raises `TypeError("number.every is not a function")` and its
  kin, and over a plain object or an instance it yields `null` because `every`
  is read as a missing property. A quantifier is not a method call, so it
  raises NUC 11's `TypeError("<collection> is not a collection")` for every
  non-null value that is neither a list nor a declared class's instances,
  naming the collection's path or canonical source.
- Rejected: iterating a string's characters, as `for` does under
  [NUC 51](nuc-0051.md). `"abc".every(...)` raises at the accepted revision,
  and character-level quantification is rarely what a model means. It can be
  added later without breaking programs that this proposal accepts.
- **Grouped rendering.** `(all v in xs:v>0)` keeps a quantifier distinct from
  an enclosing operator in graph keys and `rule` text, as `(c?a:b)` and
  `(left??right)` do, and parses back to the same expression. The callback
  spelling renders as `xs.every(function())`, which hides its condition.
- **`.value` follows the callback spelling.** The collection is frozen when a
  declaration is stored, as a receiver is, and the condition reads `.value` at
  each evaluation, as a callback body does. Freezing the condition would
  evaluate the binder before it exists.
- **Reasoning observers.** A quantifier over a selection is an observer, like
  `(why c).every(...)`. A reasoning operation inside the condition also makes
  it one, because the condition is part of the declaration rather than a
  separate function.
- **Not added.** A `|> all` pipeline terminal and NUC 11's
  `SyntaxError("Cannot chain past <name>")`, `require` constraints, several
  binders such as `all a, b in ...`, filters such as `all v in xs if p: q`,
  other quantifiers such as `none` or `exactly`, and iteration of strings or
  objects.

### Departures from Draft NUC 11

- NUC 11 makes `all` and `any` pipeline terminals; here they are prefix
  expressions only, and `x |> all` keeps raising
  `TypeError("all is not an operation")`.
- NUC 11 says `all c in Check: c.passed` and `Check.every(c => c.passed)`
  denote the same node. Here they have the same results and dependencies, but
  a quantifier is its own `Expr::Quantified` node with its own rendering, and
  only it can read an enclosing binder.
- NUC 11's stage 5 reuses the nodes `every` and `some` build. Here the
  condition is evaluated in place, because a callback cannot see an enclosing
  binder.
- NUC 11's contextual keywords lose to variables of the same name. Here
  recognition depends only on the three-token prefix, and variables named
  `all` and `any` do not disable quantifiers.
- NUC 11 says quantifiers depend on every property the expression reads. Here
  they depend only on what the visited members read, as `every` and `some` do.
- NUC 11 parenthesizes a selection, as in `all s in (total |> why): ...`. Here
  the collection extends to the quantifier's colon, so the parentheses are
  optional.
- NUC 11 also allows quantifiers in constraints. `require` is not
  implemented, so this proposal covers expressions, statements and class-level
  rules.
- NUC 11 itself is not edited and remains Draft.

## Specification

### Syntax

- `quantified: ("all" | "any") NAME "in" collection ":" condition`, where
  `all` and `any` are ordinary identifiers, `NAME` is an identifier and `in`
  is the existing keyword.
- The quantifier is an operand, recognized where an operand begins and those
  three tokens follow each other. Every other sequence keeps its accepted
  reading: `all`, `any`, `all(x)`, `all = 1`, `all: int`, `for all in xs:`,
  `{all: 1}`, `{a: all b: b}`, `x = all c`, `def all(xs)`, `all => 1`,
  `Name.all()` and `xs.any(callback)`.
- `collection` is a complete expression in the header context of a `for`
  source: it ends at the quantifier's own top-level `:`, may hold `|>`, `??`,
  `and`, `or`, a prefix stage such as `why c`, a Python-style conditional and
  conditional expressions whose colons pair with their `?`, and needs
  parentheses for a top-level `lambda`.
- `condition` is a complete expression in the enclosing context, like an
  arrow or lambda body, so it extends as far right as possible, including
  over `|>`, `??`, conditional expressions, `and`, `or` and assignment. In an
  `if` header or another clause, the clause's own `:` ends it.
- A quantifier nested in the collection or the condition pairs with its own
  colon.
- At the top level of a template interpolation the prefix is not recognized,
  and the interpolation keeps ignoring its trailing tokens. Inside parentheses,
  brackets, braces or call arguments in an interpolation it is recognized.
- Layout is suppressed only inside `(` and `[`, so a quantifier spanning lines
  must be parenthesized or bracketed.
- Statement headers take quantifier conditions: `if`, `else if`, `elif if`,
  NUC 49's colon-free `if` and the indented direct alternatives `else` and
  `elif` of NUC 43. The direct-alternative lookahead and the native REPL's
  colon-free header scan count a top-level quantifier prefix as an opener whose
  colon is not the suite colon, as they count a top-level `?`.
- Canonical rendering is `(all NAME in COLLECTION:CONDITION)` or
  `(any NAME in COLLECTION:CONDITION)`.

```
covered = all t in Task: any w in Worker: w.skill == t.skill
spare = any w in Worker: all t in Task: t.skill != w.skill
label = (all v in scores: v > 0) ? "clean" : "dirty"
whole = groups.filter(g => all v in g: v > 0)
```

### Semantics

- Evaluate the collection once.
  - A declared class, written by name or held by a variable, yields its
    instances in population order and records the population dependency that
    `Name.every(...)` records.
  - A list yields its items. A reasoning selection is a list of steps.
  - Null or undefined yields no member, and the quantifier yields undefined,
    which a stored declaration settles to `null`. Reading a null collection
    also sets the null-read rule.
  - Any other value raises `TypeError("<collection> is not a collection")`.
- For each member in order, push a new innermost frame, bind `NAME` to the
  member, evaluate the condition in place and pop the frame.
- `all` returns `false` at the first member whose condition is falsy, and
  `true` when none is. `any` returns `true` at the first member whose condition
  is truthy, and `false` when none is. Truthiness is that of `if`. Later
  members are not visited.
- Reads are tracked as they happen, so a stored declaration depends on the
  collection, on the population or list, and on what the condition read for
  each visited member. It re-evaluates when any of them changes and replaces
  obsolete dependencies.
- A stored declaration whose evaluation read a null binding or property,
  including a null member or a null property in the condition, settles to
  `null`, as with `every` and `some`.
- The condition reads the enclosing scope: enclosing binders, parameters,
  locals, `this` and `self`, and the class-level instance that `$Class` names.
  The binder shadows outer names only inside the condition and is undefined
  after it. Functions and arrows called from the condition start from their
  own scope and do not see the binder.
- Over a list, an instance list, null or undefined, and with a condition that
  reads only the binder and state names, the result, reads, dependencies,
  short-circuiting, null settling and errors equal those of
  `COLLECTION.every(NAME => CONDITION)` and `COLLECTION.some(NAME =>
  CONDITION)`.
- `.value` adds no dependency. In the collection it is frozen when a
  declaration is stored, as in the receiver of `every`, which replaces a
  scalar or object reading with its value and reads a list again at each
  evaluation. In the condition it is read at each test, as in a callback body.
- In a class-level rule, references are validated when the rule is declared,
  with the binder bound inside the condition: another undefined name raises
  `ReferenceError("<name> is not defined")`, and a `$Class` property read in
  the collection or condition takes part in `TypeError("Circular Dependency")`
  checks. Each instance evaluates its own quantifier.
- A quantifier whose collection or condition contains a reasoning operation is
  a reasoning observer: graph walks neither select nor traverse it, and
  `model` excludes it.
- Errors raised by the collection or the condition propagate through the
  existing transaction; a failed standing re-evaluation rolls back the change
  that triggered it, including a new instance.

```
class Check
ready = all c in Check: c.passed
blocked = any c in Check: c.failed
assert(ready, true)
assert(blocked, false)
first = Check()
second = Check()
first.passed = true
second.passed = true
assert(ready, true)
second.passed = false
second.failed = true
assert(ready, false)
assert(blocked, true)
```

```
class Line(sent):
    this.sent = sent
class Order(lines):
    this.lines = lines
$Order.complete = all line in $Order.lines: line.sent
$Order.started = any line in $Order.lines: line.sent
first = Line(true)
second = Line(false)
order = Order([first, second])
empty = Order([])
assert(order.complete, false)
assert(order.started, true)
assert(empty.complete, true)
assert(empty.started, false)
```

```
all = [1, 2, 3]
any = 0
large = all n in all: n > any
some = any n in all: n > 2
assert(large, true)
assert(some, true)
any = 2
assert(large, false)
n = 10
doubled = all n in all: n * 2 > n
assert(doubled, true)
assert(n, 10)
```

### Compatibility

- The lexer and its token stream are unchanged; no keyword is reserved.
- Accepted programs keep their parsing, positions, diagnostics and behavior.
  Outside comments and literal text, an accepted program can contain the
  three-token prefix only at the top level of a template interpolation, where
  it is still not recognized; anywhere else the accepted parser rejects it.
- These are the only observable changes:
  - Source that contains the prefix where the parser reads an operand, outside
    a top-level interpolation, now parses as a quantifier. At the accepted
    revision every such source was rejected with a `SyntaxError`; the changed
    diagnostics are listed under Errors.
  - The public Rust `parse_expression`, which ignores trailing tokens, returns
    a quantifier for input such as `all x in xs: x`, where it returned the
    name `all`.
  - The native REPL buffers `if all v in xs: v > 0` as a colon-free header
    awaiting its indented body, where it previously ran the line and reported
    a `SyntaxError`.
  - The public `Expr` enum gains `Expr::Quantified`, `Ast` gains
    `Ast::Quantified`, and `lang::ast` gains the `Quantifier` enum and the
    `quantified` module. Exhaustive downstream matches stop compiling, so this
    needs human SemVer review. No project version is changed.
- `Expression::roots` no longer reports a binder read inside its condition as
  a root; it is only reachable from quantifier source.
- `xs.every(...)`, `xs.some(...)`, `xs.any(...)`, `Name.all()` and every other
  method keep their dispatch, results and errors.

## Reference Implementation

- `src/lang/ast/mod.rs` adds `Expr::Quantified { quantifier, binder,
  collection, condition }`, the `Quantifier` enum with `All` and `Any`,
  `Quantifier::starting`, which holds the three-token recognition rule shared
  by the parser and the REPL, `Ast::Quantified`, and quantifier support in
  `contains_reasoning`.
- `src/lang/ast/quantified.rs` evaluates a quantifier.
  `Runtime::evaluate_quantified` evaluates the collection once, reads a class
  through the existing `population`, which records the population dependency,
  and tests each member in a pushed scope frame, stopping at the deciding
  member.
- `src/lang/ast/parser.rs` recognizes the prefix in `primary` outside a
  template interpolation, parses the collection as a clause expression and the
  condition in the inherited context, and pairs a top-level quantifier's colon
  in `has_direct_condition_suite`. A unit test covers the lookahead.
- `src/lang/ast/generator.rs` renders the grouped canonical form.
- `src/expression.rs` visits the collection and condition and removes the
  binder from the condition's roots, so class-rule validation and block
  analysis treat it as bound. `src/nuc/expression.rs` freezes `.value` in the
  collection only.
- `src/main.rs` pairs a top-level quantifier's colon in the native REPL's
  colon-free header scan through `Quantifier::starting`; a unit test covers it.
- `tests/common/assertions.rs` visits the collection and condition when it
  collects protected assertions.
- `tests/quantifiers.rs` covers the appended document cases and their
  assertion counts, the AST and canonical rendering and its round trip,
  precedence in every expression position, template interpolations, every
  accepted reading of `all` and `any`, `parse_expression`, parity with
  `every` and `some` in results, dependencies and structural subscriptions

  evaluation of the collection, short-circuiting and visited dependencies,
  null settling, non-collection errors, lexical binders, statement headers,
