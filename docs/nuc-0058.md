# NUC 58 -- In-Place List Sorting

```
NUC: 58
Title: In-Place List Sorting
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Utility enhancement
Created: 29-Oct-2026
Requires: 8, 53
```

## Abstract

- `list.sort()` and `list.sort(comparator)` reorder a writable receiver in
  place, as JavaScript's `Array.prototype.sort` does, and return the sorted
  list.
- This deliberately changes, at the user's request, the accepted runtime
  meaning of one existing form: `sort` on a writable receiver returned a
  sorted copy and left the receiver unchanged. The sorted list is now written
  back, versioned and propagated like the results of `push`, `pop` and
  `shift`.
- Receivers without a writable list place keep their accepted results: list
  literals, call, operator and pipeline results such as
  `scores.slice().sort()`, indexes such as `grid[0]`, `.value` snapshots,
  selected state versions and class populations still return a sorted copy
  and write nothing.
- Parsing, the ordering algorithm, every other list method, `push`, `pop`,
  `shift`, error types and messages are unchanged.
- The authoritative contract is
  [In-place list sorting](../nucleoid.spec.md#in-place-list-sorting).

## Motivation

- The user asked to "make sort mutate the list in place like JavaScript".
  This is a direct request for one concrete feature, prepared in
  single-proposal mode.
- Nucleoid aims to be a superset of Python, JavaScript/TypeScript, Kotlin,
  Go, Rust, Java, C# and C/C++. JavaScript's `array.sort()`, Python's
  `list.sort()`, Kotlin's `MutableList.sort()`, Java's `List.sort`, C#'s
  `List<T>.Sort()`, Go's `slices.Sort`, Rust's `slice::sort` and C++'s
  `std::sort` all reorder the receiver itself.
- Today `scores.sort((a, b) => a - b)` written as a statement is a silent
  no-op: the sorted copy is discarded and `scores` keeps its order. Programs
  written in any of those styles, including LLM-written ones, then read an
  unsorted list.
- Accepted programs that use the result of a copy, such as
  `ranked = scores.slice().sort((a, b) => a - b)` and
  `assert([3, 1, 2].sort()[0], 1)`, keep their results, so no accepted case
  needs a rewrite.
- In-place sorting composes with the dependency graph: a sort inside a
  declaration keeps its list sorted as the list, the comparator or anything
  the comparator reads changes.

## Rationale

- **Reuse the mutating-method write path.** `sort` joins `push`, `pop` and
  `shift` in `call_list_method` and writes through the same `write_list`
  route. Variable and property writes, versions, dependents, propagation,
  transactions and rollback are inherited unchanged.
- **The same writable receivers as `push`.** Variables, parameter and loop
  bindings, members of objects (through a name, `this`, `self`, `$Class` or
  a call result), and properties of an object selected through a state
  version. Nothing else is a list place.
- **Read the receiver once.** For a member receiver, `sort` evaluates the
  object once and writes the resolved property, as version-derived receivers
  already do. `pick().entries.sort()` calls `pick` once, and the declaration
  `snapshot = scores.value.sort()` stays a frozen snapshot.
- Rejected: writing back by evaluating the receiver expression again, as
  `push`, `pop` and `shift` do. It would call `pick` twice and make the
  `.value` declaration above depend on `scores`, changing accepted results.
  Those three methods keep their receiver evaluation; changing it is outside
  this request.
- **Ordering is unchanged.** The comparator path stays the accepted stable
  insertion sort, making the same comparator calls in the same order. The
  default path stays a stable sort of string forms. It matches JavaScript's
  default order wherever both render items as the same text, such as
  integers below `1e21` and ASCII strings; JavaScript renders `1e21` and
  `1e-7` with exponents, Nucleoid without.
- Rejected: a merge sort or a `sort_by` adapter, which would change the
  comparator call order and the result of inconsistent comparators.
- **Non-function arguments stay ignored.** Accepted programs such as
  `values.sort(null)` keep the default order. Rejected: JavaScript's
  `TypeError` for a non-function comparator, which the request does not need
  and which would break those programs.
- **Indexes keep returning copies.** `grid[0].sort()` and
  `record["items"].sort()` return the sorted list without writing, exactly
  as `grid[0].push(5)` writes nothing today. JavaScript would sort the nested
  array; widening index write-back for every mutating method belongs to its
  own proposal.
- **State versions are sorted as copies.** [NUC 53](nuc-0053.md) keeps
  read-only list queries available on selected versions and rejects
  mutable-list write-back into history. `values@first.sort()` was such a
  query. In-place sorting needs a place, and history is not one, so it keeps
  returning the sorted copy.
- Rejected: raising `TypeError("State versions are read-only")`, as `push`
  does and as JavaScript does for a frozen array. It would break accepted
  history reads that the request does not need to change.
- **Class populations keep their order.** A population is maintained by
  construction and deletion, has no stored list to write, and accepts no
  `push`, `pop` or `shift`. `Item.sort(comparator)` keeps returning sorted
  instances.
- Rejected: reordering the population, which would change `Item[0]`, loops
  and every class query, and would need population-order state, history and
  rollback.
- **Lists are values.** A parameter or loop binding holds a copy, so sorting
  it reorders that binding only, as `push` does. Reference semantics for
  lists is a language-wide change outside this request.
- **Standing sorts.** A declaration whose right-hand side mutates a list
  re-runs whenever what it reads changes, as `n = arr.push(2)` already does.
  For `sort` the re-run is the useful reading: `ranked = scores.sort(cmp)`
  keeps `scores` sorted. A statement never re-runs for its own write, so
  re-sorting does not loop, whatever the comparator returns.
- **Equal sorts still write.** Re-sorting an ordered list stores an equal
  list: no version is appended and, inside a cascade, nothing wakes. Outside
  a cascade the write re-runs dependents like any explicit write, as
  `values.pop()` on an empty list and `x = x` already do.
- Rejected: skipping equal writes, which would give `sort` a write rule of
  its own.
- **Replacement order is inherited.** While a replacing declaration's
  right-hand side runs, the replaced rule is still filed, so a new standing
  sort's write re-runs the old one once, exactly as a replaced
  `n = arr.push(2)` re-runs.
- Rejected: changing declaration replacement here. It applies to every write
  and belongs to its own proposal.
- **Category.** `sort` is a standard built-in collection helper, as in Draft
  [NUC 10](nuc-0010.md) and accepted [NUC 41](nuc-0041.md), so this is a
  Utility enhancement. The user's request fixed it; there was no random draw.
- **Single-proposal mode.** Token comparison is skipped. No accepted case is
  rewritten; seven specification entries and one reference entry are
  appended.

## Specification

### Ordering

- A function argument is a comparator. Items are placed in input order, each
  before the first already placed item for which `comparator(item, placed)`
  converts to a number below zero. Equal items keep their order; a `NaN`,
  `true` or `false` result never places an item earlier.
- Without a function argument, including a non-function argument, items
  order stably by their string forms.
- The receiver is read once, before the arguments are evaluated. The complete
  order is computed before anything is written.

```
codes = [10, 9, 1]
codes.sort()
assert(codes, [1, 10, 9])
names = ["b", "a", "C"]
names.sort(null)
assert(names, ["C", "a", "b"])
people = [{ name: "a", age: 30 }, { name: "b", age: 20 }, { name: "c", age: 30 }, { name: "d", age: 20 }]
people.sort((x, y) => x.age - y.age)
assert(people.map(person => person.name), ["b", "d", "a", "c"])
```

### Writable receivers

- `sort` writes the sorted list back and returns it when the receiver is a
  variable, a parameter or loop binding, a member of an object, or a property
  of an object selected through a state version, by name or by index. These
  are exactly the receivers `push`, `pop` and `shift` write back to.
- Members of objects include members reached through a name, `this`, `self`,
  a class-level `$Class` receiver or a call result.
- A member receiver's object is evaluated once; the write never evaluates the
  receiver again, so `pick().entries.sort()` calls `pick` once.
- A variable or property write appends a version only when the order
  changes, and re-runs the receiver's dependents.
- An equal list written outside a propagation cascade still re-runs them,
  like any explicit write; inside a cascade it wakes nothing.
- Lists are values: sorting a parameter or loop binding reorders that binding
  only, and the list it was copied from is unchanged.

```
scores = [30, 10, 20]
first = scores[0]
scores.sort((a, b) => a - b)
assert(scores, [10, 20, 30])
assert(first, 10)
assert(scores.sort((a, b) => b - a), [30, 20, 10])
assert(scores, [30, 20, 10])
assert(first, 30)
```

```
board = { entries: [3, 1, 2] }
board.entries.sort((a, b) => b - a)
assert(board.entries, [3, 2, 1])
class Team:
    def init(scores) => this.scores = scores
    def ranked() => self.scores.sort((a, b) => b - a)
team = Team([2, 9, 4])
assert(team.ranked(), [9, 4, 2])
assert(team.scores, [9, 4, 2])
```

### Receivers without a list place

- List literals, call, operator and pipeline results, other indexes such as
  `grid[0]` and `record["items"]`, `.value` snapshots, selected state versions
  and class populations return the sorted list and write nothing, exactly as
  before.
- A class population keeps its creation order.
- `push`, `pop` and `shift` keep writing nothing through those indexes, and
  keep raising `TypeError("State versions are read-only")` on a selected
  version.

```
scores = [30, 10, 20]
ranked = scores.slice().sort((a, b) => a - b)
assert(ranked, [10, 20, 30])
assert(scores, [30, 10, 20])
assert([3, 1, 2].sort(), [1, 2, 3])
grid = [[3, 1], [2, 0]]
assert(grid[0].sort(), [1, 3])
assert(grid, [[3, 1], [2, 0]])
scores = [5, 4]
oldest = scores@first.sort()
assert(oldest, [10, 20, 30])
assert(scores@first, [30, 10, 20])
```

### Standing sorts

- A `sort` in a declaration is a standing sort. It sorts its list in place and
  re-runs whenever the list, the comparator or anything the comparator reads
  changes, including a reassignment of the list.
- A statement never re-runs for its own write, so re-sorting does not loop,
  whatever the comparator returns.
- `scores = scores.sort()` reads its own target, so it sorts once.
- Two standing sorts of one list with different orders re-run each other: a
  later change to that list raises `TypeError("Propagation did not settle")`
  and rolls back.
- Replacing a standing sort keeps the accepted replacement order: the
  replacement's write re-runs the replaced rule once, so the list keeps the
  replaced order until it next changes.

```
class Player(name, score):
    this.name = name
    this.score = score
alice = Player("alice", 30)
bob = Player("bob", 10)
cara = Player("cara", 20)
players = [alice, bob, cara]
direction = 1
ranked = players.sort((a, b) => (a.score - b.score) * direction)
names = players.map(player => player.name)
assert(names, ["bob", "cara", "alice"])
dave = Player("dave", 5)
players.push(dave)
assert(names, ["dave", "bob", "cara", "alice"])
bob.score = 40
assert(names, ["dave", "cara", "alice", "bob"])
direction = -1
assert(names, ["bob", "alice", "cara", "dave"])
```

### Transactions

- A comparator error leaves the receiver unchanged and propagates through the
  existing transaction.
- A failed run or a caught savepoint restores the list, its history and its
  dependents.

```
scores = [3, 1, 2]
failure = ""
try:
    scores.sort((a, b) => a - b)
    throw "SORT_ROLLBACK"
catch error:
    failure = error
assert(failure, "SORT_ROLLBACK")
assert(scores, [3, 1, 2])
assert(scores@1, null)
```

### Compatibility

- Parsing, the AST, canonical rendering and graph keys are unchanged; `sort`
  is still an ordinary method name. A class method named `sort`, an object
  property holding a `sort` function, and `sort` on a string keep their
  accepted dispatch and results.
- Every accepted case keeps its source, assertions and expected return. The
  accepted uses `assert([3, 1, 2].sort()[0], 1)` and
  `ranked = scores.slice().sort((a, b) => a - b)` sort a literal and a call
  result, so their results are unchanged.
- Draft [NUC 10](nuc-0010.md) lists `sort` among the list functions that only
  depend on the list. This NUC moves `sort` on a writable receiver beside
  `push` and `pop`; NUC 10's copy example keeps its meaning, and NUC 10 itself
  is not revised here.
- Draft [NUC 11](nuc-0011.md) says `sort` over a selection returns a
  selection, which still holds. A selection held by a variable or property is
  a writable list and is now reordered until its rule re-derives; a pipeline
  result such as `(c |> why).sort(byNode)` is not written.
- These deliberate result changes are limited to writable receivers:

| Program | Accepted result | Result under this NUC |
| --- | --- | --- |
| `scores = [3, 1, 2]`, `scores.sort()`, `scores` | `[3,1,2]` | `[1,2,3]` |
| `board = { entries: [3, 1, 2] }`, `board.entries.sort()`, `board.entries` | `[3,1,2]` | `[1,2,3]` |
| `def ordered(values)` that runs `values.sort()` and returns `values`, called on `[3, 1, 2]` | `[3,1,2]` | `[1,2,3]` |
| `scores = [3, 1, 2]`, `ranked = scores.sort()`, `scores.push(0)`, `scores` | `[3,1,2,0]` | `[0,1,2,3]` |
| `holder = { items: [3, 1, 2] }`, `holder.items = [5, 4]`, `holder@first.items.sort()`, `holder.items` | `[5,4]` | `[4,5]` |
| `scores = [3, 1, 2]`, `scores.sort()`, `scores@1` | `null` | `[1,2,3]` |

## Errors

- No new error type, message or diagnostic is added.

| Condition | Error |
| --- | --- |
| A comparator throws or fails | The comparator's own error or thrown value, unchanged; the receiver keeps its order and the transaction rolls back |
| Two standing sorts of one list with different orders, after a change to that list | `TypeError("Propagation did not settle")` |
| `$Squad.scores = $Squad.scores.sort()` | `TypeError("Circular Dependency")`, unchanged |
| `"cba".sort()` | `TypeError("cba.sort is not a function")`, unchanged |
| `push`, `pop` or `shift` on a selected version | `TypeError("State versions are read-only")`, unchanged |

- `sort` on a selected version raises nothing; it returns the sorted copy.
- A null or undefined receiver keeps returning undefined without evaluating
  the arguments, as before.

## Reference Implementation

- `src/lang/ast/array.rs`:
  - `call_list_method` gains a `sort` arm beside `push`, `pop` and `shift`.
    It evaluates the arguments, orders the receiver snapshot with
    `sort_items`, writes back through `write_list` unless the receiver is
    history or detached, and returns the sorted list.
  - `sort_items` holds the unchanged insertion and string-form orderings;
    the string-form path renders each item once, with the same stable order.
    `list_query` keeps using it for class populations, whose `sort` stays a
    read-only query.
  - `VersionListTarget` becomes `ListTarget`, which adds `Detached` for
    `.value` snapshots and members of anything that is not an object.
  - `sort_receiver` and `version_list_receiver` share `member_list_receiver`,
    which evaluates a member receiver's object once and resolves the
    property to write. Any other owner resolves to `Detached` for `sort` and
    to `ReadOnly` for versions, as before.
- `src/lang/ast/call.rs`: `call_method` resolves non-version `sort` receivers
  through `sort_receiver`.
- `tests/in_place_sort.rs` covers the appended document cases and their
  assertion counts, writable and detached receivers, single receiver reads,
  unchanged `push`, `pop` and `shift` receivers and errors, comparator call
  order, default-order ties, inconsistent comparators, standing sorts and
  their dependencies, equal writes inside and outside a cascade, class
  populations and class rules, parameters and loop bindings, rollback, the
  non-settling conflict and the inherited replacement order.
- The root specification, executable reference, consolidated reference, a
  new canonical `dataset/nucleoid.synth.38.jsonl`, the specification export,
  the generated specification tests and the dataset record counts are
  synchronized in the isolated candidate. `README.md` and
  `docs/examples.md` have no affected `nuc` block.
- No public Rust API, dependency, MSRV or project version changes. The
  observable change to `sort` on writable receivers needs human SemVer
  review before publication.

## Evaluation

- Accepted in single-proposal mode under the user-requested proposal rule in
  `.claude/rules/proposals.instructions.md`, against accepted language
  revision `7066b1bbc83eb45760d5566bdb280396a69c6210` and its immutable
  697-case accepted-corpus baseline. The candidate was integrated unchanged.
- Evaluated proposal Git blob:
  `793fe7477d637b647d8b95c4511413ccb536a5d9`, before this outcome metadata.
- The independent evaluator's overall decision was `Rejected`, on syntax
  compatibility: `sort` on a writable receiver changes the runtime meaning
  of accepted programs as a replacement, not an additive, optional form. The
  user-requested rule accepts the NUC regardless, because the frozen
  candidate compiles and passes every existing and new test.
- The evaluator's reproductions, run on the accepted and candidate binaries:
  - `scores = [30, 10, 20]`, `top = scores.sort((a, b) => b - a)[0]`,
    `assert(scores, [30, 10, 20])` passes at the accepted revision; here
    `scores` is reordered and the assertion fails.
  - `scores = [2, 1]`, `up = scores.sort((a, b) => a - b)`,
    `down = scores.sort((a, b) => b - a)`, `scores = [1, 3]` returns
    normally at the accepted revision; here it raises
    `TypeError("Propagation did not settle")` and rolls back.
  - A function that sorts a global list now reorders the global,
    `$Squad.best = $Squad.scores.sort(...)[0]` reorders every instance's
    `scores`, and a deferred `r = holder.items.sort()` sorts `holder.items`
    once it is assigned.
