# NUC 97 -- In and Not In Membership Tests

```
NUC: 97
Title: In and Not In Membership Tests
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 09-Nov-2026
```

## Abstract

- Adds the membership tests `A in B` and `A not in B`. `x in xs` is
  `xs.includes(x)`, three lexer tokens instead of six, and `x not in xs` is
  `!xs.includes(x)`, four instead of seven.
- The right operand is a list, a class population or a string, the values
  whose `includes` tests membership: a list or population holds an item equal
  to `A` under the deep equality `includes` uses, and a string holds the text
  of `A`.
- A null or undefined right operand yields undefined in both forms, which a
  declaration stores as `null`, as a quantifier over a null collection does:
  declarations store a pending result as `null`, so a rule over a list that
  is not yet set waits for it, and `not in` never reads `true` from it.
- Any other right operand raises
  `TypeError("<collection> is not a collection")`, the error of a quantifier
  over a value that is not a collection, where `includes` returns
  `undefined` for an object. A silent `undefined` would make
  `"a" not in {a: 1}` read `true`, and no later NUC could change that
  accepted result, so key membership on objects stays open.
- A membership test stands with `<`, `<=`, `>` and `>=`: it binds tighter
  than `==`, `is`, `&&`, `and`, `||`, `or` and `??`, and looser than
  arithmetic. It stays live as `includes` does, so `known = "green" in tags`
  follows `tags`.
- Only inputs that were errors at the accepted revision change. A template
  interpolation such as `` `${x in xs}` `` keeps ignoring its trailing tokens
  and reading `x`, the class of break that rejected [NUC 91](nuc-0091.md),
  and so does the public Rust `parse_expression`, so
  `parse_expression("x in xs")` still returns `x`. The only other inputs
  whose result it changes are Python-style conditionals whose condition
  holds a membership test, as NUC 62 and NUC 75 changed it; see
  [Compatibility](#compatibility).
- Outside a clause, `in` directly before a collection and `:` keeps its
  accepted reading, so malformed quantifiers such as `ok = all 1 in xs: v`
  keep `SyntaxError("Unexpected keyword 'in'")`.
- The public `BinaryOp` enum gains `In` and `NotIn`, which needs a human
  SemVer decision; no version is changed. No token or keyword is added, and
  no error message that a program can reach: only the public Rust function
  `binary`, which has no runtime, gains a message for the two operators, as
  [Errors](#errors) lists. The authoritative contract is
  [Membership tests](../nucleoid.spec.md#membership-tests).

## Motivation

- Membership is the everyday test of a rule: a status among the allowed
  ones, a color in a palette, a point in a figure. Accepted Nucleoid spells
  it `xs.includes(x)`, which names the collection before the item and costs
  six lexer tokens, or seven with `!` for the negation.
- `x in xs` and `x not in xs` are Python's spellings, and `in` is also an
  operator of JavaScript and SQL, so language models write them in
  conditions and rules. At the accepted revision each is a syntax error that
  stops the whole program before any statement runs: `x in xs` raises
  `SyntaxError("Unexpected keyword 'in'")`, and
  `if color in ["red", "blue"]:` raises
  `SyntaxError("Expected ':' but found keyword 'in'")`.
- The accepted ARC instruction datasets already test membership in their
  world-model rules, all through `includes`:
  `pair.includes($Obj.color@first)` in `0d3d703e`,
  `$Obj.points.includes([canvas_width - 1 - point[0], point[1]])` in
  `44f52bb0` and `figure.holes.includes(hole)` in `fafffa47`. Written as
  `hole in figure.holes`, a rule reads in the order it is said.
- `in` is already a reserved word. Outside template interpolations, which
  ignore their trailing tokens, the accepted grammar reads it only after the
  loop name of `for`, the bound name of a quantifier and the name of a
  comprehension, and as a property after `.`. An infix `in` is therefore
  new syntax, not a new meaning for accepted source.
- [NUC 64](nuc-0064.md) listed `in` and `not in` among the forms it did not
  add, and [NUC 95](nuc-0095.md) notes that accepted Nucleoid has no `in`
  operator.

## Rationale

- **Category and mode.** The confirmed category is Syntax enhancement, from
  one uniform draw over the five categories that NUC 1 marks eligible for
  automatic selection, index 0 with probability 1/5 and no redraw, in the
  continuous cycle that allocated this NUC. The user resumed it by number,
  so it is a single-proposal, user-requested NUC: token comparison is
  skipped as `single_proposal`, and the new cases need no accepted-syntax
  counterparts. Runtime applicability does not apply. No hint was supplied.
  Strategy learning is `not_configured`, so this trial is unattributed, and
  advisory usefulness is unscored (`missing_rubric`), not zero.
- **Two operators, not a lowering to `includes`.** `A in B` builds
  `Expr::Binary` with the new `BinaryOp::In`, and `A not in B` with
  `BinaryOp::NotIn`. Every generic path over binary nodes then applies
  unchanged: dependency walks, `.value` freezing, class-level rule
  validation and cycle checks, reasoning, the protected-assertion walker and
  rendering. Rejected:
  - lowering to the call `B.includes(A)`, which returns `undefined` for an
    object or `null`, so `!B.includes(A)` reads `true`; it would also share
    the call's graph key and its dispatch, where a class named `Math` reaches
    the built-in namespace;
  - a new `Expr` variant, which every exhaustive match over the public enum
    would need, while catch-all arms such as the `.value` freezer would
    silently skip it;
  - a `negated` flag, which the Rust guidelines replace with a dedicated
    variant.
- **The comparison of `includes`.** Lists and populations are searched by
  `Runtime::holds`, which `includes` now calls too, and strings by
  `builtins::string_contains`, which the string `includes` query now calls.
  Both were factored out of the accepted search, so the two spellings
  cannot drift apart.
- **Null and undefined collections wait.** The allocation first proposed a
  `TypeError` for `null` as well. Declarations store a pending result as
  `null`, so a rule chain such as `$Item.tags = $Item.raw.split(",")`
  followed by `$Item.hot = "red" in $Item.tags` would fail every instance
  whose `raw` is not yet set, where `includes` and quantifiers wait. Both
  forms therefore yield undefined for a null or undefined collection, as a
  quantifier does, and `not in` does not read `true` there. Every other
  value keeps the allocation's `TypeError`, so key membership in objects
  stays open.
- **The error of quantifiers.** The `TypeError` reuses the quantifier's
  `<collection> is not a collection`, naming the collection's path or
  canonical source through one shared constructor, so no error message that
  a program can reach is added. A string is not a collection for a
  quantifier, but it holds text, so membership accepts it as `includes`
  does.
- **The level of `<`.** As requested, both forms join the left-associative
  level of `<`, `<=`, `>` and `>=`, below arithmetic and above `==` and
  `is`, as JavaScript places `in`. Python puts every comparison on one level
  and chains them; Nucleoid already keeps `==` and `is` below `<`, and
  chaining would give `a < b < c` a new meaning. `not` stays the prefix it
  is for `<`, so `not x in xs` is `(not x) in xs`, as `not x < y` is
  `(not x) < y`. Rejected: Python's lower `not` for `in` alone, which would
  make `not x in xs` and `not x < y` group differently; `x not in xs` is the
  negated test.
- **Left to right.** `A` is evaluated before `B`, as for every binary
  operator, while `B.includes(A)` evaluates its receiver first. Only side
  effects, the first of two errors and the order of the reads that `why`
  lists can show the difference; the reads themselves are the same.
- **No retry pass.** `in` is a reserved word, and no accepted construct
  reads it after a complete operand, so a membership test changes only
  inputs that failed to parse. Unlike the `is` comparisons of
  [NUC 86](nuc-0086.md), which read an ordinary identifier, it needs no
  accepted-first retry. The exceptions are the two places whose trailing
  tokens are ignored: the top level of a template interpolation, whose
  ignored `++` rejected NUC 91, and the top level of `parse_expression`,
  whose ignored `in` is pinned by `tests/list_comprehensions.rs` and
  `tests/quantifiers.rs`. A private `ExpressionContext::Standalone` keeps
  the second; it behaves as `Ordinary` in every other respect, so
  `parse_expression` still reads quantifiers, noun queries, lambdas and
  Python-style conditionals.
- **The quantifier colon.** `tests/quantifiers.rs` and
  `tests/universal_claims.rs` pin `SyntaxError("Unexpected keyword 'in'")`
  for seven malformed quantifiers, such as `ok = all 1 in xs: v` and
  `ok = every (v) in xs: v`, where a binder that is not a name leaves `in`
  after an operand. Outside a clause, a colon directly after a membership
  test's right operand can only close such a quantifier: no statement or
  value continues with it. So the parser reads the right operand, sees the
  colon and returns to the `in`, and the accepted error follows. It follows
  [NUC 98](nuc-0098.md), whose `every NAME` is not a class reference when a
  colon follows outside a clause. The step back happens only on input that
  then fails, so no successful parse reads an operand twice. Rejected:
  refusing `in` after the words `all`, `any` and `every`, which misses
  `all (v) in` and ties the operator to quantifier spellings.
- **Tentative conditions.** A Python-style conditional is tentative, and
  `parse_expression` ignores what follows its leading expression, so
  `parse_expression("a if x in xs else b")` returned `a`: its condition
  failed at `in`. It now returns the conditional, or the error of what
  follows `else` when that is not an expression. A program cannot observe
  this, because its statement parser then read `if` as a statement and
  failed at the same `in`. Keeping the old result would mean refusing
  membership tests in every construct nested in `parse_expression`, so the
  change is recorded instead, as NUC 62 and NUC 75 recorded theirs.
- **Grouped rendering.** Both forms render grouped, `(A in B)` and
  `(A not in B)`, as word comparisons and quantifiers do, so an enclosing
  operator cannot absorb them in a graph key or `rule` text, and `if` rules
  over the two spellings stay distinct nodes. The power-grouping helpers
  treat them as already grouped.
- **Where the cases stand.** `tests/universal_claims.rs` requires NUC 98's
  entries to end each executable document. The new entries therefore stand
  directly before them, which moves NUC 98's five records in the positional
  specification export from `spec-0722`–`spec-0726` to
  `spec-0727`–`spec-0731` with unchanged descriptions, code and returns, and
  their generated tests keep their names. Rejected: appending after them,
  which would edit that existing assertion.
- **Not added.** Key membership in objects, chained comparisons, `is in`,
  word readings of the operands, and any change to `includes`.

## Specification

- The normative contract is
  [Membership tests](../nucleoid.spec.md#membership-tests).

### Syntax

- `ITEM in COLLECTION` and `ITEM not in COLLECTION`, where `not in` is the
  keyword `not` directly followed by the keyword `in`. Both stand on the
  left-associative level of `<`, `<=`, `>` and `>=` and share its chain
  limit of 128 operators.
- They bind more tightly than `==`, `!=`, `===`, `!==`, `is`, `is not`,
  `and`, `&&`, `or`, `||`, `??`, `|>`, both conditional forms and
  assignment, and more loosely than `+`, `-`, `*`, `/`, `%`, `**` and every
  prefix operator, including `not`, `!`, `-`, `typeof`, noun queries and
  prefix stages:

| Source | Reads as |
| --- | --- |
| `x + 1 in xs` | `(x + 1) in xs` |
| `x in xs == true` | `(x in xs) == true` |
| `a < b in c` | `(a < b) in c` |
| `a in b in c` | `(a in b) in c` |
| `x in xs and y not in ys` | `(x in xs) and (y not in ys)` |
| `not x in xs` | `(not x) in xs` |
| `x in why c` | `x in (why c)` |
| `(a is b in c)` | `(a is (b in c))` |

- They apply wherever the accepted grammar reads a comparison, apart from
  the top level of a template interpolation and of the `parse_expression`
  input, whose trailing tokens are ignored and where `in` stays the first
  ignored token. Inside parentheses, brackets, braces, arguments and
  clauses there, they apply.
- Outside a clause, they are not formed when `:` directly follows the right
  operand; `in` then keeps its accepted reading. The clauses are statement
  headers, `suppose` premises, subscript starts, the consequent after `?`,
  Python-style conditions and quantifier collections.
- `in` keeps every other reading: `for NAME in`, `for KEY, VALUE in`, list
  comprehensions, the quantifiers `all`, `any` and `every NAME in`, and a
  property after `.`.

### Semantics

- `ITEM` is evaluated first, then `COLLECTION`.
- A list, including a reasoning selection, holds `ITEM` when an item
  matches it under the deep equality of `includes`. A declared class holds
  `ITEM` when one of its instances does, as `Name.includes(ITEM)` compares.
  A string holds `ITEM` when the text of `ITEM` occurs in it.
- `in` yields `true` or `false`, and `not in` the opposite. Over these
  collections the results equal those of `COLLECTION.includes(ITEM)` and
  `!COLLECTION.includes(ITEM)`, except that a declared class named `Math`,
  `Number`, `String` or `Date` holds its instances, while its `includes`
  call reaches the built-in namespace of that name and raises a
  `TypeError`.
- A null or undefined collection yields undefined in both forms, which a
  declaration stores as `null`.
- Any other collection raises
  `TypeError("<collection> is not a collection")`.
- A declaration, `if` rule or class-level rule depends on what both
  operands read, including the population of a class, but not on the
  properties of compared objects. `.value`, class-level validation, null
  settling and rollback follow the rules of every operator.

```
tags = ["red"]
known = "green" in tags
missing = "green" not in tags
assert([known, missing], [false, true])
tags.push("green")
assert([known, missing], [true, false])
class Order(status):
    this.status = status
$Order.open = $Order.status in ["new", "paid"]
first = Order("new")
second = Order("shipped")
assert([first.open, second.open], [true, false])
```

### Rendering

| Source | Rendering |
| --- | --- |
| `ok = x in xs` | `ok=(x in xs)` |
| `ok = x not in xs` | `ok=(x not in xs)` |
| `ok = not (x in xs)` | `ok=!(x in xs)` |
| `ok = a < b in c` | `ok=(a<b in c)` |
| `ok = (a in b) ** 2` | `ok=(a in b)**2` |
| `if "b" not in tags:` | the `if` node `if(("b" not in tags))` |

### Compatibility

- **Programs.** At the accepted revision, `in`, or `not` and `in`, directly
  after a complete operand is always a syntax error outside the top level
  of a template interpolation, which ignores it and still does. Only such
  inputs change: they now parse, or report the diagnostic where the parser
  now stops, as Errors lists. Every other program keeps its tree,
  positions, rendering, result, errors, JSON, graph and REPL behavior. The
  REPL buffers a colon-free `if x in xs` header for its indented body as
  before, and the submitted input now parses.
- **`parse_expression`.** It keeps every accepted result, including `x` for
  `x in xs`, `x not in xs` and `x in xs: v`, and `all` for `all in xs`,
  except for a Python-style conditional whose condition holds a membership
  test. It returned the consequent, as `a` for `a if x in xs else b`, and
  now returns the conditional, or the error of what follows `else` when
  that is not an expression: `A if c in q else (B` raises
  `SyntaxError("Expected ')' but found end of input")` at line 1,
  column 20. Inputs on which it failed, because a nested construct such as
  `(x in xs)` held the test, now parse.
- **Tests.** No existing assertion, pinned diagnostic or case byte changes.
  The seven pinned `Unexpected keyword 'in'` diagnostics of
  `tests/quantifiers.rs` and `tests/universal_claims.rs`, the
  `parse_expression` tails of `tests/list_comprehensions.rs` and
  `tests/quantifiers.rs`, and the requirement of `tests/universal_claims.rs`
  that NUC 98's entries end each document hold unchanged. Count-only pins
  follow the eight added document cases: the specification record count of
  `tests/dataset.rs`, from 726 to 731, the document case totals of 13 corpus
  suites, from 1,052 to 1,060, and the programs without spread entries in
  `tests/object_spread_entries.rs`, from 1,041 to 1,049.
- **Exports.** The positional specification export gives the five new
  records `spec-0722`–`spec-0726` and moves NUC 98's five records to
  `spec-0727`–`spec-0731`. All 726 accepted records keep their
  descriptions, code and returns, and every generated test keeps its name.
- **Public API.** The public `BinaryOp` enum, which is not
  `#[non_exhaustive]`, gains `In` and `NotIn`, so exhaustive downstream
  matches stop compiling. The public `binary` function returns
  `TypeError("'in' needs the runtime's state")` or the `not in` equivalent
  for them, because populations and object equality need the runtime; the
  runtime never calls it with them. This needs human SemVer review; no
  version number is changed.

## Errors

- No error type is added, and no message that a program can reach. A
  collection that is neither null, undefined, a list, a string nor a
  declared class raises the quantifier's `TypeError`, at the start of the
  statement that runs:

| Exact source | Error |
| --- | --- |
| `count = 5`, then `1 in count` | `TypeError("count is not a collection")`, line 2, column 1 |
| `record = {a: 1}`, then `"a" not in record` | `TypeError("record is not a collection")`, line 2, column 1 |
| `"a" in {a: 1}` | `TypeError("{\"a\":1} is not a collection")`, line 1, column 1 |
| `1 in Math` | `TypeError("Math is not a collection")`, line 1, column 1 |
| `class Order`, `$Order.ok = 1 in $Order`, then `order = Order()` | `TypeError("Order is not a collection")`, line 3, column 1 |
| `items = [1]`, `present = 1 in items`, then `items = 7` | `TypeError("items is not a collection")`, line 3, column 1, and `items` stays `[1]` |

- Malformed membership tests report the existing diagnostics where the
  parser stops:

| Exact source | Error |
| --- | --- |
| `ok = x in` | `SyntaxError("Unexpected end of input")`, line 1, column 10 |
| `ok = x in` and a newline | `SyntaxError("Unexpected end of line")`, line 2, column 1 |
| `ok = x not in` | `SyntaxError("Unexpected end of input")`, line 1, column 14 |
| `ok = (x in )` | `SyntaxError("Unexpected ')'")`, line 1, column 13 |
| `ok = [x in ]` | `SyntaxError("Unexpected ']'")`, line 1, column 13 |
| `ok = x in in xs` | `SyntaxError("Unexpected keyword 'in'")`, line 1, column 14 |
| `if x in:` | `SyntaxError("Unexpected ':'")`, line 1, column 9 |

- These keep their accepted errors, at their accepted positions, because a
  colon follows the right operand outside a clause:

| Exact source | Error |
| --- | --- |
| `ok = all 1 in xs: v` | `SyntaxError("Unexpected keyword 'in'")`, line 1, column 15 |
| `ok = all (v) in xs: v` | `SyntaxError("Unexpected keyword 'in'")`, line 1, column 17 |
| `ok = all this in xs: 1` | `SyntaxError("Unexpected keyword 'in'")`, line 1, column 18 |
| `every all v in xs: v` | `SyntaxError("Unexpected keyword 'in'")`, line 1, column 16 |
| `ok = every (v) in xs: v` | `SyntaxError("Unexpected keyword 'in'")`, line 1, column 19 |
| `ok = x not in xs: v` | `SyntaxError("Unexpected keyword 'in'")`, line 1, column 15 |
| `ok = {a: 1 in xs: 2}` | `SyntaxError("Expected '}' but found keyword 'in'")`, line 1, column 12 |

- The public Rust function `lang::ast::operator::binary`, which has no
  runtime, returns `TypeError("'in' needs the runtime's state")` and
  `TypeError("'not in' needs the runtime's state")`, without a position,
  for the two operators and any operands, including a list or string that
  holds the item and undefined. These are its only new messages, and no
  program reaches them: the runtime evaluates both operators itself.

## Reference Implementation

- No token, keyword, `Expr`, `Stmt` or `UnaryOp` variant, option, flag or
  dependency is added, and no error message that a program can reach. The
  public `BinaryOp` gains `In` and `NotIn`, and the public `binary` gains
  the two messages that Errors lists.
- `src/lang/ast/parser/precedence.rs`: `relational` takes `in` and
  `not in` through `membership`, which refuses them at the top level of an
  interpolation or a `parse_expression` input. After the right operand,
  `leaves_quantifier_colon` returns to the `in` when a colon follows outside
  a clause.
- `src/lang/ast/parser.rs`: the private `ExpressionContext::Standalone`,
  which `parse_expression` now passes instead of `Ordinary`.
- `src/lang/ast/operator.rs`: the spellings `in` and `not in`;
  `evaluate_binary` routes both operators to `membership`, which matches
  every `Value` variant explicitly, and `binary` returns its error for them.

### Findings

- **Low, `parse_expression`.** The public Rust function returns another
  result for some inputs it accepted: Python-style conditionals whose
  condition holds a membership test. Some successes become errors:
  `A if c in q else (B` returned `A` and now raises
  `SyntaxError("Expected ')' but found end of input")` at line 1, column
  20. [Compatibility](#compatibility) documents it, no program can observe
  it, and NUC 62 and NUC 75 were accepted with the same kind of change.
- **Info, public API.** The exhaustive public `BinaryOp` gains `In` and
  `NotIn`, and the public `binary` returns
  `TypeError("'in' needs the runtime's state")` and its `'not in'`
  counterpart. No version changed; whether the change needs a
  semantic-versioning step is the version owner's call.
- **Info, interpolations.** `` `${x in xs}` `` still reads `x`, as
  documented, and `` `${(x in xs)}` `` gives the boolean.
- **Info, exports.** NUC 98's specification records move in the positional
  export, with their bodies and generated test names unchanged.
- **Pre-existing.** Ten `native_cli_*` tests write into
  `<CARGO_MANIFEST_DIR>/target/` and fail when that directory is missing;
  they pass at both revisions when it exists. A debug command line
  overflows its 1 MB stack at depths 47 to 54 for nested programs, at the
  same depth on both revisions for six nesting shapes, so the 64-byte frame
  growth of `relational` changes nothing observable.
