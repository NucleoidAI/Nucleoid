# NUC 9 -- Transactions and Error Handling

```
NUC: 9
Title: Transactions and Error Handling
Author: Can Mingir <canmingir@gmail.com>
Status: Draft
Type: Standards Track
Created: 31-Jul-2026
Requires: 1, 2, 3, 4, 5
```

## Abstract

- Specifies `throw`, transaction boundaries, rollback, and the complete error taxonomy.
- Every statement runs in a transaction: it takes effect entirely or not at all.
- A rule that throws rejects the change that triggered it, leaving the state as it was.

## Motivation

- A declarative rule can reject a change -- an invalid amount, an out-of-range reading, a password that is too short.
- If a rejected change left half its effects behind, the state would violate its own rules.
- Validation is therefore expressed as a rule that throws, and the runtime guarantees the change never lands.

## Rationale

- **A statement and everything it triggers form one transaction.** A rule fires because of an assignment, so its failure must undo that assignment. Otherwise a validation rule could not actually prevent anything.
- **Any value may be thrown.** Constants such as `'INVALID_SKU'` are the common case, and requiring an error object would add ceremony to the language's most common validation idiom.
- **Errors are typed and their messages are exact.** They are observable behaviour that programs branch on, so both type and text are part of the specification.

## Specification

### Throwing

- `throw` raises a value.
- The value may be a string, a number, or a variable or property reference.
- A reference is resolved before being thrown.

```
try:
    throw 'INVALID'
catch error:
    assert(error, "INVALID")
```

```
try:
    throw 123
catch error:
    assert(error, 123)
```

```
length = 0.1

if length < 1:
    throw length
```

- The thrown value is `0.1`.
- Quoting it instead throws the string `"length"`.
- A property may be thrown the same way.

### Transactions

- A statement and every rule it triggers run in one transaction.
- If anything throws, the whole transaction is rolled back.
- The state after a rollback is exactly the state before.

```
a = 5

if a > 5:
    throw 'INVALID_VALUE'
```

- Assigning `a = 6` throws `'INVALID_VALUE'`.
- Afterwards `a` is still `5`.

### Rollback of variables and their dependents

- Dependents are rolled back with the variable that triggered the failure.

```
limit = 10
double = limit * 2

if double > 40:
    throw "OVER_LIMIT"
```

- Assigning `limit = 25` throws.
- Afterwards `limit` is `10` and `double` is `20`.

### Rollback of properties

- A property assignment rejected by a rule leaves the property as it was.

```
class Item:
    pass

if $Item.sku == 'A':
    throw 'INVALID_SKU'

item1 = Item()
```

- Assigning `item1.sku = 'A'` throws `'INVALID_SKU'`.
- `item1.sku` is `null`.

- Related properties are rolled back together.

```
$Battery.percentage = $Battery.level * 100 / $Battery.capacity

if $Battery.percentage > 100:
    throw "INVALID_LEVEL"
```

- With capacity `50`, assigning `level = 75` throws.
- Both `level` and `percentage` keep their previous values.

### Rollback of instances

- An instance rejected at creation is not registered.
- Its variable name is not bound.

```
class User(first: str, last: str):
    this.first = first
    this.last = last

if $User.first.length < 3:
    throw 'INVALID_USER'
```

- `user1 = User('F', 'L')` throws `'INVALID_USER'`.
- `User.length` is `0`.
- Using `user1` raises `ReferenceError("user1 is not defined")`.

- The same holds for instances created in a loop: if a later iteration throws, earlier ones are rolled back too.

```
try:
    for item of Item:
        Label(item)
catch error:
    assert(error, "INVALID_ITEM")
```

- `Label.length` is `0`, even though the first iteration succeeded.

### Rollback of class-level rules

- A rule that throws for any existing instance is not installed at all.

```
reading1.celsius = 200

if $Reading.fahrenheit > 300:
    throw "OUT_OF_RANGE"
```

- Assigning `$Reading.fahrenheit = $Reading.celsius * 9 / 5 + 32` throws.
- `reading1.fahrenheit` is `null`.
- With `celsius` lowered to `100`, the same assignment succeeds and gives `212`.

### Rollback in blocks and functions

- A block is one transaction, including its nested blocks.
- A function that throws rolls back the assignment that called it.

```
{
    {
        if threshold > 100:
            throw "TOO_HIGH"
    }
}
```

- Assigning `threshold = 150` throws and leaves `threshold` at `50`.

```
def validate(n):
    if n < 0:
        throw "NEGATIVE"
    return n

checked = validate(value)
```

- With `value` `5`, `checked` is `5`.
- Assigning `value = -1` throws; `value` is `5` and `checked` is `5`.
- Assigning `value = 8` updates `checked` to `8`.

## Errors

The complete taxonomy. Messages are exact.

### ReferenceError

| Condition | Message |
| --- | --- |
| Reading an undefined variable | `<name> is not defined` |
| Throwing an undefined reference | `<name> is not defined` |
| Using a deleted variable or instance | `<name> is not defined` |
| Creating an instance of an undeclared type | `<Name> is not defined` |
| Writing through an undefined instance property | `<path> is not defined` |
| Writing through an undefined class-level reference | `<Name>.<property> is not defined` |
| Reading `.value` of an undefined property | `<path> is not defined` |
| Declaring a variable with no value | `Missing definition` |

### TypeError

| Condition | Message |
| --- | --- |
| An assignment that would close a dependency cycle | `Circular Dependency` |
| Deleting an instance that still has properties | `Cannot delete object '<id>'` |
| Using `value` as a property name | `Cannot use 'value' as a property` |
| Calling an unknown function of a built-in or list | `<Object>.<name> is not a function` |

### SyntaxError

| Condition | Message |
| --- | --- |
| Declaring a class-level rule in a non-class block | `Cannot define class declaration in non-class block` |
| A character that begins no token | `Unexpected character '<character>'` |
| A token other than the one required | `Expected <what> but found <what>` |
| A block or template that is never closed | `Unterminated block`, `Unterminated template expression` |

### Thrown values

- A `throw` raises the value itself, not an error object.
- Strings, numbers, and resolved references are all permitted.

### Limits

- Nesting and chain length are bounded, so that a program which would exhaust the
  machine is reported instead.
- A limit is reached before anything is applied, so the state is untouched.

| Condition | Message |
| --- | --- |
| Statements nested past the limit | `Statements are nested too deeply` (SyntaxError) |
| Expressions nested past the limit | `Expressions are nested too deeply` (SyntaxError) |
| One chain of operators with too many operands | `Expression has too many operands` (SyntaxError) |
| One expression with too many parts | `Expression has too many parts` (SyntaxError) |
| Evaluation or propagation nested past the limit | `Maximum statement depth exceeded`, `Maximum expression depth exceeded` (TypeError) |

- The limits are a property of the runtime rather than of the language, and a program
  written for people will not meet them.

### Where an error happened

- Every error records a line and column.
- A syntax error is placed at the token the parser stopped at.
- A runtime error is placed at the beginning of the top-level statement that was
  running, so a failure inside a block, a branch or a rule is reported against the
  statement that set it off rather than the line within it.
- The position is part of how an error is *reported*, not part of what it *is*.
- What a `catch` binds is `<Kind>: <message>` with no position, so a program can
  compare against it and keep working wherever the statement is written.

```
a = 1

t = e + 1
```

- Reported to whoever ran the program, this reads
  `ReferenceError: e is not defined (line 3, column 1)`.

```
try:
    t = e + 1
catch error:
    assert(error, ReferenceError("e is not defined"))
```

- The value bound to `error` is `"ReferenceError: e is not defined"`, with no position,
  which is what makes the comparison hold.
