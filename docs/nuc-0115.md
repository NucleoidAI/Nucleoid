
## Abstract

- `repeat COUNT:` followed by a suite, an indented block or statements on
  the same line separated by `;`, runs the suite `COUNT` times: `repeat 3:`
  runs its body three times and `repeat years:` once a year. It is the
  count-controlled sibling of [NUC 63](nuc-0063.md)'s `while CONDITION:`
  loop.
- `COUNT` is evaluated once, before the first iteration, and converted to a
  number and then as the count of the string method `repeat` converts it:
  fractions truncate, and NaN and negative numbers give 0. So `"3"` runs
  the body three times, `2.9` twice, and `null` or `-1` not at all. What the
  body changes does not change how many times it runs.
- The body runs as a `while` body does: in the enclosing scope, with no loop
  variable and no new scope frame, carried out rather than filed as
  standing rules. Each iteration's assignments, and the propagation they
  cause, are visible to the next. `return` leaves the enclosing function,
  errors and thrown values roll back through the existing transaction, and
  a completed loop yields `null` and files nothing in the graph.
- The bound of `while` keeps every loop finite: a count that converts to
  more than 100,000 raises `TypeError("Repeat count is too large")` before
  the first iteration.
- At the accepted revision every such statement is a `SyntaxError`, usually
  `SyntaxError("Unexpected ':'")` at its colon. No keyword or lexer token is
  added. `repeat` stays an ordinary name everywhere else, in variables,
  functions, `repeat(...)` calls and the string method `repeat`, and the
  four spellings that NUC 63 keeps for `while`, such as `repeat NAME: TYPE`,
  keep their accepted readings for `repeat`.
- The authoritative contract is
  [Count-controlled repeat loops](../nucleoid.spec.md#count-controlled-repeat-loops).

## Motivation

- World models often advance in steps: a simulation ticks its clock, a
  balance compounds once a year, a population grows each generation, and a
  constructor builds a fixed number of parts. Each runs a block a known
  number of times.
- The accepted spellings count by hand. A `while` loop needs its own
  counter, initialized, tested and incremented around the body, and leaves
  it behind: `i = 0`, `while i < years:` and `i = i + 1` are 15 lexer
  tokens with their newlines, where `repeat years:` is 3, and with
  `i += 1` they are still 13. A `while` loop that counts the count itself
  down, `while years:` with `years -= 1`, adds 4 tokens and destroys the
  count. A string loop turns the count into characters:
  `for _ of "a".repeat(years):` is 10 tokens, and `for _ of "aaa":` is 5
  for a literal count.
- The string loop is also wrong for local accumulators. A `for` loop pushes
  a scope frame for each iteration, and inside a function, method, loop or
  block body that frame turns a name the enclosing body already assigned
  into a local of the iteration, so `for _ of "a".repeat(k):` with the body
  `total = total + 1` leaves `total` at `0` there. Property writes, pushes,
  parameters and top-level names still work, but only a `while` loop with
  its own counter accumulates a local.
- Kotlin's `repeat(n)`, Logo's and Scratch's `repeat n`, Smalltalk's
  `timesRepeat:`, Ruby's `n.times` and Python's `for _ in range(n)` give the
  operation a name.
- Each of the seven new executable cases uses 4 to 13 fewer lexer tokens
  than the most compact fair accepted spelling found, one that runs any
  count the case could give its loops, and 2 to 6 fewer than every excluded
  spelling found, which hardcode a count, write the body out, recurse or
  rewrite other lines, as [Counterparts](#counterparts) records.

## Rationale

- **Category and mode.** The caller drew Runtime features with one
  tool-backed uniform draw over the five categories that NUC 1's registry
  marks eligible for automatic selection: index 1, with probability 1/5, at
  15:42:53 on 17-Nov-2026, and no redraw. This is a continuous cycle, so the
  token non-regression gate is required. Runtime applicability is
  `existing_comparable`: counted repetition is written today with a `while`
  loop and its own counter, with a `while` loop that counts a variable down,
  or with a string loop such as `for _ of "a".repeat(n):`, and every case of
  this proposal is paired with such an accepted-syntax program.
- **Selection.** Within the category the caller chose one bounded
  enhancement, `repeat COUNT:`, the count-controlled sibling of NUC 63's
  condition-controlled loop, which no NUC proposes. It set aside, after
  probing the accepted revision:
  - two-name loops over lists, `for i, x of xs:`, whose
    `TypeError("xs is not an object")` `tests/object_entry_loops.rs` pins;
  - receivers and parameters read by lambdas inside methods and functions,
    whose `ReferenceError`s `tests/list_comprehensions.rs`,
    `tests/indented_named_arrows.rs` and others pin, and where a global
    would shadow a parameter;
  - inherited-method lookup, `super().f()`, callback indexes, class-level
    static properties and fields of caught errors, which give `undefined` or
    `null` without an error at the accepted revision, so they are protected;
  - `break` and `continue`, which parse as names;
  - `match`, which loses tokens to conditional expressions and lookup
    objects;
  - `transaction:` blocks, since every statement is already a transaction.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero, because no rubric was frozen. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Kotlin's and Logo's word without a reserved word.** `repeat` stays an
  ordinary identifier. At the accepted revision `repeat` followed by an
  expression is two juxtaposed statements, the name `repeat` and the
  expression, so a colon after a complete count is a syntax error. A
  statement is a loop only when it starts with the name `repeat`, the tokens
  after it form one complete count, and that count is immediately followed
  by `:`. Rejected: reserving `repeat`, which would break programs that use
  it as a variable, function, parameter or property name, and Kotlin's
  braced `repeat(3) { ... }`, which is the accepted juxtaposition of a call
  and a block. `repeat (3):` and `repeat(3):` are loops, because `(3)` is a
  complete count.
- **The detection of `while`, shared.** The parser recognizes a `repeat`
  header with the very rule that recognizes a `while` header: one helper
  that takes the leading word runs the cached trial parse of NUC 63, its
  four exceptions, and the rule of NUC 86 and NUC 93 for headers in the
  second reading of programs with `is` words. The two loops therefore agree
  on every header, and a change to one rule changes both. Rejected: a copy
  of the `while` detection, which could drift.
- **Four accepted readings stay.** The accepted parser reads four
  colon-bearing spellings after `repeat` as other statements, so they keep
  their readings, exactly as they do after `while`:
  - `repeat NAME: TYPE` before a statement boundary is `repeat` followed by
    the declaration `NAME: TYPE`. Executing a statement-level declaration
    always raises `ReferenceError("Missing definition")`, and a loop whose
    same-line body is a single bare name could only read that name, so no
    useful loop is lost.
  - `repeat assert: ACTUAL, EXPECTED` is `repeat` followed by
    [NUC 45](nuc-0045.md)'s colon-led assertion.
  - A count whose last token is a bare `lambda` keeps its reading:
    `repeat x + lambda: 1` is `repeat` followed by `x + (lambda: 1)`
    ([NUC 57](nuc-0057.md)).
  - A count that is the name `suppose`, or an assignment whose value is the
    name `suppose`, keeps its accepted [NUC 65](nuc-0065.md) reading, usually
    a `suppose` block.
- **Colon-free and braced headers stay juxtapositions.** Statements need no
  separators, so `repeat n < 3 { n = n + 1 }` and `repeat n < 3` followed by
  an indented block are valid accepted programs: with `repeat = 7` they run
  the block once as a separate statement. Giving them loop meaning would
  change accepted programs, so they are not loops.
- **A complete count parsed like an `if` header.** The count is a clause
  expression, so conditional expressions ([NUC 59](nuc-0059.md)),
  quantifiers ([NUC 62](nuc-0062.md)), `??` ([NUC 60](nuc-0060.md)), `|>`
  and arrows pair their own colons, and a lambda must be bracketed.
- **The count is read once.** A count read before every iteration would make
  the loop a condition loop, and a body that grows what the count reads, as
  `repeat queue.length: queue.push(0)` does, would never end. Reading it once,
  before the first iteration, fixes the number of iterations when the loop
  starts, which is what a counted loop promises: Kotlin's `repeat`, Logo's
  `repeat`, Smalltalk's `timesRepeat:`, Ruby's `times` and Python's `range`
  all evaluate the count once.
- **The conversion of the string method `repeat`.** `"ab".repeat(n)` and
  `repeat n:` agree on how many times `n` is, so `for _ of "a".repeat(n):`
  and `repeat n:` run the same number of iterations for every count up to
  the bound: the count converts to a number, NaN and negative numbers give
  0, and fractions truncate. A count computed from data, a difference or a
  ratio, runs as often as it can, and a negative difference runs nothing,
  as Python's `range(-1)` and Kotlin's `repeat(-1)` do. Rejected: raising
  for a negative or fractional count, where the string method does not, and
  rounding, which no accepted count conversion does.
- **The bound of `while`, checked before the first iteration.** A count is
  known before the loop starts, so a count that converts to more than
  100,000 raises `TypeError("Repeat count is too large")` at once, with no
  iteration run and nothing to roll back, instead of after 100,000
  iterations as a runaway `while` loop raises
  `TypeError("Loop did not terminate")`. The bound is the one `while` uses,
  and the message has the form of `Repeated string is too large`, naming
  the count as the cause. The converted count is what is bounded, so
  `100000` and `100000.9` run 100,000 times. Rejected: capping the count
  silently, and running 100,000 iterations before raising.
- **One-shot and imperative, like `while`.** The loop runs when its
  statement runs and leaves nothing in the graph. Rejected: a standing loop
  that runs again when its count changes, whose effects would pile up with
  every change.
- **The body runs in the enclosing scope, like `while`.** A `for` body
  pushes a scope frame for each iteration to hold its loop variable, and in
  a function, loop or block body that frame turns a name the enclosing body
  already assigned into a local of the iteration. A repeat loop binds no
  variable, so it pushes no frame, and an accumulator in its body updates
  the enclosing local. Parameters and other locals, enclosing loop
  variables, `this`, `self` and `return` behave exactly as in a `while`
  body.
- **No loop variable.** The most common counted loop needs no index, and an
  index would need a binding for each iteration: a scope frame, which would
  bring back the lost accumulators, or a write to an enclosing name, which
  would collide with the program's own names. Rejected: an implicit index
  such as Kotlin's `it` or Logo's `repcount`, and `repeat COUNT as NAME:`. A
  `while` loop with its own counter still counts by hand where an index is
  needed.
- **`$Class` follows `while`.** A repeat statement is never kept on a class.
  Outside a class-level rule, `$Class` reads the declared class and an
  undeclared `$Name` raises `ReferenceError("Name is not defined")`; a body
  statement that is itself a class-level declaration is declared when it
  runs. Inside the body of a class-level rule, the loop runs for each
  instance and `$Class` reads that instance.
- **Canonical rendering.** Graph keys render a loop as
  `repeat(COUNT){BODY}`, including the body, as `while(CONDITION){BODY}`
  does. Inside default-bearing declarations a loop renders in the suite
  form `repeat COUNT:` with an indented body, as `while` does there.
- **REPL and terminal workspace.** The native REPL already buffers a line
  that ends in `:` until a blank line, and the terminal workspace's indented
  newline already indents after one, so `repeat COUNT:` needs no change;
  tests cover both. The workspace completes `repeat` as it completes
  `while`, from its alphabetical place among the completion words.
- **The public syntax tree and statement nodes.** The public `Stmt` enum
  gains `Stmt::Repeat { count, body }`, beside
  `Stmt::While { condition, body }`. `Nuc::convert` maps every `Stmt` to the
  public `Nuc` enum of executable statements, so the loop also needs a
  `Nuc::Repeat` variant, whose node keeps its fields private, as NUC 63
  added `Nuc::While`. Both enums are exhaustive, so the variants break
  exhaustive downstream matches; this needs human SemVer review, and no
  version number changes.
- **Requires.** [NUC 63](nuc-0063.md), whose header detection, four
  exceptions, body semantics, iteration bound, rendering and REPL behavior
  this loop shares, and which already requires the NUCs of those rules;
  [NUC 86](nuc-0086.md) and [NUC 93](nuc-0093.md), whose rule for `while`
  headers in the second reading of programs with `is` words the shared
  detection applies to `repeat`; and [NUC 10](nuc-0010.md), whose string
  method `repeat` defines the count conversion.
- **Not added.** A loop variable or index, `break` and `continue`,
  `repeat ... until`, `do ... while`, `times`, `range`, braced or colon-free
  headers, class-level standing loops, and any change to `while`, `for`,
  the string method `repeat`, recursion limits or existing diagnostics.

## Specification

- The normative contract is
  [Count-controlled repeat loops](../nucleoid.spec.md#count-controlled-repeat-loops).

### Syntax

- `repeat_statement: "repeat" count ":" suite`, where `repeat` is an
  ordinary identifier, `count` is a complete expression in the context of an
  `if` header, and `suite` is the suite of `if`, `for` and `while`: an
  indented block, or statements on the same line separated by `;`.
- A statement is a loop when it starts with the name `repeat` and the tokens
  after it parse as one complete count immediately followed by `:`, except
  in the four spellings that keep their accepted readings, as for `while`:
  - `repeat NAME: TYPE` followed by a newline, `;`, a dedent or the end of
    input: the statement `repeat` and the typed declaration `NAME: TYPE`;
  - `repeat assert: ...`: the statement `repeat` and a colon-led assertion;
  - a count whose last token is a bare `lambda`: the statement `repeat` and
    an expression holding a zero-parameter lambda;
  - a count that is the name `suppose`, or an assignment whose value is the
    name `suppose`: its accepted reading, usually a `suppose` block.
- In the second reading that NUC 86 gives programs with `is` words, a
  header whose tokens through its colon also parse as the accepted separate
  statements keeps that reading, as a `while` header does.
- Statements are loops wherever a statement starts: at the top level, in
  suites, braced blocks, function and method bodies, constructor bodies and
  same-line suites, as in `if ready: repeat 3: n = n + 1`.
- Only statements separated by `;` belong to a same-line suite.
- Inside a call's parentheses, as in `[2].map(k => { ... })` or a callback
  passed to a user function, the indented suite of a loop in a braced
  callback holds only its first statement, and the statements after it run
  once, after the loop. This is accepted parser behavior for indented
  suites there, which this proposal neither causes nor changes: at both
  revisions a `while` counter loop there gives `[10]` where `[20]` is
  meant, the string loop `for _ of "a".repeat(k):` gives `[10]`, and an
  indented `if` suite raises `ReferenceError("k is not defined")`. So a
  repeat loop over `k` whose indented body is `total = total + 1` and
  `total = total + 10`, in such a callback that starts with `total = 0` and
  returns `total`, gives `[12]` for `[2]`, not `[22]`. A same-line suite,
  `repeat k: total = total + 1; total = total + 10`, holds both statements
  there and gives `[22]`. An indented suite in a braced arrow assigned to a
  name, as in `f = (k) => { ... }`, holds every statement, and `f(2)` gives
  `22`.
- Everything else keeps its accepted reading: `repeat COUNT` followed by an
  indented block, `repeat COUNT { ... }`, `repeat = 1`, `repeat := 1`,
  `repeat(4)`, `def repeat(x)`, a parameter or loop variable named
  `repeat`, including either name of a two-name `for` loop, `{repeat: 1}`,
  `point.repeat`, the declaration `repeat: int`, `repeat` inside
  expressions and the string method `"ab".repeat(2)`. `parse_expression`,
  which reads expressions only, still reads the name `repeat`.
- Canonical rendering is `repeat(COUNT){BODY}` in graph keys, as in
  `block(repeat(3){n=n+1})`, and `repeat COUNT:` with an indented body
  inside default-bearing declarations.

```
rabbits = 2
food = rabbits * 3
generations = 3
repeat generations:
    rabbits = rabbits * 2
assert(rabbits, 16)
assert(food, 48)
generations = 5
assert(rabbits, 16)
repeat 2: rabbits = rabbits + food
assert([rabbits, food], [256, 768])
```

- Each generation doubles the rabbits, and `food` follows every iteration;
  setting `generations` later does not run the loop again, and the second
  loop reads the `food` that its own first iteration changed.

### Count

- The count is evaluated once, in the current state, before the first
  iteration. Its errors and thrown values propagate unchanged, and no
  iteration runs.
- The count converts to a number, as arithmetic converts its operands, and
  then as the count of the string method `repeat` does: NaN and negative
  numbers give 0, and fractions truncate toward zero.
- So `3` and `"3"` run the body three times, `2.9` twice, `true` once and
  `[2]` twice, while `0`, `-1`, `null`, `false`, `""`, a non-numeric string,
  an object, NaN and an undefined value, such as a missing property, run no
  iteration.
- What the body changes, including the names, properties and lists that the
  count read, never changes how many times the body runs.

```
team = ["ana", "bo"]
size = team.length
repeat size:
    team.push("hire")
assert(team, ["ana", "bo", "hire", "hire"])
assert(size, 4)
def culture(cells, hours):
    total = cells
    repeat hours:
        total = total * 2
    return total
assert([culture(1, 3), culture(1, 2.9), culture(1, "3"), culture(1, true)], [8, 4, 8, 2])
assert([culture(5, 0), culture(5, -2), culture(5, null)], [5, 5, 5])
```

- `size` follows the team while it grows, but the loop read it once, so the
  team doubles once. `culture` keeps its own accumulator in a local, which
  a string loop would leave unchanged.

### Bound

- Each run of a repeat loop runs its body at most 100,000 times, the bound
  of `while`. A count that converts to more than 100,000, `Infinity`
  included, raises `TypeError("Repeat count is too large")` before the
  first iteration, positioned at the start of the running top-level
  statement, and the transaction rolls back. A count that converts to
  exactly 100,000, such as `100000` or `100000.9`, runs.
- Each run of a nested loop has its own bound, so every run terminates, but
  nested loops multiply and the bound is not a cap on total work.

### Body

- The body runs imperatively, as a `while` body does: its statements,
  including nested conditionals, blocks and loops, are carried out once per
  iteration and never filed as standing rules. Each iteration's
  assignments, and the propagation they cause, are visible to the following
  statements and to the next iteration.
- The body runs in the enclosing scope, with no scope frame and no loop
  variable, so an assignment in the body resolves exactly as the same
  assignment would in place of the loop statement: a parameter, a local of
  the enclosing function or loop body or an enclosing loop variable is
  updated in place, and a top-level name is a state assignment carried out
  once. `this` and `self` denote the enclosing receiver.
- `return` in the body leaves the enclosing function, method, block or loop,
  as from a `while` body. At the top level it ends the program with its
  value.
- A completed loop yields `null`. The loop files nothing in the graph and
  does not run again when its count's inputs, or anything its body read,
  change later. A loop inside the body of a standing rule, such as the
  branch of a top-level `if` or a function called from a declaration, runs
  again whenever that rule runs, as a `while` loop does there.
- A repeat statement is never kept on a class. Outside a class-level rule,
  `$Class` in its count or body reads the declared class, and an undeclared
  `$Name` raises `ReferenceError("Name is not defined")`. A body statement
  that is itself a class-level declaration, such as `$Item.flag = true`, is
  declared on the class when it runs. Inside the body of a class-level rule,
  the loop runs for each instance and `$Class` reads that instance.
- Errors raised by the body, including thrown values, propagate through the
  existing transaction unchanged. An uncaught failure rolls back the whole
  program run; a caught one restores the state from before the enclosing
  `try` body, including every iteration that already ran.

```
class Shelf(levels):
    this.bins = []
    repeat levels:
        this.bins.push(this.bins.length * 10)
    def take(count):
        weight = 0
        repeat count:
            if this.bins.length == 0:
                return "short"
            weight = weight + this.bins.pop()
        return weight
shelf = Shelf(3)
assert(shelf.bins, [0, 10, 20])
assert(shelf.take(2), 30)
assert(shelf.take(2), "short")
assert(shelf.bins, [])
```

```
class Crate(row):
    this.row = row
rows = 2
repeat rows:
    repeat 3: Crate(rows)
    rows = rows + 1
assert(Crate.map(crate -> crate.row), [2, 2, 2, 3, 3, 3])
loaded = Crate.length
try:
    repeat 2:
        Crate(0)
        if loaded > 7:
            throw "FULL"
catch error:
    failure = error
assert(failure, "FULL")
assert([loaded, rows], [6, 4])
```

- The second iteration's throw rolls back both iterations, their crates
  and the propagation to `loaded`.

### Cost

- The count is evaluated and converted once, and the body then runs in one
  bounded `for` loop, so a repeat loop does its body's work and nothing else
  per iteration, where a `while` counter also tests its condition and
  increments its counter in every iteration.
- A statement that starts with the name `repeat` costs one trial parse of
  the tokens after it, cached by token position and nesting depth, exactly
  as a statement that starts with the name `while` does at the accepted
  revision.
- **Measured** on the final tree, after the caller's improvement pass, with
  release builds of the accepted and the candidate library, rustc 1.97.1,
  through the public API: `Runtime::run` of the statement in a new runtime
  after its setup, the median of 101 runs for 1,000 iterations and of 11
  runs for 100,000, and the median of those medians over five rounds that
  alternate the libraries. Each body adds 1 to `n`; the function rows call
  `f(k)`, whose loop counts its parameter. The string loop has no function
  row, because inside a function it loses the local it adds to.

| Workload | `repeat`, candidate | `while` counter, candidate | `while` counter, accepted | String loop, candidate | String loop, accepted |
| --- | ---: | ---: | ---: | ---: | ---: |
| Top level, 1,000 | 1.12 ms | 2.32 ms | 2.42 ms | 1.27 ms | 1.41 ms |
| Top level, 100,000 | 118.5 ms | 256.4 ms | 260.4 ms | 148.9 ms | 154.3 ms |
| Function, 1,000 | 1.18 ms | 2.61 ms | 2.59 ms |  |  |
| Function, 100,000 | 123.2 ms | 269.1 ms | 272.8 ms |  |  |

- A repeat loop takes 45 to 48 percent of the time of its `while` counter
  spelling, at both sizes and in both places, and 80 to 88 percent of the
  time of the string loop. Every row gives the same result on both
  libraries.
- **Programs without repeat loops keep their cost.** The same harness ran
  them on both libraries, five rounds each, alternately; the case rows time
  the tool that runs every accepted case with its assertions in a new
  runtime, and every result is the same:

| Program without a repeat loop | Accepted: median, rounds | Candidate: median, rounds |
| --- | ---: | ---: |
| The 1,158 accepted cases, run with their assertions | 335.0 ms, 327.2 to 344.7 ms | 335.2 ms, 325.9 to 339.4 ms |
| The 1,158 accepted cases parsed as one program of 14,444 statements | 212.5 ms, 209.1 to 213.5 ms | 210.4 ms, 207.3 to 215.6 ms |
| 10,000 lines of the five forms below with a name that heads no loop, parsed | 12.82 ms, 12.70 to 12.96 ms | 12.91 ms, 12.47 to 13.00 ms |
| The same lines, run | 33.29 ms, 32.98 to 35.17 ms | 34.24 ms, 32.79 to 34.65 ms |
| The same lines with the name `while`, parsed | 14.62 ms, 14.37 to 14.92 ms | 14.82 ms, 14.56 to 15.30 ms |
| The same lines with the name `while`, run | 35.50 ms, 34.06 to 35.86 ms | 34.76 ms, 34.36 to 35.84 ms |
| The string method `repeat`, 50,000 copies of `"ab"` | 0.048 ms, 0.044 to 0.051 ms | 0.046 ms, 0.044 to 0.047 ms |

- **Statements that start with the name `repeat` now cost what statements
  that start with the name `while` cost.** The five forms are
  `repeat = repeat + 1`, `repeat(4)`, `x = "ab".repeat(2)`, `repeat n` and
  `o.repeat = repeat`; 10,000 lines of them hold 12,000 statements, 6,000 of
  which start with the name `repeat`. They parse in 12.99 ms at the accepted
  revision, rounds 12.73 to 13.19 ms, and in 15.06 ms with this proposal,
  rounds 14.66 to 15.20 ms, and run in 34.44 ms and 35.52 ms. That is 0.34
  µs for each statement that starts with the name, the trial parse that
  statements starting with the name `while` already pay: their 14.62 ms
  against 12.82 ms for a name that heads no loop.
- `examples/scaling.rs`, unchanged, stays linear on both builds, about 2x
  per doubling, with matching times: the medians of three runs are 3.96 and
  3.88 ms for a chain of 800 variables and 14.55 and 14.29 ms for 800
  instances under a class rule, accepted and candidate.
- **Loops inside class-level rules.** A loop in the body of a class-level
  rule whose body writes what the rule reads runs again with the rule. With
  two instances and the body `o.count = o.count + 1` inside
  `if $Item.n < 100:`, a count of N runs the rule N + 2 times, so `o.count`
  ends at N(N + 2) and the work grows as N². A repeat loop, a `while` loop
  that keeps its counter on the instance and a string loop give the same
  result at counts of 25 to 400, at both revisions where they parse, and
  grow alike: at 400 they take 0.46 s, 0.89 and 0.89 s, and 0.52 and 0.53 s,
  accepted and candidate. At 100,000 the repeat loop and the string loop
  exceed the differential's 120-second limit or its memory cap in every mode
  run, the string loop at both revisions. This is how class-level rules
  propagate, not a cost of the loop.

### Findings

- **Low, documentation (F1).** [Count](#count) says that the count converts
  "as arithmetic converts its operands" and lists a non-numeric string
  among the counts that run no iteration. The conversion reads
  `"Infinity"`, `"+Infinity"` and `"inf"` as Infinity, where arithmetic
  reads them as NaN, so `repeat "Infinity":` raises
  `TypeError("Repeat count is too large")` instead of running nothing. The
  loop still converts exactly as the string method `repeat` does, which
  raises `TypeError("Repeated string is too large")` for the same strings
  at both revisions, and `nucleoid.spec.md` and `docs/README.md`, which
  name only the string method, are accurate.
- **Low, counterparts (F2).** [Counterparts](#counterparts) compares each
  case with counterparts in the case's layout. Collapsing a
  single-statement indented loop body and its countdown into a same-line
  suite shortens six of them by three tokens, and the count-rules case's
  by six, as Policy results records; every case still uses fewer tokens,
  so the gate's verdict is unchanged.
- **Info, cost (F3).** Pushes inside a loop body grow time and memory
  quadratically for every spelling: 10,000 pushes take about 1.3 s, and
  20,000 exceed a 3 GB cap with `repeat` on the candidate, with `while` on
  both builds and with the string loop at the accepted revision. A count
  of 100,000 therefore runs only with light bodies, and [Cost](#cost)
  names only the growth of class-level rules. This proposal does not cause
  it.
- **Info, metadata (F4).** `Requires: 10` names [NUC 10](nuc-0010.md), an
  unallocated reference Draft; the dependency is the implemented and
  specified string method `repeat`, and the accepted
  [NUC 39](nuc-0039.md) sets the same precedent.
- **Info, syntax (F5).** Because the count is any complete expression,
  `repeat[2]:` and `repeat[0]: 1` are loops with list counts, as
  `while[0]: 1` is a `while` loop at the accepted revision. They were
  `SyntaxError`s, so compatibility holds, and [Syntax](#syntax) covers them
  by its general rule, though it names only `repeat(3):`. The caller
  reproduced F1 and F5 on its own build: `repeat "inf":` raises the bound
  error, and `repeat[2]:` runs its body twice.
