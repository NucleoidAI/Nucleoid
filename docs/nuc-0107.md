# NUC 107 -- Python-Style Self Parameters

```
NUC: 107
Title: Python-Style Self Parameters
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Language compatibility
Created: 14-Nov-2026
Requires: 8, 47, 86, 87, 92, 93, 102
```

## Abstract

- Lets a method written with `def` directly in a class's indented body
  declare its receiver explicitly as a leading `self` parameter, as Python
  methods do:
  - `def deposit(self, amount):` declares exactly what
    `def deposit(amount):` declares;
  - `def area(self) => self.w * self.h` declares exactly what
    `def area() => self.w * self.h` declares.

  Calls pass no receiver: `account.deposit(5)` runs as before.
- `def __init__(self, ...)` declares the class's `init` constructor, as
  Python's `__init__` does: `def __init__(self, balance):` declares exactly
  what `def init(balance):` declares, so `Account(100)` runs it.
- The receiver parameter is the keyword `self`, or its accepted alias
  `this`, written first and followed by `,` or `)`. It adds no binding: the
  body reads the receiver through `self` or `this`, as every accepted method
  does.
- Every accepted program keeps its parse and behavior:
  - a program is parsed exactly as at the accepted revision first, and only
    when that whole parse fails are receivers read, in a second run of the
    same parse passes;
  - `def __init__(...)` without a leading `self` stays an ordinary method
    named `__init__`;
  - `super().__init__(...)` keeps its accepted behavior;
  - `class Dog(Animal):` still declares a constructor parameter named
    `Animal`, not a parent class.
- Only inputs that were errors at the accepted revision change. Most raised
  `SyntaxError("Expected a parameter but found keyword 'this'")`. Some
  raised another error first, from a statement that the parser reads
  tentatively: a destructuring declaration whose value holds a class with a
  receiver method raised `Unexpected '='`, `Unexpected ':'` or
  `Unexpected ','`. Those programs failed as a whole, so their other
  statements now run too.
- `self` and `this` parameters keep their accepted errors everywhere else:
  in top-level and nested functions, function literals, arrows and lambdas,
  `function` declarations, methods outside a class's indented body,
  same-line class bodies, class headers such as `class P(self)` and bare
  signatures. A program that still fails reports exactly its accepted error.
- No token, keyword, syntax-tree node, error message, runtime path or public
  item is added: each form parses to the tree that its accepted spelling
  parses to. The authoritative contract is
  [Python-style self parameters](../nucleoid.spec.md#python-style-self-parameters).

## Motivation

- Python is among the languages that language models read and write most,
  and its classes declare every method's receiver as `self`. A model writing
  a Nucleoid world model writes the class the way it writes Python:

  ```
  class Account:
      def __init__(self, balance):
          self.balance = balance
      def deposit(self, amount):
          self.balance = self.balance + amount
          return self.balance
  account = Account(100)
  account.deposit(5)
  ```

  The accepted parser rejects the whole program with
  `SyntaxError("Expected a parameter but found keyword 'this'")` at line 2,
  column 22, and nothing runs. Writing `def init(balance):` and
  `def deposit(amount):` makes it run and return `105`, with the same
  method bodies.
- The two spellings differ only where Python declares what Nucleoid leaves
  implicit: the receiver parameter and the constructor's name. Nucleoid
  methods already read their receiver as `self`, the accepted alias of
  `this`, so the bodies need no change.
- Accepted Nucleoid already welcomes familiar forms from Python and its
  neighbours: [NUC 57](nuc-0057.md)'s Python-style lambdas,
  [NUC 87](nuc-0087.md)'s `self.x` initializing parameters, which Dart and
  TypeScript also have, and [NUC 92](nuc-0092.md)'s list comprehensions.
  Explicit receivers are the Python habit that still fails a whole program.
- Prior art: Python's explicit `self` and `__init__`; Rust's `&self` method
  receivers, as in `fn area(&self) -> f64`; and TypeScript's `this`
  parameters, as in `function f(this: Window)`.

## Rationale

- **Confirmed category and mode.** The allocating cycle drew Language
  compatibility with one tool-backed uniform draw over the five categories
  that NUC 1's registry marks eligible for automatic selection, index 4 with
  probability 1/5 and no redraw, and recorded the requested change in the
  allocation commit `c10b67e8`. This continuous cycle picked the Draft up
  under the stale-Draft rule after it had waited 1 day and 15 hours, claimed
  it in `ee8a2239`, and kept its number, category and requested change.
  Token comparison is therefore skipped as `language_compatibility`. That
  skip is categorical; it is neither a measured comparison nor a passing
  token gate. Runtime applicability does not apply to this category.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts. They execute their assertions and explicit
  returns with full coverage, and every pre-existing case is unchanged.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Only a former error.** At the accepted revision a `self` or `this`
  where a parameter name belongs raises
  `SyntaxError("Expected a parameter but found keyword 'this'")`, placed at
  the token after the keyword, as [NUC 87](nuc-0087.md) records; `self`
  lexes as the keyword `this`. No test pins that error for a `def` with a
  leading receiver in a class's indented body.
- **Accepted first, then receivers.** Accepted inputs can already hold a
  class-body `def m(self)` in a part that a tentative parse gives up on.
  `parse_expression` ignores the tokens after the expression it reads, so
  `1 if function(){`, an indented `class P:` with `def m(self): 1` and
  `} else 2` returns `1`: the Python-style condition fails at the receiver
  and is dropped. Reading receivers in place would make it return the whole
  conditional, the class of break that rejected [NUC 91](nuc-0091.md).
  Template interpolations, which also ignore their tails, are not at risk:
  they read no Python-style condition, so
  `` `${2 if function(){ ``, the same class and `` }() else 3}` `` gives
  `"2"` with or without the receiver. So a program is parsed exactly as at
  the accepted revision first, through its whole parse sequence: the plain
  parse, the `is` retry of [NUC 86](nuc-0086.md), the comprehension retry
  of [NUC 92](nuc-0092.md) and the final parse of [NUC 102](nuc-0102.md).
  Only when that whole sequence fails does the same sequence run once more,
  reading receivers. Every accepted input keeps its parse by construction,
  and no list of tentative parts has to be complete.
- **The same readings everywhere in the second run.** Every parser the
  second run creates reads receivers: each retry and the final parse, the
  `accepted` and `separates` probes with which a `while` header or a
  `suppose` premise in an `is` retry decides [NUC 93](nuc-0093.md)'s
  separate statements, the tentative statements and every template
  interpolation, as are `parse_expression` inputs. So a receiver method
  parses as its spelling without the receiver in every position, including
  the probe shape of NUC 102's evaluation finding F1: a `while` header that
  holds a receiver method and ends in `is a: b` runs as its spelling's
  separate statements and raises `ReferenceError("while is not defined")`.
- **A cheap trigger.** The second run starts only when the tokens hold
  `def`, a name, `(`, `self` or `this` and then `,` or `)`, or a template
  whose text holds `def` and `self` or `this`, because interpolations are
  lexed only when they are parsed. Any other failing program is reported
  after its first sequence, with no extra parse.
- **Methods directly in a class's indented body.** A `def` written there is
  a method, and these are exactly the places where NUC 87 lets `def init`
  take prefixed parameters. Elsewhere a `def` has no receiver to declare:
  functions at the top level or in other bodies, a `def` inside an `if` or a
  braced block of a class body, which is a constructor statement, and a
  `def` of a same-line class body such as `class P: def m(self): 1`, which
  is a constructor statement too. A class written with indentation inside
  `(` or `[` is a same-line class body, because the lexer suppresses layout
  there, so `z = (1 if function(){`, an indented class with `def m(self):`
  and `} else 2)` keeps its accepted
  `SyntaxError("Expected ')' but found keyword 'if'")`, and its spelling
  without `self` defines a constructor statement, not a method.
- **Exactly the keyword, first, then `,` or `)`.** Python lets any name be
  the receiver, but `def m(s, x)` is an accepted method of two parameters,
  so only the keyword spellings `self` and `this` can be a receiver. An
  annotation, default, rest marker or prefix on the receiver would give it
  a meaning that no Nucleoid parameter has, a second receiver would be an
  ordinary parameter named after a keyword, and a receiver after another
  parameter is not Python's receiver, so all of these keep the accepted
  error. A leading `self.x` in an `init` stays NUC 87's prefixed parameter.
- **`__init__` only with the receiver.** `def __init__(balance):` is an
  accepted ordinary method named `__init__`, which construction does not
  run, so it keeps that meaning. With a receiver the name becomes `init`, so
  the class adopts it exactly as it adopts `def init(...)`. Rejected:
  reading every `def __init__` as the constructor, which would change
  accepted programs.
- **Accepted nodes.** The receiver is dropped while the list is parsed, and
  `__init__` with a receiver is named `init`. The parser builds the same
  `Function`, `Parameter` and `ClassDecl` values as the spelling without the
  receiver, so binding, arity, labels, defaults, rest lists, adoption,
  header constructors, inheritance, `super`, class-level rules,
  redeclaration, rendering, graph keys, `why`, transactions and rollback are
  those of that spelling. Rejected: a receiver flag on `Function` or
  `Parameter`, which would change the public syntax tree and every walker
  of it without changing what a method does.
- **Python forms that keep their accepted meaning.** At the accepted
  revision `super().__init__(name)` runs without error: `super()` runs the
  parent's constructor with no arguments, and the call of `__init__` on its
  result does nothing, so the parent's properties stay `null`. A subclass
  forwards its arguments with `super(name)`. `class Dog(Animal):` declares
  a constructor parameter named `Animal`, and `class Dog extends Animal:`
  names the parent. Both are accepted programs, so they are documented
  limits rather than changed.
- **Errors keep their accepted reports.** When the second run fails too,
  the program reports its accepted error, at its accepted position. So
  `def m(self, self)` keeps its error at the first receiver, and every input
  that fails on the candidate fails exactly as at the accepted revision.
  Rejected: reporting whichever error lies further into the source, as NUC
  102 does, which would move that error to the second receiver. The cost is
  that a program whose receivers are valid but which fails elsewhere still
  points at its first receiver, as it did before this proposal.
- **Interactive input.** The native REPL keeps its buffering: a class
  header opens a buffer that a blank line submits. A blank line inside a
  class body therefore submits the class without the methods after it, and
  each such method is then a top-level `def`, where a receiver keeps its
  accepted error, as the spelling without it would define a top-level
  function. Neither the REPL nor the terminal workspace needs a change.
- **Requires.** The Draft named NUC 8 for methods, NUC 47 for constructor
  binding and NUC 87 for `init` parameter lists. This revision adds NUC 86,
  NUC 92 and NUC 102, whose parse sequence the receiver run repeats, and
  NUC 93, whose probes the receiver run reads receivers in.

## Specification

- The normative contract is
  [Python-style self parameters](../nucleoid.spec.md#python-style-self-parameters).

### Grammar

- A method written with `def` directly in a class's indented body may begin
  its parenthesized parameter list with a receiver:

```
method          = "def" name "(" receiver [ "," [ parameters ] ] ")" body
receiver        = "self" | "this"
```

- `name` is an identifier, `parameters` are the parameters of an accepted
  method, with literal defaults ([NUC 54](nuc-0054.md)) and a final rest
  parameter ([NUC 74](nuc-0074.md)), and for `init` and `__init__` NUC 87's
  prefixed parameters. `body` is a block, a same-line suite, `=>`, `->` or
  the indented `=>` of [NUC 32](nuc-0032.md). Line breaks inside the
  parentheses are not layout, and a trailing comma is allowed, as in every
  parameter list.
- The receiver qualifies only when `def`, a name, `(` and the keyword are
  directly followed by `,` or `)`.

### Semantics

- The method declares exactly what its spelling without the receiver
  declares: the same name, parameters and body. `def m(self):` is
  `def m():`, `def m(self, a, b = 1)` is `def m(a, b = 1)` and
  `def m(this) => e` is `def m() => e`.
- A method named `init` or `__init__` with a receiver declares the method
  `init`, with the list of `def init(...)`, so a class adopts it as its
  constructor as it adopts `def init(...)`: a header constructor with a body
  still wins, two `init` methods keep the later one, and `obj.init(...)`
  calls it as a method.
- The receiver adds no binding. The body reads the receiver through `self`
  or `this`, as every method does, and either spelling of the receiver may
  be mixed with either spelling in the body.

```
class Account:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance
    def deposit(self, amount):
        self.balance = self.balance + amount
        return self.balance
    def covers(self, amount):
        return self.balance >= amount
account = Account("ada", 100)
assert([account.owner, account.balance], ["ada", 100])
assert(account.deposit(5), 105)
assert([account.covers(100), account.covers(200)], [true, false])
assert(Account.length, 1)
account.balance
```

- Arrow and same-line methods take the receiver too, and `this` is the same
  receiver as `self`:

```
class Tank:
    def __init__(self, capacity, level = 0):
        self.capacity = capacity
        self.level = level
    def free(self) => self.capacity - self.level
    def fill(self, amount): self.level = self.level + amount
    def full(this) -> this.level >= this.capacity
tank = Tank(50)
assert([tank.level, tank.free(), tank.full()], [0, 50, false])
tank.fill(30)
assert([tank.level, tank.free()], [30, 20])
tank.fill(20)
assert(tank.full(), true)
tank.free()
```

- A subclass passes its arguments to the parent's constructor through
  `super(...)`, and its methods override the parent's:

```
class Vessel:
    def __init__(self, name, capacity):
        self.name = name
        self.capacity = capacity
    def describe(self):
        return self.name + " holds " + self.capacity
class Tanker extends Vessel:
    def __init__(self, name, capacity, cargo):
        super(name, capacity * 1000)
        self.cargo = cargo
    def describe(self):
        return self.name + " carries " + self.cargo
barge = Vessel("barge", 40)
tanker = Tanker("aurora", 80, "oil")
assert([tanker.name, tanker.capacity, tanker.cargo], ["aurora", 80000, "oil"])
assert([barge.describe(), tanker.describe()], ["barge holds 40", "aurora carries oil"])
assert([Vessel.length, Tanker.length], [1, 1])
tanker.capacity
```

- Class-level rules, standing declarations, `why`, transactions and
  rollback see what the methods change, as for the spelling without the
  receiver. A failed call or construction is rolled back.

### Lowering and rendering

| Source in a class's indented body | Builds the tree of |
| --- | --- |
| `def m(self): s` | `def m(): s` |
| `def m(this, a, b) => e` | `def m(a, b) => e` |
| `def m(self, a = 1, ...rest) -> e` | `def m(a = 1, ...rest) -> e` |
| `def m(self,)` | `def m()` |
| `def __init__(self, a): s` | `def init(a): s` |
| `def __init__(this, this.x, b = 2): s` | `def init(this.x, b = 2): s` |
| `def init(self, a): s` | `def init(a): s` |
| `def __init__(a): s` | itself, an ordinary method `__init__` |

- Canonical rendering writes the spelling without the receiver. A class
  renders as `class Tank` unless a list carries a default or a rest
  parameter, and then as its full source, so
  `def pump(self, amount = 1) => self.level + amount` renders as
  `def pump(amount=1):` with the body `return this.level+amount`, and
  `def __init__(self, level = 0):` as `def init(level=0):`.

### Parse passes

- Every input first runs the parse sequence of the accepted revision: the
  plain parse, the parse with `is` comparisons when its tokens hold `is` or
  a template, the parse with comprehensions when they hold `for` or a
  template, the parse with both, and NUC 102's final parse when they hold a
  receiver dot or a template. The first success is the result.
- Only when that whole sequence fails, and its tokens hold `def`, a name,
  `(`, `self` or `this` and then `,` or `)`, or a template whose text holds
  `def` and `self` or `this`, the same sequence runs once more, reading
  receivers in every pass, probe, tentative statement and interpolation.
  Its first success is the result.
- When that run fails too, the input reports the error of the first
  sequence, at its position.
- `parse_expression` runs the same sequence on its input. An input that an
  accepted pass reads keeps that result, even when the tokens it ignores
  hold a receiver method: `parse_expression` of `1 if function(){`, an
  indented `class P:` with `def m(self): 1` and `} else 2` returns `1`, as
  at the accepted revision, while its spelling without the receiver returns
  the whole conditional. As a program, `parse_program` reads the whole
  conditional for both spellings.

## Reference Implementation

- **State:** Implemented and Accepted; the frozen candidate, after the
  caller's Rust improvement pass, is integrated unchanged, as
  [Evaluation](#evaluation) records. No token, keyword, `Expr`, `Stmt` or

- `src/lang/ast/parser/self_parameter.rs`, a new private child module:
  - `Selves`, the mode of a parse, `Accepted` or `Dropped`, and
    `ReceiverMethod`, `Constructor` for `init` and `__init__` or `Ordinary`.
  - `PYTHON_CONSTRUCTOR`, the name `__init__`, and `RECEIVER_WORDS`, the
    spellings `self` and `this` that the template trigger looks for.

  - `mentions_self_parameters`, the trigger of the receiver run: a window
    in the tokens or a template whose text holds `def` and `self` or `this`.
  - `receiver_method`, which reports a window at the parser's position only
    in the `Dropped` mode, comparing the name with `CONSTRUCTOR` and
    `PYTHON_CONSTRUCTOR`; `receiver_declaration`, which reads the keyword,
    the name, the list and the body with `function_keyword`,
    `function_name`, `receiver_parameters` and `declaration_body`, names a
    constructor `CONSTRUCTOR` and builds the method with
    `class::declared_method`; and `receiver_parameters`, which steps over
    `(` and the receiver, takes a following comma and parses the rest of
    the list with the accepted loop, with NUC 87's prefixes for
    constructors.
  - Its unit tests, in `self_parameter/tests.rs`, check the trigger on 31
    sources and the mode check on 11.
- `src/lang/ast/parser.rs` declares the module and gives `Parser` the field
  `selves`, `Accepted` in every new parser. `attempt` runs
  `attempt_readings`, the former `attempt`: the accepted sequence with NUC
  102's final parse. When it fails and the trigger holds, `attempt` runs it
  once more in a parser whose mode is `Dropped` and reports the first
  error if that fails too. `rewound`, which every reset of the sequence now
  uses, starts a parser over the same tokens with the same mode.
- `parser/class.rs` holds `CONSTRUCTOR`, the name `init`, and
  `declared_method`, which builds a method from its name, its
  `ParameterList` and its body: the statements that NUC 87's prefixes

  `receiver_method` first; its `init` branch compares the name with
  `CONSTRUCTOR`, reads the keyword, the name, `constructor_parameters` and
  `declaration_body` in the accepted order and builds the method with
  `declared_method`, so `def init(...)` and `def __init__(self, ...)` share
  one builder. `parser/function.rs`: `parameter_list` is `(` and then
  `parameter_items`,
  the accepted loop, which `receiver_parameters` shares.

### Policy results

- **Evaluator:** the independent evaluator's overall decision is
  **Accepted**, with one low-severity finding and two informational ones.
- **Core gate:** the `evaluate_proposal` report decided `accepted` with no
  issues: 1,105 legacy and 1,113 candidate cases passed.
- **Token check:** skipped, with the reason `language_compatibility`, as
  NUC 1's matrix requires for continuous Language compatibility cycles. The
  skip is categorical: it is neither a measured comparison nor a passing
  token gate, and the new cases have no counterparts.
- **Semantics: passed.**
  - The receiver is the keyword `self` or `this`, first and followed by `,`
    or `)`; it is dropped and adds no binding. `__init__` with a receiver
    declares `init`, and without one stays an ordinary method, and
    `def init(self, ...)` declares `init`.
  - Prefixed parameters after the receiver, arity, defaults, rest lists,
    labels, adoption, header constructors, two `init` methods, inheritance,
    colon parents, `super`, class-level rules, redeclaration, rendering, the
    graph, `why` and `affects`, transactions and rollback are those of the
    spelling without the receiver.
  - The `parse_expression` and template traps keep their accepted results.
    A mutant whose trigger always fires, the proposer's one surviving
    mutant, gives identical results on all 5,651 sources, so the trigger

### Findings

- **Low, documentation (F1).** The fourth bullet of the language
  reference's `Python-style self parameters` section in `docs/README.md`
  says that lambdas and bare signatures keep the accepted
  `Expected a parameter but found keyword 'this'` error. Their accepted
  errors, which they keep, are `SyntaxError("Unexpected ':'")` for
  `f = lambda self: 1` and
  `SyntaxError("Expected '(' but found keyword 'this'")` for a bare
  signature such as `def m self:`. The behavior is correct, and the
  authoritative
  [specification](../nucleoid.spec.md#python-style-self-parameters) and
  [Errors](#errors) state both errors correctly. The frozen candidate is
  integrated unchanged, so that bullet stays as written.
- **Info, documented cost (F2).** A program whose receivers are valid but
  which fails elsewhere reports its accepted error at its first receiver: a
  later misplaced `every` reports the parameter error, where its spelling
  reports `Use all instead of every inside if`. In the REPL, methods after a
  blank line keep a top-level `def`'s error. [Rationale](#rationale)
  records both.
- **Info, measurement (F3).** The cost ratios are noisy medians from one
  machine. Two of the evaluator's ratios, 1.19 for a large class and 1.53
  to 1.55 for a single late receiver, fall just outside the stated ranges
  of 1.22 to 1.26 and 1.43 to 1.52.
