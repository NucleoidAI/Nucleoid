# NUC 136 -- Unknown Constructor Arguments as Properties

```
NUC: 136
Title: Unknown Constructor Arguments as Properties
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Runtime features
Created: 22-Nov-2026
Requires: 14, 47, 54, 74, 78, 87, 93, 95, 107
```

## Abstract

- A label in a constructor call that names no parameter of the effective
  constructor no longer raises
  `TypeError("Unknown constructor argument '<name>' for <class>")`. The
  call acts as if that constructor declared the name as one more parameter
  and its statements were followed by `this.<name> = <name>`. After
  `class Shape(type):` with the body `this.type = type`,
  `shape1 = Shape(type='SQUARE', color='RED')` builds the instance that
  `class Shape(type, color):` with the body `this.type = type` and
  `this.color = color` builds:
  `{"id": "shape1", "type": "SQUARE", "color": "RED"}`. The one deliberate
  difference from that spelling, which the user decided, is that the
  assignments run however the constructor's statements end, after an early
  `return` too, so an expression-bodied `def init(...) => value` keeps its
  labels.
- Every constructor route takes unknown labels: class headers with or
  without a body or a parameter list, a parent named after a colon or with
  `extends` ([NUC 78](nuc-0078.md)), inherited constructors, adopted
  `def init(...)` and `def __init__(self, ...)` ([NUC 107](nuc-0107.md)),
  initializing `this.` parameters ([NUC 87](nuc-0087.md)), literal
  defaults ([NUC 54](nuc-0054.md)) and final rest parameters
  ([NUC 74](nuc-0074.md)), `new`, assignment-named, expression and nested
  instances, shared class rules, `is` assignments, and `super(...)`, which
  assigns them on the same instance after the parent constructor's
  statements.
- Declared labels, positional binding and the other binding errors are
  unchanged: surplus positional values are still evaluated and ignored, and
  a repeated label, a positional argument after a label and a label naming
  a rest parameter keep their `TypeError`s. Function, method, built-in and
  direct `init` calls keep their assignment-expression arguments.
- **Compatibility break accepted in advance.** The user accepted this one
  break on 22-Nov-2026: a constructor call with an unknown label, which
  raised that `TypeError` before evaluating any argument, now evaluates its
  values once in source order and builds the instance. The 14 existing
  assertions that pin exactly that error move to the new reading, keeping
  their case identities, and this NUC lists each one under
  [Compatibility](#compatibility), with the direct consequences of the same
  calls, the byte seal of the rewritten specification case among them: the
  specification case
  `Nucleoid validates constructor names without caller assignments` and
  assertions in `tests/named_constructors.rs`, with its CLI fixture
  `tests/fixtures/named-constructors-invalid.nuc`, which is unchanged,
  `tests/initializing_parameters.rs`, `tests/self_parameters.rs`,
  `tests/rest_parameters.rs`, `tests/literal_parameter_defaults.rs` and
  `tests/item_words.rs`. That break alone fails no hard criterion; any
  other break or test edit still does.
- **Outcome: Accepted**, on the user-requested basis: the frozen candidate
  met all three hard criteria in the independent evaluation and again on
  the integrated tree. The independent evaluator's policy decision was
  Rejected, solely because the deterministic core gate flags the migration
  the user authorized, the specification case
  `Nucleoid validates constructor names without caller assignments`, as an
  invalid legacy case on replay and as changed assertions in its migrated
  copy. Token comparison was skipped as a single-proposal request; see
  [Evaluation](#evaluation).

## Motivation

- The user requested this change directly: "Automatically accept unknown
  argument in constructor in all constructor types", so that
  `Shape(type='SQUARE', color='RED')` on `class Shape(type):` with the body
  `this.type = type` acts like `class Shape(type, color):` with the body
  `this.type = type` and `this.color = color`.
- A world model's instances often carry more attributes than their
  constructor needs to reason about. Today a class must list every one of
  them in its header and repeat it in a body assignment, and one label it
  does not list stops the whole construction. The ARC datasets build every
  instance with labels, such as `Obj(x=0, y=0, width=2, height=2, ...)`, so
  a model that adds an attribute the class leaves out, such as `color=3`,
  loses the instance to that `TypeError`.
- With unknown labels as properties a class declares only the parameters
  its constructor uses, and callers name the rest where they create the
  instance, as Python's `types.SimpleNamespace(type='SQUARE', color='RED')`
  and its `self.__dict__.update(kwargs)` idiom, JavaScript's
  `Object.assign(this, options)` and Ruby's
  `OpenStruct.new(type: 'SQUARE', color: 'RED')` do.
- The price is [NUC 47](nuc-0047.md)'s check for misspelled labels:
  `Student(nmae="Can", age=20)` now builds a student whose `name` is `null`
  and whose `nmae` is `"Can"`. That is the break the user accepted.

## Rationale

- **The user's equivalence, taken literally.** An unknown label is one more
  parameter of the effective constructor, followed by
  `this.<name> = <name>`. Every observable then comes from the accepted
  behavior of that written-out spelling: property order, snapshots,
  dependencies, `why` rules, graph keys, transactions, rollback and
  class-level rules. No second way of writing properties is added.
- **The parsed statement, not a copy of it.** Each assignment is the
  statement an initializing parameter `this.<name>` lowers to
  ([NUC 87](nuc-0087.md)), the tree the parser builds for
  `this.color = color`, so it explains, renders, depends and rolls back as
  the written statement does.
- **After the constructor's statements.** The user's spelling writes
  `this.color = color` last. The statements can read the label as a
  parameter, and a caller's label replaces a value the statements set, the
  usual reason to pass a value the constructor does not declare.
- **However the statements end.** Taken literally, the written-out spelling
  would skip the assignments after a `return`, including the one an
  expression-bodied `def init(...) => value` lowers to, so such a
  constructor would accept a label and drop it. The user decided on
  23-Nov-2026 that every constructor keeps its labels: the assignments run
  once the statements finish, normally or with a `return`. This is the one
  deliberate difference from the written-out spelling. A failing statement
  still skips them and rolls back the whole instance.
- **Per call, not per class.** Only the call that passes a label gets its
  property; the class's signature, its other instances and later calls are
  unchanged. The unknown names come after every declared parameter and any
  rest formal and bind only by label, so positional values never reach
  them, and surplus positional values keep their accepted evaluation.
- **Validation still comes first.** The whole call is checked before any
  value runs, as [NUC 47](nuc-0047.md) requires. A repeated unknown label is
  a duplicate binding of its written-out parameter and raises the existing
  duplicate error; the positional-after-label and rest-label errors stay.
  Only the unknown-name rejection goes, because the user asked for exactly
  that.
- **No syntax.** Labels and their trees exist since NUC 47; the lexer,
  parser, generator, canonical rendering and `docs/nucleoid.ebnf` are
  unchanged.
- **Rejected alternatives.**
  - An opt-in marker, a `**kwargs` parameter or a rest-of-labels formal:
    the user asked for automatic acceptance in all constructor types, and
    each would add syntax.
  - Assigning the properties before the constructor's statements: the
    statements would overwrite a caller's value, and the user's spelling
    writes the assignment last.
  - Writing the properties directly from the runtime: a second property
    path would bypass the dependency, explanation, graph and transaction
    behavior that the written statement has.
  - Extending the class's signature: later positional calls would bind the
    new name and every other instance would gain a `null` property.
  - Keyword arguments for functions and methods: out of scope; they keep
    their assignment-expression arguments.

## Specification

### Unknown labels

- An unknown label is a constructor-call label, a bare `name=value`
  argument ([NUC 47](nuc-0047.md)), that names no parameter of the
  effective constructor: the nearest nonempty constructor of the class or
  an ancestor, with adopted `def init(...)` and `def __init__(self, ...)`
  signatures. A label that names only a parameter of a bodyless subclass
  header, which is not the effective constructor, is unknown too.
- The call acts as if the effective constructor declared each unknown
  label's name as one more parameter, after its declared parameters in
  label source order, and its statements were followed by
  `this.<name> = <name>` for each unknown label in source order, with the
  one deliberate difference that [Assignments](#assignments) states for a
  `return`.

```
class Shape(type):
    this.type = type
shape1 = Shape(type="SQUARE", color="RED")
assert(shape1, {"id": "shape1", "type": "SQUARE", "color": "RED"})
assert([shape1.type, shape1.color, Shape.length], ["SQUARE", "RED", 1])
```

### Binding

- The whole call is validated before any value runs, in source order. A
  repeated label, an unknown one included, raises
  `TypeError("Duplicate constructor argument '<name>' for <class>")`; a
  positional argument after a label and a label naming a rest formal keep
  their errors. No other check is added.
- Values run once, in source order, in the caller's scope, `.value` reads
  included. Declared parameters bind as before. Each unknown label's value
  is bound to its name in the constructor scope after the declared
  parameters and any rest formal, so a positional value never reaches it.
  Surplus positional values are still evaluated, then ignored or collected
  by a rest formal: `Pair(mark("A"), mark("S"), b=mark("B"))` on
  `class Pair(a)` runs all three and builds `a` and `b`.
- A named or mixed call pins its validated plan before any value runs, so a
  value that redeclares the class with a parameter of an unknown label's
  name leaves that label unknown for the call; purely positional calls
  carry no labels and keep their delayed constructor selection.
- Labels never read, write or depend on caller variables, unknown ones
  included.

### Assignments

- The assignments run in the constructor after its own statements,
  including a leading `super(...)` and the assignments of initializing
  `this.` and `self.` parameters. The statements can read an unknown
  label's name as they read a parameter, and an assignment replaces a
  property the statements set, which keeps its place among the instance's
  properties; a new property follows the ones set before it.
- The assignments run once the statements finish, whether they end
  normally or with a `return`. An early `return` in a body therefore keeps
  the call's unknown labels, and so does an adopted
  `def init(...) => value`, which lowers to the single statement
  `return value`. This is the one deliberate difference from the
  written-out spelling, where a statement after a `return` never runs; the
  user decided it on 23-Nov-2026 so that every constructor keeps its
  labels. It holds for the parent constructor that `super(...)` runs too. A
  failing statement still skips the assignments and rolls back the whole
  instance.
- Each assignment is the statement `this.<name> = <name>`: the property
  holds a snapshot of the value, with no dependency on a caller variable,
  and `why` reports its rule as `$<Class>.<name> = <name>` for the
  instance's class. Graph keys, transactions and rollback treat it as that
  statement.
- Class-level rules still apply after the constructor, so they read the
  new properties like any other, and a rule for the same property sets it
  after construction: `$Shape.color = "BLUE"` wins over
  `Shape(color="RED")`.
- A label named `id` reassigns the instance's `id` property, as
  `this.id = id` does, and the instance keeps its name. A label named
  `value` raises `TypeError("Cannot use 'value' as a property")`, as
  `this.value = value` does, after the values ran, and the construction
  rolls back.
- A declared parameter still creates no property by itself:
  `class Shell(code: int)` called as `Shell(code=7, note="spare")` builds an
  instance with `note` and without `code`.

```
class Shape(type):
    this.type = type
    this.size = 1
plain = Shape(type="CIRCLE")
sized = Shape(type="SQUARE", size=2, color="RED")
assert(plain, {"id": "plain", "type": "CIRCLE", "size": 1})
assert(sized, {"id": "sized", "type": "SQUARE", "size": 2, "color": "RED"})
class Badge(name):
    this.name = name
    this.title = rank + " " + name
badge = Badge(name="Ada", rank="Captain")
assert(badge, {"id": "badge", "name": "Ada", "title": "Captain Ada", "rank": "Captain"})
class Lamp(room):
    this.room = room
    if room == "attic":
        return
    this.lit = true
attic = Lamp(room="attic", watts=60)
assert(attic, {"id": "attic", "room": "attic", "watts": 60})
```

### Routes

- Every construction route takes unknown labels: class headers with or
  without a body or a parameter list ([NUC 14](nuc-0014.md)), a parent
  after a colon or `extends` ([NUC 78](nuc-0078.md)), inherited and bodyless
  subclass constructors, adopted `def init(...)` and
  `def __init__(self, ...)` ([NUC 107](nuc-0107.md)), initializing
  parameters ([NUC 87](nuc-0087.md)), literal defaults
  ([NUC 54](nuc-0054.md)), final rest parameters ([NUC 74](nuc-0074.md)),
  `new`, assignment-named, expression, nested-property and collection
  instances, shared class rules, and `is` assignments
  ([NUC 93](nuc-0093.md)), whose label values in item positions read as
  item words ([NUC 95](nuc-0095.md)).
- A standing declaration that holds a construction builds a new instance
  when it re-evaluates, with the label values of that evaluation, as for
  declared labels; a named instance reads its values once.
- `super(...)` binds its labels against the effective parent constructor on
  the same receiver. Its unknown labels are assigned after the parent
  constructor's statements, before the calling constructor goes on; the
  calling constructor's own unknown labels follow its statements, so they
  win over the same name passed to `super`.
- Static class-level rule checks no longer reject an unknown label. They
  still raise the other binding errors when the rule is declared and still
  require every right-hand reference, so `$Holder.tag = Tag(color=missing)`
  raises `ReferenceError("missing is not defined")` there.
- A failing value fails before the instance is registered, and a failing
  statement or assignment restores the instance, the population, the
  properties and the graph, inside `try` and `suppose` as at the top level.

```
class Shape(type):
    this.type = type
class Square: Shape
    pass
class Tile(size): Shape
    super(type="SQUARE", color="RED")
    this.size = size
square = Square(type="SQUARE", color="BLUE")
tile = Tile(size=2, glaze="MATTE")
assert(square, {"id": "square", "type": "SQUARE", "color": "BLUE"})
assert(tile, {"id": "tile", "type": "SQUARE", "color": "RED", "size": 2, "glaze": "MATTE"})
assert([Shape.length, Square.length, Tile.length], [0, 1, 1])
```

### Unchanged

- Purely positional calls, declared labels, omitted parameters and their
  defaults, and the repeated-label, positional-after-label and rest-label
  errors with their placement and evaluation order.
- Function, method, built-in and direct `object.init(...)` calls keep their
  assignment-expression arguments: `pair(color=2, shade=1)` assigns `color`
  and `shade` in the caller and passes `2, 1`.
- Grouped assignments such as `Legacy((b=2), (a=1))` stay positional, and
  the canonical rendering of `Shape(type='SQUARE', color='RED')` is
  `Shape(type="SQUARE",color="RED")`.
- No token, keyword, grammar rule, syntax-tree node or error message is
  added, and no parse changes: `docs/nucleoid.ebnf` is unchanged.

## Errors

- No error is added, and
  `TypeError("Unknown constructor argument '<name>' for <class>")` is no
  longer raised by any route.
- These keep their messages, their placement at the top-level statement and
  their validation before any value runs, where `<class>` names the
  effective constructor's class:
  - `TypeError("Duplicate constructor argument '<name>' for <class>")` for
    a repeated label, declared or unknown, or a label for a positionally
    bound parameter;
  - `TypeError("Positional constructor argument after named arguments for <class>")`;
  - `TypeError("Rest parameter '<name>' cannot be a named constructor argument for <class>")`.
- A failing value, statement or class-level rule raises its existing error,
  and an unknown label named `value` raises
  `TypeError("Cannot use 'value' as a property")`, as
  `this.value = value` does.

## Reference Implementation

- **State:** Implemented and Accepted. The candidate was prototyped in an
  isolated worktree of accepted revision
  `870bc76b5af8f5061e0e7e37b0b3dcdd3656a147`, the pushed allocation, and
  the frozen candidate, after the caller's Rust improvement pass, is
  integrated unchanged, as [Evaluation](#evaluation) records.
- `src/nuc/object.rs`: binding gives each argument a `Slot`: a declared
  parameter, a surplus positional value, or a property for an unknown
  label. `label_slot` keeps the rest-label and duplicate checks and records
  unknown names in a set of their own, so a repeated unknown label is a
  duplicate. `prepare_constructor` collects the unknown labels' values in
  source order into `ConstructorCall::Bound`, and `run_constructor` binds
  them after the declared parameters and, once the constructor's
  statements finish, normally or with a `return`, runs one
  `this.<name> = <name>` statement each in the same tracking scope. It runs
  a class without parameters or statements when the call has unknown
  labels. Every route, `super(...)` included, already reaches these two
  functions, and `check_constructor_bindings` uses the same binding.
- `src/lang/ast/parser/class.rs` and `src/lang/ast/parser.rs`: the existing
  `initializer` lowering of initializing parameters is re-exported to the
  crate. The lexer, the parser's rules, the generator, evaluation, the CLI,
  the terminal and `docs/nucleoid.ebnf` are unchanged.
- **Rust improvement pass.** The caller's pass added one line,
  `debug_assert!(!scope.has(&label.name))`, before each label's assignment
  in `run_constructor`. It is a side-effect-free Power of 10 rule 5
  invariant: `label_slot` guarantees that an unknown label names no
  parameter and does not repeat, so each label declares a fresh binding in
  the constructor scope, whose frames `Scope::has` alone searches. Its
  suggestion to move `initializer` to an AST-level `Stmt::initializer` was
  not applied, by the caller's decision: widening the existing NUC 87
  lowering to `pub(crate)` and re-exporting it from `parser.rs` is the
  smallest visibility the runtime needs and keeps one source of truth for
  `this.x = x`.
- `tests/unknown_constructor_arguments.rs` (19 tests) covers the claims
  above; existing tests change only as [Compatibility](#compatibility)
  lists.
- The specification gains its section and eight entries, and its Default
  named constructors, Literal parameter defaults and Item words sentences
  that stated the old behavior are corrected. `docs/README.md` gains its
  subsection, its syntax summary line and corrected constructor bullets, and
  loses the error table row; `tests/reference.md`, `README.md` and
  `docs/examples.md` gain one case each. Nothing under `arc/` changes.
- Token comparison is skipped as `single_proposal`; the user requested
  this NUC. Runtime applicability is `existing_comparable`: every instance
  an unknown label builds has a behavior-equivalent accepted spelling, the
  label declared as one more parameter and assigned after the
  constructor's statements, or, where those statements end with a
  `return`, assigned before it.
