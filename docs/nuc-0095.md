# NUC 95 -- Item Words

```
NUC: 95
Title: Item Words
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 08-Nov-2026
Requires: 17, 47, 86, 93, 94
```

## Abstract

- Inside the value of an `is` assignment of [NUC 93](nuc-0093.md), three
  kinds of item are item positions: an item of a list, the value of a
  dictionary entry and the value of a `name=value` argument of a call whose
  callee is a bare name, `new Name(...)` or `super(...)`. So
  `colors is [RED, GREEN]`, `glow is {small: DIM, large: BRIGHT}[size]` and
  `first is Light(color=RED, parts=[GREEN, GREEN])` hold words.
- An item position holding exactly one identifier token is a word, read by
  NUC 93's word rule through the same `UnaryOp::Word` marker: the name's
  value when something defines it, and otherwise its own text, recording a
  dependency on the variable of that name.
- Item positions exist wherever such a list, dictionary or call stands in
  the value, at any depth, including conditions, branches, operands,
  subscripts, receivers, comprehension sources and grouping parentheses.
  They do not exist inside function and lambda bodies, comprehension
  elements and filters, template interpolations, inner assignment values
  and assignment targets.
- Item positions are word positions of [NUC 94](nuc-0094.md), so a
  conditional standing in one has word branches, and the lists,
  dictionaries and calls in a word branch have item positions.
- It is always on, with no option or flag, as `is` assignments and
  conditional words are since `d9452132` and `f463d94f`. No token, keyword,
  syntax-tree variant or error message is added. `=` assignments,
  dictionary keys, the shorthand `{A}`, parenthesized items and positional
  arguments keep their readings. The authoritative contract is
  [Item words](../nucleoid.spec.md#item-words).
- Not backward compatible in one respect, which the user accepted on
  8 Nov 2026: inside an `is` value, a bare one-identifier item whose name is
  not defined used to raise `ReferenceError`, and now reads as its own text.
  See [Backward Compatibility](#backward-compatibility).
- Accepted: the user requested this feature directly and chose always-on
  item words, accepting their compatibility break. After the independent
  evaluation, the user also accepted the one further effect it found, where
  an undefined item that the same statement already read as a word gave
  `undefined` rather than raising `ReferenceError`. With that break
  accepted, the frozen candidate meets every hard criterion of the automatic
  acceptance rule, so the user-requested basis applies. The independent
  evaluator's overall decision was Rejected, solely because of that effect
  under the break as first stated. Token comparison was skipped as
  `single_proposal`, the rule for a single-proposal request, not a failed
  check; see [Evaluation](#evaluation).

## Motivation

- The user writes ARC instruction datasets in Nucleoid and wants them free
  of quotes. NUC 93 removed the quotes of a value that is one word, and
  NUC 94 those of a conditional's branches. Lists, tables and constructed
  objects of words still need them:

```
$Light.partner is [['RED', 'GREEN'], ['BLUE', 'AMBER']].find(pair => pair.includes($Light.color@first)).find(other => other is not $Light.color@first)
$Light.glow is {small: 'DIM', large: 'BRIGHT'}[$Light.size@first]
$Light.shade is ['RED', 'GREEN', 'BLUE'][$Light.x@first]
first is Light(color='RED', size='small', x=2, parts=['GREEN', 'GREEN'])
```

- The user wants them written as words, as a value of one word already is:

```
$Light.partner is [[RED, GREEN], [BLUE, AMBER]].find(pair => pair.includes($Light.color@first)).find(other => other is not $Light.color@first)
$Light.glow is {small: DIM, large: BRIGHT}[$Light.size@first]
$Light.shade is [RED, GREEN, BLUE][$Light.x@first]
first is Light(color=RED, size=small, x=2, parts=[GREEN, GREEN])
```

- At the accepted revision the second spelling fails, because NUC 93 makes
  a value a word only when the whole value is one identifier token and
  NUC 94 adds only conditional branches:
  - `z is [A, B]` raises `ReferenceError("A is not defined")` at line 1,
    column 1, and `m is {s7: C}` raises `ReferenceError("C is not defined")`.
  - After `class Light(color, size, x, parts):` with a constructor that
    assigns each parameter, declaring the `partner` rule raises
    `ReferenceError("RED is not defined")`, because class-rule validation
    requires every name in it, and `first is Light(color=RED)` raises the
    same error when it runs.
- With item words, a model states lists, tables and constructed objects of
  words and decides later whether each word is its text or a variable that
  remaps it:

```
colors is [RED, GREEN]
pair is {left: RED, right: BLUE}
RED = "red"
```

- `colors` is `["RED", "GREEN"]` and `pair.left` is `"RED"` until `RED` is
  defined, and `"red"` after it. The programs of this proposal execute as
  written in `tests/item_words.rs::the_documented_examples_run_as_written`,
  and the ARC forms that motivated it were run through the command line
  while preparing it.

## Rationale

- **Category and mode.** The user requested this concrete feature, so there
  was no random draw. Its category is Syntax enhancement, that of NUC 93 and
  NUC 94, which it extends. It runs in single-proposal mode, which skips
  token comparison. Runtime applicability does not apply. No hint was
  supplied.
- **Always on.** The user asked for item words without an option or flag,
  as `is` assignments and conditional words are. `d9452132` removed
  `SyntaxOptions`, the `*_with_options` APIs and the
  `--c-style-comments` and `--is-assignment` flags, and `f463d94f` made
  NUC 94's conditional words always on the same way. Here
  `parser/is_assignment.rs` parses every `is` value with item positions, and
  there is no option struct, lexer field or command-line flag to add.
- **The name.** The form is a word as an item: an item of a list, the value
  of an item of a dictionary, and the value of a named argument, the item
  of a call's argument list that names its slot. So "item words", plural as
  "conditional words" is. Rejected: "literal words", since a call is not a
  literal and every number and string is one; "collection words", since a
  call is not a collection; "member words", since a member is a `.name`
  access in the grammar; and "argument words", which names one of the three
  positions and suggests positional arguments too.
- **Item positions.** A list item, a dictionary value and a named
  argument's value are each one element of the data the value states, so
  each is a word position where the user would otherwise quote a word.
- **Named arguments are constructor labels.** [NUC 47](nuc-0047.md) makes a
  bare `name=value` argument a constructor label only in a call whose callee
  is a bare name, including `new Name(...)`, or `super`, when that name is a
  class. The parser reads such an argument as a potential label, and the
  grammar records that rule for a plain-name callee. In every other call,
  such as `o.m(k=A)` or `f()(k=A)`, `name=value` is an assignment
  expression, which NUC 47 keeps for functions and methods, so its value is
  the value of an inner assignment and is not an item position. The parser
  cannot know whether a bare name is a class or a function: when
  `pick(color=A)` calls a function, the argument still assigns `color` as
  before, now from the word. Positional arguments stay ordinary
  expressions; the user did not ask for them.
- **Keys and shorthand.** Dictionary keys are unchanged, because an
  identifier key is already its own text: `{s7: C}` has the key `"s7"`
  whatever `s7` names. The shorthand entry `{A}` of [NUC 17](nuc-0017.md)
  keeps reading the variable `A`: it means "this variable under its own
  name", and reading it as a word would make it the different entry
  `{A: "A"}`. The accepted grammar has no list spread and no computed key,
  and a spread source `{...o}` names an object to copy, not an entry, so it
  is not an item position either.
- **Anywhere in the value.** The item positions are those of every list,
  dictionary and named argument in the value, at any depth: nested
  literals, receivers, subscripts and slice bounds, arguments, operands,
  conditions and branches of conditionals, quantifiers, pipeline stage
  arguments and the source of a comprehension. Conditions are included, so
  `X if [A, B].includes(c) else Y` reads the words `A` and `B`; there is no
  `in` operator, and a list in a condition is data as anywhere else.
- **Grouping parentheses.** A parenthesized item, `[(A)]`, is not a word,
  so parentheses stay the way to ask for a reference, as under NUC 86, 93
  and 94. Parentheses around a literal, as in `([A, B])` or
  `([A] if c else B)`, do not remove its item positions: they group, and
  grouping does not change what a list contains. Rejected: ending the item
  positions at parentheses, which would make `([A, B])` and `[A, B]` differ.
- **Excluded parts.** Function, arrow and lambda bodies run later, with
  their own locals; an `is` assignment in a block body has its own value and
  its own item positions. A comprehension's element and filter condition
  become the bodies of the functions it lowers to, so they are excluded as
  bodies are, while its source is an ordinary operand: `[x for x in [A]]` is
  `[A].map(x => x)`. Template interpolations are parsed separately and hold
  no `is` value, as for NUC 93 and NUC 94. The value of an inner assignment,
  as in `a is b = [A]`, is that assignment's value, as NUC 93 and NUC 94
  treat it. The target of an assignment operator is a target:
  `a is [A][0] = 1` keeps the tree of its `=` spelling.
- **One identifier token.** An item is a word exactly when NUC 93 would read
  it as a word if it were the whole value. `1`, `"B"`, `true`, `this`,
  `$Light`, `A.x`, `f(A)`, `A + 1`, `not A` and `(A)` are not words.
- **Composition with NUC 94.** An item position is a word position in
  NUC 94's sense, so `[A if c else B]` and `Light(color=c ? A : B)` have word
  branches, and the items of a literal in a branch are words, as everywhere
  in the value: `a is [A] if c else {k: B}` makes `A` and `B` words. Both
  rules are always on, so one reading covers a statement that uses both.
- **Semantics.** An item word is NUC 93's word: the marker is evaluated by
  NUC 86's `read_word`, so dependency collection, `.value` freezing, cycle
  checks, static class-rule validation and the protected-assertion walker
  already handle it wherever it stands. The evaluator is unchanged: a list
  evaluates its items, a dictionary its values and a constructor its
  labeled values, and a word there reads as a word.
- **Marking while parsing.** The syntax tree drops grouping parentheses, so
  the parser marks an item where it knows the item's tokens, as NUC 94
  marks branches. NUC 94's branch mode is a parameter because it passes only
  through a conditional's branches. Item positions reach every construct of
  the value, so the item mode is parser state, `Items`: `Words` while the
  value of an `is` assignment is parsed, and `Plain` inside the excluded
  parts and everywhere else. A parameter would add a stack slot to every
  frame of every precedence level. Probe parsers and interpolations start
  with `Plain`. NUC 59 memoizes Python-style condition attempts by position
  and depth, and a condition's tree now also depends on the item mode, so
  attempts made with item words keep a memo of their own.
- **Host stack.** NUC 94's evaluation found debug builds overflowing one
  nesting level sooner. Here the item checks stay out of the deepest frames:
  the label check is a boolean before the accepted argument path, lists and
  dictionaries call their item parsers directly, and the operator tail of
  `assignment_expression` moved into its own function, so the frame that
  every nesting level passes through is smaller. The debug command line now
  overflows later than the accepted one for 36 of 87 measured pairs of a
  statement head and a nesting shape, and never sooner; see Reference
  Implementation.
- **Rendering.** A statement whose value holds a word renders as
  `target is value`, as under NUC 93 and NUC 94. When the value holds an
  item word, every item position renders as a word position, so a name
  there that is not a word renders in parentheses, `a is [A,(B)]`, and the
  rendering reads back as the same statement. A value whose only words are
  NUC 94's branch words renders exactly as at the accepted revision, which
  keeps every output of a program without item words unchanged. Its
  rendering can then read back differently: `a is [(A)] if c else B` renders
  as `a is c?[A]:B`, as before, which now reads back with the item word `A`,
  and a block holding it shares its key with a block holding
  `a is [A] if c else B`. Rejected: rendering the item positions of such
  values as word positions, as `a is c?[(A)]:B`, which would read back the
  same but would change the graph keys, `--graph` output and `why` rules of
  accepted programs that hold no item word, outside the accepted break.
- **Diagnostics.** No message is added. Item words change only markers,
  never which tokens a value consumes or how deeply it nests, so every
  program parses, or fails to parse at the same place with the same message,
  as its `=` spelling does one column to the left.
- **Not added.** Words in positional arguments, dictionary keys, spread
  sources, subscripts and operands of other operators; words in `=`, `:=`
  and `return` values; method-call labels; an option, a flag, a REPL command
  or a terminal toggle.
- **Optional evidence.** Advisory usefulness is unscored (`missing_rubric`),
  not zero. Strategy learning is `not_configured`; this revision is
  unattributed, without a policy, selection receipt, trial or reward.

## Specification

- The normative contract is
  [Item words](../nucleoid.spec.md#item-words).

### Item positions

- These are the item positions of an `is` assignment's value:
  - each item of a list literal;
  - the value of each `key: value` entry of a dictionary literal;
  - the value of each named argument `name=value` of a call whose callee is a
    bare name, including `new Name(...)`, and of `super(...)`.
- They are item positions wherever the literal or call stands in the value:
  inside another literal or named argument, as a receiver, argument,
  operand, subscript, slice bound or pipeline stage argument, in a condition
  or a branch, in a quantifier, in the source of a comprehension and inside
  grouping parentheses.
- Not item positions: anything inside a function, arrow or lambda body, the
  element or filter condition of a list comprehension, a template
  interpolation, the value of an assignment operator inside the value, or
  the target of an assignment operator; a `name=value` argument of any other
  call; positional arguments; dictionary keys; shorthand entries; and spread
  sources.
- An item position whose expression is exactly one identifier token is a
  word. Every other expression there keeps its reading.
- An item position is also a word position of [NUC 94](nuc-0094.md), so a
  conditional there has word branches, recursively.
- Statement positions are those of NUC 93: every position where an `is`
  assignment applies, including the block bodies of function literals
  inside expressions and template interpolations. The top level of
  `parse_expression` holds no `is` assignment and so no item word.

### Semantics

- An item word reads by NUC 93's word rule: the local, variable, class,
  function or built-in global of that name when one exists, read as an
  identifier is, and otherwise the string of its spelling, recording a
  dependency on the variable of that name. A standing declaration whose
  item word names a variable holding `null` therefore stores `null`, as
  `xs = [D, 2]` does.
- A list literal evaluates every item in order and a dictionary literal
  every value in order. A constructor call validates its labels and then
  evaluates every supplied value once, in source order, so a call with an
  unknown label reads none of them. A conditional reads only its selected
  branch, and `&&`, `||` and `??` skip their right operand when the left one
  decides. An item word that is not evaluated is not read and adds no
  dependency.
- A standing declaration, property, constructor property or class-level
  rule re-evaluates when the variable named by an item word it read is
  defined, changed or deleted, including inside a `suppose` block whose
  rollback restores it. Deleting the variable returns the word to its text.
  While undefined, the word is a pending graph node that `why` lists among
  the sources.
- A named instance, such as `second is Light(size=large, x=2)`, reads its
  constructor values once, when it is built, as every constructor value is.
  An anonymous construction inside a standing value, as in
  `lights is [Light(color=BLUE)]`, builds a new instance when the value
  re-evaluates.
- Static class-rule validation does not require an item word to be defined.
  It still requires every other name, so `$Light.bad is [(MISSING)]` raises
  `ReferenceError("MISSING is not defined")` when declared.

```
class Light(size, x):
    this.size is size
    this.x is x
    this.corners is [[RED, BLUE], [GREEN, AMBER]]
$Light.glow is {small: BLUE, large: GREEN}[$Light.size@first]
$Light.shade is [RED, BLUE, GREEN][$Light.x@first]
first = Light("small", 0)
second is Light(size=large, x=2)
assert([first.glow, second.glow], ["BLUE", "GREEN"])
assert([first.shade, second.shade], ["RED", "GREEN"])
assert(first.corners, [["RED", "BLUE"], ["GREEN", "AMBER"]])
GREEN = "green"
assert([second.glow, second.shade], ["green", "green"])
```

```
colors is [RED, GREEN]
pair is {left: RED, right: BLUE}
assert([colors, pair], [["RED", "GREEN"], {"left": "RED", "right": "BLUE"}])
RED = "red"
assert([colors[0], pair.left], ["red", "red"])
```

### Rendering

- An `is` assignment whose value holds a word renders as `target is value`
  in statement rendering, block graph keys, `--graph` output and the `rule`
  of `why` and `affects`. When the value holds an item word, every item
  position renders as a word position: a name there that is not a word
  renders in parentheses, and a shorthand entry renders as `"A":(A)`. A
  conditional in a word position that holds a word renders without its
  grouping parentheses, as under NUC 94.

| Statement | Rendering |
| --- | --- |
| `a is [A, (B)]` | `a is [A,(B)]` |
| `a is {k: A, B}` | `a is {"k":A,"B":(B)}` |
| `a is Light(B, color=(A), size=C)` | `a is Light(B,color=(A),size=C)` |
| `a is {small: DIM, s7: OFF}[x]` | `a is {"small":DIM,"s7":OFF}[x]` |
| `a is [A] if c else B` | `a is c?[A]:B` |
| `a is [A] if c else 1` | `a is (c?[A]:1)` |
| `a is [A if c else B]` | `a is [c?A:B]` |
| `a is [(A if c else B), D]` | `a is [(c?A:B),D]` |
| `{ total is [A, (B)] }` | the block key `block(total is [A,(B)])` |
| `a is [(A)]` | `a=[A]` |
| `a is [(A)] if c else B` | `a is c?[A]:B`, as at the accepted revision |

- Every rendering in the table reads back as the same statement, except the
  last. No path re-parses rendered statements; graph keys, `--graph` output
  and `why` rules are labels. Function literals render as `function()` as
  before.
- **Known limitation.** A value whose only words are NUC 94's branch words
  renders as at the accepted revision, even when an item position in it
  holds a parenthesized name, a shorthand entry or a parenthesized label
  value. Such a rendering does not read back as the same statement:
  `a is [(A)] if c else B` renders as `a is c?[A]:B`, which now reads back
  with the item word `A`, and a block holding it shares its key with a block
  holding `a is [A] if c else B`. Of the 5,492 word-rendered assignments in
  the final differential's candidate trees, these are the 81 that do not
  read back, all of this kind, in four forms after any target: `c?[A]:B`,
  `c?{"A":A}:B`, `[A].includes(c)?X:Y` and a labeled call such as
  `c?Light(color=A):B`. The accepted rendering is kept because rendering such
  values to read back would change the graph keys, `--graph` output and
  `why` rules of accepted programs that hold no item word, outside the
  accepted break.

## Backward Compatibility

- **The break.** Inside the value of an `is` assignment, a bare
  one-identifier item in an item position whose name is not defined used to
  raise `ReferenceError("<name> is not defined")`, and now reads as its own
  text. The user explicitly accepted this break on 8 Nov 2026: asked how to
  redo this proposal, they chose "Redo it always on", described as "the same
  compatibility break you accepted for those", that is, for `is`
  assignments in `d9452132` ("Remove opt-in syntax options") and for
  conditional words in `f463d94f` ("Merge origin/main with conditional words
  always on"), whose word rule has the same consequences.
- **Its exact scope.** An input changes only when an `is` assignment's
  value holds an item position, as Specification defines it, whose
  expression is one identifier token, or a conditional standing in an item
  position with such a branch at any depth of its nested branches, and then
  only by word markers on those identifiers. Every other token, node and
  position of its syntax tree is unchanged. Each marked identifier reads by
  the word rule, with exactly these effects, counted over the 8,353 changed
  inputs of the final differential in Preparation checks:
  - **(a)** A bare item whose name is undefined, which raised
    `ReferenceError` when it was evaluated or when a class-level rule holding
    it was declared, now reads as its text, and while undefined it is a
    pending graph node that `why` lists among the sources. 2,112 inputs:
    1,889 now finish with a value where they raised; 214 now stop later, at
    another error, 209 of them at a `ReferenceError` for a later name that is
    not a word, 4 at a `TypeError` and 1 at a thrown value; and 9 no longer
    catch a `ReferenceError` in a `try` block, so 4 end with another value
    and 5 keep their value but run other assertions, 2 of them also building
    other graph nodes.
  - **(b)** An item word whose name is defined, or whose reading does not
    decide the result, because it is not evaluated or the program raises the
    same error either way, keeps that result, but its rendering, the block
    keys of the graph and the output of `why` and `affects` take the word
    form, `target is value` instead of `target=value`. 6,240 inputs: 6,239
    keep their result and change only these outputs, 2,124 of them without
    any error and 4,115 raising the same error either way for a name that
    is not a word, and 1 more has a `why` rule as its result.
  - **(c)** A word whose name has been deleted reads as its text, where the
    reference reading gave `undefined`: after `good = 3`, `xs is [1, good]`
    and `delete good`, `xs` is `[1, "good"]`, where it was `[1, undefined]`.
    1 input.
- **What stays.** A defined name still reads its value. `=`, `:=`, compound
  assignment and `return` values are unchanged and keep the reference
  reading, as do dictionary keys, shorthand entries, spread sources,
  parenthesized items, positional arguments, method-call labels and every
  excluded part of an `is` value. Every program whose `is` values hold no
  such item keeps its parse, syntax tree, positions, rendering, result,

  branch words keep their accepted rendering, so no output of a program
  without item words changes. The cost is the known limitation of
  Rendering: 81 such renderings do not read back as the same statement.
- **Public API.** No public item changes. `crate::expression::visit_children`
  widens from private to `pub(crate)`, and the parser and renderer gain
  private types. The public `generate` and `generate_all` render a tree that
  holds a `UnaryOp::Word` marker in an item position as `target is value`;
  the accepted parser never built such a tree, so only a hand-built one
  renders differently. No version number is changed.

## Errors

- No error type or message is added. A malformed value reports what its `=`
  spelling reports, at the same place, which is one column further right
  when that place follows `is` on its line:

| Exact source | Error |
| --- | --- |
| `a is [A, ` | `SyntaxError("Unexpected end of input")`, line 1, column 10 |
| `a is {k: A` | `SyntaxError("Expected '}' but found end of input")`, line 1, column 11 |
| `a is Light(color=A` | `SyntaxError("Expected ')' but found end of input")`, line 1, column 19 |

- Runtime errors are those of the `=` spelling wherever a name is not a
  word: `a is [(A)]`, `a is [A.x]`, `a is pick(color=(A))`,
  `a is [A for x in [1]]` and `a is [() => A][0]()` raise
  `ReferenceError("A is not defined")` while nothing defines `A`, and so does
  `r is o.m(k=A)` for a method `m`.
- A constructor call with an unknown label raises
  `TypeError("Unknown constructor argument '<name>' for <class>")` before
  any value is read, as at the accepted revision.
- Item words add no nesting level. Nested lists, dictionaries and named
  arguments are rejected where their `=` spellings are, with
  `SyntaxError("Expressions are nested too deeply")` one column further
  right.

## Reference Implementation

- No token, keyword, `Expr`, `Stmt` or `UnaryOp` variant, option, flag or
  public item is added.
- `src/lang/ast/parser/is_assignment.rs` adds the private `Items` mode,
  `Plain` or `Words`, which `is_assignment` sets to `Words` for the value of
  every `is` assignment and restores after it. `Items::mark` wraps an item
  of exactly one identifier token in `UnaryOp::Word`, in place, through
  NUC 93's `is_word`. `item` and `object_item` parse an item at the depth
  and in the context of the accepted item parse, with NUC 94's
  `Branches::Words` while items are words. `starts_item_label` and
  `item_label` parse a constructor label's value as an item at the accepted
  label depth. `without_words`, a worklist over every expression kind except
  function bodies and templates, replaces NUC 94's conditional-only version
  and strips the markers of an assignment target and of a comprehension
  element. `conditions` selects the Python-condition memo of the current
  mode.
- `src/lang/ast/parser.rs` adds the `items` state and the `item_conditions`
  memo. `src/lang/ast/parser/expression.rs` clears the item mode for the
  value of an inner assignment and moves the operator tail of
  `assignment_expression` into `assignment`. `primary.rs` marks list items
  and dictionary values and clears the mode for arrow, lambda and `function`
  bodies; `postfix.rs` routes a constructor label to `item_label`;
  `comprehension.rs` strips the element's markers and clears the mode for
  the filter condition; and `statement.rs` checks with a `debug_assert_eq!`
  that every statement starts outside an item region.
- `src/lang/ast/generator/shown.rs` holds the renderer of every expression,
  `Shown`, with a `Mode` of `Plain`, `Region` or `Position`.
  `Display for Expr` renders in `Plain` mode, which writes exactly what the
  accepted renderer wrote. `src/lang/ast/generator/words.rs` holds
  `WordValue`, which renders a value holding words in `Position` mode, with
  item positions as word positions when the value holds an item word, and
  NUC 94's branch scan. The shared formatting helpers stay in
  `src/lang/ast/generator.rs`, where lists, dictionaries, argument lists,
  signatures and enum members are now written straight into the output
  through a `Joined` adapter instead of being joined from separately
  allocated strings. `src/expression.rs` widens `visit_children` to the
  crate, with explicit lifetimes, for the word scan.
- `tests/item_words.rs`, `tests/item_words_cli.rs` and the terminal unit
  test cover the claims above.
- The root specification, its `is`-assignment and conditional-word
  sections, the consolidated reference with its syntax summary, the README
  and both NUC 0 indexes are synchronized. The specification change is
  prose, and the exports are unchanged.
- `docs/nucleoid.g4` extends the `is`-assignment contract with the item
  positions, their exclusions and their composition with branch words, and
  adds their lowering and their source files. No rule changes, and the
  parse-pass note, which says that word positions never change whether or
  where a pass succeeds or fails, covers item positions as written.

### Measured cost

- Measured before the caller's Rust improvement pass, with release builds
  of the accepted library and of the candidate, without debug assertions,
  linked into one process. Accepted and candidate samples alternate, and
  each figure is a median in milliseconds, accepted first.
- Over the 2,515 programs of the executable corpora, two series of 21
  samples parse in 74.92/75.02 and 75.16/74.90, run in 613.30/606.35 and
  614.05/608.64 and render with `generate_all` in 11.43/9.21 and
  11.54/9.34. Over the 9,529 programs that respell their `=` assignments
  with `is`, they parse in 127.26/127.29 and 127.15/126.55, run in
  1860.79/1846.59 and 1876.07/1859.17 and render in 21.02/17.52 and
  21.10/17.65. Parsing and running are unchanged within noise, and rendering
  is 16 to 19 percent faster.
- Rendering is faster because lists, dictionaries, argument lists,
  signatures and enum members are written straight into the output: on
  generated programs of 1,000 to 8,000 lines of lists, calls and objects,
  `generate_all` takes 0.68 to 0.78 of the accepted time.
- On generated programs of 1,000 to 8,000 short statements, parsing is up
  to 3 percent slower, about 2 percent for Python-style conditionals with or
  without `is`, in 41 samples alternating which side runs first; a
  conditional value renders up to 6 percent slower through the shared
  renderer. Neither shows on the corpora, and the order of the samples alone
  moves other shapes by up to 8 percent.
- Item words cost what NUC 93 and NUC 94 measured for words. A value with
  item words parses 3 to 8 percent slower than the same tokens did, one
  marker node per word, and `xK is [AK, BK]` runs in 9.59 per 1,000 lines
  where the quoted `xK is ['AK', 'BK']` runs in 5.77, because each word that
  nothing defines files a pending graph node.
- The debug command lines of the accepted revision and of the candidate,
  both built with `CARGO_PROFILE_DEV_DEBUG=false`, ran 29 nesting shapes at
  every depth from 15 to 70 after three statement heads, `x is `, `x = ` and
  none: lists, dictionaries, calls, parentheses, labels, subscripts, arrows,
  lambdas, both conditional spellings, consequents, assignments, compound
  assignments, unary operators, `not`, powers, function literals, block
  bodies, `??`, spreads, comprehensions, quantifiers, member chains, method
  labels, block `is` statements and mixtures. No pair overflows sooner on
  the candidate. 36 pairs overflow 1 to 3 levels later, such as lists at 48
