# NUC 93 -- Opt-In Is Assignments

```

Title: Opt-In Is Assignments
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 08-Nov-2026
Requires: 13, 66, 76, 86
```

## Abstract

- Add the opt-in statement `target is value`, which means `target = value`
  for a variable or a property: `status is "open"`, `order.total is 12` and
  `this.name is name`.
- Quotes are optional around a word. When the value is exactly one bare
  identifier, it follows the word rule of [NUC 86](nuc-0086.md): it reads the
  local, variable, class, function or built-in of that name when one exists,
  and otherwise stores its own text. So `a is good` stores `"good"`, and after
  `good = 2` it stores `2` and keeps following `good`.
- The form is enabled explicitly, as [NUC 76](nuc-0076.md) enables C-style
  comments: CLI `--is-assignment`, or the new `is_assignment` field of
  `SyntaxOptions` in Rust. Without it, every program keeps its accepted
  reading, in which `a is good` is the three statements `a`, `is` and `good`.
- It applies only where a statement starts, after a target that `:=`
  accepts, and only when `is` is followed by a token that can begin an
  expression. `is` and `is not` comparisons in conditions and other enclosed
  positions are unchanged.
- `target is value` builds exactly the syntax tree of `target = value`, so
  everything about it follows from `=`. Only a word value adds a marker, the
  new `UnaryOp::Word`, which reads its name by the word rule and renders as
  `target is word`.
- No token, keyword or error message is added. The authoritative contract is
  [Opt-in is assignments](../nucleoid.spec.md#opt-in-is-assignments).
- Accepted: the user requested this feature directly, and the frozen
  candidate meets every hard criterion of the automatic acceptance rule, so
  the user-requested basis applies. The independent evaluator's overall
  decision is also Accepted. Token comparison was skipped as
  `single_proposal`, the rule for a single-proposal request, not a failed
  check; see [Evaluation](#evaluation).

## Motivation

- The user asked for `is` as an assignment keyword, "same as NUC 86 but for
  assigning", with quotes optional: "`a is good` like `a = "good"`", "but
  `good` is defined as variable before then that is `a = good`". World
  models state facts in that shape: an order is shipped, a light is red.
  Writing `light is RED` beside `if light is RED:` reads as one sentence
  pattern, and language models write it naturally.
- At the accepted revision none of the requested statements assigns. Each
  parses as juxtaposed statements and then fails or does something else:
  - `a is good` raises `ReferenceError("a is not defined")` at line 1,
    column 1.
  - `a = 1` then `a is good` raises `ReferenceError("is is not defined")` at
    line 2, column 3.
  - `o = {x: 1}` then `o.x is 5` raises `ReferenceError("is is not defined")`
    at line 2, column 5.
  - `is = 4`, `a = 1` and `a is 5` return `5` without assigning `a`, and
    `is = 0` then `is is 3` returns `3`.
  - With `=`, a word must be quoted or defined: `a = good` raises
    `ReferenceError("good is not defined")` until `good` is defined.
- With the option, a model can state values as words and decide later
  whether a word is just its text or a variable that remaps it. Defining
  `OPEN = "open"` re-evaluates every `is` assignment that names `OPEN`, and
  deleting it returns them to `"OPEN"`.

```
status is OPEN
label is "shipped"
total is 2 + 3
assert([status, label, total], ["OPEN", "shipped", 5])
OPEN = "open"
assert(status, "open")
delete OPEN
assert(status, "OPEN")
```

- The program above runs with the option. It and the other examples of this
  proposal execute as written in
  `tests/is_assignments.rs::the_documented_examples_run_as_written`.

## Rationale

- **Category and mode.** The user requested this concrete feature and
  confirmed the category Syntax enhancement, as for NUC 86, so there was no
  random draw. It runs in single-proposal mode, which skips token comparison.
  Runtime applicability does not apply. No hint was supplied.
- **Opt-in, chosen by the user.** Statement-level `a is good` already parses
  at the accepted revision as the juxtaposed statements `a`, `is` and `good`,
  and NUC 86's test `is_stays_a_name_where_a_statement_can_follow` and its
  specification entry `Nucleoid keeps is as an ordinary name where a
  statement can follow` pin that reading for `value is "EXACT"`,
  `a is 1 ? 2 : 3`, `{ a is b }` and more. Reading `is` as an assignment by
  default would change accepted programs and fail those tests. The caller
  showed the user this collision, and the user chose an opt-in flag, as
  NUC 76 did for `//` comments.
- **Rejected: an accepted-first retry, as NUC 86 uses.** NUC 86 turns `is`
  into an operator only when the accepted reading fails to parse. The
  requested statements already parse at the accepted revision, as juxtaposed
  statements, so a retry would never reach them.
- **Rejected: a keyword or a new token.** `is` names variables, parameters,
  properties and functions in accepted programs (`is = 5`, `def f(is) => is`,
  `{is: 1}`). The lexer is unchanged; the parser recognizes the identifier
  `is` only after a complete statement target.
- **Statements only.** Inside an expression, `is` is NUC 86's comparison, and
  an assignment there would be ambiguous with it. So the form applies only
  where a statement starts, and `flag is (value is EXACT)` both assigns and
  compares. Template interpolations and `parse_expression_with_options` read
  an expression, so their top level is unchanged, while the block bodies of
  function literals are statement positions wherever they appear.
- **Targets that `:=` accepts.** The target rule is the one that compound
  assignment ([NUC 13](nuc-0013.md)) and `:=` ([NUC 66](nuc-0066.md)) already
  share: names and dotted paths rooted in a name, `this`, `self` or `$Class`.
  Calls, subscripts, literals, operators and bare `this` cannot be assigned,
  so `f() is 5` and `a[0] is 1` keep their accepted readings rather than
  becoming new errors.
- **The token after `is`.** `is` begins an assignment only when the next
  token can begin an expression. That keeps `a is: T` (the declaration
  `is: T`), `a is = 5`, `a is := 5` and `a is += 1` (assignments to a variable
  named `is`), and `a is` at the end of a line (two statements), and it
  leaves every operator or keyword after `is` to its accepted reading.
- **Exactly the `=` tree.** `target is value` lowers to what `target = value`
  builds, with the value parsed as `=` parses it at statement level, in the
  same context and at the same nesting depth. Every existing behavior of `=`
  therefore applies unchanged: standing declarations and their dependencies,
  property and class-level rules, `this.p` in constructors, `.value`
  snapshots, transactions, chains such as `a is b = c`, `a is suppose:` with
  a body, and the errors and their positions. No runtime path is added.
- **The word rule.** The user's "quotes optional ... but if `good` is defined
  ... `a = good`" is NUC 86's *variable, else text* rule, reused unchanged
  through its `read_word`: a defined name reads as itself, and an undefined
  one stores its text and records a dependency on the variable of that name,
  so a later definition re-evaluates the assignment and a deletion returns it
  to the text. Quoted values are ordinary strings, and parentheses, as in
  `a is (good)`, require a defined name, as with NUC 86.
- **The word marker.** A word assignment must differ from `target = word`,
  which raises for an undefined name, so it needs a marker in the syntax
  tree. The smallest change that keeps every walker correct is one more
  `UnaryOp` variant, `Word`, whose operand is the identifier, following the
  existing `UnaryOp::Positional` marker. Every walker already visits a unary
  operand, so dependency collection, `.value` freezing, class-reference
  scans, cycle checks and the protected-assertion walker need no change.
  Only evaluation (through `read_word`), rendering, the `why` rule text and
  static class-rule validation (which skips a word, as it skips NUC 86's)
  change. Rejected:
  - a new `Expr` variant, which every exhaustive expression match, renderer,
    evaluator dispatch and walker would have to handle;
  - a new `Stmt` variant or a flag on `Stmt::Assign`, which would split the
    one assignment path that standing declarations, properties, class rules,
    blocks and `suppose` share, and break every pattern on the public variant;
  - lowering a word to a string or an identifier, which loses either the
    variable read or the text fallback and its dependency;
  - reusing `BinaryOp::Is`, which is a comparison.
- **Rendering.** A non-word `is` assignment renders as its `=` spelling, as
  NUC 86 renders an ordinary `is` as `==`. A word assignment renders as
  `target is word`, so `{ a is good }` and `{ a = good }` are different
  block keys and `why` shows the rule as written. No path re-parses rendered
  statements: parsing enters only through `Runtime::run`, the checks and the
  public `parse*` functions, while graph keys, `--graph` output and `why`
  rules are labels, and the REPL and terminal submit source text.
- **Opt-in readings of NUC 86's protected forms.** With the option, a
  program is still read with the accepted grammar first, now including `is`
  assignments, and is read again with NUC 86's comparison only when that
  fails. NUC 86's `while` and `suppose` header checks run in the same mode.
  So statements that NUC 86 keeps as juxtaposed names take new readings, but
  only with the option: `value is "EXACT"` assigns, `while v is x: T` is a
  loop on the comparison `v is x`, and `suppose v is x: T` is a `suppose`
  block with that premise. These are new opt-in readings, listed in the
  Specification; the default mode keeps every accepted reading.
- **Diagnostics.** No message is added. A malformed value reports what its
  `=` spelling reports at the same place.
- **Not added.** `is` assignments inside expressions, `is not` as a negated
  assignment, a REPL command or terminal toggle, automatic detection, and a
  lexer change that would let a regular expression follow `is`.
- **Optional evidence.** Advisory usefulness is unscored (`missing_rubric`),
  not zero. Strategy learning is `not_configured`; this revision is
  unattributed, without a policy, selection receipt, trial or reward.

## Specification

- The normative contract is
  [Opt-in is assignments](../nucleoid.spec.md#opt-in-is-assignments).

### Activation and API

- `SyntaxOptions` gains the public field `is_assignment: bool`, which defaults
  to false. `Runtime::new()`, `Runtime::default()`, `Runtime::check` and every
  parsing function without options keep the accepted grammar.
- `Runtime::with_options(SyntaxOptions { is_assignment: true, ..SyntaxOptions::default() })`
  selects the form for every `run` and template interpolation;
  `Runtime::options()` returns it and `clear()` keeps it.
  `Runtime::check_with_options`, `parse_program_with_options`,
  `parse_with_options`, `parse_expression_with_options` and
  `statement::compile_with_options` accept it. It combines with
  `c_style_comments`.
- `nucleoid --is-assignment` enables it for file runs, the plain and
  redirected REPL and the terminal workspace, with `--json`, `--graph` and
  `--c-style-comments`. `.clear` keeps it. REPL continuation and terminal
  indentation are lexical and unchanged.

### Syntax

- With the option, the statement parser reads the leading expression of an
  expression statement as before. It is the target of `target is value` when
  all of these hold:
  - `:=` accepts it as a target: a name or a dotted path rooted in a name,
    `this`, `self` or `$Class`, possibly grouped in parentheses, where a root
    `this`, `self` or `$Class` needs a property, a link may be a state
    version, and a path has at most 128 links;
  - the next token is the identifier `is`, with nothing between them but
    spaces or comments on the same line;
  - the token after `is` can begin an expression: an identifier, a `$Class`
    reference, a number, a string, a template, a regular expression, `(`,
    `[`, `{`, `!`, `-`, `+`, or one of the keywords `true`, `false`, `null`,
    `None`, `undefined`, `this`, `self`, `super`, `new`, `delete`,
    `function`, `not` and `typeof`.
- Every other statement keeps the accepted reading. In particular `:`, `=`,
  `:=`, every compound assignment operator, every other operator and
  punctuation, a keyword such as `if`, `else`, `and`, `or` or `of`, and the
  end of the line or input after `is` leave `is` a name that begins the next
  statement.
- The value is parsed exactly as the value of `=` in an expression statement:
  in the ordinary context, not enclosed, and at the same nesting depth. It
  ends where that value would end, and the statement then continues as an
  expression statement that began with `target = value`: a following `:=`
  and a `suppose` value with its premise and suite are handled exactly as for
  `=`.
- The value is a word when it is exactly one identifier token. Keywords,
  `$Class` references, paths, calls, subscripts, versions, operator
  expressions and parenthesized operands are not words.
- Positions: every statement position, as listed in the specification,
  including the block bodies of function literals inside expressions and
  template interpolations. Not: conditions, headers, enclosed positions,
  named arrow bodies, enum members, the top level of a template
  interpolation and the top level of `parse_expression_with_options`.
- A `/` directly after `is` is division, as after any name, because the lexer
  is unchanged; a regular-expression value is written in parentheses, as in
  `pattern is (/colou?r/)`.
- A statement that starts with `why`, `affects`, `stated` or `derived`
  followed by `is` keeps its accepted reading as a reasoning selection of the
  name `is`, because that leading expression is not a target; such variables
  are assigned with `=`.

### Semantics

- A non-word `target is value` is `target = value` in every respect,
  including its syntax tree.
- A word assignment stores the value of the word: the local, variable, class,
  function or built-in global of that name when one exists, read as an
  identifier is and recording what that read records, and otherwise the
  string of its spelling, recording a dependency on the variable of that
  name.
- A standing declaration, property, constructor property or class-level rule
  assigned from a word re-evaluates when the variable of that name is
  defined, changed or deleted, inside a `suppose` block too, whose rollback
  restores it. A later function definition of that name also wakes it. A
  later class declaration does not, as NUC 86's evaluation recorded for word
  comparisons: after `k is Order` and then `class Order:`, `k` stays
  `"Order"`. No executable case pins that inherited behavior.
  While the name is undefined it is a pending graph node, which `why` lists
  among the sources and whose `affects` lists nothing until it is defined.
- Static class-rule validation does not require a word to be defined. It
  still requires every other name, so `$Order.bad is (MISSING)` raises
  `ReferenceError("MISSING is not defined")` when declared.
- A word assignment renders as `target is word` in statement rendering, block
  graph keys, `--graph` output and the `rule` of `why` and `affects`; a word
  value alone renders as the word.

```
class Order(total):
    this.total is total
    this.stage is NEW
$Order.state is OPEN
$Order.big is $Order.total > 10
first = Order(5)
second = Order(20)
assert([first.state, second.state], ["OPEN", "OPEN"])
assert([first.stage, second.big], ["NEW", true])
OPEN = "open"
assert([first.state, second.state], ["open", "open"])
```

```
value is EXACT
if value is EXACT:
    hit is "yes"
flag is (value is EXACT)
xs = ["EXACT", "B"]
found is xs.filter(x => x is EXACT)
assert([hit, flag, found], ["yes", true, ["EXACT"]])
EXACT = "B"
assert([value, flag, found], ["B", true, ["B"]])
```

### Compatibility

- Without the option, every input keeps its accepted parse, syntax tree,
  rendering, result, assertions, runtime errors, JSON and graph: the only
  new parser step is a check of the option, and `UnaryOp::Word` is never
  built. A differential in Reference Implementation confirms it.
- With the option, every program that contains no statement of this form
  reads and runs as without it. These default readings change with the
  option, each because it contains such a statement; they are new opt-in
  readings:

| Program | Without the option | With the option |
| --- | --- | --- |
| `value is "EXACT"` | `value`, `is`, `"EXACT"` | `value = "EXACT"` |
| `a is 1 ? 2 : 3` | `a`, `is`, `1 ? 2 : 3` | `a = 1 ? 2 : 3` |
| `{ a is b }` | a block of `a`, `is`, `b` | a block assigning the word `b` |
| `while v is x: T` | `while`, `v`, `is`, `x: T` | a loop on `v is x` with the body `T` |
| `suppose v is x: T` | `suppose`, `v`, `is`, `x: T` | a `suppose` block with the premise `v is x` and the body `T` |
| `while v is suppose:` with an indented `a = 1` | `while`, `v`, `is`, a `suppose` block | `while`, then `v = suppose:` with that body |
| `while v is assert: a, b` | `while`, `v`, `is`, `assert: a, b` | `SyntaxError("Unexpected ','")`, line 1, column 23 |
| `a is x: T` | `a`, `is`, `x: T` | `SyntaxError("Unexpected ':'")`, line 1, column 9 |

- The public `SyntaxOptions` struct is not `#[non_exhaustive]` and gains a
  field, so a downstream struct literal that names every field stops
  compiling, and the public `UnaryOp` enum gains `Word`, so an exhaustive
  downstream match stops compiling. Both need human SemVer review. No
  project version is changed.

## Errors

- No error type or message is added. A malformed value reports the
  diagnostic of its `=` spelling at the same place, which is one column
  further right when that place follows `is` on its line:

| Exact source, with the option | Error | Its `=` spelling |
| --- | --- | --- |
| `a is (1 + )` | `SyntaxError("Unexpected ')'")`, line 1, column 12 | the same, column 11 |
| `a is [1, ` | `SyntaxError("Unexpected end of input")`, line 1, column 10 | the same, column 9 |
| `a is {k: }` | `SyntaxError("Unexpected '}'")`, line 1, column 11 | the same, column 10 |
| `a is good.` | `SyntaxError("Expected a property but found end of input")`, line 1, column 11 | the same, column 10 |
| `a is c ? 1` | `SyntaxError("Expected ':' but found end of input")`, line 1, column 11 | the same, column 10 |
| `a is b := 1` | `SyntaxError("Invalid value assignment target")`, line 1, column 8 | the same, column 7 |
| `a is 1 + ` and a newline | `SyntaxError("Unexpected end of line")`, line 2, column 1 | the same |

- Runtime errors are those of `=`: `a is (good)`, `a is good.x` and
  `a is not good` raise `ReferenceError("good is not defined")` at line 1,
  column 1 while nothing defines `good`; `a@first is 1` raises
  `TypeError("State versions are read-only")`; `$Order.bad is (MISSING)`
  raises `ReferenceError("MISSING is not defined")` when declared.
- `a = 1` then `a is b is c` assigns the word `b`, then runs the juxtaposed
  statement `is`, which raises `ReferenceError("is is not defined")` at
  line 2, column 8, and the transaction rolls back, leaving `a` undefined.
- The opt-in syntax errors of `a is x: T` and `while v is assert: a, b` are
  listed under Compatibility.

## Reference Implementation

- `src/lang/ast/mod.rs` adds `UnaryOp::Word`. No `Expr` or `Stmt` variant,
  token or keyword is added.
- `src/lang/ast/parser/statement.rs` moves the expression-statement branch of
  `statement_inner` into `expression_statement`, which consults
  `starts_is_assignment`, and `expression_tail`, which keeps the accepted
  `:=`, `suppose` and plain-statement handling in its accepted order.
- The new private child module `src/lang/ast/parser/is_assignment.rs` holds
  the token rule (`begins_expression`), `starts_is_assignment`, which checks
  the option first, then the next token, the token after it and the target
  through `PathTarget::of`, the plain-path check in
  `src/lang/ast/parser/expression.rs` that `check_path_target` also uses, and
  `is_assignment`, which parses the value at the depth of `=`'s value,
  finishes the statement through `expression_tail` and marks a one-token
  identifier value as a word.
- `src/lang/ast/operator.rs` evaluates `UnaryOp::Word` through NUC 86's

  `target is word`. `src/reasoning/rules.rs` writes the `why` rule of a word

- `src/main.rs` adds `--is-assignment`.

### Measured cost

- Measured with release builds of the accepted library and of the final
  candidate, timing `Runtime::check_with_options` and `Runtime::run` on
  generated programs of 1,000, 2,000, 4,000 and 8,000 lines. Each figure is
  the median of 15 runs on the development machine, in milliseconds.
- Without the option, the parser adds one test of the option per expression

### Findings

- **Minor, documentation, option on only: "the same line" is too narrow.**
  Inside parentheses and brackets, layout drops line breaks, so with the
  option a function-literal body inside a call can put `is` on the line
  after its target and still assign, as `=` does there. For example,
  `f(() => {`, `status`, `is OPEN`, `return status`, `})` on five lines
  assigns `status`. The Syntax section above, the specification and the
  consolidated reference still say "on the same line".
- **Minor, documentation, option on only: the Compatibility table is not
  exhaustive.** It lists the opt-in readings of NUC 86's protected forms,
  but others change too. `suppose is is 5:` with a body is a `suppose` block
  on a comparison at the accepted revision. With the option it raises
  `SyntaxError("Unexpected ':'")`, because `suppose` is a plain target, and
  `while suppose is (good):` also changes reading. Each follows from the
  stated rule and contains the statement form.
- **Info, SemVer, for the human owner.** `SyntaxOptions` gains a public field
  and `UnaryOp` gains `Word`, so downstream struct literals that name every
  field and exhaustive matches stop compiling. The `Debug` output of
  `SyntaxOptions` and `Runtime` now shows `is_assignment`. No project version
  was changed.
- **Info.** Without the flag, the only visible command-line change is the new
  `--is-assignment` line of `--help`.
- **Info.** With the option, `a is a` stores `"a"` without an error, while
  mutual words such as `a is b` and then `b is a` raise
  `TypeError("Circular Dependency")` and roll back.
- The proposer's other claims reproduced: the test totals and names, the
  corpus claim, the error table and the mutant exclusions.
