```

Requires: 8, 18, 45, 57, 59, 60, 61, 68
```

## Abstract

- Lists and class instance lists gain the read-only queries `max` and `min`.
  `RECEIVER.max()` returns the largest numeric value of the items and
  `RECEIVER.max(selector)` the largest `selector(item)`; `min` returns the
  smallest.
- The result is exactly `Math.max` or `Math.min` applied to those values in
  order. Each value is converted with the numeric conversion of the Math
  helpers, a NaN value makes the result NaN, an undefined value makes it
  undefined, which a declaration stores as `null`, and an empty receiver
  gives `-Infinity` for `max` and `Infinity` for `min`, as `Math.max()` and
  `Math.min()` do.
- The selector is called once for every item, in order, with only the item,
  as [NUC 68](nuc-0068.md)'s `sum` calls its selector. A supplied selector
  that is not a function raises `TypeError("max expects a function")` or
  `TypeError("min expects a function")`.
- `max` and `min` follow [NUC 61](nuc-0061.md)'s shared query rules beside
  `sum`. They accept every receiver the list queries accept, read the
  receiver before their arguments, never write it, and stay live in
  declarations and class-level rules like `map`, `reduce` and `sum`.
- At the accepted revision these calls raise
  `TypeError("<receiver>.max is not a function")` and its `min` counterpart.
  No syntax, keyword, error type or public Rust API is added. The
  authoritative contract is
  [List and population extremes](../nucleoid.spec.md#list-and-population-extremes).

## Motivation

- World models keep extremes: the highest bid, the hottest and coldest
  reading in each room, the cheapest open offer, the peak load of a
  building. Each is an extreme over a list or over a class's instances, and
  it has to stay true while the model changes.
- The accepted spelling is a comparing `reduce`. For a list,
  `high = temps.reduce(lambda a, b: a > b ? a : b)` is 19 lexer tokens where
  `high = temps.max()` is 7. For a population,
  `top = Bid.map(bid -> bid.amount).reduce(lambda a, b: a > b ? a : b)` is
  28 tokens where `top = Bid.max(bid -> bid.amount)` is 12, and the
  class-level rule
  `$Room.high = Sensor.filter(sensor -> sensor.room == $Room).reduce(lambda a, s: Math.max(a, s.temp), -1 / 0)`
  drops from 40 tokens to 25.
- The comparing `reduce` is easy to get subtly wrong. Without a seed an empty
  list gives `null`, and a one-item list gives its item unconverted, so
  `["10"].reduce(lambda a, b: a > b ? a : b)` is the string `"10"`. A seed
  has to be spelled
  `-1 / 0` or `Number.NEGATIVE_INFINITY`: `Infinity` is not defined,
  `Math.max` is not a function value, so `xs.reduce(Math.max)` raises
  `TypeError("reduce expects a function")`, and `Math.max(...xs)` is a
  `SyntaxError`. A ternary comparison compares strings as text, so
  `["10", "9"]` gives `"9"`.
- Python's `max` and `min`, Kotlin's `maxOf` and `minOf`, C#'s `Max` and
  `Min`, Ruby's `max` and `min` and Java streams' `max` and `min` name the
  operation. JavaScript has only `Math.max(...)`, and LLM-written code such
  as `orders.max(o => o.total)` raises
  `TypeError("orders.max is not a function")` at the accepted revision.
- NUC 68 left minimum and maximum over lists out of `sum`; this NUC adds
  them with the same receivers, selector and liveness rules.

## Rationale

- **Category and mode.** The caller selected the Utility enhancement
  category by one uniform draw over the four eligible registry categories,
  index 2 with probability 1/4 and no redraw, in continuous mode, so the
  token non-regression gate applies. Each new case is paired with the most
  compact accepted-syntax counterpart found, recorded in the evaluation
  baseline.
- **Two more shared queries.** `max` and `min` are operations of the
  read-only list query that serves `map`, `filter`, `reduce`, `sum` and
  NUC 61's queries. Lists, list properties, call results such as
  `filter(...)`, `map(...)` and `slice(...)`, ranges, `.value` snapshots,
  selected versions, class instance lists and `Name.list()` therefore accept
  them through one implementation, with the receiver, argument and liveness
  rules they already share.
- **Exactly the Math helpers.** The values, after the selector, are passed to
  the function that `Math.max` and `Math.min` call. Conversion, NaN, the
  undefined gate, infinities, ties between signed zeros and the empty result
  are therefore those of `Math.max(v1, v2, ...)` by construction, not a
  second set of rules that could drift.
- **A numeric result.** `max` returns a number, as `Math.max` and `sum` do:
  `["10", "9"].max()` is `10`, `[true, false].max()` is `1`, and the maximum
  of two dates is the later time in milliseconds.
- Rejected: returning the extreme item itself, as Python's `max` does. For
  numbers both agree; for strings, booleans and dates the item would differ
  from what `Math.max` and `sum` return. The item with the largest value is
  still a `find` away: `best = Bid.find(bid -> bid.amount == top)`.
- Rejected: comparing strings as text, as Python does. Nucleoid compares
  numbers here, so `["apple", "pear"].max()` is NaN, as
  `Math.max("apple", "pear")` is.
- **Empty receivers are the identities.** `[].max()` is `-Infinity` and
  `[].min()` is `Infinity`, as `Math.max()` and `Math.min()` are. The result
  stays a number, `Bid.max(bid -> bid.amount) > reserve` is `false` before
  any bid, and the extreme of two lists is the extreme of their extremes
  even when one is empty.
- Rejected: raising an error for an empty receiver, as Python does. A
  population is empty before its first instance is created, and a live
  declaration over it must have a value rather than fail the statement that
  declares it.
- Rejected: `null` for an empty receiver, as Kotlin's `maxOrNull` and an
  unseeded `reduce` give. A declaration would then store `null`, which reads
  as a missing value rather than as an extreme of nothing, and comparisons
  and arithmetic on it would follow the null rules instead of the numeric
  ones.
- **Undefined stays unknown.** An undefined item or selector result makes the
  result undefined, which a declaration stores as `null`. This is the rule of
  the Math helpers' undefined gate and of `sum`, so `Bid.max(b -> b.amount)`
  waits for every amount to be defined. An undefined value outranks a NaN
  value, as in `Math.max`.
- **No artificial null read.** `max()` and `min()` read items, not bindings,
  so a `null` item counts `0` and does not settle a declaration to `null`, as
  in `sum` and in `Math.max(null, -1)`. A selector's own reads follow the
  existing rules: `Gauge.max(gauge -> gauge.level)` over a `null` level
  settles a declaration to `null`, as the same callback does in `map`.
- **Signed zeros by parity, not by JavaScript.** A tie between `0` and `-0`
  gives the same result as `Math.max` or `Math.min` on the same values in the
  same order. That parity is the contract, and the specification, not
  JavaScript, is the authority. The accepted Math helpers fold with Rust's
  floating-point maximum and minimum, which leave the sign of a zero tie
  unspecified, so the language does not otherwise fix the sign of a zero tie,
  as [NUC 23](nuc-0023.md) fixed none for `Math.saturate`. The current x86-64
  reference build keeps the later zero: there `[0, -0].max()` is `-0` and
  `[-0, 0].min()` is `0`, exactly as `Math.max(0, -0)` and `Math.min(-0, 0)`
  are, where JavaScript gives `0` and `-0`. That result describes the build,
  not a promise of the language. Rejected: special-casing zero ties to match
  JavaScript, which would make `xs.max()` and `Math.max` disagree.
- **The selector is called like `map`'s callback.** It runs once per item, in
  order, with only the item; further parameters stay `null`. Every item is
  visited even after the result has become NaN or undefined, so every item's
  reads are dependencies, as in `map` and `sum`.
- **A supplied selector must be a function.** Any other first argument,
  including `null`, raises `TypeError("max expects a function")` or
  `TypeError("min expects a function")` after the arguments are evaluated,
  even on an empty receiver, as `sum`, `map` and `reduce` raise for their
  callbacks.
- Rejected: reading a number argument as a second operand or as Python's
  `default`. `xs.max(5)` stays an error rather than silently meaning
  `Math.max(xs.max(), 5)`; `Math.max(xs.max(), 5)` states it.
- **Extra arguments** are evaluated once, left to right, and ignored, as
  every list query does.
- **Instance lists.** On a class name, `Name.max(...)` and `Name.min(...)`
  are population queries even when the class declares instance methods
  `max` or `min`, as NUC 68 made `Name.sum(...)`. The methods stay reachable
  through each instance, `gauge.max()`, and `Gauge.max(each -> each.max())`
  takes their maximum.
- **Bounded cost.** The receiver and the arguments are evaluated once per
  call, the selector once per item, and the comparison is one linear fold.
  The call keeps its ordinary rendering in graph keys and `why`. Nothing is
  copied or expanded beyond the selected values, so cost and rendered size
  stay linear in the receiver and the source.
- **Not added.** A global `max(...)` or `min(...)`, `Math.max` over a list,
  spread arguments, `maxBy`, `minBy` or other queries that return the extreme
  item, comparisons of strings as text, `default` values, property-name
  selectors and averages.

## Specification

### Extremes

- `RECEIVER.max()` returns the largest of the receiver's items and
  `RECEIVER.max(selector)` the largest `selector(item)` for every item;
  `RECEIVER.min()` and `RECEIVER.min(selector)` return the smallest. The
  result is `Math.max(v1, v2, ...)` or `Math.min(v1, v2, ...)` over those
  values, in receiver order.
- The receiver is a list, however it is reached: a variable, a property, a
  call result such as `filter(...)`, `map(...)`, `slice(...)` or
  `concat(...)`, a range, a literal, a `.value` snapshot or a selected
  version. It may also be a class's instance list, named by the class or by a
  variable that holds the class, in population order; a range of one and
  `Name.list()` are lists.
- An empty receiver gives `-Infinity` for `max` and `Infinity` for `min`.

```
temps = [18, 24, 9]
high = temps.max()
low = temps.min()
assert: high, 24
assert: low, 9
temps.push(30)
assert: high, 30
temps = []
assert: high, Number.NEGATIVE_INFINITY
assert: low, Number.POSITIVE_INFINITY
trip = {legs: [{km: 5, mins: 10}, {km: 12, mins: 30}]}
fastest = trip.legs.max(leg -> leg.km / leg.mins)
trip.legs.push({km: 3, mins: 4})
assert: fastest, 0.75
```

```
class Bid(amount, live):
    this.amount = amount
    this.live = live
highest = Bid.max(bid -> bid.amount)
assert: highest, Number.NEGATIVE_INFINITY
first = Bid(120, true)
second = Bid(90, false)
third = Bid(150, true)
open = Bid.filter(bid -> bid.live).min(bid -> bid.amount)
recent = Bid[-2:].min(bid -> bid.amount)
assert: highest, 150
assert: open, 120
assert: recent, 90
```

### Conversion and special values

- Each compared value, an item or a selector result, is converted with the
  numeric conversion of `-`, `*` and the Math helpers: a number is itself;
  `null`, `false`, an empty or whitespace-only string and an empty list are
  `0`; `true` is `1`; a numeric string, after trimming, is its number; a
  one-item list is its item's number; a date is its time in milliseconds;
  objects, instances, classes, functions, regular expressions, other strings
  and longer lists are NaN.
- The result is the converted number, never the item: `["10", " 7 "].max()`
  is `10`.
- A NaN value makes the result NaN. Infinities compare as 64-bit floating
  point.
- An undefined value makes the result undefined, which a declaration stores
  as `null`, even when another value is NaN. Every item is still visited.
- `max()` and `min()` read items, not bindings: a `null` item counts `0`
  without settling a declaration to `null`. Reads inside a selector follow
  the existing rules, so a selector that reads a `null` binding or property
  settles a declaration to `null`.
- A tie between `0` and `-0` gives the same result as `Math.max` or
  `Math.min` on the same values in the same order; the language does not
  otherwise fix the sign of a zero tie. The current x86-64 reference build
  keeps the later zero, so there `[0, -0].max()` is `-0` and `[-0, 0].min()`
  is `0`, where JavaScript's `Math.max(0, -0)` is `0` and `Math.min(-0, 0)`
  is `-0`.

```
inputs = ["10", " 7 ", "9"]
largest = inputs.max()
smallest = inputs.min()
assert: largest, 10
assert: smallest, 7
inputs.push(null)
assert: smallest, 0
inputs.push("n/a")
assert: Number.isNaN(largest), true
class Gauge(level): this.level = level
pump = Gauge(55)
tank = Gauge(40)
peak = Gauge.max(gauge -> gauge.level)
idle = Gauge(null)
assert: peak, null
idle.level = 70
assert: peak, 70
```

### Selectors

- A selector is called once for every item, in order, with the item as its
  only argument; further parameters are `null`. The call order and the
  argument are those of `map`.
- A supplied first argument that is not a function, including `null`, raises
  `TypeError("max expects a function")` or `TypeError("min expects a function")`,
  even on an empty receiver.
- Every supplied argument, including unused extras, is evaluated once, left
  to right, after the receiver and before the first selector call.
- A null or undefined receiver keeps the existing method-call route: the call
  yields undefined without evaluating its arguments.

```
seen = []
def weigh(item, position):
    seen.push(position ?? item)
    return item * item
items = [3, -4, 2]
def heaviest() => items.max(weigh)
assert: heaviest(), 16
assert: seen, [3, -4, 2]
target = 4
def gap item => Math.abs(item - target)
spread = items.max(gap)
assert: spread, 8
target = -1
assert: spread, 4
```

### Liveness and transactions

- `max` and `min` never write their receiver. A declaration that uses one
  depends on the list or the population, on its argument expressions and on
  whatever the selector reads, as for `map`, `reduce` and `sum`.
- Pushing, popping or replacing a list, creating or deleting an instance, and
  changing a property that a selector reads re-evaluate the declaration.
- In a class-level rule, each instance evaluates its own extreme, and
  `$Class` inside a selector is the instance the rule is evaluated for.
- Selector errors propagate through the existing transaction, so a failed
  standing re-evaluation rolls back the change that triggered it, including
  a list write or a new instance.

```
class Room(name): this.name = name
class Sensor(room, temp):
    this.room = room
    this.temp = temp
$Room.high = Sensor.filter(sensor -> sensor.room == $Room).max(sensor -> sensor.temp)
$Room.low = Sensor.filter(sensor -> sensor.room == $Room).min(sensor -> sensor.temp)
$Room.swing = $Room.high - $Room.low
lab = Room("lab")
Sensor(lab, 21)
probe = Sensor(lab, 25)
assert: lab.swing, 4
probe.temp = 18
assert: lab.swing, 3
attic = Room("attic")
assert: attic.high, Number.NEGATIVE_INFINITY
```

## Errors

- No error type or message format is added. The selector errors reuse the
  message format of the other list queries.

| Condition | Error |
| --- | --- |
| A supplied first argument to `max` that is not a function, including `null`, even on an empty receiver | `TypeError("max expects a function")` |
| A supplied first argument to `min` that is not a function, including `null`, even on an empty receiver | `TypeError("min expects a function")` |
| A supplied argument, including an unused extra, reads an undefined name | `ReferenceError("<name> is not defined")`, raised before the selector is validated |
| The selector raises an error or throws a value | That error or thrown value, unchanged; the triggering change rolls back |
| `max` or `min` on a string, number, boolean, date, function or regular expression | Its accepted `TypeError`, unchanged |

- Calls that raised `TypeError("<receiver>.max is not a function")` or
  `TypeError("<receiver>.min is not a function")` on lists and instance lists
  now return extremes; with a non-function first argument they raise
  `TypeError("max expects a function")` or `TypeError("min expects a function")`
  instead.

## Reference Implementation

- `src/lang/ast/array.rs`: `list_query`, the read-only query shared by lists
  and class instance lists, gains `max` and `min` beside `sum`. The private
  `optional_selector` validates the optional selector for `sum`, `max` and
  `min` with the message format `<query> expects a function`, and the private
  `Runtime::select_items` calls the selector once per item, in order. The
  selected values go to `builtins::math(property, &values)`, the function
  that `Math.max(...)` and `Math.min(...)` call, so the undefined gate, the
  conversion, NaN, zero ties and the empty results are those of the Math
  helpers by construction. Lists reach the query through `call_list_method`
  and populations through `call_class_method`, unchanged, so the receiver and
  the arguments are evaluated once by the existing routes and the
  null-receiver route stays in front of it. `sum` keeps its behavior and only
  shares the selector validation.
- `src/terminal/completion.rs`: the list members that lists and instance
  lists offer include `max` and `min`, and the completion unit test covers
  `scores.max`, `scores.min`, `User.max` and `User.min`.
- `tests/list_extremes.rs` holds 21 tests, one of them limited to x86-64. They
  cover the appended document cases and their 101 assertions, every
  Compatibility row, every receiver kind, bit-exact parity with `Math.max`
  and `Math.min` over 316 lists with and without a selector, including signed
  zeros, NaN and infinities, zero ties in every order, the conversion of 26
  value kinds in three spellings, numeric results rather than items,
  undefined values, `null` items beside selector reads, the selector's
  arguments and visit order, selector validation and argument order for both
  queries, once-only evaluation of the receiver, the selector and extras,
  graph dependencies, populations gaining and losing instances, class-level
  rules, unchanged forms and errors, the population queries beside instance
  methods `max` and `min`, rendering in `why`, rollback compared with a
  control runtime, and 20,000-item extremes that call their selector exactly
  20,000 times per query.
- Extra arguments are checked with values that would change the result if
  they were compared: `[1, 2].max(value -> value, 99)` is `2`,
  `[1, 2].min(value -> value, -99)` is `1` and
  `[1, 2].max(value -> -value, 5)` is `-1`. On empty receivers an extra is
  never a default: `[].max(value -> value, 5)` is `-Infinity` and
  `[].min(value -> value, -99)` is `Infinity`. With `Item(1)` declared and
  `grow(size)` creating `Item(size)` and returning `item -> item.size`,
  `Item.max(grow(9))` and then `Item.min(grow(-9))` both give `1`: each call
  reads the population before its argument creates the new instance.
- Zero ties are guarded on every platform by the parity test, which compares
  each list extreme bit for bit with `Math.max` or `Math.min` on the same
  values in the same order. The x86-64 test asserts the later-zero results,
  which differ from JavaScript's; it pins what the current compiler produces
  for the host maximum and minimum, which Rust leaves unspecified for zero
  ties, not a promise of the language.
- Expression results that must be NaN are checked as `String(...)` equal to
  `"NaN"` or by their bits, because `Number.isNaN` is also true for
  undefined.
- The required Rust improvement pass ran before the freeze and changed only
  `tests/list_extremes.rs`, still 21 tests: it strengthened the extra-argument
  rows and the population-order rows above, confirmed with deliberately
  broken runtimes that they catch extras being compared, an extra used as the
  empty result and instances read after the arguments, and left `src/`
  unchanged.
- `tests/value_assignment.rs`: NUC 66's whole-corpus count changes from 791 to
  802 cases. Its list of titles that use `:=` is unchanged, because no
  appended case uses `:=`.
- `tests/dataset.rs` counts 547 specification records and 1,211 synthesized
  records, with the new shard pinned at eight.
- The root specification, executable reference, README, examples, the
  consolidated reference with its built-in table, error table and syntax
  summary, both NUC 0 indexes, a new canonical
  `dataset/nucleoid.synth.47.jsonl` with eight records, the regenerated
  specification export and the generated specification tests are
  synchronized in the isolated candidate. The export gains eight records and
  the generated tests eight functions; every existing record and test is
  byte-identical.
- No dependency, MSRV, edition, project version or public Rust API changes:
  `list_query`, `select_items` and `optional_selector` are crate-private, and
  `builtins::math` was already public. The new results in the Compatibility
  table are observable language changes for human SemVer review.
