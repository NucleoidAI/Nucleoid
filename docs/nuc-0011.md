# NUC 11 -- Reasoning Operations

```
NUC: 11
Title: Reasoning Operations
Author: Can Mingir <canmingir@gmail.com>
Status: Draft
Type: Standards Track
Created: 09-Aug-2026
Requires: 1, 2, 3, 4, 5, 9, 10
```

## Abstract

- Specifies the operations that reason over the logic graph rather than extend it.
- Every operation takes a **selection** -- a set of graph nodes -- and returns one, so operations compose.
- `|>` chains them left to right: `alarm |> why |> stated |> affects`.
- **Stages** walk the graph: `why`, `why not`, `affects`, `rules`, `conflicts`, `describe`, `export`, `depth`.
- **Filters** narrow a selection: `stated`, `derived`, and the list functions of [NUC 10](nuc-0010.md).
- **Terminals** end a chain with a value or an effect: `all`, `any`, `retract`, `require`.
- **`suppose`** scopes a chain to a world that is discarded, and `diff` selects what changed in it.

## Motivation

- A world model that cannot be interrogated cannot be corrected, and a conclusion no one can trace is indistinguishable from a hallucination.
- The runtime already derives `socrates.mortal`, but nothing in the language asks it *why*, so the derivation is visible to the implementation and to no one else.
- An absent conclusion is the more common failure. A model that says `null` gives no hint whether the rule is missing, its input is missing, or its condition was not met.
- Single operations answer single questions. The questions worth asking are compound: *which of the facts behind this alarm were stated rather than derived, and what else rests on them.*
- Answering that with separate operations means moving results out of the runtime and back in by hand, which is where a world model stops being one thing.
- An LLM proposing a change needs to know what the change would do before committing it, which today means committing it and undoing it by hand.
- Rules written incrementally across sessions overwrite each other silently, because later rules win and nothing reports that an earlier one stopped applying.
- A model is written by one session and read by another, so it must be possible to ask the runtime what it currently holds without reading the transcript that built it.

## Rationale

- **One currency makes composition possible.** Every operation takes a selection and returns a selection. An operation returning a bespoke shape would end the chain at itself, which is what forces reasoning back out into the caller.
- **A selection is a list.** It is a list of steps, so `filter`, `map`, `length` and the rest of [NUC 10](nuc-0010.md) already work on it and no parallel collection vocabulary is introduced.
- **`|>` over method chaining.** `alarm |> why |> affects` costs fewer tokens than `affects(why(alarm))` and reads in the order it happens, where the nested form reads inside out. Method form would need every stage to be a member of the selection type, which makes user code and reasoning code compete for the same names.
- **Chains are declarative.** `risk = alarm |> why |> stated` is a dependency like any other expression and re-derives when a rule behind `alarm` changes. A stale answer about a live model is worse than no answer.
- **The dependency edges are the derivation.** A property knows what it was computed from, so an explanation is a walk backwards over edges the runtime already maintains. Recording provenance separately would create a second copy of the truth, free to disagree with the first.
- **`affects` is `why` in the other direction.** One walks `dependencies`, the other walks `dependents`. They are specified together because a design that explains a value but cannot say what rests on it is only half an account.
- **Stages are transitive and idempotent.** `why` reaches every ancestor, so `why |> why` selects what `why` already did. A stage that went one step would make depth the caller's problem; `depth` makes it explicit where it is wanted.
- **`source` was dropped.** Whether a node is stated or derived is a property of every step, so it is a field rather than an operation, and `stated` and `derived` are filters over it.
- **A chain depends on shape, not only on values.** Every other expression in the language re-derives when a value changes. A derivation also changes when a *rule* changes, even if every value stays put, so chains need a second kind of edge. The runtime already observes edge mutation -- `Transaction` records `DependentAdded` and `DependentRemoved` -- so the event exists and only needs to be published.
- **Reasoning observes the model without joining it.** A chain node is never selected by a stage. Otherwise `exposure = alarm |> affects` would select itself, every `describe` would drag in every observer, and adding an explanation would change what the explanation says.
- **The cost of that is deliberate.** `affects` cannot tell you who is watching a node. Observers are not part of the model, so leaving them out is what keeps a derivation stable under being observed.
- **A selection that escapes a hypothetical is frozen.** It names nodes the rollback may have removed, so it must stop being live at the boundary. This is `.value` from [NUC 5](nuc-0005.md) applied to a selection, rather than a new concept.
- **Keywords lose to variables.** A name is a stage only when no variable of that name is in scope. This keeps the vocabulary strictly additive: no program that already uses `rules` or `source` changes meaning, which is what a language claiming to be a superset owes its inputs.
- **`model` replaced a nullary `export`.** A bare `export` could not be told from a variable, and a root selection is more useful than the one operation it was needed for -- `model |> conflicts` asks a question that had no spelling before.
- **Reasoning that changes the world is a terminal.** `suppose`, `require` and `retract` do not return selections and cannot be chained past.
- **`why` is a special form, not a function.** `why(socrates.mortal)` written as an ordinary call would receive `true` and could no longer tell which node produced it. The operand is resolved to a graph node, not evaluated to a value.
- **A hypothetical is a transaction that always rolls back.** Transactions already record every variable, property, object, class and edge they touch. `suppose` is that machinery with the commit removed, so a hypothetical world is exactly as consistent as a real one.
- **Quantifiers are dependencies and are terminals.** `ready = all c in Check: c.passed` must fall to `false` when a check is added or a `passed` flips, and it reduces a selection to a boolean, so nothing follows it.
- **A constraint is not a rule that throws.** A rule computes a property; a constraint admits or rejects a world and names itself when it rejects one.
- **`retract` is not `delete`.** Deleting erases: it removes the dependent nodes and clears the values they held. Retracting withdraws one support and lets the model settle on whatever still holds, so an instance property that was overriding a class-level rule falls back to the rule rather than vanishing.
- **Reasoning keywords are contextual.** They are recognised in operator position only, so `rules = 1` and `export.push(s)` keep working. A language that aims to be a superset cannot afford to reserve eight common nouns.
- **Rejected: a `violations()` query.** In a committed world it is always empty, because a violating transaction never commits. Testing admissibility is `try` around `suppose`.
- **Rejected: implicit binders.** `all Human: mortal` is shorter than `all h in Human: h.mortal`, but it introduces a scope where bare names silently mean instance properties.
- **Rejected: graded belief.** Weights on facts would buy uncertainty at the cost of the near-determinism that makes the model checkable.
- **Deferred, for want of machinery rather than merit:**
  - *Temporal* -- `history`, `as of`, `since`. Transactions are per-run undo logs cleared at commit, so nothing survives to query.
  - *Abductive* -- goal-seeking, repair, planning. These need search the runtime has no basis for.
  - *Inductive* -- `generalize`, `specialize`. A proposal the runtime cannot itself accept belongs with tooling.
  - *Open-world* -- `unknown`. Distinguishing "not known" from "known null" needs a third state beside `Null`.

## Specification

### Selections

- A **selection** is an ordered set of graph nodes, carried as a list of steps.
- A step has:
  - `node` -- the name the statement is filed under.
  - `holds` -- the value at that node. It is not called `value`, which [NUC 5](nuc-0005.md) reserves for freezing a reading.
  - `rule` -- the statement that produced it.
  - `state` -- `"stated"`, `"derived"`, `"missing"`, `"unsatisfied"` or `"unstated"`.
  - `from` -- the nodes the step points at.
- A node appears once in a selection, however many paths reach it, so every stage terminates.
- A **reference** -- a variable, a property, or a class-level property -- coerces to a selection of one node, resolved rather than evaluated.
- A selection is a list, so the list functions of [NUC 10](nuc-0010.md) apply to it.
- `filter`, `slice` and `sort` over a selection return a selection; `map` returns a plain list.
- `model` is the selection of every node the runtime holds.

```
model |> conflicts

model |> export
```

- A node whose statement is itself a chain is never selected, so reasoning observes the model without joining it.

### Chaining

- `<selection> |> <operation>` applies the operation to the selection.
- `a |> f` and `f(a)` denote the same node; `a |> f(b)` and `f(a, b)` likewise.
- A chain is an expression and a dependency: it re-derives when the nodes it reads change.
- A stage in prefix position takes its operand directly, so `why c` and `c |> why` are the same node.

```
a = 1
b = a + 2
c = b * 2

assert(why c, c |> why)
```

### Grammar

- `|>` binds looser than every other operator and tighter than assignment, so `x = a + 1 |> why` is `x = ((a + 1) |> why)`.
- A stage in prefix position takes a unary operand, so `why a |> affects` is `(why a) |> affects` and `why a + 1` is `(why a) + 1`.
- `not` following `why` is part of the stage name, not the logical operator.
- `|>` is lexed ahead of `||`, which is the only sequence it can be confused with.

#### Contextual keywords

- The names in this document are keywords **unless a variable of the same name is in scope**, in which case they are that variable.
- A program that already uses `rules`, `source`, `export` or `model` as names keeps its meaning, and simply does not have those stages.
- The reasoning vocabulary is therefore additive: no existing program changes meaning by adopting this NUC.

```
rules = [1, 2]

assert(rules.length, 2)
```

- A stage that has been shadowed cannot be reached by any spelling, including the call form.

### Stages

- A stage takes a selection and returns a selection.

| Stage | Selects |
| --- | --- |
| `why` | every node the selection derives from, transitively |
| `why not` | every node blocking a selection that holds no value |
| `affects` | every node derived from the selection, transitively |
| `rules` | the rules and constraints governing the selected types |
| `conflicts` | the properties of the selected types that more than one rule assigns |
| `describe` | each selected node with its derivation and impact attached |
| `export` | each selected node as the statement that states it |
| `depth(n)` | the selection narrowed to nodes within `n` steps of where the chain began |

#### Derivation

- `why` selects the nodes a value follows from, nearest first, including the node itself.

```
a = 1
b = a + 2
c = b * 2

why c
```

- Evaluates to:

```
[
  { "node": "c", "holds": 6, "rule": "c = b*2", "state": "derived", "from": ["b"] },
  { "node": "b", "holds": 3, "rule": "b = a+2", "state": "derived", "from": ["a"] },
  { "node": "a", "holds": 1, "rule": "a = 1", "state": "stated", "from": [] }
]
```

- A `rule` is the statement as the runtime holds it, which is the source normalised rather than the source as typed.
- A property derived from a class-level rule names the rule it was instantiated from, in one step.
- A class-level rule is not itself a node, so it is named by the step it governs rather than selected beside it.

```
class Human(name: str):
    this.name = name

$Human.mortal = true

socrates = Human("Socrates")

why socrates.mortal
```

- Evaluates to:

```
[{ "node": "socrates.mortal", "holds": true, "rule": "$Human.mortal = true", "state": "derived", "from": [] }]
```

- The step is `derived` although its `from` is empty, because it is governed by a rule rather than stated on the instance.

#### Absence

- `why not` selects what stands between a reference and a value.
- `state` is `"missing"` when a rule applies but an input is null, `"unsatisfied"` when a condition was not met, and `"unstated"` when no rule applies.

```
class Review:
    pass

$Review.rate = $Review.sum / 10

review1 = Review()

why not review1.rate
```

- Evaluates to:

```
[{ "node": "review1.rate", "holds": null, "rule": "$Review.rate = $Review.sum / 10", "state": "missing", "from": ["review1.sum"] }]
```

- `why not` over a reference that holds a value selects nothing.

#### Impact

- `affects` selects what would change if the selection changed, in the order it would be re-evaluated.

```
a = 1
b = a + 2
c = b * 2

affects a
```

- Evaluates to:

```
[
  { "node": "b", "holds": 3, "rule": "b = a+2", "state": "derived", "from": ["a"] },
  { "node": "c", "holds": 6, "rule": "c = b*2", "state": "derived", "from": ["b"] }
]
```

- `affects` over a class-level property selects every instance the rule reaches.

#### Consistency

- `conflicts` selects the properties of a type that more than one rule assigns.
- Each step carries `rules`, in declaration order, and `holds`, the one that wins.

```
class Alert:
    pass

if $Alert.level > 1:
    $Alert.tone = "LOW"

if $Alert.level > 2:
    $Alert.tone = "HIGH"

conflicts $Alert
```

- Evaluates to:

```
[{
  "node": "$Alert.tone",
  "holds": null,
  "rule": "if $Alert.level > 2",
  "state": "derived",
  "from": [],
  "rules": ["if $Alert.level > 1", "if $Alert.level > 2"],
  "holds": "if $Alert.level > 2"
}]
```

- The selection is empty when no property is assigned twice.

#### Introspection

- `rules` selects the rules and constraints governing a type, each step carrying `kind`, which is `"rule"` or `"constraint"`.
- `describe` attaches `why` and `affects` to each step of a selection.
- `export` renders each step as the statement that states it.
- What `export` returns over the whole model, run into an empty runtime, reproduces the model.

```
class Human(name: str):
    this.name = name

$Human.mortal = true

rules $Human
```

- Evaluates to:

```
[{ "node": "$Human.mortal", "holds": true, "rule": "$Human.mortal = true", "state": "stated", "from": [], "kind": "rule" }]
```

### Filters

- `stated` narrows a selection to steps whose `state` is `"stated"`.
- `derived` narrows it to the rest.
- Both are the named form of a `filter` over `state`.

```
assert(c |> why |> stated, c |> why |> filter(s => s.state == "stated"))
```

- Compound questions are chains of stages and filters.

```
exposure = alarm |> why |> stated |> affects
```

- `exposure` selects everything resting on a stated fact behind `alarm`, and re-derives when any rule behind it changes.

### Terminals

- A terminal ends a chain, returning a value or performing an effect.

#### Quantification

- `all <name> in <collection>: <expression>` is true when the expression holds for every member.
- `any <name> in <collection>: <expression>` is true when it holds for at least one.
- The collection is a class list, a list, or a selection.
- Both are dependencies on the population and on every property the expression reads.

```
class Check:
    pass

check1 = Check()
check2 = Check()
check1.passed = true
check2.passed = true

ready = all c in Check: c.passed
```

- `ready` is `true`; after `check2.passed = false`, `false`; after `check3 = Check()`, `false`.
- `all` over an empty collection is `true`; `any` over an empty collection is `false`.
- Quantifiers nest, and may be written in a class-level rule or a constraint.
- `all c in Check: c.passed` and `Check.every(c => c.passed)` denote the same node.

- Over a selection, a quantifier states a claim about a derivation.

```
grounded = all s in (total |> why): s.state != "unstated"
```

#### Constraints

- `require <expression>` states a condition that every admissible world satisfies.
- A constraint written over `$Name` applies to every instance of the type, whenever it was created.
- An instance whose inputs are missing is not checked, as with class-level rules.
- A statement that would leave a constraint unsatisfied is rolled back in full.

```
class Account:
    pass

require $Account.balance >= 0

account1 = Account()
account1.balance = 10

try:
    account1.balance = -5
catch error:
    assert(error, ConstraintError("$Account.balance >= 0"))

assert(account1.balance, 10)
```

- A constraint may be written over a variable rather than a type.
- A constraint declared after instances exist is checked against them immediately.
- Constraints are checked inside `suppose`, so an inadmissible hypothetical throws where it is written.

#### Retraction

- `retract <selection>` withdraws stated facts and re-derives what rested on them.
- What a fact supported is recomputed under the rules that remain, rather than removed.
- A property that was overriding a class-level rule falls back to the rule.

```
class Alert:
    pass

$Alert.tone = "LOW"

alert1 = Alert()
alert1.tone = "HIGH"

retract alert1.tone

assert(alert1.tone, "LOW")
```

- A value with no remaining support becomes `null`, and its node stays in the graph.
- `del` removes the node and everything filed under it; `retract` keeps the model and withdraws one of its inputs.
- Retracting a selection retracts every stated node in it, so a chain may be retracted directly.

```
retract reading |> why |> stated
```

- Retracting a derived node is an error.

### Hypotheticals

- `suppose` opens a block whose statements are applied to a copy of the world.
- Rules propagate and constraints are checked inside the block exactly as they are outside it.
- The block's effects are discarded when it ends, whether it ended normally or by throwing.

```
threshold = 90
reading = 40
alarm = reading > threshold

suppose reading = 95:
    assert(alarm, true)

assert(alarm, false)
assert(reading, 40)
```

- A `suppose` block may be assigned. Its value is the value of its last expression statement, and that value survives the rollback.

```
peak = suppose reading = 95:
    alarm

assert(peak, true)
assert(alarm, false)
```

- `suppose` blocks nest, and an inner block is discarded before the outer one.
- A `throw` inside a `suppose` block is raised to the enclosing statement after the rollback.

#### Differences

- `diff` is a selection, valid only inside a `suppose` block.
- It selects the nodes whose values differ from the enclosing world, in the order they were re-evaluated.
- Each step carries `before` and `after` beside the usual fields.
- Being a selection, it chains.

```
threshold = 90
reading = 40
alarm = reading > threshold

fallout = suppose reading = 95:
    diff |> affects
```

### Evaluation

- A chain is filed in the graph as a node, keyed by the statement it was written as.
- It re-derives when either the **values** or the **shape** of what it walked changes.
- Its value dependencies are every node in the selection it produced.
- Its shape dependencies are the edges among those nodes: a chain re-derives when any node it selected gains or loses a dependency.
- A chain re-registers both on every evaluation, so a rule that introduces a new ancestor is picked up by the chain that walked the old one.

```
a = 1
b = a + 2
c = b * 2

trace = why c

d = 5
b = a + d

assert(trace.length, 4)
```

- A chain over a reference that does not exist yet selects nothing, and fills in when the reference is defined.

#### Escaping a hypothetical

- A selection computed inside a `suppose` block names nodes that the rollback may remove.
- A selection that leaves the block is **frozen**: it becomes plain data, stops re-deriving, and cannot be chained further.
- Freezing is the same idea as `.value` in [NUC 5](nuc-0005.md), applied to a selection rather than a reading.

```
changes = suppose reading = 95:
    diff

assert(changes.length, 2)
```

- `changes` keeps what it recorded and does not follow the model afterwards.

#### Reasoning in rules and constraints

- A chain may be written in a class-level rule, giving each instance its own.

```
$Alert.trace = why $Alert.tone
```

- The cost is one derivation per instance, so a chain over a large population is paid for on every change to it.
- A constraint may require a property of a derivation rather than of a value.

```
require all s in ($Order.total |> why): s.state != "unstated"
```

- This admits only worlds where every input behind a total is accounted for.

#### Transactions

- Chains read and never write, so they add nothing to a transaction's undo log.
- A chain evaluated during propagation sees the state as of its turn in the queue, like any other dependent.
- A rolled-back statement rolls back the chain nodes it created, like any other node.

### Built-in equivalents

| Chain | Call form |
| --- | --- |
| `x \|> why` | `why(x)` |
| `x \|> why not` | `why_not(x)` |
| `x \|> affects` | `affects(x)` |
| `x \|> depth(2)` | `depth(x, 2)` |
| `$Name \|> rules` | `rules($Name)` |
| `$Name \|> conflicts` | `conflicts($Name)` |
| `x \|> describe` | `describe(x)` |
| `x \|> export` | `export(x)` |
| `x \|> stated` | `x.filter(s => s.state == "stated")` |
| `all c in Check: c.passed` | `Check.every(c => c.passed)` |
| `any d in Device: not d.active` | `Device.some(d => not d.active)` |
| `suppose`, `require`, `retract` | none; they are statements |

## Errors

| Condition | Error |
| --- | --- |
| A stage over a name that is not defined | `ReferenceError("<name> is not defined")` |
| A stage over an operand that is neither a reference nor a selection | `TypeError("Cannot explain <expression>")` |
| `rules` or `conflicts` over a selection that is not of types | `TypeError("<name> is not a type")` |
| `rules` or `conflicts` on an undeclared type | `ReferenceError("<Name> is not defined")` |
| `\|>` onto something that is not an operation | `TypeError("<name> is not an operation")` |
| Chaining past a terminal | `SyntaxError("Cannot chain past <name>")` |
| Chaining a selection frozen by leaving a `suppose` block | `TypeError("Cannot chain a frozen selection")` |
| `retract` over a frozen selection | `TypeError("Cannot retract a frozen selection")` |
| Using a stage whose name is shadowed by a variable | `TypeError("<name> is not an operation")` |
| `all` or `any` over a value that is not a collection | `TypeError("<name> is not a collection")` |
| `diff` outside a `suppose` block | `SyntaxError("Cannot use 'diff' outside suppose")` |
| Assigning the value of a `suppose` block that ends in no expression | `TypeError("suppose has no value")` |
| A statement that leaves a constraint unsatisfied | `ConstraintError("<constraint>")` |
| Declaring a constraint that existing instances violate | `ConstraintError("<constraint>")` |
| `require` on an undeclared type | `ReferenceError("<Name> is not defined")` |
| `retract` over a derived node | `TypeError("Cannot retract a derived value")` |
| `retract` over a name that is not defined | `ReferenceError("<name> is not defined")` |

- The constraint in a `ConstraintError` is written as it appears in the `require` statement.
- `ConstraintError` is a new error type; the types in [NUC 9](nuc-0009.md) are unchanged.

## Reference Implementation

- **Stage 1 is implemented**: selections, `|>`, `model`, `why` and `affects`, specified by the reasoning entries in `nucleoid.spec.md` and run by `tests/spec.rs`.
- The rest of this document is a design under review and defines nothing until `nucleoid.spec.md` does.
- Building stage 1 settled three things the design had wrong:
  - `value` is reserved by [NUC 5](nuc-0005.md) for freezing a reading, so a step names its value `holds`.
  - A class-level rule is not a graph node, so `why socrates.mortal` is one step naming `$Human.mortal = true`, not two steps ending at it.
  - A step governed by a class-level rule is `derived` with an empty `from`, so `state` and `from` are not two spellings of the same fact.
- The selection type and `|>` come first, because every stage is defined in terms of them and nothing composes until they exist.
- Proposed staging, each stage landing spec entries, synth cases, documentation and runtime together:
  1. **Selections and `|>`** -- the step shape, coercion from a reference, `model`, and the pipeline operator, with `why` and `affects` as the first two stages over `dependencies` and `dependents` in `Graph`.
  2. **Shape dependencies** -- publishing edge mutation as a propagation event, which `Transaction`'s `DependentAdded` and `DependentRemoved` already record but nothing currently listens to. Until this lands, chains are correct only until a rule is redeclared.
  3. **Filters** -- `stated` and `derived`, and selections answering to the list functions of [NUC 10](nuc-0010.md).
  4. **Declaration stages** -- `rules`, `conflicts`, `export`, `depth`, then `describe`, which composes what precedes it.
  5. **Quantifiers** -- `all` and `any`, reusing the nodes `every` and `some` already build.
  6. **Hypotheticals** -- `suppose`, `diff` and freezing, reusing `Transaction::mark` and `rollback_to` without a commit.
  7. **Constraints** -- `require`, adding `ConstraintError` and a check at the end of each transaction.
  8. **Truth maintenance** -- `retract` and `why not`, which share the support tracking that neither can be built without.
