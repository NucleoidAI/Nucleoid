## Abstract

- **Rejected: eight historical source/field-seal tests fail.** The full
  test-suite hard criterion is not met. The prototype remains isolated;
  neither glyph spelling nor its document and dataset rewrites is accepted.
- Add only `≤` (U+2264) and `≥` (U+2265) as optional, one-character
  spellings of the existing `<=` and `>=` tokens. Reuse their token kinds,
  parser paths, comparison semantics and canonical rendering.
- Preserve every accepted input and output, including ASCII operators,
  operator sections, precedence, bounded comparison chains, declarations,
  rules, templates, literal text, diagnostics and source positions.
- The caller's one uniform eligible-category draw selected Syntax
  enhancement. This is a mathematical source-spelling change, not a
  foreign-language compatibility alias. Continuous-mode lexer-token
  comparison and all behavior, integrity and development checks apply.
- Rewrite only the existing inclusive condition in
  `Nucleoid throws an error inside a block` and the existing recursion
  boundary in
  `Nucleoid runs a recursive function with several return statements`.
  Preserve their identities, assertions, results and executed coverage.
  No new normative case or movement of existing cases is requested.

## Motivation

- Inclusive bounds are common in declarative models. One mathematical
  character can express each existing two-character source spelling without
  changing its meaning or adding a runtime operation.
- Reusing the existing lexer tokens avoids new keywords, public variants,
  lowering, dependencies, options and numerical behavior. The spelling is
  shorter in characters; no reduction in lexer-token counts is claimed.
- The accepted runtime rejects both glyphs outside literals and comments.
  Keep every other lexical boundary, including ASCII names and whitespace.
  No Unicode normalization or additional mathematical symbol is requested.
- Existing executable conditions provide accepted-syntax counterparts
  without appending cases that would shift protected document locators.
  Never alter a protected test, assertion, diagnostic or sealed case to
  accommodate the candidate.

## Rationale

- Attach the two spellings to the existing Logos variants rather than
  adding tokens, parser branches or comparison operations. Every consumer
  receives the same `LessEqual` or `GreaterEqual` token it already handles.
- Keep the ASCII spellings optional and unchanged. This proposal improves
  mathematical source notation, not compatibility with a foreign language;
  its confirmed Category remains Syntax enhancement.
- Accept exactly two code points, not similar-looking mathematical signs,
  combining sequences, Unicode names or Unicode whitespace. No
  normalization, feature flag, dependency or public API is needed.
- Reuse existing executable conditions for the required token comparison.
  The proposal changes characters, not the number of operator tokens;
  independent lexer measurements remain required and no saving is claimed.
- Leave NUC 109's sealed section examples and written-out counterparts
  unchanged. Focused native regressions exercise the glyphs in sections
  without adding or moving measured normative cases.

## Specification

- `≤` (U+2264) lexes as the existing `LessEqual` token, exactly as adjacent
  ASCII `<=` does. `≥` (U+2265) lexes as the existing `GreaterEqual` token,
  exactly as adjacent ASCII `>=` does. Each spelling is one lexer token.
- The parser, syntax tree and execution paths are unchanged. Both
  spellings use the existing left-associative relational level, below
  arithmetic and above equality, with at most 128 comparison links and the
  existing expression nesting guard. `3 ≤ 2 ≤ 0` means `(3 <= 2) <= 0`,
  not a conjunction of two bounds.
- All existing contexts apply: ordinary expressions, standing assignments,
  conditions, functions, callbacks, class-level rules, comprehensions,
  operator sections and template interpolation expressions. A section
  remains a whole positional argument of a parenthesized call, including
  calls to constructors; the glyphs do not widen that boundary.
- Eager operand evaluation, numeric conversion, null and undefined
  handling, errors, snapshots, graph dependencies, propagation and
  transaction rollback are those of the existing comparisons.
- Canonical rendering still uses ASCII `<=` and `>=`. Expression, rule and
  block keys therefore do not distinguish the spellings, and existing
  graph observations and diagnostics keep their accepted output.
- Strings, regular expressions, literal template text and comments retain
  glyphs as text or ignore them as before. Only an interpolation's parsed
  expression reads comparison tokens. ASCII names and whitespace,
  longest-token matching and all other lexical contracts remain unchanged.
- Logos and the existing position calculation handle UTF-8 boundaries.
  Lines and columns remain one-based; columns count characters rather than
  bytes. A glyph occupies one source column. Parser errors retain the
  existing lookahead positioning rather than being moved to the glyph.
- The isolated candidate's proposed `Symbolic inclusive comparisons`
  prose and executable rewrites remain unintegrated. The accepted
  [specification](../nucleoid.spec.md) is unchanged. In the candidate,
  `Nucleoid throws an error inside a block` changes only `if k >= 99:` to
  `if k ≥ 99:`; its canonical assertion remains `assert(error,"INVALID")`.
  The existing reference case
  `Nucleoid runs a recursive function with several return statements`
  changes only `if n <= 1:` to `if n ≤ 1:`; its canonical assertion remains
  `assert(result,120)`. Both expected-return metadata values remain null.
- No normative case is appended, inserted, reordered or renamed. README
  and examples executable blocks, section examples and every protected
  assertion remain unchanged. Relevant reference prose and two existing
  synthesized records use the same contract in the rejected candidate.

## Errors

- No error kind or message is introduced. Outside literals and comments,
  these two glyphs previously raised `SyntaxError("Unexpected character
  '≤'")` or `SyntaxError("Unexpected character '≥'")`; the candidate
  instead reaches the existing parser and comparison behavior.
- An operator where an operand is required uses its canonical token
  description. `x = ≤ 1` raises `SyntaxError("Unexpected '<='")`, and
  `x = ≥ 1` raises `SyntaxError("Unexpected '>='")`, each at line 1,
  column 7 under the existing parser's lookahead positioning. The
  corresponding ASCII inputs keep their original messages and positions.
- The 129th relational link raises
  `SyntaxError("Expression has too many operands")`. Excessive expression
  nesting raises `SyntaxError("Expressions are nested too deeply")`.
  Neither limit nor the accepted ASCII diagnostics changes.
- Operands remain eager: `false ≤ missing()` raises
  `ReferenceError("missing is not defined")`, as `false <= missing()` does.
  Every other runtime error follows the existing comparison path.
- Other unsupported characters still raise
  `SyntaxError("Unexpected character '<character>'")`. For example,
  `a≤b≠c` raises `SyntaxError("Unexpected character '≠'")` at line 1,
  column 4. Similar signs `≦` and `≧`, variation selectors, non-ASCII
  identifier letters and non-ASCII inter-token whitespace are not added.

## Reference Implementation

- The rejected prototype adds only `#[token("\u{2264}")]` to
  `Raw::LessEqual` and `#[token("\u{2265}")]` to `Raw::GreaterEqual` in
  `src/lang/ast/lexer/raw.rs`. Their existing public token conversion and
  all parser, evaluator and generator code are reused without changes.
- Its `docs/nucleoid.ebnf` replaces the blanket ASCII token-source contract
  with exactly the two glyph exceptions and extends `LESS_EQUAL` and
  `GREATER_EQUAL` using W3C EBNF `#x2264` and `#x2265`. No word-token or
  `anyToken` alternative is added because both token kinds already exist.
- Its `tests/symbolic_inclusive_comparisons.rs` covers token identity,
  character columns across CRLF, literal/comment boundaries, canonical
  syntax trees and graph-key rendering, precedence and eager/coerced
  comparisons, live sections/callbacks/class conditions/interpolations,
  rollback, mixed-spelling chain bounds and exact new-input errors.
- The two executable source rewrites regenerate
  `dataset/nucleoid.spec.jsonl` and `tests/nucleoid.spec.rs` through their
  authorized generators. Canonical synthesized records `synth-02-0005`
  and `synth-05-0005` change only their inclusive operator spelling,
  preserving IDs, descriptions, assertions and expected returns.
- The caller completed exactly one Rust improvement pass. Its existing
  literal/comment regression now borrows the complete token stream to
  reject leaked comparison tokens before consuming it in the unchanged
  payload assertions. The lexer was not changed by that pass.
- All 13 implementation, grammar, executable-document and data changes
  remain in the isolated candidate. This outcome integrates only the
  rejection document and its two index entries.
