# NUC 111 -- Reactive String Padding

```
NUC: 111
Title: Reactive String Padding
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Utility enhancement
Created: 16-Nov-2026
```

## Abstract

- Adds JavaScript's standard padding methods to string receivers:
  - `TEXT.padStart(length, fill)` puts copies of `fill` before `TEXT` until
    the result holds `length` characters, so `"7".padStart(3, "0")` is
    `"007"`;
  - `TEXT.padEnd(length, fill)` puts them after `TEXT`, so
    `"ab".padEnd(4, ".")` is `"ab.."`.
- `fill` defaults to one space, and a fill longer than the missing count is
  cut to it, so `"5".padStart(4, "ab")` is `"aba5"`. A `TEXT` that already
  holds `length` characters or more, and an empty fill, give `TEXT`
  unchanged.
- Lengths count characters as the accepted `length`, `slice` and `repeat`
  do, and `length` converts as the count of the accepted `repeat` does. A
  result too large to allocate raises
  `TypeError("Padded string is too large")`, as `repeat` raises
  `TypeError("Repeated string is too large")`.
- A declaration or class-level rule that calls a padding method stays live:
  `label = String(n).padStart(3, "0")` follows later writes of `n`.
- Only calls on a string receiver that raised
  `TypeError("<receiver>.padStart is not a function")` or
  `TypeError("<receiver>.padEnd is not a function")` change, along with the
  programs that caught that error. Numbers, lists, objects, `null` and every
  other receiver, property reads without a call, the static `String.<name>`
  calls and every accepted result are unchanged.
- No token, keyword, syntax, syntax-tree node, error type, option or public
  item is added; one error message is. The authoritative contract is
  [Reactive string padding](../nucleoid.spec.md#reactive-string-padding).

## Motivation

- World models render values as text: clock times such as `09:05`,
  zero-padded identifiers such as `T-0007`, and aligned columns of a report.
  At the accepted revision:
  - `"7".padStart(3, "0")` raises `TypeError("7.padStart is not a function")`;
  - `"ab".padEnd(4, ".")` raises `TypeError("ab.padEnd is not a function")`.
- The accepted spelling repeats the fill and writes the receiver twice:
  `"0".repeat(3 - id.length) + id`. With a computed receiver it converts
  the receiver a second time for its length, as in
  `"0".repeat(2 - String(h).length) + h`, and a fill of more than one
  character also needs a `slice`:
  `"ab".repeat(4 - s.length).slice(0, 4 - s.length) + s`.
- `id.padStart(3, "0")` is 8 lexer tokens against 12 for its `repeat`
  spelling, `String(h).padStart(2, "0")` 11 against 15, and
  `title.padEnd(12, ".:")` 8 against 23 for its cut spelling.
- The short accepted idiom `("00" + id).slice(-3)`, 11 tokens, is not a
  padding: it cuts every value to three characters, so `"1234"` becomes
  `"234"`, where `"1234".padStart(3, "0")` keeps all four.
- `padStart` and `padEnd` are standard JavaScript, which LLMs write
  routinely when they format output. Python's `str.rjust`, `str.ljust` and
  `str.zfill`, Kotlin's `padStart` and `padEnd`, C#'s `PadLeft` and
  `PadRight` and Rust's `format!("{:0>3}", id)` meet the same need.
- The methods join the accepted string helpers `repeat`, `slice`, `trim`
  and `replaceAll`. Like them, they are reached only through calls on
  strings, and a declaration that calls them stays live:
  `label = String(n).padStart(3, "0")` follows later writes of `n`.
- No accepted document case, dataset record, ARC dataset or test calls
  either name. The repository's own TypeScript in `arc/` uses `padStart`
  for the two needs this proposal serves: `String(index).padStart(2, "0")`
  numbers terminal rows, and `String(instance_index++).padStart(12, "0")`
  zero-pads object identifiers.

## Rationale

- **Confirmed category and mode.** The allocating continuous cycle drew
  Utility enhancement with one tool-backed uniform draw over the five
  categories that NUC 1's registry marks eligible for automatic selection,
  index 2 with probability 1/5 and no redraw, and recorded the requested
  change in the allocation commit `8f730054`, which this revision pins.
  Token comparison is therefore required. Runtime applicability does not
  apply to this category.
- **Selection.** Within the category the caller chose JavaScript's
  `String.prototype.padStart` and `padEnd` over the other built-ins missing
  at the accepted revision: the string methods `at`, `lastIndexOf`,
  `trimStart` and `trimEnd`, `Math.hypot` and `Math.gcd`, and the list
  helpers `sumBy`, `take` and `compact`. Padding renders values that world
  models show as text, LLMs write it routinely, and its accepted spelling is
  long and repeats the receiver. [NUC 103](nuc-0103.md) only lists
  `padStart` among the helpers it considered and set aside; no NUC proposes
  it.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **Defined by its accepted spelling.** `TEXT.padStart(N, F)` is
  `F.repeat(N - TEXT.length).slice(0, N - TEXT.length) + TEXT` with the
  length and fill converted as below, and `TEXT.padEnd(N, F)` puts the same
  padding after `TEXT`. For a fill of at most one character the `slice` is
  not needed: `F.repeat(N - TEXT.length) + TEXT`. Every result claim is a
  claim about these accepted spellings, which the accepted runtime already
  runs, and each document case below has an accepted-syntax counterpart
  built from them, the shortest that [Token counts](#token-counts) found.
  They differ only in the message of the size error,
  `Padded string is too large` here and `Repeated string is too large`
  there.
- **The string method route.** Both methods join the string methods behind
  `nucleoid::builtins::string_method`, beside `repeat`, so every string
  receiver gains them at once with the receiver snapshot, the evaluation of
  every argument, the receiver text and the null-receiver routing of every
  other string method. Rejected: rewriting a call to its `repeat` spelling
  at parse time, which would render a call the source never wrote and
  evaluate a computed receiver twice.
- **The length converts as `repeat`'s count.** One rule converts the
  whole-number arguments of string methods: the argument converts to a
  number as arithmetic converts it, NaN and negative numbers read as 0, and
  fractions truncate. JavaScript's `ToLength` agrees on every value whose
  number conversion Nucleoid shares with JavaScript: `"3"` is 3, `true` 1,
  `null` 0 and a missing length 0, so `TEXT.padStart()` is `TEXT`.
- **The fill converts as other string arguments.** A supplied fill takes its
  string form, as the arguments of `replace`, `replaceAll` and `startsWith`
  do: `0` fills with `"0"` and `null` with `"null"`, as in JavaScript. A
  missing fill, or an undefined value such as a missing property, is one
  space, as JavaScript's `undefined` is.
- **The keyword `undefined` is `null`.** The lexer reads `undefined`, `null`
  and `None` as one keyword, so `"5".padStart(3, undefined)` is
  `"5".padStart(3, null)`, `"nu5"`, where JavaScript gives `"  5"`. A
  program that wants spaces omits the fill or writes `" "`. Rejected:
  reading `null` as a space too, which would differ from JavaScript for
  `null` and from the conversion of every other string argument.
- **Characters.** Lengths, the missing count and the cut count Unicode
  scalar values, as `length`, `slice`, `repeat`, `charAt` and `indexOf` do,
  so `"日".padStart(3, "本")` is `"本本日"`. JavaScript counts UTF-16 code
  units, so a character outside the Basic Multilingual Plane counts once
  here and twice there. Rejected: UTF-16 counting, which would disagree with
  Nucleoid's own `length`.
- **The cut keeps the start of the fill,** as JavaScript's does:
  `"abc".padStart(10, "123")` is `"1231231abc"` and
  `"abc".padEnd(6, "123456")` is `"abc123"`.
- **Bounds and the message.** The method computes the size of its whole
  result with checked arithmetic, the receiver's bytes plus the whole copies
  of the fill plus the bytes of the cut copy, and reserves it with a
  fallible reservation before writing, as `repeat` and `replaceAll` do, so a
  pad never aborts or grows without bound. A result too large to represent
  or reserve raises `TypeError("Padded string is too large")`, parallel to
  `repeat`'s `Repeated string is too large` and `replaceAll`'s
  `Replaced string is too large`, and naming the operation that failed.
  Rejected: reusing `repeat`'s message, which would name a method the
  program never called. JavaScript raises a `RangeError` instead.
- **Further arguments** are evaluated and ignored, as for the other string
  methods and in JavaScript.
- **Live as written.** A declaration or class-level rule that calls a
  padding method depends on what its receiver and arguments read, as its
  accepted spelling does. Its dependencies are the same, in the order the
  call reads them, the receiver, the length and then the fill, where the
  spelling `F.repeat(N - TEXT.length) + TEXT` reads the fill first.
- **Rendered as written.** Statements, `why`, `affects`, `--graph` and graph
  and block keys show the call as the source wrote it. A padding call and
  its `repeat` spelling are different statements and keys, as `flat` and
  its `flatMap` spelling are under NUC 103.
- **Completion.** The terminal workspace offers the JavaScript names of
  string members, so it gains `padStart` and `padEnd`, as NUC 103, NUC 105
  and NUC 108 added their list helpers.
- **The public string method.** `nucleoid::builtins::string_method` is the
  public function behind every string method, so it accepts `padStart` and
  `padEnd` where it returned the `TypeError`. No public item is added or
  removed; the widened set of names is the change to report for
  semantic-versioning review, and no version number changes.
- **No `Requires`.** `repeat`, `slice`, `length` and the string method route
  are base built-ins of the specification, documented by the reference
  [NUC 10](nuc-0010.md), which no accepted NUC introduced. The routing rules
  that [NUC 42](nuc-0042.md) and [NUC 110](nuc-0110.md) state for string
  methods are followed, not depended on.
- **Not added.** Padding of numbers, lists or other receivers, static
  `String.padStart` and `String.padEnd`, Python's `rjust`, `ljust`, `zfill`
  and `center`, centring, truncation to the length, a width-based
  formatter, a `RangeError` type, and any change to `repeat`, `slice` or
  `length`.

## Specification

- The normative contract is
  [Reactive string padding](../nucleoid.spec.md#reactive-string-padding).

### Calls

- `RECEIVER.padStart(...)` and `RECEIVER.padEnd(...)` are padding calls when
  `RECEIVER` evaluates to a string: a literal, a name, a property, a call
  result, a template, an index, a `.value` snapshot, a string read from a
  state version, `String(n)` or a method result.
- On every other receiver the two names keep their accepted readings, which
  [Compatibility](#compatibility) lists.

### Length

- The first argument is the target length, in characters. It converts to a
  number as arithmetic converts it, and then as the count of `repeat` does:
  NaN and negative numbers give 0, and fractions truncate toward zero.

| `length`, the first argument | Target length |
| --- | --- |
| missing | 0 |
| `3`, `3.9`, `"3"`, `" 3 "`, `[3]` | 3 |
| `true`, `1`, `"1"` | 1 |
| `0`, `-0`, `0.5`, `-1`, `-2.5`, `null`, `false`, `""`, `[]`, `Number.NEGATIVE_INFINITY` | 0 |
| `Number.NaN`, `"a"`, `"0x10"`, `[1, 2]`, `{}`, an instance, a function, a regular expression, an undefined value such as a missing property | 0 |
| a date | its milliseconds |
| `Number.POSITIVE_INFINITY`, `1 / 0`, `"Infinity"`, `"inf"`, `1e300` | more than any result can hold, so a nonempty fill raises `TypeError("Padded string is too large")` |

### Fill

- The second argument is the fill. It converts to its string form, as the
  other string arguments do.

| `fill`, the second argument | Padding characters |
| --- | --- |
| missing, or an undefined value such as a missing property | one space, `" "` |
| a string | its characters: `"0"`, `"ab"`, `"日本"` |
| `""` | none, so the receiver is returned unchanged |
| `0`, `1.5`, `true`, `null`, `[1, 2]` | their string forms `"0"`, `"1.5"`, `"true"`, `"null"`, `"1,2"` |
| the keyword `undefined` | `"null"`, since the keyword is `null` |
| an object or instance | `"[object <id>]"` |

### Padding

- `missing` is the target length minus the number of characters of the
  receiver. When `missing` is 0 or less, or the fill is empty, the result is
  the receiver unchanged.
- Otherwise the padding is the characters of the fill repeated and cut to
  exactly `missing` characters, keeping the start of the fill. `padStart`
  returns the padding followed by the receiver and `padEnd` the receiver
  followed by the padding. The receiver is never written.
- Characters are Unicode scalar values, as `length`, `slice` and `repeat`
  count them. Further arguments are evaluated and ignored.

| Program | Result |
| --- | --- |
| `"7".padStart(3, "0")` | `"007"` |
| `"ab".padEnd(4, ".")` | `"ab.."` |
| `"42".padStart(5)` | `"   42"` |
| `"5".padStart(4, "ab")` | `"aba5"` |
| `"abc".padStart(10, "123")` | `"1231231abc"` |
| `"abc".padEnd(6, "123456")` | `"abc123"` |
| `"1234".padStart(3, "0")` | `"1234"` |
| `"abc".padEnd(6, "")` | `"abc"` |
| `"".padStart(2, "0")` | `"00"` |
| `"日".padStart(3, "本")` | `"本本日"` |
| `"é".padEnd(3, "·")` | `"é··"` |
| `"5".padStart(3, [1, 2])` | `"1,5"` |
| `"5".padEnd(4, true)` | `"5tru"` |

- This program is the specification entry
  `Nucleoid pads strings at the start with padStart`:

```
ids = ["7", "42", "123", "1234"]
codes = ids.map(id -> id.padStart(3, "0"))
h = 9
m = 5
clock = String(h).padStart(2, "0") + ":" + String(m).padStart(2, "0")
assert(codes, ["007", "042", "123", "1234"])
assert(clock, "09:05")
ids.push("5")
h = 14
assert(codes, ["007", "042", "123", "1234", "005"])
clock
```

- This returns `"14:05"`: identifiers that already hold three characters or
  more keep them, and both declarations follow later writes.
- The entry `Nucleoid pads strings at the end with padEnd` pads columns with
  the default space and cuts a fill of two characters:

```
items = ["tea", "jam", "honey"]
width = 6
rows = items.map(item -> item.padEnd(width) + "|")
title = "Total"
rule = title.padEnd(12, ".:")
assert(rows, ["tea   |", "jam   |", "honey |"])
assert(rule, "Total.:.:.:.")
width = 4
title = "Sum"
assert(rows, ["tea |", "jam |", "honey|"])
rule
```

- This returns `"Sum.:.:.:.:."`.

### Evaluation

- The receiver is read first and then every supplied argument once, left to
  right, including unused extras, as for every call. A missing name among
  them raises `ReferenceError("<name> is not defined")` before the method
  runs.
- A `null` or undefined receiver keeps the accepted route: the call is
  undefined and the arguments are not evaluated.
- A declaration whose receiver or argument reads a `null` binding holds
  `null` until the binding is defined, as for `repeat`: after `fill = null`,
  `shown = "5".padStart(3, fill)` holds `null`, and `fill = "0"` makes it
  `"005"`.

### Liveness and class-level rules

- A declaration that calls a padding method depends on what its receiver
  and arguments read: writes of a receiver, length or fill held in a name or
  a property re-evaluate it, and so do pushes and replacements of a list
  that a callback pads.
- In a class-level rule each instance pads its own values, and the rule
  follows that instance's properties. This program is the specification
  entry
  `Nucleoid keeps padded strings live in declarations and class level rules`:

```
label = "7"
width = 3
fill = "0"
shown = label.padStart(width, fill)
assert(shown, "007")
label = "42"
assert(shown, "042")
width = 5
assert(shown, "00042")
fill = ""
assert(shown, "42")
fill = "*"
assert(shown, "***42")
class Ticket(id):
    this.id = id
$Ticket.code = "T-" + String($Ticket.id).padStart(4, "0")
first = Ticket(7)
second = Ticket(42)
assert([first.code, second.code], ["T-0007", "T-0042"])
first.id = 12345
[first.code, second.code]
```

- This returns `["T-12345","T-0042"]`: the empty fill leaves the label as it
  is, and an identifier of five digits is not cut.

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` and graph and block keys show the
  call as written: after `shown = label.padStart(width, fill)`,
  `(why shown)[0].rule` is `"shown = label.padStart(width,fill)"`.
- The dependencies are those of the accepted spelling, in the order the
  call reads them: `(why shown)[0].from` is `["label", "width", "fill"]`,
  where `shown = fill.repeat(width - label.length) + label` gives
  `["fill", "width", "label"]`. A literal fill reads nothing, so after
  `w = 3`, `shown = label.padStart(w, "0")` depends on `label` and `w`, and
  its spelling on `w` and `label`.

### Transactions

- Errors of a padding call, and of its receiver and arguments, propagate
  through the existing transaction, so a failed statement rolls back the
  change that triggered it, and a failed block restores declarations that
  pad, their values and their dependencies. This program is the
  specification entry
  `Nucleoid rolls back failed updates through padded strings`:

```
ids = []
codes = ids.map(id -> id.padStart(size, "0"))
failure = ""
try:
    ids.push("7")
catch error:
    failure = error
assert(failure, ReferenceError("size is not defined"))
assert([ids, codes], [[], []])
size = 3
ids.push("7", "42")
assert(codes, ["007", "042"])
try:
    ids.push("5")
    size = 2
    assert(codes, ["07", "42", "05"])
    throw "UNDO"
catch error:
    assert(error, "UNDO")
[codes, size]
```

- This returns `[["007","042"],3]`: the first push fails while its new item
  is padded, because the length names nothing yet, and the thrown block
  restores both the list and the length.

### Bounds

- A padding call sizes its whole result with checked arithmetic and
  reserves it fallibly before writing, so the result is never larger than
  the target length in characters, or the receiver when that is longer. A
  result too large to represent or reserve raises
  `TypeError("Padded string is too large")`. No padding-specific cap is
  added: `"x".padStart(1000000000)` builds a string of 1,000,000,000
  characters, as `" ".repeat(999999999) + "x"` does, while
  `"x".padStart(1e15)` and `"x".padStart(1 / 0)` raise. With an empty fill
  every length gives the receiver: `"x".padStart(1 / 0, "")` is `"x"`.
- The accepted expression, statement and propagation limits apply.

### Cost

- A padding call writes each character of its result once into one string
  reserved at its exact size, so its time and memory are linear in the
  length of the result. Its `repeat` spelling builds the padding and then a
  second string for the concatenation, and with a fill of several
  characters it repeats the whole fill `missing` times before `slice` cuts
  it.
- **Measured**, not projected, through the command line on release builds,
  rustc 1.97.1: the median of five runs of each program with `--json`,
  including process start, with the peak working set of the process, on
  `nucleoid-final.exe` for the padding call and its accepted spelling, and
  on the accepted revision's binary for the accepted spelling, one process
  at a time with nothing else running. `items` is
  `"x".repeat(100000).split("")`, 100,000 one-letter strings, which takes
  31.9 ms on the final build and 30.4 ms on the accepted one before the
  measured work.

| Program | Padding | Its spelling | Its spelling at the accepted revision | Peak memory, padding against spelling |
| --- | ---: | ---: | ---: | ---: |
| `items.map(x -> x.padStart(4, "0")).length`, 100,000 calls | 83.5 ms | 89.0 ms | 87.1 ms | 31.6 MiB, 30.6 MiB |
| `items.map(x -> x.padEnd(4, "0")).length`, 100,000 calls | 80.6 ms | 86.4 ms | 89.7 ms | 31.6 MiB, 31.6 MiB |
| `"x".padStart(1000000, "0").length`, one pad of 1,000,000 characters | 11.7 ms | 11.2 ms | 12.5 ms | 9.7 MiB, 10.8 MiB |
| `"x".padStart(100000000, "0").length`, one pad of 100,000,000 characters | 211.3 ms | 161.8 ms | 264.8 ms | 103.2 MiB, 294.0 MiB |
| `"x".padEnd(100000, fill)` with a fill of 1,000 characters | 10.4 ms | 46.1 ms | 42.2 ms | 9.1 MiB, 103.5 MiB |

- Net of `items`, 100,000 calls take 51.6 ms with `padStart` and 57.1 ms
  with its spelling, and 48.7 ms with `padEnd` and 54.5 ms with its
  spelling: 0.89 to 0.90 times.
- A pad of 100,000,000 characters takes about a third of its spelling's
  peak memory, one reserved string against the repeated padding and the
  concatenated copy. Its time is 0.80 times that of the spelling on the
  accepted revision's build, and 1.31 times that of the spelling on the
  final build, whose `repeat` the improvement pass made faster, as the last
  item states.
- With a long fill the general spelling repeats the whole fill 99,999 times,
  a string of 99,999,000 characters, before it cuts 99,999 of them; padding
  writes the 99,999 it needs, as the counted spelling does.
- The 10,000 writes alone take 42.7 ms on the final build and 42.4 ms on the
  accepted one; the standing declaration adds 35.7 ms with padding and
  44.6 ms with its spelling.
- A pad of 1,000,000,000 characters builds in 2.1 s; its spelling takes
  1.6 s on the final build and 2.6 s on the accepted revision's.
- The improvement pass, which moved `repeat` onto the shared reservation,
  changes its speed but none of its results. Interleaved over seven rounds,
  `"0".repeat(100000000)` takes 100.5 ms on the final build, against
  210.0 ms on the accepted revision's build and 210.9 ms on this
  candidate's build before the pass. That earlier build pads 100,000,000
  characters in the same time as the final build, 214.0 against 214.8 ms.
  So the final build runs the spellings of the pads of 1,000,000 and
  100,000,000 characters at 0.90 and 0.61 times the accepted revision's
  time, and the general spelling of the long fill, which repeats a string
  of 1,000 characters, at 1.09 times. It runs every other spelling in the
  table, `items` and the 10,000 writes within 5 percent of the accepted
  revision's time. A second full pass agreed with the table within
  4 percent on every entry.

### Findings

- **Low, documentation (F1).** [Rationale](#rationale) and the Length
  subsection of [Specification](#specification) say that the length
  converts to a number as arithmetic converts it. That is wrong for the
  texts `"Infinity"`, `"inf"` and `"infinity"`: arithmetic and `Number()`
  read them as NaN, so `"inf" - 1` is NaN, while the padding length, like
  the count of `repeat`, reads them as Infinity and raises the size error.
  `"5".padStart("inf", "0")` raises `TypeError("Padded string is too
  large")`, as `"5".repeat("inf")` raises
  `TypeError("Repeated string is too large")`. The NUC's length table, the
  root specification and `docs/README.md` state the conversion of `repeat`
  correctly. The evaluated text is integrated unchanged; the caller
  reproduced the difference on the frozen binary and the accepted
  revision's.
- **Info, cost of accepted code (F2).** The improvement pass changes the
  speed of the accepted `repeat` but none of its results, as [Cost](#cost)
  discloses: `"0".repeat(100000000)` takes about 101 ms on the candidate
  against 213 ms at the accepted revision, while repeating a
  1,000-character string is slower, 46.4 against 39.5 ms in the evaluator's
  run.
- **Info, tests (F3).** The exact-capacity unit tests depend on
  `try_reserve_exact` reserving exactly what is requested, which the
  standard library does today though its documentation allows more.
- **Info, counts (F4).** The evaluator's corpus of 4,527 programs, 29
  changed and 3 reading the clock, differs from the proposer's 4,523, 26
  and 4 only by extraction; in both, the changed set is exactly this
  proposal's sources.
