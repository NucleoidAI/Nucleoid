# NUC 14 -- Bodyless Empty Class Declarations

```

Title: Bodyless Empty Class Declarations
Author: Copilot <223556219+Copilot@users.noreply.github.com>
Status: Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 13-Oct-2026
```

## Abstract

- Specifies `class Entity` as a shorter spelling of an empty class with an indented pass-only body.
- Preserves the existing optional parameter list, including `class Shell(code: int)`.
- Reuses the existing class declaration and execution path; this is syntax sugar, not a new type or constructor mechanism.

## Motivation

- Empty classes supply instance populations and class-level rules without needing constructor statements.
- Repeating a colon and a placeholder body adds syntax without adding behavior.
- Compact headers keep those declarations readable while retaining the existing reactive model.

## Rationale

- An indented `pass` contributes no fields, constructor statements, or methods to the existing class AST.
- A bodyless header lowers to that exact representation, including its existing parameters.
- A statement boundary ends the header; the next statement must not become a constructor.
- Indentation without a colon is rejected rather than interpreted as a compact body.
- Constructor-property assignment, a new type mechanism, and a separate inheritance shorthand are out of scope.
- Nonempty bodies and subtype declarations keep the existing colon grammar.
- Canonical rendering and graph keys stay unchanged rather than distinguishing equivalent spellings.

## Specification

### Headers and boundaries

- A root class header consists of `class`, an identifier, and an optional existing parameter list.
- Omitting the colon and body denotes an empty class.
- A legal terminator is a logical newline, semicolon, end of input, or a closing brace or dedent owned by the enclosing block.
- The parser leaves the terminator for its enclosing statement, suite, or block parser.
- Comments and blank lines do not introduce a body.
- Newlines inside parentheses retain the existing parameter-list layout rules; they are not header terminators.
- An indentation increase after the header's newline or semicolon separators requires the existing colon/body form.
- Unsupported following tokens are syntax errors, not constructor statements.
- Existing explicit colon/body forms remain valid, including typed attributes, constructor statements, `init`, methods, and inheritance.
- The normative description is in [nucleoid.spec.md](../nucleoid.spec.md); boundary, malformed-input, and position regressions are in [tests/bodyless_classes.rs](../tests/bodyless_classes.rs).

### Empty declaration and parameters

- The resulting `ClassDecl` has the existing name and parameters, no parent, and empty fields, constructor, and methods.
- An explicit indented pass-only body produces the same full AST and canonical source.
- Optional annotations and argument binding keep their existing behavior.
- Parameters alone do not create properties or assign arguments to them.
- `Nucleoid keeps bodyless class declarations equivalent` in the specification covers type identity, registration, and instance population.
- `Nucleoid preserves parameters and scope in bodyless classes` covers annotated parameters without implicit properties, and scoped instance registration.

```nuc
class Shell(code: int)
first = Shell(5)
second = Shell()
assert(first, {id: "first"})
assert(first.code, null)
assert(second.code, null)
assert(Shell.length, 2)
```

### Instances, rules, and transactions

- `$Name` still denotes the class, `Name` still denotes its instance list, and declarations still register in `Class`.
- Instances created inside a block retain their existing anonymous identity and membership; a local variable does not invent a named identity.
- Class-level rules and property dependencies use the existing runtime nodes and values.
- Re-declaration preserves existing populations and rules.
- Parent and child instance lists remain distinct; inherited class-level rules still apply to child instances.
- Inherited declarations stay on their existing accepted colon grammar; this revision adds no inheritance shorthand and does not tighten legacy body handling.
- Transactions and rollback remain unchanged.
- `Nucleoid keeps rules reactive on bodyless classes` covers propagation through variables and instance properties.
- `Nucleoid preserves bodyless class populations and inheritance` covers re-declaration, distinct parent/child lists, and inherited rules.
- `Nucleoid rolls back creation of bodyless class instances` covers failed creation, population rollback, and the missing rolled-back name.

```nuc
class Entity
assert(typeof $Entity, Class)
assert(typeof Entity, List)
assert(Class.length, 1)
assert(Entity.length, 0)
entity1 = Entity()
assert(entity1, {id: "entity1"})
assert(Entity.length, 1)
```

### Compatibility and limits

- Existing specification entries `Nucleoid creates a class with constructor`, `Nucleoid creates a class with a constructor and a typed attribute`, and `Nucleoid creates a class and a subclass` retain their explicit bodies.
- Existing entries for inherited rules, `super`, class counts, and expression-bodied initializers and methods retain their behavior.
- No public keyword, token variant, AST variant, field, or type is added.
- No runtime node, value, or evaluation path is added.
- Existing source-position, statement-nesting, expression-nesting, and operator-chain safeguards remain in force.
- The canonical class spelling stays `class Name`; equivalent enclosing blocks retain their graph keys.
- The CLI's existing immediate execution of lines without a trailing colon also handles bare headers; explicit multiline entry is unchanged.

## Errors

- The feature adds no runtime error kind or catch value.
- Unsupported tokens use the existing `SyntaxError("Expected ':' but found <token>")` diagnostic with `Token::describe()` substituted exactly.
- Malformed names and parameter lists retain the existing parser diagnostics.
- The following exact messages are specified by the normative header rules and covered by the focused diagnostic regressions.

| Source condition | Error |
| --- | --- |
| Missing class name at end of input | `SyntaxError("Expected a name but found end of input")` |
| Numeric class name `123` | `SyntaxError("Expected a name but found number 123")` |
| `class Entity other` | `SyntaxError("Expected ':' but found identifier 'other'")` |
| `class Entity =` | `SyntaxError("Expected ':' but found '='")` |
| `class Entity {}` | `SyntaxError("Expected ':' but found '{'")` |
| `class Entity => 1` | `SyntaxError("Expected ':' but found '=>'")` |
| `class Entity.code` | `SyntaxError("Expected ':' but found '.'")` |
| `class Entity)` | `SyntaxError("Expected ':' but found ')'")` |
| `class Entity]` | `SyntaxError("Expected ':' but found ']'")` |
| `class Entity, next` | `SyntaxError("Expected ':' but found ','")` |
| `class Entity(code:)` | `SyntaxError("Expected a type but found ')'")` |
| `class Entity(1)` | `SyntaxError("Expected a parameter but found number 1")` |
| Unclosed `class Entity(code` | `SyntaxError("Expected ')' but found end of input")` |
| `class Entity(code = 1)` | `SyntaxError("Expected ')' but found '='")` |
| Header followed by a newline and an indented body without a colon | `SyntaxError("Expected ':' but found end of line")` |
| Header followed by semicolon separators and an indented body without a colon | `SyntaxError("Expected ':' but found ';'")` |
| Excessive enclosing statement nesting | `SyntaxError("Statements are nested too deeply")` |
| Excessive expression nesting after a header | `SyntaxError("Expressions are nested too deeply")` |
| Excessive operator chain after a header | `SyntaxError("Expression has too many operands")` |

- Error positions retain the existing one-based line and character-column convention.
- The rollback specification case throws `"LIMIT"` from its existing validation rule and then observes `ReferenceError("limited2 is not defined")`; compacting its class header does not change either value.
- Other runtime errors remain those of the existing class, property, rule, and transaction semantics.
