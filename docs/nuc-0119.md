```

Status: Accepted
Type: Standards Track
Category: Runtime features
Created: 18-Nov-2026
Requires: 9, 46
```

## Abstract

- A complete `try`/`catch` statement may end with a `finally` clause,
  `finally:` followed by a suite, which runs every time the statement
  ends: after the body completes, after the catch suite handles a
  failure, and before a `return` in either of them leaves the function or
  the program.
- The pending outcome stands unless the `finally` suite changes it: a
  value that the body or the catch suite returns is still returned, and
  an error that the catch suite raises still propagates afterwards. A
  `return` or a failure of the `finally` suite replaces it, as in Python,
  JavaScript and Java.
- Nucleoid's transactions are kept. A failed body's changes are rolled
  back before the catch suite runs, as they are now, and a failed catch
  suite's changes before the `finally` suite runs, so no suite runs on the
  partial changes of a failed one. When an error leaves the statement, the
  enclosing rollback undoes what the `finally` suite changed, with the
  rest of the statement.
- At the accepted revision each of these programs raises
  `SyntaxError("Unexpected ':'")`, reported at the token after `finally:`.
  Only those programs change. `finally` stays an ordinary name everywhere
  else, as a variable, property, object key, function, parameter or enum,
  as in `finally = 4`, `c ? finally : 1` and `{a: 2 finally: 3}`;
  `finally: NAME` before the end of its statement stays the typed
  declaration of `finally`; a bare `finally` line followed by an indented
  block keeps its accepted reading; and `try` without `catch` keeps
  `SyntaxError("Expected 'catch' after 'try'")`.
- No keyword, lexer token, error type or message format is added. The
  authoritative contract is
  [Finally clauses](../nucleoid.spec.md#finally-clauses).

## Motivation

- Mainstream languages with `try`/`catch` have a clause that runs however
  the statement ends: `finally` in Python, JavaScript, TypeScript, Java,
  Kotlin and C#, `ensure` in Ruby, and `defer` in Swift and Go. Programs
  and models written by people and LLMs use it to record that an
  operation ran, to count attempts or to log on every path. In Nucleoid
  each of them raises `SyntaxError("Unexpected ':'")` at `finally:`.
- Without it, a function whose body and catch suite both return has to
  repeat the shared work before each `return`, or turn each `return` into
  an assignment of a result followed by one `return` after the statement.
  Inside a function such an assignment writes state, because a function's
  only local names are its parameters and loop variables, so the rewrite
  changes the shape of the program and adds a state name the model did
  not have.
- World models record what happened as well as what holds: an attempt, an
  audit entry, a retry count. A `finally` clause states such a record
  once, beside the operation it follows, and keeps the statement's
  transaction: what the record writes commits with the statement or rolls
  back with it.

## Rationale

- **Category and mode.** The allocating continuous cycle drew Runtime
  features with one tool-backed uniform draw over the five categories that
  NUC 1's registry marks eligible for automatic selection, index 1 with
  probability 1/5 and no redraw, and recorded the requested change in the
  allocation commit `9eeb878b`, which this revision pins.
- **Runtime applicability: `new_feature`.** No accepted construct runs a
  suite on every exit of a `try` statement. Code written after the
  statement does not run when the body or the catch suite returns, and the
  rewrite that emulates the clause turns each `return` into an assignment
  of a result, which inside a function writes state: a function's only
  local names are its parameters and loop variables, so at the accepted
  revision a function that assigns `r` in its suites leaves the state
  name `r` behind. A counterpart therefore changes the program's state and
  structure, as [NUC 74](nuc-0074.md)'s rest parameters did. Token
  comparison is skipped entirely, as NUC 1's matrix states for a brand-new
  runtime feature (`new_runtime_feature`). The skip is neither a measured
  comparison nor a passing token gate.
- **No counterparts.** Because comparison is skipped, the new cases have no
  accepted-syntax counterparts and there is no Baseline B or extra
  baseline. They execute their assertions and explicit returns with full
  coverage, and every pre-existing case is unchanged.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored (`missing_rubric`), not zero. Strategy learning is
  `not_configured`, so this revision is unattributed, with no policy,
  selection receipt, trial or reward.
- **The name of Python, JavaScript and Java, without a reserved word.**
  `finally` stays an ordinary identifier. At the accepted revision a line
  that starts with the name `finally` and `:` after a catch suite is the
  name followed by a stray colon, which raises
  `SyntaxError("Unexpected ':'")`, so giving that line clause meaning
  changes no accepted program. Rejected: reserving `finally`, which would
  break programs that use it as a variable, property, key, function,
  parameter or enum name; Ruby's `ensure`, which follows `rescue` rather
  than `catch`; and Swift's and Go's `defer`, a statement that registers
  work for the end of a scope rather than a clause of `try`.
- **On its own line, at the `try` statement's level.** The clause starts
  the logical line that directly follows the catch suite, at the `try`
  statement's own layout level, as `catch` follows the body. On the catch
  suite's line, `finally` is already accepted syntax: after an inline
  suite, `x = 2 finally` is the statement `x = 2` followed by the name
  `finally`, and `c ? 2 finally : 3` would be a conditional, so a
  same-line clause would collide with juxtaposition and conditionals. A
  `finally:` after `;`, inside the catch suite, at a shallower level or
  without a `try` keeps its accepted error.
- **The declaration `finally: NAME` stays.** At the accepted revision
  `finally: NAME` before a newline, `;`, dedent or the end of input is the
  typed declaration of `finally`, which raises
  `ReferenceError("Missing definition")` when it runs. A function whose
  `try` returns before it reaches that line is an accepted program that
  succeeds: `def g():` with a `try` that returns `1`, a `catch` that
  returns `2` and the line `finally: x` returns `1`, which the clause
  reading would turn into `ReferenceError("x is not defined")`. The
  statement parser's own declaration test therefore excludes it, as
  [NUC 115](nuc-0115.md) keeps `repeat NAME: TYPE`. Only a `finally` suite
  of one bare name, which reads it and does nothing else, is lost.
- **The colon is required.** A bare `finally` line followed by an indented
  block is an accepted program, the name `finally` followed by the block,
  so the clause takes its colon even where
  [NUC 46](nuc-0046.md) lets `try` and `catch` omit theirs.
- **Parentheses have no lines.** Inside `(` and `[` the lexer suppresses
  layout, so the statements of a braced callback passed to a call stand on
  one logical line, and a `finally:` there follows the catch suite on its
  line. It keeps its accepted `SyntaxError("Unexpected ':'")`, as a
  same-line `finally:` does. A braced arrow assigned to a name has lines
  and takes the clause.
- **The outcome of Python, JavaScript and Java.** The `finally` suite runs
  after the body or the catch suite completes, normally or by `return`,
  and the statement then completes as that suite did. A `return` in the
  `finally` suite replaces a pending `return` or error, and a failure of
  the `finally` suite propagates in its place, as in all three. A pending
  `return` keeps the value it computed, as in all three, so a later write
  in the `finally` suite does not change it; Nucleoid lists
  are values, so a returned list keeps the elements it had when the
  `return` ran. Rejected: rerunning the `return` expression after the
  `finally` suite, which no source language does.
- **Transactions as Nucleoid keeps them.** A failed body is rolled back
  before the catch suite runs, as at the accepted revision. A failed catch
  suite is rolled back before the `finally` suite runs, so no suite runs
  on the partial changes of a failed one, and its error then propagates.
  Python, JavaScript and Java have no rollback, so the `finally` suite
  there sees what a failed suite left. Rejected: running the `finally`
  suite on a failed suite's partial changes, which would let it read and
  commit state that the failure is meant to undo.
- **The enclosing rollback undoes the `finally` suite when an error
  leaves.** The `finally` suite's changes belong to the statement: they
  commit with it, and when an error leaves the statement the rollback of
  the enclosing `try` or of the whole run undoes them with everything else.
  Rejected: committing the `finally` suite's changes separately, which
  would break the rule that a statement takes effect entirely or not at
  all.
- **The scope of the `try` statement.** The catch parameter is bound in a
  scope pushed for the catch suite, as before, and the `finally` suite
  runs after it is popped, so the parameter is not bound there, as in
  Python, JavaScript and Java. Its statements run as those of a catch
  suite do: a
  top-level assignment is a declaration, and in a function, method or loop
  body they run in that body.
- **Executed when reached.** A `try` statement runs when it is reached and
  files nothing of its own, with or without the clause. One inside the
  branch of a standing `if`, or in a function called from a declaration,
  runs its `finally` suite whenever that rule runs it.
- **One savepoint more, only with the clause.** The catch suite runs on a
  savepoint of its own only when a `finally` clause follows, so a `try`
  statement without the clause runs exactly the accepted code.
- **Rendering and graph keys.** A `try` statement's graph key stays `try`,
  with or without the clause. Its suite rendering, used inside
  default-bearing declarations, appends `finally:` and the indented
  `finally` suite after the catch suite; without the clause it renders
  byte for byte as before.
- **REPL and terminal workspace.** The native REPL already buffers a
  `try:` statement until a blank line, and `finally:` ends in a colon, so
  the clause is buffered with its statement and parsed with it. A blank
  line commits the statement first, as it does before a `catch`; the REPL
  needs no change. The workspace completes `finally` from its alphabetical
  place among the completion words, between `false` and `for`, as
  [NUC 115](nuc-0115.md) added `repeat`.
- **The documents spell `finally:`.** The specification exporter's
  statement splitter groups a top-level line that starts with `finally:`
  with the statement before it, which keeps the clause with its `try`.
  `finally :` with a space is the same clause in programs, but the
  documents do not use it, and the splitter is unchanged.
- **The public syntax tree and statement nodes.** The public `Stmt` enum
  gains `Stmt::TryFinally { body, parameter, catch, finally }`, produced
  only for a statement with the clause; `Stmt::Try { body, parameter,
  catch }` is unchanged, so existing code that builds or matches it keeps
  compiling and every try statement without the clause parses to exactly
  the accepted tree. The public node `nuc::Try` gains the public field
  `finally: Option<Vec<Stmt>>`; `Try::new` keeps its signature and leaves
  it `None`, and `Nuc::convert` sets it by struct update over `Try::new`,
  as it sets `For`'s `value`. No
  `Nuc` variant or other public item is added. The new variant breaks
  exhaustive downstream matches over `Stmt`, as NUC 115's `Stmt::Repeat`
  did, and the new field breaks downstream struct literals and exhaustive
  patterns of `nuc::Try`; both need human SemVer review, and no version
  number changes.
- **Requires.** [NUC 9](nuc-0009.md), whose transactions, `throw`, caught
  failures and catch bindings the clause keeps and extends to the
  `finally` suite; and [NUC 46](nuc-0046.md), whose colon-free `try` and
  `catch` headers may precede the clause and whose REPL buffer of a bare
  `try` header holds it.
- **Not added.** `try`/`finally` without `catch`, a colon-free `finally`, a
  clause on the catch suite's line, Python's `else` clause, several catch
  suites, typed or filtered catches, `ensure` and `defer`, and any change
  to `try`, `catch`, `throw`, rollback, the REPL, the exporter or an
  existing diagnostic.

## Specification

- The normative contract is
  [Finally clauses](../nucleoid.spec.md#finally-clauses).

### Syntax

- `try_statement: "try" body "catch" parameter? body finally_clause?`, and
  `finally_clause: NEWLINE* "finally" ":" suite`, where `finally` is an
  ordinary identifier and `suite` is the explicit-colon suite of `catch`:
  an indented block, statements on the same line separated by `;`, or a
  braced block.
- After the catch suite, a `finally` clause is the name `finally`
  immediately followed by `:`, when the name starts the logical line that
  directly follows the catch suite at the `try` statement's own layout
  level: only line breaks stand between the end of the catch suite and
  the name, and the token before the name is a line break or the dedent
  that closes the catch suite. Blank lines and comment lines produce no
  tokens, so they may stand between, and `finally :` with a space is the
  same tokens.
- The lexer closes a width between two open levels to the shallower one,
  for every line, so a `finally:` indented less than the catch suite but
  more than the `try` belongs to that `try`, as a `catch` at such a width
  does.
- `finally: NAME` followed by a newline, `;`, a dedent or the end of input
  is not a clause: it keeps its accepted reading, the typed declaration of
  `finally`.
- The innermost `try` statement whose catch suite the clause follows takes
  it. A `try` nested in a catch suite takes a `finally:` at its own level,
  and the enclosing `try` one at the enclosing level.

```
attempts = []
def charge(balance, amount):
    try:
        if amount > balance:
            throw "DECLINED"
        return balance - amount
    catch reason:
        return reason
    finally:
        attempts.push(amount)
assert(charge(50, 30), 20)
assert(charge(20, 40), "DECLINED")
assert(attempts, [30, 40])
log = []
try:
    log.push("body")
catch:
    log.push("catch")
finally:
    log.push("finally")
try: log.push(1)
catch: log.push(2)
finally: log.push(3); log.push(4)
assert(log, ["body", "finally", 1, 3, 4])
```

- Each charge is recorded on its way out, whether the body returns the new
  balance or the catch suite returns the reason it declined.

### Outcomes

- The body runs as before. When it completes, normally or by `return`, the
  `finally` suite runs, and then the statement completes as the body did.
- When the body fails, its changes roll back and the catch suite runs with
  the error bound, as before. When the catch suite completes, normally or
  by `return`, the `finally` suite runs, and then the statement completes
  as the catch suite did.
- When the catch suite fails, its changes roll back, the `finally` suite
  runs, and then the catch suite's error propagates.
- A `return` in the `finally` suite replaces the pending outcome, a pending
  `return` or a pending error, and a failure of the `finally` suite
  propagates in its place.
- A pending `return` keeps the value computed when its `return` ran. The
  statement's value, which the REPL prints and which a program that ends
  with the statement returns, is the value of the suite it completes as.
- At the top level a `return` in any of the three suites ends the program,
  after the `finally` suite has run.

| Body | Catch suite | `finally` suite | Statement |
| --- | --- | --- | --- |
| completes | not run | completes | completes as the body did |
| returns `v` | not run | completes | returns `v` |
| fails, rolled back | completes | completes | completes as the catch suite did |
| fails, rolled back | returns `v` | completes | returns `v` |
| fails, rolled back | fails with `e`, rolled back | completes | fails with `e` |
| any | any | returns `w` | returns `w` |
| any | any | fails with `f` | fails with `f` |

```
log = []
try:
    try:
        log.push("read")
        throw "SENSOR"
    catch fault:
        log.push("retry")
        throw fault + " DOWN"
    finally:
        assert(log, [])
        log.push("cleanup")
catch outage:
    assert([outage, log], ["SENSOR DOWN", []])
    log.push(outage)
assert(log, ["SENSOR DOWN"])
def settle(order):
    try:
        order.state = "paid"
        return order.state
    catch:
        return "failed"
    finally:
        order.state = "closed"
cart = {state: "open"}
assert([settle(cart), cart.state], ["paid", "closed"])
def recover(order):
    try:
        throw "LOST"
    catch problem:
        order.state = problem
        throw problem
    finally:
        return order.state
assert(recover(cart), "closed")
```

- The inner `finally` suite sees neither the body's nor the catch suite's
  push, and its own push leaves with the error. `settle` returns the state
  it read before the `finally` suite closed the order, and `recover`'s
  `finally` suite returns over the catch suite's error, after that suite's
  write was rolled back.

### Transactions

- The `finally` suite's changes commit with the statement. When an error
  leaves the statement, the enclosing rollback, of an enclosing `try` or of
  the whole run, undoes them with the rest of the statement, as it undoes
  every other change of a failed statement.
- A failed body is rolled back, with its pending propagation and deletion
  tracking, before the catch suite runs, as at the accepted revision. A
  failed catch suite is rolled back the same way before the `finally`
  suite runs. So a pending error that a `return` in the `finally` suite
  replaces leaves the failed catch suite's changes rolled back.

```
class Tank(level):
    this.level = level
tank = Tank(80)
reading = tank.level * 2
audit = []
entries = audit.length
try:
    tank.level = 120
    assert(reading, 240)
    throw "OVERFLOW"
catch alarm:
    audit.push(alarm)
finally:
    audit.push(tank.level)
assert([tank.level, reading], [80, 160])
assert([audit, entries], [["OVERFLOW", 80], 2])
```

- The overflowing write and its propagation to `reading` are undone before
  the catch suite runs, and the `finally` suite records the restored level.

### Scope and standing rules

- The `finally` suite runs in the scope of the `try` statement: the catch
  parameter is not bound there, so reading it there reads whatever the
  name means outside the catch suite. Parameters, locals, loop variables,
  `this` and `self` are those of the enclosing body.
- Its statements run as those of a catch suite do: a top-level assignment
  is a declaration that stays live, and in a function, method,
  constructor, loop or block body they run in that body.
- A `try` statement runs when it is reached and files nothing of its own.
  Inside the branch of a standing `if`, or in a function called from a
  declaration, it runs its `finally` suite whenever that rule runs it.

### Rendering and graph keys

- Graph and block keys render a `try` statement as `try`, with or without
  the clause, as in `{try;y=4}`.
- Inside default-bearing declarations a `try` statement renders as
  `try:`, its body, `catch NAME:` and its catch suite, then `finally:` and
  the indented `finally` suite; without the clause it renders as before,
  and both renderings parse to the statement they render.
- `why`, `affects`, `--graph` and `--json` show the declarations of a
  `finally` suite as they show those of a catch suite: after a failed body,
  `z = a * 3` in the `finally` suite gives the same `why z`, `affects a` and
  dependencies as in the catch suite.

### REPL and terminal workspace

- The native REPL buffers a `try:` statement through its catch suite and a
  following `finally` clause until a blank line, and parses them together.
- A blank line commits the statement first, so a `finally:` typed after it
  is a statement of its own and raises `SyntaxError("Unexpected ':'")`, as
  a `catch:` typed after one raises
  `SyntaxError("Unexpected keyword 'catch'")`. A `try` line with an inline
  suite is submitted on its own, as at the accepted revision.
- The terminal workspace completes `finally`.

### Cost

- A `try` statement without the clause runs exactly the accepted code: its
  node holds `None` and runs no `finally` suite and takes no further
  savepoint.
- With the clause, the `finally` suite runs once on every exit, as the same
  statements would after the statement, and a failed body adds one
  savepoint for the catch suite: the transaction mark, a copy of the
  pending propagation stack and of the deletion tracking, as the body's
  savepoint already takes.
- Recognizing the clause costs one look at the tokens after each catch
  suite: the line breaks, the name and the colon.
- **Measured**, not projected, on the final tree: on `nucleoid-final.exe`,
  its release build, against the caller's release build of the accepted
  revision, rustc 1.97.1, through the command line with `--json`: the
  median of 21 interleaved runs of each program, including process start,
  one process at a time with nothing else running. Each program runs a
  `repeat 100000:` loop at the top level whose body is the statement
  shown, with `n = n + 1` as the work of the body that completes; a failing
  body throws and its catch suite adds 1, and in the "catch fails" rows the
  statement stands in a `try` whose own catch suite adds 1. Times are in
  milliseconds; the accepted build parses none of the programs with a
  clause.

| --- | ---: | ---: |

- Every program without a clause takes 0.99 to 1.02 times its time on the
  accepted build, so `try` statements without the clause cost what they
  cost.
- A clause costs its suite and a little more: `finally: pass` takes
  8.1 ms longer than `pass` after the statement over 100,000 statements
  whose body completes, about 81 ns a statement; 7.4 ms longer when the
  body fails, which also takes the catch suite's savepoint; and 17.8 ms
  longer when the catch suite fails, which also rolls that savepoint back.
  The suite `m = m + 1` takes 21.8 ms longer than the same statement after
  the `try`. Phase 1 measured the same rows on the same production sources
  at 4.1, 10.6, 22.6 and 19.6 ms, so differences of this size are within
  the variation between rounds.
- Pushing to a list in a loop grows quadratically at both revisions, as
  lists are values: 5,000 and 10,000 pushes take 0.84 and 3.86 s on the
  accepted build without a clause, and 0.82 and 3.57 s on
  `nucleoid-final.exe` with the push in a `finally` suite, single runs. So
  the measured programs count with a number instead.

### Compatibility

- The lexer and its token stream are unchanged; no keyword is reserved.
- Only inputs that were errors at the accepted revision change: a complete
  `try`/`catch` statement followed, on the next logical line at its level,
  by `finally` and `:`, outside the declaration `finally: NAME`. Each
  raised `SyntaxError("Unexpected ':'")`, reported at the token after
  `finally:`: at the colon's own column when the colon ends its line,
  because a line break takes the position of its line's last token, and
  otherwise at the suite's first token. Every accepted program keeps its
  parse, positions, diagnostics and behavior.

  parses through the statement path that `MAX_NESTING` guards and runs
  through the execution path that `MAX_DEPTH` guards. Every production
  file has at most 430 lines, and Clippy's `too_many_lines` and
  `tests/power_of_ten.rs` pass.
- **Public API and versions:** the variant `Stmt::TryFinally` and the
  public field `nuc::Try::finally` are the only public changes, which
  finding F4 reports for the human semantic-versioning review. `Try::new`
  keeps its signature. The version stays human-owned and unchanged, as do
  `Cargo.toml` and `Cargo.lock`, and nothing under `arc/` changes.

### Findings

- **Low, documentation (F1).** [Abstract](#abstract) and
  [Compatibility](#compatibility) state that every changed program raised
  `SyntaxError("Unexpected ':'")` at the accepted revision. A program that
  also uses Python-style `self` parameters raised
  [NUC 107](nuc-0107.md)'s kept first-pass error instead: a class `Meter`
  whose method `read(self, scale)` holds a `try` statement with a
  `finally` clause raised
  `SyntaxError("Expected a parameter but found keyword 'this'")`, line 2,
  column 18, where its spelling with `this` raised
  `SyntaxError("Unexpected ':'")`, line 10, column 16. It was still an
  error, so compatibility holds. The caller reproduced both on the
  accepted revision's build, and both programs now give `[6, [2]]`.
- **Low, rationale (F2).** The caller's applicability rationale said that
  a `return` replacing a pending error or `return` has no accepted form,
  and [Preparation checks](#preparation-checks) counts 44 programs without
  an accepted spelling. At the accepted revision, a nested `try` around
  the catch suite reproduces a `return` that replaces a failed catch
  suite's error (`recover` gives `"closed"`, and the count example
  `[0, 0]`), dropping a dead `return` reproduces a replaced pending
  `return`, and helper functions whose parameters hold the value reproduce
  pending returns (`[1, 5]` and `["paid", "closed"]`). These are rewrites
  program by program, so the `new_feature` classification stands.
- **Low, audit limit (F3).** As
  [Reference Implementation](#reference-implementation) states, the test
  walkers of `tests/repeat_loops.rs`, `tests/suppose.rs`,
  `tests/value_assignment.rs` and `tests/while_loops.rs` descend into
  `Stmt::Try` but reach `Stmt::TryFinally` only through their `_` arms, so
  a feature nested in a statement with a clause would escape their audits.
  `tests/finally_clauses.rs` asserts that none of the six cases holds one.
- **Info, public API (F4).** `Stmt::TryFinally` breaks downstream
  exhaustive matches over `Stmt`, and the public field `nuc::Try::finally`
  breaks downstream struct literals and exhaustive patterns of `nuc::Try`.
  Both need the human semantic-versioning review; `Try::new` keeps its
  signature, and no version number changed.
- **Info, editor (F5).** The terminal workspace now offers `finally` among
  its completion words, as [NUC 115](nuc-0115.md) added `repeat`.
- **Info, evidence (F6).** The evaluator did not rebuild the proposer's 29
  mutants; their two equivalence arguments read consistently with the
  parser and the transaction code.

### Records

- **Decisions before implementation:** the caller's binding decisions made
  `finally:` an optional clause of a complete `try`/`catch` statement:
  - the identifier `finally` immediately followed by `:` and a suite, as
    the first tokens of the logical line that directly follows the catch
    suite at the `try` statement's own level, with blank and comment lines
    allowed between, every suite form of an explicit-colon catch suite, and
    no new keyword or token kind;
  - every other reading kept: `finally` as a name, property, object key,
    function or parameter; the colon-free `finally` line with an indented
    block; `try` without `catch`, with its pinned
    `SyntaxError("Expected 'catch' after 'try'")`; the clause on the catch
    suite's line or after `;`, where it would collide with accepted
    juxtaposition and conditionals; every misplaced `finally:`; and every
    `try` and `catch` form of [NUC 9](nuc-0009.md) and
    [NUC 46](nuc-0046.md);
  - the outcomes of Python, JavaScript and Java, with a failed body and a
    failed catch suite each rolled back before the next suite runs, a
    pending `return` keeping the value it computed, the `finally` suite's
    changes undone with the statement when an error leaves it, the catch
    parameter unbound in the `finally` suite, and no new error type or
    message format;
  - the rendering with the clause and the graph key `try`, the REPL's
    buffering until the blank line, documented for a blank line before
    `finally:`, `finally` as a completion word, as
    [NUC 115](nuc-0115.md) added `repeat`, the exporter's splitter
    unchanged and the optional clause in `docs/nucleoid.g4`;

  - the compatibility claim in [NUC 108](nuc-0108.md)'s form, and the
