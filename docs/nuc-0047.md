# NUC 47 -- Opt-In Named Constructors

```
NUC: 47
Title: Opt-In Named Constructors
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Created: 21-Oct-2026
```

## Abstract

- A leading `*` in a class constructor header opts that constructor into
  named-only binding: `class Pair(*, a, b):` accepts `Pair(b=2, a=1)` without
  assigning caller variables.
- Preserve every unmarked class's positional and assignment-expression
  semantics, all function/method/built-in calls, existing construction routes,
  argument snapshots, graph behavior and transactional failures.
- The accepted contract is the authoritative
  [Opt-in named constructors](../nucleoid.spec.md#opt-in-named-constructors)
  section and its eight paired executable entries. Independent evaluation
  accepted the frozen r2 Draft as recorded below.

## Motivation

- Symbolic objects often have several same-shaped properties. Their call-site
  order should not determine which declared parameter receives each value.
- The requested `Obj(a=1, b=2)` currently evaluates ordinary assignment
  expressions positionally. Reinterpreting all existing calls would silently
  change both their values and caller-scope effects.
- A class-owned opt-in lets new models use meaningful labels without
  invalidating established positional construction.
- This is an explicitly requested runtime/data-modeling enhancement, not an
  unspecified-feature draw. The caller selected `opt_in_equals` after resolving
  the compatibility choice; no category redraw or substitute feature is used.

## Rationale

- Choose `class Obj(*, a, b)` over globally enabling keyword arguments.
  Existing class/function/method/built-in calls must not change binding mode.
- Use a concrete `ConstructorBinding` enum on class declarations and class
  data, not a fake parameter, annotation sentinel, magic name or dynamic map.
- Keep calls as their existing `Expr::Call`/`Expr::Super` with assignment
  expressions. Resolve the meaning of `name=value` from the effective
  constructor at runtime; no lexer keyword or broad call rewrite is needed.
- Keep the selected binding mode with the constructor, including initializer
  adoption and inheritance. Do not add callable class aliases or repair
  unrelated legacy routing differences.
- Validate labels before evaluating any RHS. This prevents invalid calls from
  executing side effects or `.value` reads merely to discover a binding error.
- Preserve the accepted snapshot semantics. A constructor parameter value is
  not a new reactive link to the caller's source variable.
- Missing values remain `null`; defaults, positional/named mixing, rest
  parameters, automatic fields and general function keyword arguments are
  separate features and are not added.
- Retain all 611 historical measured programs without rewriting their syntax.
  Append only the nine caller-supplied, pre-executed counterparts, preserving
  document/title identities, assertion order, expected returns and coverage.

## Specification

- A parenthesized class parameter list may begin with a single `*`.
  Accept `(*)`, `(*,)` and `(*, a, b: int, ...)` with ordinary parameter
  annotations, trailing commas and existing parenthesized layout.
- Unmarked class lists and every function signature use their unchanged
  parser path. A star anywhere else does not introduce a new signature form.
- Marked formal names must be unique. Unmarked duplicate formals retain their
  existing behavior; annotations remain metadata rather than new type checks.
- Constructor bodies, field declarations, class-body suites and inheritance
  punctuation keep their accepted grammar. An empty/bodyless constructor does
  not automatically assign its parameters to properties.
- `class Pair(*)` with `def init(a, b):` adopts that method's parameters/body
  under the existing adoption rule, retaining the class's named mode. The
  adopted parameters must be unique; calling `pair.init(...)` directly remains
  positional.
- Resolve the effective constructor with the existing nearest-nonempty-body
  inheritance rule. Use that constructor's declaring class, parameters, body
  and mode together; an empty child header does not override a parent's mode.
- In named mode, every argument must be a parsed assignment expression with a
  simple identifier target. Parenthesized assignments and existing equivalent
  assignment lowering retain that AST interpretation. Member-target
  assignments and other positional expressions are not named arguments.
- Treat the target identifier only as a label; do not read it, assign it,
  require it to exist in caller scope or add it to dependency/root sets.
  Expressions inside the RHS retain their ordinary scope and side effects.
- Before any RHS evaluation, scan all argument bindings left to right.
  Reject the first invalid shape, unknown label or repeated known label.
- Evaluate supplied RHS values exactly once in source order in the caller's
  scope. Bind those results by declared parameter name/order, initializing
  omitted parameters to `null`. No positional surplus is accepted in named
  mode; ordinary constructors keep their existing permissive positional arity.
- Pin a named call's selected signature/body before evaluating RHS values, so
  a class redeclaration within an RHS cannot invalidate the validated plan.
  Positional calls keep their accepted constructor selection after evaluation.
- Re-declaration takes its binding mode from the new class header, preserving
  existing populations and class-level declarations exactly as before.
- Apply named binding through existing direct expression, assignment, property,
  shared class-rule and `new` construction routes. Preserve the existing
  assignment-instantiation versus ordinary-call shadowing differences.
- Named shared class-rule construction evaluates once in the declaration
  caller's scope, including its function parameters. Keep positional shared
  construction's accepted global-only scope and its existing diagnostics.
- `super(b=second, a=first)` binds according to the effective parent
  constructor's mode, on the same object. Constructor context advances from
  the executing constructor; method fallback uses the receiver's actual class.
- Bare `super` and `super()` still supply no arguments. Missing parent values
  become `null`; positional parents, no-parent calls and missing-receiver
  argument/error order remain unchanged.
- Preserve `.value`'s snapshot/no-dependency behavior. Named calls defer their
  argument snapshot reads until after binding validation, in RHS source order.
  Values stored by constructors remain snapshots; surrounding standing
  expressions retain their existing dependencies and may create new instances
  when re-evaluated.
- Class-rule reference checks and block instance-read checks distinguish
  labels from real RHS references using actual call routing and the selected
  mode. Continue checking RHS references and class-property cycles.
- Canonical call source stays `Pair(b=2,a=1)`. Named class header rendering
  retains the star, declared names and annotations; its class node still uses
  the class name. All legacy header/call keys remain unchanged.
- Keep the accepted fresh caller scope for each separate `Runtime::run`.
  The Rust exporter retains assignment-expression cases as whole original
  programs with executed assertions and AST coverage, rather than extracting
  a later caller-local read into another invocation.
- Binding failures precede object registration. Other RHS/body/parent/rule
  errors retain existing transaction and catch-savepoint rollback of objects,
  populations, properties, class metadata and graph writes. Existing local
  RHS-assignment behavior is not changed.
- Keep source positions, layout rules and expression/statement/chain limits.
  Introduce no new parameter-count cap, dependency, project version change,
  ARC change, runtime provider or network requirement.
- Executable specification traces:
  - `Nucleoid binds opted-in constructor arguments by name`: out-of-order
    mapping and caller isolation.
  - `Nucleoid evaluates named constructor values in source order`: once-only,
    left-to-right values.
  - `Nucleoid inherits opted-in named constructors`: inherited mode.
  - `Nucleoid binds named parameters through opted-in initializers`: marker-only
    opt-in and unchanged `def init` signatures.
  - `Nucleoid keeps missing opted-in constructor parameters null`: omitted
    values without defaults.
  - `Nucleoid snapshots named constructor argument values`: accepted snapshot
    behavior after the source variable changes.
  - `Nucleoid preserves positional constructor assignment arguments`: the
    supplied legacy program is unchanged.
  - `Nucleoid forwards named arguments to opted-in parent constructors`:
    an ordinary positional child forwards names to its parent.
- The executable reference adds only
  `Nucleoid constructs an object with named parameters`; `docs/README.md`
  repeats that exact example. README/examples add prose links, not unpaired
  executable blocks.
- The isolation entry, without its case-title comment, is:

```
a = 10
b = 20
class Pair(*, a, b):
    this.a = a
    this.b = b
pair = Pair(b=2, a=1)
assert(pair, {"id": "pair", "a": 1, "b": 2})
assert(a, 10)
assert(b, 20)
```

## Errors

- After a leading marker, a token other than comma/right-parenthesis raises
  `SyntaxError("Expected ',' or ')' after constructor '*'")` at that token.
- A repeated marker at a marked-list parameter position raises
  `SyntaxError("Constructor '*' must appear once, before all parameters")`
  at the repeated star. A nonleading star in an unmarked class list retains
  `SyntaxError("Expected a parameter but found '*'")` and its existing position.
- A repeated marked formal raises
  `SyntaxError("Duplicate named constructor parameter '<name>'")` at the
  repeated identifier. In an adopted initializer it is placed at that method's
  `def`. Other malformed parameter/suite errors are inherited unchanged.
- A positional or non-identifier-target argument raises
  `TypeError("Constructor <class> requires named arguments")`.
- An undeclared label raises
  `TypeError("Unknown constructor argument '<name>' for <class>")`.
- A repeated declared label raises
  `TypeError("Duplicate constructor argument '<name>' for <class>")`.
- `<class>` names the selected constructor's declaring class, including
  inherited and `super` calls. Runtime placement and position-free caught-value
  rendering use the existing error system.
- RHS/body/rule failures keep their existing error kinds/messages; no new
  exception kind is introduced.

## Reference Implementation

- The isolated Rust prototype adds typed class binding metadata, a guarded
  class-header parser, validated named argument preparation, effective
  constructor resolution and corresponding `super` handling.
- Validate named binding plans against borrowed effective class metadata
  before cloning the selected signature/body. Only a complete valid plan pins
  that owned constructor snapshot, before any RHS evaluation.
- Move evaluated argument values and owned parameter names into constructor
  scope rather than cloning them. Preserve source order, omitted `null`,
  duplicate legacy-formal behavior and evaluation of surplus legacy arguments.
- Named calls retain the selected constructor while legacy calls retain
  delayed constructor selection. Both use the existing object registration,
  scope, receiver, graph and transaction machinery.
- Context-aware root collection and `.value` preparation prevent labels or
  pre-validation snapshots from leaking into caller analysis/evaluation.
- Preserve the complete legacy class AST `Debug` rendering by omitting only
  the new default positional field; named metadata is explicit and equality
  always checks it. Existing historical fingerprint constants stay unchanged.
- The existing export-shape scanner conservatively selects whole-program
  execution for grouped assignment expressions, without reclassifying ordinary
  block assignments. The actual parser/runner still
  validates syntax, assertions, coverage and returns; no new parser or
  runtime scope-lifetime rule is introduced by the build tooling.
- `tests/named_constructors.rs` and two native CLI fixtures cover new edge
  cases, exact diagnostics, typed/untyped/bodyless forms, adoption, construction
  routes, inheritance/super, scope, snapshots, roots, graph/reasoning,
  redeclaration, rollback, legacy calls and resource bounds. The ownership
  regression covers composite values, omitted `null`, duplicate legacy
  formals and surplus argument evaluation.
- `tests/nuc47_compatibility.rs` provides an explicitly invoked, behavior-only
  replay of all pinned accepted documents, the nine supplied extra sources and
  their candidate counterparts. It checks source preservation, canonical
  assertions, expected returns and executed assertion coverage; it does not
  measure tokens, write a report or decide acceptance.
- Preserve every existing synthesized record; add a focused four-record
  `dataset/nucleoid.synth.28.jsonl` batch. Generate the normative JSONL and Rust
  exports only with the documented dataset/build commands.
- Adding `constructor_binding` to public `ClassDecl` and `ClassData` is
  source-breaking for downstream Rust struct-literal users. Downstream
  initializers must choose `ConstructorBinding::Positional` or `Named`; the
  existing `ClassData::new` defaults to positional. A human-owned breaking
  semantic-version decision is required before releasing that public API.
  This proposal changes neither Cargo version metadata nor dependencies.
- Preparation incorporates the completed caller-owned Rust improvement pass
  and performs development/compatibility checks only. Independent token
  measurement and the verdict belong to a fresh evaluator after the frozen
  handoff.
- Independent evaluation accepted the frozen r2 Draft blob
  `f828f9742d1ca8713341f79b739aeea8da1155b5` against accepted revision
  `e9b275615f52a36bb818e3a90cb96fe78b1241d7`, after the sole Rust improvement
  pass and fresh r2 preparation. The r1 snapshot was not evaluated or rejected.
- All 620 paired cases passed: eight use fewer lexer tokens, 612 are
  unchanged, and none increased. The metric includes every layout token and
  excludes only `Eof`; no increase was offset by another case's savings.
- All 611 historical programs remain unchanged. The accepted and candidate
  counterparts preserve 2,784 executed assertions and 50 explicit returns on
  each side, all canonical assertions and all expected results.
- Independent ordinary checks passed 1,379 tests with 15 intentionally
  ignored. The explicit compatibility replay, actual proposal gate, native
  construction probes, formatting, warning-denied Clippy and export consistency
  passed without repairs or regeneration during evaluation.
