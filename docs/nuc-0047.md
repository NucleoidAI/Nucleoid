# NUC 47 -- Default Named Constructors

```
NUC: 47
Title: Default Named Constructors
Author: Can Mingir <canmingir@gmail.com>
Status: Accepted
Type: Standards Track
Category: Runtime features
Created: 21-Oct-2026
```

## Abstract

- Revise NUC 47 so ordinary class headers support positional arguments, names
  in any order, and positional arguments followed by names.
- Remove the constructor star-header syntax entirely; there is no optional
  marker, named-only class mode, or class binding metadata.
- A bare constructor `name=value` is a label, not a caller assignment.
  Explicit grouping, as in `Legacy((b=2), (a=1))`, preserves a positional
  assignment argument.
- These two changes are intentional, narrowly authorized source migrations.
  They are not a claim that every formerly accepted source is unchanged.
- This revision was independently accepted under the two explicitly
  authorized constructor migrations. The prior opt-in outcome remains
  historical evidence, not the current constructor contract.
- The authoritative accepted contract is
  [Default named constructors](../nucleoid.spec.md#default-named-constructors).

## Motivation

- The requested `Student(name, age)` model should work naturally with both
  `Student("Can", 20)` and `Student(age=20, name="Can")`.
- A separate class mode makes the same model choose between positional and
  labeled construction, rather than allowing each caller to choose clarity.
- The latest explicit direction is: "I don't want * at all but I agreed with
  the table". It replaces the earlier `opt_in_equals` design choice; retaining
  the star as an optional compatibility spelling would contradict it.
- This is an explicit runtime/data-modeling feature request, not an
  unspecified enhancement selection or random draw.

## Rationale

- Bind labels by the effective constructor's declared parameter names, while
  preserving every existing purely positional construction case.
- Interpret only bare identifier `=` arguments as labels, and only when the
  existing call route actually constructs a class or invokes a parent
  constructor. Functions, methods and built-ins keep assignment expressions.
- Keep ordinary `Expr::Call`, `Expr::Super` and bare `Expr::Assign` shapes.
  Preserve explicit positional intent only for assignment-shaped arguments
  that were not bare labels; do not wrap every existing call argument.
- Use a typed identity unary boundary for those positional assignments.
  Render it with parentheses and retain it on reparse. Existing expression
  walkers then continue to see the underlying assignment and its real reads.
- Reject unknown names, duplicate bindings and positional-after-named calls
  before any argument effects or snapshot reads. Rollback after effects is
  not a substitute for validating first.
- Preserve parameter snapshots, inheritance's nearest nonempty constructor
  body, initializer adoption, actual caller scope, receivers, class rules,
  shadowing routes, canonical instance expressions and transactions.
- Keep omitted parameters `null`, surplus positional evaluation/ignore
  behavior, duplicate legacy formals, and existing purely positional
  constructor-selection and `.value` preparation rules.
- Default parameter expressions, rest parameters, automatic fields, callable
  class aliases and general function keyword arguments are out of scope.
- Preserve every protected case identity, canonical assertion and its order,
  expected return and executed assertion coverage. Historical titles saying
  "opted-in" remain stable corpus identities, not continuing syntax.
- The explicitly approved migration set is eleven star-header counterparts
  and one raw-constructor-assignment counterpart. No broad class,
  assignment-bearing, or error-case exclusion is permitted.

## Specification

- An ordinary class declaration uses its existing typed/untyped parameter
  grammar, including empty/bodyless headers, trailing commas and layout.
  No constructor-header `*` form is accepted.
- For `class Student(name, age)` the requested calls have these meanings:

| Call | Binding |
| --- | --- |
| `Student("Can", 20)` | `name` is `"Can"`, `age` is `20`; unchanged positional binding |
| `Student(name="Can", age=20)` | Bind labels without assigning caller variables |
| `Student(age=20, name="Can")` | Reorder values into the declared slots |
| `Student(nmae="Can", age=20)` | Unknown-name error before values run |
| `Student("Can", age=20)` | Fill the first slot positionally, then bind `age` |

- A bare identifier immediately followed by ordinary `=` at an argument
  boundary denotes a constructor label. Its RHS is an ordinary expression;
  nested assignments in that RHS still execute.
- `Legacy((b=2), (a=1))` explicitly evaluates assignments and passes their
  values positionally. Redundant grouping is canonicalized to one boundary.
  Grouped identifier targets and compound assignments also stay positional.
  Member-target assignments remain ordinary positional expressions.
- Only constructors and effective parent-constructor calls interpret labels.
  `pair(b=2, a=1)`, `object.method(b=2, a=1)`, native calls and direct
  `object.init(...)` retain their accepted assignment-expression behavior.
- For a call with at least one label, scan every binding left to right before
  evaluating any argument. Positional arguments fill successive declared
  slots; labels select their named slots. Reject the first unknown name,
  already bound slot, or positional argument following a label.
- A positional binding and a label for that same parameter are duplicates,
  even if their values would be equal. Missing arguments remain `null`.
  Surplus positional expressions are still evaluated and ignored; no new
  arity or parameter-count restriction is introduced.
- Evaluate values exactly once in source order in the actual caller's scope,
  then bind the resulting snapshots in parameter declaration order.
  Labels neither require nor write caller variables and never become
  dependency/root names.
- Use the existing nearest nonempty constructor body's signature. Bodyless
  child headers do not replace a selected ancestor signature. Adopted `init`
  methods provide the same parameters/body as before, without a class mode.
  Empty constructors do not automatically create properties.
- Pin a valid named/mixed call's effective signature/body before evaluating
  values, including positional values before its labels. An RHS class
  redeclaration cannot change that validated plan.
- Purely positional calls retain constructor selection after argument
  evaluation and their existing `.value` preparation. Redeclarations retain
  existing instances and class declarations.
- Support existing expression, assignment, property, collection, `new` and
  shared class-rule construction routes. Do not change class/function/local
  shadowing precedence or add callable class aliases.
- Named/mixed shared class-rule construction evaluates once in the
  declaration caller's scope, including function parameters. Purely positional
  shared construction keeps its accepted global-only scope and diagnostics.
- `super(...)` uses the effective parent constructor's signature on the same
  object. Positional, reordered named and positional-then-named forwarding
  work with ordinary parent headers.
- Constructor context advances from the executing constructor; method
  fallback uses the receiver's actual class. Bare `super`, `super()`,
  no-parent calls and missing-receiver argument/error order remain unchanged.
- Only named/mixed forwarding pins the parent before values run. Purely
  positional `super` resolves the current parent after all arguments run,
  including any argument-side class redeclaration. Explicit grouped
  assignment arguments keep that same positional order.
- Named/mixed calls defer all argument `.value` reads until after complete
  binding validation, in source order. `.value` still introduces no dependency.
  Stored constructor values remain snapshots; surrounding standing
  expressions retain their actual reads and may create new instances when
  re-evaluated.
- Class-rule static checks validate known constructor bindings before RHS
  reference checks. Context-aware roots ignore labels, but still inspect
  real RHS references, grouped assignments and class-property cycles.
- Canonical labeled source remains `Pair(b=2,a=1)`; the explicit assignment
  escape remains `Pair((b=2),(a=1))` on render/reparse. Ordinary class statement
  keys remain `class Pair`; no instance identifier or reasoning spelling is
  changed merely to make binding work.
- Binding failures precede object registration. RHS, body, parent and rule
  failures retain existing transaction/catch-savepoint restoration of objects,
  populations, properties, class metadata and graph writes.
- Caller-local assignment effects and fresh `Runtime::run` caller scopes
  retain their accepted rules. The normative exporter keeps scope-sensitive
  programs whole, including their actual assertions and returns.
- Keep existing statement positions, nesting and chain bounds, field and
  annotation rules, dependencies, version metadata and unrelated ARC work.
- Executable specification traces retain these identities:
  - `Nucleoid binds opted-in constructor arguments by name`: reordering and
    caller isolation with an ordinary class header.
  - `Nucleoid evaluates named constructor values in source order`: once-only
    source-order evaluation.
  - `Nucleoid inherits opted-in named constructors`: effective inheritance.
  - `Nucleoid binds named parameters through opted-in initializers`: adoption.
  - `Nucleoid keeps missing opted-in constructor parameters null`: omissions.
  - `Nucleoid snapshots named constructor argument values`: snapshots.
  - `Nucleoid preserves positional constructor assignment arguments`: explicit
    grouped assignments with every original canonical assertion unchanged.
  - `Nucleoid forwards named arguments to opted-in parent constructors`: super.
  - `Nucleoid constructs students with positional and named arguments`:
    actual positional and labeled calls.
  - `Nucleoid mixes positional and named constructor arguments`: ordered,
    reordered and actual mixed calls.
  - `Nucleoid validates constructor names without caller assignments`:
    unknown and mixed duplicate errors with caller isolation.
  - `Nucleoid preserves ordinary function argument assignments`: functions.
- The executable reference retains
  `Nucleoid constructs an object with named parameters`; `docs/README.md`
  repeats that example with its ordinary header. README/examples add prose
  links, not unpaired executable snippets.

## Errors

- A constructor header star raises the ordinary parameter diagnostic
  `SyntaxError("Expected a parameter but found '*'")`. No optional star
  compatibility grammar or marker-specific diagnostic is retained.
- An undeclared label raises
  `TypeError("Unknown constructor argument '<name>' for <class>")`.
- A repeated label or positional-plus-named binding raises
  `TypeError("Duplicate constructor argument '<name>' for <class>")`.
- A positional argument following a label raises
  `TypeError("Positional constructor argument after named arguments for <class>")`.
- `<class>` names the effective constructor's declaring class, including
  inherited and `super` calls. These binding errors occur before RHS effects
  or `.value` reads and use existing runtime source placement and
  position-free caught-value rendering.
- Other malformed parameters, suites, RHS/body/rule failures and resource
  limits retain their existing error kinds, messages and placement.
- Duplicate legacy formal parameters remain permitted; no new signature
  uniqueness check or exception kind is introduced.

## Reference Implementation

- The Rust prototype removes `ConstructorBinding` and the associated public
  `ClassDecl`/`ClassData` mode fields. Ordinary headers use the existing
  parameter parser.
- At the call-argument boundary the parser preserves non-bare identifier
  assignments with `Expr::Unary { operator: UnaryOp::Positional, ... }`.
  It is identity evaluation with explicit canonical parentheses, not a
  general grouping or assignment redesign. Unrelated argument ASTs and all
  protected canonical assertions remain unchanged.
- A concrete argument binding plan tracks each source expression and its
  optional declared slot. Validate against borrowed effective class metadata
  before cloning/pinning a valid named/mixed constructor snapshot.
- Move evaluated values and owned parameter names into constructor scope.
  Purely positional calls retain delayed selection; named/mixed calls keep
  their validated signature/body through argument-side redeclaration.
- Context-aware constructor routing controls labels, roots, snapshots, shared
  scope and `super`; ordinary function/method/native assignment arguments
  continue through existing evaluation.
- `tests/named_constructors.rs` and native fixtures cover no-star rejection,
  defaults, reordered/mixed binding, exact diagnostics, validation before
  effects/snapshots, grouped/compound assignments, rendering/reparse,
  scope/shadowing, inheritance/super, class rules, graph/reasoning, rollback,
  initializer adoption, omitted `null`, duplicate legacy formals and surplus
  positional evaluation.
- The positional-super regression test covers ordinary positional, grouped
  assignment, named and mixed forwarding in both constructor and method
  contexts, checking parent selection, once-only effects and populations.
- `tests/nuc47_compatibility.rs` pins accepted revision
  `835c1ac3087a1aee3cc5cc578f02a5784a8a0c3b`: 620 accepted executable cases
  plus four pre-executed supplied equivalents. It enumerates the twelve exact
  authorized migrations, verifies their replacements against the immutable
  assertions/returns/coverage, and replays every other accepted program
  unchanged. It does not pretend removed star headers or raw assignment
  arguments keep their former meaning.
- The replay requires the caller's immutable baseline, extra-source and
  authorization artifacts. Its separate development lexer probe prints
  actual baseline/candidate counts without running `evaluate_proposal`,
  writing an acceptance report or issuing a verdict.
- Keep synthesized record IDs, assertions and expected results in
  `dataset/nucleoid.synth.28.jsonl` while removing obsolete star forms.
  Regenerate normative JSONL with `UPDATE_DATASET=1 cargo test --test dataset`
  and exported Rust with `UPDATE_SPEC_TESTS=1 cargo build`; do not edit them
  manually. The four supplied new spec identities account for the explicit
  specification count change from 416 to 420.
- Historical evidence, not this revision's result: the prior opt-in r2 Draft
  blob `f828f9742d1ca8713341f79b739aeea8da1155b5` was independently accepted
  against `e9b275615f52a36bb818e3a90cb96fe78b1241d7`. Its 620 pairs had eight
  shorter and 612 equal cases, no increases, 2,784 executed assertions and
  50 explicit returns. The r1 snapshot was not evaluated or rejected.
  Earlier session artifacts are not overwritten or reused as this baseline.
- Removing public mode types/fields and adding a unary enum variant are
  source-breaking for downstream Rust users that name those types/fields or
  exhaustively match operators. The two authorized language migrations also
  require a human-owned breaking-release decision. No dependency or project
  version metadata is changed by this proposal worker.
- Preparation performs development checks only. The caller owns the single
  Rust improvement pass, subsequent fresh independent evaluation,
  status/index outcomes and integration. This worker does not decide the
  candidate's acceptance.

### Accepted Default-Constructor Revision Outcome

- Decision: Accepted for frozen proposal blob
  `b35cecf5e0066e40c115b9622e5e0504e9c23519`, against accepted revision
  `835c1ac3087a1aee3cc5cc578f02a5784a8a0c3b`.
- The independent lexer gate measured 624 paired cases: 11 shorter, 613
  equal, and none longer. Layout tokens count; only `Eof` is excluded.
- All protected canonical assertions, assertion order, 2,796 executed
  assertions and 50 explicit expected returns were preserved.
- Compatibility replay executed 612 accepted sources unchanged. The twelve
  exact replacements below are authorized migrations, not unchanged-source
  compatibility claims. No other compatibility exception was accepted.

  are not repository data.
- This outcome updates status/index metadata only; the accepted runtime,
  executable sources, synchronized data and generated exports are unchanged.
- A human-owned major-release decision remains necessary for the breaking
  language and public Rust API changes. Project versions remain unchanged.
