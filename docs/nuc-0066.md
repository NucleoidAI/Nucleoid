# NUC 66 -- Imperative Value Assignment

```
NUC: 66
Title: Imperative Value Assignment
Author: Claude <noreply@anthropic.com>
Status: Accepted
Type: Standards Track
Category: Runtime features
Created: 31-Oct-2026
Requires: 8, 13, 45, 51, 53, 57, 59, 62, 65
```

## Abstract

- Adds the value assignment statement `TARGET := EXPR`, as Go and Pascal
  spell assignment. It is an action taken once, beside the standing
  declarations, the laws, that `=` makes.
- `EXPR` is evaluated once in the current scope, and its value is assigned to
  `TARGET` exactly as `TARGET = LITERAL` would assign it. The value is the
  one `TARGET = EXPR` would store at that moment, null-read rule included.
- The statement records no dependency and no structural subscription, for
  its target or for anything around it. That covers the reads made by the
  functions, methods and callbacks `EXPR` calls, and the reads that locate
  the target.
- Where `=` files a declaration, the target becomes a stated fact whose
  declaration is the literal: it replaces any standing relationship, its
  dependents still propagate, and `why` shows `TARGET = LITERAL` as
  `stated`. Where `=` is only carried out, in a `for` body, a standing `if`
  branch or a block, `:=` is carried out once each time it runs.
- `:=` is one lexer token and a statement only. Targets follow the compound
  assignment target rules of [NUC 13](nuc-0013.md). Outside a class-level
  rule, a class-level target raises
  `TypeError("Cannot use ':=' on a class-level property")`.
- Every accepted program keeps its tokens, parse and behavior: `:` was never
  directly followed by `=` in a valid program, except in the ignored trailing
  tokens of a template interpolation, which stay ignored.
- The authoritative contract is the
  [value assignment](../nucleoid.spec.md#value-assignment) section.

## Motivation

- A world model has laws, relationships that must keep holding, and actions,
  events that happen once. `available = stock - reserved` is a law. "An order
  of three ships, so stock drops by three" is an action. An LLM that
  maintains a world model needs both, and needs to write each plainly.
- Accepted Nucleoid spells every assignment as a law. An action written with
  `=` silently becomes a standing relationship that is applied again whenever
  its inputs change:
  - with `stock = 10` and `qty = 3`, `stock = stock - qty` gives `7`, and a
    later `qty = 5` re-applies it to give `2`;
  - the same happens through an instance property: `stock = stock - o.qty`
    becomes `3` instead of `7` after `o.qty = 4`;
  - a constructor that copies the catalog price, `this.price = catalog.price`,
    makes every existing order follow later price changes;
  - a method that accrues interest, `this.balance = this.balance + rate`,
    accrues again on its stored result whenever `rate` changes.
- Inside the branch of a standing rule the trap is worse. In
  `if paid: stock = stock - qty`, and even with `stock -= qty.value`, the
  branch reads `stock`, so restocking with `stock = 20` re-runs the branch
  and deducts the order again. A class-level version of that rule loops until
  the runtime reports `TypeError("Propagation did not settle")`.
- Accepted syntax can take a value once, but each spelling is indirect:
  - `.value` on every read, `stock = stock.value - qty.value`, which keeps
    the frozen expression as the stored rule and must be repeated per read;
  - a one-iteration loop, `for t of "a": stock = stock - qty`, which never
    replaces a standing relationship and still leaks its reads into an
    enclosing `if`, block or declaration;
  - `stock = suppose: stock - qty`, which runs the expression in a
    hypothetical world and discards everything that expression did.
- `TARGET := EXPR` states the action directly, at the cost of `=`. It is
  the spelling LLMs already know from Go and Pascal, and the one-token
  difference from `=` keeps the law and the action side by side in the same
  statement form.

## Rationale

- **Category and applicability.** The caller selected Runtime features by one
  uniform draw over the four eligible registry categories, index 1 with
  probability 1/4 and no redraw, in continuous mode. Value assignment adds an
  execution mode for the existing assignment statement: one evaluation with
  dependency tracking switched off, then the existing assignment.
- Runtime applicability is `existing_comparable`. Draft
  [NUC 2](nuc-0002.md) defines `.value` as the opt-out from dependency
  tracking, accepted [NUC 51](nuc-0051.md) runs `for` bodies once, and
  accepted [NUC 65](nuc-0065.md) assigns a one-shot snapshot with
  `TARGET = suppose: EXPR`. Every new measured case therefore has a
  behavior-equivalent accepted-syntax counterpart. The precedents are
  NUC 51, 54, 55, 59 and 60.
- **Token policy.** In this continuous cycle, Runtime features with
  `existing_comparable` applicability require the token non-regression gate.
  All eleven new measured cases were paired with the most compact
  accepted-syntax counterparts found, executed by the accepted runtime and
  supplied through `NUC_PROPOSAL_EXTRA_BASELINES` before any candidate edit.
  The counterparts use `.value` on each read that later changes, compound
  assignment with `.value` where the target reads itself, `= suppose:` where
  a literal or a self-read inside a rule must be kept, and one-iteration
  `for` packs over runs of top-level actions. No pre-existing case is
  rewritten; the independent evaluator measures the comparison.
- **Isolated tracking.** The statement runs inside an isolated tracking
  frame, the barrier that `.value` already uses for its operand. Reads stop
  at the barrier, so nothing reaches the target's declaration, an enclosing
  `if` or block, or a declaration whose evaluation called the function that
  holds the statement. Structural subscriptions stop at the same barrier, so
  a reasoning selection read by `EXPR` is a one-shot count, not an observer.
- The target-locating reads are isolated too. A rule such as
  `if paid: order.status := "shipped"` then depends only on `paid`. Rejected:
  tracking the target path as `=` does, which would make the statement a
  partial law again.
- **The value `=` would store.** `EXPR` is evaluated by the existing
  assignment evaluator, so its value is exactly what `TARGET = EXPR` stores
  at that moment: a read of a null binding or property stores `null`, as do
  undefined values. The two statements always agree right after they run
  and differ only in what happens later. Rejected: the snapshot rule of
  `.value` and `suppose`, under which `x := n + 1` with a null `n` would store
  `1` while `x = n + 1` stores `null`.
- **A stated literal.** Where `=` files a declaration, `:=` files the same
  node kind with the value written back as a literal, as NUC 65 does for an
  assigned `suppose` block: a number, string, boolean or `null`, a list of
  literals, an object reference, a function, `Date(<milliseconds>)` or a
  class name. The node has no dependencies and no structural subscriptions,
  so it never runs again, and `why` explains it as a stated fact instead of
  as the expression it came from.
- **Imperative where `=` is imperative.** In a `for` body, a standing `if`
  branch and a block, `=` is carried out without being filed, and so is
  `:=`. A standing `if` therefore takes the action each time its branch runs,
  which is what "when the order is paid, take the stock" means, and never
  because the action's own inputs or its target changed.
- **Distinct from `= suppose:`.** `TARGET = suppose: EXPR` also stores a
  one-shot literal, but it is a hypothetical, not an action:
  - `suppose` runs `EXPR` in a hypothetical world and discards its effects,
    so `kept := bump()` keeps the counter that `bump` advances while
    `suppose: bump()` rolls it back, and `first := Order(2)` keeps the
    instance it creates;
  - `suppose` converts objects to plain copies, while `:=` keeps the object:
    `picked := Item.find(...)` is the instance itself;
  - `suppose` takes the raw value, while `:=` applies the null-read rule of
    `=`;
  - `suppose` pays for a savepoint, a fresh propagation queue and a rollback,
    while `:=` runs in the real world once;
  - `:=` costs the same as `=`, two tokens fewer than `= suppose:`.
  The development suite executes the first three differences.
- **Distinct from `.value`.** `.value` freezes one read and leaves the
  expression in the stored rule, and it does not apply the null-read rule. A
  call inside a frozen read is isolated only when the whole call carries
  `.value`. `:=` freezes the whole statement, including the reads that
  locate its target.
- **Targets.** NUC 13 already defines the targets a statement-level
  assignment operator accepts, and `:=` takes them unchanged: names, plain
  dotted paths rooted in a name, `$Class`, `this` or `self`, grouping, and the
  128-link bound. Other targets fail when parsed, at the `:=`, with
  `SyntaxError("Invalid value assignment target")`. Rejected: accepting any
  target and failing when the statement runs, as `=` does for `xs[0] = 1`,
  which would evaluate nothing and report a parse-time mistake late.
- **Class-level targets.** A class-level declaration such as
  `$Order.status = "new"` also governs instances created later, so it is a
  law by construction. `:=` on it outside a class-level rule raises
  `TypeError("Cannot use ':=' on a class-level property")`. Inside a
  class-level `if` or block, `$Class` names the instance being processed, so
  `$Class.property := EXPR` is an ordinary action on that instance. To act on
  every current instance once, loop over them:
  `for order of Order: order.status := "shipped"`. Rejected: a frozen class
  rule, which would apply one snapshot to future instances, and a per-instance
  loop hidden behind `$Class.property :=`, which would differ from every
  other use of `$Class`.
- **Instantiation.** `x = Order(qty)` already names the instance after its
  target and records no dependency for the variable. `x := Order(qty)` keeps
  that naming, so `x.id` is `"x"`, and additionally reads the constructor
  arguments without dependency.
- **Bounded literals.** A literal for a deeply nested list is itself a deeply
  nested expression. When the statement files a declaration, a value that
  nests lists 192 levels or more, beyond the runtime's 192-level expression
  limit, raises `TypeError("Maximum expression depth exceeded")` before the
  literal is built, and the statement rolls back. The depth is measured
  without recursion. Where nothing is filed, no literal is built and no limit
  beyond those of `=` applies. In a debug build, the accepted runtime already
  overflows its stack while building a list nested about 2,000 levels, before
  any assignment. Rejected: building the literal unconditionally, which in a
  debug build aborted the process at about 1,500 levels while `x = a`
  succeeded, and changing the accepted `= suppose:` path, which keeps its
  documented behavior.
- **A statement only.** Python's expression-level walrus is out of scope.
  Every expression position keeps its existing diagnostic, which now names
  `':='`, and `parse_expression` keeps ignoring trailing tokens. Rejected:
  an expression form, which would make every declaration that contains it
  partly imperative.
- **`suppose` stays `=`-only.** NUC 65 recognizes a block only where the
  accepted grammar rejected the input, after `=` or alone, and an assigned
  block already stores a one-shot snapshot. `x := suppose` reads the name
  `suppose`, and a following colon stays `SyntaxError("Unexpected ':'")`.
  Premises stay expressions and `=` assignments.
- **Lexing and compatibility.** `:=` is one token by longest match, so `: =`
  stays two tokens and typed declarations, colon assertions, conditional
  expressions, quantifiers, lambdas, slices, object keys and suites keep
  their readings. Scanning the 769 accepted executable cases and 1,710
  dataset records with the accepted lexer finds no `:` directly followed by
  `=`.
- **Header scans.** The native REPL's colon-free `if` and `else` scans and the
  parser's direct-alternative scan treat a top-level `:=` like `;`, because a
  value assignment cannot be part of a condition. `if x := 1` keeps running
  at once with an error, and `else x := 1:` keeps its exact accepted
  diagnostic.
- **Not added.** Compound value assignments such as `:+=`, an
  expression-level walrus, `do:` blocks, value assignment in `suppose`
  premises, and any change to `=`, `.value` or `suppose`.

## Specification

### Syntax

- `:=` is a single lexer token, `Token::ColonAssign`, described as `':='`,
  read by longest match.
- A value assignment is a statement: `target := expression`. It may appear
  wherever a statement may: at the top level, in suites, blocks, class bodies
  and function bodies, and among same-line statements separated by `;`.
- `target` is a name or a plain dotted path rooted in a name, `$Class`,
  `this` or `self`; a class or receiver root needs a property; parentheses may
  group the path. A path holds at most 128 dotted links.
- `expression` is any expression accepted on the right of `=`.
- The statement renders canonically as `target:=expression`, which parses
  back to the same statement.

```
stock = 10
qty = 3
low = stock < 8
stock := stock - qty
assert: stock, 7
assert: low, true
qty = 5
assert: stock, 7
stock := stock - qty
assert: stock, 2
assert: stock@previous, 7
assert: (why stock)[0].rule, "stock = 2"
assert: (why stock)[0].state, "stated"
assert: (affects qty).length, 0
stock
```

- This is the complete `Nucleoid applies a value assignment once` entry,
  without its title and expected-return metadata; it returns `2`.

### Semantics

- Evaluate `expression` once, in the current scope, with the existing
  assignment evaluator. Apply the null and undefined rule of `=`: an
  evaluation that reads a null binding or property, or yields an undefined
  value, gives `null`.
- Record no dependency and no structural subscription. Every read made
  while locating the target and evaluating `expression`, including reads in
  called functions, methods, callbacks and reasoning selections, stops at an
  isolated tracking frame. No enclosing `if`, block, call or declaration
  depends on them.
- Assign the value exactly as `target = literal` would assign it in the same
  place:
  - a local name, such as a parameter, loop variable or a name bound by an
    enclosing block, is assigned locally;
  - any other name is a state variable, and a property path names the
    property of the object it reaches, as with `=`;
  - where `=` files a declaration, as at the top level, the declaration is
    the literal with no dependencies. It replaces any standing relationship
    the target had, its old dependency edges are removed, and its dependents
    propagate;
  - where `=` is only carried out, in a `for` body, a standing `if` branch, a
    block and the functions these run, the assignment is carried out without
    being filed, each time the statement runs.
- `target := Class(arguments)` creates the instance as `=` does, named after
  the target, and evaluates the arguments without dependency.
- The statement's value is the assigned value. A state version is recorded
  when the value changes, as for `=`. `target.value` reads the assigned
  value; `.value` inside `expression` changes nothing.
- `why` explains a variable assigned this way as one step,
  `target = literal`, with state `stated` and an empty `from`. A property
  keeps the rendering every instance property has, `$Class.property =
  literal`, with state `derived` and an empty `from`. `affects` of anything
  the expression read no longer reaches the target.
- Errors raised while locating the target, evaluating the expression,
  assigning, or propagating the change roll back through the existing
  transaction.

### Class-level rules

- Without an instance in scope, a target that resolves to a class-level
  rule, `$Class.property` or `Name.property` where `Name` is a class, raises
  `TypeError("Cannot use ':=' on a class-level property")` when the statement
  runs. An undeclared class raises `ReferenceError("<Class> is not defined")`
  first, as for `=`.
- Inside a class-level `if` or block, `$Class` is the instance being
  processed. `$Class.property := expression` assigns that instance's property
  once each time the rule runs for it, and `$Class` inside the expression
  reads the instance. Elsewhere `$Class` inside the expression reads exactly
  as on the right of `=`.
- A value assignment counts like `=` when a block or conditional decides
  whether it is a class-level rule: mentioning `$Class` anywhere in the
  statement makes the enclosing block or conditional class-level.

### Contexts

- **Top level.** A stated declaration, as above.
- **Functions and methods.** Locals stay local. Other names and properties,
  including `this.property`, are assigned as `=` would assign them. A
  declaration whose evaluation calls the function does not depend on what the
  statement read.
- **Constructors and class bodies.** `this.property := expression` snapshots
  state when the instance is created; `this.price := catalog.price` keeps the
  price an order was created at.
- **`for` bodies, standing `if` branches and blocks.** Carried out each time
  the statement runs, without being filed. A standing `if` repeats it
  whenever its branch runs, and the statement adds nothing to what the `if`
  depends on.
- **`suppose` suites.** A value assignment inside a suite runs in the
  hypothetical world and is discarded with the block.
  `TARGET := suppose ...` is not a block: `x := suppose` assigns the value of
  the name `suppose`, and `x := suppose: 1` raises
  `SyntaxError("Unexpected ':'")`. A premise cannot be a value assignment.
- **Expression positions.** Not accepted; see Errors.

### Bounded literals

- When the statement files a declaration, a value whose literal would nest
  more than 192 expression levels, a list nested 192 levels or more, raises
  `TypeError("Maximum expression depth exceeded")` at the statement, before
  the literal is built, and the statement rolls back.
- A list nested 191 levels is stored and explained normally.
- Where nothing is filed, in a `for` body, a standing `if` branch or a block,
  no literal is built and no limit beyond those of `=` applies.

### Rendering, REPL and terminal

- Graph keys render the statement as `target:=expression`, so `{ x := a }`
  and `{ x = a }` are different blocks. Default-bearing declarations render
  it inside their suites the same way.
- The native REPL runs a `:=` line at once and prints its value. Its
  colon-free `if` and `else` header scans, which the terminal workspace's
  Ctrl-J indentation shares, treat a top-level `:=` like `;`, so `if x := 1`
  is not held as a header. The parser's direct-alternative scan does the same
  for `else x := 1:`. Completion words are unchanged; operators are not
  completion words.

## Errors

- `SyntaxError("Invalid value assignment target")`, at the `:=`, for a target
  that is not a name or plain dotted path rooted in a name, `$Class`, `this` or
  `self`: indexes, slices, calls, a bare `this` or `$Class`, literals, grouped
  expressions other than paths, and assignment expressions such as
  `y = x := 1`, `x += 1 := 2` and `f = lambda:=1`.
- `SyntaxError("Expression has too many parts")`, at the `:=`, for a grouped
  path of more than 128 dotted links. A single postfix chain longer than that
  reaches the parser's existing chain bound first, with the same message at
  its 129th link.
- `TypeError("Cannot use ':=' on a class-level property")`, at the start of
  the statement, for `$Class.property := expression` or
  `Name.property := expression`, where `Name` is a class, without an instance
  in scope.
- `TypeError("State versions are read-only")`, at the start of the statement,
  for a target with a version selector, such as `x@previous := 2`.
- `TypeError("Maximum expression depth exceeded")`, at the start of the
  statement, when a filed declaration would hold a value nested 192 list
  levels or more.
- The target errors of `=`, unchanged:
  `ReferenceError("<path> is not defined")` for a missing object or class,
  `TypeError("Cannot assign '<property>' on <type>")` for a base that is not an
  object, and `TypeError("Cannot use 'value' as a property")`.
- Errors and thrown values from the expression, and from the propagation the
  assignment causes, propagate unchanged and roll back the statement.
- Expression positions keep their existing diagnostics, naming `':='`:
  `Expected ']' but found ':='`, `Expected ')' but found ':='`,
  `Expected ':' but found ':='` and `Unexpected ':='`. A missing value raises
  `SyntaxError("Unexpected end of input")` or
  `SyntaxError("Unexpected end of line")`.
- No other new error type or message is added.

## Reference Implementation

- `src/lang/ast/lexer.rs` adds `Token::ColonAssign` and its `':='`
  description, with a unit test for longest-match neighbours, regular
  expressions, literal text and positions.
- `src/lang/ast/mod.rs` adds `Stmt::ValueAssign { target, value }`. The
  assigned-name, read-root and class-reference walkers treat it like
  `Stmt::Assign`.
- `src/lang/ast/parser.rs` parses a statement-level `:=` after a complete
  expression and validates its target with the NUC 13 path check, which now
  takes the diagnostic as a parameter. The direct-alternative scan stops at a
  top-level `:=`, with a unit test.
- `src/lang/ast/generator.rs` renders `target:=value`.
- `src/lang/ast/literal.rs` adds `snapshot`, which measures a value's list
  depth without recursion before building the literal.
- `src/nuc/mod.rs` adds `Nuc::ValueAssign`. It resolves the target through
  the existing assignment dispatch inside an isolated tracking frame and
  rejects a class-level owner. `src/nuc/value_assign.rs` runs the resulting
  local, variable or property node inside an isolated frame and, when that
  node is filed, replaces its expression with the value's literal through the
  `hold` step that `src/nuc/variable.rs` and `src/nuc/property.rs` add. It
  files the node through `Nuc::graph` with an empty dependency set, so the
  stored declaration has no dependencies and no structural subscriptions by
  construction. `src/nuc/block.rs` treats a `$Class` value-assignment target
  like an assignment's.
- `src/main.rs` treats a top-level `:=` like `;` in the REPL's colon-free
  header scan, with a unit test.
- `tests/value_assignment.rs` covers the appended cases and their assertion
  counts, parsing and rendering, invalid targets and expression positions with
  exact positions, colon readings, stored literals, dependencies and
  structural subscriptions, target paths located without dependency, the
  null-read rule, the executed differences from `= suppose:` and `.value`,
  instantiation, imperative contexts, functions, methods and constructors,
  class-level rules, rollback, bounded literals for variable and property
  targets, `suppose` suites, state versions and the native REPL.
- `tests/common/assertions.rs` walks `Stmt::ValueAssign`. `tests/dataset.rs`
  records the eight new specification records and the eight-record
  `dataset/nucleoid.synth.45.jsonl` split.
- The root specification, executable reference, README, examples, the
  consolidated reference with its error reference and syntax summary, both
  NUC 0 indexes, the new synthesized split and the regenerated normative
  exports are synchronized in the isolated candidate. Every existing exported
  case and test is byte-identical.
- The required Rust improvement pass ran before the freeze and changed no
  behavior. It replaced `ValueAssign::graph_observed`, which only forwarded
  the empty dependency and subscription sets it was given, with
  `ValueAssign::graph`, which files the node through `Nuc::graph` with an
  empty dependency set, and dropped the imports that became unused. It also
  extended the bounded-literal test to property targets: at 191 levels
  `holder.items := a` is stored and explained in one step, and at 192 and 400
  levels it raises `TypeError("Maximum expression depth exceeded")` at line 1,
  column 1 and leaves the old value in place. The documents, data and
  generated exports were unchanged by it.
