# NUC 102 -- Implicit Receiver Properties

```

Title: Implicit Receiver Properties
Author: Can Mingir <canmingir@gmail.com>
Status: Automatic-Accepted
Type: Standards Track
Category: Syntax enhancement
Created: 09-Nov-2026
Requires: 13, 26, 64, 66, 79, 86, 92, 93, 98
```

## Abstract

- In the value of an assignment to a property, a `.` that begins an operand
  and is followed by a property name reads that property of the assigned
  object, its receiver:
  - `$Order.total = .price * .qty` is
    `$Order.total = $Order.price * $Order.qty`.
  - `box.area = .width * .height` is `box.area = box.width * box.height`.
  - `this.area = .w * .h` in a constructor is
    `this.area = this.w * this.h`.
- The receiver is the target without its last property, a plain dotted path
  rooted in a name, `$Class`, `every Class`, `this` or `self`. In
  `order.customer.label = .first`, `.first` reads `order.customer.first`.
- The assignment forms are `=`, `:=`, the compound assignments `+=`, `-=`,
  `*=`, `**=`, `/=` and `%=`, and the logical compound assignments `&&=` and
  `||=`.
- The read continues as member access does, so `.a.b`, `.a[0]`, `.a()` and
  `.a@first` read `RECEIVER.a.b`, `RECEIVER.a[0]`, `RECEIVER.a()` and
  `RECEIVER.a@first`. It works wherever an operand begins in the value:
  operands of operators, `?:` and Python-style conditionals with their
  conditions, list items, object values, subscripts, lambda and function
  bodies and template interpolations. The innermost assignment decides, so
  an assignment nested in the value has its own receiver.
- The parser builds the member expression `RECEIVER.name`, so evaluation,
  dependencies, class-level rules, `why`, `affects`, graph keys, rendering
  and rollback are those of the spelling written out.
- Receivers are read only in one final parse, after every parse of the
  accepted grammar has failed. So only inputs that were errors at the
  accepted revision change, and each such dot raised
  `SyntaxError("Unexpected '.'")`. Every accepted reading stays:
  - An argument that begins with a dot is still a selector of
    [NUC 79](nuc-0079.md), or its accepted error.
  - `is` assignments keep their readings: `$Obj.h is .h * 2` parses as the
    two statements `$Obj.h` and `is.h * 2`.
  - A dot that begins a statement or an assignment target, and a dot after a
    name, as in `x .a`, keep their readings.
  - A variable or destructuring target, a statement start, a top-level
    condition and every other place without a property target keep their
    accepted errors, which accepted tests pin, such as `x = .a`.
- No token, keyword, syntax-tree variant, error type or message, option,
  flag or public item is added. The authoritative contract is
  [Implicit receiver properties](../nucleoid.spec.md#implicit-receiver-properties).
- **Automatic-Accepted** on 10-Nov-2026: the frozen candidate meets every
  hard criterion of the automatic acceptance rule, and the core gate passed
  with every new case using fewer tokens, but the independent evaluator's
  overall policy decision was Rejected. A `while` condition or `suppose`
  premise inside a property value that holds a receiver read and ends in
  `is NAME: NAME` does not build the tree of its written-out spelling:
  `o.f = function() { while 1 + .x is a: b` followed by `return 1 }` builds
  a loop, while `while 1 + o.x is a: b` runs as separate statements and
  raises `ReferenceError("while is not defined")`. Those inputs were syntax
  errors at the accepted revision. See [Evaluation](#evaluation).

## Motivation

- World models state an object's properties in terms of its other
  properties: `$Order.total = $Order.price * $Order.qty`,
  `this.area = this.w * this.h`. The target already names the object, yet
  every read repeats it.
- In the ARC instruction datasets, 40 of the 89 class-level rules read their
  own class, 61 times in all, such as
  `$Obj.height is $Obj.height@first * 3 / 2` and
  `$Obj.x is canvas_width - $Obj.x@first - $Obj.width`.
- Each repetition costs tokens to generate and to read back. `.price` is two
  lexer tokens and `$Order.price` three, and a nested receiver saves more:
  `.first` against `order.customer.first` saves three tokens per read. A
  template literal is one lexer token, so a read inside an interpolation
  shortens the source without changing its lexer-token count.
- A repeated receiver is also a place to mistype. In
  `$Order.total = $Ordr.price * $Order.qty` one copy names another class.
- Prior art: Visual Basic's `With` blocks read `.Name` of the object they
  name, Pascal's `with` statement reads fields of its record, Swift's
  implicit member expressions write `.red` for a member of the type in
  context, and Kotlin's scope functions make the receiver implicit.
- [NUC 79](nuc-0079.md) gave a leading dot a meaning only in argument
  lists and left it an error everywhere else, so an assignment value is free
  to read the receiver with it.

## Rationale

- **Category and mode.** The caller made one tool-backed uniform draw over
  the five categories that NUC 1's registry marks eligible for automatic
  selection and selected Syntax enhancement, index 0, with probability 1/5
  and no redraw. This is a continuous cycle, so token comparison is
  required. Runtime applicability does not apply to this category.
- **Selection.** Within the category the caller chose this bounded
  enhancement from the ARC evidence in [Motivation](#motivation): every
  class-level rule that reads its own class repeats a receiver its target
  already names.
- **Optional evidence.** No hint was supplied. Advisory usefulness is
  unscored, not zero. Strategy learning is `not_configured`, so this
  revision is unattributed, with no policy, selection receipt, trial or
  reward.
- **Only former errors.** Outside argument lists, a `.` where an operand
  begins reaches the operand parser, which raises
  `SyntaxError("Unexpected '.'")` at the name after it.
- **The target names the receiver.** The receiver is the target without its
  last property, so the reader finds it on the same line, left of the
  operator. Targets are plain paths, the paths that compound assignments
  already accept, apart from a bare name, which has no object. Rejected:
  computed targets such as `xs[i].p`, whose receiver would be an arbitrary
  expression copied into every read, evaluated again for each one and
  possibly with effects; compound assignments refuse them for the same
  reason.
- **The innermost assignment.** An assignment nested in a value is the
  nearest target in the source, so it decides: in `o.p = (q.r = .a)` the dot
  reads `q.a`. A nested variable assignment has no receiver, so
  `o.p = (x = .a)` keeps its error rather than reaching past it to `o`. A
  destructuring declaration assigns variables, so its value has no receiver
  either, while a property assignment nested in it has its own:
  `{a} = (q.r = .x)` reads `q.x`.
- **Bodies read lexically.** A lambda or function body in the value reads
  the receiver of the assignment around it, as its source shows. The read
  is the written-out path, so it is evaluated where that path would be,
  with the accepted scoping rules:
  `$Cell.taller = Cell.filter(c -> c.h > .h).length` compares every cell
  with the instance that the rule computes, as `$Cell.h` does there.
- **Exactly the written-out path.** The parser builds `Expr::Member` over a
  copy of the receiver path, the tree that `RECEIVER.name` builds. Rejected:
  a receiver node resolved at run time, which would need a new `Expr`
  variant, a public API change, and new evaluation, dependency and
  rendering code that could drift from member access. Rendering shows the
  expanded path, as a compound assignment renders its lowering, so the two
  spellings are one rule, one graph key and one `why` step.
- **Requires.** The draft named NUC 13, 26, 64 and 66 for the assignment
  forms, NUC 79 for the selector rule and NUC 98 for `every Class`. This
  revision adds NUC 86 and NUC 92, whose parse passes the final parse
  follows and reuses, and NUC 93, whose `is` assignments keep their values.
- **Call arguments keep selectors.** An argument that begins with `.` is
  NUC 79's selector or its accepted error, also inside a property value. So
  `$O.p = f(.a)` keeps passing `v -> v.a`, and one rule decides what a
  leading dot means in an argument wherever the call stands. A dot later in
  the argument begins an operand like any other and reads the receiver.
- **`is` assignments keep their values.** `$Obj.h is .h * 2` parses at the
  accepted revision as the statements `$Obj.h` and `is.h * 2`, so it keeps
  that reading. Reading receivers only in the `is` values that fail at the
  accepted revision, such as `$Obj.d is 2 * .h`, would make a value's
  meaning depend on its first operator. No `is` value reads a receiver.
- **Statement starts and targets.** A line that begins with `.` ends the
  previous statement and raises its accepted error, as NUC 79 kept it. A
  dot that begins an assignment target would be an implicit target, another
  feature, so `.a = 1` and `o.p = (.a = 1)` keep their errors.
- **The lexer's operand position.** A dot reads only after a token in
  operand position, the rule the lexer uses to tell a regular expression
  from a division: not after a name, a class reference, a literal, `)`,
  `]`, `}` or `this`. After those tokens a dot is member access in the
  accepted grammar, so `x .a` stays member access, and contextual names
  stay names: `while .a` reads `while.a`, `affects .a` reads `affects.a`,
  and `(x is .a)` keeps its error, while `(x is not .a)` reads, because
  `not` is a keyword. The rule stays one token rule rather than a list of
  words, and the parser and the trigger of the final parse share it.
- **A final parse after every accepted parse.** The parse passes of NUC 86
  and NUC 92 run first, exactly as at the accepted revision and with no
  receiver reads. Only when all of them fail, and the tokens hold a
  receiver dot or a template, whose interpolations the top-level tokens do
  not show, one final parse reads receivers, with the `is` comparisons and
  comprehensions that the tokens enable. Every input that an accepted pass
  parses, `parse_expression` inputs and template interpolations with
  ignored trailing tokens included, gets that pass's result before the
  final parse can run. So compatibility holds by construction, and no list
  of tentative parts has to be complete. The final parse may therefore read
  receivers in the tentative parts too, and `o.p = .a if .b else .c` reads
  all three.
- **Rejected: reading receivers inside the comprehension retry.** A first
  design of this proposal read receivers in the retry with comprehensions
  itself, and kept them out of the tentative parts. Two refinements kept
  that design compatible: reads only in the retry's last parse, so that a
  plain parse with reads could not return a result where the accepted
  revision returned the `is` parse's, and no reads in the condition of a
  Python-style conditional, a `while` condition, a `suppose` premise or a
  destructuring value, because a read inside a try can turn a failed try
  into a successful one. At the accepted revision
  `parse_expression("o.p = [v for v in xs] if .c else 2")` ignores its
  trailing tokens and returns the tree of `o.p = [v for v in xs]`, so
  reading `.c` there would change an accepted result. That design depended
  on a complete list of tentative parts and refused
  `o.p = .a if .b else .c`; the final parse needs neither.
- **The cost of the final parse.** It adds one parse for inputs that fail
  every accepted pass and hold a receiver dot or a template: at most five
  parses, and at most three when the source holds neither `for` nor a
  template. A program with receiver reads parses two to five times.
  Interpolations are parsed inside each pass with its readings rather than
  retried on their own, so nothing multiplies, and this is not a third
  retry dimension.
- **Errors point past the reads.** When the final parse fails too, the
  input reports whichever of the accepted error and the final parse's error
  lies further into the source, by line and column, the accepted one on a
  tie. Interpolation errors already carry positions in the program, so the
  comparison is between absolute positions. So `o.p = .a +` reports the
  missing operand at its end rather than `Unexpected '.'` at a dot that now
  reads, and every diagnostic that accepted tests pin keeps its message and
  position.
- **Bounds.** Each read copies one plain path of at most 128 links, so the
  expansion is linear in the source. A read and its suffixes form one
  member chain, as `(RECEIVER).name` would, under the accepted chain bound.
  No recursion is added outside the existing nesting guards, and the read
  is a constant check of at most three tokens, with no lookahead past them.
- **Not added.** A `with` block, which would need a new statement and
  indentation for every rule; implicit targets, as in `.total = .qty * 2`;
  reads in `is` values; a spelling flag or option, which the user removed
  from the language; and reads of a variable's value, as in `x = .a`.

## Specification

- The normative contract is
  [Implicit receiver properties](../nucleoid.spec.md#implicit-receiver-properties).

### Receivers

- The value of an assignment `TARGET OP VALUE`, where `OP` is `=`, `:=`,
  `+=`, `-=`, `*=`, `**=`, `/=`, `%=`, `&&=` or `||=`, has a receiver when
  `TARGET` is a plain path whose last link is a property, `RECEIVER.NAME`,
  with at most 128 links, rooted in a name, a class reference, `this` or
  `self`. Grouping parentheses do not count. The receiver is `RECEIVER`.

| Target | Receiver |
| --- | --- |
| `o.p` | `o` |
| `order.customer.label` | `order.customer` |
| `$Order.total`, `every Order.total` | `$Order` |
| `this.area`, `self.area` | `this` |
| `o.a@first.p` | `o.a@first` |
| `x`, `{a, b}`, `a, b` | none |
| `o.p@first`, `$Order` | none |
| `xs[0].p`, `f().p`, `(a + b).p` | none |

- A target of more than 128 links has a receiver that no read may use.

### Receiver reads

- In the value of an assignment with a receiver, a `.` token that begins an
  operand and is directly followed by an identifier or keyword token
  `NAME` reads `RECEIVER.NAME`. A keyword reads its canonical spelling, as
  after any `.`: `.self` reads `RECEIVER.this`, `.elif` reads
  `RECEIVER.else`, and `.None` and `.undefined` read `RECEIVER.null`.
- A dot begins an operand only after a token in operand position, or at the
  start of the input or of an interpolation: not after an identifier, a
  class reference, a number, version index, string, template or regular
  expression literal, `)`, `]`, `}` or `this`.
- The operand continues with every postfix suffix that member access takes:
  members, versions, subscripts, slices and calls.

```
class Order(price, qty):
    this.price = price
    this.qty = qty
$Order.total = .price * .qty
first = Order(4, 5)
second = Order(2, 10)
assert([first.total, second.total], [20, 20])
first.qty = 6
assert([first.total, second.total], [24, 20])
$Order.change = .total - .total@first
second.price = 3
assert([first.change, second.change], [4, 10])
assert((why first.total)[0].rule, "$Order.total = $Order.price*$Order.qty")
```

### Where a dot reads

- A dot reads the receiver of the innermost assignment whose value contains
  it. Through the value, that includes operands of operators, `?:` and
  Python-style conditionals with their conditions, list items, object
  values, object spread sources, subscripts and slice bounds, quantifiers,
  lambda, arrow and function bodies with the `if`, `for` and `while`
  headers and the `suppose` premises of their statements, and template
  interpolations, at any depth.
- An assignment nested in the value, written in parentheses or as a
  statement of a function body, is the innermost assignment for the dots of
  its own value. When it has no receiver, its dots keep their errors, as do
  the dots in the values of variables and destructuring declarations. A
  property assignment nested in one of those values reads its own receiver,
  so `{a} = (q.r = .x)` reads `q.x`.

```
person = {first: "Ada", last: "Lovelace"}
order = {customer: person, qty: 2, price: 5}
order.total = .qty * .price
order.customer.label = .first + " " + .last
assert([order.total, person.label], [10, "Ada Lovelace"])
person.first = "Augusta"
person.last = "King"
order.qty = 3
order.price = 4
[order.total, order.customer.label]
```

- Lambda and function bodies read the receiver lexically, with the
  accepted scoping rules for the written-out path: when a constructor
  holds `this.xs = [1, 2].map(i -> i * .w)`, creating an instance raises
  `ReferenceError("this is not defined")`, as `this.w` does in that lambda.

```
class Cell(h):
    this.h = h
$Cell.taller = Cell.filter(other -> other.h > .h).length
low = Cell(1)
high = Cell(3)
mid = Cell(2)
assert([low.taller, high.taller, mid.taller], [2, 0, 1])
high.h = 0
[low.taller, high.taller, mid.taller]
```

### Kept readings

- These dots keep their accepted readings and errors:
  - the first token of a call argument, a selector when the argument is
    exactly a property path and otherwise its accepted error, and the first
    tokens of the two arguments of an `assert:` statement;
  - every dot in the value of an `is` assignment, including the values of
    assignments nested in it;
  - a dot that begins a statement or the target of an assignment;
  - a dot after a token that is not in operand position, which is member
    access where the accepted grammar reads one, as after the names `while`,
    `why`, `affects`, `stated` and `derived`, so `while .a: x` keeps its
    accepted error and a `while` condition reads after an operator, as in
    `while 0 < .n:`;
  - every dot outside the value of an assignment with a receiver, among
    them the dots in the values of variables, destructuring declarations and
    label arguments such as `P(n = .a)`.
- So these keep their accepted results: `$O.p = f(.a)` passes the selector
  `v -> v.a`; `x .a` and `1 .a` stay member access and `.5` a number; and
  `$Obj.h is .h * 2`, `o.p is .a` and `o.p = x is .a` parse as the
  juxtaposed statements `$Obj.h` and `is.h * 2`, `o.p` and `is.a`, and
  `o.p = x` and `is.a`, whose second statement raises
  `ReferenceError("is is not defined")` at the `is` when it runs.
- The two comparison words differ under the same rule: `is` is a name and
  `not` a keyword. So `o.p = (1 is .a)` keeps its error, while
  `o.p = (1 is not .a)` reads `o.a` and builds the tree of
  `o.p = (1 is not o.a)`, as do `[1 is not .a]` and `f(1 is not .a)`.
  Without grouping, `o.p = 1 is not .a` is the three statements `o.p = 1`,
  `is` and `not .a`, whose dot has no receiver and keeps its error.

### Lowering and rendering

| Source | Builds the tree of |
| --- | --- |
| `$Order.total = .price * .qty` | `$Order.total = $Order.price * $Order.qty` |
| `order.customer.label = .first` | `order.customer.label = order.customer.first` |
| `this.area = .w * .h` | `this.area = this.w * this.h` |
| `o.t += .a` | `o.t += o.a`, which is `o.t = o.t + (o.a)` |
| `o.p ||= .a` | `o.p ||= o.a` |
| `o.p := .a` | `o.p := o.a` |
| `every Obj.d = .h * 2` | `$Obj.d = $Obj.h * 2` |
| `o.p = .a[0] + .b.c()` | `o.p = o.a[0] + o.b.c()` |
| `o.p = (q.r = .a) + .b` | `o.p = (q.r = q.a) + o.b` |
| `o.p = .a if .b else .c` | `o.p = o.a if o.b else o.c` |
| `o.p = (1 is not .a)` | `o.p = (1 is not o.a)` |
| `o.p = new .a(1)` | `o.p = new o.a(1)` |

- Statement rendering, the rules that `why` and `affects` report, `--graph`
  output and graph and block keys are those of the written-out spelling, so
  `why first.total` reports `$Order.total = $Order.price*$Order.qty`.

### Parse passes

- Every input first runs the parse passes of the accepted revision, with no
  receiver reads: the plain parse, the parse with `is` comparisons when its
  tokens hold the name `is` or a template, the parse with comprehensions
  when they hold `for` or a template, and the parse with both. The first
  that succeeds is the result.
- Only when all of them fail, and the tokens hold a receiver dot, a `.`
  directly followed by an identifier or keyword after a token in operand
  position or at the start, or a template, one final parse reads receivers.
  It reads `is` comparisons when the tokens hold `is` or a template and
  comprehensions when they hold `for` or a template.
- An input is parsed at most five times, and at most three times when it
  holds neither `for` nor a template.
- Template interpolations take the parse's readings, receivers included,
  and the receiver of the assignment that contains the template.
- When the final parse fails too, the input reports whichever of the
  accepted error and the final parse's error lies further into the source,
  by line and column, and the accepted error when they are at the same
  place.

### Compatibility

- Only inputs that were errors at the accepted revision change. Every input
  an accepted pass parses keeps its tree, positions, rendering, result,
  errors, JSON, graph and REPL behavior, and every accepted
  `parse_expression` result keeps its tree, because that pass returns it
  before the final parse can run.
- The changed inputs are those that failed every accepted pass and hold a
  receiver dot or a template. They now parse, or report another error
  further into the source.
- **Exports.** Regenerating `dataset/nucleoid.spec.jsonl` inserts this
  proposal's eight records as `spec-0722` to `spec-0729` and renumbers the
  five records of [NUC 98](nuc-0098.md) from `spec-0722`..`spec-0726` to
  `spec-0730`..`spec-0734`, because `tests/universal_claims.rs` keeps NUC
  98's cases last in each document, so this proposal's cases stand before
  them. Their titles, sources, assertions, expected returns and generated
  test names are unchanged. NUC 98's document keeps the identifiers of the
  export at its acceptance.
- **Tests.** The only edits to existing tests are count-only pins that
  follow from the eleven document cases and the eight synthesized records:
  `tests/dataset.rs` moves from 726 to 734 specification records and from
  1,378 to 1,386 synthesized records and pins the new split
  `nucleoid.synth.67.jsonl` at 8; 13 corpus suites move from 1,052 to 1,063
  document cases; and `tests/object_spread_entries.rs` moves from 1,041 to
  1,052 programs without spread entries. No other existing assertion,
  pinned diagnostic or case byte changes, and the full suite confirms that
  nothing else pins a position after the inserted cases.
- **Public API.** No public item is added or removed. `parse`,
  `parse_program` and `parse_expression` return the new trees for the
  changed inputs. No version number is changed.

## Reference Implementation

- **State:** Implemented, Automatic-Accepted; the frozen candidate is
  integrated unchanged, as [Evaluation](#evaluation) records. No token,
  `Expr` or `Stmt` variant, error message, dependency or public item is
  added.
- `src/lang/ast/parser/receiver.rs`, a new private child module of 147
  lines:
  - `Dots`, the mode of a parse, `Accepted` or `Receivers`, and `Receiver`,
    the receiver of the value being parsed: `Absent`, `Path` with the
    receiver path, or `Unreadable` for a target of more than 128 links,
    with no `Default`. `Receiver::of` derives it from a target with the
    existing `PathTarget`.
  - `receiver_dot`, the one token rule of a receiver dot, which
    `mentions_receivers`, the trigger of the final parse, and the reads
    share: a `.` followed by an identifier or keyword, after no token or a
    token for which `Token::precedes_regex` holds.
  - `reads_receiver`, which tells `postfix` that its primary begins with a
    read, looking past leading `new` keywords with `primary_head`;
    `reads_behind` and `receiver_read`, the read, which reports an
    unreadable receiver at its dot through the shared `previous_position`.
  - `with_receiver`, which sets the receiver for one parse and restores the
    outer one whatever that parse returns, behind `receiving`,
    `without_receiver` and `without_reads`; `without_head_read`, which keeps
    a head that starts with `.` without a receiver; and
    `check_target_start`.
- `src/lang/ast/parser.rs` declares the module, gives `Parser` the fields
  `dots` and `receiver`, Accepted and Absent in every new parser and so in
  every `accepted` probe, and splits `attempt`: `attempt_accepted` is the
  accepted pass sequence unchanged, and `attempt` adds the final parse and
  the reported error with the existing `furthest`.
- `parser/expression.rs`: `assignment` checks the target start and parses
  the value through `receiving`. `parser/statement.rs`: `value_assignment`
  parses the value of `:=` through `receiving`, and `expression_statement`
  keeps a statement that starts with `.` without reads.
- `parser/primary.rs` reads at a receiver dot in one match arm, and
  `parser/postfix.rs` starts the chain bound of a read at one link, keeps
  an argument that starts with `.` without reads and makes `member_property`
  visible to the read. `parser/is_assignment.rs` parses `is` values without
  reads, `destructured_value` in `parser/destructuring.rs` parses
  destructuring values without a receiver, so that only assignments nested
  in them read, and `parser/template.rs` passes the mode and the receiver
  to interpolations and shares `previous_position` with the parser.
- `src/lang/ast/lexer/token.rs` makes `Token::precedes_regex` visible to the
  crate; the lexer's behavior is unchanged.
- `tests/implicit_receivers.rs` holds the 19 tests listed in

  adds eight self-contained synthesized records.

### Failed policy check: independent semantic check

- **F1, medium.** A `while` condition or `suppose` premise in a property
  value that holds a receiver read and ends in `is NAME: NAME` does not build
  the tree of its written-out spelling.
  `o.f = function() { while 1 + .x is a: b` followed by `return 1 }` builds
  `While` with the condition `(1 + o.x) is a` and the body `b`, so `o.f()`
  returns `1`. Its written-out spelling `while 1 + o.x is a: b` builds the
  separate statements of [NUC 93](nuc-0093.md), `while`, `1 + o.x`, `is` and
  the declaration `a: b`, on both revisions and raises
  `ReferenceError("while is not defined")`. A `suppose` premise of the same
  shape gives `2` against `ReferenceError("suppose is not defined")`.
- 240 of the evaluator's 1,500 targeted header probes diverge, all `while` or
  `suppose` headers ending in `is NAME: NAME`; `if` and `for` headers agree.
  Every affected input raised `SyntaxError("Unexpected '.'")` at the accepted
  revision, so compatibility is unaffected, but the claim that a read
  behaves exactly as its written-out path does not hold there, and
  `tests/implicit_receivers.rs` does not cover it.
- Cause: in the `is` words pass, `attempt_while_condition` in
  `parser/control.rs` and `attempt_suppose_premise` in
  `parser/statement.rs` decide NUC 93's separation through the `accepted`
  and `separates` probes, whose parsers come from `Parser::new` with reads
  off and no receiver. The probes fail at the dot, so the separation never
  applies to the receiver spelling. Giving the probes the parse's mode and
  receiver is a follow-up revision.

  for both. This follows from the specified rule that every accepted
