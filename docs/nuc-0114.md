## Abstract

- Lists and class instance lists gain the read-only query `product`.
  `RECEIVER.product()` returns the numeric product of the items and
  `RECEIVER.product(selector)` the product of `selector(item)`, multiplied
  left to right from `1`. An empty receiver gives `1`.
- It is the multiplicative sibling of [NUC 68](nuc-0068.md)'s `sum`. Each
  value is converted to a number as `sum` and `*` convert it: `true` counts
  `1`, `null` and `""` count `0`, and `"3"` counts `3`. An undefined value
  makes the product undefined, which a declaration stores as `null`, as it
  makes a sum undefined.
- For a list of numbers, `xs.product()` is exactly
  `xs.reduce((total, x) => total * x, 1)`: the same order and the same
  rounding.
- The selector is called once for every item, in order, with only the item,
  as `sum` calls it. A supplied selector that is not a function raises
  `TypeError("product expects a function")`, as `sum` raises
  `TypeError("sum expects a function")`.
- `product` follows [NUC 61](nuc-0061.md)'s shared query rules, as `sum`
  does. It accepts every receiver the list queries accept, reads the
  receiver before its arguments, never writes it, and stays live in
  declarations and class-level rules like `map` and `reduce`.
- At the accepted revision, these calls raise
  `TypeError("<receiver>.product is not a function")`. No syntax, keyword,
  token, error type or public Rust API is added, and `product` is not a noun
  query, so `product of xs` keeps raising
  `SyntaxError("Unexpected keyword 'of'")`. User methods named `product`,
  such as `calculator.product(2, 3, 4)` in accepted cases, are called on
  instances, which the list queries never reach, so they keep their meaning.
- The authoritative contract is
  [List and population products](../nucleoid.spec.md#list-and-population-products).

## Motivation

- World models multiply as often as they add: the chance that independent
  events all happen, growth compounded over periods, a chain of conversion
  or scaling factors, the number of combinations of independent choices,
  and the volume of a box from its sides. Each is a product over a list or
  over a class's instances, and it has to stay true while the model
  changes.
- The accepted spelling is the accumulator `reduce`:
  `chance = Event.reduce((total, event) => total * event.chance, 1)` is 20
  lexer tokens where `chance = Event.product(event -> event.chance)` is 12,
  and `volume = sides.reduce((total, side) => total * side, 1)` is 18 where
  `volume = sides.product()` is 7. A Python `lambda` accumulator, the
  tightest, saves one token of each, 19 and 17.
- Compounding adds parentheses: `growth = rates.product(rate -> 1 + rate)`
  is 12 tokens where
  `growth = rates.reduce((total, rate) => total * (1 + rate), 1)` is 22. In
  a class-level rule,
  `$Route.chance = Leg.filter(leg -> leg.route == $Route).product(leg -> leg.onTime)`
  is 25 tokens where its accumulator is 33.
- The accumulator restates a running name, `*` and the initial `1` every
  time, and it is easy to get subtly wrong. Without the initial `1`, an
  empty list multiplies to undefined and `[true]` to `true`, and with a
  selector the first item itself becomes the running product, so
  `[{q: 2}].reduce((t, x) => t * x.q)` is the object `{q: 2}`. An initial
  `0` copied from a sum makes the product of any finite numbers `0`.
- Python's `math.prod`, NumPy's `prod`, Rust's `Iterator::product`,
  Haskell's and Scala's `product`, R's `prod` and the spreadsheet function
  `PRODUCT` give the same operation a name.
- [NUC 84](nuc-0084.md) set `product` aside because accepted cases use it as
  a user method name. That method is called on an instance, which the list
  queries never reach, and on a class name `Calculator.product(2, 3)` raises
  `TypeError("Calculator.product is not a function")` at the accepted
  revision, so the name is free for lists and populations.

- **One more aggregate.** `product` joins the arm of `Runtime::list_query`
  that serves `sum`, `average`, `median`, `max`, `min`, `distinct` and
  `mode`, so lists however they are reached and class instance lists accept
  it through the route and the receiver, argument and liveness rules they
  already share. Rejected: a list-only method, which would leave
  `Event.product(...)` raising where `Event.sum(...)` runs.
- **From `1`, left to right.** The result is `1 * v1 * v2 * ... * vn` in
  64-bit floating point, the order and the rounding of the accumulator
  `reduce`, so `[1.1, 2.2, 3.3].product()` is `7.986000000000001`,
  `[1e308, 10].product()` overflows to `Infinity` and `[-1, 0].product()` is
  `-0`, as the accumulator gives. Multiplying the identity by the first
  value changes no bit of it, so a one-number list multiplies to that number.
- Rejected: another order or a compensated product, which no accepted
  spelling reproduces, and a product of logarithms such as
  `Math.exp(xs.sum(x -> Math.log(x)))`, which rounds differently and fails
  for zero and negative factors.
- **The empty product is `1`.** An empty receiver gives the identity, as
  Python's `math.prod`, NumPy's `prod`, Rust's `Iterator::product`,
  Haskell's `product` and R's `prod` give, so a standing product over a
  population that starts empty, or over a filter that matches nothing, has
  a value. Rejected: NaN, the value of `average` for an empty receiver, and
  undefined, either of which would make the product of nothing unknown
  where it is the identity.
- **The conversion of `sum`.** Each value is converted with the numeric
  conversion of `sum`, which is the conversion `*` applies to its operands:
  `null`, `false`, an empty or whitespace-only string and an empty list are
  `0`, `true` is `1`, a numeric string and a one-item list are their number,
  a date is its time in milliseconds, and objects, other strings and longer
  lists are NaN. As an expression the accumulator `reduce` therefore gives
  the same number for every kind of value: `[2, "3", true, null]`
  multiplies to `0` and `[[2], [3]]` to `6` in both spellings.
- Rejected: raising an error for a non-numeric item. Nucleoid's arithmetic
  never raises for the kind of a value, as NUC 68 argued for sums.
- **Undefined stays unknown.** An undefined item or selector result makes
  the product undefined, which a declaration stores as `null`, and every
  item is still visited. That is the rule of `*`, so
  `Part.product(part -> part.works)` waits for every part's chance to be
  defined, as `a * b` waits for both operands. An undefined value wins over
  NaN in either order, as it does in the accumulator.
- **No artificial null read.** `product()` reads items, not bindings, so a
  `null` item counts `0` without settling a declaration to `null`, as in
  `sum`: `p = [2, null].product()` stores `0`. The accumulator reads each
  item through its callback's parameter, so
  `p = [2, null].reduce((t, x) => t * x, 1)` stores `null`; as expressions
  both are `0`. A selector's own reads follow the existing rules.
- **The selector is called like `sum`'s.** It runs once per item, in order,
  with only the item; further parameters stay `null`. Every item is visited
  even after the product has reached `0`, NaN or undefined, so every item's
  reads are dependencies, as in `sum` and `reduce`. Rejected: stopping at
  the first `0`, which would make what a declaration depends on depend on
  its data, and JavaScript's `(item, index, list)` arguments, which no list
  query passes.
- **A supplied selector must be a function.** Any other first argument,
  including `null`, raises `TypeError("product expects a function")` after
  the arguments are evaluated, even on an empty receiver, as `sum` raises
  `TypeError("sum expects a function")`. Rejected: property-name selectors
  such as `Order.product("qty")`, and a number as a start value, as Python's
  `math.prod(xs, start=2)` takes it: `* 2` states it, and `xs.product(2)`
  stays an error rather than a silent product.
- **Extra arguments** are evaluated once, left to right, and ignored, as
  every list query does.
- **Instance lists.** On a class name, `Name.product(...)` is the population
  query even when the class declares an instance method `product`, as
  NUC 68 made `Name.sum(...)`. The method stays reachable through each
  instance: with `class Calculator(base):`, the body `this.base = base`, the
  method `def product(a, b) => this.base + a * b` and `c = Calculator(1)`,
  `c.product(2, 3)` is `7`, while `Calculator.product(2, 3)`, which raised
  `TypeError("Calculator.product is not a function")`, raises
  `TypeError("product expects a function")`, because `2` is not a function.
- **No noun form.** `product` is not added to [NUC 75](nuc-0075.md)'s noun
  queries, so `product of xs` keeps raising
  `SyntaxError("Unexpected keyword 'of'")`. Rejected: a global
  `product(...)`, `Math.product` and `Math.prod`. They would add names
  beside the list query, while `product` is a common name: accepted cases
  bind it as a local variable and a lambda parameter, read it as an instance
  property and call it as an instance method, and all of these keep their
  meaning.
- **Bounded cost.** The receiver and the arguments are evaluated once per
  call and the selector once per item, in one pass that multiplies into one
  64-bit accumulator, so a call is linear in the receiver, as a sum is.
- **Rendered as written.** The call keeps its ordinary rendering:
  `volume = sides.product()` explains as `volume = sides.product()`, a lambda
  selector renders as `function()`, and a `product` call and its
  accumulator, which explains as `volume = sides.reduce(function(),1)`, are
  different statements and graph keys.
- **Where the accumulator spelling differs.** With no selector or a
  function as its selector, a product gives what its accumulator spelling
  gives, bit for bit, except in three places, which the differential under
  [Preparation checks](#preparation-checks) found and no others; a selector
  that is not a function raises the documented error instead:
  - the rendering of the call: `why`, `affects`, `--graph` and graph and
    block keys name `product`, as above;
  - a `null` item in a declaration without a selector counts `0`, where the
    accumulator's callback reads it through a parameter and stores `null`;
  - a named selector is an argument expression, so `p = xs.product(f)`
    depends on `f` even while `xs` is empty, where
    `xs.reduce((t, x) => t * f(x), 1)` reads `f` only inside a callback
    that an empty receiver never calls. `sum` behaves the same way.
- **`sum` stays as it is.** `product` multiplies where `sum` adds. It shares
  one accumulation helper with `sum`, which keeps every result, selector
  call and dependency of `sum` exactly what it is.
- **Pre-existing defects stay.** A callback in a function body cannot read
  the function's parameters, at both revisions: after

- **Requires.** [NUC 61](nuc-0061.md), whose shared list query, population

## Specification

- The normative contract is
  [List and population products](../nucleoid.spec.md#list-and-population-products).

### Calls

- `RECEIVER.product()` and `RECEIVER.product(SELECTOR, ...)` are list
  queries when `RECEIVER` evaluates to a list, however it is reached: a
  variable, a property, an index, a slice, a call result such as
  `filter(...)`, `map(...)`, `slice(...)` or `concat(...)`, a literal, a
  `.value` snapshot or a selected version. The receiver may also be a
  class's instance list, named by the class, by a variable that holds the
  class or by `$Name`, in population order; a range such as `Part[-1:]` and
  `Name.list()` are lists.
- The receiver is read once, before the arguments. Every supplied argument
  is then evaluated once, left to right, and only the first is used.
- A `null` or undefined receiver keeps the accepted method route: the
  arguments are not evaluated and the call is undefined, so a declaration
  holding it stores `null`.
- On a class name the call is the population query even when the class
  declares an instance method `product`; `instance.product(...)` keeps
  calling the method.

### Multiplication

- The result is the product of the receiver's items, or of `selector(item)`
  for every item, converted to numbers and multiplied left to right,
  starting from `1`, in 64-bit floating point. An empty receiver gives `1`.
- For a list of numbers the result is exactly what
  `xs.reduce((total, x) => total * x, 1)` gives, bit for bit, and with a
  selector `f` exactly what `xs.reduce((total, x) => total * f(x), 1)`
  gives.

```
sides = [2, 3, 4]
volume = sides.product()
floor = sides.slice(0, 2).product()
assert([volume, floor], [24, 6])
sides.pop()
sides.push(10)
assert([volume, floor], [60, 6])
sides = []
assert([volume, floor], [1, 1])
account = {rates: [0.1, 0.1]}
growth = account.rates.product(rate -> 1 + rate)
assert(growth, 1.2100000000000002)
account.rates.push(0.1)
assert(growth, 1.3310000000000004)
account.rates.push(-0.5)
assert(growth, 0.6655000000000002)
```

- The rates compound left to right in 64-bit floating point, so three years
  at 10% give `1.3310000000000004`, as the accumulator gives.

### Conversion and special values

- Each value, an item or a selector result, is converted with the numeric
  conversion of `sum`: a number is itself; `null`, `false`, an empty or
  whitespace-only string and an empty list are `0`; `true` is `1`; a numeric
  string, after trimming, is its number; a one-item list is its item's
  number; a date is its time in milliseconds; objects, instances, classes,
  functions, regular expressions, other strings and longer lists are NaN.
- NaN and infinities multiply as 64-bit floating point: a NaN value makes
  the product NaN, `0` times an infinity is NaN, and an overflow gives an
  infinity.
- An undefined value makes the product undefined, which a declaration stores
  as `null`; every item is still visited, and an undefined value wins over
  NaN.
- `product()` reads items, not bindings: a `null` item counts `0` without
  settling a declaration to `null`. Reads inside a selector follow the
  existing rules, so a selector that reads a `null` binding or property
  settles a declaration to `null`, as it would in `map`, `sum` or `reduce`.

| Exact source | Result |
| --- | --- |
| `[2, "3", true, null].product()` | `0` |
| `[2, " 3 ", true].product()` | `6` |
| `[[2], [3]].product()` | `6` |
| `[1.1, 2.2, 3.3].product()` | `7.986000000000001` |
| `[-1, 0].product()` | `-0` |
| `[1e308, 10].product()` | `Infinity` |
| `[2, 0 / 0].product()` | NaN |
| `o = {}`, then `[2, o.missing].product()` | undefined |
| `o = {}`, then `[0 / 0, o.missing].product()` | undefined |
| `p = [2, null].product()`, then `p` | `0`, where `p = [2, null].reduce((t, x) => t * x, 1)` stores `null` |

### Selectors

- A selector is called once for every item, in order, with the item as its
  only argument; further parameters are `null`. The call order and the
  argument are those of `map`, `sum` and `average`.
- A supplied first argument that is not a function, including `null`, raises
  `TypeError("product expects a function")`, even on an empty receiver.
- Every supplied argument, including unused extras, is evaluated once, left
  to right, after the receiver and before the first selector call.

```
class Part(name, works):
    this.name = name
    this.works = works
pump = Part("pump", 0.5)
Part("valve", 0.75)
chance = Part.product(part -> part.works)
newest = Part[-1:].product(part -> part.works)
assert([chance, newest], [0.375, 0.75])
Part("seal", 0.5)
assert([chance, newest], [0.1875, 0.5])
pump.works = 1
assert(chance, 0.375)
class Day(dry): this.dry = dry
staysDry = Day.product(day -> day.dry)
assert(staysDry, 1)
Day(0.5)
Day(0.25)
assert(staysDry, 0.125)
```

- `chance` is the chance that every part works when the parts fail
  independently, and `staysDry` the chance that every day stays dry: an
  empty class gives `1`, and each new instance multiplies in.

### Liveness and class-level rules

- `product` never writes its receiver. A declaration that uses it depends on
  the list or the population, on its argument expressions and on whatever
  the selector reads for every item, as for `sum` and `reduce`.
- Pushing, popping or replacing a list, creating or deleting an instance,
  and changing a property that a selector reads re-evaluate the
  declaration.
- The selector is an argument expression, so a named selector's binding is
  a dependency even while the receiver is empty: after `def f(x) => x * 3`
  and `xs = []`, `why` of `p = xs.product(f)` lists `xs` and `f`, as for
  `p = xs.sum(f)`.
- In a class-level rule, each instance evaluates its own product, and
  `$Class` inside a filter or a selector is the instance the rule is
  evaluated for.

```
class Box(sides): this.sides = sides
$Box.volume = $Box.sides.product()
crate = Box([2, 3, 4])
cube = Box([3, 3, 3])
assert([crate.volume, cube.volume], [24, 27])
crate.sides.push(0.5)
cube.sides = []
assert([crate.volume, cube.volume], [12, 1])
class Route(name): this.name = name
class Leg(route, onTime):
    this.route = route
    this.onTime = onTime
$Route.chance = Leg.filter(leg -> leg.route == $Route).product(leg -> leg.onTime)
north = Route("north")
south = Route("south")
Leg(north, 0.5)
slow = Leg(north, 0.5)
Leg(south, 0.75)
network = Route.product(route -> route.chance)
assert([north.chance, south.chance, network], [0.25, 0.75, 0.1875])
slow.onTime = 1
Leg(south, 0.5)
assert([north.chance, south.chance, network], [0.5, 0.375, 0.1875])
west = Route("west")
assert([west.chance, network], [1, 0.1875])
Leg(west, 0.5)
assert(network, 0.09375)
```

- Every box keeps its own volume, and every route the chance that all of its
  legs are on time; `network`, the product of those chances, follows every
  new leg, changed leg and new route.

### Rendering and graph keys

- Statements, `why`, `affects`, `--graph` output and graph and block keys
  show the call as written, with function arguments rendered as
  `function()`: the rule that `why volume` reports is
  `volume = sides.product()`, and `why` lists the receiver in the
  declaration's `from` list. A `product` call and its accumulator are
  different statements and keys.
- Errors that quote an expression quote the call: `xs.product()(1)` raises
  `TypeError("xs.product() is not a function")` and a quantifier over
  `xs.product()` raises `TypeError("xs.product() is not a collection")`, as
  they do for `sum`; `why xs.product()` keeps raising
  `TypeError("Cannot explain xs.product()")`.

### Transactions

- Selector errors propagate through the existing transaction, so a failed
  standing re-evaluation rolls back the change that triggered it, including
  a list write or a new instance, and a rolled-back transaction restores
  the products of its declarations.

```
def checked(chance):
    if chance > 1:
        throw "NOT_A_CHANCE"
    return chance
chances = [0.5, 0.5]
both = chances.product(checked)
failure = ""
try:
    chances.push(2)
catch error:
    failure = error
```

### Cost

- The receiver and the arguments are evaluated once per call, the selector
  once per item, and each value is converted once and multiplied into one
  64-bit accumulator, so a call is linear in the receiver, as a sum is, and
  a standing product is re-derived once per change of what it reads.
- **Measured** on the final tree, after the improvement pass, with release
  builds of the accepted and the candidate library, rustc 1.97.1, through
  the public API: `Runtime::run` of the statement after its setup, the
  median of 101, 51, 21 or 5 runs as the rows say, and the median of those
  medians over five rounds. A list of 1,000 or 100,000 numbers is placed in
  a property, all `1` but every thousandth `1.0001`; a population holds
  1,000 instances `Item(v)`; the standing rows declare `p` over 101
  instances and then make 10,000 writes `last.v = 1 + k % 5` in a `while`
  loop, each of which re-derives `p`. Every product gives the same number
  as its accumulator spelling.

| Workload | `product` | Accumulator spelling | Runs |
| --- | ---: | ---: | ---: |
| 1,000 numbers, `xs.product()` | 0.010 ms | 0.373 ms | 101 |
| 100,000 numbers, `xs.product()` | 1.31 ms | 37.4 ms | 21 |
| 100,000 numbers, `xs.product(x -> x * 1)` | 26.7 ms | 39.5 ms | 21 |
| 1,000 instances, `Item.product(i -> i.v)` | 0.54 ms | 0.67 ms | 51 |
| A standing product over 101 instances, 10,000 writes | 956 ms | 1,084 ms | 5 |

- A product without a selector multiplies in one loop over the items, about
  13 ns per item, while the accumulator calls its callback for every item.
  With a selector both call a function per item, and `product` still takes
  less time: about a third less over 100,000 items, a fifth less over 1,000
  instances and an eighth less per standing write.
- **Programs without `product` keep their cost.** The same harness ran
  eight programs without it on both libraries, five rounds each,
  alternately. The median of the five round medians differs by at most 3.7
  percent between the libraries, and by 8.7 percent on the 0.01 ms
  `average()` row, each less than the spread of the accepted library's own
  rounds on that row, and every result is the same:

| Program without `product` | Accepted: median, rounds | Candidate: median, rounds |
| --- | ---: | ---: |
| 100,000 numbers, `sum()` | 1.215 ms, 1.167 to 1.233 | 1.208 ms, 1.159 to 1.360 |
| 100,000 numbers, accumulator `reduce` | 37.22 ms, 36.48 to 37.72 | 37.33 ms, 37.01 to 38.08 |

| 1,000 instances, accumulator `reduce` | 0.666 ms, 0.645 to 0.685 | 0.690 ms, 0.628 to 0.708 |
