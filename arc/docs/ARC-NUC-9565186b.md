## Puzzle

Each training input is a 3 by 3 canvas filled by a mosaic of two to four
colors, with no background cell of color 0. The output keeps the canvas and
the cells of the color with the most cells, and turns every other cell color
5, which no training input holds. The kept color has 5, 4, 7, and 3 of the 9
cells in the four training pairs: always the most, but more than half only in
the first and third. The count decides, not the color: 8 appears in every
training pair and never stays, and the smallest color value stays only in the
second and third. The output keeps the input's 3 by 3 canvas, so the dataset
is `EXACT`; with no zero cell to crop, `FIT` would frame the same grids.

`/arc-purposal` chose this puzzle by default: among the 384 training puzzles
other than the genesis puzzle `3aa6fb7a` and those with a dataset, its largest
training matrix has the fewest cells, 9, with 72 cells in all its training
matrices. Two other puzzles, `a85d4709` and `ed36ccf7`, tie on both measures,
and `9565186b` has the lowest ID among them. It also tied with
[`74dd1130`](ARC-NUC-74dd1130.md), which the previous invocation took.

## Gestalt overview

- **Whole grid.** A 3 by 3 canvas filled by a mosaic of two to four colors,
  with no background cell.
- **Figures.** The mosaic first, then its color regions: all the cells of one
  color form one group, whether or not they touch.
- **Relations.** The regions compete by size. One region has more cells than
  any other: 5, 4, 7, and 3 of the 9 in the four training pairs.
- **Change.** The largest region keeps its color, and every other region
  turns gray, color 5.
- **World model.** One object per color region, one level below the whole
  mosaic. The mosaic does not change as one: each cell keeps or loses its
  color by its region, which no scalar property of a single mosaic object
  states. The regions are still whole figures, and no cell is modeled on its
  own.

## Dataset

The dataset holds the four original training pairs in source order, followed
at the same level by the puzzle's test pair, which the same rule annotates.
Each object is one color region, all the cells of one color whether or not
they touch, as in `dataset.d631b094.json`: an instance of
`Obj(x, y, orientation, color, cell_count)`, tagged `l9100`, a single shape.
`color` and `cell_count`, the region's number of cells, are scalars, as in
`dataset.9af7a82c.json`. The class has no parts list, histogram, rank, output
color, canvas size, or matrix of cells, so no input property names the kept
color. One conditional class-level rule turns gray every region that another
region of its pair outnumbers:

```nuc
if any other in Obj: other.cell_count > $Obj.cell_count:
    $Obj.color = 5
```

The quantifier `any` ranges over the pair's whole population, and
`$Obj.cell_count` reads the region the rule is evaluated for. The region with
the most cells has no larger region and keeps its color; a tie for the most,
which no training pair has, would keep every tied region's color. The
condition reads no color, so the rule rewrites `color` without an `@first`
anchor, as `dataset.017c7c7b.json` recolors its objects. The rule creates no
property and leaves `x`, `y`, `orientation`, and the tag unchanged, so a gray
region's output state differs from its input state only in `color`; 9 of the
13 training regions turn gray. The declarations carry no `#` comments. The
[README](../README.md#instruction-datasets) describes the dataset in full.

The worker started from the big picture, each grid as one whole mosaic, as in
`dataset.3c9b0459.json` and `dataset.74dd1130.json`. That fell short: the
mosaic does not change as one, since each cell keeps or loses its color by the
color region it belongs to, which no scalar property of a single mosaic object
can state. Only a parts list could, as in `dataset.5582e5ca.json`, and the
user approved that list for that puzzle alone. The model therefore went one
level down, to the color regions the mosaic is made of, which are still whole
figures, and models no cell on its own.

The training pairs also fit edge-connected pieces with the largest piece
kept, because the only split color, the fourth pair's two color-8 corner
cells, turns gray either way. The worker counted each color as one region, the
unit in which every output changes. `Obj.some(...)`,
`$Obj.cell_count < max of Obj.map(...)`, and a conditional expression with
`@first` ran identically, and the worker chose `any` because it states the
relation once, with no derived property or anchor. The training pairs rule
out a more-than-half threshold, the color's value, and the top-left cell's
color. The worker fixed the rule from the training pairs before it read the
test pair and reported that the same rule reproduces it.

The caller checked the handoff against the declarative, higher-order, and
gestalt requirements and the user's ARC conventions, found that it met them,
and sent nothing back. It replayed the four training pairs on the accepted
runtime, and all 259 checks passed. They covered:

- grids and keys;
- the keep-the-most-frequent-color rule;
- one single-color mask per color;
- mask shapes and cells, bounding boxes, and merges;
- implementations and orientations;
- input and output snapshots.

The rule depends on the whole population, so the caller also ran each
training pair with its instances in every order, the rule declared before
and after them. All 112 programs gave every region its snapshot's color.

The worker wrote the dataset, its README paragraph, and the puzzle's entry in
the **ARC puzzle report** workflow's list, its 17th puzzle. The caller made
the puzzle the solver's default in `src/app.ts`, in place of `74dd1130`,
before the run.

### Standard entries

On 5-Nov-2026, at the user's request, every ARC dataset moved to the standard
object entries `x`, `y`, `width`, `height`, and `orientation`. `width` and
`height` are the column and row counts of the object's input bounding box. An
orientation change alone leaves them unchanged, and a rule changes them only
when the shape itself changes size, reading the input with `@first`. Every
implementation now passes the input box's `width` and `height` after `y`, and
the class and rules read:

```nuc
class Obj(x: int, y: int, width: int, height: int, orientation: int, color: int, cell_count: int):
if any other in Obj: other.cell_count > $Obj.cell_count:
    $Obj.color = 5
```

No rule changed: recoloring keeps each region's size, and `cell_count` stays
because it counts cells, not the box. The migration worker regenerated every
snapshot with the accepted runtime at `491512d`, and the caller replayed every
pair offline against the unchanged grids, masks, positions and instance names.
No solver run has measured this version yet.

### Orientation convention

On 6-Nov-2026 the user asked `/arc-purposal` to make `orientation` consistent
across all 29 instruction datasets, with a reference of eight directed 3-cell
lines, each of which points toward its head. Every state now takes the
direction its own shape points, by the convention in the
[README](../README.md#3-extract-instances): a line toward its head or along
its axis, a corner or chevron toward its vertex, and anything else 0, while a
turn adds its angle. Every dataset's first declaration also carries one shared
comment line, directly above its class, that states the convention for the
model:

```nuc
# Orientation is the direction an object points, in degrees clockwise from north (0 up, 90 right, 180 down, 270 left)
```

Seven of the sixteen regions changed: the first training pair's color-2 and
color-8 regions are corners that point toward the top-left and bottom-right
vertices of their boxes, 315 and 135, and five horizontal rows of two or three
cells are lines without a head, 90. The vertical lines, single cells, T and C
shapes, and split regions stay 0. A region keeps its cells when it turns gray,
so each output keeps its input orientation, and no rule changed.

The grids, masks, positions, instance names, tags, and every other property
are as before; only the orientation values changed, so the world model keeps
its level.

The arc-dataset worker made the change in an external staging directory with
the accepted runtime at `d3413e6` (last runtime change `7096171`), and every
snapshot reruns byte for byte on it. The caller's own offline check passed on
the staged file and again after integration: the pairs, grids, masks,
positions, and instance names are as before, every state's orientation matches
the convention's labeller, every snapshot replays on that runtime, and
`document()` loads the dataset with the other 28. No NUC was requested, so no
proposal strategy was selected and strategy learning did not apply. At the
user's choice, no solver run has measured this version.

### Letter colors

On 8-Nov-2026, at the user's request, every instruction dataset started
writing its colors as letters instead of numbers. `0` stays `0`, and every
other color is a letter of `ABCDEFGHI`, ranked by how often it occurs across
all of the dataset's input and output matrices, training and test pairs
together: `A` for the most used, then `B`, and so on, a tie going to the color
read first, as `Matrix.silhouette` ranks one matrix. This dataset writes its
colors as letters ranked by count: 2 as `A`, 5 as `B`, 1 as `C`, 3 as `D`, 8
as `E`, and 4 as `F`. Mapping the letters back reproduces the puzzle's pairs
cell for cell.

The pair grids, both instance masks, the implementations, and the snapshots
use those letters, and the class and rules name the same colors by letter.
Only the color literals changed, and the changed declarations now read:

```nuc
class Obj(x: int, y: int, width: int, height: int, orientation: int, color: str, cell_count: int):
if any other in Obj: other.cell_count > $Obj.cell_count:
    $Obj.color = 'B'
```

Every snapshot was regenerated with the accepted runtime at `adc282a` and
equals its earlier snapshot with its colors replaced by their letters, so the
rules behave as before; instance names, positions, sizes, orientations, and
tags are unchanged. `Matrix.silhouette` now also takes letters, so the
orientation call's few-shot crops read exactly as before. No solver run has
measured this version, so its difference is unknown, not zero.

### Is assignments

On 8-Nov-2026 the user asked to apply [NUC 93](../../docs/nuc-0093.md) and
[NUC 86](../../docs/nuc-0086.md) to every dataset in `src/dataset`. Every
assignment in the declarations and implementations now uses `is`, the opt-in
assignment of NUC 93, and a quoted word that was a whole value, or the whole
right operand of an `is` comparison, lost its quotes:

```nuc
class Obj(x: int, y: int, width: int, height: int, orientation: int, color: str, cell_count: int):
    this.x is x
    this.y is y
    this.width is width
    this.height is height
    this.orientation is orientation
    this.tag is l9100
    this.color is color
    this.cell_count is cell_count

if any other in Obj: other.cell_count > $Obj.cell_count:
    $Obj.color is B
```

`target is value` builds exactly the syntax tree of `target = value`. A bare
word reads the name of its spelling when one exists and otherwise stores its
own text: in the constructor, `this.x is x` reads the parameter `x`, and no
program of this dataset defines any of `l9100` and `B`, so those words read as
their own text. Implementations construct their instances with `is` as well,
as in
`objfd8da1fb82d2 is Obj(x=0, y=0, width=3, height=3, orientation=315, color='A', cell_count=5)`,
and keep their quoted keyword arguments, which are not assignments. Only the
spelling changed: the class, the rules' structure, the grids, masks,
positions, instance names, and snapshots are as before, and the world model
keeps its level, so the gestalt overview above still holds.

The rules now need a runtime at `ad45ba4`, the NUC 93 commit, or later, run
with `--is-assignment`, which `src/lib/nucleoid.ts` now passes to every
program; without the flag, `objfd8da1fb82d2 is Obj(...)` reads as three
juxtaposed statements and raises `ReferenceError`. Offline, with the accepted
runtime at `4ac649b` (last runtime change `ad45ba4`), the flag reproduced all
16 input and 16 output snapshots of the 5 pairs, both in a direct replay and
through the solver's own `nucleoid.run`, and the previous version reproduced
them with and without the flag. No NUC was requested, so no proposal strategy
was selected and strategy learning did not apply. No solver run has used this
version.
