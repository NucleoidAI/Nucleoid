## Puzzle

Each training input is a 3 by 3 canvas holding one five-cell pattern of a
single color, and each output is a single 1 by 1 cell. The output's color is a
code for the pattern's shape. Neither the pattern's color nor its cell count
decides it: color 5 gives 1, 2, and 6, color 8 gives 2 and 3, and every
pattern has five cells. The seven training patterns show four shapes, with
outputs 1, 2, 2, 3, 3, 1, and 6. The output shrinks from 3 by 3 to 1 by 1, so
the dataset is `FIT`.

## Gestalt overview

- **Whole grid.** A 3 by 3 canvas holds one five-cell pattern of a single
  color; the output is one cell.
- **Figures.** One figure per grid, the whole pattern, seen as one of four
  shapes: a hollow diamond with a filled corner, a diagonal cross, a square
  with a diagonal tail, and an orthogonal cross.
- **Relations.** Only the shape matters. The same shape gives the same
  output in different colors, and every pattern has five cells.
- **Change.** The whole pattern collapses into one cell whose color codes
  its shape: 1 for the diamond, 2 for the diagonal cross, 3 for the square
  with a tail, and 6 for the orthogonal cross.
- **World model.** One object per pair, the whole block, whose kind names its
  shape whatever its turn, while its orientation carries the turn. A block
  whose kind the code table lacks has no code, so the world model stops with
  that kind as its error instead of leaving the cell without a color.
  Version 2's one object per cell was the pixel-level start that version 3
  replaced.

## Dataset

The dataset holds the seven original training pairs in source order, followed
at the same level by the puzzle's three test pairs, which the same rules
annotate. Each pair has one instance of `Obj(x, y, width, height,
orientation, volume, kind)`, the whole five-cell block, and `kind` names the
block's shape. The class has no color, canvas size, or list or matrix of
cells. Its class-level rules turn every block into the output cell and stop
on a block whose kind has no code:

```nuc
class Obj(x: int, y: int, width: int, height: int, orientation: int, volume: int, kind: str = 'l9100'):
    this.x is x
    this.y is y
    this.width is width
    this.height is height
    this.orientation is orientation
    this.volume is volume
    this.kind is kind

$Obj.kind is l7544

$Obj.width is 1

$Obj.height is 1

$Obj.fill_color is {l4262: 1, l2404: 2, l3743: 3, l1707: 6}[$Obj.kind@first]

if $Obj.fill_color is null:
    throw $Obj.kind@first

$Obj.volume is $Obj.width * $Obj.height
```

The four training shapes are the kinds `l4262` for the hollow diamond with a
filled corner, `l2404` for the diagonal cross, `l3743` for the square with a
diagonal tail, and `l1707` for the orthogonal cross, and every implementation
names its block's kind, as in
`obj3fc7d6382a47 is Obj(x=0, y=0, width=3, height=3, orientation=0, volume=5, kind=l4262)`.
The output cell is a single point, `l7544`, 1 by 1 with one cell, and its
color is the code that the block's input kind selects; the `@first` anchor
reads that kind after the first rule replaces it. A kind that the table lacks,
such as the default `l9100`, reads `null` there, and the class-level `if`
throws it, so the run stops with that kind as its error. Every block's box
spans the canvas, so `x` and `y` stay at the origin. `fill_color` is absent
from the input states. The datasets carry no `#` comments since the user
removed them on 24-Nov-2026. The [README](../README.md#instruction-datasets)
describes the dataset in full, including why no measure of the shape yields
the code.

Version 3 starts from the big picture, as the gestalt requirement that
`/arc-purposal` and the arc-dataset profile added on 4-Nov-2026 asks: each
training input shows one figure, the whole block, so the block is the object
and its shape is its tag. Version 2 had started from single cells, one object
per cell, without showing that a whole-block formulation falls short.
Version 4 keeps version 3's whole block.

The caller sent version 1 back for two reasons. Its lookup table put the
training patterns into the rule, which the arc-dataset profile forbids as
hard-coded grids, and it said only what the training inputs show, short of the
requirement to say the most with the least. Its `points` list gave the object
a list of its cells, which the user's standing standard allows only where a
hint asks for one, as for `dataset.44f52bb0.json`. The review named no feature
to use instead.

For version 2 the worker surveyed features on the training pairs alone. Color,
cell count, and the other features it tried do not separate the outputs; four
single derived properties do:

| Property | Training values | Decision |
| --- | --- | --- |
| Isolated cells | 2, 5, 5, 1, 1, 2, 0 | Chosen: the narrowest relation between cells, one yes-or-no property per cell, and one population count |
| Pairs of cells touching through an edge or a corner | 12, 8, 8, 14, 14, 12, 16 | A wider relation, counted twice per pair |
| Cells on a canvas corner | 1, 4, 4, 2, 2, 1, 0 | Places cells against the canvas rather than relating them, and holds only while the pattern spans the canvas |
| Edge-connected pieces | 3, 5, 5, 2, 2, 3, 1 | Needs the transitive closure of adjacency; a recursive label rule raises `TypeError: Circular Dependency` |

The worker froze version 2's rules before running them on any test pair, and
the same rules reproduce every train and test pair. No enhancement was
needed, because the isolated-cell rule already explains every training pair.
Every point was tagged `l7544` in both states, and unconditional class-level
rules decided which cells are isolated, counted them over the pattern, and
collapsed every cell into the output cell:

```nuc
$Obj.isolated = not any other in Obj: (other.x@first - $Obj.x@first) ** 2 + (other.y@first - $Obj.y@first) ** 2 == 1
$Obj.fill_color = {0: 6, 1: 3, 2: 1, 5: 2}[Obj.count(.isolated)]
$Obj.x = 0
$Obj.y = 0
```

A cell was isolated when no other cell of its pattern shared one of its edges,
a squared distance of 1, so the mapping gave 6 for none, 3 for one, 1 for two,
and 2 for five isolated cells.

`88c781d` replaced version 2 with version 3 on 4-Nov-2026, after version 2's
run and 15 minutes after the gestalt requirement was added. Version 3 keeps
version 1's single object per pair, the whole block, without its `points`
list or its table of point lists.

### Is assignments

On 8-Nov-2026 the user asked to apply [NUC 93](../../docs/nuc-0093.md) and
[NUC 86](../../docs/nuc-0086.md) to every dataset in `src/dataset`. Every
assignment in the declarations and implementations now uses `is`, the opt-in
assignment of NUC 93, and a quoted word that was a whole value, or the whole
right operand of an `is` comparison, lost its quotes:

```nuc
class Obj(x: int, y: int, width: int, height: int, orientation: int, tag: str):
    this.x is x
    this.y is y
    this.width is width
    this.height is height
    this.orientation is orientation
    this.tag is tag

$Obj.tag is l7544

$Obj.width is 1

$Obj.height is 1

$Obj.fill_color is {'l4262': 'C', 'l2404': 'D', 'l3743': 'G', 'l1707': 'H'}[$Obj.tag@first]
```

`target is value` builds exactly the syntax tree of `target = value`. A bare
word reads the name of its spelling when one exists and otherwise stores its
own text: in the constructor, `this.x is x` reads the parameter `x`, and no
program of this dataset defines `l7544`, so that word reads as its own text. A
string inside a larger value keeps its quotes, as in
`$Obj.fill_color is {'l4262': 'C', 'l2404': 'D', 'l3743': 'G', 'l1707': 'H'}[$Obj.tag@first]`,
because a word must be the whole value. Implementations construct their
instances with `is` as well, as in
`obj3fc7d6382a47 is Obj(x=0, y=0, width=3, height=3, orientation=0, tag='l4262')`,
and keep their quoted keyword arguments, which are not assignments. Only the
spelling changed: the class, the rules' structure, the grids, masks,
positions, instance names, and snapshots are as before, and the world model
keeps its level, so the gestalt overview above still holds.

The rules now need a runtime at `ad45ba4`, the NUC 93 commit, or later, run
with `--is-assignment`, which `src/lib/nucleoid.ts` now passes to every
program; without the flag, `obj3fc7d6382a47 is Obj(...)` reads as three
juxtaposed statements and raises `ReferenceError`. Offline, with the accepted
runtime at `4ac649b` (last runtime change `ad45ba4`), the flag reproduced all
10 input and 10 output snapshots of the 10 pairs, both in a direct replay and
through the solver's own `nucleoid.run`, and the previous version reproduced
them with and without the flag. No NUC was requested, so no proposal strategy
was selected and strategy learning did not apply. No solver run has used this
version.

### Visible kinds

On 26-Nov-2026 the user ran `/arc-purposal 27a28665` after
`/arc-debug 27a28665` had examined the 25-Nov-2026 run. The hint asked to make
`kind` survive the implementation step, or fail visibly when it is not in the
table, using training evidence only, and to decide which kind turned shapes
get. The solver's implementation step has the model write each object's
implementation from a query that names only `input_x`, `input_y`,
`input_width`, `input_height`, `orientation`, and `input_volume`
(`src/object.ts`). The class default `l9100` is not a key of the code table,
so an implementation that left out `kind` silently gave the output point no
color.

The dataset cannot make the model write the kind, so version 4 takes the
hint's second half. The arc-dataset worker probed the accepted runtime at
`56f40dfe`:

- a missing constructor argument binds `null`, so dropping the default would
  fail nothing;
- an absent key, such as the default's or an invented kind's, reads `null`;
- `kind in {...}` raises `TypeError` for every kind, valid ones included;
- a failed `assert` stops a program but cannot single out the object.

A class-level `if` with a `throw` does what the hint asks. It is the
validation rule the specification writes as
`if $Item.sku == 'A': throw 'INVALID_SKU'`. It never fires on the four
training kinds, in either declaration order, and gives a turned `l4262` its
code. It stops the program with status 1 and `l9100 (line 27, column 1)` for
the default, or `l5555 (line 27, column 1)` for an invented kind. A training,
synthesized, or test object whose kind is not in the table therefore ends the
run with that kind as its error, instead of producing a state without a code
and leaving the cell's color to the composition step. The cost is that a
turned synthesized block whose kind the model invents ends the run too.

A turned block keeps its kind, and its orientation carries the turn. A turned
hollow diamond stays `l4262` at 90 and a turned square with a tail stays
`l3743` at 90, while the two crosses, which look the same after a quarter
turn, keep `l2404` and `l1707` at 0. The training pairs show that the code
follows the shape and not its color: three shapes appear in two colors with
the same code. Other datasets keep a kind across turns, as the trominoes of
`dataset.25ff71a9.json` keep `l9100` and the genesis corners keep `l6747` at
every orientation. No training block is turned, so whether a turn changes a
code stays open, and the table holds one code per shape.

The table's keys are now names, `{l4262: 1, ...}`, which an object literal
reads as the same keys. The implementations pass bare kinds, `kind=l4262`,
which read as their own text, as the item words of NUC 95 do. Both give the
same states as their quoted spellings. Only the class default keeps its
quotes, because the bare `kind: str = l9100` raises
`SyntaxError: Expected a scalar literal parameter default`.

The worker regenerated every snapshot with the accepted runtime at
`56f40dfe`. The caller replayed all 10 input and 10 output snapshots offline
on the runtime rebuilt at `d536eec8`. The grids, masks, positions, and
instance names are those of version 3; only the key order of the snapshots
changed, with `kind` now before `orientation`, as the runtime prints it.

The [dataset grammar](../arc.ebnf) gained the forms the dataset uses: a
`throw` in an `if` body, `null`, and a bare word as an argument value, with
`null` and `throw` among its reserved words. It lost three forms:

- the `#` comment line before every declaration and implementation, which no
  dataset has used since 24-Nov-2026;
- quoted object keys, which only this dataset used;
- quoted argument values, which only this dataset used.

No NUC was requested for the dataset, so no proposal strategy was selected.
