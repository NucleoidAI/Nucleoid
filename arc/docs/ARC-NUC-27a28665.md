## Puzzle

Each training input is a 3 by 3 canvas holding one five-cell pattern of a
single color, and each output is a single 1 by 1 cell. The output's color is a
code for the pattern's shape. Neither the pattern's color nor its cell count
decides it: color 5 gives 1, 2, and 6, color 8 gives 2 and 3, and every
pattern has five cells. The seven training patterns show four shapes, with
outputs 1, 2, 2, 3, 3, 1, and 6. The output shrinks from 3 by 3 to 1 by 1, so
the dataset is `FIT`.

## Gestalt overview

- **Whole grid.** A 3 by 3 canvas holds one five-cell pattern of a single
  color; the output is one cell.
- **Figures.** One figure per grid, the whole pattern, seen as one of four
  shapes: a hollow diamond with a filled corner, a diagonal cross, a square
  with a diagonal tail, and an orthogonal cross.
- **Relations.** Only the shape matters. The same shape gives the same
  output in different colors, and every pattern has five cells.
- **Change.** The whole pattern collapses into one cell whose color codes
  its shape: 1 for the diamond, 2 for the diagonal cross, 3 for the square
  with a tail, and 6 for the orthogonal cross.
- **World model.** One object per pair, the whole block, whose tag names its
  shape. Version 2's one object per cell was the pixel-level start that
  version 3 replaced.

## Dataset

The dataset holds the seven original training pairs in source order, followed
at the same level by the puzzle's three test pairs, which the same rules
annotate. Each pair has one instance of `Obj(x, y, orientation, tag)`, the
whole five-cell block, and `tag` names the block's shape. The class has no
color, count, canvas size, or list or matrix of cells. Two unconditional
class-level rules turn every block into the output cell:

```nuc
$Obj.tag = 'l7544'
$Obj.fill_color = {'l4262': 1, 'l2404': 2, 'l3743': 3, 'l1707': 6}[$Obj.tag@first]
```

The four training shapes are tagged `l4262` for the hollow diamond with a
filled corner, `l2404` for the diagonal cross, `l3743` for the square with a
diagonal tail, and `l1707` for the orthogonal cross. The output cell is a
single point, `l7544`, and its color is the code that the block's input tag
selects; the `@first` anchor reads that tag after the first rule replaces it.
Every block's box spans the canvas, so `x` and `y` stay at the origin.
`fill_color` is absent from the input states. The declarations carry `#`
comments, as the other datasets do. The
[README](../README.md#instruction-datasets) describes the dataset in full,
including why no measure of the shape yields the code.

Version 3 starts from the big picture, as the gestalt requirement that
`/arc-purposal` and the arc-dataset profile added on 4-Nov-2026 asks: each
training input shows one figure, the whole block, so the block is the object
and its shape is its tag. Version 2 had started from single cells, one object
per cell, without showing that a whole-block formulation falls short.

### Versions

| Version | Instances | Rules | Outcome |
| --- | --- | --- | --- |
| 1 | One whole pattern per pair, with a `points` list of its cells: 10 | `fill_color` looked up in a literal table of the four training patterns' point lists | Sent back by the caller before any run |
| 2 | One point per nonzero input cell: 50 | The four rules below | Run once, exit 0 |
| 3 | One whole block per pair, tagged by its shape: 10 | The two rules above | Committed in `88c781d`; not run |

The caller sent version 1 back for two reasons. Its lookup table put the
training patterns into the rule, which the arc-dataset profile forbids as
hard-coded grids, and it said only what the training inputs show, short of the
requirement to say the most with the least. Its `points` list gave the object
a list of its cells, which the user's standing standard allows only where a
hint asks for one, as for `dataset.44f52bb0.json`. The review named no feature
to use instead.

For version 2 the worker surveyed features on the training pairs alone. Color,
cell count, and the other features it tried do not separate the outputs; four
single derived properties do:

| Property | Training values | Decision |
| --- | --- | --- |
| Isolated cells | 2, 5, 5, 1, 1, 2, 0 | Chosen: the narrowest relation between cells, one yes-or-no property per cell, and one population count |
| Pairs of cells touching through an edge or a corner | 12, 8, 8, 14, 14, 12, 16 | A wider relation, counted twice per pair |
| Cells on a canvas corner | 1, 4, 4, 2, 2, 1, 0 | Places cells against the canvas rather than relating them, and holds only while the pattern spans the canvas |
| Edge-connected pieces | 3, 5, 5, 2, 2, 3, 1 | Needs the transitive closure of adjacency; a recursive label rule raises `TypeError: Circular Dependency` |

The worker froze version 2's rules before running them on any test pair, and
the same rules reproduce every train and test pair. No enhancement was
needed, because the isolated-cell rule already explains every training pair.
Every point was tagged `l7544` in both states, and unconditional class-level
rules decided which cells are isolated, counted them over the pattern, and
collapsed every cell into the output cell:

```nuc
$Obj.isolated = not any other in Obj: (other.x@first - $Obj.x@first) ** 2 + (other.y@first - $Obj.y@first) ** 2 == 1
$Obj.fill_color = {0: 6, 1: 3, 2: 1, 5: 2}[Obj.count(.isolated)]
$Obj.x = 0
$Obj.y = 0
```

A cell was isolated when no other cell of its pattern shared one of its edges,
a squared distance of 1, so the mapping gave 6 for none, 3 for one, 1 for two,
and 2 for five isolated cells.

`88c781d` replaced version 2 with version 3 on 4-Nov-2026, after version 2's
run and 15 minutes after the gestalt requirement was added. Version 3 keeps
version 1's single object per pair, the whole block, without its `points`
list or its table of point lists.

### Standard entries

On 5-Nov-2026, at the user's request, every ARC dataset moved to the standard
object entries `x`, `y`, `width`, `height`, and `orientation`. `width` and
`height` are the column and row counts of the object's input bounding box. An
orientation change alone leaves them unchanged, and a rule changes them only
when the shape itself changes size, reading the input with `@first`. Every
implementation now passes the input box's `width` and `height` after `y`, and
the class and rules read:

```nuc
class Obj(x: int, y: int, width: int, height: int, orientation: int, tag: str):
$Obj.tag = 'l7544'
$Obj.width = 1
$Obj.height = 1
$Obj.fill_color = {'l4262': 1, 'l2404': 2, 'l3743': 3, 'l1707': 6}[$Obj.tag@first]
```

Two rules, `$Obj.width = 1` and `$Obj.height = 1`, give the single output cell
its size. The migration worker regenerated every snapshot with the accepted
runtime at `491512d`, and the caller replayed every pair offline against the
unchanged grids, masks, positions and instance names. No solver run has
measured this version yet.

## Open items

- **The run saw the answer.** Resolved on 6-Nov-2026: the user decided this is
  intended, because the datasets are being prepared as few-shot examples and
  runs at this stage are not yet held-out tests. The ARC instructions now say
  so, and the suggested change to keep the running puzzle's test pairs out of
  `document(puzzle_id)` is withdrawn. `src/lib/llm.ts` sends
  `document(puzzle_id)` as few-shot context, and `src/dataset/dataset.ts`
  discards `puzzle_id`. The prompts therefore held this dataset's three
  annotated test pairs, expected outputs included, and the exact match does
  not show that the rules were inferred from the training pairs.
- **The model's segmentation did not follow the dataset.** On its training
  side, the solver's log shows the model's declarations equal to the
  dataset's, but 32 training instances where the dataset has 35: six
  instances for the fifth training pair's five cells, and one for the
  seventh's. Version 2's rules needed one instance per cell. The analyzer does
  not check the instances against the training grids, although the
  [README](../README.md#8-visualize-output-instance) says that a training
  mismatch stops the run. With the item above, the exact match does not show
  that the per-cell model worked. Suggested, not applied: replay each training
  pair from the model's instances and stop on a mismatch, as the README
  describes, or correct the README. `/arc-debug 27a28665` can examine the
  run's log in full.
- **Messages are not JSON-only.** `src/lib/llm.ts`, `src/analyzer.ts`, and
  `src/visualizer.ts` wrap JSON in text labels such as `few_shot:`,
  `train_dataset:`, and `input_x:`, while the ARC instructions require every
  message to parse as one JSON document. Suggested, not applied: build each
  message with `JSON.stringify` of one data object.
- **Test-pair facts.** Before this dataset existed, `arc/README.md` held a
  paragraph from an earlier session describing a `dataset.27a28665.json` that
  was never committed, including facts about this puzzle's test pairs and an
  earlier rule set. The caller had read it earlier in this session, while
  editing the README for the canvas-size change in `f771c15`, before this
  invocation. The worker was told not to read it and replaced it by script
  without reading it, and nothing from it reached the worker, the dataset, or
  the run. The worker read the test pairs while annotating version 1, as its
  profile directs, before the caller sent that version back; it chose
  version 2 by training-only criteria and froze it before checking it against
  the test pairs.
- **Comments in declarations.** Resolved on 6-Nov-2026: the user decided that
  natural-language `#` comments may reach the model only as part of
  `declarations`, and the ARC instructions now say so. Datasets with and
  without such comments both follow them, so nothing needs to change.
- **Workflow timeout.** Resolved on 6-Nov-2026: at the user's request, the
